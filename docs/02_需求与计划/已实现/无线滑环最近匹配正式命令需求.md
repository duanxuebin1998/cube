# 无线滑环最近匹配正式命令需求

日期：2026-05-23

## 1. 需求背景

当前 CPU2 已提供本地串口调试命令 `SPR`，用于按 RSSI 近距离规则匹配最近的无线滑环从机。该命令会扫描 CH9141K 从机候选，选择信号最强且满足阈值和差值条件的设备，连接成功后保存为 CH9141K 默认连接。

现有 `SPR` 只能通过 CPU2 调试串口触发，不能通过 CPU3 菜单或 CPU2/CPU3 共享命令通道统一下发。现场维护时希望把“匹配最近无线滑环”做成一个正式命令，使维护人员可以在显示端或内部命令入口直接触发。

## 2. 需求目标

新增一个 CPU2/CPU3 共享的正式命令：匹配最近无线滑环。

该命令应复用 CPU2 现有 `WirelessPairing_RunByRssi()` 流程，不重新实现扫描、RSSI 选择、连接、默认连接保存和透传链路探测逻辑。

命令触发后，CPU2 应执行与 `SPR` 等价的近距离匹配流程：

1. 接管 UART6，并让 CH9141K 主机模块进入 AT 配置流程。
2. 扫描无线滑环从机候选。
3. 按 RSSI 近距离规则选择最近候选。
4. 连接目标从机。
5. 保存默认连接。
6. 复位模块并恢复透传。
7. 探测无线主机和从机链路。
8. 输出匹配结果和失败原因。

匹配完成后，CPU2 应把匹配状态和从机 MAC 通过 CPU2->CPU3 输入寄存器发布给 CPU3。CPU3 根据 CPU2 发布的设备状态显示“匹配中”、匹配成功后的从机 MAC，或匹配失败后的错误码，形成现场操作闭环。

## 3. 使用场景

### 3.1 维护人员现场匹配

维护人员进入 CPU3 维护或调试菜单，选择“匹配无线滑环”后，设备自动匹配最近的目标无线滑环从机。

### 3.2 上位或内部命令触发

上位机或内部控制逻辑通过 CPU2/CPU3 共享 `command` 寄存器写入新增命令码，CPU2 主循环按正式命令调度执行匹配。

### 3.3 保留调试串口入口

CPU2 调试串口 `SPR` 继续保留，用于台架调试和串口日志验证。正式命令与 `SPR` 复用同一底层匹配函数，避免两套行为不一致。

## 4. 功能范围

本需求包含：

- 新增 CPU2/CPU3 共享命令码。
- CPU2 主循环正式命令分发支持该命令。
- CPU3 菜单增加无参命令入口。
- CPU3 通过现有 `send_cpu2_command()` 写入 CPU2 `command` 寄存器。
- CPU2 执行现有 RSSI 最近匹配流程。
- CPU2 发布无线滑环匹配运行态结果、从机 MAC 和失败错误码。
- CPU3 匹配命令下发后退出罐上操作覆盖页，收到 CPU2 匹配中状态后显示“匹配中”，收到成功结果后显示两行从机 MAC，收到失败结果后显示错误码。
- 匹配期间状态、日志、失败恢复和 UART6 恢复行为明确化。
- 同步升级 CPU2/CPU3 共享协议版本，并更新协议变更记录。

本需求不包含：

- CPU3 显示扫描候选列表。
- CPU3 显示匹配进度条或阶段状态。
- 手动选择某个 MAC 或某个扫描序号。
- 按蓝牙名称匹配。
- 新增无线滑环 MAC、名称、RSSI 的持久化参数。
- 配置无线滑环从机模块。

## 5. 命令定义

新增命令：

| 项目 | 建议值 |
| --- | --- |
| 命令枚举 | `CMD_PAIR_NEAREST_WIRELESS_SLIPRING` |
| 命令值 | `117` |
| 命令类别 | 调试/维护类命令 |
| 是否带参数 | 否 |
| CPU2 执行动作 | 调用 `WirelessPairing_RunByRssi()` |
| CPU3 入口 | 维护或调试菜单无参命令 |

选择 `117` 的原因：

- 当前 `CommandType` 中 100 到 199 用于调试、标定和维护类命令。
- 现有 `CMD_CALIBRATE_WATER` 使用 `116`。
- `117` 不占用现有命令值，也不改变已有命令数值。

## 6. 状态与触发条件

### 6.1 允许触发状态

建议只允许在以下状态触发：

- `STATE_STANDBY`
- `STATE_ERROR`
- `STATE_MAINTENANCEMODE`

匹配过程会临时中断 UART6 透传链路，不应在测量、运动、标定或传感器通信过程中直接执行。

### 6.2 测量中触发规则

如果测量或运动过程中收到该正式命令，系统应按现有命令切换机制处理：

1. 当前流程检测到命令切换请求后退出。
2. 主循环取出新增命令。
3. CPU2 执行无线滑环最近匹配。

如果当前流程无法及时响应命令切换，应保持现有机制，不为本需求新增强制中断电机或强制抢占 UART6 的逻辑。

### 6.3 重复触发规则

匹配命令执行期间再次收到同一命令时，默认按现有重复命令处理逻辑执行，不要求新增自身打断自身能力。

## 7. CPU2 功能需求

### 7.1 正式命令分发

CPU2 `ProcessMeasureCmd()` 应识别 `CMD_PAIR_NEAREST_WIRELESS_SLIPRING`。

该命令不应走通用 `MeasureStart()` 初始化流程，原因是：

- 无线滑环匹配只需要 UART6 和 CH9141K AT 配置。
- 不需要电机初始化。
- 若电机或编码器异常，不应阻止维护人员执行无线滑环匹配。

建议像 `CMD_CANCEL_MEASUREMENT` 一样，在 `MeasureStart()` 前单独处理。

### 7.2 底层流程复用

CPU2 正式命令应直接复用：

```c
WirelessPairing_RunByRssi();
```

不得另写一套扫描、RSSI 选择、连接保存流程。

### 7.3 返回和错误处理

匹配失败时，CPU2 应保持现有 `WirelessPairing_Finish()` 行为：

- 打印明确失败阶段和错误码。
- 尝试复位 CH9141K 模块。
- 恢复 UART6 透传。
- 将 `device_status.error_code` 置为匹配失败错误码，并将 `device_status.device_state` 置为 `STATE_ERROR`。

匹配流程应同步发布设备状态和运行态结果：

- 匹配开始时，CPU2 将 `device_status.device_state` 置为 `STATE_WIRELESS_PAIRING`。
- 匹配成功且 MAC 有效时，CPU2 将 `device_status.device_state` 置为 `STATE_WIRELESS_PAIRING_OVER`。
- 匹配失败时，CPU2 将 `device_status.error_code` 置为失败错误码，并将 `device_status.device_state` 置为 `STATE_ERROR`。
- 匹配结果通过运行态输入寄存器发布，不写入参数区。
- 更细的失败阶段文本仍通过 CPU2 串口日志定位。

### 7.4 当前命令状态

CPU2 主循环执行该正式命令时，`current_command` 应能反映当前正在执行的命令，便于 CPU3 或日志判断系统不是空闲状态。

命令结束后，按现有主循环规则清除 `current_command`。

## 8. CPU3 功能需求

### 8.1 菜单入口

CPU3 在维护/调试菜单中增加一个无参菜单项：

- 中文：`匹配无线滑环`
- 英文：`Pair Wireless`

该菜单项执行后，通过现有无参命令路径下发新增命令码。

### 8.2 操作码映射

CPU3 需要新增对应 `COM_NUM_*` 操作码，并在无参命令映射表中映射到：

```c
CMD_PAIR_NEAREST_WIRELESS_SLIPRING
```

### 8.3 页面反馈

CPU3 下发匹配命令后应退出罐上操作菜单覆盖页，让普通设备状态页按 CPU2 发布的设备状态显示匹配流程：

- CPU2 发布 `STATE_WIRELESS_PAIRING` 时，设备状态显示“无线滑环匹配中”。
- CPU2 发布 `STATE_WIRELESS_PAIRING_OVER` 且 `mac_valid != 0` 时，设备状态显示“无线滑环匹配完成”，并显示两行 MAC：
  - `AA:BB:CC`
  - `DD:EE:FF`
- CPU2 发布匹配失败时，设备状态切到 `STATE_ERROR`，CPU3 按现有故障页显示 `device_status.error_code`。
- CPU3 应轮询 `WirelessPairingStatus` 所在输入寄存器区间，用于在匹配完成状态下显示 MAC。
- 成功结果由设备状态页承载，不再依赖“匹配成功”覆盖页反复显示。

### 8.4 字库检查

如果 CPU3 新增中文显示文案，必须检查显示字库覆盖。新增文案中可能涉及的汉字包括：

- 匹
- 配
- 无
- 线
- 滑
- 环
- 最
- 近

若字库缺字，应先列出缺失字并等待补字库后再合入显示文案。

## 9. 协议和兼容性

新增 CPU2/CPU3 共享命令码属于协议可见行为变化。

需要同步修改：

- CPU2 `CommandType`
- CPU3 `CommandType`
- CPU2/CPU3 `MeasurementResult`
- CPU2/CPU3 输入寄存器映射
- `DEVICE_PROTOCOL_VERSION`
- CPU2/CPU3 协议变更记录
- 版本改动与测试方案
- `CHANGELOG.md`

本需求落地时协议版本升级为：

```c
#define DEVICE_PROTOCOL_VERSION 5u
```

兼容性要求：

- CPU3 新版本不应与旧 CPU2 混用，因为旧 CPU2 不识别新增命令。
- 协议版本不一致时，继续按现有 CPU3 协议兼容检查机制提示不兼容。
- 不新增保持寄存器地址，不改变现有 `command` 寄存器宽度和写入方式。
- 输入寄存器末尾追加运行态 `WirelessPairingStatus`，不移动既有输入寄存器地址。

## 10. 版本要求

本需求落地会改变 CPU2 和 CPU3 可见行为，最终版本口径如下：

- CPU2：`V1.8.1.0 -> V1.9.0.0`。
- CPU3：`V1.6.0.0 -> V1.7.0.0`。
- 协议版本：`4 -> 5`。
- `V1.8.0.0` 是 CPU2 无线滑环本地调试能力的阶段性开发口径，不单独发布。

提交前需要补齐：

- `CHANGELOG.md`
- `docs/01_协议与寄存器/CPU2_CPU3协议变更记录.md`
- `docs/00_构建与版本/版本改动与测试/` 下的改动与测试方案

## 11. 日志要求

CPU2 串口日志应能区分：

- 正式命令触发无线滑环最近匹配。
- `SPR` 调试串口触发无线滑环最近匹配。
- 扫描开始。
- 候选数量。
- RSSI 选择通过或失败。
- 连接目标。
- 保存默认连接。
- 复位模块。
- 主机和从机透传探测。
- 最终结果。

日志应继续使用现有中文字段格式，便于现场检索。

## 12. 验收标准

### 12.1 静态检查

- CPU2 和 CPU3 的 `CommandType` 命令值一致。
- 新增命令不改变已有命令值。
- CPU3 菜单操作码能映射到新增命令。
- CPU2 `ProcessMeasureCmd()` 能分发新增命令。
- 新增命令不走电机 `MeasureStart()` 初始化。
- `DEVICE_PROTOCOL_VERSION` 两边一致。
- 协议变更记录、版本记录和测试方案同步更新。

### 12.2 构建验证

- CPU2 构建通过。
- CPU3 构建通过。
- 版本检查脚本通过。

### 12.3 台架验证

1. 只打开目标从机，通过 CPU3 菜单触发匹配，CPU2 完成连接并保存默认连接。
2. 断电重启后，CH9141K 主机自动连接上次匹配的从机。
3. 同时打开多个从机且 RSSI 差值不足时，CPU2 拒绝自动匹配，不静默误配。
4. 匹配失败后，CPU2 能复位 CH9141K 并恢复 UART6 透传。
5. 匹配成功后，无线主机和从机探测成功。
6. CPU2 调试串口 `SPR` 仍可正常使用。

### 12.4 兼容验证

- CPU3 新版本连接旧 CPU2 时，协议版本不匹配应按现有机制提示。
- CPU2 新版本连接旧 CPU3 时，不影响旧 CPU3 原有命令使用。

## 13. 非目标

第一版不实现以下内容：

- CPU3 实时显示扫描候选。
- CPU3 显示 RSSI、名称或扫描阶段明细；成功 MAC 显示已纳入本需求。
- CPU3 手动选择候选。
- 持久化保存无线滑环默认 MAC 参数。
- 通过设备端配置无线滑环从机模块。
- 改变 `SPS`、`SPN=<name>`、`SPC` 调试命令行为。

## 14. 已确认事项

1. CPU3 菜单入口放在维护/调试菜单的无参命令区域。
2. 中文文案使用 `匹配无线滑环`，英文文案使用 `Pair Wireless`。
3. CPU3 下发后退出罐上操作覆盖页，不使用本地倒计时或本地固定提示；匹配中和匹配完成均由 CPU2 设备状态驱动显示。
4. 匹配失败时 CPU3 显示 CPU2 错误码，详细失败阶段仍看 CPU2 串口日志。
5. 第一版只按 RSSI 自动选择，不提供 CPU3 候选列表和手动选择。
