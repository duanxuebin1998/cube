## 1. 已确认的实施边界

| 项目 | 决定 |
| --- | --- |
| `<30.0 pF -> 99999.9 pF` | 这是产品特殊处理，保持现状；本方案不得删除、迁移或改变该规则，也不清理既有 `zero_cap` |
| DSM CPU1 固件 | 不在本方案范围内；不修改 `CB/CD`、`Cb`、ACK 或 CPU0 交互语义 |
| CUBE 范围 | 只改 CPU2 的传统 DSM UART6 文本协议适配及其 CUBE 侧测试、文档 |
| CPU3 和共享协议 | 不改变 CPU2/CPU3 共享字段、命令、寄存器及 `DEVICE_PROTOCOL_VERSION` |
| `CX` | 本批不实现；完成可靠 `Cv=05.40` 识别后仍作为后续可选能力 |
| 方案阶段门禁 | 当前只形成详细方案，不改固件、不升版、不暂存、不提交 |

CPU1 已知问题仍然是现场兼容风险，但不能把 CUBE 侧严格 ACK 校验表述成“已经证明 CPU0 模式切换成功”。本方案只保证 CUBE 收到的帧与当前事务契约一致。

## 2. 目标和完成标准

### 2.1 目标

1. 将 UART6 接收从“遇到第一个 `LF` 结束”改为“按当前命令允许的响应形状和精确长度完成”。
2. 支持 `Cv/CV` 的 6 字节无 CRLF 版本帧，建立运行期 DSM 版本/能力上下文。
3. 对 ACK、BCC、CRLF、固定标识、数字字段和响应长度执行统一校验。
4. 把业务字段解析放入同一次有界事务重试中，避免通信成功但解析失败后直接结束调用。
5. 保持现有公开业务 API、返回值主链和低电容特殊处理不变，减少上层测量流程回归。

### 2.2 完成标准

- 20 组上游 golden frames 中与 CUBE 已用命令及版本查询相关的向量全部有确定结果。
- BCC 为 `0x00`、`0x0A`、`0x0D` 时都按原始字节处理，不被当作字符串终止或帧结束。
- `Cv/CV` 收满 6 字节即进入校验，不等待 `LF`。
- ACK 只接受精确的 `25 0D 0A`，不再使用 `strstr(response, "%")`。
- 短帧、超长帧、错误终止符、错误 BCC、错命令响应、非法数字字段均进入有界重试。
- `STATE_SWITCH` 立即退出，不记为通信故障；最终失败仍返回现有错误码体系中的具体错误。
- CPU2 clean-first 构建通过；真实 DSM 台架覆盖正常、坏帧、版本帧和重试场景。

## 3. 当前实现与目标分层

当前链路把 DMA 接收、LF 截帧、BCC 校验、特殊错误映射、重试和业务解析分散在不同层级：

```text
业务 API
  -> UART6_SendWithRetry()
      -> UART6_SendCommand()
          -> UART6_WaitTextReceiveDma()：遇 LF 提前结束
          -> 通用 BCC 校验
  -> 各业务函数再次检查长度/字段并解析
```

目标链路按四层收敛：

```text
业务 API（签名保持不变）
  -> DSM_ExecuteTransaction()：统一尝试次数、日志和错误传播
      -> DSM_ReceiveExpectedFrame()：只按响应形状和精确长度收原始字节
      -> DSM_ValidateFrame()：长度、literal、CRLF、BCC、标识和字段格式
      -> 命令解析回调：把值写入本次临时结果
  -> 事务成功后一次性发布到输出参数/全局数据
```

关键原则是先完成并验证整个事务，再写业务输出；失败尝试不得留下部分更新的数据。

## 4. 数据结构设计

### 4.1 响应形状 `DsmResponseShape`

建议字段：

| 字段 | 用途 |
| --- | --- |
| `frame_kind` | `LITERAL`、`BCC_PAYLOAD`、`NO_RESPONSE` |
| `exact_length` | 当前形状的精确总长度，例如 ACK=3、版本=6、普通值=11、角度/错误=19、密度=27 |
| `payload_length` | 参与 BCC 的字节数；ACK 不使用 |
| `terminator_length` | 0 或 2；版本帧为 0，其余常规 BCC 帧为 2 |
| `literal` | ACK 等固定帧的完整字节值 |
| `discriminator` | 根据首字节或固定字段区分正常帧与 19 字节错误帧 |
| `validator` | 命令专属的固定字段和数字格式校验函数 |

所有原始帧字段使用 `uint8_t` 和显式长度，禁止用 `strlen()`、`strstr()` 或 NUL 终止符判断帧边界。只有日志输出时才生成单独的安全字符串视图。

### 4.2 命令规格 `DsmCommandSpec`

每个已使用命令至少绑定：

| 命令 | 正常形状 | 可替代形状 | 超时策略 | 解析器 |
| --- | --- | --- | --- | --- |
| `CD`、`CB`、`CL` | 精确 ACK 3 字节 | 无 | 现有普通超时 | exact ACK |
| `Cv`、`CV` | 版本 6 字节、无 CRLF | 无 | 版本探测超时 | 版本文本和 BCC |
| `CN` | 编号 11 字节 | 错误 19 字节 | 现有普通超时 | `N/E/e + 7位字段` |
| `Cl` | 水测量 11 字节 | 错误 19 字节 | 现有普通超时 | `D + 7位数值` |
| `Cb` | 液位频率 11 字节 | 错误 19 字节 | 现有普通超时 | `F + 7位数值` |
| `Cd` | 密度数据 27 字节 | 错误 19 字节 | 现有普通超时 | `F/D/T` 固定位置字段 |
| `Ch` | 角度 19 字节 | 错误 19 字节 | 500 ms、3 次、间隔 300 ms | `A/B` 两组固定宽度字段 |
| `CK` | 电压 11 字节 | 无 | 现有普通超时 | `e/E + 7位数值` |

正常帧和错误帧同为 19 字节时，必须先看固定标识/布局，再选择解析器，不能仅用长度区分。

### 4.3 版本档案 `DsmVersionProfile`

建议至少保存：

- `profile_id`：`LEGACY_UNKNOWN`、`V3_02`、`V4_X`、`V5_0`～`V5_4`、`V6_X`、`V5_0_AMBIGUOUS`。
- `cpu1_version[6]`：保留 5 字节版本载荷和结束 NUL，供日志显示，不参与收帧。
- `combined_prefix[3]`：`CV` 的两字符前缀；未读取时为空。
- `capability_bits`：只记录协议矩阵已证明的命令能力。
- `water_value_kind`：历史 ADC 电压、FDC2214 电容或未知。
- `identified`、`ambiguous`：区分可靠识别、已知歧义和兼容回退。

`05.00 + 08` 仍不能区分标准 V5.0 与 V5.0-Lemis，应归为 `V5_0_AMBIGUOUS`，只开放两条维护线共同且 CUBE 已使用的命令。不得据此启用维护线专属动作。

### 4.4 运行期上下文 `DsmSessionContext`

上下文只保存在 RAM，不增加参数存储字段，不改变共享协议。建议在以下时机清空：

- CPU2 启动和 UART6 初始化；
- 重新执行 `DetectSensorType()`；
- 无线链路断开后重新识别传感器；
- 连续通信失败触发既有传感器重新识别流程时。

当前 `g_deviceParams.sensorSoftwareVersion` 已属于设备参数结构，参与持久化和 CPU2/CPU3 Modbus 同步，但最新程序没有把 DSM `Cv/CV` 识别结果写入该字段。它的既有编码语义、历史值迁移和 CPU3 展示口径均未为 DSM 多维护线定义，因此本批不得为了少加一个 RAM 字段而直接复用。若以后确需在 CPU3 展示 DSM 版本，应另行确定编码、无效值、迁移和共享协议兼容性。

## 5. 定长接收算法

### 5.1 接收缓冲和完成条件

1. 根据 `DsmCommandSpec` 计算本事务最大允许长度，并额外预留 1 字节用于检测超长帧。
2. 在发送命令前启动 DMA，避免快速应答丢头；保持当前先 RX 后 TX 的顺序。
3. 轮询 DMA 已接收长度，不扫描 `LF`、`CR` 或 NUL。
4. 收到足以判别响应形状的字节后确定 `exact_length`；例如 `Cd` 的正常帧为 27 字节，已知错误布局为 19 字节。
5. 收到 `exact_length` 后进入有界尾部保护阶段，只额外接收 1 字节用于识别超长帧；该阶段不得复用整笔业务超时。
6. 尾部保护时间必须由真实无线透传的字节间隙和残帧行为确定，并用独立常量命名；当前没有台架证据，不能把原建议的 `3 ms` 写成已确定参数。
7. 超时时 0 字节返回 `SENSOR_DEVICE_COMM_TIMEOUT`，有部分字节返回 `SENSOR_RESP_FORMAT_ERROR`。
8. UART ORE/FE/NE、DMA 状态异常和命令切换沿用现有具体出口。

尾部保护策略在实施前保留一个台架决策门：若透传链路能证明帧内最大间隙上限，则按实测值加裕量设置；若链路会长时间分片且无法建立可靠上限，则改为“达到精确长度后立即完成，本次停止 DMA，下一事务 drain 对残留字节做诊断记录”。无论选哪种策略，等待都必须有界，且不能把控制字符当终止符。

### 5.2 校验顺序

校验顺序固定为：

1. 精确长度；
2. literal 或响应标识；
3. CRLF（仅要求带终止符的形状）；
4. BCC；
5. 固定位置标识和符号；
6. 数字字段逐字符格式；
7. `strtof/strtoul` 转换结束位置和有限值检查；
8. 命令专属业务范围。

`Cl` 的 `<30.0 pF -> 99999.9 pF` 在上述协议校验全部通过后继续执行，保持当前产品特殊处理不变。

## 6. 版本识别流程

版本识别必须在定长接收可用后接入 `Sensor_ProbeDsmSensor()`：

1. 发送 `Cv`，按 6 字节形状接收并校验 BCC。
2. `Cv` 成功时映射 CPU1 版本；必要时再发送 `CV` 读取组合前缀进行交叉检查。
3. 已识别版本写入 RAM 上下文，再执行现有 `CN` 读取和 `CD` 密度模式切换。
4. `Cv` 无响应但 `CN` 能通过时，归类为 `LEGACY_UNKNOWN`，保留当前 `CN -> CD` 探测兼容路径，避免一次升级直接淘汰 V3.02 以前设备。
5. `LEGACY_UNKNOWN` 和 `V5_0_AMBIGUOUS` 不开放任何新增版本专属能力；尤其不得发送 `CX`。
6. `Cv` 返回格式错误、坏 BCC 或未知版本文本时进入有界重试；重试后仍失败则记录“版本未可靠识别”，但不要把它伪装成明确版本。

第一版只让版本档案约束帧形状和新增能力，不改变当前已用命令集合的业务入口。是否进一步按版本禁止 `Cl` 或模式命令，应有单独的现场维护线清单和产品决定，不能在本次结构整改中顺带扩大行为变化。

## 7. 严格解析和重试

### 7.1 重试边界

将解析器回调放入 `DSM_ExecuteTransaction()` 的单次尝试内。以下错误继续下一次尝试：

- 无响应、部分帧、超长帧；
- UART/DMA 传输错误；
- BCC、CRLF、literal、标识、数字字段或字段范围错误；
- 收到本命令不允许的帧形状；
- 已有错误帧映射返回的传感器错误，第一版保持当前重试语义，避免行为回退。

以下情况立即退出：

- `STATE_SWITCH`；
- 入参为空、输出缓冲不足等本地编程错误；
- 事务规格不存在或版本档案明确禁止的新增能力。

### 7.2 数据发布

- 每次尝试解析到局部临时结构，不直接写 `dsmsensor_data` 或调用方输出。
- 只有整帧校验、全部字段解析和范围检查通过后才一次性提交。
- 最终失败时保持调用前输出不变；不得发布前一次尝试的部分字段或旧 DMA 缓冲内容。

### 7.3 日志

重试日志至少包含：命令、版本档案、期望形状、实际长度、失败阶段、UART 错误和原始 HEX。禁止用 `%s` 直接打印可能含 NUL/BCC 控制字符的原始帧。

本方案不顺带改变 `Ch` 冷唤醒日志等级和 `CK` 高低压文案；两项可在事务层稳定后单独处理。

## 11. 版本和兼容性影响

- 实施会改变 CPU2 的 DSM UART6 收帧和解析行为，因此应从复核时 CPU2 `V1.36.2.0` 基线提升 CPU2 固件版本；具体目标版本在实施收口时确定。
- 不修改 CPU3 固件行为；只要 CPU2/CPU3 共享字段和语义不变，就保持当前 `DEVICE_PROTOCOL_VERSION=31`。
- 对合法现有帧应保持业务结果不变；对过去被宽松接受的短帧、错字段、模糊 ACK 和尾随垃圾将改为拒绝并重试，这是预期收紧。
- 新增版本查询会增加开机 DSM 探测时长。应实测正常 V5.4、`Cv` 无响应历史设备和无线断链三种上限，并确保不破坏系统启动看门狗与命令切换响应。
- CPU1 内部 ACK、HardFault 和 `Cb` 新鲜度不由本方案解决；即使 CUBE 事务测试全部通过，也不能宣称这些传感器端问题已经闭环。

## 12. 当前不做和后续项

- 不修改或重新发布 DSM CPU1 固件。
- 不删除 `<30.0 pF -> 99999.9 pF` 特殊处理，不清理历史参数。
- 不实现 `CX`、`CR`、`CS` 或其它当前未调用命令。
- 不处理 `CK` 高低压日志语义和 `Ch` 冷唤醒首轮日志等级。
- 不新增 CPU2/CPU3 共享协议字段来上报 DSM 版本；如以后确需 CPU3 展示，再单独评估协议升版。
