# CUBE 高价值问题分阶段整改审批方案

编制日期：2026-07-23

实施状态：部分实施；第1批C-10与第2批C-31已进入CPU2 V1.32.0.0，第2批C-33仅补区间测量失败不发布，其余批次仍待审批。

## 1. 审批结论摘要

建议采用“一个问题包、一次独立验证、一个独立提交”的方式推进，不把全部安全改动合并成一个大版本。

| 批次 | 问题 | 主要收益 | 实施风险／依赖 | 建议审批结论 |
| --- | --- | --- | --- | --- |
| 第 0 批 | V1.31.1.0、C-01、C-02 | 关闭已有代码整改的证据缺口 | 主要是目标板、畸形帧和副作用验证 | 立即执行，不新增功能代码 |
| 第 1 批 | C-10 | 消除合法 128～200 点导致的负索引写栈 | 代码已落地，仍需canary和目标板边界验证 | 已实施，未完成台架关闭 |
| 第 2 批 | C-31、C-33 | 让传感器明确失败能够及时终止测量 | `0xFF`映射已冻结；C-33尚未覆盖全部裸`EnableDensityMode()`调用 | C-31已实施；C-33部分实施 |
| 第 3 批 | C-09、C-30 | 恢复扭力碰撞输入的新鲜度与可信性 | 必须取得正式帧契约或现场抓包，不能猜 CRC／帧头 | 先批准协议冻结和设计，满足依赖后实施 |
| 第 4 批 | C-24、C-34 | 消除地址 0 回包、总线碰撞和非预期写入 | 需批准 DSM 对外广播语义 | CPU2 板间可直接批准；DSM 需二选一 |
| 第 5 批 | C-05、C-04、C-11 | 保证取消、运动、探底的终态和结果真实 | 需到位容差、停机策略、探底降级决策 | 原则批准，决策冻结后分四步实施 |
| 第 6 批 | C-42A、C-42B；建议带 C-42D/E/F/H | 建立所有运动入口不可绕过的边界 | 强依赖机械边界、位置源、制动距离和真实台架 | 原则批准，机械参数未签字前不得编码 |
| 第 7 批 | C-41 | 全局阻塞故障能及时打断长循环 | 需阻塞故障分类表和第 5 批单次停机终态 | 建议批准框架，先覆盖高风险循环 |
| 第 8 批 | C-08 | CPU2 前台失活时真正触发 IWDG | 依赖长流程有可信进度点；必须先观察后强制 | 放在 C-41／C-42 后实施 |
| 可选批 | C-37、C-45、C-38 | 降低 CPU3 阻塞和显示异常 | 安全收益低于上述问题 | 本轮默认延期，可单独批准 |

第0～2批已形成部分代码增量，但在目标板、canary和故障注入完成前不得标记闭环。若继续批准完整安全链，推荐按“终态真实性 → 阻塞故障打断 → 运动边界 → 看门狗强制”的顺序推进。

## 2. 本方案边界

### 2.1 本轮包含

1. 对高价值问题给出函数级整改方向、依赖、错误语义、验收矩阵、版本影响和回滚条件。
2. 把代码修复、静态验证、目标板验证和真实机械台架分成不同证据层。
3. 明确必须由产品、机械、现场或协议资料确认的事项，禁止由软件实现阶段自行代决。

### 2.2 剩余方案不包含

- 除已明确记录的C-10、C-31和C-33区间测量失败出口外，不把其它方案条目写成已实现。
- 不新增共享字段、错误码、参数槽或协议地址。
- 不因方案批准自动执行后续批次的Git暂存、提交或推送。
- 不把 C-01～C-45 全部纳入同一整改周期。
- 不把 clean-first 构建或静态脚本通过写成硬件安全闭环。

## 3. 总体依赖和共同门禁

### 3.1 依赖关系

| 前置项 | 后续项 | 原因 |
| --- | --- | --- |
| C-31 | C-33 | `0xFF` 必须先被识别为失败，模式切换调用方才能正确传播错误 |
| 扭力正式帧契约 | C-30、C-09 | 只有通过正式帧契约的样本才能定义“新鲜” |
| C-05 单次停机终态 | C-04、C-11、C-41、C-42 | 所有取消、故障和边界出口都必须只停一次并证明停稳 |
| C-04 新鲜位置验收 | C-42 | 边界和到位不能继续使用未证明新鲜的缓存位置 |
| C-41 有界打断 | C-08 强制门控 | 长同步流程没有可信进度点时，健康票据会误复位或掩盖死循环 |
| C-42H 参数组合校验 | C-42A/B | 不能用非法 `tankHeight`、`blindZone`、`maxDownDistance` 计算安全包络 |

C-10 和 C-24/C-34 与运动安全主链基本独立，可并行实施，但仍需独立构建和提交。

### 3.2 每批统一阶段门禁

| 门禁 | 必须产物 | 退出条件 |
| --- | --- | --- |
| G0 基线 | HEAD、版本、工作树、目标文件清单 | 不覆盖其它在途修改 |
| G1 契约 | 输入、输出、状态、错误优先级、禁止副作用 | 所有待决事项已有签字结论 |
| G2 纯逻辑 | 边界向量、golden frame、纯函数或主机测试 | 异常输入结果确定且无部分提交 |
| G3 固件 | CPU2／CPU3 按影响范围 clean-first 构建 | 编译、链接、编码、版本门禁通过 |
| G4 目标板 | 串口、外设、FRAM、IWDG 或显示验证 | 静态结论得到目标板证据 |
| G5 机械台架 | 速度、距离、边界、故障注入和停机证据 | 所有安全关闭条件均有记录 |
| G6 发布 | 版本头、CHANGELOG、版本测试方案、问题总账 | 代码、文档、版本和证据一致 |

任一批未通过本批门禁时，只回滚该批，不得把后续批次的成功用来抵消前置失败。

## 4. 第 0 批：既有整改先收口

### 4.1 V1.31.1.0

`684d8054` 已把 CPU2 TIM4 从约 2 s 调整为 250 ms，并以 8 分频保持继电器、AO 和 UART 恢复约 2 s 周期；`490820b` 已加入的 `RETTOBASE` 喂狗门禁继续保留。线程态前台死锁／阻塞时，TIM4 从 thread 进入，`RETTOBASE` 仍可为 1，因此它不能证明 CPU2 前台推进，C-08 保持“部分整改”。

本批应补：

- 目标板测量 TIM4、业务 2 s 节拍和 IWDG 实际窗口，覆盖 LSI 偏差。
- 主循环卡死但 TIM4 正常、UART ISR 压力、全局关中断三类注入。
- 持久参数写门禁的真实 CPU2/CPU3/DSM/LH 请求矩阵和 FRAM 失败。

### 4.2 C-01／C-02

这两项不再设计新代码，先验证已有门禁。

| 问题 | 用例 | 必须断言 |
| --- | --- | --- |
| C-01 FC03 | 数量 0、1、125、126、127、128、346、347；表首、表尾、表尾＋1和跨表 | 仅 1～125 且地址跨度合法时进入组包 |
| C-01 FC04 | 数量 0、1、125、126、497、498、499、1000、1001、2632 | 非法数量不组超长响应、不启动越界 DMA |
| C-01 内存 | 发送区和临时数组前后放 canary；回归 CPU3 普通组 114、点阵组 96 | canary、相邻内存和后续事务不变；合法最大组行为不回归 |
| C-02 数量／对齐 | 0、1、2、3、122、123、124、253；奇／偶起始地址 | 只有偶地址、偶数量 2～122 可进入解码 |
| C-02 帧形 | `byteCount=0/2N-1/2N/2N+1/255`；实际长度为期望−1／期望／期望＋1 | 只有精确 `byteCount=2N` 且实际长度精确匹配时合法 |
| C-02 残留／副作用 | DMA 尾部预填 `0xA5` 后发送 CRC 正确短帧 | 不消费旧 DMA 残留；RAM、镜像、硬件、保存标志、FRAM 全部不变 |

退出条件：目标板记录完整后才能把 C-01、C-02 移到已闭环；失败则恢复为代码整改项。

## 5. 第 1 批：C-10 区间密度点规划越界

### 5.1 目标

消除 `BuildPoints_Interval_Exact()` 中 `int8_t i` 在合法 128～200 点回绕为负数、负索引写入 `points01[200]` 的确定性风险。

### 5.2 函数级方案

涉及 `LTD_MAIN_CPU2/Application/Src/measure_density.c`。

1. 把点数、索引和容量统一为 `uint32_t` 或 `size_t`，禁止有符号窄类型承载 200 点上限。
2. 将 `BuildPoints_Interval_Exact()` 增加 `out_capacity`；入口先校验：
   - `out_p01`、`out_n` 非空；
   - `1 <= requested_count <= MAX_MEASUREMENT_POINTS`；
   - `requested_count <= out_capacity`；
   - 上下边界和参数组合合法。
3. `count==0` 或 `count>200` 返回现有 `MEASUREMENT_DENSITY_PLAN_INVALID`，删除静默钳位。
4. 任何失败先令 `*out_n=0`，不得留下可被调用方误发布的部分点数。
5. 使用统一 append helper 或在每次写入前证明 `index < out_capacity`；最后一个端点修正同样经过容量门禁。
6. 本批只修运行时规划安全；参数层通用原子事务仍归 C-03，不顺带扩大范围。

### 5.3 验证和关闭标准

| 输入 | 预期 |
| --- | --- |
| 0、201、`UINT32_MAX` | 明确拒绝，`out_n=0`，输出区和前后 canary 不变 |
| 1、2、3、126、127 | 正常生成，首尾、方向和单调性正确 |
| 128、129、199、200 | 有界返回，无负索引、无栈破坏 |
| 上行／下行、取消、中途测点失败 | 发布点数不超过容量，不误发布部分剖面 |

关闭必须包含：纯规划边界测试、数组 canary、目标 Release 构建和 CPU2 clean-first 构建。若代码仍存在窄化转换告警或非法值仍被钳位，本批不通过。

### 5.4 版本和回滚

本批已随CPU2 V1.32.0.0实现：点数/索引改为`uint32_t`，增加`out_capacity`，非法点数不再钳位，失败保持`out_n=0`。共享协议和参数结构未变。128～200点canary与目标板回归仍未执行；出现合法1～200点结果变化、性能异常或canary破坏时，整批回滚。

## 6. 第 2 批：C-31／C-33 传感器失败传播

### 6.1 审批前冻结

LTD/V2 的第 7 字节 `0xFF` 只表达远端粗粒度失败。建议映射到现有 `SENSOR_REMOTE_INTERNAL_ERROR`，不得在没有供应商证据时猜成“不支持”“模式未就绪”等更具体原因。

### 6.2 C-31 函数级方案

涉及 `LTD_MAIN_CPU2/Services/Sensor/ltd_sensor_communication.c`。

1. 修改 `DSM_V2_CheckReply()`：完成长度、校验和、功能码检查后，`rx[6]==0xFF` 返回 `SENSOR_REMOTE_INTERNAL_ERROR`。
2. 模式、浮点和整数三类调用均先检查业务结果，再解析 `rx[2..5]`。
3. 每次尝试只解析到局部候选值；仅完整成功后一次性提交输出。
4. `0xFF` 进入现有有界重试；最终失败保留具体错误。
5. 失败帧不得更新模式、数值、valid、generation 或完成态。

### 6.3 C-33 函数级方案

涉及 `measure_density.c`、`measure.c`、`sensor.c`。

1. 两处裸调用 `EnableDensityMode()` 必须保存并检查返回值。
2. `STATE_SWITCH` 原样返回；其它失败立即停止后续规划、运动、读点和完成发布。
3. 每个测量事务只保留一个模式保障责任入口。推荐：
   - `Density_MeasureByMode_Exact()` 负责一次找液位和一次切密度模式；
   - 综合测量入口删除重复 Search／Enable；
   - 独立单点 API 保留自己的显式模式保障，但被多点流程调用时不得重复切换。
4. 首次模式失败不能被后续一次成功覆盖；调用次数应能在测试桩中断言。

### 6.4 验证和关闭标准

| 场景 | 预期 |
| --- | --- |
| 模式／浮点／整数各返回 `0xFF` | 进入远端失败重试，模式和输出不变 |
| 前两次 `0xFF`、第三次成功 | 只提交第三帧完整结果 |
| 三次均失败 | 返回 `SENSOR_REMOTE_INTERNAL_ERROR`，不发布完成 |
| 坏校验与 `0xFF` | 分别归类链路失败和远端业务失败 |
| `EnableDensityMode()` 超时／坏 ACK／`0xFF` | 无规划、无运动、无点数、无完成沿 |
| `STATE_SWITCH` | 正常取消，不新增故障，不继续第二次切换 |

C-31已随CPU2 V1.32.0.0实现：`0xFF`映射为现有`SENSOR_REMOTE_INTERNAL_ERROR`并进入有限重试，恢复日志保留最后一次错误原因。C-33目前只补充区间测量失败后立即返回、不发布空/部分点阵；`Density_MeasureByMode_Exact()`中未检查`EnableDensityMode()`返回值等剩余入口仍待后续独立整改。共享协议保持27，未新增错误码。

## 7. 第 3 批：C-09／C-30 扭力完整帧和新鲜度

### 7.1 硬前置：正式帧契约

仓库当前没有足以证明扭力模块帧头、地址、类型、长度、字节序和校验算法的正式资料。本批不得从现有“第 19／20 字节”反推完整协议。

实施前必须取得以下任一证据：

1. 供应商正式协议；
2. 已确认型号的现场抓包，覆盖零点、正负扭力、边界值、坏帧和断线；
3. 供应商 golden frames 与校验算法说明。

契约至少冻结：串口参数、精确帧长、帧头、来源／地址、类型、值偏移、符号和单位、校验范围、半帧／粘包处理。

### 7.2 函数级方案

涉及 `Core/Src/stm32f4xx_it.c`、`Services/Weight/weight.c/.h`，必要时新增无 HAL 的扭力编解码模块。

1. ISR 只记录或投递 UART4 RX 快照；帧长使用至少 16 位类型，不再在 ISR 中把任意 `>=21 B` 片段直接写入扭力。
2. 前台解析器按冻结契约处理精确帧、错位、半帧、粘包和重同步。
3. 新增内部快照语义：`value + valid + tick + generation`。
4. 只有完整合法帧才能原子更新数值、tick、generation，并只清除本模块拥有的 `WEIGHT_COMM_TIMEOUT`。
5. 坏帧只累计诊断，不刷新时间戳、不清错、不覆盖 last-valid。
6. 将 `weight_init()` 拆分为一次初始化和参数应用；测量重入不得修改通信新鲜度。
7. 上电从未收到合法帧或 `age >= 1000 ms` 时，所有依赖扭力的运动启动／继续入口拒绝或安全停止；取消、停机和安全收尾始终允许。
8. 运动启动记录本次最小 generation，运动中持续检查年龄和代际，不能仅凭启动前一次快照继续运行。

### 7.3 验证和关闭标准

| 场景 | 必须结果 |
| --- | --- |
| 上电无帧 | 首次依赖扭力的运动立即拒绝，无 1 s 伪宽限 |
| 合法帧后断线 | 999 ms 可用、1000／1001 ms 按冻结边界失效 |
| 重复 `MeasureStart()` | tick、generation、valid 均不被重置 |
| 20／21／22 B 噪声、单比特错、插删、半帧、粘包 | 不更新值和新鲜度；合法帧可正确重同步 |
| 持续坏帧超过阈值 | 报 `WEIGHT_COMM_TIMEOUT`，坏帧不能续命 |
| 运动中断线和恢复 | 按批准的 fail-safe 停止；恢复只清本模块错误 |
| tick／generation 回绕 | 无符号差值判断正确 |

关闭需要真实扭力模块、碰撞保护和运动中断链台架。若只能证明解析而未证明机械策略，本批最多关闭 C-30，不能关闭 C-09 的安全影响。

## 8. 第 4 批：C-24／C-34 地址 0 语义

### 8.1 推荐决定

| 链路 | 推荐语义 | 理由 |
| --- | --- | --- |
| CPU2↔CPU3 UART5（C-34） | 不支持广播；地址 0 全部静默丢弃 | 当前固定点对点地址 1，没有广播需求，最小改动和副作用最少 |
| CPU3 对外 DSM（C-24） | 方案 A：不支持广播，地址 0 全部静默丢弃 | 当前正式资料没有证明地址 0 是特殊单播；保守兼容 |
| CPU3 对外 DSM 备选 | 方案 B：仅批准的 FC05／FC10 广播写可执行，但绝不回包 | 只有确认旧主站需要广播写时采用 |

无论选择哪种 DSM 方案，地址 0 的读、非法功能、非法地址和异常均不得回包。

### 8.2 函数级方案

1. C-34：`SlaveCheckAddress()` 只接受固定本机地址；地址 0 按地址不匹配静默退出，不设置整机故障。
2. C-24：`DSM_CommunicationProcess()` 在入口明确形成 `unicast/broadcast` 请求属性。
3. 采用方案 A 时，地址 0 在 CRC 通过后立即静默退出，`tx_len=0` 且无读写副作用。
4. 采用方案 B 时，只允许批准的写功能继续执行；读和所有异常静默；发送层增加最终 `broadcast => no TX` 兜底。
5. 所有正常和异常组包器仍服务单播；不得依靠调用者“记得不发送”实现广播静默。
6. 更新板间协议和 DSM 对外协议卷，明确地址 0 的执行／响应矩阵。

### 8.3 验证和版本

覆盖地址 0／本机地址／其它地址 × FC01／03／04／05／10／非法功能／坏 CRC；同时检查 RAM、FRAM、硬件动作和 TX 波形。DSM 还需两台从站并联验证总线无碰撞。

C-34 通常只提升 CPU2 固件版本；C-24 只提升 CPU3 固件版本；均不改变共享字段。若现场抓包证明旧主机依赖地址 0 非标准单播，不得静默恢复旧代码，应把它转成有协议和设备范围的受控偏差重新审批。

## 9. 第 5 批：C-05／C-04／C-11 终态真实性

建议将 C-11 与取消／运动终态一起审批，但分四个小步骤实施。三者共享“首错不丢、只停一次、停稳后裁决、失败不发布完成”的基本语义。

### 9.1 公共终态对象

在 MotorControl 内建立本地终态对象，不进入共享结构：

`cause_error + stop_error + position_error + cleanup_error + stop_confirmed + arrived + cancelled`

固定优先级：

1. 停止命令、运动状态读取、VZERO 或停机 deadline 失败：对外激活停机错误并置 `motion-inhibit`；原始故障保留为因果。
2. 停稳已证明时，保留本轮首个业务／运动／驱动／位置源故障。
3. 前述无错但最终位置无效、不新鲜或超差：返回位置无效或 `POSITION_ARRIVAL_DEVIATION`。
4. 前述均成功但速度／配置恢复失败：恢复错误成为最终错误。
5. 只有无阻塞故障且停稳已证明，`STATE_SWITCH` 才是正常取消；只有停稳、到位、位置新鲜和驱动健康全部成立才发布完成。

### 9.2 C-05 取消流程

涉及 `measure.c` 的 `CMD_CancelMeasurement()`。

1. 进入时快照原故障、当前命令和取消原因；可以清命令槽，但不得先清故障。
2. `MotorCtrl_SlowStop()` 在一次取消中严格调用一次。
3. 停止、VZERO、速度恢复全部成功且原故障允许清除时，才发布 `STATE_STANDBY`。
4. 停机失败使用“停机已尝试”专用终结器，只锁存错误、发布 `STATE_ERROR` 和 motion inhibit；不得再进入 `HandleError() -> MotorCtrl_SlowStop()` 递归停机。
5. motion inhibit 同时放在命令准入和电机公共 API；重复取消幂等，新运动不得绕过。
6. 第一版不新增 `STATE_CANCELLING`，减少协议影响；如产品需要展示取消中，再另行升级共享状态。

### 9.3 C-04 运动结果

涉及 `motor_ctrl_motion_api.c`、`motor_ctrl_driver_param.c`。

1. 拆分 `motion_ret/sync_ret/stop_ret/verify_ret/restore_ret`，后续成功不得覆盖首个运动错误。
2. 拆开位置同步和驱动健康语义；驱动健康不能把位置同步失败改成成功。
3. 新增“本次新鲜活动位置快照”，携带来源和 generation/tick：
   - 电机位置源传播本次 XACTUAL 同步失败；
   - 编码器位置源证明样本晚于本次运动开始。
4. 无论主动停机还是驱动先报告停止，都走统一“确认停稳 → 刷新位置 → 判到位容差”。
5. `MotorCtrl_MoveToPosition()` 第 10 轮后再采样；到位才成功，仍超差返回 `POSITION_ARRIVAL_DEVIATION`。
6. 小位移不能再因 `<=5 mm` 自动绕过无位移验收。

### 9.4 C-11 探底结果

涉及 `measure.c` 的 `CMD_MeasureBottom()` 及 CPU3／SI／DSM／LH 消费端。

1. 每轮开始 generation++ 并立即令本轮 valid=0；历史 last-good 与本轮结果分离。
2. 删除随机回退和“失败后提前成功”出口。
3. 只有 `SearchBottom()==NO_ERROR`、结果新鲜且通过唯一偏差阈值时，才更新罐底值、valid 和 `STATE_FINDBOTTOM_OVER`。
4. 失败保留首个具体错误；`STATE_SWITCH` 进入取消终态，不得发布完成沿或沿用旧 valid。
5. 默认建议“失败即失败，不发布降级结果”。如产品允许降级，必须新增独立 source／quality／state，并逐一批准 SI、密度、校准和外部协议是否可消费；不得复用普通完成态。
6. 硬编码 10 mm 与 `maxTankHeightDeviation` 二选一，必须冻结唯一权威阈值。

### 9.5 实施顺序和验收

| 子阶段 | 内容 | 关键退出条件 |
| --- | --- | --- |
| A1 | 终态对象、新鲜位置、停稳验收、专用终结器 | 纯裁决测试证明错误不被覆盖、停机不重入 |
| A2 | C-05 | 未停稳、原故障或收尾失败时绝无 `STANDBY+NO_ERROR` |
| A3 | C-04 | 驱动提前停、丢步、位置过期、小步和 10 轮耗尽均有确定失败 |
| A4 | C-11 | 失败／取消绝无完成沿、valid=1、随机值或清错 |
| A5 | 可选降级共享语义 | CPU2／CPU3／SI／DSM／LH 联合发布和协议验证 |

台架必须覆盖：停止写失败、VZERO 失败、15 s 停机超时、速度恢复失败、丢步后同步成功、驱动提前停止、位置样本过期、第 10 轮边界、探底超时／碰撞／偏差／取消、旧 last-good 和重复取消。

### 9.6 版本和回滚

若 A1～A4 复用现有状态／错误且不改共享结构，按最终 diff 提升 CPU2 版本；CPU3 消费端有行为修改时同步提升 CPU3。新增取消／降级／quality／generation 字段时，两端同步并评估协议升级。绝对禁止用参数开关绕过停稳、到位或 motion inhibit。

## 10. 第 6 批：C-42 运动安全边界

### 10.1 审批前必须签字的机械契约

| 项目 | 必须确认 |
| --- | --- |
| 坐标 | 上／下方向、零点、单位和正负方向 |
| 绝对机械边界 | 上端、下端的权威数值和来源；`tankHeight` 是否等于机械行程 |
| 位置源 | 电机、编码器各自的有效条件、新鲜定义和失效策略 |
| 制动 | 各速度下停止距离、预留量和快速停机动作 |
| 水位边界 | 最深允许位置使用 `tankHeight`、专用水位高度还是探底扩展 |
| 强制入口 | 是否保留、维护授权、单次最大距离和审计要求 |
| 失效动作 | 保持驱动、快停、失能或断电是否会造成悬挂探头下坠 |

上述信息未冻结前，只能实现纯包络模型和测试桩，不能发布机械参数。

### 10.2 C-42A 公共安全包络

建议新增 `motor_safety_envelope` 内部模块，所有比较使用明确的 `int32_t position_01mm`，只在 API 边界做 mm 转换。

建议接口：

- `MotorSafety_ResolveEnvelope(context, params, out)`
- `MotorSafety_CheckStart(context, direction, target/current)`
- `MotorSafety_PollDuringMotion(context, deadline)`
- `MotorSafety_StopAndReturn(cause)`

实施要求：

1. 形成绝对机械、普通业务、探底扩展、维护四类包络，场景例外不能泄漏给普通运动。
2. `MotorCtrl_MoveNoWait()` 对有限距离计算绝对目标，越界时不下发。
3. `MotorCtrl_StartVelocity()` 改为带 context/envelope/deadline 的受保护入口；所有等待循环周期检查，启动前检查不能代替运行中检查。
4. `MotorCtrl_MoveBlockingNoDetectForceDebug()` 只能绕过获批的业务软边界；绝对机械边界、最大距离、deadline 和 motion inhibit 不可绕过。
5. Wait、Jog、异步运行态轮询全部复用同一个硬边界函数。
6. ISR 内不得读取 SPI 位置或执行停机；软件边界需要“所有调用点有界轮询 + C-08 前台失活复位”共同证明，不能宣称等同物理限位开关或 SIL 闭环。

### 10.3 C-42B 水位粗找／精找

在 `measure_waterLevel.c` 建立每次 attempt 的 guard：

`start_tick + absolute_deadline + lower/upper_limit + last_position_generation`

粗找、精找、快速状态翻转和跟随入口都必须复用：

1. 每轮刷新位置并检查新鲜度和上下边界。
2. 下行调用 `CheckWeightCollision()`；扭力无效时按批准的 fail-safe 退出。
3. 检查驱动、C-41 阻塞故障、命令切换和绝对 deadline。
4. 任一失败走一次性 StopAndReturn。
5. 成功必须同时满足：水状态有效、停稳、最终位置新鲜且处于本场景包络内。

只改 `SearchWaterRough()`／`SearchWaterPrecise()` 而遗漏快速找水或跟随入口，不能关闭 C-42B。

### 10.4 建议同批的低成本子项

- C-42D：油位负位置保留原始值，停止并返回位置异常；钳 0 只能用于报告。
- C-42E：`SearchAir()` 增顶部边界、位置刷新和绝对 deadline。
- C-42F：找零粗／精找增不可关闭上限和 deadline；校准模式只能放宽业务偏差。
- C-42H：`DeviceParams_ValidateMotionEnvelope()` 在加载、FC10 候选提交和每次运动启动三处校验参数组合。

首轮不建议同时扩展 C-42C/G 的授权和普通／维护入口语义，除非产品已给出完整权限表。

### 10.5 验收和版本

必须覆盖所有公开运动入口 × 上下方向 × 边界内／边界点／越界 × 电机／编码器位置源；并覆盖全速度、长距离、强制入口、位置刷新失败、水状态卡死、扭力超时、TMC、24 V、编码器和参数异常。

早期从现有参数派生边界，不增加参数结构尺寸。若确需新增持久参数，优先复用预留槽，并证明结构 size、offset、CRC 范围和后续地址不变。只改 CPU2 内部包络通常不升共享协议；新增共享状态、错误或参数语义时两端同步评估。

## 11. 第 7 批：C-41 全局阻塞故障及时打断

### 11.1 设计

在 `fault_manager.h/.c` 增加纯查询、表驱动接口：

- `FaultManager_Classify(error_code, operation_context)` → `NONE/WARNING/BLOCKING`
- `FaultManager_GetBlockingAbort(operation_context)` → `NO_ERROR` 或具体阻塞错误

查询函数不得停机、清错或递归进入 `HandleError()`。owner、当前活动位置源、自动恢复上下文等例外必须由 context 明确表达，禁止按错误码连续范围推断。

保留现有 `AbortableDelay_CommandSwitch()`，新增：

`AbortableDelay_ErrorOrCommandSwitch(total_ms, step_ms, context)`

返回语义：

| 返回 | 调用方 |
| --- | --- |
| `NO_ERROR` | 正常继续 |
| `STATE_SWITCH` | 进入取消／切令终态 |
| 具体阻塞错误 | 复用第 5 批一次性停机终态 |

同时出现切令和阻塞故障时保留阻塞故障；随后若停机失败，停机错误对外最高，原阻塞故障保留为因果。

### 11.2 分阶段迁移

1. 先完成分类表纯函数测试。
2. 第一阶段只替换密度长监测、油位密度／频率闭环、水位搜索、运动等待和 Wärtsilä 后置等待。
3. 第二阶段审计全部业务长循环和业务态 `AbortableDelay`。
4. 传感器初始化、模式切换和故障恢复逐个确认；禁止全仓机械替换。
5. `FaultRecovery_Poll()` 使用独立恢复 context，原故障是恢复对象，不能立即打断自身；恢复中新产生的 I/O／驱动错误仍可打断。
6. `measure.c` 等当前只判断 `delay_ret == STATE_SWITCH` 的调用点必须改为保存返回值并处理全部 `delay_ret != NO_ERROR`；否则扩展后的阻塞错误会被吞掉。

### 11.3 待审批的分类原则

| 类别 | 推荐原则 |
| --- | --- |
| 运动驱动、位置源、运动中扭力超时 | 当前运动上下文中 BLOCKING |
| 当前业务所依赖的传感器通信／数据失效 | 当前业务中 BLOCKING |
| 非活动位置源编码器异常 | 可为 WARNING，但必须保留诊断 |
| AO、外部通信、显示类故障 | 是否阻塞取决于操作上下文，不能全局一刀切 |
| 自动恢复正在处理的原故障 | 恢复 context 中不自我打断，新故障仍按分类处理 |

通过标准：异步置入阻塞错误后，在一个 `step_ms` 加规定停机时间内退出；warning 不误停；重复检查不重复停机；CPU3 能稳定读到具体故障。未完成故障分类签字前，不得批量替换调用点。

## 12. 第 8 批：C-08 CPU2 前台健康票据

### 12.1 现状边界

V1.31.1.0 把 CPU2 TIM4 节拍缩短到 250 ms，并保留此前已有的 `RETTOBASE` 门禁；它仍不能识别线程态主循环死锁。CPU3 已有前台 generation 门控，但不能代替 CPU2，且 CPU3 自身仍需目标板故障注入。

### 12.2 两阶段方案

建议新增 `cpu2_watchdog_supervisor.c/.h`：

- `CPU2_WatchdogReportProgress(checkpoint, token)`
- `CPU2_WatchdogHealthAdvancedFromISR()`
- 可选 `CPU2_WatchdogBeginOperation(id, deadline)`／`CompleteOperation(id)`

实施要求：

1. TIM4 喂狗条件改为 `RETTOBASE && HealthAdvanced`，保留 `RETTOBASE` 为附加门禁；`RETTOBASE==0` 时不得消费本次新票据。
2. `App_Init()` 和 `MotorCtrl_BootSafeStop()` 只在有界启动里程碑打票；`App_MainLoop()` 只在完成有意义的调度阶段后打票。
3. 禁止在 while 顶部、通用 delay、单纯 tick 变化或错误重试空转中打票。
4. 同步长命令只能在完成新鲜传感／位置／驱动检查且 operation token 真正推进时打票；重复 token 不算健康，超过 operation deadline 不再续票。所有可能超过 IWDG 窗口的合法等待必须先建立这样的安全进度点。
5. 第一提交为 observe-only：保留当前喂狗行为，只记录如果启用门控会漏票的 checkpoint 和最长时长。
6. 覆盖全部最长正常流程后，第二提交才启用 enforcement。
7. ISR 内不写 FRAM、不打印、不做 SPI 或电机动作；启动后只读取和记录 RCC IWDG reset flag。

### 12.3 验证

覆盖前台死循环但 TIM4 正常、同步外设永久阻塞、UART ISR 风暴、全局关中断、重复 token、generation 回绕、启动卡点、最长正常密度／液位／运动和长时间 soak。

通过标准：

- 坏前台在实测 LSI 容差窗口内复位；
- 正常最长流程零误复位；
- 复位原因和最后 checkpoint 可追溯；
- 复位后的机构行为有实机证据。

仅内部健康票据不升共享协议，但需提升 CPU2 固件版本。若 enforcement 产生误复位，应只回滚 enforcement 提交，保留 observe 证据；不得恢复成无条件 ISR 喂狗后宣称 C-08 已完成。

## 14. 版本、协议和存储原则

不预先写死未来版本号；每批在实施／发布阶段按最终 diff 决定。

| 改动 | 默认版本原则 |
| --- | --- |
| CPU2 内部逻辑、复用现有错误／状态 | CPU2 PATCH；共享协议通常不变 |

每批独立构建、验证和提交。提交标题按仓库规则包含受影响固件版本；推送前执行提交标题版本门禁。不得用一个提交同时合并数组、传感器、运动、看门狗和 UI 改动。

| 静态契约 | 类型、容量、错误传播、无裸调用、调用点清单 | 不能替代目标板和机械台架 |
| 主机／纯函数 | planner canary、错误裁决、分类表、golden frame | 不能证明 HAL、UART、SPI 时序 |
| clean-first 构建 | CPU2／CPU3 编译链接、版本和编码 | 不能证明运动停止或帧波形 |
| 串口／目标板 | 畸形帧、地址 0、UART4、FRAM、IWDG | 不能单独证明全速度机械安全 |
| 机械台架 | 多速度、长距离、极限、卡滞、24 V、TMC、编码器、扭力断线 | 是 C-04/C-05/C-09/C-42/C-08 的必要关闭证据 |
| 长稳 | OLED、通信压力、看门狗误复位 | 不能替代故障注入 |

## 16. 回滚规则

1. 每批单独提交并保留目标文件清单，禁止用 `git add .` 混入其它改动。
2. 回滚只撤销本批；协议升级批必须 CPU2／CPU3 成对回滚。
3. 运动安全、停稳、到位和 motion inhibit 不提供现场关闭开关。
4. 若合法帧被拒、正常流程误停、看门狗误复位或旧主机兼容发生变化，先停止发布并回到上一套已验证固件，同时保留失败证据。
5. 参数或存储有变化时，回滚前证明旧固件能读取现有 FRAM；不能只回滚代码而忽略存储兼容。
6. 未做的台架项目继续标为开放，不得因回滚或延期改写成“已通过”。
