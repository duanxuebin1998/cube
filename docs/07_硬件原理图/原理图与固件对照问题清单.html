原理图与固件对照问题清单

更新日期：2026-06-06

对照范围

  • 原理图：00_原始资料/储罐自动计量仪原理图汇总.pdf
  • 原理图整理：储罐自动计量仪原理图汇总整理.md
  • 固件工程：LTD_MAIN_CPU2、LTD_DISPLAY_CPU3
  • 验证命令：
    • cmake --build build\LTD_MAIN_CPU2
    • cmake --build build\LTD_DISPLAY_CPU3

两个构建目标当前均为 ninja: no work to do，本清单关注的是硬件接口闭环、引脚命名、功能覆盖和可维护性风险，不是当前编译失败。

总体结论

当前固件的核心测量、电机、CPU2/CPU3 内部通信、CPU3 COM1/COM2/COM3 方向控制等主流程已经有实现。风险主要集中在三类：

  1. 原理图上已经预留或明确画出的硬件检测链路，在固件里没有形成闭环。
  2. CubeMX 标签和实际外设方向不一致，短期不一定影响 HAL 复用功能，但会影响调试、维护和后续手动 GPIO 操作。
  3. 部分接口可能是预留接口，但固件中没有显式文档化为“未使用/预留”，容易在联调时误判为已支持。

高优先级问题

1. CPU2 24V/12V 电源检测链路未形成固件闭环

原理图依据

  • 主控板 CPU2 页包含 24V-TEST、12V-TEST、复位/看门狗和电源检测相关网络。
  • 电源树页包含 48VIN、24V_MD、24V、12V、5V、3V3 等电源域。

固件现状

  • LTD_MAIN_CPU2.ioc 中 PC2 标为 POWER_24V_TEST，PC3 标为 POWER_12V_TEST。
  • Core/Src/adc.c 同时把 PC2/PC3 初始化为模拟输入，但 ADC1 只配置了 ADC_CHANNEL_12，ScanConvMode = DISABLE，NbrOfConversion = 1。
  • 代码搜索未看到业务层调用 HAL_ADC_Start、HAL_ADC_GetValue 或对 POWER_12V_TEST 的运行时采样。
  • 当前电机 24V 故障主要通过 TMC5130 DRV_STATUS.CS_ACTUAL 间接判断，不能替代 12V/24V 板级检测。

影响

  • 12V 掉电、异常偏低或异常偏高无法被固件主动识别。
  • 24V 检测电路存在，但没有形成独立诊断，电机侧只能在 TMC5130 已参与通信的场景下间接发现问题。
  • 现场问题定位时，原理图上的电源检测点和固件诊断信息不一致。

建议

  • 增加电源监测服务，至少轮询 PC2/PC3 两路 ADC。
  • ADC 配置改为双通道扫描，或每次采样前显式切换 ADC_CHANNEL_12/ADC_CHANNEL_13。
  • 给 24V/12V 建立标定系数、阈值、迟滞和故障恢复策略，并接入 error_log/fault_manager。
  • 将电源状态映射到 Modbus 调试寄存器，方便联调时直接查看。

2. CPU2/CPU3 原理图存在 WDI 网络，但固件没有外部看门狗 GPIO 闭环

原理图依据

  • CPU2 主控页整理中列出复位/看门狗、WDI、NRESET。
  • CPU3 主控页整理中列出 SEL_485、WDI 等主控引脚和复位相关网络。

固件现状

  • CPU2/CPU3 都启用了 STM32 内部 IWDG，并通过 TIM4 中断刷新。
  • 固件目录搜索 WDI 未发现业务 GPIO 或外部看门狗喂狗逻辑。
  • .ioc 中看到的是虚拟 IWDG 外设配置，没有看到名为 WDI 的 GPIO 标签。

影响

  • 如果板上外部看门狗芯片的 WDI 确实接到 MCU 并要求周期翻转，那么当前固件没有服务外部看门狗。
  • 如果 WDI 被硬件固定或未装配，固件侧没有说明，后续维护会反复踩这个确认点。

建议

  • 和硬件确认 WDI 是否装配、是否接 MCU、有效时序和是否允许空置。
  • 如果需要服务外部看门狗，增加独立 GPIO 翻转逻辑，不要只依赖内部 IWDG。
  • 在硬件文档中明确标注：外部 WDI 已使用、未装配、硬件禁用，或预留。

3. CPU2 HART 串口标签方向反了，协议格式也需要复核

原理图依据

  • 主控板 HART/4-20mA 页包含 SD2017B、AD5421、HART RTS/TX/RX 和外部回路。

固件现状

  • LTD_MAIN_CPU2.ioc 中 PD5 是 USART2_TX，却标为 HART_RXD2；PD6 是 USART2_RX，却标为 HART_TXD2。
  • Core/Inc/main.h 也生成了 HART_RXD2_Pin = GPIO_PIN_5、HART_TXD2_Pin = GPIO_PIN_6。
  • Core/Src/usart.c 的 HAL 复用配置仍按 PD5/PD6 配置 USART2，因此电气复用本身大概率能工作。
  • USART2 配置为 1200 + UART_WORDLENGTH_9B + UART_PARITY_NONE + 1 stop bit。如果现场对接的是标准 HART 字符格式，需要确认是否应为 8 位数据加奇校验。

影响

  • 调试日志、示波器标注、线束排查和后续手动控制 GPIO 时容易把 TX/RX 判断反。
  • 如果 HART 对端要求奇校验，当前 9B + NONE 会按 9 位数据发送，而不是 8 位数据加校验。

建议

  • 修正 CubeMX 标签：PD5 使用 HART_TXD2，PD6 使用 HART_RXD2。
  • 复核 HART 字符格式；若确认需要奇校验，按 STM32 HAL 规则调整 WordLength/Parity。
  • 用逻辑分析仪同时抓 PD5、PD6、HART_RTS，验证发送前 RTS 拉低、发送完成后回到接收、字节格式和校验位。

中优先级问题

4. CPU2 SPI2/SPI3 的 MISO/MOSI 标签错误

固件现状

  • SPI2：PB14 实际是 SPI2_MISO，但标签是 MOTOR_SPI2_MOSI；PB15 实际是 SPI2_MOSI，标签也是 MOTOR_SPI2_MOSI。
  • SPI3：PB4 实际是 SPI3_MISO，但标签是 AD5421_SPI3_MOSI；PB5 实际是 SPI3_MOSI，标签也是 AD5421_SPI3_MOSI。
  • main.h 因此生成了 MOTOR_SPI2_MOSI_Pin 指向 PB14、AD5421_SPI3_MOSI_Pin 指向 PB4 等误导性宏名。

影响

  • HAL SPI 外设复用仍按实际 Signal 初始化，当前不一定影响通信。
  • 任何后续手动 GPIO 调试、临时 bit-bang、示波器记录或驱动封装都会被宏名误导。

建议

  • 修正 CubeMX GPIO 标签：PB14/PB4 使用 MISO，PB15/PB5 使用 MOSI。
  • 更新生成后的宏名引用，避免保留 MOSIB15 这类自动补名。

5. CPU3 HART/BPM 插座与固件支持边界不清

原理图依据

  • CPU3 第 1 页包含 HART/BPM 接口连接器和滤波。
  • HART 板页包含 HART 本安端子、光耦隔离 RX/TX/RTS 和回路保护。

固件现状

  • CPU3 .ioc 和 Core/Src/usart.c 只配置了 UART5、USART1、USART2、USART3、USART6。
  • CPU3 固件中没有 UART4/UART8 初始化，也没有独立 HART/BPM 通讯模块。
  • COM1/COM2/COM3 主通道已有 USART6/USART2/USART3、DMA 接收、方向切换和参数重配逻辑。

影响

  • 如果 CPU3 HART/BPM 插座是量产功能，当前固件缺少对应串口和协议实现。
  • 如果只是硬件预留，当前文档未明确“预留/未支持”，联调时容易误解。

建议

  • 明确 CPU3 HART/BPM 是否为本版本需求。
  • 若需要支持，补齐对应 UART、RTS/方向控制、协议模块和错误上报。
  • 若暂不支持，在硬件整理文档和版本说明中标为预留接口。

6. CPU2 传感器供电 BA_EN/SENSOR_ENN 缺少明确的运行时电源管理

原理图依据

  • CPU2 传感侧电源/接口页包含由 BA_EN 控制的 24V 开关、TXD6/RXD6 缓冲、OUT_12V、SA+、SB-。

固件现状

  • SENSOR_ENN 在 GPIO 初始化时默认写为 GPIO_PIN_SET。
  • 搜索业务代码未看到专门的 SensorPower_Enable/Disable 封装或测量前后供电时序控制。
  • 固件中大量传感器通信复用 USART6，但供电使能没有和通信状态机显式绑定。

影响

  • 如果该脚为高有效，传感侧电源会在 GPIO 初始化阶段即打开。
  • 如果该脚为低有效，命名 ENN 与原理图 BA_EN 容易造成有效电平误判。
  • 传感器通信异常时，缺少通过断电/上电恢复的统一策略。

建议

  • 和硬件确认 BA_EN/SENSOR_ENN 的有效电平。
  • 封装 SensorPower_SetEnabled(bool enabled)，并在注释中写清有效电平。
  • 测量前上电后增加稳定等待；通信连续失败时可选择受控重启传感器电源。

7. AD5421 故障引脚和状态寄存器未接入故障闭环

原理图依据

  • CPU2 HART/4-20mA 页包含 AD5421 输出、HART 回路和外部保护。

固件现状

  • PB8 配置为 AD5421_FAULT 输入。
  • ad5421.c 中有 AD5421_GetStatus()，但自检 CurrentSelfTest() 被注释，Ad5421Init() 中也没有启用自检结果。
  • 参数中有故障电流配置，但 AD5421 硬件故障没有看到接入 fault_manager。

影响

  • 4-20mA 回路开路、过流、芯片 fault 等状态可能不能及时上报。
  • 现场只看到输出异常，但固件没有明确故障码。

建议

  • 初始化后读取 AD5421 fault/status，输出电流变化后也做一次状态确认。
  • 将 PB8 fault 引脚和 READFAULT 结果合并成 4-20mA 输出故障码。
  • 触发故障时按参数设置故障电流，并记录 error_log。

低优先级优化项

8. CPU3 OLED SPI 配置可收敛为写-only

固件现状

  • CPU3 SPI1 配置为 SPI_DIRECTION_2LINES、硬件 NSS，PA6 配置为 MISO。
  • OLED 驱动代码只调用 HAL_SPI_Transmit()，没有读取 MISO。

建议

  • 如果 OLED 硬件确认为单向写入，SPI1 可改为 1-line TX 或保持 2-line 但在文档中说明 PA6/硬件 NSS 的用途。
  • 这样可以减少未使用引脚和后续误判。

9. TMC5130_Pins.h 保留旧宏且自引用

固件现状

  • TMC5130_Pins.h 中 CHIP_SELECT_1_PIN 指向 TMC1_CS_Pin，但当前工程实际片选是 MOTOR_SPI2_CS_Pin。
  • 同一文件还存在 #define TMC1_CS_Pin TMC1_CS_Pin 的自引用宏。
  • 当前 TMC5130 底层直接使用 GPIOB/GPIO_PIN_12 或调用方传入片选，因此构建未失败。

影响

  • 该头文件一旦被其他模块按旧接口使用，会展开到不存在或无意义的符号。

建议

  • 删除旧头文件，或改成明确映射到 MOTOR_SPI2_CS_Pin/MOTOR_SPI2_CS_GPIO_Port。
  • 优先让 TMC5130 驱动只依赖结构体传入的硬件资源，减少双重来源。

10. 源码中文注释存在混合编码/乱码风险

现象

  • 部分文件中文注释正常，部分文件在 UTF-8 读取时出现乱码。
  • 当前仓库要求修改文件时注意编码，避免中文乱码。

建议

  • 对 CPU2/CPU3 源码做一次编码盘点，明确哪些文件是 GBK/936，哪些是 UTF-8。
  • 后续修改中文注释前先确认文件编码。
  • 新增文档保持 UTF-8；若需要批量转换源码，应单独立项并构建验证。

已对齐或相对健康的点

  • CPU2/CPU3 内部 IWDG 已启用，并通过 TIM4 中断刷新。
  • CPU3 COM1/COM2/COM3 已有 USART、DMA、方向控制和发送完成后回接收的逻辑。
  • CPU2 TMC5130 驱动已经增加 DRV_STATUS.CS_ACTUAL 等功率级健康检查，对电机 24V 断电有间接诊断能力。
  • CPU2 传感器链路 USART6 已有 DSM/LTD/无线 AT 相关通信逻辑，主要缺口是供电使能和硬件电源状态闭环。

建议验证顺序

  1. 先确认 WDI、BA_EN、CPU3 HART/BPM 是否为当前硬件装配和软件需求。
  2. 用万用表/示波器验证 PC2/PC3 分压输出和 24V/12V 标定关系。
  3. 用逻辑分析仪抓 HART PD5/PD6/RTS，确认方向、波特率、校验格式。
  4. 断开或拉低 12V/24V，确认固件能否记录并上报电源异常。
  5. 触发 AD5421 fault 条件，确认 PB8 和 fault/status 寄存器行为。
  6. 修改 CubeMX 标签后重新生成并构建 CPU2，确认不引入宏名回归。
