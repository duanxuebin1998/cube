# 处理器与传感器架构确认基线

更新日期：2026-08-07

## 1. 用途与优先级

本文记录用户已经确认的二代计量仪处理器、传感器和通信关系，并结合当前源码标明已实现范围。后续 ER02 Word、Visio、CPU2 软件详细设计及相关评审均应先与本文核对。

发生冲突时按以下优先级处理：

1. 用户最新确认的产品架构事实。
2. 当前 CPU2、CPU3 和 CPUW 源码所证明的实现事实。
3. 已批准的系统架构、接口协议和需求资料。
4. 一代 ER02 仅用于章节、表格和版式参考，不继承其处理器关系。

## 2. 已确认的系统关系

| 对象 | 当前定位 | 当前状态 | 后续文档约束 |
| --- | --- | --- | --- |
| CPU1 | 传感器端处理单元 | 整机在 DSM、LTD、DM4 三种传感器中三选一；任一配置均向 CPU2 传输原始数据和计算结果 | DM4 是 CPU1 传感器的一种，不能与 CPU1 并列成独立处理器；具体字段以所选协议为准 |
| CPU2 | 主控处理器 | 测量、运动、参数、故障和安全动作的业务权威端；直接承担 AO/HART、继电器和电机，并与 CPU1、CPU3、CPUW 交互 | 以 `LTD_MAIN_CPU2` 当前源码为实现依据 |
| CPU3 | 显示与对外协议处理器 | 负责显示、按键、CPU2 数据同步和全部外部数字协议网关；未来接收 CPU4 实时温度数据并上传上位机 | 以 `LTD_DISPLAY_CPU3` 当前源码为实现依据 |
| CPUW | 扭力处理器 | 每台必装；采集扭力及内部诊断量，并通过串口向 CPU2 提供数据 | 必须纳入整体架构、接口和故障边界；属于非安全链路；源码根目录为 `D:\CSS_workspace\newhall` |
| CPU4 | 未来扩展预留 | 当前尚未设计；目标为连接铂电阻温度计等外部实时温度计，并按 `外部实时温度计 → CPU4 → CPU3 → 上位机` 上传 | 属于非安全相关扩展，不经过 CPU2；只能描述已确认的数据路径和待设计边界 |
| 无线主机/无线从机 | 蓝牙透明传输链路两端 | 当前不再作为独立 CPU 节点 | ER02 不设置“无线主机 CPU”或“无线从机 CPU”章节，不把旧无线工程映射为 CPU4 |

当前二代架构中不存在 CPU0。CPU4 也不属于当前已实现处理器，只保留已经确认用途和数据方向的未来扩展位置。处理器责任分配没有例外：AO/HART、继电器和电机归 CPU2，外部数字协议归 CPU3。

## 3. CPU1 传感器类型与协议状态

| 传感器选择 | 协议版本/形态 | 上传内容 | 安全属性 | 当前状态及文档口径 |
| --- | --- | --- | --- | --- |
| DSM 传感器 | 现有 DSM 协议 | 原始数据和计算结果，具体字段以 DSM 协议为准 | 非安全通信 | `DSM_SENSOR` 及 DSM 通信、识别和测量调用路径已存在；真实传感器和链路验证另列 |
| LTD 传感器 | 现有 LTD/LTD V2 协议 | 原始数据和计算结果，具体字段以 LTD 协议为准 | 非安全通信 | `LTD_SENSOR` 及 LTD/V2 通信、识别和测量调用路径已存在；真实传感器和链路验证另列 |
| DM4 传感器 | DM4 非安全协议或 DM4 安全协议；协议组织类似 LTD，SIL 认证配置使用安全协议 | 原始数据和计算结果；安全版的完整性和诊断字段以最终安全协议为准 | 非安全版为非安全通信；使用安全版时仅 `CPU1（DM4）↔ CPU2` 为安全通信链路 | 两种协议正在添加，尚未完成实现冻结和联调；不得把在编协议、单端代码或静态检查写成完整实现、链路验证或 SIL 认证完成 |

整机物理传感器选择只有 DSM、LTD、DM4 三种，且三选一。DM4 的安全协议和非安全协议是同一种 DM4 传感器的两个协议版本，不表示存在第四种传感器。三种传感器都会上传原始数据和计算结果，字段名称、单位、倍率和诊断项分别由对应协议冻结。

DSM、LTD 以及采用非安全协议的 DM4 均不构成安全通信链路。SIL 认证配置选择 DM4 安全协议时，逻辑安全通信端点只有 CPU1（DM4）和 CPU2；CPU2 同时是测量、故障判断和安全动作权威端。CPUW、CPU2↔CPU3、CPU4→CPU3→上位机以及 CPU3 对外数字协议均不纳入这条安全通信链路。

CPU2 当前枚举还存在 `SAFE_SENSOR` 和通用安全协议探测代码。产品方向已经明确为“DM4 安全协议用于 SIL 认证配置”，但仍需在 DM4 协议添加过程中核对 `SAFE_SENSOR` 与最终 DM4 安全协议的映射、版本和完整调用链；不能只凭候选代码声明 DM4 安全协议已经完整实现。

CPU1 与 CPU2 之间的无线部分按蓝牙透明传输链路描述。在 DM4 安全协议配置中，蓝牙只承载 CPU1 与 CPU2 端到端安全通信帧；无线主机和无线从机不再作为具有独立业务软件架构的 CPU。CPU2 现有 CH9141 AT 管理、配对和连接状态代码属于链路管理，不改变这一处理器边界。

## 5. CPUW 到 CPU2 的实际调用链

### 5.1 CPUW 发送侧

1. `main.c` 初始化 16 MHz 时钟、UART1、扭力采集、温度和 ADC。
2. 主循环调用 `ReadWeight()`；原始扭力数据来自 ADS1220。
3. 每次扭力采样后置位 `OPERA_UARTCOM`，随后调用 `UartCommunicate()`。
4. `UartCommunicate()` 当前固定选择 `UART_READ_ALL`，不使用本次收到的请求功能码决定响应类型。
5. `uartAllPackage()` 形成 `CC 03 83` 全量帧并追加异或 BCC，然后由 UCA1 逐字节发送。

CPUW 虽然保留以 `AA 02` 开头的请求接收状态机，也保留 `0x81` 电压帧和 `0x82` 扭力帧组包函数，但当前主循环会在每次采样后主动触发通信，`UartCommunicate()` 又固定发送 `0x83` 全量帧。因此，面向当前 CUBE CPU2 的有效运行路径应描述为“CPUW 主动推送、CPU2 被动接收”，不能写成已经确认的查询应答事务。

### 5.2 当前 22 字节帧

| 字节范围（0 基索引） | CPUW 发送内容 | CPU2 当前使用情况 |
| --- | --- | --- |
| 0～2 | `CC 03 83` | 校验固定帧头 |
| 3～12 | IA、IB、VIN、AVCC、VREF | 当前扭力接收路径未消费 |
| 13～14 | CPUW 滤波扭力值 | 当前 CPU2 扭力接收路径未消费 |
| 15～18 | 温度的 4 字节 IEEE 754 原始位 | CPU2 组合为 32 位温度快照；NaN/Inf 不更新 |
| 19～20 | CPUW 原始扭力值 | CPU2 按高字节在前组合成有符号 16 位 `g_weight` |
| 21 | 异或 BCC | CPU2 在更新数据前校验 |

上表使用 0 基索引：温度字段是帧内第 16～19 字节，原始扭力字段是第 20～21 字节。索引 3～14 的载荷仍参与整帧 BCC 校验，但当前 CPU2 不解释其业务含义。

### 5.3 CPU2 接收与消费侧

1. CPU2 的 UART4 配置为 19200 bps、8N1，PA0/PA1，DMA 接收并使用空闲中断判定一帧结束。
2. `UART4_NewhallFrameIsValid()` 要求长度正好为 22 字节、帧头为 `CC 03 83` 且 BCC 正确；非法帧被丢弃，不更新扭力、温度或有效帧存活时间，也不立即生成独立的坏帧错误码。
3. 合法帧的 0 基索引 19、20（即帧内第 20、21 字节）组合为 `g_weight`；CPU2 计算 `empty_weight - g_weight` 作为当前扭力值。
4. `Weight_Update()` 以 200 ms 节拍更新稳定值和调试数据，`Weight_MarkFrameReceived()` 刷新通信存活时间。
5. 合法扭力值由 CPU2 继续用于扭力量程、漂移、碰撞、零点、探底和相关测量判断。
6. 超过 1000 ms 未收到合法帧时，扭力服务（源码 `Weight` 模块）形成 `WEIGHT_COMM_TIMEOUT` 并进入 CPU2 统一错误处理；电机驱动有效时调用慢停流程，错误写入 CPU2 共享状态并由 CPU3 轮询同步。

CPU2 当前源码中未找到 UART4 向 CPUW 发送 `AA 02` 请求的调用。因此，正式架构图的箭头应按当前有效数据流画为 `CPUW → CPU2`；如以后改成 CPU2 轮询，必须同步修改两端程序、接口协议和 ER02。

### 5.4 CPUW 诊断责任与当前实现缺口

1. CPUW 的产品责任包含非安全自诊断。当前软件已具备 ADS1220 启动回读检查、温度接口初始化检查和看门狗，并采集 IA、IB、VIN、AVCC、VREF 等原始监测量；这些监测量当前尚未形成 CPUW 侧阈值判断或故障状态。
2. 当前有效 `0x83` 全量帧没有独立诊断状态码；`EquipmentErrCode` 当前保持为 0，且只出现在未被有效运行路径采用的 `0x82` 帧中。
3. 初始化失败时 CPUW 当前只发送单字节错误值，不能通过 CPU2 对 22 字节 `CC 03 83` 帧的合法性检查，因而不能形成 CPU2 可消费的独立诊断状态。
4. CPU2 目前负责帧长度、帧头、BCC、1000 ms 通信超时，以及扭力量程、漂移和碰撞诊断；这些 CPU2 侧检查不能替代 CPUW 内部自诊断状态的正式上报。

ER02 应分层表述为：CPUW 的产品责任包括非安全自诊断，但当前独立诊断状态码的组帧、传输、CPU2 接收、故障映射和向 CPU3 发布尚未形成闭环。不得把“具备本地检查和诊断量采集”写成“CPUW 诊断已经完整上报”。

## 6. 后续 ER02 图文整改约束

1. 总体架构图必须包含 CPU1、CPU2、CPU3 和 CPUW，并画出 `外部实时温度计 → CPU4 → CPU3 → 上位机` 的未来非安全扩展路径。
2. CPU1 下展开 DSM、LTD、DM4 三种互斥选择，注明三种传感器均上传原始数据和计算结果；DM4 不得与 CPU1 并列。
3. DM4 下区分安全协议和非安全协议，均标注“正在添加/尚未冻结”；不得继续写成“协议待设计”，也不得写成已经完成实现或认证。
4. 安全通信语义只标在 SIL 配置的 `CPU1（DM4 安全协议）↔ CPU2`；DSM、LTD、DM4 非安全协议、CPUW、CPU2↔CPU3、CPU4 和 CPU3 对外接口不得误画成同一安全链路。
5. 无线主机/无线从机只画成蓝牙透明传输链路，不画 CPU 节点或独立软件状态机。
6. CPU2 图中固定承担 AO/HART、继电器和电机，CPU3 图中固定承担外部数字协议，不设置例外分支。
7. 原 V0.1 的 CPU4 无线模块图和状态图不得继续作为 CPU4 事实；后续改编为 CPUW 模块图及 CPUW→CPU2 数据流图，并明确 CPUW 非安全自诊断责任和当前上报缺口。
8. CPU4 当前不单独编写已实现的软件模块、调度、状态转移或故障恢复章节，只保留已确认用途、数据方向和待设计接口。
9. V0.1 Word 与九张 Visio 的版式检查结果可以作为排版经验保留，但其处理器和接口内容未通过用户评审，不能作为软件详细设计上位基线。

## 7. 待确认项

1. DM4 安全协议和非安全协议的最终物理参数、帧字段、命令、数据项、错误处理、协议版本，以及与当前 `SAFE_SENSOR` 候选代码的映射和兼容关系；“两种协议正在添加”和 SIL 配置使用安全协议不再作为待确认项。
2. CPU4 所接实时温度计的具体类型、输入接口、采样和转换要求，以及 CPU4→CPU3 接口协议、更新周期和上位机字段映射；CPU4 非安全分类和数据方向不再作为待确认项。
3. CPUW 独立诊断状态码、帧字段、CPU2 接收与故障映射、CPU3 发布方式的闭环设计；当前主动推送方向按源码确定，不再作为待确认项。
4. CPUW 的正式版本号、发布方式及其与 CPU2 固件版本的兼容矩阵。
5. 蓝牙透明链路的正式硬件型号、配对策略、断链恢复和真实设备验证证据；无线两端不作为 CPU 的边界已经确认。
