CPU2 安全版与现场版双版本架构方案

本文用于指导 LTD_MAIN_CPU2 在一套源码下同时维护 SIL 安全认证版、现场正式版和开发调试版， 并把液位测量、4-20mA 输出、四路继电器方式2 HH/H/L/LL 报警等安全功能形成清晰、可审查、可复现的工程边界。

工程：LTD_MAIN_CPU2 主题：SIL 软件架构 日期：2026-06-06 状态：实施方案

一、目标和基本结论

当前 CPU2 是安全功能板，安全功能涉及液位测量、4-20mA 输出和四路继电器方式2 HH/H/L/LL 报警输出。 由于找液位流程依赖传感器、编码器、电机控制和参数存储，不能简单把驱动层排除在安全范围外。

核心结论：不要维护两套源码。应维护一套源码，通过明确的目录边界、接口边界和 CMake 显式源码清单， 生成 SAFETY、FIELD、DEV 三类构建产物。

安全版和现场版的关系不是“安全代码”和“非安全代码”两套并列程序，而是： 

安全认证版 = 安全核心 + 安全支撑 + X-CUBE-STL + 最小启动入口
现场正式版 = 安全核心 + 安全支撑 + X-CUBE-STL + 现场辅助功能
开发调试版 = 安全核心 + 安全支撑 + 现场辅助功能 + 调试测试代码

三、安全功能边界

建议把 CPU2 的安全功能声明为下列闭环链路，而不是泛化为“CPU2 所有功能都是安全功能”。 

CPU2 完成液位测量，并基于有效液位值输出：
1. 4-20mA 液位电流信号
2. 四路继电器方式2 HH/H/L/LL 液位报警信号
3. 故障时进入定义的安全状态

液位测量结果 是 错误液位会直接导致错误电流或错误继电器报警。 保留认证用单一路径，加入有效性、新鲜度和范围检查。
传感器、编码器、电机 是，作为安全支撑 这些驱动会影响找液位结果。 通过安全接口封装，并增加合理性诊断。
AD5421 4-20mA 输出 是 直接构成安全功能输出。 只能由 Safety/Output 控制。
四路继电器方式2 HH/H/L/LL 报警 是 直接构成报警输出。 只能由 Safety/Output 控制，并检查 NO/NC 反馈。
Modbus/HART/日志/显示 非安全或现场辅助 不应直接影响安全输出。 现场版可编译，但必须通过安全接口读写状态和参数。

四、版本定义

构建变体 用途 编译范围 产物建议命名
SAFETY SIL 认证、型式测试、安全基线 S0 安全核心 + S1 安全支撑 + X-CUBE-STL + 最小启动入口 LTD_MAIN_CPU2_Vx.x.x.x_SAFETY.hex
FIELD 实际现场交付、运维、通信、参数管理 S0 + S1 + S2 现场辅助 + X-CUBE-STL LTD_MAIN_CPU2_Vx.x.x.x_FIELD.hex
DEV 内部开发调试、问题定位、实验功能 S0 + S1 + S2 + S3 调试测试代码 LTD_MAIN_CPU2_Vx.x.x.x_DEV.hex
注意：FIELD 不是“放松安全要求”的非安全版。只要 CPU2 在现场仍负责液位安全输出， 现场版就必须保留同一套安全核心，并且不能绕过安全输出接口。

五、代码分类方法

所有 CPU2 源码文件需要在代码范围矩阵中标成 S0、S1、S2、S3。分类的关键不是目录名，而是它是否会影响安全输出。

分类 含义 典型内容 SAFETY FIELD DEV
S0安全核心 直接决定安全功能输出和故障状态。 安全监督、液位有效性、4-20mA 输出、继电器输出、故障降级。 编译 编译 编译
S1安全支撑 会影响安全功能输入或安全核心判断。 找液位、传感器、编码器、电机控制、必要参数、基础驱动。 编译 编译 编译
S2现场辅助 服务现场使用，但不允许直接影响安全输出。 Modbus、HART、日志、CPU3 通信、现场维护。 不编译或只读接口 编译 编译
S3调试测试 实验、人工测试、临时命令和未受控输出。 test.c、人工输出测试、临时串口命令、调试脚本入口。 不编译 不编译 编译

当前工程需要重点关注的文件

文件或模块 建议分类 说明
Application/Src/measure_oilLevel.c S1 找液位逻辑依赖多层驱动，不能简单排除。后续应抽出认证用单一路径。
BSP/Peripherals/src/ad5421.c S1/S0 支撑 底层驱动可作为支撑，但写电流的调用权限必须收口到 Safety/Output。
Services/Relay/relay_output.c S2 或重写为 S0 子集 当前功能较宽，支持多来源、多通道和复杂报警逻辑。安全版建议写一个更窄的安全继电器模块。
Services/ParamStorage/system_parameter.c/h S1 子集 不能整体纳入安全范围。应抽取 AO/DO、报警阈值、故障电流等安全参数快照。
Application/Src/test.c S3 安全版和现场正式版均不应编译。

六、推荐架构

推荐先新增 Safety/ 目录，把安全判断和安全输出收口进去；旧模块先不大规模移动，避免一次性改造风险过大。

安全核心入口

安全版主循环只运行安全入口，减少非安全任务对安全链路的干扰。

void SafetyApp_Init(void);
void SafetyApp_Run(void);

现场版入口

现场版可以运行通信和日志，但安全输出仍然由安全核心独占。

void FieldApp_Init(void);
void FieldApp_Run(void);

七、强制隔离规则

安全输出写权限必须独占。只要存在非安全模块直接写 AD5421 或 RELAY GPIO，安全边界就不清晰。
规则 允许 禁止
4-20mA 输出 Safety/Output/safety_analog_output.c 调用 AD5421_SetCurrent() Modbus、HART、测试代码、应用层直接调用 AD5421_SetCurrent()
继电器输出 Safety/Output/safety_relay_output.c 写 RELAYx 非安全模块直接 HAL_GPIO_WritePin(RELAYx...)
安全参数 通过 Safety_RequestConfigUpdate() 请求更新 通信层直接改安全阈值并立即生效
故障状态 Safety/Core 统一锁定和清除 非安全模块绕过安全监督清故障

推荐接口

typedef struct {
    uint32_t level_01mm;
    uint8_t valid;
    uint32_t timestamp_ms;
} SafetyLevelSnapshot;

void Safety_Init(void);
void Safety_Run10ms(void);
void Safety_UpdateLevel(const SafetyLevelSnapshot *level);
uint8_t Safety_RequestConfigUpdate(const SafetyConfig *config);
SafetyStatus Safety_GetStatus(void);

八、CMake 构建维护

当前 LTD_MAIN_CPU2/CMakeLists.txt 使用 GLOB 自动收集源码。双版本维护时必须改为显式源码清单， 否则新增测试文件可能被自动编进安全版。 

set(CPU2_VARIANT "FIELD" CACHE STRING "CPU2 build variant: SAFETY, FIELD, DEV")

set(CPU2_COMMON_SOURCES
    Core/Src/main.c
    Core/Src/gpio.c
    Core/Src/spi.c
    Core/Src/iwdg.c
    BSP/Peripherals/src/ad5421.c
    BSP/Peripherals/src/AS5145.c
    BSP/Peripherals/src/TMC5130.c
)

set(CPU2_SAFETY_SOURCES
    Safety/Core/safety_supervisor.c
    Safety/Measure/safety_level_measure.c
    Safety/Input/safety_level_input.c
    Safety/Output/safety_analog_output.c
    Safety/Output/safety_relay_output.c
    Safety/Diagnostics/safety_stl.c
)

set(CPU2_FIELD_SOURCES
    Services/Modbus/dataanalysis_modbus.c
    Services/Hart/...
)

set(CPU2_DEV_SOURCES
    Application/Src/test.c
)

构建命令

cmake -S LTD_MAIN_CPU2 -B build/LTD_MAIN_CPU2_safety -G Ninja `
  "-DCMAKE_TOOLCHAIN_FILE=D:/CUBE/cmake/toolchain-arm-none-eabi.cmake" `
  -DCMAKE_BUILD_TYPE=Release `
  -DCPU2_VARIANT=SAFETY

cmake -S LTD_MAIN_CPU2 -B build/LTD_MAIN_CPU2_field -G Ninja `
  "-DCMAKE_TOOLCHAIN_FILE=D:/CUBE/cmake/toolchain-arm-none-eabi.cmake" `
  -DCMAKE_BUILD_TYPE=Release `
  -DCPU2_VARIANT=FIELD

九、实施阶段

阶段 工作内容 输出物 完成标准
1. 代码范围矩阵 逐个文件标注 S0/S1/S2/S3、是否进入 SAFETY、纳入理由和依赖。 CPU2安全功能代码范围矩阵.md 每个安全相关文件都有分类和理由。
2. 输出权限收口 把 AD5421 和 RELAY GPIO 写操作集中到 Safety/Output。 安全输出接口和调用替换记录 非安全模块不再直接写安全输出。
3. 找液位单路径化 安全版只保留认证用液位测量路径，剥离密度、水位、调试测量分支。 safety_level_measure.c 安全版液位路径唯一、可追踪。
4. 参数安全化 抽取 AO/DO、报警阈值、故障电流和量程参数，做范围、单位、互斥、CRC 检查。 safety_config.c/.h 参数更新必须通过安全接口。
5. 引入 X-CUBE-STL 通过 safety_stl.c 调度 CPU、Flash、RAM 自检。 STL 封装、链接脚本配置、启动/周期测试策略 STL 失败进入安全故障状态。
6. 双版本 CMake 取消自动 GLOB，建立 SAFETY/FIELD/DEV 显式源码清单。 改造后的 CMakeLists.txt 三个变体可独立构建，产物可区分。
7. 自动检查 增加扫描脚本，检查安全版中是否存在越权调用。 构建前检查脚本 检查失败时阻止安全版发布。

十、自动检查建议

自动检查不是替代代码审查，而是防止明显越权调用进入安全版。

检查项 失败条件 处理方式
安全版源码清单 test.c 或 S3 文件进入 SAFETY 构建失败
AD5421 写权限 非 Safety/Output 文件调用 AD5421_SetCurrent 构建前检查失败
继电器写权限 非 Safety/Output 文件写 RELAYx 构建前检查失败
安全参数更新 通信层直接修改安全参数并生效 代码审查或脚本扫描阻止
看门狗喂狗 中断或非安全任务直接喂狗 收口到安全监督健康检查后喂狗 
# 示例扫描目标，不是最终脚本
rg -n "AD5421_SetCurrent|HAL_GPIO_WritePin\\(RELAY" LTD_MAIN_CPU2
rg -n "test\\.c" LTD_MAIN_CPU2/CMakeLists.txt

十一、X-CUBE-STL 放置策略

X-CUBE-STL 只用于 MCU 自检，不能替代液位、AD5421、继电器和传感器诊断。建议只引入受控文件：

  • STM32_Safety_STL/Inc
  • STM32_Safety_STL/Lib/STL_Lib.a
  • STM32_Safety_STL/Src/stl_util.c
  • 基于模板定制的 stl_user_param.c
  • 链接脚本中的 backup_buffer_section
STL 的调用入口应放在 Safety/Diagnostics/safety_stl.c，由 safety_supervisor 调度。 STL 失败后不能交给通信层或应用层处理，应直接进入安全故障策略。

十二、架构验收标准

  1. SAFETY 构建不包含 test.c 和 S3 文件。
  2. SAFETY 构建不包含 Modbus/HART 直接输出逻辑。
  3. AD5421 和继电器输出只有 Safety/Output 可写。
  4. 找液位安全路径唯一、可追踪、可测试。
  5. STL、AD5421、继电器反馈、看门狗故障能统一进入安全状态。
  6. 每个安全相关文件都有 S0/S1 分类和纳入理由。
  7. SAFETY、FIELD、DEV 可独立构建，产物名称可区分。
  8. 安全版构建日志、源码清单、版本号和测试记录可追溯。
推荐第一步交付：先完成代码范围矩阵和 CMake 显式源码清单，再开始移动或拆分具体代码。 这样可以先把安全边界固定下来，避免边改边扩大认证范围。
