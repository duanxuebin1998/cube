# CPU2 编码规范

日期：2026-06-02

适用对象：`LTD_MAIN_CPU2` 固件源码、CPU2 安全相关软件设计、后续 SIL2 认证准备资料。

## 1. 目标

本规范用于约束 CPU2 固件的新代码、重构代码和安全相关代码，使代码逐步满足功能安全认证所需的可读性、可分析性、可追溯性和可验证性要求。

本规范不是 SIL2 认证结论。SIL2 认证仍需要系统级安全功能定义、硬件安全架构、FMEDA/FMEA/FTA、验证确认和认证机构评估。

## 2. 标准基线

CPU2 编码规范采用以下基线：

- MISRA C:2012 作为主要 C 语言安全子集。
- MISRA C:2012 Amendments 1-4 和 Technical Corrigenda 作为后续补充输入。
- SEI CERT C Coding Standard 作为安全缺陷、未定义行为和漏洞风险的补充规则来源。
- 项目 CPU2 专用规则用于覆盖电机、测量、通信、参数存储、日志和中断上下文的工程约束。

参考资料：

- [MISRA C:2012 Amendment 4](https://misra.org.uk/app/uploads/2023/03/MISRA-C-2012-AMD4.pdf)
- [SEI CERT C Coding Standard](https://wiki.sei.cmu.edu/confluence/display/c)
- [SEI CERT C Introduction](https://wiki.sei.cmu.edu/confluence/display/c/Introduction)

## 3. 适用范围

### 3.1 强制适用

以下模块属于第一批强制适用范围：

- `LTD_MAIN_CPU2/Application/Src/app_main.c`
- `LTD_MAIN_CPU2/Application/Src/fault_manager.c`
- `LTD_MAIN_CPU2/Application/Src/fault_recovery.c`
- `LTD_MAIN_CPU2/Application/Src/measure*.c`
- `LTD_MAIN_CPU2/Services/MotorControl/*.c`
- `LTD_MAIN_CPU2/Services/Encoder/*.c`
- `LTD_MAIN_CPU2/Services/Sensor/*.c`
- `LTD_MAIN_CPU2/Services/ParamStorage/*.c`
- `LTD_MAIN_CPU2/Services/Utilities/my_crc.c`
- `LTD_MAIN_CPU2/Core/Src/main.c`
- `LTD_MAIN_CPU2/Core/Src/stm32f4xx_it.c`

### 3.2 受控适用

以下代码参与构建，但允许通过偏离记录管理：

- STM32 HAL/CMSIS 代码。
- 启动汇编和链接脚本。
- CubeMX 生成的初始化文件。
- 已确认来自芯片厂商或第三方供应商的驱动代码。

### 3.3 非安全代码

以下代码不得作为安全功能实现依据：

- 调试命令。
- 现场临时测试函数。
- `Application/Src/test.c`。
- 单纯串口打印或人工观察日志。
- CPU3 显示逻辑。

非安全代码允许保留，但安全发布版应通过构建配置隔离，避免进入安全基线。

## 4. 规则分级

### 4.1 强制规则

违反强制规则时，必须修复或提交偏离记录并获得批准。

适用对象：

- 安全相关模块。
- 新增代码。
- 改动影响安全状态、运动控制、参数存储、故障处理、通信命令解析的代码。

### 4.2 需评审规则

违反需评审规则时，必须在代码评审中说明原因。若影响安全功能，需要升级为偏离记录。

适用对象：

- 存量业务流程。
- 测量算法。
- 通信协议适配。
- 历史代码局部修改。

### 4.3 建议规则

建议规则用于改善可维护性和一致性，不作为当前阶段构建门禁。

### 4.4 暂缓治理

暂缓治理只适用于历史代码。暂缓项必须有整改计划，不得作为新增代码的例外理由。

## 5. CPU2 强制规则

### CUBE-C-001 禁止动态内存

安全相关代码不得使用：

- `malloc`
- `calloc`
- `realloc`
- `free`

说明：CPU2 固件是资源受限的实时嵌入式系统，动态内存会引入碎片、释放后使用、分配失败和不可预测时延风险。

### CUBE-C-002 指针入参必须受控

所有指针入参必须满足至少一个条件：

- 函数入口显式检查 `NULL`。
- 函数注释明确说明调用者保证非空，并且调用点可验证。
- 指针仅来自静态对象或模块内部受控缓冲区。

安全相关函数优先使用入口检查。中断上下文函数不得因空指针进入阻塞或打印路径。

### CUBE-C-003 禁止未验证的数组访问

数组访问必须证明索引在范围内。通信帧、DMA 缓冲区、Modbus 寄存器、FRAM 数据、测量点数组必须携带长度或使用固定边界常量。

禁止把外部输入直接作为数组下标。

### CUBE-C-004 类型转换必须显式且可证明

以下转换必须通过命名 helper 或局部范围检查完成：

- 宽整数到窄整数。
- 有符号整数到无符号整数。
- 无符号整数到有符号整数。
- 浮点到整数。
- 整数到浮点后参与安全阈值判断。
- 指针类型转换。

允许的转换必须说明：

- 输入范围。
- 溢出处理。
- 单位换算。
- 饱和或钳位策略。

### CUBE-C-005 安全判断优先使用定点数

以下逻辑原则上不得依赖浮点直接比较：

- 电机停止条件。
- 上下限位判断。
- 探头撞底或碰撞判断。
- 故障触发阈值。
- 看门狗健康条件。
- 安全态进入条件。

如确需使用浮点，必须记录误差范围和偏离理由。

### CUBE-C-006 禁止复杂函数式宏

函数式宏只允许用于简单常量封装、编译期断言或轻量包装。包含多语句、赋值、副作用、隐式返回、重复求值风险的宏必须改为 `static inline` 或普通函数。

### CUBE-C-007 禁止静默丢弃错误

硬件访问、通信、参数存储、运动控制、传感读取、CRC 校验函数的返回值不得静默丢弃。

允许写 `(void)` 丢弃返回值的场景：

- 调用目的只是尽力清理。
- 后续有独立诊断确认。
- 函数注释或局部注释说明失败不会改变安全结论。

### CUBE-C-008 安全路径禁止直接依赖打印

安全相关路径不得用 `printf` 作为动作依据或状态同步机制。

以下位置禁止直接打印：

- 中断服务函数。
- 看门狗喂狗路径。
- 电机紧急停机路径。
- 故障态切换关键区。
- 安全输出控制路径。

如需要记录，优先使用延迟日志或固定长度事件缓存。

### CUBE-C-009 中断上下文不得阻塞

中断服务函数不得调用：

- `HAL_Delay`
- 长时间轮询等待。
- 非确定性打印。
- 可能阻塞的通信发送。
- 需要互斥锁或复杂状态机的函数。

中断中只能做快速采样、置位、清标志、读取必要寄存器和记录轻量事件。

### CUBE-C-010 看门狗喂狗必须受健康监督控制

看门狗刷新不得只由定时中断自动执行。安全发布版应改为健康监督模型：

- 主循环周期正常。
- 电机控制任务正常。
- 传感读取任务正常。
- 通信解析任务正常。
- 故障管理任务正常。
- 安全输出状态可确认。

全部条件满足后才允许喂狗。

### CUBE-C-011 全局变量必须受控

安全相关全局状态不得随意 `extern` 访问。应优先通过模块接口读写。

ISR 和主循环共享变量必须：

- 使用 `volatile`。
- 说明读写上下文。
- 对多字节共享状态说明一致性策略。

### CUBE-C-012 参数必须有范围和完整性保护

从 FRAM、Modbus、CPU3、传感器或串口命令获得的参数必须经过：

- 范围检查。
- 单位检查。
- CRC 或协议校验。
- 默认值兜底。
- 安全边界钳位。

未经校验的参数不得直接影响电机运动、安全阈值和故障状态。

### CUBE-C-013 安全相关状态机必须完整处理默认分支

`switch` 处理命令、状态、错误码时必须有 `default`，并明确未知值的安全策略。

未知命令不得执行动作。未知状态不得继续运动。

### CUBE-C-014 构建基线必须显式

安全发布版不得依赖 `file(GLOB...)` 自动收集源码。构建脚本应列出明确源码清单。

安全发布构建不得包含 `test.c`、临时调试文件和未评审工具代码。

### CUBE-C-015 中文和编码必须受控

新增 Markdown 文档使用 UTF-8。修改 CPU2 既有源码时必须保留原编码，不得批量转换历史文件。

对已存在乱码的源码，不在编码规范整改中做批量修复，只在局部修改时按原编码维护并保留可读性。

## 6. CERT C 重点补充规则

CPU2 第一阶段重点关注以下 CERT C 分类：

- `PRE`：预处理器，限制复杂宏和条件编译。
- `DCL`：声明与初始化，禁止未初始化对象。
- `EXP`：表达式，避免副作用和未定义行为。
- `INT`：整数，治理溢出、符号转换和截断。
- `FLP`：浮点，治理异常值和精度风险。
- `ARR`：数组，防止越界。
- `STR`：字符串，防止缓冲区溢出和未终止字符串。
- `MEM`：内存管理，禁止动态内存。
- `ERR`：错误处理，统一返回值和故障状态。
- `CON`：并发，处理中断和主循环共享状态。

## 7. MISRA C 第一阶段重点

第一阶段不追求一次性全量 MISRA 合规，优先治理以下类别：

- 预处理器和宏。
- 类型转换。
- 指针和数组。
- 控制流完整性。
- 返回值处理。
- 外部链接和全局状态。
- volatile 和中断共享状态。
- 不可达代码和测试代码隔离。

## 8. 代码评审要求

安全相关代码评审至少检查：

- 是否改变安全状态或运动控制。
- 是否改变故障码传播。
- 是否引入新全局变量。
- 是否引入新强制类型转换。
- 是否引入新函数式宏。
- 是否引入阻塞等待。
- 是否引入直接打印。
- 是否增加外部输入到数组索引、寄存器地址或 FRAM 地址的路径。
- 是否需要更新偏离记录。
- 是否需要更新测试用例。

## 9. 验证要求

编码规范落地后的最低验证：

- `cmake --build build\LTD_MAIN_CPU2`
- `git diff --check`
- CPU2 编码规范检查脚本或静态分析工具报告。
- 安全相关模块人工评审记录。
- 偏离记录清单。

如果工具链不可用，必须记录未执行原因，并保留已完成的静态搜索或人工检查结果。

## 10. 分阶段门禁

### 10.1 第一阶段门禁

- 新增代码不得违反强制规则。
- 安全相关改动必须完成代码评审。
- 新增偏离必须填写记录。
- 文档默认只保留 Markdown。

### 10.2 第二阶段门禁

- 安全相关模块不得存在未分类违反项。
- 构建清单显式化。
- `test.c` 与安全发布构建隔离。
- 建立静态分析报告归档。

### 10.3 第三阶段门禁

- 安全相关模块的强制规则违反项清零。
- 所有保留违反项都有批准的偏离记录。
- 关键安全函数有单元测试或等效验证证据。
- 工具链版本和规则配置可追溯。

## 11. 与版本和提交的关系

编码规范文档和检查表属于流程资料，单独新增不改变 CPU2 固件版本。

后续如果修改源码、构建脚本、安全发布配置或测试代码隔离方式，应按项目版本规则评估是否需要升级 CPU2 固件版本。
