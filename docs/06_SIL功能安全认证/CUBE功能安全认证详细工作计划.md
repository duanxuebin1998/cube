# CUBE 功能安全认证详细工作计划

更新日期：2026-06-06

## 1. 计划定位

本计划用于指导 CUBE 后续功能安全认证准备工作，重点结合当前 `docs/06_SIL功能安全认证` 资料、NMS81 案例整理、ST/X-CUBE-STL 资料和 CPU2/CPU3 程序现状，形成可执行的工程路线。

本计划不是 SIL 认证结论。当前需求调整为参考 NMS8x/NMS81 单通道 HFT=0 路线做 SIL2 准备，不做 SIL3。CUBE 是否能声明 SIL2，仍必须由系统级危险分析、SIF 定义、硬件架构、FMEDA/FMEA、软件生命周期证据、验证确认和认证机构评估共同决定。

### 2.2 当前程序观察

| 区域 | 当前观察 | 对认证工作的影响 |
| --- | --- | --- |
| 构建基线 | `LTD_MAIN_CPU2/CMakeLists.txt` 和 `LTD_DISPLAY_CPU3/CMakeLists.txt` 使用 `file(GLOB...)` 或 `file(GLOB_RECURSE...)` 自动收集源码 | 安全发布构建不可追溯，且容易把 `test.c` 等调试源码带入安全基线，必须改成显式源码清单 |
| 启动和主循环 | CPU2 `main.c` 初始化后进入 `app_main()`，`app_main.c` 初始化继电器、电机、参数、故障信息，并支持上电默认命令 | 需要定义上电安全态、自检完成前禁止运动、初始化失败后的安全输出和故障锁存策略 |
| 看门狗 | `stm32f4xx_it.c` 中存在定时中断刷新 `HAL_IWDG_Refresh(&hiwdg)` | 需要改为健康监督喂狗，不能由中断自动喂狗掩盖主循环或安全监督失效 |
| 中断和打印 | `stm32f4xx_it.c` 中断接收路径存在 `printf`，安全相关模块中也有大量直接打印 | 需要把安全路径打印改成延迟日志或事件记录，ISR 中禁止打印和重操作 |
| 故障处理 | `fault_manager.c` 是统一故障入口，调用 `MotorCtrl_SlowStop()` 停机并记录错误 | 需要证明停机失败会升级为安全故障，错误码不会丢失，故障态不会被普通流程覆盖 |
| 自动恢复 | `fault_recovery.c` 支持按命令白名单和重试次数自动恢复 | 需要明确哪些 SIF 允许自动恢复，哪些故障必须人工确认；恢复期间安全状态和输出必须可证明 |
| 电机和测量 | `measure*.c`、`motor_ctrl_*`、编码器、称重、水位等参与运动和测量 | 需要逐项做安全需求、边界、返回值、超时、停机确认和故障注入验证 |
| 参数存储 | `system_parameter.c` 已有 FRAM A/B、magic、version、CRC、协议版本和默认值逻辑 | 需要补齐安全参数清单、范围、单位、写保护、SIL 锁定、变更审批和 proof test 触发规则 |
| 继电器输出 | `relay_output.c` 已有四路继电器方式2 HH/H/L/LL 报警配置、失效值策略、手动抑制和运行态输出 | 若继电器作为安全相关输出，需要定义触点安全态、上电默认态、故障态、手动抑制条件、反馈诊断和 proof test |
| HART/4-20 mA | `Services/Hart` 和 AD5421 引脚资料存在，但当前安全功能边界未确认 | 若 4-20 mA 作为安全输出，需要定义失败电流、输出自检、AD5421 fault 处理和逻辑单元判据 |
| CPU3/Modbus | CPU3 显示、外部 Modbus 和协议版本管理存在 | 参考 NMS81，Modbus 和显示默认应定位为诊断/维护信息，不应作为唯一安全动作通道 |

### 2.3 NMS81 案例对 CUBE 的关键约束

- 证书只能证明设备在规定型号、版本、配置、输出和生命周期条件下具备能力，不能自动证明整条 SIF 达到目标 SIL。
- 安全功能必须在 SRS 中写清楚：输入、触发条件、安全动作、安全状态、响应时间、允许旁路、proof test 和失败处理。
- 安全相关输出应优先落在继电器、故障电流或专用停机输出；Modbus、HART、显示和调试日志只能作为信息或维护通道。
- SIL 锁定、参数确认、维修后复测、修改控制和 proof test 记录是证据包的一部分。
- NMS81 单通道 HFT=0 时可用于最高 SIL 2；HFT=1 冗余架构才讨论 SIL 3。CUBE 当前目标按单通道 SIL2 路线准备，SIL3 冗余架构不纳入当前需求。

## 3. 总体推进原则

1. 先定范围再改代码：先确定申请或评估的安全功能，不把普通测量、显示、通信全部默认纳入安全功能。
2. 先安全输出再信息通道：安全相关动作以 CPU2、继电器、故障电流、停机输出为核心，CPU3/Modbus 只作为诊断和维护通道。
3. 先证据链再工具报告：MISRA、静态分析和单元测试必须追溯到软件安全需求和设计项。
4. 安全发布构建独立：安全版、现场版、开发调试版要有明确源码清单、编译开关、版本标识和发布记录。
5. 所有偏离受控：历史代码可分阶段整改，但保留项必须有偏离记录、风险说明、缓解措施和验证证据。
6. 不把外部资料结论直接照搬：ST Safety Manual、FMEA/FMEDA、X-CUBE-STL 和 NMS81 案例只能作为输入，必须转化为 CUBE 项目假设和验证项。

## 4. 认证工作阶段计划

### 阶段 0：认证策略和范围确认

目标：明确 CUBE 按 NMS81 单通道思路做 SIL2 产品能力准备，还是作为项目系统的一部分做 SIL2 SIF 级安全评估。

| 工作项 | 负责人建议 | 输出物 | 验收标准 |
| --- | --- | --- | --- |
| 确认 SIL2 目标、认证类型和认证机构沟通路线 | 项目负责人、质量、认证接口人 | `认证策略与范围说明.md` | 明确目标为 SIL2、适用标准、认证对象、认证机构和计划边界 |
| 确认硬件版本、CPU2/CPU3 版本、传感器、继电器、4-20 mA、供电和下游逻辑单元范围 | 系统工程师、硬件、软件 | `系统边界和配置基线.md` | 形成可审查的硬件/软件/配置基线 |
| 明确不做 SIL3 的范围边界 | 项目负责人、系统安全工程师 | `02_软件架构/SIL2目标与SIL3排除说明.html` | 说明当前不做 SIL3，不启动冗余 HFT/CCF 专项；后续若改为 SIL3 必须重新立项 |

优先级：P0。没有阶段 0 结论，后续软件整改只能算工程治理，不能形成认证范围。

### 阶段 1：SIF 和软件安全需求

目标：把系统级危险分析和安全目标拆成可验证的软件需求。

| 工作项 | 主要输入 | 输出物 | 验收标准 |
| --- | --- | --- | --- |
| 建立 SIF 清单 | HAZOP/LOPA、现场工艺、安全目标、NMS81 案例字段 | `SIF清单与安全状态定义.md` | 每条 SIF 有名称、输入、触发条件、安全动作、安全状态、响应时间和 proof test 入口 |
| 编写软件安全需求规格 | SIF 清单、CPU2 模块清单、ST Safety Manual、现有程序 | `软件安全需求规格.md` | 每条需求唯一编号、可验证、可追踪 |
| 建立需求追踪矩阵 | SRS、架构、代码、测试 | `软件需求追踪矩阵.xlsx` 或 `.md` | 需求能追踪到设计、代码文件、测试用例和验证记录 |
| 定义安全相关参数 | 参数存储、Modbus 寄存器、四路继电器方式2报警配置、自动恢复参数 | `安全相关参数清单.md` | 标明单位、范围、默认值、写权限、锁定规则、变更后验证要求 |

第一批建议 SIF 候选：

| SIF 候选 | 输入 | 安全动作 | 备注 |
| --- | --- | --- | --- |
| 高高/高/低/低低液位继电器报警 | 液位测量值、继电器配置、参数 CRC | 继电器进入安全报警态，必要时故障电流 | 当前 `relay_output.c` 可作为实现基础，SIF 可按现场风险选择 HH/LL 或 H/L 子集，但需定义触点安全态和 proof test |
| 电机异常停机 | TMC5130 状态、编码器、运动超时、停机反馈 | 停止运动、锁存故障、禁止继续测量 | 当前 `fault_manager.c` 和 `motor_ctrl_*` 需要重点证明 |
| 罐底/下行保护 | 编码器位置、称重、传感器、测量流程状态 | 停止下行、进入故障或保护态 | 当前 `measure_tank_height.c`、`Weight`、电机位置模型相关 |
| 参数损坏安全态 | FRAM magic/version/CRC、协议版本、参数范围 | 拒绝危险运动，恢复默认安全参数或锁存故障 | 当前参数 CRC 已有基础，但需补安全参数策略 |
| MCU 自检失败安全态 | X-CUBE-STL 或等效诊断、看门狗健康监督 | 输出安全态，锁存诊断故障 | 需先完成 STL 采用决策和调度设计 |

建议的软件分层：

| 层级 | 包含内容 | 处理原则 |
| --- | --- | --- |
| 安全核心 S0 | 启动安全态、safety supervisor、fault manager、停机、继电器/故障电流输出、看门狗健康监督 | 强制编码规范、强制审查、强制测试 |

| 设计 STL wrapper | `Safety/Diagnostics/safety_stl.c` 方案 | `STL集成设计.md` | 业务代码不直接调用 STL，失败统一进入安全故障 |
| 实测诊断耗时 | CPU2 主循环、继电器输出、看门狗窗口 | `安全诊断调度和耗时报告.md` | STL 或等效诊断不破坏实时性和看门狗策略 |

必须避免的表述：不能把 X-CUBE-STL 写成“装上即满足 SIL2”。它只能提供 MCU 内核、Flash、RAM 等诊断输入，不能替代液位、传感器、AD5421、继电器、参数和整机级验证。

| 用例 | 注入方式 | 期望结果 |
| --- | --- | --- |
| FRAM A/B 参数 CRC 失败 | 修改 CRC 或模拟读取错误 | 不使用危险参数，进入默认安全策略或锁存参数故障 |

| 看门狗健康条件缺失 | 阻塞主循环或安全监督任务 | 不再由中断喂狗，系统按设计复位或进入安全态 |

## 8. 当前最大风险

| 风险 | 影响 | 建议处理 |
| --- | --- | --- |
| 未定义具体 SIF 就开始整改代码 | 认证证据无法追溯，整改方向可能返工 | 阶段 1 优先，先冻结 SIF 和 SRS |
| 单通道架构口径不清 | 认证机构可能认为目标和架构假设不一致 | 明确当前只按 SIL2 路线准备；SIL3 需重新立项并做冗余和 HFT/CCF 专项 |
| 安全输出边界不清 | Modbus/显示/日志可能被误当安全动作 | 明确继电器、故障电流或专用停机输出为安全相关输出 |
| 自动 GLOB 构建和 test.c 混入 | 安全发布基线不可追溯 | P0 立即改安全版显式源码清单 |
| 中断喂狗和 ISR 打印 | 主循环失效可能被掩盖，实时性不可证明 | P0 改健康监督喂狗，ISR 延迟处理 |
| 大量直接打印、阻塞等待和浮点安全判断 | MISRA/实时性/可验证性风险高 | 按 S0/S1 优先级分批整改和偏离 |
| 参数没有 SIL 锁定和变更控制 | 现场改参后安全功能不再满足假设 | 建立安全参数清单、锁定、解锁、复测和记录 |
| 缺少供应商安全资料 | PFDavg/PFH、FMEDA 和 proof test 周期无法闭环 | 尽早索取传感器、继电器、AD5421、下游逻辑单元资料 |
