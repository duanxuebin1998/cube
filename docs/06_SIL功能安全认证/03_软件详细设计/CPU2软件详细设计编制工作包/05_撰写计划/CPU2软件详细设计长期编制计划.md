## 2. 编制目标

建立一套可以长期维护、分批撰写、分卷渲染和分卷评审的 CPU2 软件详细设计文件，最终满足以下目标：

1. 模块、函数、接口、参数、故障和执行上下文均可追踪到当前批准基线。
2. 每个设计结论都能区分源码证据、静态检查、构建、测试、台架、现场和认证证据。
3. 单册长度受控，避免一个超长 Word 导致编辑、渲染和评审效率下降。
4. 分册之间不重复维护同一份事实，通过总册、设计编号和交叉引用建立关系。
5. 版式、表格和流程图与一代参考文档及 V0.4 基准保持一致。
6. 后续固件变化可以按影响范围只更新相关分册，不必重做整个文档。

文档完成只表示软件设计资料达到对应评审状态，不表示整机已经通过 SIL2、硬件台架、故障注入或认证机构评估。

## 3. 编制范围与明确不做

### 3.1 本计划范围

- CPU2 启动、初始化、应用调度和命令处理。
- 测量、电机、位置模型、编码器、传感器和扭力诊断。
- CPU2/CPU3 内部通信、外部设备接口和共享数据。
- 参数、运行态、FRAM 持久化、版本迁移和掉电边界。
- 故障管理、错误码传递、故障恢复、安全动作和执行上下文。
- AO/HART、继电器、电源、看门狗和底层外设服务。
- 需求、设计、代码、测试和证据追踪。
- 编码规范、构建隔离、维护约束和未验证风险。

### 3.2 本计划不直接执行

- 不修改固件行为。
- 不改变协议、参数语义、错误码或安全动作。
- 不升级 CPU2、CPU3 或共享协议版本。
- 不把代码审查、构建或文档渲染表述为硬件和 SIL 验证。
- 不在资料不足时推定传感器端、机械系统或现场设备行为。
- 不在用户未授权时暂存、提交或推送。

发现源码与需求、安全目标或旧资料冲突时，先登记差异和影响，再由用户决定是修正文档、修改软件还是补充验证。

## 6. 证据状态规则

每项设计结论使用以下证据状态之一，不使用含义不清的“已确认”：

| 状态 | 含义 |
| --- | --- |
| 源码已核对 | 已在指定基线的源码、头文件或构建配置中找到直接证据 |
| 文档已核对 | 已与批准的需求、协议、规范或设计资料核对 |
| 静态检查通过 | 仅完成文本、规则或静态分析检查 |
| 构建通过 | 仅证明目标基线能够完成对应构建 |
| 主机测试通过 | 已执行不依赖真实硬件的自动测试 |
| 台架验证通过 | 已记录真实板卡、仪器、固件、步骤和结果 |
| 现场验证通过 | 已记录真实设备、场景、版本和原始证据 |
| 认证证据 | 已纳入安全生命周期并由授权角色或认证机构接受 |
| 待确认 | 当前资料不足或存在冲突，需要补充决策 |
| 待验证 | 设计或实现已描述，但对应验证尚未执行 |

同一设计项可以同时具有多个证据状态，例如“源码已核对、构建通过、台架待验证”。

## 9. 各分册详细工作分解

### 9.1 总册

输入：

- 用户批准范围。
- 固件、协议和参数存储基线。
- 分册版本和评审状态。
- 术语、需求和风险总表。

任务：

1. 建立文档信息、版本记录和适用范围。
2. 固化 CPU2/CPU3/协议/参数存储四条版本轴。
3. 建立系统上下文、模块总图和分册依赖关系。
4. 维护全局术语、设计编号和证据状态。
5. 汇总各册未验证项，不复制分册详细内容。

验收：

- 任一读者可以从总册定位到对应分册、设计项和证据状态。
- 总册不包含与分册相互冲突的第二份模块细节。

### 9.2 第1分册：总体架构与运行框架

章节：

- 软件分层与模块边界。
- MCU 启动、HAL/时钟/外设初始化。
- `App_Init()` 和应用服务初始化。
- `App_MainLoop()`、命令接收和业务调度。
- 周期任务、后台任务和看门狗喂狗。
- ISR、DMA、PendSV 和主循环上下文。
- 模块依赖、共享状态和可重入约束。

验收：

- 启动到进入稳定主循环的调用链可追踪。
- 正常、无命令、命令切换、错误和恢复调度路径均有说明。
- 中断上下文不被误写成普通任务上下文。

### 9.3 第2A/2B分册：测量、运动与传感器

拆分原则：拆分前 V0.4 超过单册 70 页上限，按专业域拆成第2A分册《测量与传感器》和第2B分册《运动、位置与编码器》。两册分别维护封面、版本记录、目录和正文页码，通过设计编号和跨卷说明保持关系。

章节：

- 第2A分册：测量命令总调度，以及油位、水位、罐高、密度、SI Profile、零点和固定频率闭环。
- 第2B分册：电机驱动参数、运动 API、位置模型、位置源切换、尺带拟合和失步检测。
- 第2B分册：AS5145 编码器采集、原点、持久化和诊断。
- DSM、LTD、传感器安全协议、无线配对和 RSSI 管理。
- 扭力、频率和辅助诊断。

验收：

- 每种测量说明入口、状态机、完成条件、提前退出和故障出口。
- 电机动作与位置、编码器、扭力和传感器结果的依赖关系清楚。
- 传感器端或机械系统未验证行为明确标记。

### 9.4 第3分册：通信、接口与数据

章节：

- CPU2/CPU3 共享 Modbus 物理层、帧层和地址层。
- `DEVICE_PROTOCOL_VERSION` 检查和兼容性。
- `DeviceParameters`、状态、命令、ACK 和错误码。
- UART、DMA、CRC、超时和重试。
- CPU2 权威数据、CPU3 快照和写后补读边界。
- CPU2 与传感器、AO/HART、继电器及调试串口的接口。

验收：

- 每个接口明确方向、所有者、长度、字节序、倍率、更新条件和异常行为。
- 发送成功与响应成功、持久化成功与运行态生效不得混淆。

### 9.5 第4分册：参数管理与 FRAM 持久化

章节：

- 参数类型、范围、单位、默认值和入口。
- 参数校验、归一化、运行态同步和消费点。
- FRAM 驱动、记录结构、CRC 和版本。
- A/B 区、写后校验、迁移和恢复默认。
- 掉电中断、延迟写入、PendSV 和失败回滚。
- `DEVICE_PARAM_VERSION` 与固件版本关系。

验收：

- 每个关键参数完成“入口-校验-持久化-运行态-消费-输出-恢复”追踪。
- 未完成真实掉电和故障注入验证的项目保持“待验证”。

### 9.6 第5分册：故障、恢复与安全机制

章节：

- 故障分类和错误码。
- `fault_manager` 的故障置位、最终出口和停机职责。
- `fault_recovery` 的恢复上下文、白名单、取消和重跑请求。
- 错误日志、重试、恢复成功和最终报错。
- 电机、测量、通信、AO 和继电器的安全动作。
- 电源监测、看门狗、中断和 PendSV 边界。
- 安全状态、进入、保持、退出和人工处置。

验收：

- 具体错误码不会在设计描述中被压缩成通用失败。
- 故障检测、安全动作、锁存、恢复和清除链路完整。
- 源码行为与硬件诊断覆盖、FTTI 和 SIL 结论严格分开。

### 9.7 第6分册：输出控制与硬件服务

章节：

- AO 和 AD5421 初始化、输出、诊断与看门狗。
- HART 数据交换和并发边界。
- 继电器配置、输出、反馈和报警判定。
- 电源监测、外部看门狗及关键 GPIO。
- SPI、UART、DMA、定时器、CRC 和 BSP 驱动。
- 调试、测试和安全构建隔离。

验收：

- 每个硬件服务说明初始化顺序、寄存器/接口、失败表现和上层消费。
- 寄存器配置和真实硬件效果分别标注证据状态。

### 9.8 第7分册：追踪、验证与附录

章节：

- 需求-设计-代码-测试追踪矩阵。

## 10. 并行协作规则

允许多个智能体并行执行只读盘点和独立模块分析，必须遵守：

1. 同一时间只有一个写入者生成或修改正式 Word。
2. 子智能体按分册或模块边界返回结构化底稿，不同时修改同一个 DOCX。
3. 每份底稿必须包含文件路径、符号和行号，不只给结论。
4. 主写入者统一术语、编号、证据状态、表格和版式。
5. 合入 Word 前重新检查源码是否发生漂移。
6. 发现并行修改时，只继续处理能够安全分离的章节。

## 11. Word 和流程图实施策略

- 每个分册独立 DOCX、独立版本记录、独立目录和独立页码。
- 总册维护分册清单和适用版本，不把所有分册嵌入一个 Word。
- 每完成一个有实质内容的章节，立即渲染该分册全部页面。
- 渲染预览写入 `tmp/<任务号>/`，不进入正式文档目录。
- V0.x 编制阶段暂不机械生成正式 PDF；到用户指定评审节点统一导出 PDF。
- 流程图继续使用白底、黑色细线、原生判断框和 V0.4 箭头留白标准。
- 正式流程图必须同时保留 Word 中的可编辑 Visio 对象和独立 VSDX。
