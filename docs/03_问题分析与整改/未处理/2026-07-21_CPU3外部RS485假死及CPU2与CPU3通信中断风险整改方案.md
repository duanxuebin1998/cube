## 1. 一页结论

用户通过 COM3 持续发送数据，已稳定复现以下整机现象：

- 屏幕停止刷新，按键不能控制；
- 停止发送及断开 COM3 后不能自动恢复；
- COM1、COM2 同时失去通信能力；
- 调试串口 COM12 停止打印；
- CPU3 电源正常，`NRESET` 无动作，设备不重启。

ST-Link 以 Hot Plug 方式接入，未下载、未复位、未修改 Flash。第二次复现后连续 12 次随机暂停，12 次全部落在 `USART3_IRQHandler()`、`uart_idle_rx_dma_ready()` 或 `HAL_UART_IRQHandler()` 中。寄存器同时显示：

- COM3 普通模式 DMA 已收满并停止：`DMA1_Stream1 NDTR=0`、`EN=0`；
- `USART3_SR=0x000001F8`，其中 `ORE`、`IDLE`、`RXNE` 同时置位；
- `USART3_CR1=0x0000201C`，`IDLEIE=1`，IDLE 中断仍开启；
- `USART3_CR3=0x00000000`，`DMAR=0`、`EIE=0`，DMA接收和错误中断已关闭；
- `SCB->ICSR=0x00000837`，活动异常号为 55，即 USART3；
- `CFSR=0`、`HFSR=0`，没有 HardFault、BusFault 或 UsageFault。

根因已经从“高可信推断”升级为“实机确认”：

```text
COM3连续流量填满512字节普通DMA
  → HAL关闭DMAR、PEIE和EIE，但工程没有用户态RxCplt回调
  → 自定义IDLEIE仍保持开启
  → 后续字节触发RXNE、ORE和IDLE
  → 自定义IRQ前置分类发现ORE后提前返回，不清IDLE
  → HAL因EIE/RXNEIE/PEIE均关闭，也不处理本次错误
  → IDLE触发源始终未清，CPU无限重入USART3_IRQHandler
  → 主循环、OLED、按键、COM1/COM2、CPU2调度和COM12日志全部停摆
  → 更高优先级TIM4仍无条件喂IWDG，设备长期不复位
```

这不是 MCU 内核硬死，也不是 HardFault，而是确定性的 USART3 中断活锁。此前静态分析发现的“错误回调中立即重启 DMA 可能形成恢复风暴”仍是需要整改的次生风险，但不是本次实机假死的直接路径。

整改提交 `490820b` 已完成以下内容：

1. **P0 消除活锁**：COM1/COM2/COM3和板间UART5均补齐DMA收满接管；UART错误出口先关闭IDLEIE、执行`SR→DR`清除、停止DMA并丢弃候选帧；DMA启动成功后才重新开启IDLEIE。
2. **P1 最小隔离和自恢复**：ISR只隔离端口和投递事件，主循环按四个端口独立执行100 ms退避恢复；外部COM口异常即时日志按端口至少间隔1秒，5秒摘要输出收满及恢复计数。
3. **P1 看门狗兜底**：CPU3的TIM4只有观察到启动阶段、主循环关键阶段或CPU2事务边界的健康代际推进才喂IWDG；单次响应等待循环内部不持续续票，原USART3中断活锁将不再被TIM4永久掩盖，同时避免正常启动Logo和连续板间事务误复位。
4. **P1完整恢复**：普通错误/收满执行100 ms后RX DMA恢复；`App_Init`加载参数后的启动重配置、运行期参数重配置和协议切换发生HAL重初始化失败时进入“完整UART重初始化+RX DMA”队列，仅重试失败端口；UART5发送失败后的接收回退若失败也进入统一恢复队列。
5. **同类问题扫描和CPU2最小修复**：CPU2三处512字节接收长度改为16位；四路普通DMA接收统一按“先关IDLEIE、DMA成功后再开IDLEIE”恢复；增加收满/错误回调；HART和UART5板间Modbus由硬件UART IRQ投递到最低优先级PendSV执行；FC03/04、FC10和HART声明长度在业务解析前校验；TIM4只检查恢复并触发PendSV，不依赖不可更改的阻塞式主循环。
6. **暂缓的架构项**：尚未实现100/500/1000 ms多级退避、循环/双缓冲DMA和统一`t3.5`帧边界；CPU2 SPI5编码器DMA回调仍包含解析、重试和日志/FRAM风险，须在SPI4/FRAM并发边界明确后单独整改。

该整改未改变CPU2阻塞式主循环、业务协议、寄存器、命令、参数含义、FRAM结构和合法帧处理顺序。发布阶段将CPU2由V1.30.0.0升至V1.30.1.0、CPU3由V1.29.0.0升至V1.29.1.0，并由 `490820b` 交付。COM3短回归已通过，但当前完整代码仍未完成全部台架验收。

## 3. 确定性根因

### 3.1 DMA普通模式收满后留下IDLE中断

COM3接收DMA配置为`DMA_NORMAL`，缓冲区为512字节。HAL的`UART_DMAReceiveCplt()`在普通模式收满后会：

1. 将`RxXferCount`置零；
2. 关闭`PEIE`和`EIE`；
3. 关闭`DMAR`；
4. 将UART接收状态置为READY；
5. 调用用户`HAL_UART_RxCpltCallback()`。

当前工程没有实现用户态`HAL_UART_RxCpltCallback()`。工程使用自定义`HAL_UART_Receive_DMA()+IDLEIE`，不是HAL的ReceiveToIdle模式，所以HAL完成回调不会替工程关闭自定义开启的`IDLEIE`。最终形成：

```text
DMA已停止、错误中断已关闭、IDLE中断仍开启、没有用户恢复入口
```

### 3.2 错误优先分类与HAL状态形成死锁组合

USART3 IRQ先调用`uart_idle_rx_dma_ready()`，再调用`HAL_UART_IRQHandler()`。

前置函数读取一次SR。如果`PE/FE/NE/ORE`任一置位，`CPU3_UartClassifyRxIrq()`返回ERROR，`uart_idle_rx_dma_ready()`在第199行直接返回。该路径没有清除IDLE，也没有关闭IDLEIE。

随后HAL读取同一组错误标志，但HAL只有在以下任一中断源开启时才进入错误处理：

- `CR3.EIE=1`；
- `CR1.RXNEIE=1`；
- `CR1.PEIE=1`。

实机快照中三者均为0，因此HAL既不会清错误，也不会调用用户错误回调。IRQ返回时，`IDLEIE=1`且`IDLE=1`仍成立，NVIC立刻再次进入USART3 IRQ。

本问题违反了UART ISR的基本不变量：

> 中断函数返回前，所有已使能且已挂起的触发源必须已经被清除，或者对应中断必须被关闭并投递到受控恢复路径。

### 3.3 看门狗为什么没有复位

USART3和DMA1 Stream1中断优先级为1；TIM4中断优先级为0，高于USART3。TIM4每次中断都直接执行`HAL_IWDG_Refresh()`，不检查主循环是否推进。

因此USART3即使占满除TIM4以外的CPU时间，TIM4仍可抢占并刷新IWDG。设备表现为屏幕、按键、通信和日志全部停止，但永不自动复位。

### 3.4 已确认根因与次生风险分层

| 风险 | 当前证据 | 状态 |
| --- | --- | --- |
| DMA收满后`IDLE+ORE`无法清除导致USART3中断活锁 | 实机寄存器、12/12 PC采样、带副作用SR→DR读取后恢复 | 已确认直接根因/P0 |
| TIM4独立于主循环无条件喂狗 | 故障现场与整改前源码证据 | 历史放大因素；CPU3 已改为健康代际门控，CPU2 残余归 C-08 |
| 错误回调中立即停DMA并重启，持续错误下可能形成恢复风暴 | 当前源码静态证据 | 已确认代码风险，尚未单独量化/P1 |
| 单个端口异常影响COM1/COM2、OLED、按键、CPU2和日志 | 实机现象 | 已确认系统影响/P0 |
| A-B短接产生的具体错误类型、电流和收发器行为 | 用户先前现场描述；本轮在线取证为COM3发包复现 | 待独立硬件故障注入 |

## 4. 整改目标和设计不变量

### 4.1 整改目标

1. 任一COM口DMA收满、UART错误或持续异常流量时，不得形成中断活锁。
2. 单端口异常只能隔离该端口，OLED、按键、CPU2和其它COM口继续运行。
3. ISR执行时间有界，只锁存事件、关闭/清除必要触发源并释放DE。
4. 主循环按端口独立、限频、可退避地恢复DMA接收。
5. DMA收满数据视为溢出垃圾，不进入协议解析和业务控制。
6. IWDG能识别主循环长期不推进，且正常端口隔离不会造成复位循环。
7. 异常解除后端口自动恢复，无需断电。

### 4.2 必须保持的不变量

| 编号 | 不变量 |
| --- | --- |
| I01 | UART IRQ退出时不存在“中断源已使能且触发标志未清除”的组合。 |
| I02 | `NDTR=0`或DMA停止后，必须由RxCplt/overflow事件接管；不能等待永远不会到来的下一次正常IDLE帧。 |
| I03 | 发生`ORE/FE/NE/PE`后，本次候选帧整体丢弃，不允许部分数据进入协议层。 |
| I04 | ISR不得`printf`、循环恢复、忙等或反复调用DMA初始化。 |
| I05 | 每个端口拥有独立事件、计数、退避和恢复时刻，禁止跨端口共用恢复标志。 |
| I06 | 只有DMA启动成功后才能重新开启IDLEIE；启动失败期间保持端口隔离。 |
| I07 | CPU3 TIM4只有观察到前台有界阶段健康代际推进时才允许刷新IWDG；等待响应循环内部不得持续续票。 |
| I08 | CPU2主循环是阻塞式且不可更改；CPU2 UART恢复和HART/板间Modbus调度不得依赖主循环。 |
| I09 | 运行期UART初始化失败不得进入`Error_Handler()`；普通DMA恢复与完整UART重初始化必须分级处理。 |

## 5. 已实施：P0消除确定性活锁

当前工作区已按本节原则完成最小实现；实机是否完全关闭故障链仍以第10节台架用例为准。

### 5.1 补齐四路UART DMA收满回调

已实现用户态`HAL_UART_RxCpltCallback()`，处理USART6、USART2、USART3和板间UART5：

1. 识别端口；
2. 记录累计收满次数并投递独立恢复事件；
3. 关闭该端口IDLEIE，避免DMA已停止后残留IDLE中断；
4. 清空`rx_ready`和接收长度，不发布512/256字节垃圾块；
5. 释放485 DE，保持接收方向；
6. 设置`recovery_pending`并返回；
7. 不在DMA中断回调中立即重启DMA，不打印日志。

该回调的直接目标是保证DMA普通模式收满后存在明确的软件接管点，不再落入“DMAR关闭但IDLEIE保持开启”的悬空状态。

### 5.2 修正UART IRQ错误出口

已在UART IRQ前置处理错误，使其按同一份SR快照执行：

1. 先识别`PE/FE/NE/ORE`；
2. 若存在错误，按STM32F4要求执行一次受控的`SR→DR`清除序列；
3. 关闭IDLEIE和相关接收中断源；
4. 锁存错误位和恢复事件；
5. 丢弃当前候选帧；
6. 不再让HAL在同一IRQ中重复处理已消费的错误事件；
7. 返回前验证不存在仍开启的挂起触发源。

读取DR会丢弃一个错误字节，这是正确行为：发生ORE等错误后帧完整性已经不存在，整帧必须丢弃，不能为了保留该字节继续解析。

禁止保留当前这种行为：

```text
发现ERROR → 直接return → IDLEIE仍开、IDLE仍置位
```

### 5.3 明确DMA启动与IDLEIE开启顺序

当前统一恢复函数遵循固定顺序：

```text
释放DE并进入接收方向
  → 关闭IDLEIE/PEIE/EIE
  → 停止并归一化HAL UART/DMA状态
  → 清SR/DR残留标志
  → 清rx_ready和接收长度
  → 尝试一次HAL_UART_Receive_DMA
  → HAL_OK后才开启IDLEIE
  → HAL失败则保持IDLEIE关闭并进入退避
```

这样可以避免“DMA未运行但IDLE中断已打开”的非法中间状态。

### 5.4 P0最小验收

静态契约、clean-first构建和COM3约150秒短回归已经通过；以下项目仍必须使用最新完整工作区固件完成实机验收：

- COM3无间隔发送超过512字节，不再卡入USART3 IRQ：P0修复固件短测通过，最新完整代码仍需复测；
- COM1/COM2无间隔发送超过256字节，不再出现同类活锁；
- DMA收满计数增加，本次数据不进入协议处理；
- 停止异常流量后端口可由主循环恢复；
- OLED、按键、COM12和CPU2继续运行。

## 6. 已实施最小P1与后续增强边界

当前实现采用每端口独立恢复标志、独立到期时刻和固定100 ms重试，并区分“仅RX DMA恢复”与“完整UART重初始化”；异常即时日志限制为同端口至少1秒一次。下述`ACTIVE/BACKOFF/RESTART_PENDING`完整状态机、错误窗口和100/500/1000 ms多级退避属于后续增强设计，尚未落地，不得写入本轮已完成口径。

### 6.1 每端口独立状态

后续多级退避状态机建议每个端口至少维护：

- `uart_error_pending`：ISR锁存的错误位；
- `rx_overflow_pending`：DMA收满事件；
- `recovery_pending`：需要主循环恢复；
- `recovery_due_tick`：下次允许恢复时间；
- `error_window_start`、`error_window_count`：错误风暴窗口；
- `backoff_level`：退避等级；
- `rx_overflow_count`、`recovery_count`、`quarantine_count`：诊断计数；
- `last_valid_frame_tick`：最近合法帧时间。

建议状态：

| 状态 | 含义 | 允许动作 |
| --- | --- | --- |
| `ACTIVE` | DMA和IDLE接收正常 | 发布合法候选帧。 |
| `FRAME_READY` | 一帧等待主循环处理 | 不覆盖当前缓冲区。 |
| `BACKOFF` | 持续错误或溢出后隔离 | IDLEIE和接收关闭，不解析、不回包。 |
| `RESTART_PENDING` | 退避到期 | 主循环只尝试一次DMA启动。 |

### 6.2 ISR边界

外部UART ISR和错误回调只允许：

- 读取并锁存错误位；
- 清除或关闭当前中断触发源；
- 发送冲突时立即释放DE；
- 清理必要的端口忙标志；
- 投递恢复事件。

禁止在ISR中：

- 立即反复停止、清理、重启DMA；
- 调用`printf`或会直接输出的`ErrorLog_*`；
- 执行协议解析；
- 改变整机业务状态；
- 在一次中断中循环重试。

### 6.3 当前主循环恢复与后续退避

当前主循环每轮遍历四个端口，每个到期端口最多执行一次恢复，不是“整轮最多一个端口”。普通恢复只执行RX DMA重启；完整恢复只对失败的外部COM口执行`HAL_UART_DeInit/Init`和RX DMA启动；失败后保持IDLEIE关闭并重新投递100 ms。若后续升级多级退避，再按以下流程扩展：

1. 汇总ISR错误和DMA溢出；
2. 达到风暴门限后进入`BACKOFF`；
3. 到期后只尝试一次DMA启动；
4. 启动失败时增加计数并进入下一级退避；
5. 至少完成一帧合法请求/响应周期后才降低退避等级；
6. 一个端口的恢复不能写入其它端口状态。

初始调参建议：

| 参数 | 初始值 | 说明 |
| --- | --- | --- |
| 错误风暴窗口 | 100 ms | 统计短时间连续错误。 |
| 风暴门限 | 8次/窗口 | 偶发错误仍允许快速恢复。 |
| 一级退避 | 100 ms | 首次持续异常。 |
| 二级退避 | 500 ms | 恢复后立即再次异常。 |
| 最大退避 | 1000 ms | 持续攻击下每秒最多尝试一次。 |
| 恢复清零条件 | 一帧完整合法响应周期 | DMA启动成功不等于链路恢复。 |

这些数值是台架初值，不是已确认产品参数，需结合三种协议和最低波特率验证后固化。

### 6.4 限频日志

- ISR只累计计数，不打印；
- 同一端口异常最多每秒输出一条汇总；
- 汇总包含新增`ORE/FE/NE/PE/DMA/overflow/recovery/quarantine`；
- 恢复尝试使用`ErrorLog_Retry`，恢复成功使用`ErrorLog_Recover`，持续隔离使用`ErrorLog_Warn`；
- 日志发送队列满不能影响端口恢复状态机。

### 6.5 已实施两级恢复入口

| 触发入口 | 恢复级别 | 当前处理 |
| --- | --- | --- |
| UART错误、DMA收满、空帧DMA续启失败 | 普通恢复 | 关闭IDLEIE，100 ms后仅重启对应端口RX DMA。 |
| 启动加载配置后UART重初始化失败 | 完整恢复 | 仅把失败端口加入完整重初始化队列，不重复重配成功端口。 |
| 菜单/参数触发三路重配置失败 | 完整恢复 | 在原安全点逐端口应用，失败端口后台重试。 |
| 协议切换或回滚后的目标端口重初始化失败 | 完整恢复 | 保留已确认的运行态配置，目标端口进入完整重初始化队列，其它端口不受影响。 |
| UART5发送DMA启动失败且RX DMA回退也失败 | 普通恢复 | `wait_response`解除并返回本次通信失败，同时把UART5加入统一恢复队列。 |

运行期`Cpu3_ReinitOneUart()`已经改为返回失败，不再调用`Error_Handler()`形成永久停机。完整重初始化成功后才清除对应full-reinit标志并开启IDLEIE。

## 7. 已实施：CPU3主循环健康票据和IWDG

### 7.1 健康代际

CPU3通过`CPU3_WatchdogReportProgress()`在有界阶段完成时递增健康代际。当前报告点包括：

- `App_Init()`启动、日志、显示初始化、2秒Logo、FRAM加载、UART重配和末尾固定等待等阶段边界；
- `App_MainLoop()`入口、显示任务返回、COM1/COM2/COM3各处理段返回、调试任务、CPU2轮询和日志服务边界；
- 每次`CPU2_CombinatePackage_Send()`事务开始和所有成功/失败出口。

CPU2响应等待循环内部不会按迭代持续报告，只在超时出口报告一次，因此`wait_response`或时间基准真正卡死时不会永久续命。TIM4只在观察到健康代际相较上次刷新有推进时调用`HAL_IWDG_Refresh()`；如果前台不再跨越任何有界阶段，TIM4停止喂狗，由IWDG执行复位。当前TIM4约2秒检查一次，IWDG配置为预分频32、重装值4095，名义超时约4秒，仍需实机验证LSI偏差和最长合法业务路径。

### 7.2 避免持续流量造成复位循环

IWDG不是端口流量控制器。必须先完成P0 DMA收满接管和P1端口隔离，使异常流量在启动后迅速进入BACKOFF；IWDG只兜底未覆盖的死锁。

复位后应保留或输出复位原因。若上电后同一端口立即再次异常，应隔离端口继续维持屏幕、按键和CPU2通信，不能形成启动—假死—复位循环。

### 7.3 CPU2阻塞式主循环约束

CPU2主循环包含设计内的同步阻塞业务，用户已明确该结构不可更改，因此不能套用CPU3的“每轮主循环完成”健康代际，否则正常测量也可能被误判复位。当前CPU2采用以下边界：

- UART IRQ只完成候选帧收取和投递；HART、UART5板间Modbus解析以及RX恢复由最低优先级PendSV执行；
- TIM4只检查DMAR/RxState并触发PendSV，不在高优先级定时中断中执行HAL重启；
- TIM4仅在没有抢占其它ISR时喂狗，持续UART/SPI中断占用不能继续掩盖故障；
- 该门控不能证明线程态业务已经推进，属于阻塞式主循环约束下的已知能力边界。

若未来必须检测CPU2线程态业务死锁，需要由各个既有长事务提供独立阶段票据，不能依赖修改主循环轮次，也不能在等待循环中无条件续票；该项不在本轮授权范围内。

## 8. 后续阶段：P2规范化RTU接收

P0/P1闭环后，再结合《2026-07-10_Modbus_RTU帧间隔与字节间超时问题分析及整改方案》统一外部协议接收架构：

1. 使用循环DMA或双缓冲持续接收；
2. IDLE只记录候选帧尾和DMA写位置；
3. 主循环按端口波特率确认`t3.5`静默后发布完整帧；
4. 超过协议最大帧长立即进入丢弃状态；
5. 丢弃持续到下一次有效`t3.5`，再重新同步；
6. 进入具体协议前统一校验地址、长度、功能码形状和CRC；
7. 上位机执行“发送请求—释放总线—等待响应或超时—再发送下一帧”的半双工时序。

本阶段会影响DSM、Wärtsilä、SI、LTD和协议切换，不应与P0活锁修复绑成一个大改动。

## 11. 通过标准

1. 任一单端口异常不能造成USART中断活锁，随机暂停不得连续命中同一UART IRQ链。
2. DMA收满后必须出现overflow计数，`IDLEIE`不能在DMA停止且无接管路径时保持开启。
3. 单端口异常期间OLED持续刷新、按键可响应；建议工程门限为最大失去响应不超过1秒，最终以产品要求确认。
4. COM3异常不改变COM1/COM2恢复状态，另外两路对合法请求仍能响应。
5. 外部异常不制造CPU2 `20-7`，不清空或伪造CPU2业务快照。
6. 持续异常期间，目标端口恢复频率受当前100 ms固定退避约束，不形成中断活锁；是否需要升级为多级退避由30分钟压力测试决定。
7. 异常解除后，在100 ms恢复周期加一轮合法请求时间内自动恢复；初始工程目标不超过1秒。
8. 日志按端口限频汇总，不耗尽主循环或调试发送队列。
9. 人工阻止CPU3前台推进时IWDG能够复位；仅单端口持续异常时不依赖整机反复复位维持可用性。CPU2阻塞式主循环不适用该判据，其能力边界见第12.1节。
10. DSM、Wärtsilä、SI、LTD和协议切换合法帧的现有ACK、响应和兼容性不回归。

## 12. 风险和待确认事项

### 12.1 实施风险

- UART错误清除采用`SR→DR`序列，会消费一个字节；必须确保整帧已标记丢弃，不能再解析残帧。
- 手动关闭中断源和HAL状态机必须保持一致，避免`RxState`、DMA句柄状态和硬件DMAR出现新的不同步。
- COM处于发送期发生错误时必须先释放DE，并正确清理pending发送，避免主机与CPU3持续对驱。
- 协议切换期间的DMA收满/错误恢复要取消或回滚pending配置，不能用旧参数重启接收。
- CPU3 IWDG健康票据已覆盖启动和主要业务边界，但最新票据布点尚未做人工冻结与最长合法路径台架验证；LSI偏差可能缩短实际超时窗口。
- CPU3 CubeMX底层`MX_USARTx_UART_Init()`发生首次HAL初始化失败时仍沿用生成代码的`Error_Handler()`策略；完整重初始化队列覆盖的是`App_Init`加载参数后的重配置和运行期失败。该启动硬故障不由连续串口流量触发，若要改成单端口降级启动，需另行确认产品上电故障策略。
- CPU2主循环是设计内阻塞且不可更改，TIM4的`RETTOBASE`门控只能识别“持续占用在其它ISR”的假死，不能证明线程态长事务推进；这是明确保留的能力边界。
- CPU2 HART和板间Modbus已从硬件UART IRQ迁移到最低优先级PendSV，但PendSV仍属于异常上下文；HART遗留调试打印会延长PendSV，后续应在不改变HART响应内容的前提下改成计数或延后日志。
- CPU2 USART1逐字节投递和UART4重量更新仍在UART IRQ内，但循环/计算有明确缓冲区上限，当前没有发现与COM3相同的悬空IDLE触发链；仍需用连续流验证IRQ预算。
- CPU2/CPU3的统一恢复仍会调用`HAL_UART_DMAStop()`，HAL内部`HAL_DMA_Abort()`在极端DMA流无法关闭时依赖`HAL_GetTick()`超时；正常硬件路径有界，极端DMA硬故障的中断上下文超时仍是残余风险。
- CPU2 SPI5编码器DMA2 Stream3优先级为0，完成/错误回调仍直接解析SSI、立即重试、调用`ErrorLog_*`，并可能通过`Update_Encoder_Count()`执行A/B两份FRAM写。直接迁移到PendSV会与线程态SPI4 FRAM访问并发，不能在没有SPI4/FRAM仲裁时强行改动。

CPU2 SPI5残余项的独立闭环条件为：先建立不依赖主循环改造的SPI4/FRAM非阻塞仲裁或所有权约束；随后把SPI5 IRQ收敛为“锁存4字节结果/错误并投递”，在最低优先级延后上下文完成解析、限次重试和持久化；ISR内禁止`printf`、`ErrorLog_*`和FRAM写；最后执行编码器连续DMA错误、A/B区写失败、测量运动和CPU2板间通信并发台架验证。在这些条件满足前，本轮保留现有编码器业务流程并把风险列为P1未闭环项。

### 12.2 待补证据

1. 本次COM3发包的波特率、数据位、校验、停止位、字节内容、单次写入长度和实测间隔。
2. 被测设备CPU3准确固件版本；当前只确认运行共享协议24并匹配Debug ELF符号。
3. COM1和COM2是否能用同类连续流稳定复现相同活锁。
4. A-B短接时实际产生的UART错误类型、短路电流、收发器温升和电源波形。
5. 三路`TY-485`及保护电路在实际硬件批次上的失效安全输出。
6. 当前100 ms固定恢复节拍是否满足DSM、Wärtsilä、SI和LTD全部正常最坏时序，以及是否需要升级为100/500/1000 ms多级退避。
