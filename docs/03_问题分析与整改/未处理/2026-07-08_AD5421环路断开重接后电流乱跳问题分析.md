# AD5421 环路断开重接后电流 4mA/24mA 乱跳问题分析

更新日期：2026-07-08

> 当前复核（2026-07-08）：状态：代码已实现，待台架验证。当前 `MAIN` 分支为正常有回读代码，`Ad5421Init()` 会执行控制寄存器回读校验，AO 运行期会节流轮询 `READFAULT`。本文只按当前正常代码分析。

## 1. 问题摘要

在 CPU2 AO 模拟电流输出正常回读代码中，正常接好 4-20mA 环路时电流输出稳定；但现场执行“固定下发 `AO1200`，稳定后断开环路，再接回环路”的测试后，电流会在约 `4mA` 和 `24mA` 附近乱跳。此时再次发送 `AO1200` 后，电流恢复稳定。

已确认的关键现象：

| 项目 | 现象 |
| --- | --- |
| 正常不断环 | `AO1200` 可稳定输出约 `12.00mA` |
| 断开环路再接回 | 输出出现 `4mA/24mA` 附近乱跳 |
| 再次发送 `AO1200` | 输出恢复约 `12.00mA` 稳定 |
| 当前代码口径 | `READCONTROL` 与 `READFAULT` 均保留，用于控制字校验和运行期诊断 |

该现象说明问题不在基础 DAC 换算，也不在正常状态下的 SPI 写入链路。更可能是 AD5421 或外部 4-20mA 环路在开路后进入 fault、compliance 或输出级异常状态，环路接回后单纯维持上一次 DAC 目标不能可靠恢复，需要结合回读诊断判断恢复条件。

## 2. 当前固件背景

### 2.1 串口 AO 测试路径

文件：`LTD_MAIN_CPU2/Application/Src/test.c`

`AO1200` 命令执行路径：

1. `TestCommand_HandleAoOutputTest()` 暂停 AO 自动刷新。
2. `TestCommand_RunAoOutputPoint(1200)`。
3. `Ad5421Init()`。
4. 循环调用 `AD5421_SetCurrentX100(1200)`。
5. 每次写电流后调用 `AD5421_PollDiagnostics()`。
6. 退出时恢复 AO 自动刷新。

关键点：再次发送 `AO1200` 能恢复，并不只证明“再写一次 DAC 有效”；它同时执行了 `Ad5421Init()`。当前 `Ad5421Init()` 会复位 AD5421、写控制字、回读控制寄存器、写初始电流、读取故障寄存器，随后测试命令再写 `12.00mA` 并继续诊断。

### 2.2 AO 自动刷新路径

文件：`LTD_MAIN_CPU2/Services/AoOutput/ao_output.c`

AO 自动刷新路径会：

1. `AoOutput_EnsureDriverReady()` 在驱动未就绪时调用 `Ad5421Init()`。
2. `AoOutput_PollDiagnosticsThrottled()` 按 1 秒节流读取 `READFAULT`。
3. `AoOutput_SelectTarget()` 选择目标电流，诊断失败时切到 `FaultCurrent_mA`。
4. `AoOutput_ShouldWriteCurrent()` 判断是否需要下发。
5. 调用 `AD5421_SetCurrentX100(target_mA_x100)` 写 DAC。

当前关键限制：一旦 `ao_output_driver_ready != 0`，运行期只轮询 `READFAULT` 并重写 DAC，不会在断环重接后自动重新执行 `ResetAD5421()` 和控制寄存器回读校验。若 AD5421 断环后需要重新初始化才能退出异常状态，现有路径可能不足。

### 2.3 AD5421 初始化和诊断路径

文件：`LTD_MAIN_CPU2/BSP/Peripherals/src/ad5421.c`

当前 `Ad5421Init()` 顺序为：

1. `AD5421_TryBeginSequence()` 占用多帧初始化序列。
2. 清 `ad5421_fault_flags` 和 `ad5421_fault_register`。
3. `ResetAD5421()`。
4. `WriteControlRegister(CUR_SPIOFF_READBACK_COMMAND)`。
5. `WriteControlRegister()` 内部写 `WRITECONTROL 0x1800` 后执行 `READCONTROL` 回读校验。
6. `AD5421_SetCurrentX100(g_deviceParams.InitialCurrent_mA)`。
7. 延时 10ms 后调用 `AD5421_PollDiagnostics()` 读取 `READFAULT`。

当前 `AD5421_PollDiagnostics()` 行为为：

1. 读取 `READFAULT`。
2. 保存 `ad5421_fault_register`。
3. 清除历史 PB8 引脚故障位，因为当前硬件 PB8 不作为可靠 AD5421 故障来源。
4. 若 `READFAULT != 0`，置 `AD5421_FAULT_FLAG_STATUS` 并返回 `AD5421_READFAULT_ERROR`。

## 3. 根因判断

### 3.1 高置信判断

“断环接回后乱跳，再次发送 `AO1200` 恢复”说明恢复动作的有效部分至少包含：

| 恢复动作 | 是否由再次 `AO1200` 执行 | 作用 |
| --- | --- | --- |
| AD5421 软件复位 | 是 | 退出开路后可能残留的输出级/故障状态 |
| 重新写控制寄存器并回读校验 | 是 | 恢复 SPI watchdog、控制字配置和读回链路确认 |
| 重新写目标电流 | 是 | 把 DAC 输出拉回现场要求值 |
| 重新读取 `READFAULT` | 是 | 更新 AD5421 故障状态，给后续恢复判断提供依据 |

因此，根因优先级最高的是：

1. AD5421 在环路开路后进入输出级异常、故障报警或环路合规电压异常状态。
2. 环路接回时外部负载、电源或保护网络出现瞬态，导致 AD5421 当前输出状态不再只由最后一次 DAC 写入决定。
3. 当前 AO 运行期虽然读取 `READFAULT`，但诊断异常后只切故障电流，没有自动重做 AD5421 初始化恢复。

### 3.2 不是首要根因的项

| 项目 | 判断 |
| --- | --- |
| 普通 DAC 换算错误 | 正常不断环时 `AO1200` 稳定，暂不作为首要原因 |
| 参数配置错误 | 再次发送同一 `AO1200` 能恢复，说明参数不是唯一原因 |
| 液位映射目标跳变 | 串口 `AO1200` 暂停自动刷新后仍能复现断环重接问题，优先级降低 |
| SPI 写入链路永久断开 | 再次 `AO1200` 可恢复，说明前向写入链路仍可用 |
| 单纯回读链路全失效 | 当前测试能通过 `Ad5421Init()` 恢复，需结合 `READCONTROL` 和 `READFAULT` 现场日志判断，不能直接定为唯一根因 |

### 3.3 对照 AD5421 手册后的补充判断

对照 [Analog Devices `AD5421` 数据手册 Rev. I](https://www.analog.com/media/en/technical-documentation/data-sheets/ad5421.pdf) 后，`4mA/24mA` 附近乱跳不应再按普通随机噪声理解，而应优先按“上电默认/故障报警电流、量程端点、环路合规电压异常”三类状态排查。

| 手册依据 | 与现场现象的对应关系 | 结论 |
| --- | --- | --- |
| AD5421 支持 `4-20mA`、`3.8-21mA`、`3.2-24mA` 三种引脚选择量程；上行报警可为 `22.8mA/24mA`，下行报警为约 `3.2mA`。 | 现场高端跳到约 `24mA`，非常接近 `3.2-24mA` 量程的满量程或上行报警电流。 | 高端跳变更像 AD5421 进入报警/满量程状态，而不是 `AO1200` 的正常 DAC 换算结果。 |
| 手册的 Power-On Default 说明：芯片上电后环路电流停在报警态 `3.2mA` 或 `22.8/24mA`，直到被重新写入寄存器。 | 断环重接可能让 AD5421 的环路供电、REGIN/REGOUT、DVDD 或输出级经历掉电/欠压/复位样瞬态。 | 如果重接后芯片回到上电默认报警态，再发 `AO1200` 通过 `Ad5421Init()` 恢复是合理现象。 |
| 手册的 SPI watchdog 默认上电使能，默认超时 `1s`；SPI fault 可把环路电流强制到报警值。 | 当前控制字 `0x1800` 会关闭 SPI watchdog；但如果断环导致 AD5421 复位，控制字会回默认值。 | 需要确认断环重接后 AD5421 是否丢失控制寄存器配置。 |
| 手册的 ILOOP Under/Over：实际环路电流低于/高于编程电流时置位；ILOOP Under 可由合规电压不足、负载过大或环路电源过低导致。 | 断开 4-20mA 环路本质上会破坏实际环路电流与目标电流的一致性；接回瞬间还可能伴随负载和保护器件瞬态。 | 断环期间优先应观察 `READFAULT` 中 ILOOP Under/Over、VLOOP 6V/12V 和电源轨。 |
| 手册要求 `LDAC` 不应悬空；若 `LDAC` 高电平，写入只更新输入寄存器，输出更新要等 `LDAC` 下降沿。 | 既有原理图问题清单已把 `LDAC` 是否悬空列为疑点。 | `LDAC` 应从低优先级疑点上调为必须现场核对项。 |
| 手册给出的 `3.2-24mA` 传递函数为 `ILOOP = 3.2mA + D * 20.8mA / 2^16`。 | 当前 `AD5421_SetCurrent()` 正按 `3.2..24.0mA` 计算 DAC。`12mA` 对应中低码值，不会自然变成满量程 `24mA`。 | 需要抓断环重接期间的实际 `WRITEDAC` 原始码，排除 MCU 是否写出了接近 `0xFFFF` 的码值。 |

调整后的根因排序：

1. 最高优先级：断环重接导致 AD5421 回到上电默认报警态或 SPI fault 报警态，报警方向/量程配置使输出落在约 `24mA`，重新初始化后恢复。
2. 高优先级：环路合规电压不足或 VLOOP/REGIN/REGOUT/DVDD 瞬态异常导致 ILOOP Under/Over，AD5421 输出级在重接后没有靠普通 DAC 重写稳定恢复。
3. 高优先级：`LDAC`、`ALARM_CURRENT_DIRECTION`、`RANGE0/1` 或外部保护网络实际状态与固件/文档假设不一致。
4. 中优先级：AO 服务在断环期间或重接瞬间写入了故障电流、初始电流或满量程码；需要用串口运行态和 SPI 原始帧排除。
5. 低优先级：`AD5421_SetCurrent()` 的基础换算错误。当前正常不断环 `AO1200` 稳定，且源码换算与 `3.2-24mA` 量程一致。

### 3.4 手册命令和抓包判据

对照手册和当前驱动宏定义，现场逻辑分析仪应优先识别下列帧：

| 操作 | 命令字节 | 判据 |
| --- | --- | --- |
| 写 DAC | `0x01` | 正常周期写电流只应看到该命令和目标码值。 |
| 写控制寄存器 | `0x02` | 初始化应写 `0x1800`。 |
| 软件复位 | `0x07` | `Ad5421Init()` 中应出现；普通运行期 DAC 重写不应频繁出现。 |
| NOOP | `0x09` | 可用于读回时序辅助判断。 |
| 读控制寄存器 | `0x82` | 初始化控制字校验应出现，且读回值应等于 `0x1800`。 |
| 读故障寄存器 | `0x85` | 初始化后和运行期诊断应出现，用于确认 ILOOP/VLOOP/SPI fault。 |

按当前 `AD5421_SetCurrent()` 的 `3.2..24.0mA` 换算，理论 DAC 码如下：

| 命令 | 目标电流 | 理论 DAC 码 | 现场判断 |
| --- | --- | --- | --- |
| `AO400` | `4.00mA` | `0x09D9` | 接近低端，不能解释 `24mA` 高端跳变。 |
| `AO1200` | `12.00mA` | `0x6C4E` | 若断环重接期间抓到接近该码值但输出仍跳 `24mA`，优先查 AD5421/环路状态。 |
| `AO2000` | `20.00mA` | `0xCEC4` | 正常高端测试点。 |
| `AO2200` | `22.00mA` | `0xE762` | 接近上行报警区，需和报警电流区分。 |
| `24.00mA` | `24.00mA` | `0xFFFF` | 若断环重接期间出现该码，说明 MCU/AO 服务主动写了满量程。 |

如果硬件 `RANGE0/1` 实际不是 `3.2..24.0mA`，上述码值和实际电流的对应关系会变化；因此不能只看命令名，必须同步记录 AD5421 侧 `WRITEDAC` 原始码和 `RANGE0/1` 实测电平。

## 4. 为什么不能直接复用 `Ad5421Init()`

可以用 `Ad5421Init()` 临时验证恢复效果，但不建议直接把它塞进 AO 自动刷新长期使用，原因是：

1. `Ad5421Init()` 会先写 `g_deviceParams.InitialCurrent_mA`，默认是 `4.00mA`。
2. 如果当前目标是 `12.00mA` 或 `20.00mA`，恢复过程中可能先短暂输出 `4.00mA`，再写回目标值。
3. 对 PLC 或仪表来说，这个短暂跳变可能被视为真实过程量波动。
4. `Ad5421Init()` 返回错误时会让 AO 服务进入驱动错误状态，直接套用到运行期需要明确恢复节流和错误状态回退策略。

更合适的方式是新增一个“按当前目标恢复并保留诊断”的底层函数，而不是直接复用初始化函数。

建议接口：

```c
uint32_t AD5421_RecoverCurrentX100(uint32_t target_mA_x100);
```

建议内部顺序：

1. 占用 AD5421 sequence。
2. 清必要的本地故障缓存。
3. `ResetAD5421()`。
4. 调用当前控制字写入和 `READCONTROL` 回读校验逻辑，确认控制寄存器恢复到 `0x1800`。
5. 直接写 `target_mA_x100`，不要先写 `InitialCurrent_mA`。
6. 延时后调用 `AD5421_PollDiagnostics()`，记录 `READFAULT`。
7. 释放 sequence。

这样可以保留当前正常代码的控制回读和故障回读闭环，同时避免恢复时先写初始电流造成额外跳变。

## 5. 推荐处理方案

### 5.1 推荐方案：基于回读诊断的目标电流恢复

在 AD5421 驱动层新增 `AD5421_RecoverCurrentX100(target_mA_x100)`，在 AO 服务中基于 `READFAULT` 或连续写入异常触发恢复。

推荐策略：

| 场景 | 动作 |
| --- | --- |
| 目标电流变化 | 正常 `AD5421_SetCurrentX100(target)`，保持现有路径。 |
| `READFAULT` 非 0 | 记录 fault 原始值，并触发一次带回读的恢复序列。 |
| `READCONTROL` 回读失败 | 启动初始化阶段仍按错误码上报；运行期恢复失败只记录 AO 运行态和驱动故障标志，不应盲目继续写 DAC，也不应触发整机最终错误。 |
| 连续断环重接验证阶段 | 从 `1s` 恢复节流开始验证，确认接回后能自动回到目标电流。 |
| 稳定后正式应用 | 根据现场可接受瞬态，把恢复节流放宽到 `2s..5s`，并保留最后一次 `READFAULT` 原始值。 |

优点：

- 保留当前正常分支的 `READCONTROL` 和 `READFAULT` 诊断闭环。
- 与现场复现证据一致，再次初始化类动作能恢复输出。
- 能区分控制回读失败、故障寄存器异常、普通 DAC 写失败和环路状态异常。

缺点：

- 复位 AD5421 可能带来短暂输出扰动，需要台架测量确认。
- 如果 HART 同环路通信正在进行，恢复过程可能影响通信，需要单独验证。
- 若回读链路受硬件问题影响持续返回 `0xFFFF`，恢复逻辑会被卡在驱动错误状态，需要先修复回读链路。

### 5.2 备选方案：只记录诊断，不自动恢复

保持当前逻辑，只增强现场日志和运行态寄存器记录，把 `READFAULT`、控制回读原始字节、最后 DAC 码和目标电流完整发布。

优点：

- 改动小，风险低。
- 可以先确认断环重接时 AD5421 的真实 fault 位。

缺点：

- 不能自动恢复现场乱跳，需要人工再次发送 `AO1200`。
- 如果现场测试目标是验证接回后自动恢复，该方案不足。

### 5.3 不推荐方案：只增加普通 DAC 重写

仅提高 `AD5421_SetCurrentX100(target)` 的重复写入频率，不建议作为主方案。

原因：

- 当前 AO 服务已经具备目标不变的周期刷新能力。
- 现场现象显示重新发送 `AO1200` 恢复，而 `AO1200` 包含 `Ad5421Init()` 和回读诊断，不能证明“单纯多写 DAC”足够。
- 如果 AD5421 输出级已进入开路后的异常保持状态，普通 DAC 重写可能无法恢复。

## 6. 建议实现切入点

### 6.1 AD5421 驱动层

目标文件：

- `LTD_MAIN_CPU2/BSP/Peripherals/inc/ad5421.h`
- `LTD_MAIN_CPU2/BSP/Peripherals/src/ad5421.c`

建议新增：

```c
uint32_t AD5421_RecoverCurrentX100(uint32_t target_mA_x100);
```

实现约束：

- 复用 `AD5421_TryBeginSequence()` 和 `AD5421_EndSequence()`。
- 复用 `ResetAD5421()`。
- 复用当前控制字写入和 `READCONTROL` 回读校验逻辑。
- 最后直接写 `target_mA_x100`，不要写 `InitialCurrent_mA`。
- 恢复后调用 `AD5421_PollDiagnostics()`，保留 `READFAULT` 原始值。
- 如果 `READCONTROL` 回读失败，不应把恢复视为成功。

### 6.2 AO 服务层

目标文件：

- `LTD_MAIN_CPU2/Services/AoOutput/ao_output.c`

建议新增状态：

- 最近一次恢复 tick。
- 恢复节流周期，例如 `AO_OUTPUT_RECOVER_INTERVAL_MS`。
- 最近一次恢复原因，例如 `READFAULT`、写 DAC 失败、控制回读失败。

建议逻辑：

1. `AoOutput_PollDiagnosticsThrottled()` 返回 `AD5421_READFAULT_ERROR` 时，保留 fault 原始值。
2. 若恢复节流允许，调用 `AD5421_RecoverCurrentX100(target_mA_x100)`。
3. 恢复成功后更新 `last_sent_mA_x100`、`last_sent_tick`、`driver_fault_flags`、`driver_fault_register`。
4. 恢复失败时保持 `AO_OUTPUT_SOURCE_DRIVER_ERROR`，输出目标按 `FaultCurrent_mA` 处理。
5. 不要在 TIM4 ISR 里执行恢复，必须保持 PendSV 或前台上下文。

## 7. 验证方案

### 7.1 复现基线

使用当前正常代码先复现一次：

1. 接电流表或标准负载到正确 4-20mA 回路。
2. 发送 `AO1200`。
3. 确认输出稳定在约 `12.00mA`。
4. 断开环路。
5. 接回环路。
6. 记录是否出现 `4mA/24mA` 乱跳。
7. 记录串口日志中的 `write`、`diag`、`fault`、`flags`。
8. 再次发送 `AO1200`。
9. 确认是否恢复稳定，并记录恢复前后的 `READCONTROL` / `READFAULT` 结果。

通过标准：

- 能稳定复现“断开重接后乱跳，再发 `AO1200` 恢复”。
- 若 `write=0x00000000` 时仍乱跳，说明 MCU 认为写入成功，但硬件输出未稳定。
- 必须记录断环、重接、恢复三个阶段的 `READFAULT` 原始值。

### 7.2 修复验证

加入 `AD5421_RecoverCurrentX100(target)` 后测试：

1. 发送 `AO1200`。
2. 稳定后断开环路。
3. 接回环路。
4. 不再手动发送 `AO1200`。
5. 等待一个恢复节流周期。
6. 观察输出是否自动回到约 `12.00mA`。

通过标准：

- 接回后无需人工再次发送 `AO1200`，输出自动恢复。
- 恢复时间小于设定恢复节流周期加一次刷新延迟。
- 恢复期间没有长期停在 `4mA` 或 `24mA`。
- 控制寄存器回读与目标控制字一致。
- `READFAULT` 原始值能解释或记录恢复前故障状态。

### 7.3 SPI 逻辑分析仪验证

建议同时抓 AD5421 侧 `SYNC/SCLK/SDIN/SDO`。

恢复周期内应看到：

| 操作 | 允许出现 |
| --- | --- |
| `RESETAD5421REG` 写帧 | 是 |
| `WRITECONTROL 0x1800` 写帧 | 是 |
| `READCONTROL 0x82` | 是，读回应为 `0x1800` |
| `WRITEDAC` 写帧 | 是 |
| `READFAULT 0x85` | 是，用于确认故障状态 |

补充对照手册后的抓包要求：

| 观测项 | 目的 |
| --- | --- |
| 断环前 `WRITEDAC` 原始码 | 确认 `AO1200` 对应的 DAC 码稳定，不接近 `0x0000` 或 `0xFFFF`。 |
| 断环重接期间是否出现 `WRITEDAC 0xFFFF` 或接近满量程码 | 排除 MCU/AO 服务主动写入 `24mA`。 |
| 重接后第一次 `WRITECONTROL 0x1800` 是否出现并读回一致 | 判断是否重新关闭 SPI watchdog、重新设置自动 fault 回读策略。 |
| `READFAULT` 的 `SPI/PEC/ILOOP Over/ILOOP Under/VLOOP 6V/VLOOP 12V` 位 | 区分 SPI fault、环路电流不匹配和环路电源不足。 |
| `LDAC` 实际电平 | 确认写 DAC 帧是否会立即更新输出。 |

### 7.4 回归测试

| 测试项 | 预期 |
| --- | --- |
| `AO400` | 输出约 `4.00mA` |
| `AO1200` | 输出约 `12.00mA` |
| `AO2000` | 输出约 `20.00mA` |
| `AO2200` | 输出约 `22.00mA` |
| `AOS` | 依次稳定输出 `4/12/20/22mA` |
| AO 使能关闭 | 不访问 AD5421，不触发恢复 |
| 正常液位跟随 | 按液位映射输出 |
| 高低报警电流 | 按参数覆盖输出 |
| 故障/调试电流 | 按优先级输出 |
| 连续断环重接 10 次 | 每次接回后可自动恢复，并记录故障寄存器变化 |

## 8. 风险和开放问题

### 8.1 风险

1. 复位 AD5421 可能造成短暂电流扰动，需要用示波器或高速采样表确认扰动幅度和持续时间。
2. 如果恢复周期过短，可能影响 HART 同环路通信或外部 PLC 对模拟量的滤波判断。
3. 如果环路接回瞬间硬件电源仍不稳定，软件恢复可能需要延后或多次执行。
4. 如果 24V 环路电源、负载或保护器件存在接触抖动，固件恢复只能缓解，不能替代硬件修复。
5. 如果回读链路本身不可靠，恢复逻辑会持续报 `READCONTROL` 或 `READFAULT` 错误，需要优先排查硬件回读链路。

### 8.2 待确认

| 问题 | 建议确认方式 |
| --- | --- |
| 断环接回后 AD5421 侧供电是否跌落或尖峰 | 示波器测 AD5421 供电、P420+、P420- |
| 恢复是否必须复位 AD5421 | 对比“仅写控制+目标电流”和“复位+写控制+目标电流” |
| 恢复周期取值 | 从 `1s` 开始验证，再放宽到 `2s..5s` |
| HART 是否受影响 | 在 HART 通信场景下做断环重接恢复测试 |
| PLC 是否能接受短暂扰动 | 用现场 PLC 趋势记录确认 |
| `ALARM_CURRENT_DIRECTION` 实际接 DVDD 还是 COM | 判断报警态应落到上行 `22.8/24mA` 还是下行约 `3.2mA` |
| `RANGE0/1` 实际接法 | 判断芯片实际量程是 `4-20mA`、`3.8-21mA` 还是 `3.2-24mA` |
| `LDAC` 是否固定到有效低电平 | 排除 DAC 输出更新被悬空脚随机延迟 |
| 断环重接后控制寄存器是否丢失 | 比较重接前后 `READCONTROL` 读回值 |
| `VLOOP` 分压是否按手册 20:1 或其它比例实现 | 正确解释 `VLOOP 6V/12V` 告警位，避免把比例差异误判为芯片异常 |

## 9. 当前结论

本问题的直接处理方向不是单纯提高 DAC 重写频率，而是在当前正常回读代码基础上增加“按当前目标电流恢复 AD5421”的带诊断恢复动作。

对照手册后，断环重接后输出跳到约 `24mA`，更像 AD5421 进入上电默认报警态、SPI fault 报警态、量程满端或环路故障状态，而不是 DAC 换算本身随机失控。最关键的现场证据是断环重接期间的 AD5421 供电轨、`READCONTROL`、`READFAULT`、`ALARM_CURRENT_DIRECTION`/`RANGE0/1`/`LDAC` 实际电平，以及 `WRITEDAC` 原始码是否曾被 MCU 写到满量程。

建议优先实现：

```text
AD5421_RecoverCurrentX100(target_mA_x100)
= ResetAD5421 + WRITECONTROL(0x1800) + READCONTROL校验 + AD5421_SetCurrentX100(target_mA_x100) + READFAULT诊断
```

并在 AO 自动刷新中按 `READFAULT` 或连续写入异常触发。这样既符合当前正常有回读代码，又能覆盖现场已验证的“重新 `AO1200` 可恢复”现象。

## 10. 详细改动说明

本节按“先驱动层、再 AO 服务层、最后验证”的顺序说明具体怎么改。核心原则是：恢复动作必须继续保留 `READCONTROL` 控制寄存器校验和 `READFAULT` 故障寄存器诊断；恢复目标应为当前 AO 目标或最近一次有效输出目标，不能在恢复过程中先写 `InitialCurrent_mA`。

### 10.1 改动文件总览

| 文件 | 改动类型 | 目的 |
| --- | --- | --- |
| `LTD_MAIN_CPU2/BSP/Peripherals/inc/ad5421.h` | 新增函数声明 | 对 AO 服务暴露“按目标电流恢复 AD5421”的接口。 |
| `LTD_MAIN_CPU2/BSP/Peripherals/src/ad5421.c` | 新增恢复函数 | 复用现有复位、控制字写入、控制字回读、电流写入、故障回读流程。 |
| `LTD_MAIN_CPU2/Services/AoOutput/ao_output.c` | 新增恢复节流和恢复分支 | `READFAULT` 或连续写入异常后自动执行恢复，恢复失败才进入驱动错误/故障电流处理。 |
| `docs/03_问题分析与整改/未处理/2026-07-08_AD5421环路断开重接后电流乱跳问题分析.md` | 同步问题分析和验证方案 | 记录手册依据、现场抓包判据、修改方案和回归项目。 |

本次方案不需要调整 CPU3 协议寄存器，也不需要修改参数表。若最终只新增 CPU2 内部恢复逻辑、未改变外部 Modbus 寄存器和共享结构，`DEVICE_PROTOCOL_VERSION` 原则上不需要变化；但因为 CPU2 AO 运行行为发生变化，提交前仍应评估 CPU2 固件版本影响。

### 10.2 第一步：在 `ad5421.h` 增加恢复接口

位置建议：放在 `AD5421_SetCurrentX100()` 和 `AD5421_PollDiagnostics()` 附近，便于看出它属于 AD5421 输出控制和诊断之间的恢复动作。

建议新增声明：

```c
uint32_t AD5421_RecoverCurrentX100(uint32_t target_mA_x100);
```

接口语义：

| 返回值 | 含义 | AO 服务处理建议 |
| --- | --- | --- |
| `NO_ERROR` | 复位、控制字回读、目标电流写入、故障回读均通过 | 更新 `last_sent_mA_x100`，本轮不再切到故障电流。 |
| `AD5421_READBACK_ERROR` | `READCONTROL` 读回值和写入控制字不一致 | 启动初始化阶段返回错误；运行期记录 AO 驱动错误状态并返回 `NO_ERROR`，避免后台刷新把 AO 回读异常升级为整机最终错误。 |
| `AD5421_READFAULT_ERROR` | 目标电流已写入，但 `READFAULT` 仍有故障位 | 保留故障寄存器原始值，按恢复失败处理或等待下一次节流恢复。 |
| 其它 SPI/初始化错误 | 恢复序列未完整执行 | 启动初始化阶段保持错误上报；运行期记录 AO 运行态，等待下一次节流恢复或重新初始化。 |

### 10.3 第二步：在 `ad5421.c` 实现 `AD5421_RecoverCurrentX100()`

位置建议：放在 `Ad5421Init()` 后面，或放在 `AD5421_PollDiagnostics()` 后面。推荐放在 `Ad5421Init()` 后面，因为两者流程相近，后续维护时容易对照。

建议实现骨架：

```c
uint32_t AD5421_RecoverCurrentX100(uint32_t target_mA_x100)
{
    uint32_t ret;

    if (AD5421_TryBeginSequence() == 0U)
    {
        ad5421_fault_flags |= AD5421_FAULT_FLAG_SPI_WRITE;
        return AD5421_INIT_ERROR;
    }

    ad5421_fault_flags = 0U;
    ad5421_fault_register = 0U;

    ResetAD5421();

    ret = WriteControlRegister(CUR_SPIOFF_READBACK_COMMAND);
    if (ret != NO_ERROR)
    {
        AD5421_EndSequence();
        return ret;
    }

    ret = AD5421_SetCurrentX100(target_mA_x100);
    if (ret != NO_ERROR)
    {
        AD5421_EndSequence();
        return ret;
    }

    HAL_Delay(10);

    ret = AD5421_PollDiagnostics();

    AD5421_EndSequence();

    return ret;
}
```

实现时要注意以下边界：

| 边界 | 处理要求 |
| --- | --- |
| sequence 占用失败 | 直接返回初始化类错误，避免和正在进行的多帧访问交叠。 |
| 控制字回读失败 | 不继续把恢复标记为成功，因为手册中 SPI watchdog 和 fault 行为依赖控制寄存器配置。 |
| 目标电流写入失败 | 返回写入错误，保持原有错误码来源。 |
| `READFAULT` 非 0 | 返回 `AD5421_READFAULT_ERROR`，同时保留 `ad5421_fault_register`，用于现场判断 ILOOP/VLOOP/SPI fault。 |
| 目标电流范围 | 继续交给 `AD5421_SetCurrentX100()` 现有限幅逻辑处理，避免新增一套不一致的换算。 |

这一步的关键不是“多写一次 DAC”，而是把手册要求相关的状态重新拉回已知配置：

```text
复位 AD5421
写控制寄存器 0x1800
读控制寄存器确认 0x1800
写回目标电流
读取 READFAULT 保存诊断证据
```

### 10.4 第三步：在 `ao_output.c` 增加恢复节流状态

位置建议：和现有 `AO_OUTPUT_DIAG_INTERVAL_MS`、`ao_output_last_diag_tick` 放在一起。

建议新增宏：

```c
#define AO_OUTPUT_RECOVER_INTERVAL_MS 1000U
```

建议新增静态状态：

```c
static uint8_t ao_output_recover_valid = 0U;
static uint32_t ao_output_last_recover_tick = 0U;
static uint32_t ao_output_last_recover_error = NO_ERROR;
```

建议新增节流函数：

```c
static uint8_t AoOutput_ShouldRecover(uint32_t now)
{
    if (ao_output_recover_valid == 0U)
    {
        return 1U;
    }

    if ((now - ao_output_last_recover_tick) >= AO_OUTPUT_RECOVER_INTERVAL_MS)
    {
        return 1U;
    }

    return 0U;
}
```

恢复节流的初始建议值是 `1000ms`，便于台架验证“接回后一个诊断周期内恢复”。现场稳定后可根据 HART 通信和 PLC 趋势记录把周期放宽到 `2000ms..5000ms`。

### 10.5 第四步：增加恢复目标选择函数

不要在恢复时固定写 `FaultCurrent_mA`，否则现场 `AO1200` 断环重接后可能被恢复到故障电流，而不是恢复到测试目标。

建议新增一个内部函数，优先使用最近一次成功下发的目标；如果系统刚启动还没有成功下发记录，再退回初始电流：

```c
static uint32_t AoOutput_GetRecoverTarget(void)
{
    if (ao_output_runtime.last_sent_mA_x100 > 0U)
    {
        return ao_output_runtime.last_sent_mA_x100;
    }

    return AoOutput_NormalizeHardwareCurrent(g_deviceParams.InitialCurrent_mA);
}
```

如果后续希望更精确，也可以在诊断前先计算当前业务目标，再作为恢复目标。但第一版建议用 `last_sent_mA_x100`，因为它代表 AD5421 最近一次已经接受过的正常输出目标，和“断环前稳定输出 12mA，接回后恢复到 12mA”的现场需求一致。

### 10.6 第五步：改造 `AoOutput_UpdateInternal()` 的诊断异常分支

当前逻辑在 `diag_ret != NO_ERROR` 后会把目标切到 `FaultCurrent_mA`。建议改成：先尝试带回读恢复；恢复成功则本轮结束或保持目标，不再写故障电流；恢复失败时记录 AO 运行态和驱动错误，运行期刷新返回 `NO_ERROR`，避免由后台刷新触发整机最终错误。

建议逻辑骨架：

```c
diag_ret = AoOutput_PollDiagnosticsThrottled(now);
if (diag_ret != NO_ERROR)
{
    uint32_t recover_ret;
    uint32_t recover_target_mA_x100;

    recover_target_mA_x100 = AoOutput_GetRecoverTarget();

    if (AoOutput_ShouldRecover(now) != 0U)
    {
        recover_ret = AD5421_RecoverCurrentX100(recover_target_mA_x100);

        ao_output_recover_valid = 1U;
        ao_output_last_recover_tick = now;
        ao_output_last_recover_error = recover_ret;
        ao_output_runtime.driver_fault_flags = AD5421_GetFaultFlags();
        ao_output_runtime.driver_fault_register = AD5421_GetFaultRegister();

        if (recover_ret == NO_ERROR)
        {
            ao_output_last_diag_error = NO_ERROR;
            ao_output_diag_valid = 0U;
            ao_output_runtime.target_mA_x100 = recover_target_mA_x100;
            ao_output_runtime.last_sent_mA_x100 = recover_target_mA_x100;
            ao_output_runtime.last_sent_tick = now;
            ao_output_runtime.last_error = NO_ERROR;
            return NO_ERROR;
        }

        diag_ret = recover_ret;
    }

    source = AO_OUTPUT_SOURCE_DRIVER_ERROR;
    target_mA_x100 = AoOutput_NormalizeHardwareCurrent(g_deviceParams.FaultCurrent_mA);
    ret = diag_ret;
}
```

这里有两个关键点：

1. 恢复成功后本轮应直接返回，或者显式把 `should_send` 置为不再写，避免后续代码又把 `FaultCurrent_mA` 写进去。
2. 恢复失败才进入 `AO_OUTPUT_SOURCE_DRIVER_ERROR`，并按现有故障电流策略处理。
3. 恢复成功时不要把 `source` 强行写成固定来源；如果需要更新来源，应复用恢复前的来源，或在下一轮正常调用 `AoOutput_SelectTarget()` 重新计算。

如果代码结构不方便直接 `return NO_ERROR`，也可以用局部标志控制：

```c
uint8_t recovered_this_cycle = 0U;
```

恢复成功后设置 `recovered_this_cycle = 1U`，后续计算 `should_send` 时跳过本轮普通写电流路径。

### 10.7 第六步：清理恢复状态的时机

以下场景建议清理恢复节流状态，避免旧错误影响下一次启用：

| 场景 | 建议动作 |
| --- | --- |
| AO 使能关闭 | `ao_output_recover_valid = 0U; ao_output_last_recover_error = NO_ERROR;` |
| `Ad5421Init()` 重新成功 | 清恢复节流状态和最近恢复错误。 |
| AO 参数重新加载或输出模式切换 | 保留最近恢复错误用于诊断，但允许下一次立即恢复。 |
| 连续恢复失败 | 不清节流状态，避免每个刷新周期都复位 AD5421。 |

### 10.8 第七步：错误和运行态记录建议

建议至少保留以下信息，方便现场判断到底是手册中的哪类故障：

| 字段 | 记录内容 | 用途 |
| --- | --- | --- |
| `driver_fault_flags` | 驱动层综合故障位 | 判断 SPI 写、SPI 读、控制回读、故障寄存器异常。 |
| `driver_fault_register` | `READFAULT` 原始值 | 对照手册拆分 ILOOP、VLOOP、SPI fault、PEC fault。 |
| `ao_output_last_diag_error` | 最近一次诊断错误 | 判断是否由 `READFAULT` 触发恢复。 |
| `ao_output_last_recover_error` | 最近一次恢复错误 | 区分恢复成功、控制回读失败、恢复后 fault 仍存在。 |
| `last_sent_mA_x100` | 最近一次成功下发目标 | 判断恢复目标是否等于断环前稳定目标。 |

如果不想扩展对外运行态结构，至少应在调试串口或内部状态中保留 `READFAULT` 原始值和恢复返回值，方便台架复盘。

### 10.9 第八步：不建议这样改

| 不建议做法 | 原因 |
| --- | --- |
| 诊断失败后只提高 `AD5421_SetCurrentX100()` 重写频率 | 手册指向的报警态、SPI fault、控制寄存器默认态无法靠普通 DAC 重写可靠解除。 |
| 直接在 AO 周期里调用 `Ad5421Init()` | `Ad5421Init()` 会先写 `InitialCurrent_mA`，可能引入额外输出跳变。 |
| 恢复时固定写 `FaultCurrent_mA` | 现场需求是断环接回后回到断环前目标，例如 `AO1200` 应回到 `12mA`。 |
| 在 TIM4 ISR 中执行恢复 | 恢复包含 SPI 多帧访问和 `HAL_Delay(10)`，不适合中断上下文。 |
| `READFAULT` 非 0 时直接清错误不处理 | 会丢失手册要求的 ILOOP/VLOOP/SPI fault 证据，也不能解释 `4mA/24mA` 跳变来源。 |

### 10.10 建议代码审查清单

实现完成后逐项检查：

| 检查项 | 通过标准 |
| --- | --- |
| `AD5421_RecoverCurrentX100()` 是否使用 `AD5421_TryBeginSequence()` | 多帧恢复不会和普通访问交叠。 |
| 控制寄存器是否仍写 `CUR_SPIOFF_READBACK_COMMAND` | 恢复后控制字与当前正常初始化一致。 |
| 是否保留 `READCONTROL` 校验 | 控制字读回不一致时不能报恢复成功。 |
| 是否保留 `READFAULT` 原始值 | 现场能继续对照手册判断 ILOOP/VLOOP/SPI fault。 |
| 恢复目标是否使用当前目标或最近成功目标 | 断环接回后不会无条件恢复到故障电流。 |
| 恢复成功后是否跳过本轮故障电流写入 | 避免刚恢复目标又被后续分支覆盖。 |
| 恢复失败是否节流 | 避免环路未稳定时反复复位 AD5421。 |
| AO 关闭时是否清恢复状态 | 下次启用不受旧恢复节流影响。 |
| C 注释是否使用 `/* ... */` | 符合仓库 C/C++ 注释约束。 |

### 10.11 台架验证顺序

建议按以下顺序验证，避免一开始就混入自动液位映射、报警输出和 HART 场景：

1. 固件烧录后，先接标准负载和电流表。
2. 发送 `AO1200`，确认稳定约 `12.00mA`。
3. 逻辑分析仪确认 `WRITEDAC` 码值接近 `0x6C4E`。
4. 断开环路，记录 `READFAULT` 原始值。
5. 接回环路，不再手动发送 `AO1200`。
6. 确认恢复周期内出现 `RESET`、`WRITECONTROL 0x1800`、`READCONTROL`、`WRITEDAC 0x6C4E`、`READFAULT`。
7. 确认电流自动回到约 `12.00mA`。
8. 连续重复 10 次，确认不会长期停在约 `4mA` 或约 `24mA`。
9. 再测 `AO400`、`AO2000`、`AO2200` 和 `AOS`。
10. 最后再测 AO 自动液位跟随、故障电流、报警电流、AO 关闭和 HART 通信。

### 10.12 预期最终效果

修改完成后，断环重接场景应表现为：

```text
断环
-> READFAULT 出现 ILOOP/VLOOP/SPI fault 等异常证据
-> AO 服务发现诊断异常
-> 按节流触发 AD5421_RecoverCurrentX100(断环前目标)
-> AD5421 复位并重新写 0x1800 控制字
-> READCONTROL 校验通过
-> 写回目标 DAC 码
-> READFAULT 更新
-> 输出回到目标电流
```

如果恢复后 `READFAULT` 仍非 0，则说明软件已执行了手册建议方向上的复位、控制字恢复和诊断读取，剩余问题应转向环路电源、负载、保护网络、`LDAC`、`RANGE0/1`、`ALARM_CURRENT_DIRECTION` 和 AD5421 供电瞬态排查。
