1. 文档目的与结论口径

本文对当前 CUBE 工程做多轮、跨 CPU、跨协议、跨文档和构建工具的系统梳理，目标不是重复历史问题清单，而是回答以下问题：

  1. 当前源码中还有哪些可以由代码直接证明的问题；
  2. 哪些问题已经有实现，但仍缺真实硬件、PLC 或故障注入证据；
  3. 哪些是正式接受的兼容偏差或残余风险，不能误写成普通代码缺陷；
  4. 哪些检查失败来自本机工具基线过期，而不是固件行为回归；
  5. 下一轮整改应按什么顺序推进，避免只处理表面告警。

本报告中的“确认”表示当前源码和正式资料已经形成可达证据链，不等于已经在真实硬件上复现；“条件风险”表示影响等级依赖物理可达性、主机契约或产品决策；“待台架”表示不能仅凭静态检查宣称闭环。

1.1 总体判断

  • 当前双固件可以 clean-first 构建，CPU2／CPU3 共享协议、结构体、枚举和寄存器公式未发现漂移。
  • 仍有一组需要优先处理的运行态问题，集中在：CPU2 Modbus 输入边界、命令与停机错误语义、双 CPU 看门狗活性监督、CPU3 参数掉电原子性、CPU3 断链阻塞、SI Manual 安全语义和外部命令闭环。
  • 现有测试和文档数量很多，但真实掉电、SPI/UART 故障、长线、PLC、4～20 mA、Wärtsilä 主机、电机限位和长时间跨日调度证据仍不足。构建通过不能替代这些验证。
  • 当前协议台架闭环产物明确给出 Unverifiable：75 个命令中 70 个启用，67 个不可证明闭环，68 个只有寄存器写回显，业务接受／完成 ACK 为 0。这个结果不能因为 catalog 差异为 0 就解释成协议验收通过。
  • 本机 tools/ 已形成较强的专项检查能力，但它不纳入 Git 和 CI，且已有 3 个契约脚本和 2 个单元测试与当前版本基线漂移。当前“本机检查很多”仍不等于“新克隆和服务器可以复现”。

4. P1：优先整改的问题

P1-01 CPU2 Modbus 请求边界不完整，可造成发送缓冲越界和截断帧污染

现状与证据

  • CPU2 发送缓冲区只有 1000 字节：LTD_MAIN_CPU2/Services/Modbus/hostcommu.h:8、hostcommu.c:40-42。
  • 输入寄存器表总量为 0x0A48，即 2632 个寄存器：stateformodbus.h:390-395。
  • FC03／FC04 只按整个寄存器表范围检查，没有执行标准最大 125 个寄存器和响应缓冲容量检查：hostcommu_modbus.c:126-146。
  • FC04 组帧长度为 3 + 2 * count，随后再追加 2 字节 CRC：hostcommu_modbus.c:244-258、hostcommu.c:313-317。
  • 现有通用入口只拒绝长度 <=3 或 >=256，随后无条件读取请求的 [4]、[5]：hostcommu.c:208-259。
  • FC10 不接收实际帧长，不检查 byte-count，直接按声明数量读取 revframe[7 + 2*i]：hostcommu_modbus.c:263-286,358-374。

最小触发

  • FC04 请求 498 个寄存器时，数据最后写到索引 998，CRC 低字节写索引 999，CRC 高字节写索引 1000，首次越过 HCOM_SendBuff[1000]。
  • 先发送完整 FC10 帧在 DMA 缓冲尾部留下旧数据，再发送 CRC 自洽但数据区截断、byte-count 不匹配的 FC10；CRC 只覆盖本次长度，但解析会继续读取 CRC 字节和旧缓冲内容。

影响

可能破坏相邻静态状态、返回畸形响应、错误改变命令／电机／参数并触发保存，严重时导致异常复位或不可预测行为。

建议与验证

  1. FC03／FC04 必须精确 8 字节，数量限制为 1..125。
  2. FC10 必须满足 1<=count<=123、byte_count==2*count、rcvcount==9+2*count。
  3. 所有组帧统一校验 response_len <= sizeof(send_buffer)，区间计算使用无溢出的减法口径。
  4. 用主机桩／ASan 或边界哨兵覆盖数量 0、1、125、126、497、498、123、124，以及每一个截断字节位置和前帧残留污染。

P1-02 CPU2 UART5 中断直接执行完整 Modbus、SPI 和阻塞日志

证据链

  • UART5_IRQHandler() 在 IDLE 中断内直接调用 HostCommuProcess()：LTD_MAIN_CPU2/Core/Src/stm32f4xx_it.c:451-469。
  • FC10 写参数可进入 MotorCtrl_SetCurrent() 和位置源应用：dataanalysis_modbus.c:479-483。
  • TMC5130 SPI 路径使用 HAL_MAX_DELAY，电流应用路径还会打印：motor_ctrl_driver_param.c:485-506、TMC5130.c:358,443。
  • CPU2 printf 逐字符调用 USART1 阻塞发送并使用 HAL_MAX_DELAY：Core/Src/usart.c:27-30。

影响

合法或恶意 UART5 帧都可能放大 ISR 执行时间；电机 SPI 故障时可能长期停在高优先级中断，延迟重量采样、传感器通信、定时任务和同级／低级中断。

建议

ISR 只负责清标志、冻结长度、重启或移交 DMA 并投递事件；CRC、地址校验、参数写、SPI、FRAM 请求和日志全部移到主循环任务态。压测时同时测 UART4、UART6、TIM4 的最大中断延迟和丢帧率。

P1-03 CPU2 电机电流硬件下发失败仍会 ACK 并申请持久化

证据链

  • ReadDeviceParamsFromHoldingRegisters() 检测电流变化后调用 MotorCtrl_SetCurrent()，但显式丢弃返回值：dataanalysis_modbus.c:479-480。
  • MotorCtrl_SetCurrent() 先修改 g_deviceParams.motor_current，再写 TMC；SPI 失败只返回错误，不回滚 RAM 参数：motor_ctrl_driver_param.c:485-508。
  • FC10 随后把候选参数重新提交、请求保存并返回正常回显：hostcommu_modbus.c:278-354。

影响

运行态和 FRAM 可显示新电流，而 TMC 实际仍保持旧电流；设备重启后新值又可能突然生效，形成“显示／持久化值”和“当前执行值”分裂。

建议与验证

硬件应用成功后才能提交候选参数；失败时恢复旧值、返回 Modbus 异常并禁止保存。对 stpr_setCurrent() 注入失败，核对 ACK、FRAM、RAM 和 IHOLD_IRUN 都保持旧值。

P1-04 CPU2 取消停机失败后仍清错并发布待机

  • 取消路径先清命令和错误码，再调用慢停；慢停返回任何错误都只打印，最后仍无条件设置 STATE_STANDBY：LTD_MAIN_CPU2/Application/Src/measure.c:311-331。
  • 底层返回项既包含停止写失败、状态读取失败、健康检查失败和停机超时，也包含停稳后的同步、目标对齐、二次确认或速度恢复失败：motor_ctrl_driver_param.c:703-750、motor_ctrl_motion_api.c:840-858。

在停止下发、运动状态读取或超时阶段失败时，电机可能仍在运动或至少没有确认停稳；在停稳后的同步／恢复阶段失败时，电机可能已停稳，但具体硬件错误仍被掩盖。两类失败都会使 CPU3／外部主机看到“待机、无错误”。只有确认停稳且取消收尾成功后才能清错并进入待机；前半段失败应进入“停机未确认／错误”状态并执行硬件级安全动作，后半段失败也必须保留具体错误。

P1-05 CPU2 命令合法性、启动失败和清错边界不安全

已确认的三条路径

  1. 除取消和无线配对外，ProcessMeasureCmd() 在判断具体命令前统一调用 MeasureStart()：measure.c:93-125。
  2. MeasureStart() 先执行 fault_info_init()，成功后再次清 error_code：measure.c:407-416；未知／预留命令最终只打印“不支持”：measure.c:291-301。因此非法命令也会触发测量前置初始化；初始化成功时，已有故障会先被清除，随后却没有对应的有效业务动作。
  3. MeasureStart() 返回错误后，调用方只 SET_ERROR(start_ret)，没有 return，仍继续进入命令 switch：measure.c:113-125。这会把“初始化失败后是否安全退出”分散给所有下游命令，不能形成统一保证。

共享命令从寄存器直接强转，未见枚举白名单：dataanalysis_modbus.c:304-315。可达序列为“已有真实故障／电机初始化失败 → 写入未知或普通命令 → 入口清错或记录错误 → 仍进入业务分派”。

建议在 Modbus 接收层和命令调度层都建立显式白名单；非法值返回异常且不得触发 MeasureStart()；MeasureStart() 失败必须统一终止本次命令；故障只能由明确恢复／确认流程清除。该问题与既有 CPU2 全局错误报警响应滞后问题 属于同一系统边界，应合并整改而不是只补一个 default。

P1-06 双 CPU 看门狗都由独立定时 ISR 无条件喂狗

CPU2

  • TIM4_IRQHandler() 无条件刷新 IWDG：LTD_MAIN_CPU2/Core/Src/stm32f4xx_it.c:315-325。
  • IWDG 配置：Core/Src/iwdg.c:40-42；TIM4 约 2 s：Core/Src/tim.c:85-88。

CPU3

  • TIM4 约 2 s，IWDG 典型约 4 s：LTD_DISPLAY_CPU3/Core/Src/tim.c:169-191、Core/Src/iwdg.c:40-43。
  • TIM4_IRQHandler() 无条件执行 HAL_IWDG_Refresh()：Core/Src/stm32f4xx_it.c:619-627。

影响边界

主循环永久死锁但中断仍运行时，两颗 MCU 都不会被 IWDG 复位。看门狗并非对所有故障完全失效：全局关中断、TIM4 停止等仍可能触发复位；确定的问题是它无法监督前台主循环和关键任务是否推进。

建议由主循环维护健康代际／票据，定时 ISR 只有观察到代际推进且关键任务健康时才喂狗，或在关键调度完成后由主循环直接喂狗。必须注入“主循环死锁、中断正常”验证复位。

P1-07 CPU3 FRAM 本机参数只有单槽覆盖写，掉电可破坏最后有效镜像

证据链

  • 唯一参数槽地址为 0x1000：LTD_DISPLAY_CPU3/Application/system_param/cpu3_comm_display_params.h:12。
  • 镜像只有 magic、version、params 和 CRC，没有第二槽、generation 或 commit 标记：cpu3_comm_display_params.c:913-927,1081-1088。
  • 保存直接覆盖同一地址，完成后才读回验证：cpu3_comm_display_params.c:1258-1292。
  • FRAM 驱动的命令、地址、payload 传输均忽略 HAL 返回值并使用 HAL_MAX_DELAY：LTD_DISPLAY_CPU3/Application/system_param/mb85rs2m.c:112-162。
  • 下次启动 CRC 失败会初始化默认值并再次写回：cpu3_comm_display_params.c:1383-1399。

精确故障序列

  1. FRAM 中有一份 CRC 正确、明显非默认的 V7 配置；
  2. 修改任一字段触发同槽覆盖；
  3. 在 payload 任意字节边界断电，形成新旧混合镜像；
  4. 重启后 magic／version 可能仍合法，但 CRC 失败；
  5. 加载路径恢复整份默认值，原配置已经没有副本可回退。

V6→V7 迁移也覆盖同一槽；保存失败时当前 RAM 仍可继续运行，但旧 V6 镜像可能已被破坏。V3／V4／V5 迁移甚至丢弃保存结果后打印升级成功：cpu3_comm_display_params.c:1309-1348。

影响与建议

COM1～3 协议／波特率、显示参数、SI 自动 Profile 和报警限值可能整份恢复默认；串口恢复默认后还可能导致现场主站失联。应改为 A/B 双槽：写非活动槽、读回完整校验、最后提交有效标志，启动选择 generation 最大的有效槽；迁移成功前保留 legacy 槽；FRAM 驱动返回真实 HAL 状态。对每个字节边界做 brownout／复位矩阵，结果必须只能是完整旧值或完整新值。

P1-08 CPU3 在 CPU2 断链时约 91% 时间同步忙等

  • CPU2 轮询门限为 100 ms：LTD_DISPLAY_CPU3/Application/app_main.c:22,762-767。
  • 单次 CPU2 响应超时为 1000 ms，主循环在 while(wait_response) 中忙等：cpu2_communicate.c:17,1622-1630。
  • 返回后才更新时间戳，因此断链稳态大致是“忙等约 1000 ms + 运行约 100 ms”，阻塞占比约 1000/(1000+100)=91%。

UART／TIM 中断仍可运行，但 SI 周期任务、OLED、外部协议前台处理和重连逻辑会产生秒级停顿。十次置故障后也没有切换到低频／异步模式。建议改为非阻塞事务状态机；至少在断链后降频并让外部协议快速返回 Busy。拔掉 CPU2 后同时向三路 COM 发送 10 Hz 请求，量化最大响应延迟、OLED 刷新和重连时间。

P1-09 DSM 接受地址 0 并生成响应

  • 地址检查同时接受配置站号和 0：LTD_DISPLAY_CPU3/Communication/external/DSM_modbus/DSM_communication.c:93-96。
  • 地址 0 继续进入 FC01／03／04／05／16 和异常响应路径：DSM_communication.c:100-146。
  • 响应用配置站号构造并追加 CRC：DSM_SlaveModbus_modbus2.c:643-676。

多台从站收到地址 0 的读写帧时会同时回包，造成 RS485 冲突；广播读本身也不应执行。除非 DSM 正式协议明确把地址 0 定义成非标准单播，否则应按 Modbus 语义处理：广播读静默丢弃，允许的广播写可执行但绝不应答。

P1-10 SI 自动 Profile 在 Manual／维护状态仍会启动

  • 官方资料明确 Manual 下不能执行自动功能，自动 Profile 到点时若处于 Manual 不应开始：docs/01_协议与寄存器/SI协议适配/05_官方资料中文整理/05_操作手册_中文整理.md:345,438。
  • 当前调度只检查使能、周期、RTC、去重、重试和重启首轮 SI 阶段，没有 Manual／维护门禁：si_modbus_slave.c:1352-1442。
  • 下层 CPU2_CommCanSendCommand() 只判断通信和快照可用：cpu2_communicate.c:351-355。
  • CPU2 维护态收到新命令后会清除手动抑制并退出，随后执行新命令：LTD_MAIN_CPU2/Application/Src/measure.c:825-840、app_main.c:197-204。

最小序列为“进入 Manual → 自动计划分钟到达 → CPU3 下发 CMD_SI_PROFILE → CPU2 退出维护态并执行 Profile”。这会打断维护或强制操作，不只是显示偏差。正式 SI 待确认清单已把它列为 R-02／P0；整机总账至少按 P1 处理。应使用 CPU2 权威 Manual 状态阻止自动触发，并记录跳过原因和计数。

P1-11 SI Manual 时 CPU3 对外报警仍按阈值合成

  • CPU2 维护／强制动作会发布 manual_alarm_inhibit=1，CPU3 也已读取该共享字段：LTD_MAIN_CPU2/Application/Src/measure.c:825-840、LTD_DISPLAY_CPU3/Communication/internal/main_board_modbus/dataanalysis_modbus.c:564-571。
  • CPU3 SI 离散输入仍直接按当前值、阈值和 Profile 快照合成设备、密度、温度、液位和 Profile 报警，没有消费 manual_alarm_inhibit：si_modbus_slave.c:1135-1206。

因此进入 Manual 后，PLC 仍可能读到 10017~10026/10029~10032 报警。该偏差已经在正式 SI 清单 R-01 中登记，但尚未实现。整改时只抑制 SI 对外报警投影，不应掩盖 CPU2 本机安全故障和继电器保护。

P1-12 外部命令只有寄存器写成功回显，没有可关联本次请求的业务接受／完成 ACK

证据链

  • SI FC05 在线圈映射成功后立即构造功能码回显：si_modbus_slave.c:1519-1564,1769-1816。
  • CPU3→CPU2 FC10 返回只校验功能码、起始地址和数量回显：cpu2_communicate.c:142-164,1559-1639。
  • CPU2 Response10Process() 把寄存器写入候选并立即回显地址／数量：hostcommu_modbus.c:278-374。
  • 真正业务消费发生在后续 CPU2 主循环：LTD_MAIN_CPU2/Application/Src/app_main.c:197-204。
  • 可轮询的 device_state/error_code/current_command 没有 request id、accepted id、completed id 或事务代际，无法严格关联本次命令。

当前暂存的 command-closure 报告给出：75 个命令、70 个启用、67 个不可证明、68 个 RegisterWriteAckOnly、67 个必需参数集合未解析、0 个业务接受／完成 ACK、15 个 BenchPending。

建议共享最小事务状态：command_request_id、accepted_id、completed_id、result/error；外部协议明确区分“寄存器已接收”“业务已接受”“业务已完成”。台架覆盖忙、非法前置条件、重复／并发、运行中失败和 CPU2 重启。

P1-13 CPU2 传感器运动硬限位没有覆盖连续／强制路径

绝对目标检查主要覆盖位置目标运动：motor_ctrl_motion_api.c:1898-1919。MoveNoWait() 只检查距离、方向和 ready／health，不计算绝对目标：motor_ctrl_motion_api.c:302-344；StartVelocity() 没有位置边界：:609-635；强制入口仍走绕过编码器门禁的路径：:934-960。只有 Jog 循环具备较完整的健康、碰撞、丢步和超时 guard：:1995-2031。

这意味着水位、找空气、找零和强制速度运动不能由统一规划层证明不会越过机械边界。现有 CPU2 传感器运动上下限位风险分析 已记录该缺口。建议统一所有运动入口的绝对位置预算、硬限位、碰撞和停止确认，并把 T15／T16 故障注入作为发布门禁。

P1-14 AS5145 DMA 完成回调内同步打印并立即重启 DMA

  • HAL_SPI_RxCpltCallback() 直接进入帧解析：LTD_MAIN_CPU2/BSP/Peripherals/src/AS5145.c:232-235。
  • 失败前 3 次在 Handle_SSI_Error() 内直接调用 ErrorLog_Retry() 并立即 Start_Read_SSI_Data()：AS5145.c:197-214。
  • ErrorLog_Retry() 最终同步 printf：Services/Utilities/error_log.c:720-771；CPU2 printf 是逐字符阻塞 UART。

这与“ISR 只记录、任务态打印／重试”的边界冲突，可能放大 UART6 和其它 DMA 的时序抖动。V1.20.3 恢复三次立即重试后，断线、OCF、COF 和偶发校验错误仍缺实机覆盖。建议回调只发布错误事件和重试请求，由任务态执行日志与下一次 DMA。

P1-15 Wärtsilä 完成态与测量中对外返回同一个状态字

  • 源码注释表定义测量中为 0x0C60、完成为 0x2840：wartsila_modbus_data_analysis.c:45-50。
  • 实际 STATE_WARTSILA_DENSITY_MEASURING 和 STATE_WARTSILA_DENSITY_OVER 都返回 0x0C60：:67-73。
  • 正式兼容文档也明确记录该差异和主机待确认项：docs/01_协议与寄存器/Wartsila协议适配/当前兼容情况与协议栈.md:191-217,305-322。

确认的问题是主机无法仅靠当前状态字区分“测量中”和“完成”；具体是否直接改成 0x2840 仍需真实 PLC／golden frame 定版，因为现场抓包中该值还可能对应空气中下行阶段。完成码未定版前，不得把当前兼容文档写成已闭环。

P1-16 生产固件常开高风险 USART1 调试入口（条件风险）

  • CPU2 CMake 全量收录 Application/Src/*.c，test.c 进入正式 ELF。
  • USART1 在正式启动流程中初始化并启用 DMA／中断：Core/Src/main.c:101-105、Core/Src/usart.c:201-225,503-505。
  • 串口解析接受大量测试命令，语法合法后先 ACK，再分发正式／测试命令：serial_command.c:129-143、serial_command_parser.c:284-354。
  • test.c 可执行 AO、直接运动、循环运动、编码器清零、参数拟合等操作：test.c:1547-1800。
  • 未见认证、维护模式、物理跳线或 Release 编译隔离。

若 PA9／PA10 在成品上外部可接触，应按 P1 发布阻断处理；若必须拆机且有封签、跳线和受控维护流程，可降低等级，但仍应形成书面边界。建议生产构建默认移除测试分发，只在物理维护门禁和限时解锁后开放危险命令，并用 ELF 符号／字符串检查证明生产镜像不含入口。

5. P2：近期整改和一致性问题

P2-01 DSM／Wärtsilä 多参数写不是 CPU2 原子事务

DSM FC16 和 Wärtsilä 四参数写都会按参数逐项向 CPU2 发送。第 N 项失败时，CPU3 能恢复本地镜像并向外返回 0x06，但 CPU2 已经 ACK 的前 N-1 项不会自动回滚：

  • DSM：DSM_SlaveModbus_modbus2.c:1088-1115、DSM_DataAnalysis_modbus2.c:531-535、device_param_sync.c:515-550；
  • Wärtsilä：wartsila_modbus_communication.c:226-230,251-339。

这不是“对外伪成功”，因为外部会收到失败；它是“失败不等于全部未生效”的残余一致性风险。若参数组合要求原子一致，应提供 CPU2 批量事务／影子提交；否则协议必须强制主站在失败后补读、重试并核对最终值。

P2-02 SI 非整日周期在 CPU3 重启后相位漂移

调度锚点仅保存在静态 RAM：si_modbus_slave.c:170-179。重启后按“当日 00:00 + 配置时分”重建：si_modbus_slave.c:1314-1344,1394-1407。

示例：起始 D0 08:00，周期 1000 min，连续计划应为 D0 08:00 → D1 00:40 → D1 17:20 → D2 10:00。若 D1 09:00 重启，锚点重建为 D1 08:00，后续变为 D2 00:40，原 D1 17:20 被跳过。61 min 等不能整除 1440 的周期同样会漂移。

建议持久化绝对 next-trigger／epoch，或从固定全局 epoch 推导；验证跨午夜、计划点前后重启和 RTC 回拨。该问题已在 SI 待确认清单 R18-03 登记，不能继续只靠注释说明“锚点建立后可跨日”。

P2-03 SI 探底频次存在 off-by-one

  • SiProfile_ShouldDetectBottom() 使用 count + 1 >= N 判断：LTD_MAIN_CPU2/Application/Src/measure_density.c:1110-1118。
  • 探底后 SiProfile_AdvanceBottomDetectTriggerCount() 把计数置 1，而不是 0：:1121-1127。
  • 调用顺序是先判断、再推进、再探底：:1620-1625。

序列结果：首次 Profile 探底后 count=1；N=2 时后续每轮都满足 1+1>=2，实际每轮探底；N=5 时探底轮为 1、5、9……，间隔为 4。应明确计数语义为“已完成的非探底轮数”，探底后置 0，并对 N=1／2／5／1000 跑至少 2N+2 轮表驱动测试。

P2-04 CPU2 FC10 ACK 早于 FRAM 写后验证

FC10 只调用 request_device_params_save() 就返回 ACK：hostcommu_modbus.c:348-354；真实保存至少延后约 100 ms，写后校验失败只能稍后置全局错误：system_parameter.c:1025-1046,1074-1102。

如果 ACK 只定义为“运行态参数已接收”，必须增加可查询的 pending／result 事务状态；如果协议把 ACK 定义为“持久化成功”，当前行为不满足定义，应在任务态完成保存后再 ACK。测试要覆盖写失败、读回不一致和 ACK 后掉电。

P2-05 CPU2 A/B 参数槽缺少单槽自愈

CPU2 A 有效时不会读取和修复 B：system_parameter.c:1123-1143；只有从 B 回退或参数归一化时才主动回写：:1145-1162。因此 B 先损坏不会被发现，之后 A 再损坏会直接双槽失效并恢复默认。启动时应同时验证 A/B，只有一个有效时用有效副本修复另一槽并读回校验。

P2-06 CPU3 参数保存失败反馈和迁移日志不完整

  • OLED 参数保存使用 void 包装器丢弃失败结果，菜单仍按正常流程返回，并可能置串口重配标志：cpu3_comm_display_params.c:732-740、display_tankopera.c:3920-3939,3985-3986。
  • V3／V4／V5 迁移保存失败仍打印“已升级”；V7 修正和恢复默认路径也丢弃保存返回值：cpu3_comm_display_params.c:1309-1348,1395-1417。
  • V6 路径已经有正确的失败分支：:1367-1370，可作为统一范式。

菜单应显示“保存失败”，不得置重配成功语义；所有迁移日志必须区分“仅 RAM 生效”和“持久化成功”。根因仍应由 P1-07 的 A/B 原子存储解决。

P2-07 Modbus RTU 仍以约 1T 的 UART IDLE 直接判帧

CPU2 UART5 和 CPU3 多路外部协议都在 UART IDLE 后立即停 DMA，没有独立 t1.5／t3.5 定时器：LTD_MAIN_CPU2/Core/Src/stm32f4xx_it.c:460-468、LTD_DISPLAY_CPU3/Core/Src/stm32f4xx_it.c:199-250。

这会带来帧内停顿拆帧和过早响应风险，但当前没有现场失败波形，项目已经决定暂缓实施。应继续按 Modbus RTU 帧间隔问题分析 记录为受控偏差，不能对外宣称严格满足 RTU t1.5／t3.5。

P2-08 UART6／CH9141 缺少统一链路所有权

CH9141 AT 已有固定总时限，但仍逐字节阻塞接收：ch9141_at.c:151-175,475-511。CH9141、DSM、LTD 和安全协议模块分别执行 DMAStop／Abort／Receive_DMA，未见统一 UART6 owner：ch9141_at.c:523-556,704、dsm_sensor_communication.c:103,179,369、ltd_sensor_communication.c:113,187,265、sensor_safe_transport_uart6.c:83,139,381。

建议建立统一模式切换和恢复状态机；在不同上报周期、传感器重启、AT 超时和持续透传下做并发台架。

P2-09 Wärtsilä 测后回位／探底失败没有对外闭环

回固定点失败和 SearchBottom() 失败的部分路径只打印并切回 CMD_MONITOR_SINGLE，没有设置可关联的活动错误：LTD_MAIN_CPU2/Application/Src/measure.c:1111-1135。外部主机可能看到设备已回单点监测，却不知道测后维护动作失败。应在 Wärtsilä 状态／结果中保留失败原因和完成代际，并与 现有流程梳理 的剩余风险合并验证。

P2-10 国标密度后处理阈值硬编码为 100

LTD_MAIN_CPU2/Application/Src/measure_density.c:885-896 使用固定值 100 参与 GB_FilterPoints_ByDensity20() 点位过滤，并保留 TODO；未找到对应参数定义、单位来源和可追溯依据。建议明确单位和标准条款，再决定固化常量还是纳入参数／协议；用边界点和历史样本回放证明口径不漂移。

P2-11 CPU3 协议切换 ACK 是 Accepted，不是 Completed

协议切换帧先返回 OK，真正 FRAM 保存和 UART 重配在后续主循环执行：protocol_switch_frame.c:91-97、app_main.c:362-405,481-541。正式文档已经明确 ACK 只表示“识别并接受”，工具会等待并二次验证，因此当前不是无条件代码缺陷。残余风险是所有主站都必须遵循二次验证；应在协议字段或文档中持续使用 Accepted 语义，覆盖保存失败、DMA 启动失败和 ACK 后掉电。

P2-12 未来参数版本迁移边界不足

CPU2 当前 A/B 存储能处理现有 V3 原位复用，但 struct_size 或 param_version 不一致会直接拒绝并最终恢复默认：system_parameter.c:791-836,1172-1211。当前没有证据表明 V3 升级会清参；风险在下一次真实结构变化。提升 DEVICE_PARAM_VERSION 前必须先建立逐版本迁移表、旧镜像样例和掉电回滚测试。
