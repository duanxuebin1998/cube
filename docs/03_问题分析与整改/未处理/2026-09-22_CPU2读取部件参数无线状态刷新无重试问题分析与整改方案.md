# CPU2读取部件参数无线状态刷新无重试问题分析与整改方案

- 日期：2026-09-22，2026-09-24 完成代码整改
- 当前状态：CPU2 V1.45.1.0 已完成实现、clean-first 构建和静态契约检查，尚未完成目标板与故障注入验证
- 涉及固件：CPU2 V1.45.1.0；配套 CPU3 保持 V1.44.0.0
- 涉及错误码：`0x00140006`（`WIRELESS_RESP_FORMAT_ERROR`，无线模块响应格式异常）

## 1. 问题摘要

整改前，读取部件参数进入长驻刷新后，一次 CH9141K 无线状态响应格式异常会直接触发最终报错并停止测量。实现既不对该无线状态查询执行局部重试，也不会由命令级自动恢复重新执行 `CMD_READ_PART_PARAMS`。

本次代码核对确认四个关键问题：

1. `BLEMODE`、`BLESTA`、`CCADD` 和异步 `RSSI` 的状态查询均为单次执行，任一响应解析失败都会产生 `0x00140006`。
2. `CH9141_AT_SendCommand()` 本身不包含通用重试；进入 AT 模式只有针对上电百分号等特定异常的一次特殊补偿。
3. `CMD_READ_PART_PARAMS` 不在故障自动恢复命令白名单中，错误到达 `SET_ERROR()` 后立即进入最终报错和停机处理。
4. 顶层日志把“无线状态内容解析失败”和“UART6 未恢复透明传输”合并为同一结论。实际代码可能已经成功退出 AT 并恢复透明传输，但仍保留此前的格式错误，因此当前日志可能扩大故障含义。

CPU2 V1.45.1.0 已在无线只读状态快照更新层实现完整事务重试，并把“状态内容是否有效”和“UART6 交接是否安全”拆开；没有把整条读取部件参数命令加入自动恢复，也没有扩大到扫描、连接、保存和复位等有副作用流程。

## 2. 现场现象

现场日志：

```text
读取部件参数    蓝牙状态刷新失败，UART6透明传输未确认，停止后续流程。错误码=0x00140006
错误    阶段：最终报错    模块：滑环通信    操作：置错误状态
原因：无线模块响应格式异常    错误码：0x00140006
错误名：无线响应格式异常    处理：停止测量
详情：文件：sensor.c,行号：1563,函数：CMD_ReadPartParams
```

`HEAD` 版本的 `sensor.c:1563` 是长驻刷新循环中 `Sensor_CheckAllPartParams()` 返回后的 `SET_ERROR(ret)`。当前工作区已有其它未提交修改，该语句行号已后移，但执行语义未变。

由此可以判断：

- 报错来自 `CMD_ReadPartParams` 的周期刷新阶段，不是故障管理器自行生成的新错误。
- 初次读取很可能已经成功进入 `STATE_READPARAMETEROVER`，后续某轮刷新才失败。
- 部件参数每 `1000 ms` 刷新一次；无线 RSSI 状态每 `5000 ms` 执行一次实际查询，因此异常通常出现在某次 5 秒无线刷新点。
- 现有两行日志不能确定具体失败于 `BLEMODE`、`BLESTA`、`CCADD` 还是异步 `RSSI`。需要异常前完整 CH9141K AT 日志或原始 UART6 抓包继续定位。

## 3. 整改前执行链

```text
CMD_READ_PART_PARAMS
  -> CMD_ReadPartParams()
     -> Sensor_ReadPartParamsInternal(1)
        -> Sensor_UpdateWirelessRssiForPartParams(1)
           -> WirelessPairing_UpdateConnectionStatusSnapshot()
              -> WirelessPairing_ReadConnectionStatus()
                 -> CH9141_AT_EnterSoftwareMode()
                 -> AT+BLEMODE?
                 -> AT+BLESTA?
                 -> AT+CCADD?
                 -> AT+RSSI=ON,<周期>
                 -> 等待异步 RSSI
                 -> AT+RSSI=OFF
                 -> AT+EXIT
                 -> UART6 透明传输交接

初次成功后进入长驻循环：
  -> 每 1000 ms 调用 Sensor_CheckAllPartParams()
     -> 每 5000 ms再次执行无线状态查询
     -> 任一格式错误返回 0x00140006
     -> SET_ERROR(0x00140006)
     -> FaultManager_SetErrorState()
     -> 最终报错、置 STATE_ERROR、停止测量
```

## 4. 整改前为什么没有重试

### 4.1 无线状态查询层没有重试循环

`WirelessPairing_ReadConnectionStatus()` 依次发送以下命令：

| 阶段 | 操作 | 当前失败处理 |
| --- | --- | --- |
| 进入 AT | `AT...` | 特定上电异常允许一次补偿，其它错误返回 |
| 查询模式 | `AT+BLEMODE?` | 单次发送；解析失败直接返回 `WIRELESS_RESP_FORMAT_ERROR` |
| 查询连接状态 | `AT+BLESTA?` | 单次发送；解析失败直接返回 `WIRELESS_RESP_FORMAT_ERROR` |
| 查询对端 MAC | `AT+CCADD?` | 单次发送；MAC 无法解析直接返回 `WIRELESS_RESP_FORMAT_ERROR` |
| 打开 RSSI | `AT+RSSI=ON,<周期>` | 单次发送 |
| 等待 RSSI | 异步文本 | 单次等待；收到文本但无有效 RSSI 时返回 `WIRELESS_RESP_FORMAT_ERROR` |
| 清理和退出 | `RSSI=OFF`、`AT+EXIT` | 普通清理失败时执行一次强制恢复，但不会重新查询状态 |

`CH9141_AT_SendCommand()` 的职责是完成一次排空、发送和响应收集，没有统一重试逻辑。强制关闭 RSSI、退出 AT 和恢复 UART6 属于清理动作，不等于重新执行无线状态查询。

### 4.2 读取部件参数入口没有局部重试

`Sensor_UpdateWirelessRssiForPartParams()` 到达 5 秒刷新周期后只调用一次 `WirelessPairing_UpdateConnectionStatusSnapshot()`，收到非零返回值便向上传递。

`Sensor_ReadPartParamsInternal()` 收到该错误后打印“蓝牙状态刷新失败”并立即返回，没有重试计数、重试延时或恢复成功日志。

### 4.3 命令级自动恢复不覆盖读取部件参数

`FaultRecovery_IsRecoverableCommand()` 白名单包含回零、找液位、单点测量、分布测量、标定等正式业务命令，但不包含 `CMD_READ_PART_PARAMS`。因此即使全局自动恢复次数默认为 3，读取部件参数命令也不会进入该恢复状态机。

该排除有合理的一面：读取部件参数是长驻诊断命令，直接加入命令级自动重跑可能造成重复进入长驻循环、状态切换混乱和无线 AT 查询嵌套。瞬态无线错误更适合在无线查询层局部恢复。

## 5. 错误语义混合问题

当前实现同时维护：

- `ret`：函数执行返回值；
- `status.error_code`：本次无线状态快照中的业务错误。

但在格式错误路径中，两者没有形成清晰边界。以 `BLEMODE` 解析失败为例：

1. 解析失败后把 `ret` 和 `status.error_code` 都设为 `WIRELESS_RESP_FORMAT_ERROR`。
2. `finish` 路径仍可能成功发送 `AT+EXIT`。
3. `CH9141_AT_CompleteTransparentHandoff()` 可能成功确认 UART6 已回到透明传输状态。
4. 函数最终仍返回最早的 `WIRELESS_RESP_FORMAT_ERROR`。
5. 上层把所有非零返回统一打印为“UART6透明传输未确认”。

因此存在两种本质不同的情况：

| 情况 | 无线数据 | UART6 透明交接 | 当前处理 | 合理处理 |
| --- | --- | --- | --- | --- |
| 状态响应坏帧 | 无效 | 已确认成功 | 最终报错并停机 | 有界重试；仍失败则发布无效快照并告警 |
| AT退出、清理或交接失败 | 可能有效或无效 | 未确认 | 最终报错并停机 | 立即停止后续 UART6 访问并进入故障 |

当前日志不能可靠证明第二种情况实际发生。

## 6. 相关通信过程重试盘点

本表覆盖读取部件参数及其直接相关的 CPU2 通信路径。

| 通信过程 | 重试或确认策略 | 结论 |
| --- | --- | --- |
| DSM 常规文本命令 | `UART6_COMM_MAX_RETRY = 3`，记录错误重试和重试成功 | 有重试 |
| DSM `Cv` 兼容探测 | 只静默探测 1 次，避免旧设备连续超时 | 有意单次 |
| 多参数传感器 V3 | 读参数、切模式最多 3 次 | 有重试 |
| 多参数传感器 V4 幂等事务 | 读取以及 D/S 模式选择最多 3 次 | 有重试 |
| 多参数传感器 V4 非幂等事务 | 写入和 L/M 翻转单次发送，通过状态读回判断结果 | 有意单次，避免重复副作用 |
| 安全传感器协议 | 满足恢复策略时重新 HELLO 后再试一次；结果不确定的副作用命令不重发 | 条件重试 |
| CH9141K 无线状态查询 | 每条 AT 命令及解析单次执行；只有清理恢复，没有完整查询重试 | 缺少瞬态错误重试 |
| 无线扫描、连接和保存 | 多数 AT 步骤单次执行；失败流程可复位模块，但不会逐命令重试 | 有意谨慎处理副作用，需按动作分别评估 |
| 扭力 UART 接收 | 被动连续接收；超过 `1000 ms` 无有效帧报超时，下一有效帧可恢复 | 无主动重发 |
| AS5145 SSI 编码器 | 周期采样；连续第 3 帧异常才锁存 | 连续确认，不属于重发 |
| TMC5130 初始化写入 | 初始化寄存器写入最多 3 次 | 有重试 |
| TMC5130 运行期健康检查 | 当前健康读取失败直接返回；依赖上层故障恢复重新初始化 | 无统一局部重试 |

不能把所有“无重试”都视为缺陷。只读、幂等通信适合有界重试；可能产生副作用的写入、连接、复位和翻转命令必须先确认幂等性或增加状态读回，不能机械重复发送。

## 7. 风险评估

### 7.1 当前风险

1. 单次 AT 文本粘包、短帧、异步尾包或瞬时 UART 抖动会直接停止测量。
2. 错误日志无法区分内容格式错误与透明交接失败，现场可能沿错误方向排查无线硬件或透传状态。
3. 错误码 `0x00140006` 覆盖四个解析点，最终日志未保留具体命令、原始长度和 HEX，根因定位信息不足。
4. 读取部件参数是长驻刷新命令，周期运行会放大低概率瞬态错误；每 5 秒一次无线查询意味着运行时间越长，遇到单次异常的概率越高。
5. 当前工作区已有 DSM 成功命令间增加 `300 ms` 间隔的未提交修改。该修改只调整 DSM 命令节拍，不会为 CH9141K 无线 AT 查询增加重试，也不会修复错误语义混合。

### 7.2 直接给所有 AT 命令套三次重试的风险

1. `AT+RSSI=ON` 可能已生效但 ACK 不完整，直接重发会产生重复异步上报或残留文本。
2. `AT+EXIT` 可能已经执行但 ACK 丢失，继续按 AT 状态重发不能证明模块仍处于 AT 模式。
3. 扫描、连接、保存默认连接和复位具有业务副作用，不应与只读查询共用统一重试器。
4. 未完成清理便开始下一轮查询，会进一步污染共享 UART6，影响后续 DSM 响应。

因此重试单位应是“完成清理和透明交接后的整次只读状态查询”，而不是在同一 AT 会话中盲目重发当前命令。

## 8. 整改目标（已实现）

1. 单次可恢复的无线状态坏帧不再立即停机。
2. 最多执行 3 次完整只读状态查询，重试次数与 DSM/V3/V4 当前 UART6 策略保持一致。
3. 每次重试前必须确认上一轮 RSSI 清理、退出 AT 和 UART6 透明交接已经完成。
4. 明确区分状态内容错误和 UART6 交接错误。
5. 命令切换立即终止业务重试，但已开始的 AT 清理和透明交接必须安全收尾。
6. 保留最后一次有效错误码和原始响应诊断，不用通用错误覆盖真实原因。
7. 不对扫描、连接、保存、复位等有副作用流程自动套用同一策略。

## 9. 实际实现方案

### 9.1 分离两个结果维度

本次实现统一以下语义：

- `status.error_code` 表示无线状态内容结果，例如未连接、MAC 无效、RSSI 无效或响应格式异常。
- 函数返回值表示本次 AT/UART6 执行和交接结果，尤其是退出 AT、清理异步 RSSI、恢复 UART6 透明传输是否成功。

当响应格式异常但最终透明交接成功时：

- `status.error_code = WIRELESS_RESP_FORMAT_ERROR`；
- 执行返回值允许为 `NO_ERROR`；
- 调用方根据自身业务决定是否重试、告警或阻断。

当退出 AT、强制清理或透明交接失败时：

- 返回具体的 UART、超时或模式错误；
- `CH9141_UART6_NOT_READY` 保持可见；
- 读取部件参数立即停止后续 UART6 访问并进入最终故障。

### 9.2 为只读状态查询增加完整事务重试

在无线状态快照更新层增加只读查询策略，最多执行 3 次：

```text
for attempt = 1..3
  检查命令切换
  执行完整 WirelessPairing_ReadConnectionStatus
  完成 RSSI OFF、AT EXIT 和透明交接

  如果交接失败
    立即返回具体错误，不继续重试

  如果状态内容有效或明确为未连接
    发布快照并返回

  如果错误属于可恢复的格式异常/瞬态接收异常
    记录 ErrorLog_Retry
    等待 300 ms
    下一轮重新从进入 AT 开始

三次仍失败
  发布最终无效快照
  保留最后一次错误和原始诊断
```

可重试范围严格限制为 `WIRELESS_RESP_FORMAT_ERROR`。接收超时、UART 接收错误以及其它执行错误不在本次重试范围内，避免在无法证明收尾安全时扩大访问。

不重试或立即退出的情况：

- `STATE_SWITCH`；
- `WIRELESS_SLAVE_COMM_TIMEOUT` 等明确业务状态；
- AT 退出、强制清理或透明交接失败；
- 模块状态无法确认、UART6 owner 冲突或正在执行其它事务。

### 9.3 调整读取部件参数失败策略

读取部件参数已按以下规则处理：

| 最终结果 | 实现动作 |
| --- | --- |
| 重试后状态读取成功 | 更新快照，打印“重试成功”，继续刷新 |
| 三次均为格式异常，但 UART6 已确认透明就绪 | 标记无线快照无效，记录告警，保留其它部件参数并继续流程 |
| 蓝牙主机/从机明确未连接 | 发布专用连接错误；是否停止由产品策略决定，不再伪装成格式错误 |
| UART6 未恢复透明传输 | 立即停止后续 UART6 访问，进入最终故障 |
| 命令切换 | 正常退出，不打印最终故障 |

已采用“三次格式异常但透明链路安全时继续读取部件参数”的策略。RSSI 和无线详情属于显示/诊断快照，前面的传感器业务读取可能已经成功；仅因诊断字段坏帧停止整机测量会放大瞬态故障。连续失败时记录无线探测告警并发布无效快照，不再误写成“透明传输未确认”。

### 9.4 日志语义和后续诊断

现有 `ErrorLog_Retry`、`ErrorLog_Recover` 和 `ErrorLog_Warn` 已用于记录尝试次数、恢复成功和连续失败降级；上层失败文本仅保留给真实收尾或透明交接失败。下列逐命令长度、HAL 错误位和原始 HEX 仍需结合台架抓包补充证据，不把未实现的详细诊断写成已完成：

- 操作阶段：`BLEMODE`、`BLESTA`、`CCADD` 或 `RSSI`；
- 尝试次数：`1/3`、`2/3`、`3/3`；
- 收到的有效长度；
- UART6 HAL 错误位；
- 原始响应 HEX；
- 清理结果和最终 UART6 link state。

建议日志口径：

```text
错误    阶段：错误重试    模块：滑环通信    操作：读取BLESTA
原因：无线模块响应格式异常    尝试：1/3    错误码：0x00140006
详情：长度=...，UART错误=...，HEX=...，透明状态=READY
```

重试恢复后：

```text
错误    阶段：重试成功    模块：滑环通信    操作：刷新无线状态
原因：无线响应恢复    尝试：2/3
```

透明交接失败时单独打印：

```text
读取部件参数    无线状态查询收尾失败，UART6透明传输未确认，停止后续UART6访问。
```

## 10. 不推荐方案

### 10.1 把 `CMD_READ_PART_PARAMS` 直接加入自动恢复白名单

不推荐作为首选。该命令是长驻刷新态，命令级重跑会重新进入完整部件读取和长驻循环，容易造成命令状态、刷新节拍和错误上下文重复。局部无线查询重试更小、更可控。

### 10.2 在 `CH9141_AT_SendCommand()` 内无条件重发

不推荐。该函数服务于只读查询、RSSI 开关、退出、复位、扫描和连接等不同语义命令。底层无法仅凭字符串安全判断所有命令是否可重发。

### 10.3 所有无线错误都降级为警告

不推荐。真正的 AT 退出、清理或透明交接失败会威胁后续共享 UART6 事务，必须继续阻断。只能在明确证明 UART6 已恢复透明传输时降级内容格式错误。

### 11.1 静态和主机契约测试

| 编号 | 场景 | 期望结果 |

| T1 | 首次 `BLEMODE` 响应格式错误，第二次正常 | 记录 `1/3` 重试，第二次恢复成功，不进入最终故障 |

| T3 | 首次 `CCADD` 无有效 MAC，第二次正常 | MAC 和连接快照只发布最终完整结果 |
| T4 | RSSI 异步文本无数值，第二次正常 | 第一轮先执行 `RSSI=OFF` 和 `AT+EXIT`，第二轮重新查询 |
| T5 | 连续三次格式异常，三次透明交接均成功 | 无线快照无效并告警；按批准策略继续读取部件参数，不误报透明链路失败 |
| T6 | 格式异常后 `AT+EXIT` 或透明交接失败 | 不继续下一轮查询，立即返回具体交接错误并停止后续 UART6 访问 |
| T7 | 重试等待期间收到命令切换 | 结束必要清理后返回 `STATE_SWITCH`，不进入最终故障 |
| T8 | 蓝牙从机明确未连接 | 返回/发布 `WIRELESS_SLAVE_COMM_TIMEOUT`，不按格式错误重试 |
| T9 | DSM、V3、V4 在无线查询失败后启动 | 只有 link state 为 `TRANSPARENT_READY` 才允许发送传感器命令 |
| T10 | 长驻读取部件参数运行 24 小时 | 单次无线坏帧能够恢复；无 RSSI 异步尾包污染 DSM 响应 |

### 11.2 目标板与现场验证

1. 在 CPU2 与 CH9141K 之间抓取 UART6 双向数据，记录命令、ACK、异步 RSSI 和退出 AT 的共同时间戳。
2. 分别注入短帧、粘包、非预期文本、丢 ACK、延迟异步 RSSI、`RSSI=OFF` 失败和 `AT+EXIT` 失败。
3. 验证每次查询重试前都已完成清理，UART6 不残留 RSSI 文本。
4. 同时运行 DSM 部件参数刷新，确认重试没有污染 `CV/CK/CM/CL/CB/CD/Cb/Cd/CN/Cl/Ch` 响应。
5. 验证 CPU3 显示能够区分 RSSI 无效、从机未连接和最终 UART6 交接故障。
6. 验证命令切换不会因无线清理被长期阻塞，也不会把 UART6 留在 AT 模式。
