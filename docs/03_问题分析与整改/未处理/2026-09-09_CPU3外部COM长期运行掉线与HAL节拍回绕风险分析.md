# CPU3外部COM长期运行掉线与HAL节拍回绕风险分析

更新日期：2026-09-09

当前状态：已完成当前源码静态扫描；已确认1个能在约24.86天后关闭COM1／COM2／COM3协议处理的确定性缺陷，并发现调试日志同时段停止、49.71天回绕时旧数据短暂误判以及普通丢步检测短暂停判等同类风险。本文未修改固件，目标板边界注入和现场上电时间核对待执行。

源码基线：`MAIN@d1f21000783e`，CPU2 `V1.44.0.0`，CPU3 `V1.43.0.0`。本文涉及的固件源文件在分析开始时相对HEAD无差异；工作区已有的其它文档改动不属于本次分析。

关联历史问题：[2026-07-21_CPU3外部RS485假死及CPU2与CPU3通信中断风险整改方案](2026-07-21_CPU3外部RS485假死及CPU2与CPU3通信中断风险整改方案.md)。历史F-21是持续流量导致的UART中断活锁，本文是另一条与上电运行时长相关的主循环状态门控缺陷，二者不是同一根因。

## 2. HAL毫秒节拍的回绕边界

CPU2和CPU3均使用STM32 HAL的32位毫秒节拍。数值从 `0xFFFFFFFF` 加1后回到 `0x00000000`。

| 边界 | 毫秒 | 时间 |
| --- | ---: | --- |
| 有符号半周期 `2^31` | 2,147,483,648 | 24天20小时31分23.648秒 |
| 32位完整周期 `2^32` | 4,294,967,296 | 49天17小时2分47.296秒 |

两种常见时间写法的适用条件不同：

```c
/* 已过时间：只要事件或状态不会跨越完整2^32 ms，可跨回绕正常工作。 */
if ((uint32_t)(now - start) >= interval) { ... }

/* 绝对截止时刻：只能用于当前时刻与截止时刻相差小于2^31 ms的短期活动状态。 */
if ((int32_t)(now - due) >= 0) { ... }
```

第二种写法本身不是错误。它要求 `due` 只在短期等待状态内有效，时间到达后必须清除状态或改为一次性锁存结果。LR-01和LR-02的共同错误是：截止时刻超时后仍在整个上电周期内被反复比较。

本文的有符号边界结果基于当前STM32 ARM目标及其二补码32位整数行为；T01～T08仍要求使用项目实际编译器构建并在目标板边界注入确认，不能只用另一种主机编译器代替。

## 3. LR-01：24.86天后外部COM被重新判为未就绪

### 3.1 这个判断原本的用途

`LTD_DISPLAY_CPU3/Application/app_main.c:28`定义了 `CPU3_EXTERNAL_PORT_STARTUP_GUARD_MS=1000U`。外部COM初始化完成后，`app_main.c:1414`把“当前时刻+1秒”保存为允许外部COM开始工作的截止时刻：

```c
s_external_ports_ready_tick = HAL_GetTick() + CPU3_EXTERNAL_PORT_STARTUP_GUARD_MS;
```

它的本意只是上电时等待1秒，让外部RS485收发器和串口硬件稳定。这个保护期结束后，“外部COM已就绪”应当成为本次上电周期内不再回退的状态。

### 3.2 当前实现错误

`app_main.c:1356-1359`没有锁存就绪状态，而是每轮主循环重新计算：

```c
static bool cpu3_external_ports_startup_ready(void)
{
    return ((int32_t)(HAL_GetTick() - s_external_ports_ready_tick) >= 0);
}
```

令 `D = HAL_GetTick() - s_external_ports_ready_tick`，32位运算后再转换为 `int32_t`：

| `D` | 转换后 | 函数结果 |
| ---: | ---: | --- |
| `0xFFFFFFFF` | -1 | `false`，截止前1 ms |
| `0x00000000` | 0 | `true`，截止时刻 |
| `0x7FFFFFFF` | 2,147,483,647 | `true` |
| `0x80000000` | -2,147,483,648 | `false`，突然翻转 |
| `0xFFFFFFFF` | -1 | `false` |

因此，从启动保护截止时刻起经过精确的 `2^31 ms`后，结果从 `true` 变回 `false`。这不是概率性竞态，不需要UART错误或硬件损坏，在给定节拍下每次都会发生。

### 3.3 通信失效完整执行链

```text
CPU3上电
  → 外部COM初始化完成，保存启动保护截止时刻
  → 1秒后 external_ports_ready=true，COM1／COM2／COM3正常工作
  → 再运行2^31 ms
  → 有符号节拍差从正数翻转为负数
  → external_ports_ready=false
  → 外部COM协议切换、参数重配、SI周期任务不再执行
  → COM1／COM2／COM3接收恢复任务被跳过
  → COM3首次收到请求后，IDLE中断停止RX DMA并置com3_rx_ready=1
  → 主循环因external_ports_ready=false不消费该帧
  → 不进入协议处理，不调用HAL_UART_Transmit_DMA
  → 不会产生这一帧的发送完成中断
  → RX DMA也不由正常帧处理路径重启
  → PLC表现为设备掉线
```

直接源码证据：

- `app_main.c:1449`：每轮重新计算 `external_ports_ready`。
- `app_main.c:1450`及 `app_main.c:839-889`：恢复任务在未就绪时跳过三路外部COM。
- `app_main.c:1451-1455`：协议切换、串口重配和SI周期任务仅在外部COM就绪时执行。
- `app_main.c:1576-1625`：COM3接收帧仅在 `external_ports_ready && com3_rx_ready` 时处理，回包和RX DMA恢复都在这个分支内。

### 3.4 为什么屏幕和电流仍然正常

`external_ports_ready` 只门控CPU3的三路外部COM处理及关联任务，没有停止主循环：

- `app_main.c:1456`仍执行 `Display_Task()`，屏幕继续刷新。
- `app_main.c:1633-1637`的CPU2轮询没有受 `external_ports_ready` 限制。
- 模拟电流输出由CPU2业务维持，CPU3外部COM门控失效不会自动中断当前输出。

这个现象区分于历史F-21中断活锁。F-21发生时OLED和其它前台任务也会停止；LR-01发生时主循环仍在运行，只是外部COM分支被条件跳过。

### 3.5 为什么看门狗不会复位

`app_main.c:895-898`的 `CPU3_WatchdogReportProgress()` 只对前台健康代次加1。主循环在外部COM被跳过前后仍多次调用它，包括 `app_main.c:1448`、`1457`、`1573`、`1626`、`1630`、`1644`和`1652`。

`LTD_DISPLAY_CPU3/Core/Src/stm32f4xx_it.c:682-691`中，TIM4只检查这个代次是否变化，变化就刷新IWDG。因此当前看门狗可以发现“主循环整体不再推进”，但不能发现“主循环正常转动、外部COM永久被条件跳过”。

### 3.6 为什么会按上电顺序陆续掉线

`HAL_GetTick()`是每台CPU3的本地上电运行时间。先上电的设备先到达 `2^31 ms`边界，后上电的设备依次到达，所以故障顺序与安装上电顺序一致。重新上电后 `HAL_GetTick()`和启动保护截止值重建，通信立即恢复。

如果不重启，当tick完整回绕并再到达启动保护截止值后，该判断会再次变为 `true`。也就是说，当前实现在每个49.71天周期中大约有一半时间判为就绪，另一半时间判为未就绪。

## 4. LR-02：CPU3异步调试日志在24.86天后停止

`LTD_DISPLAY_CPU3/Application/cpu3_debug_log.c:37`定义了绝对重试截止值 `s_log_next_retry_tick`。`cpu3_debug_log.c:206`在初始化时将其置0；只有DMA启动失败或发送错误时，才在`cpu3_debug_log.c:178`或`477`改为“当前时刻+10 ms”。

`cpu3_debug_log.c:158-161`每次启动日志DMA前都执行：

```c
now = HAL_GetTick();
if ((int32_t)(now - s_log_next_retry_tick) < 0) {
    return;
}
```

成功启动DMA后没有清除 `s_log_next_retry_tick`。因此：

1. 如果日志DMA从未失败，截止值一直是0，当 `HAL_GetTick()==0x80000000`时比较翻转；
2. 如果曾发生DMA失败，将在最近一次重试截止值后24.86天翻转；
3. 翻转后 `Cpu3Log_StartNextTransfer()` 每次都直接返回，没有新的DMA尝试去刷新截止值；
4. `app_main.c:1647`仍调用 `Cpu3Log_Service()`，且入队函数不阻塞业务，所以主循环和COM3不会因日志队列卡死；
5. 队列最终填满，新日志只增加丢弃计数，COM12不再有现场输出。

日志比较会在HAL tick完整回绕到低半区后再次放行，因此LR-02表现为约半个tick周期停发、约半个周期可发，而不是永久停发。LR-01和LR-02可以在接近的运行时间发生。现场如果依赖COM12日志判断COM3掉线时状态，LR-02会显著增加取证难度。

## 5. 同类写法扫描结果

### 5.1 扫描边界

本次扫描CPU2和CPU3共279个自研 `.c/.h` 文件，重点检查：

- `HAL_GetTick()`的所有自研调用点；
- `(int32_t)(now-due)`形式的有符号节拍比较；
- `tick = now + delay`形式的绝对截止值；
- `new_tick <= old_tick`等直接时刻大小比较；
- 最近帧、最近错误、重试时刻和显示时刻等长寿命时间戳；
- 8位／16位周期计数和32位诊断计数的溢出影响。

扫描排除`Drivers/`、`Middlewares/`、MDK构建输出和Debug／Release产物。STM32 HAL库自身的短期阻塞超时使用标准无符号差值，不纳入项目缺陷数。

### 5.2 有符号截止时刻逐项复核

### 5.3 49.71天完整回绕的追加风险

#### LR-03：普通丢步检测跨回绕停判

`LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_lost_step_detect.c:243-247`先取滑动窗口最旧和最新的tick，然后直接比较：

```c
uint32_t tick_old = tick_buf[oldest_idx];
uint32_t tick_new = tick_buf[newest_idx];

if (tick_new <= tick_old) {
    return NO_ERROR;
}
```

当最旧样本在 `0xFFFFFFFF` 前、最新样本在回绕后，`tick_new` 数值必然小于 `tick_old`，函数直接返回 `NO_ERROR`。当前窗口6个样本、每1秒采样一次，直到最旧样本也移到回绕后，普通丢步判定大约停止5秒。

同文件的方式5路径在`motor_ctrl_lost_step_detect.c:428-429`直接用无符号差值计算 `window_ms`，可以正常跨越回绕；LR-03仅存在于前一条普通路径。

#### LR-04：扭力通信长期断链后短暂误判正常

`LTD_MAIN_CPU2/Services/Weight/weight.c:87,103-108`在初始化和收到有效帧时记录 `s_weight_last_rx_tick`。`weight.c:140-141`判断：

```c
if ((now - s_weight_last_rx_tick) < WEIGHT_COMM_TIMEOUT_MS) {
    return NO_ERROR;
}
```

`WEIGHT_COMM_TIMEOUT_MS` 为1000 ms。如果最后一帧之后整整49.71天都没有新帧，无符号差值会从 `0xFFFFFFFF` 回到0，接下来约1秒内返回 `NO_ERROR`。`weight.c:302-307`的碰撞检查会以此直接返回值决定是否继续使用当前扭力。

该分支没有清除 `g_measurement.device_status.error_code`，因此不能表述为“全局故障自动恢复”；确定风险是本次调用短暂返回正常并可继续使用旧扭力。

#### LR-05：DM4 V4超时快照在回绕后短暂重新变新鲜

`LTD_MAIN_CPU2/Services/Sensor/Protocols/Dm4/V4/multiparam_v4_active_stream.c:492-510`在1.5秒无新帧后锁存超时，但不清除 `s_latest_snapshot.valid`。`multiparam_v4_measurement.c:176-193`中的新鲜快照复制函数只使用：

```c
if ((HAL_GetTick() - snapshot->received_tick) > MULTIPARAM_V4_ACTIVE_TIMEOUT_MS) {
    return SENSOR_DATA_STALE;
}
```

如果最后一帧之后整整49.71天都没有新帧，此差值在回绕后从0重新增长，原快照可在1.5秒内再次通过新鲜度检查。`multiparam_v4_measurement.c:436-470`和`546-564`等密度／液位读取接口都使用该函数，因此可能返回最后一帧的旧值。

同一个失效快照还进入以下路径：

- `multiparam_v4_active_stream.c:136-157,739-746`：快照年龄再次落入1.5秒窗口；序号回退量大于等于半周期时，新收到的候选帧可能被按乱序帧拒绝，而通用“快照是否新鲜”接口会返回真。
- `LTD_MAIN_CPU2/Services/Sensor/sensor_driver_registry.c:161-177,217-239`：水位或磁零点功能开关在发送L／M命令前用同一年龄判断；旧快照恰好与目标状态一致时可直接返回 `NO_ERROR`，跳过本应执行的状态确认或调整。

该风险需要“曾有有效快照、主动接收状态未重置、随后连续49.71天无新帧、且恰好在1.5秒窗口内调用业务读取”，不是本次外部COM顺序掉线的竞争解释。

### 5.4 其余长期状态复核

- CPU2／CPU3多数周期任务使用 `(uint32_t)(now-last) >= interval`，且 `last` 在毫秒、秒或分钟周期内刷新，可正常跨越49.71天回绕。
- CPU2 TIM4的8位业务分频计数每8次清0，不会长期累加到溢出。
- CPU3显示值高亮截止值在500 ms到期后清除，长按释放保护和按键消抖使用短期无符号差值，未发现固定长运行锁死链。
- CPU3外部COM收发计数、日志丢弃计数和看门狗健康代次为32位计数。它们回绕后会从0重新计数，但当前只用于统计或与上次值做不等比较，未发现因单次溢出导致COM关闭的路径。
- CPU2 `error_log.c:56-70`的“最近错误已打印”标记也只按200 ms无符号年龄判断。如果登记错误后连续49.71天没有再次消费该标记，完整回绕后的200 ms内同码错误可被误认为刚打印过，最多漏一条诊断输出；它不改变故障码、控制或通信状态，因此作为低影响观察保留，不单列整改编号。
- 已有C-17仍存在：外部COM每端口只有1帧pending缓冲，新响应可覆盖旧响应；普通串口重配等待三口全部无RX ready、TX busy和pending，没有统一截止时间。它们可造成高流量下的响应丢失或重配长期等待，但没有固定的24.86天触发时间，不能用来解释本次“按上电顺序”特征。

## 6. 建议整改方案

### 6.1 P0：把外部COM启动保护改为一次性锁存

不再保存永久比较的绝对截止值，改为“启动时刻+已就绪标志”：

```c
static uint32_t s_external_ports_guard_start_tick;
static bool s_external_ports_ready;

static bool cpu3_external_ports_startup_ready(void)
{
    if (!s_external_ports_ready &&
        ((uint32_t)(HAL_GetTick() - s_external_ports_guard_start_tick) >=
         CPU3_EXTERNAL_PORT_STARTUP_GUARD_MS)) {
        s_external_ports_ready = true;
    }
    return s_external_ports_ready;
}
```

关键不变量：

1. 每次上电初始化时 `s_external_ports_ready=false`；
2. 保护期内允许屏幕和CPU2轮询继续；
3. 保护期结束后只允许 `false→true`，本次上电周期内不得因tick变化自动回退；
4. 如果将来需要运行期重新施加硬件稳定窗口，必须由明确的重初始化事件重置标志，不得依靠时间比较自动回退。

### 6.2 P1：日志重试增加显式有效标志

建议使用 `s_log_retry_waiting + s_log_retry_start_tick`，并用无符号已过时间判断10 ms退避。成功启动DMA或退避到期后必须清除 `s_log_retry_waiting`。不建议只用0作为无效截止值，因为0也是tick回绕时的合法时刻。

### 6.3 P1：超时后通过状态失效，只允许新帧恢复

- 扭力通信增加明确的链路有效状态；超时后置无效，只有 `Weight_MarkFrameReceived()` 可重新置有效。碰撞和极限判定先检查有效状态，再检查短期时间差。
- DM4 V4超时时使快照失效，或者使 `MULTIPARAM_V4_CopyFreshSnapshot()` 同时检查 `s_timeout_latched==0`。只有发布新的完整有效帧可清除超时状态。
- 上述状态和快照由中断／PendSV与业务共享，落地时必须保留当前临界区或快照复制边界，不能只在函数外无保护读一个新标志。

### 6.4 P1：丢步检测改用无符号窗口差值

删除 `tick_new <= tick_old` 这个绝对时刻顺序判断，改为：

```c
uint32_t window_ms = tick_new - tick_old;
if ((window_ms == 0U) || (window_ms > LOST_STEP_WINDOW_MAX_MS)) {
    return NO_ERROR;
}
```

`LOST_STEP_WINDOW_MAX_MS`应根据6个样本、1秒采样周期和允许的调度偏差明确定义，用于拒绝真正无效的长窗口，而不是拒绝合法的tick回绕。

### 6.5 P2：统一节拍API和静态检查规则

建议对CPU2和CPU3统一两类接口，并在函数注释中写明使用条件：

```c
bool TickElapsed(uint32_t now, uint32_t start, uint32_t interval);
bool TickDeadlineReached(uint32_t now, uint32_t due);
```

- `TickElapsed`：只允许 `interval < 2^31 ms`，用于防抖、周期、超时和短期窗口。
- `TickDeadlineReached`：只允许处于显式active／pending状态的短期截止值，到期必须失效或重建。
- 永久业务状态不得由绝对截止时刻在每轮重新推导；应用一次性锁存或明确状态机。
- 禁止使用 `new_tick > old_tick`或 `new_tick <= old_tick` 判断先后。
- “最近有效数据”如果可能保留超过一个tick周期，必须与有效／超时状态绑定，不得仅靠年龄差值自动恢复有效。

### 6.6 看门狗和通信自恢复增强

看门狗不应以“一定会复位”代替LR-01的源码修复。建议同时增加两层检查：

1. 启动保护到期后，如外部COM就绪状态发生 `true→false`，记录内部不可能状态并执行受控重初始化；修复后正常程序不应出现此转换。
2. 外部COM健康不能以“必须持续收到请求”作为喂狗条件，因为现场可以合法静默；应检查“串口任务被调度、RX DMA处于运行或有受控恢复事件、TX busy不超过按帧长和波特率计算的最大时间”。

对 `g_tx_busy_com1/2/3` 建议增加发送启始时刻和按帧长／波特率计算的有界超时恢复。当前源码只在DMA启动失败、UART错误回调或TX完成回调中清busy，没有主循环时间上限。这是既有C-17和通信恢复设计需要继续收口的内容，但它不改变LR-01的根因结论。

## 7. 快速稳定复现方法

### 7.1 主机边界测试（推荐作为首选）

把与硬件无关的tick判断抽成可测函数，不需要真实等待25天。至少覆盖：

| 用例 | 输入 | 当前缺陷预期 | 修复后预期 |
| --- | --- | --- | --- |
| T01 | 外部COM截止时刻前1 ms | 未就绪 | 未就绪 |
| T02 | 到达截止时刻 | 就绪 | 就绪并锁存 |
| T03 | 截止后 `0x7FFFFFFF ms` | 就绪 | 就绪 |
| T04 | 截止后 `0x80000000 ms` | 变为未就绪 | 仍就绪 |
| T05 | tick完整回绕 | 先未就绪，到截止低位值后再就绪 | 始终就绪 |
| T06 | 日志重试延时10 ms，横跨 `0xFFFFFFFF→0` | 短期退避可正常，但截止值长期保留 | 10 ms后清除waiting，后续不再比较旧截止值 |
| T07 | 扭力／V4数据超时后注入整周期的同tick值 | 旧数据短暂通过年龄检查 | 仍为无效，必须新帧才恢复 |
| T08 | 丢步滑窗的old在回绕前、new在回绕后 | 返回 `NO_ERROR`且不判定 | 计算得正确的约5秒 `window_ms` 并正常判定 |

### 7.2 目标板边界注入

使用专用Debug固件或ST-Link在暂停状态下注入tick，不等待真实25天：

1. 上电并等待外部COM保护结束，确认COM1／COM2／COM3均可回应。
2. 记录 `s_external_ports_ready_tick`，把HAL tick注入为 `ready_tick + 0x7FFFFFFE`，恢复运行并发送COM3合法请求，应仍回应。
3. 依次进入 `+0x7FFFFFFF` 和 `+0x80000000`边界。当前固件在后一边界必然得到 `external_ports_ready=false`。
4. 发送一帧COM3请求，确认IDLE中断置 `com3_rx_ready=1`，但主循环不清除它、不进入 `cpu3_port_process()`、不启动TX DMA。
5. 确认OLED继续刷新、CPU2轮询继续、TIM4仍刷新IWDG。
6. 刷入修复候选后重复同样边界，COM3必须始终回应，且不受COM1／COM2并发流量影响。

直接改写HAL tick会同时影响所有周期任务，所以此测试只用于时间边界故障注入，不作为完整业务回归。

### 7.3 现场根因核对

| 证据 | 获取方法 | 通过标准 |
| --- | --- | --- |
| 每台设备本次上电时刻 | 施工记录、PLC首次上线时刻或供电记录 | 能区分各台设备的实际连续上电起点 |
| 首次掉线时刻 | PLC通信报警、网关或主站记录 | 不使用人工发现时刻替代真实首次失联时刻 |
| 连续运行时长 | 掉线时刻减本次上电时刻 | 多台设备均聚集在24天20小时31分附近，先上电者先到边界 |
| CPU3版本 | 启动版本行、屏幕版本页或可追溯固件哈希 | 现场版本包含 `cpu3_external_ports_startup_ready()` 当前实现 |
| 掉线时本机状态 | 屏幕刷新、电流输出、按键、CPU2板间数据 | 主循环和CPU2仍运行，外部COM不回应 |
| 上电恢复 | 记录复位前后首个合法请求 | 重新上电后COM3立即恢复 |

COM12日志在LR-02条件下也可停止，因此“掉线时没有日志”不能反证LR-01。优先使用PLC侧时间、设备上电记录和边界注入结果。
