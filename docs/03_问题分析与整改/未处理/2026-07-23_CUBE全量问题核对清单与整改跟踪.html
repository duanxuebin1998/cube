C-01 P0 代码已整改，待验证 FC03／FC04 已增加 1～125 数量和响应容量门禁，原越界组包路径已被代码封堵。 覆盖数量 0、1、125、126，以及原 N=498／499／1001 边界；畸形帧不得组包、越界或污染后续事务。
C-02 P0 代码已整改，待验证 共享 FC10 已收口为偶数起始、偶数数量 2～122，并校验 byte count 和实际帧长。 覆盖短帧、长帧、奇地址、奇数量、0／1／122／123／253；失败必须不改 RAM、硬件或 FRAM。
C-03 P1 部分整改，残余仍在 FC10 尚未形成通用的候选校验、硬件应用、RAM／FRAM 提交和 ACK 原子事务；写后校验失败不回滚运行态，LH 阈值／标定／阻尼及 waterLevelCorrection 仍缺 CPU2 权威语义校验。 建立“候选—统一校验—提交—持久化—ACK”事务；故障注入验证 RAM、寄存器镜像、硬件副作用、FRAM 和重启值属于同一次提交。
C-04 P0 仍存在 电机故障仍可能被后续健康同步覆盖，目标未到位路径仍可能返回成功。 锁存首个高优先级运动故障，完成状态只能在停止、到位和驱动健康均成立时发布。
C-05 P0 仍存在 取消流程仍存在先清故障、慢停失败后发布待机的状态失真。 先停机并确认停止，再决定清错和发布待机；覆盖停机超时、驱动异常和重复取消。
C-06 P1 部分整改，残余仍在 非法命令、重复启动、全局清错和活动故障下的命令准入仍未统一；长循环的全局故障及时退出另见 C-41。 建立统一命令准入和清错权限表，活动故障、忙态、重复命令和非法值均有确定返回。
C-07 P1 仍存在 AS5145 好帧仍可能越权清运动故障，12-13／12-11 生成链未闭环；编码器 Ready 仍缺连续稳定窗口，孤立好帧可过早恢复可用。 按故障 owner 清错；要求连续 N 帧满足 parity、OCF、COF 条件后才 Ready，并验证单帧好坏交替和持续故障。
C-08 P1 部分整改，CPU2 残余仍在 CPU3 已改为前台健康代际推进后才由 TIM4 喂狗；CPU2 目前只用 RETTOBASE 避免 TIM4 抢占其它 ISR 时喂狗，仍没有主循环／关键业务健康票据，阻塞式前台失活仍可能被持续续命。 为 CPU2 建立主循环／关键任务健康投票；双端执行前台卡死、ISR 活跃、通信活锁和外设阻塞故障注入。
C-09 P0 仍存在 每次测量启动仍可能刷新扭力接收时间，制造“刚收到帧”的伪新鲜状态。 只有真实校验通过的扭力帧可更新新鲜度；覆盖启动前已超时、启动后无帧和畸形帧。
C-10 P0 仍存在 合法 128～200 点仍可能使 int8_t 索引回绕并形成负索引写栈。 改用可覆盖点数上限的无符号类型，并覆盖 127、128、199、200 和上限外输入。
C-11 P0 仍存在 探底失败、偏差超限和取消路径仍可能伪装为完成态或发布回退结果。 统一成功、失败、取消、降级四类终态；只有完整成功路径可发布完成代次和有效结果。
C-12 P1 部分整改，残余仍在 原维护模式前台忙等已改为非阻塞叠加态；CPU3 V1.31 在完整快照无效时禁发维护命令，并把结果页改为“指令已发送”。但进入／退出维护和清锁存仍占用正式命令槽，可隐式抢占测量。 产品明确“不抢占、忙时拒绝或显式取消后执行”；若不抢占，应把瞬时控制事件与测量命令槽分离。
C-13 P1 仍存在 水位跟随恢复阈值仍存在“定义 20 次、实际按 5 次”不一致，步进后水位未可靠刷新。 统一计数语义；每次步进后重新采样并更新水位，覆盖阈值两侧和状态抖动。
C-14 P1 部分整改，残余仍在 UART／HART 已部分移出硬件 IRQ，但 HART 仍在 PendSV 异常上下文；AS5145／SPI5 回调仍有同步处理和日志风险。 中断只记录事件和最小快照，协议解析、日志、重试和 SPI 重操作移至有界后台状态机，并测量最坏中断延迟。
C-15 P1 仍存在 CPU3 单次 CPU2 请求仍可同步等待约 1000 ms；LH FC10 外层 1.5 s 轮询又嵌套逐笔内部等待，不能形成真实硬截止时间。 改为跨主循环推进的异步事务，使用覆盖全部内部请求的绝对 deadline，并做断链／慢响应／并发 COM 压测。
C-16 P1 仍存在 CPU3 本机参数仍是单槽覆盖写，掉电可能同时破坏最后有效值。 实现 A/B 槽、generation、完整 CRC 和写后校验；执行逐字节掉电／复位矩阵。
C-17 P1 部分整改，残余仍在 490820b 已增强 UART 接管、失败重初始化和逐口协议切换；单帧 pending 覆盖以及普通重配等待三口全空、无总截止仍在。 建立队列或背压，给重配事务统一 deadline；覆盖三口并发、持续流量、取消和切换失败。
C-18 P1 仍存在 SI 自动 Profile 仍缺 Manual／维护态门禁，manual_alarm_inhibit 也未完整投影到 SI 对外状态。 调度器和命令入口同时门禁，并定义 Manual／维护时的报警、忙态和完成状态。
C-19 P1 部分表达改善，闭环仍缺 CPU3 维护页已不再把写 ACK 显示成“已进入／已退出”，但外部动作命令仍以寄存器写 ACK 代替业务接受／完成闭环，没有 request ID、完成 ID 或 boot epoch。 增加可关联的请求、接受、执行、完成／失败代次，重启和重复请求不得误配旧结果。
C-20 P0 仍存在 Wärtsilä 超 100 点仍会截断；旧结果失效、完成／失败关联、液位识别条件、超时按空气、整区本地写成功回显等语义仍未闭环。任意地址转发已修，但不能据此关闭本项。 明确最大点数和字段有效性；启动时失效旧结果；失败不得发布完成；覆盖 100／101／200 点、传感器超时、液面未识别和写范围边界。
C-21 — 产品行为，不整改 <30.0 pF → 99999.9 pF 已明确为产品特殊处理，不得作为缺陷删除，也不得顺带清理 zero_cap。 移至 F-18；只需把契约、适用版本和回归用例写清。
C-22 P1 仍存在 DSM 版本、定长帧、ACK、BCC 和模式业务成功判定仍未形成统一事务契约。 按命令定义精确长度、帧形和 ACK；业务解析失败允许有界重试，并覆盖全部维护线版本和 golden frame。

原因与证据：INPUTREGISTER_AMOUNT=0x0A48，但 HCOM_SendBuff 只有 1000 B；FC04 请求 N=498 时 CRC 高字节首次写到索引 1000，N≥499 时响应 payload 已越界，N≥1001 时还会越写 SlaveTempBuffer[1000]。FC03 当前表长 346，不会写越 1000 B 发送缓冲，但 N≥128 时 1 B byte count 截断。FC03／FC04 均未拒绝数量 0。位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu.c:192-327、hostcommu_modbus.c:31-34,126-167,218-258。

影响：异常大范围 FC04 可写坏响应缓冲、相邻内存或临时数组；超量 FC03 会形成错误 byte count；数量 0 会形成 start-1 的有符号负边界，并可能返回空成功帧。

当前结论仍存在，维持 P0。这是站号和 CRC 正确、但数量异常的 UART5 请求可直接触发的静态数组越界路径，不只是 Modbus 标准偏差；当前 CPU3 正常轮询不会发送这种请求。

关键边界FC04 输入表有 2632 项，发送缓冲仅 1000 B；完整响应长度为 2×N+5。N=498 首次越写 CRC 高字节，N≥499 payload 越界，N≥1001 临时数组也越界；FC03 表长 346，仅存在超标准和 byte count 截断。

当前执行链

  1. UART5 收到地址和 CRC 正确的 FC03／FC04 请求，HostCommuProcess() 只校验总长度、站号和 CRC；当前 CPU3 正常轮询最大组为 114 个寄存器，点阵块为 96，不会主动触发超 125 请求。
  2. JudgeStartAddress() 只拿起始地址和数量与整张表比较，没有要求数量大于 0，也没有限制标准上限 125。
  3. Compose03Package()／Compose04Package() 把 count×2 窄化写入 1 B byte count，并按请求数量连续写临时数组和发送缓冲。
  4. 外层继续在当前发送长度后写两字节 CRC：N=498 时 payload 止于索引 998、CRC 低字节位于 999，CRC 高字节首次写到索引 1000；N≥499 时 payload 本身开始越界，随后 CRC 计算／写入和 DMA 长度仍继续扩大；N≥1001 时 SlaveTempBuffer 也越界。
  5. 数量为 0 时变量仍是有符号 int，start+count-1 形成 start-1 的负边界值，不是整数下溢或未定义行为；start=table_count,count=0 还可能被接受并返回空成功帧。

根因

地址跨度、Modbus PDU 约束和真实缓冲容量被混在一个只看整表范围的判断中；组包器没有接收目标容量，也没有失败返回语义；byte count 窄化前没有范围证明。

整改方案

  1. 请求分派前统一要求 1<=count<=125，并用 start<table_count && count<=table_count-start 避免加法溢出。
  2. 编译期和运行期同时证明 2×count+5<=sizeof(send_buffer)；组包函数必须接收容量并能在不足时返回失败，禁止部分组包。
  3. 非法数量返回 Modbus 异常 0x03，非法地址跨度返回 0x02；长度不足以安全解析时静默丢弃。
  4. 完整方案建立按功能码的请求形状表和容量安全响应构建器，解析结果使用局部不可变对象，并与 C-14 一起把组包移出 ISR。

完整分析：短帧陈旧数据链、原子解析门禁与毒化测试

当前结论仍存在，维持 P0。CRC 正确只能证明收到的那段字节未损坏，不能证明 FC10 数据区满足声明长度；N=253 时还会读取 512 B UART5 数组之外。

核心风险Compose10Package() 不接收实际帧长，也不读取 byteCount；小数量短帧读取本次接收长度之外的 DMA 残留，大数量声明则可形成真实数组越界读并写入参数。

  1. 可构造 CRC 正确、总长度仍小于 256 B，但数量、byte count 和实际数据长度互相矛盾的 FC10；例如声明 N=253 的短帧可通过当前 CRC、功能码和整表范围检查。
  2. HostCommuProcess() 接受 4～255 B，却没有按功能码检查精确长度；4／5 B 片段通过地址和 CRC 门禁后，读取 rcvbuff[4]／rcvbuff[5] 已越过本次实际接收片段，虽仍落在 512 B UART5 数组内。
  3. JudgeStartAddress() 只判整表跨度，允许数量 0，也没有共享字段所需的偶数起始、偶数数量和 2～122 数量门禁。
  4. Compose10Package() 按声明数量读取 revframe[7+2*i] 和 revframe[8+2*i]，不证明 byteCount==2×count 或 len==9+byteCount；末次读取索引为 2×N+6，N=253 时访问索引 512。
  5. 读出的本帧数据或旧缓冲残留进入保持寄存器、g_deviceParams 和延后保存链，并可能得到成功回显。

根因与影响

解析层没有把“实际接收长度、声明数量、byte count、32 位字段对齐、表跨度和目标容量”作为一个不可分割的请求契约，组包／执行函数也没有接收 length。结果是 CRC 正确的短帧可读取 DMA 旧数据，N=253 时还会读取索引 512 越过 UART5 数组，随后污染运行参数、进入持久化并向主机回显成功。

整改方案

先执行不会越界的安全最小长度、地址和 CRC 检查；短到不足以读取 FC10 固定头的帧静默丢弃。对可安全解析的帧，在任何数据读取和全局写入前一次性验证：起始地址为偶数、count 为偶数且 2<=count<=122、byteCount==2×count、len==9+byteCount，并用 start<table_count && count<=table_count-start 校验范围。解析函数接收 (buf,len) 并只输出局部候选，全部验证成功后才提交。数量、对齐、byte count 或帧形状错误返回 0x03，地址跨度错误返回 0x02。

状态与兼容

所有门禁失败都必须保证保持寄存器、g_deviceParams、硬件、保存标志和 FRAM 请求完全不变。这是在 CPU2 端实现共享协议 25 已有契约，不需要新故障码或提升协议版本；它与 Wärtsilä 已确认的现场特殊 FC10 方言必须在代码、文档和测试中保持分离。

验证边界：需执行偏差、卡滞、编码器错误、驱动错误和循环耗尽故障注入；静态检查不替代 T15／T16 台架。

完整分析：执行链、根因、整改语义与回归矩阵

当前结论C-04A 的错误覆盖和 C-04B 的停稳后到位缺口均在实际使用的 MotorCtrl_MoveAndWait() 路径存在，维持 P0。C-04C 的 10 轮耗尽出口也存在，但当前业务已改用 Jog 绝对定位，该公共接口在当前源码中没有调用者，属于潜在 P1。

成功判定缺口当前代码把“驱动已停止、同步／健康 helper 返回 NO_ERROR”近似当作“运动成功”；该成功甚至可能来自“位置同步失败但健康检查成功”。对于 5 mm 及以下命令、位移偏差不超过 70% 的提前停止，或使用电机位置源时，即使最终偏差很大，现有丢步分支也不会返回错误。

当前执行链与触发条件

  1. MotorCtrl_MoveAndWait() 读取起点，计算相对目标并下发 TMC5130 位置运动。
  2. MotorMotion_WaitUntilStopWithTarget() 在驱动仍运动时会同步当前位置，并在当前活动位置源到达或越过目标时主动停机；缺口出现在驱动先报告停止的分支，该分支直接退出循环，只执行同步／健康检查，没有用本次新鲜的最终位置再次证明到位。
  3. 停稳后用实际位移与命令位移计算偏差；仅当偏差大于 70%、命令大于 5 mm 且使用编码器位置源时设置 ENCODER_LOST_STEP。
  4. 下一步无条件执行 ret = MotorDriver_SyncPositionOrCheckHealth(&stepper)。同步成功返回 NO_ERROR，覆盖刚刚确认的丢步错误；即使位置同步自身失败，只要随后健康检查成功，该 helper 也会返回 NO_ERROR。
  5. 局部丢步只修改该 API 的返回值，不直接发布全局故障；即使修正返回覆盖，生产调用链仍必须显式进入统一故障出口，才能让共享错误码和 CPU3 显示一致。
  6. MotorCtrl_MoveToPosition() 每轮只在运动前判断到位，第 10 次运动后不再采样，循环耗尽直接以 NO_ERROR 退出。

根因

  • 同一个 ret 同时承载主运动结果、最终同步结果和速度恢复结果，没有“主错误／附加诊断”的明确所有权。
  • 运动接口没有统一规定 NO_ERROR 必须同时满足“已停稳＋最终位置有效＋到位合格”。
  • 重试次数只限制循环，没有为“重试耗尽”定义失败出口。
  • MotorMotion_RefreshActivePositionMm() 当前除空指针外固定返回成功；电机位置源丢弃位置同步布尔结果，编码器位置源也没有“本次样本新鲜”的证明，因此整改不能继续用缓存值证明到位。

分阶段整改方案

  1. 先关闭错误覆盖：拆分 motion_ret、sync_ret、restore_ret。已经确认的运动错误保持为主错误，后续同步或恢复失败只追加日志；后续成功绝不能把主错误改回 NO_ERROR。
  2. 建立停稳后验收：无论是活动位置源主动停机还是驱动先报告停止，都取得能够证明本次刷新成功且样本新鲜的最终活动位置，确认驱动停稳后再按明确容差判断到位。读取失败返回位置源或驱动具体错误，不能使用缓存继续判成功。
  3. 修复循环耗尽：第 10 次运动后再做一次最终采样；确实到位才返回成功，仍超差则返回现有 POSITION_ARRIVAL_DEVIATION 并记录目标、实际、偏差、容差和尝试次数。
  4. 统一完成态门禁：业务调用方只有在返回 NO_ERROR 且到位验收通过时才能发布完成、保存依赖到位的结果或继续测量。

C-05 取消测量先清故障，慢停失败后仍发布待机

P0 · 仍存在

原因与证据：取消路径先清命令和错误码，再调用慢停；慢停失败只打印，最终仍无条件设置待机。位置：LTD_MAIN_CPU2/Application/Src/measure.c:312-332。

影响：停止下发、运动状态读取或停机超时失败时，外部仍可能看到“待机、无错误”，无法证明机构已安全停稳。

整改方案：把“确认停稳”和“取消收尾”分开；进入取消时快照既有锁存故障。只有取消前无锁存故障且停稳、收尾均成功，才进入待机；否则保留具体错误并进入经风险评审、已验证的停机故障策略，禁止新运动。

来源：取消流程图、全工程问题梳理 P1-04。

完整分析：取消意图、停稳证据与待机发布门禁

当前结论仍存在，复核后上调 P0：停止下发／VZERO 失败时会在未证明停稳的情况下发布待机；即便已停稳，速度配置恢复失败或取消前已有锁存故障也会被错误清零。

状态语义STATE_SWITCH 只说明取消来源，不是物理停稳证明；用户取消也不是故障复位。成功取消需停止命令、VZERO／最终运动状态和收尾共同成功，且取消前不存在必须锁存的故障。

当前执行链

  1. 运动或测量期间收到取消，当前同步业务函数通过命令切换退出。
  2. 主循环进入 CMD_CancelMeasurement()，先取消恢复／Profile，并清 pending、current command 和全局错误。
  3. 随后调用 MotorCtrl_SlowStop()；停止下发、等待 VZERO 或恢复速度任一步骤都可能失败。
  4. 失败结果当前只打印，不恢复原错误，也不进入统一故障出口。
  5. 函数最终无条件写入 STATE_STANDBY，CPU3 因而可能看到待机且错误码为 0。

根因与整改

取消被错误地等同为“非故障”，进而先清除所有故障；命令取消、物理停稳和驱动收尾没有独立结果，void 接口也不能返回取消终态。最小改法在进入取消时快照既有 error，再按“记录取消意图→发停止→确认 VZERO／停稳→恢复配置→裁决终态”排序：停止命令／VZERO 失败优先成为停机故障；VZERO 已确认后若安静速度恢复失败，物理停稳虽已证明，仍以驱动配置错误进入 STATE_ERROR。完整方案增加非阻塞 CANCELLING／STOPPING 过渡态和取消结果结构；直接硬停、失能或断电可能造成悬挂机构下坠，未完成风险评审前不得写成默认动作，应保持驱动故障态并禁止新运动。

固定终态裁决：active_error = (stop_ret != NO_ERROR) ? normalized_stop_fault : prior_latched_error。停机失败时对外激活归一后的停机故障，并把取消前故障保留为因果；停机成功仍保留必须锁存的 prior error；两者均无错且收尾成功时才进入待机。即使未来 stop_ret==STATE_SWITCH，也必须视为“停机未证明”并归一成具体停机故障。

避免重复停机的故障发布：停机失败后不能直接调用 SET_ERROR(stop_ret)，因为它会进入 FaultManager_SetErrorState()→HandleError()→MotorCtrl_SlowStop()，在同一取消路径再次执行慢停，存在潜在重入。需要增加 FinalizeAfterStopAttempt 一类“停机已尝试”专用终结器：只锁存具体错误、发布 STATE_ERROR、记录因果链并置锁存式 motion-inhibit／stop-unconfirmed，不再次调用停机动作。由于 MeasureStart()／fault_info_init() 仍会清 error，运动禁止必须同时放在命令准入和电机公共 API 两层，不能只依赖 STATE_ERROR。

完整分析：五类中断重处理、无界等待与事件化改造

当前结论仍存在，P1。HostCommu 异常日志、AO 诊断和部分保存已延后，但 UART5／HART／SSI／扭力／TIM4 的核心非恒定业务仍在 ISR，只能判“部分改善、主问题未关闭”。

最高风险触发HART TX 完成后 TC 位迟迟不置位会在回调中无上限等待；大 FC03／FC04／FC10、连续 SSI 坏帧和多串口同时满载会放大 ISR 占用。

  • UART5：停 DMA／取长度后直接进入 CRC、地址、FC03／04 投影、FC10 候选解析及可能的 TMC SPI 硬件应用，再启动 TX DMA。
  • HART：USART2 IDLE ISR 直接解析、打印和组包；TX 回调 while(TC未置位) 无超时，随后执行 180000 次 NOP 才切回接收。
  • SSI：DMA 完成回调直接解析，错误路径同步记录重试／打印并立即重启 DMA；TIM1 回调也可直接启动 DMA。
  • 扭力／TIM4：UART4 ISR 取值、滤波并更新恢复日志；TIM4 ISR 执行继电器状态计算、GPIO、AO 请求和无条件喂狗。

根因：DMA／IDLE 完成被当作业务任务入口，缺少帧所有权队列、双缓冲与前台事件层；方向切换用忙等补时序，日志 API 也没有 ISR 安全边界。

第一阶段：UART5／USART2／UART4 ISR 仅冻结 length、tick、buffer index 并投递事件，采用 ping-pong buffer 立即重启接收；SSI ISR 只复制固定 4 字节和状态。所有解析、日志、硬件应用和重试移到前台。

第二阶段：删除 TX 回调中的无界 while／NOP，改用 UART TC 中断、硬件 DE 或一次性定时器完成方向切换，并为异常设置有限截止。

完整方案：统一 SPSC 事件队列、溢出计数和背压；协议任务按优先级／截止期运行；静态门禁禁止 ISR 可达 printf／ErrorLog／HAL_Delay／FRAM／同步 SPI，继电器计算移前台，只在中断提交必要的原子 GPIO。

保持线上帧与响应期限不变时无需升共享协议；若新增 busy／重试响应则更新协议。队列溢出、DMA 重启和 TC 超时应进入通信诊断计数或现有具体错误，ISR 不直接覆盖全局最终故障。

  4. 启动读若瞬时失败，目标结构保持全 0，被解释成 magic／version 无效；随后初始化默认值并尝试覆盖 FRAM。

P0-01 电机位移偏差检测到失步后被后续健康检查覆盖

P0

证据位置：LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_motion_api.c:545-577，调用点 LTD_MAIN_CPU2/Application/Src/measure.c:835-882。

问题原因

MotorCtrl_MoveAndWait() 在检测到实际位移与目标位移偏差超过 70% 时，将 ret 设置为 ENCODER_LOST_STEP。随后函数又立即执行 MotorDriver_SyncPositionOrCheckHealth(&stepper)，并把返回值重新赋给同一个 ret。如果驱动健康检查返回 NO_ERROR，前面已经识别出的失步错误会被覆盖。

调用层通常只根据最终返回值决定是否 SET_ERROR(ret)。因此“检测到失步”和“函数最终返回成功”之间出现冲突。

影响

大幅位移异常可能不上报、不进入故障、不触发恢复，CPU3 和外部主机看到的是正常状态。该问题属于电机安全边界漏报，现场风险高。

整改方案

  • 将位移偏差结果保存为独立变量，例如 motion_ret，驱动健康检查保存为 health_ret，不得覆盖首个具体运动错误。
  • 返回优先级建议为：运动安全错误优先，其次驱动健康错误，最后速度恢复错误。
  • 当 motion_ret == ENCODER_LOST_STEP 时，强制进入故障路径并记录错误日志；如果还需要同步驱动状态，把健康检查结果作为附加诊断信息。
  • 同步检查 MotorCtrl_MoveUp/Down、手动移动、油位/水位/密度路径是否都正确传播该返回值。

验证建议

  • 构造电机实际移动距离明显小于目标距离的仿真或 HIL 场景，确认返回 ENCODER_LOST_STEP。
  • 确认 CPU2 输入寄存器、CPU3 故障页、外部 DSM/SI 状态均能看到该错误码。
  • 补单元测试或静态测试，锁定“健康检查成功不能覆盖失步错误”。

P0-02 CPU2 FC04 输入寄存器大范围读可能写爆响应缓冲区

P0

证据位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c:137、hostcommu_modbus.c:244-260、LTD_MAIN_CPU2/Services/Modbus/hostcommu.h:8、stateformodbus.h:374。

问题原因

JudgeStartAddress() 只校验起始地址和寄存器数量是否落在 INPUTREGISTER_AMOUNT 范围内，没有限制 Modbus 单帧读寄存器数量。Compose04Package() 根据 RCV_registercnt 直接写 sendframe[3...]，响应长度为 3 + RCV_registercnt * 2。

CPU2 的 HCOM_SendBuff 只有 1000 字节，而输入寄存器总量约 2570 个。一次大范围 FC04 请求可以通过地址校验，但响应组包会超过缓冲区，并且 sendframe[2] 的 byte count 只有 1 字节，超过 255 后还会截断。

影响

外部主站或 CPU3 内部主站发出大范围读取时，CPU2 可能发生内存破坏、响应 CRC 错乱、协议失步或运行异常。该问题不应依赖主站“正常不会这么读”来规避。

整改方案

  • FC04 寄存器数量必须限制为 1..125，超限返回异常码 0x03。
  • 增加响应缓冲长度保护：5 + 2 * RCV_registercnt <= HOSTCOMMU_SENDLENGTH，包含地址、功能码、byte count、数据和 CRC。
  • 把 FC03/FC04 的数量限制统一封装，避免保持寄存器和输入寄存器口径不同。
  • 对 RCV_registercnt == 0 也要返回非法数据值，不能生成空成功响应。

验证建议

  • 增加 FC04 数量边界测试：0、1、125、126、500、全表数量。
  • 确认 126 及以上返回异常响应，且不写响应缓冲越界。
  • 用地址靠近输入寄存器末尾的合法/非法组合测试半开区间边界。

P0-03 CPU2 FC10 未校验 byte count 和实际帧长，短帧可污染并持久化参数

P0

证据位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu.c:209-320、LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c:277-337。

问题原因

CPU2 接收层只做了最小长度、地址、功能码、CRC 等基础检查。FC10 处理时解析 startAddr 和 regCount 后，Compose10Package() 没有检查 revframe[6] 是否等于 regCount * 2，也没有检查实际接收长度是否等于 9 + byteCount。

组包函数直接按 RCV_registercnt 循环读取 revframe[j + 7] 和 revframe[j + 8]。短帧情况下，读取内容可能落到 CRC 字节或 DMA 缓冲旧数据，随后写入 HoldingRegisterArray，再由 ReadDeviceParamsFromHoldingRegisters() 回灌到 g_deviceParams 并触发延迟保存。

影响

构造一个 CRC 对短帧有效的 FC10 请求，就可能把错误数据写入参数区并持久化。影响范围包括命令、罐高、密度参数、报警参数、电流输出参数等所有可写保持寄存器。

整改方案

  • 在进入 Response10Process() 前按功能码做精确长度校验。
  • FC10 规则：regCount >= 1，regCount <= 123，byteCount == regCount * 2，frameLen == 9 + byteCount。
  • 长度或 byte count 非法时返回异常码 0x03，不得调用 Compose10Package()、不得回灌参数、不得请求保存。
  • 把 Compose10Package() 改成只负责“已验证帧”的寄存器写入，函数入口用断言或显式参数说明前置条件。

验证建议

  • 构造 FC10 正常写 1/2/123 个寄存器的 golden frame。
  • 构造 byte count 少 1、多 1、帧长短、帧长长但 CRC 有效的异常帧，确认全部拒绝且参数快照不变。
  • 验证异常帧不会触发 request_device_params_save()。

历史 P1 高优先级问题

P1-01 CPU2 保持寄存器边界 off-by-one，末尾地址可越界读写

P1

证据位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c:25-27、hostcommu_modbus.c:131、stateformodbus.h:200。

问题原因

HoldingRegisterArray 定义为 HoldingRegisterArray[HOLEREGISTER_STOP]，合法下标是 0..HOLEREGISTER_STOP-1。但 HoldingregisterAmount 被定义为 HOLEREGISTER_STOP + 1，地址校验因此允许访问 HOLEREGISTER_STOP 对应的越界位置。

影响

FC03 可越界读一个保持寄存器，FC10 可越界写一个保持寄存器。虽然越界宽度小，但位置靠近静态数据区，可能污染相邻状态或导致不可预测问题。

整改方案

  • 把保持寄存器数量定义统一为 HOLEREGISTER_STOP，不要加 1。
  • 边界判断改为半开区间：start >= base 且 start + count <= base + amount。
  • 使用无溢出的范围判断，避免 start + count - 1 在 count 为 0 时下溢。

验证建议

补边界测试：最后一个合法地址读写成功，HOLEREGISTER_STOP 地址读写返回非法地址。

P1-02 CPU2 FC03 保持寄存器读未限制 125 个寄存器，byte count 会截断

P1

证据位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c:218-232。

问题原因

Compose03Package() 与 FC04 一样使用 sendframe[2] = RCV_registercnt * 2，但没有限制 RCV_registercnt <= 125。保持寄存器总长度虽然通常不会超过 1000 字节缓冲，但超过 125 后已违反标准 Modbus RTU 响应长度，超过 127 后 byte count 可能接近或超过单字节边界。

影响

外部主站或 CPU3 大块读保持寄存器时，可能收到非标准响应，造成解析错位、CRC 不一致或后续通信失步。

整改方案

  • FC03 和 FC04 共用数量校验函数，统一限制 1..125。
  • 数量非法返回异常码 0x03，地址越界返回 0x02。
  • 在文档中说明大范围读取需要拆分多帧。

验证建议

用 125 和 126 个保持寄存器分别测试，确认 125 成功、126 异常。

P1-03 多个测量命令重复调用 MeasureStart 且不检查返回值

P1

证据位置：LTD_MAIN_CPU2/Application/Src/measure.c:104、measure.c:446-467、measure.c:511、measure.c:571、measure.c:613、measure_density.c:1474、measure_waterLevel.c:1355。

问题原因

调度入口 ProcessMeasureCmd() 已经调用并检查 MeasureStart()。但多个 CMD_* 函数内部再次调用 MeasureStart();，且不保存返回值。MeasureStart() 中 MotorCtrl_Init() 失败时会返回错误，但内部调用方没有处理该错误。

影响

第二次初始化失败时，流程仍可能继续进入找水、找底、密度、重量等动作，造成基于无效电机状态的后续操作。该问题还会让错误日志和 CPU3 状态无法反映真正失败原因。

整改方案

  • 优先采用单入口初始化：只在调度层执行 MeasureStart()，删除子命令内重复调用。
  • 如果某些测试命令确实需要独立初始化，应改为 ret = MeasureStart(); SET_ERROR(ret); 并在失败时立即返回。
  • 梳理所有 MeasureStart(); 未检查调用点，明确正式命令、调试命令和测试命令的不同策略。

验证建议

模拟 MotorCtrl_Init() 返回错误，确认所有正式命令都会停在错误态，不继续执行测量动作。

P1-04 取消测量时电机停机失败只打印，仍强制进入待机

P1

证据位置：LTD_MAIN_CPU2/Application/Src/measure.c:294-314、LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_motion_api.c:840-847。

问题原因

CMD_CancelMeasurement() 在用户取消时先清命令和错误码，然后调用 MotorCtrl_SlowStop()。如果停机返回真实错误，代码只打印日志，随后仍设置 device_state = STATE_STANDBY。

影响

用户取消本身不是故障，但取消过程中的停机失败是安全问题。当前逻辑会把“停止失败”对 CPU3 和外部主站隐藏起来，现场可能以为设备已经安全待机。

整改方案

  • 先执行停机，确认停机成功后再清取消相关状态。
  • 如果 MotorCtrl_SlowStop() 返回真实错误，调用 FaultManager_SetErrorState() 或等效路径进入 STATE_ERROR。
  • 取消成功和取消失败分别记录不同日志，便于现场判断。

验证建议

注入 TMC 停机失败或通信失败，执行取消命令，确认 CPU2/CPU3/外部协议均显示具体错误而不是待机。

P1-05 STATE_SWITCH 被 SET_ERROR 吞掉后，包装函数继续写完成态

P1

问题原因

P1-11 Wartsila FC16 现场特殊 byteCount 兼容被误判

已闭环

证据位置：docs/01_协议与寄存器/Wartsila协议适配/2026-01-27_莆田现场Wartsila抓包协议整理.md、LTD_DISPLAY_CPU3/Communication/external/external_read_freshness.h。

问题原因

原审查只按标准 Modbus 判断，未纳入莆田现场抓包证据。现场 Wartsila 主机的 byteCount 等于 qty，但数据区仍包含 2 * qty 字节；直接改成只接受 qty * 2 会破坏现场主机兼容。

影响

当前产品决定以莆田现场真实主机为唯一 Wartsila FC16 口径。标准调试工具若发送 byteCount == qty * 2 将收到异常码 0x03，这是受控拒绝；调试和联调必须复放现场格式。FC03 读响应不使用该特例，仍按 byteCount == qty * 2 返回实际数据字节数。

整改方案

  • 莆田现场唯一口径：所有 Wartsila FC16 命令和参数写入仅接受 byteCount == qty；标准 byteCount == qty * 2U 必须返回 0x03，且不得写寄存器池或下发 CPU2。
  • 实际数据区必须严格为 2 * qty 字节，因此 PDU 长度统一检查 6U + 2U * qty，不得按现场 byteCount 直接推导长度。
  • 保持 1 <= qty <= 123，避免请求超出 RTU 单帧合理上限。

验证建议

已补生产共享契约测试，覆盖现场格式成功，标准格式拒绝，以及单寄存器、四寄存器、最大数量、截短、超长和其它 byte count；现场命令帧 01 10 00 06 00 01 01 00 05 96 35 必须保持成功。FC03 需另行保持 byteCount == qty * 2。

  • 协议解析、日志打印、全局错误清除、恢复判断放到主循环或 deferred worker。
  • RS485 方向切换使用硬件 TC、定时器或主循环状态机，避免 ISR 忙等。

验证建议

用高频串口收发压力测试观察丢帧、IDLE 延迟和错误状态竞争，迁移后对比中断耗时。

P2-07 Wartsila 外部写操作同步等待 CPU2，可能拖长主站响应时间

P2

证据位置：LTD_DISPLAY_CPU3/Application/app_main.c:408、LTD_DISPLAY_CPU3/Communication/internal/main_board_modbus/cpu2_communicate.c:342、LTD_DISPLAY_CPU3/Communication/external/DSM_modbus/DSM_SlaveModbus_modbus2.c:903、LTD_DISPLAY_CPU3/Communication/external/si_modbus/si_modbus_slave.c:351。

问题原因

外部 COM 请求处理函数在返回前直接调用 CPU2_CombinatePackage_Send() 下发命令或参数，而该函数会等待 CPU2 响应，最坏约 1000ms。批量参数同步会进一步放大等待时间。

影响

PLC 或上位机可能因 CPU3 响应超时而重试；多串口处理也会被阻塞，造成外部通信抖动。

整改方案

  • 外部协议层先完成合法性校验并快速响应。
  • CPU2 下发改为主循环异步队列，队列记录最后一次下发结果。
  • 通过状态寄存器暴露 CPU2 下发中、成功、失败和失败原因。

验证建议

模拟 CPU2 不响应，连续写 DSM/SI/Wartsila 参数，确认外部响应时间仍满足主站超时配置。

P2-08 Wartsila 可写范围过宽，非目标地址也会触发 CPU2 参数转发

P2-09 CPU3 FRAM 显示类参数缺少合法化，非法语言值可能导致数组越界

P2

证据位置：LTD_DISPLAY_CPU3/Application/system_param/cpu3_comm_display_params.c:858-925、cpu3_comm_display_params.c:566-568、LTD_DISPLAY_CPU3/Application/display/display_tankopera.c:3810-3812。

问题原因

CPU3 从 FRAM 正常加载参数时，只对 UART 参数做 sanitize，显示类参数如语言、小数位、亮度、息屏未统一 clamp。screen_parameter.language 被直接用于二维文案数组下标。

影响

整改方案

  • 新增 Cpu3_SanitizeDisplayParams()，在 FRAM 加载、迁移和写入前统一合法化。
  • 语言限制为 0/1，息屏限制为 0/1，小数位限制为 0..4，亮度限制为 0..4。
  • 所有文案数组索引使用安全语言值，而不是裸用 screen_parameter.language。

验证建议

构造 CRC 有效但显示参数越界的 FRAM 数据，确认启动后被合法化且菜单不越界。

P2-11 传感器“读取部分参数”存在 TODO 适配器复用旧 debug_data

P2-12 维护模式前台忙等，阻塞主循环后台任务

P3-03 DSM 接受地址 0 并回包，疑似不符合 Modbus 广播习惯

P3

问题原因

DSM 地址检查允许 rcvbuff[0] == 0，响应函数仍使用本机从站地址组帧回包。标准 Modbus 中地址 0 通常作为广播地址，广播写不响应，广播读也不应正常响应。

影响

整改方案

  • 先确认 DSM 现场协议是否有“地址 0 当普通地址”的历史兼容要求。
  • 若按标准 Modbus，地址 0 写操作可执行但不响应，读操作不响应或直接丢弃。
  • 把广播行为写入协议文档和兼容说明。

验证建议

发送地址 0 的读/写帧，确认响应策略符合最终协议口径。
