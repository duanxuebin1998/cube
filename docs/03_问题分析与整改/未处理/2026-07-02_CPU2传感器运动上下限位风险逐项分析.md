## 结论摘要

当前程序已经有一部分限位和防护，主要集中在“有明确目标位置”的运动路径上。例如 `MotorCtrl_MoveAndWait()`、`MotorCtrl_JogMoveToPosition()` 会限制目标位置在 `0 ~ tankHeight` 内，油位测量有顶部 100 mm 和底部盲区保护，罐底测量有 `tankHeight + maxDownDistance` 的最大下行保护，电机运行过程中也会检查重量碰撞、丢步、驱动器故障和命令切换。

这些保护对常规目标移动、罐底探测和部分油位流程基本够用，但还不能覆盖所有危险场景。主要缺口集中在三类路径：

- 速度模式或无等待运动只依赖调用方循环检查，电机层没有统一的上下硬限位。
- 水位、找空气、找零等搜索循环存在上限、下限或超时缺口。
- 强制上行、强制下行命令绕过编码器就绪、目标范围、重量防撞和丢步检查，属于最高风险入口。

因此，当前限位不能视为足够。建议把“位置硬边界”前移到电机运动公共层，并在业务搜索流程中补齐各自的软边界、超时和碰撞检查。

## 单位和方向约定

| 项目 | 当前约定 |
| --- | --- |
| `sensor_position`、`cable_length`、`tankHeight`、`blindZone`、`maxDownDistance` | 多数业务逻辑使用 0.1 mm 单位 |
| `MotorCtrl_MoveNoWait()`、`MotorCtrl_MoveAndWait()` 入参 | 使用 mm 单位 |
| 上行方向 | `MOTOR_DIRECTION_UP = 1` |
| 下行方向 | `MOTOR_DIRECTION_DOWN = 0` |
| 电机显示运行方向 | 上行为 `1`，下行为 `2`，供 `CheckWeightCollision()` 判断 |

## 逐项风险分析

### 1. 电机公共层目标限位只覆盖部分运动

当前 `MotorCtrl_MoveAndWait()` 和 `MotorCtrl_JogMoveToPosition()` 会构造绝对目标，并通过 `MotorMotion_CheckAbsoluteTargetRange()` 限制目标在 `0 ~ tankHeight` 内。这是当前最明确、最可靠的位置限位。

风险在于 `MotorCtrl_MoveNoWait()`、`MotorCtrl_MoveUp()`、`MotorCtrl_MoveDown()` 和 `MotorCtrl_StartVelocity()` 没有同等级别的运行中位置硬限位。它们通常依赖上层循环调用 `determineTheSensorPositionAndUpdateTheLevelValue()`、`CheckWeightCollision()` 或丢步检查来停止。如果上层循环漏检、传感器状态卡死、位置刷新异常或命令距离过大，就可能越过业务边界。

整改建议：

- 在电机公共层增加运行中硬限位检查，至少覆盖 `MoveNoWait()`、速度模式和无等待循环。
- 普通业务运动使用 `0 ~ tankHeight` 作为硬边界。
- 油位、水位、密度等非探底业务再叠加 `blindZone ~ tankHeight - 1000` 软边界。
- 探底业务单独允许下行到 `tankHeight + maxDownDistance`，不要把探底放宽规则泄漏给普通测量。

### 2. 油位底部限位漏掉负位置

油位结果上报前会通过 `OilLevel_ClampLevelForReport()` 把负值钳到 0，但 `determineTheSensorPositionAndUpdateTheLevelValue()` 的下限判断条件是 `sensor_position >= 0 && sensor_position < blindZone`。如果位置变成负数，当前逻辑不会进入 `MEASUREMENT_OILLEVEL_LOW` 分支。

这会带来两个问题：一是负位置被静默修正成 0，掩盖了编码器或位置模型异常；二是业务流程可能继续运行，直到其他保护介入。

整改建议：

- 将 `sensor_position < blindZone` 统一视为下限触发，其中 `sensor_position < 0` 应按位置异常或低限位错误处理。
- 记录负位置原始值，避免只上报钳位后的 0。
- 对负位置增加日志和错误码，便于区分真实低液位和位置模型错误。

### 3. 找空气上行缺少独立上限和超时

`SearchAir()` 在未识别为空气时持续上行，循环中检查了丢步和重量碰撞，但没有看到独立的 `tankHeight` 上限判断，也没有搜索超时。正常情况下，重量零点或丢步可能会停止电机，但这属于间接保护。

危险场景包括：频率状态一直不变、重量检测异常、零点状态不可靠或位置反馈仍可刷新但业务状态卡死。此时电机可能持续上行到机械顶部附近，增加拉拽、卡滞和丢步风险。

整改建议：

- 在 `SearchAir()` 中增加 `sensor_position >= tankHeight - 1000` 的上行停止条件。
- 增加搜索超时，例如沿用油位搜索的 600000 ms 上限，或按最大上行距离和速度计算更精确的超时。
- 超时或触顶时必须 `MotorCtrl_StopAndWait()`，并返回明确错误。

### 4. 油位密度和频率闭环依赖业务层限位

密度闭环和频率闭环会通过 `MotorCtrl_StartVelocity()` 启动速度模式，再在循环里根据密度、频率、重量、丢步和位置判断停止。该设计可以实现跟随，但速度模式本身没有目标点，所以公共层目标范围校验不会生效。

当前闭环中会调用油位位置判断，因此常规情况下能触发顶部和盲区保护。问题是这种保护依赖业务循环正常运行。如果循环因为状态判断、通信等待或异常分支延迟，电机层无法独立兜底。

整改建议：

- 在速度模式运行期间，电机公共层定期读取当前位置并执行硬限位。
- 业务闭环继续保留自己的液位逻辑，但不要作为唯一限位。
- 对连续速度模式统一加最大运行时间或最大单次位移。

### 5. 水位粗找和精找缺少下行边界、碰撞和超时

`SearchWaterRough()` 和 `SearchWaterPrecise()` 主要依赖水位状态翻转、丢步检查和零点附近上行保护。下行找水过程中没有看到与罐底类似的 `Bottom_CheckMaxCableLength()`，也没有统一调用 `CheckWeightCollision()`，精找中还存在下行越过预期位置的保护代码被注释的情况。

这意味着如果水位传感状态迟迟不翻转，水位流程可能继续下行，直到丢步或更底层故障出现。对“找不到水”这种现场场景，当前保护不够完整。

整改建议：

- 水位下行应增加最大下行位置，至少不能超过 `tankHeight`；如果业务允许接近罐底，应明确是否允许使用 `tankHeight + maxDownDistance`。
- 下行循环增加 `CheckWeightCollision()`，把重量防撞纳入水位流程。
- 粗找、精找和快速状态翻转流程都增加超时。
- 恢复或重写精找中的越界保护，避免注释掉的保护成为长期缺口。

### 6. 找零上行依赖重量零点，缺少独立上限和超时

`SearchZeroRough()` 持续上行直到 `check_zero_point_status()` 识别零点。它会检查丢步并在接近零点时降速，但缺少独立的上行极限和超时。`SearchZeroPrecise()` 有最大零点偏差检查，但在找零校准状态和电机位置源模式下，该偏差检查可能被关闭。

如果重量零点判断异常或标定状态下防护被放宽，电机会更依赖机械和驱动故障保护。

整改建议：

- 找零粗找增加最大上行距离或最大时间。
- 在校准状态下也保留一个不可关闭的硬上限。
- `max_zero_deviation_distance` 的默认值和注释需要复核，当前默认值为 1000 个 0.1 mm，等于 100 mm，但注释描述存在不一致风险。

### 7. 罐底测量下行保护相对完整，但参数需要约束

罐底测量已有 `tankHeight + maxDownDistance` 保护，粗找和精找都会检查最大线长，并且有接近罐底降速、重量罐底状态和丢步检查。相比水位和找空气流程，罐底保护更完整。

剩余风险主要在参数层。如果 `tankHeight`、`maxDownDistance`、重量阈值或罐底检测模式配置错误，保护边界会被错误放宽。

整改建议：

- 参数保存或加载时校验 `tankHeight > blindZone`。
- 校验 `maxDownDistance` 的最大允许值，避免现场误设过大。
- 对罐底检测模式、罐底重量阈值和忽略区参数增加范围说明和异常日志。

### 8. 手动普通上行和下行有目标限位，但没有业务盲区限位

`CMD_MoveUp()` 和 `CMD_MoveDown()` 使用 `MotorCtrl_MoveAndWait()`，因此目标不能超出 `0 ~ tankHeight`。这对机械行程边界是有效的。

但普通手动命令没有强制使用 `blindZone` 作为下限，也不区分“普通测量允许区域”和“维护调试允许区域”。如果现场把 `motorCommandDistance` 设置得较大，手动下行可以运行到低于盲区的位置，只要仍在 `0 ~ tankHeight` 内。

整改建议：

- 普通用户界面的手动命令建议限制在 `blindZone ~ tankHeight - 1000`。
- 维护模式下才允许进入更宽的 `0 ~ tankHeight`。
- `motorCommandDistance` 增加最大单次距离限制和非零校验。

### 9. 强制上行和强制下行是最高风险入口

`CMD_ForceMoveUp()` 和 `CMD_ForceMoveDown()` 使用 `MotorCtrl_MoveBlockingNoDetectForceDebug()`。该路径会绕过编码器就绪、目标范围、重量碰撞和丢步检测，适合极少数维护调试场景，但不适合作为常规现场入口。

如果强制下行距离过大、方向错误或当前位置已经接近边界，程序缺少足够的二次确认和硬停止条件，可能导致探头撞底、拉拽、丢步或位置模型失真。

整改建议：

- 强制命令必须只在维护模式或明确授权状态下开放。
- 增加最大单次强制距离，建议远小于普通测量行程。
- 即使是强制命令，也要保留不可绕过的绝对硬限位。
- 强制命令执行前记录当前位置、方向、距离和调用来源；执行后重新同步位置并要求人工确认。

### 10. 密度单点目标校验较好，其他目标命令应对齐

密度单点测量通过 `SinglePoint_CheckTargetPosition()` 要求目标位于 `blindZone ~ tankHeight`，这个边界比电机公共层的 `0 ~ tankHeight` 更符合业务安全要求。

但其他目标类命令，例如直接跑到某个位置的命令，如果只依赖 `JogMoveToPosition()`，则只能保证不超过机械行程，不能保证不进入业务盲区。

整改建议：

- 抽出业务目标位置校验函数，统一用于单点密度、跑到位置、手动目标移动等命令。
- 明确区分机械硬边界、业务软边界和维护调试边界。

### 11. 重量防撞是必要保护，但不应作为唯一限位

`CheckWeightCollision()` 对上行和下行分别处理重量变化、零点和罐底阈值，是当前运动安全的重要组成部分。但重量检测依赖传感器通信、阈值配置、忽略区、当前运动方向和重量稳定性。

一旦重量数据超时、阈值配置错误或方向状态没有正确更新，防撞保护效果会下降。因此它应作为位置限位之外的第二道保护，而不是替代位置限位。

整改建议：

- 所有持续运动循环都应同时具备位置边界、重量防撞、丢步和驱动健康检查。
- 对重量通信超时的处理要偏保守：运动中重量不可用时应停止，而不是继续依赖其他条件。

## 推荐整改顺序

第一步先补不可绕过的底层硬保护：在电机公共层增加当前位置边界检查，保证即使上层流程漏检，也能在接近机械边界时停止。该步骤应优先覆盖速度模式、无等待运动和强制运动。

第二步修复高风险业务流程：水位下行、找空气上行、找零上行、油位负位置处理。这些流程都是搜索型循环，一旦传感器状态不变，越界风险高于固定目标移动。

第三步收紧外部命令入口：普通手动命令使用业务软边界，强制命令只留维护模式，并限制距离、记录日志和强制复位位置状态。

第四步补参数校验和测试用例：把 `tankHeight > blindZone`、`maxDownDistance` 上限、`motorCommandDistance` 上限等参数约束前置到配置保存或加载阶段。

## 详细整改方案

### 方案目标

整改目标不是把每个流程各自补一段判断，而是形成三层保护：

| 层级 | 保护范围 | 设计目标 |
| --- | --- | --- |
| 机械硬边界 | 所有电机运动，包括速度模式、无等待运动、目标运动和强制运动 | 无论上层业务是否漏检，电机都不能持续越过绝对安全边界 |
| 业务软边界 | 油位、水位、密度、手动普通命令等普通测量场景 | 默认避开盲区和罐顶预留距离，不把传感器带到非业务测量区 |
| 场景例外边界 | 罐底探测、找零、维护调试等特殊场景 | 只在明确场景下放宽边界，并保留超时、距离上限和日志 |

最终效果应满足：普通测量不进入盲区，探底只在探底流程内允许超过罐高，强制命令也不能绕过绝对硬限位。

### 一、先建立统一运动限位模型

建议在 `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_motion_api.c` 中抽出统一限位模型，避免业务代码各写一套范围判断。

建议定义三类边界：

| 边界类型 | 下限 | 上限 | 适用场景 |
| --- | --- | --- | --- |
| 绝对机械边界 | `0` | `tankHeight` | 普通目标运动、手动普通运动、速度模式兜底 |
| 普通测量业务边界 | `blindZone` | `tankHeight - 1000` | 油位、水位、密度、跑到位置等普通业务 |
| 探底扩展边界 | `0` | `tankHeight + maxDownDistance` | 仅罐底粗找、罐底精找 |

落地方式：

1. 新增内部函数用于读取当前 `tankHeight`、`blindZone`、`maxDownDistance`，并完成参数合理性修正。
2. 新增内部函数检查当前位置是否越界，输入包含方向、当前位置、边界类型和调用场景。
3. 对上行越过上限、下行越过下限、位置无效或参数无效分别返回明确错误。
4. 所有错误出口统一先执行快速停止或停止等待，再返回上层错误码。

注意事项：

- `MoveAndWait()` 已经有目标范围校验，不要删除现有逻辑；新增的是运行中兜底。
- `MoveNoWait()` 无法预知上层是否继续调用，因此启动前要基于当前位置和方向做一次检查。
- `StartVelocity()` 是连续速度模式，启动前检查不够，还要在等待循环或周期检查入口中持续检查。
- 强制运动也只能绕过编码器就绪或业务软边界，不能绕过绝对机械边界。

### 二、补电机公共层保护

建议优先修改下列路径：

| 路径 | 当前问题 | 建议修改 |
| --- | --- | --- |
| `MotorCtrl_MoveNoWait()` | 只有运动准备和驱动健康检查，没有绝对目标边界 | 启动前读取当前位置；上行时如果已接近上限则拒绝，下行时如果已接近下限则拒绝；根据距离估算目标时也做边界判断 |
| `MotorCtrl_MoveUp()`、`MotorCtrl_MoveDown()` | 封装了固定距离无等待运动，依赖调用方停止 | 调用 `MoveNoWait()` 前或内部统一继承硬限位 |
| `MotorCtrl_StartVelocity()` | 速度模式没有目标点 | 启动前检查方向边界；运行循环中增加周期硬限位检查 |
| `MotorCtrl_MoveBlockingNoDetectForceDebug()` | 强制调试路径绕过检测 | 保留维护用途，但增加绝对硬限位、最大单次距离和日志 |
| `MotorMotion_WaitUntilStopWithTarget()`、Jog 内部等待 | 已有目标停止和碰撞检查 | 保留现有逻辑，补充统一边界错误码和日志，便于错误归因 |

建议错误处理口径：

- 启动前发现越界：不发运动命令，直接返回参数或位置范围错误。
- 运行中触发硬限位：立即 `MotorCtrl_QuickStop()` 或等效快速停止，再返回限位错误。
- 位置读取失败：保守停止，不继续运动。
- 参数异常：例如 `tankHeight <= blindZone`，普通测量拒绝启动；探底流程拒绝使用扩展边界。

### 三、补业务流程软限位

公共层解决“不能机械越界”，业务层还要解决“不能进入不该测量的区域”。

#### 1. 油位流程

涉及文件：`LTD_MAIN_CPU2/Application/Src/measure_oilLevel.c`

修改点：

1. 将 `sensor_position >= 0 && sensor_position < blindZone` 改为 `sensor_position < blindZone`。
2. 对 `sensor_position < 0` 单独打印日志，记录原始位置值。
3. `SearchAir()` 增加顶部软限位：`sensor_position >= tankHeight - 1000` 时停止。
4. `SearchAir()` 增加搜索超时，超时后停止并返回找空气失败或油位高限位类错误。
5. 密度闭环和频率闭环保留现有 `determineTheSensorPositionAndUpdateTheLevelValue()`，同时依赖公共层速度模式硬限位兜底。

验证重点：

- 模拟负位置时不能继续跟随。
- 找空气时频率状态一直不变，必须在顶部软限位或超时退出。
- 正常找油、跟随、精找流程不能因为新增限位提前误停。

#### 2. 水位流程

涉及文件：`LTD_MAIN_CPU2/Application/Src/measure_waterLevel.c`

修改点：

1. `SearchWaterRough()` 下行循环增加最大下行位置判断。
2. `SearchWaterPrecise()` 下行循环增加最大下行位置判断，并恢复或重写被注释的越界保护。
3. 快速状态翻转找水流程同步增加下行边界和超时。
4. 下行循环加入 `CheckWeightCollision()`，和油位、罐底流程保持一致。
5. 对找不到水的结果使用明确错误出口，避免表现成普通丢步或未知失败。

水位最大下行边界建议：

- 默认使用 `tankHeight`，不建议直接允许 `tankHeight + maxDownDistance`。
- 如果现场业务要求水位必须允许接近罐底，应把该例外写成单独参数或单独模式，不要复用罐底探测的扩展边界。

验证重点：

- 水位状态一直不翻转时，电机到达最大下行位置或超时后停止。
- 重量通信异常、罐底重量异常时，水位下行应停止。
- 已在水中启动、先上行退出水再下行找水的流程不被误拦截。

#### 3. 找零流程

涉及文件：`LTD_MAIN_CPU2/Application/Src/measure_zero.c`

修改点：

1. `SearchZeroRough()` 增加最大上行距离或最大时间。
2. `SearchZeroPrecise()` 在校准状态下也保留不可关闭硬上限。
3. 复核 `max_zero_deviation_distance` 注释和默认值，统一为真实单位和真实距离。
4. 找零失败时明确返回零点失败，不要只依赖丢步或重量异常表现。

建议口径：

- 找零允许比普通业务更靠近上方机械零点，但必须有绝对上限。
- 标定状态可以放宽业务软边界，不能放宽机械硬边界。

验证重点：

- 零点重量状态一直不触发时，流程按上限或超时退出。
- 正常找零粗找、精找仍能完成。
- 电机位置源模式下，不会因为关闭偏差检查而丢失全部上行保护。

#### 4. 手动命令和强制命令

涉及文件：`LTD_MAIN_CPU2/Application/Src/measure.c`

修改点：

1. `CMD_MoveUp()`、`CMD_MoveDown()` 继续使用 `MoveAndWait()`，但普通模式增加业务软边界。
2. `CMD_RunToPosition()` 的目标位置建议复用密度单点的 `blindZone ~ tankHeight` 校验。
3. `CMD_ForceMoveUp()`、`CMD_ForceMoveDown()` 只允许维护模式或调试授权状态执行。
4. 强制命令增加最大单次距离，建议独立参数或固定较小常量。
5. 强制命令执行前后记录当前位置、方向、距离、错误码和位置同步结果。

建议策略：

- 普通用户入口：只能在 `blindZone ~ tankHeight - 1000` 范围内移动。
- 维护入口：可进入 `0 ~ tankHeight`，但仍需绝对硬限位和最大单次距离。
- 强制入口：只用于故障恢复或台架调试，默认现场界面不暴露。

验证重点：

- 普通手动下行低于盲区时拒绝。
- 维护模式下允许更宽范围，但不能越过 `0 ~ tankHeight`。
- 强制下行距离过大时拒绝，不发电机命令。

#### 5. 罐底流程和参数约束

涉及文件：`LTD_MAIN_CPU2/Application/Src/measure_tank_height.c`、参数加载和保存相关文件。

修改点：

1. 保留 `tankHeight + maxDownDistance` 作为罐底专用扩展边界。
2. 参数保存或加载时校验 `tankHeight > blindZone`。
3. 限制 `maxDownDistance` 最大值，避免配置过大。
4. 对 `bottom_weight_threshold`、`weight_ignore_zone`、罐底检测模式增加异常日志或范围说明。
5. 明确禁止普通水位、油位、密度流程复用探底扩展边界。

验证重点：

- 正常探底不受影响。
- `maxDownDistance` 配置异常时拒绝探底或回退安全默认值。
- 普通测量流程不会因为罐底扩展边界而放宽下行范围。

### 四、错误码、日志和上报方案

如果现有错误码足够，应优先复用现有测量错误；如果不足，建议补齐下列语义：

| 场景 | 建议错误语义 | 日志要素 |
| --- | --- | --- |
| 上行触发顶部硬限位 | 运动上限位或油位高限位 | 当前位置、`tankHeight`、方向、调用场景 |
| 下行触发底部硬限位 | 运动下限位或低限位 | 当前位置、`blindZone`、`tankHeight`、方向 |
| 探底超过扩展边界 | 罐底下行失败 | `cable_length`、`tankHeight`、`maxDownDistance` |
| 位置为负 | 位置异常或低限位 | 原始位置、钳位后位置、位置来源 |
| 搜索超时 | 对应流程搜索失败 | 流程名、运行时间、最后位置、最后传感状态 |
| 强制命令被拒绝 | 强制运动条件不满足 | 维护模式状态、方向、距离、当前位置 |

日志原则：

- 运动中触发保护时，日志必须先记录原始位置和方向，再停止或返回。
- 对 CPU3 或上位机展示的错误码应保持稳定，不要为了文档方案临时改变共享协议。
- 如果新增错误码或改变跨 CPU 错误语义，需要同步检查 CPU3 显示、协议文档和版本影响。

### 五、参数校验方案

建议在参数加载、参数保存和运动启动前分三道处理：

| 校验位置 | 处理方式 | 目的 |
| --- | --- | --- |
| 参数加载 | 发现明显非法值时回退安全默认值并记录日志 | 防止历史 FRAM 数据导致开机后边界错误 |
| 参数保存 | 拒绝保存 `tankHeight <= blindZone`、`maxDownDistance` 过大、`motorCommandDistance` 过大等配置 | 防止新配置进入持久化 |
| 运动启动 | 每次启动前再次校验关键参数 | 防止运行态变量异常或未初始化 |

建议最小校验项：

- `tankHeight > blindZone`
- `blindZone >= 0`
- `maxDownDistance` 不超过允许维护上限
- `motorCommandDistance` 大于 0 且不超过最大单次运动距离
- `max_zero_deviation_distance` 单位、默认值和注释一致
- `weight_ignore_zone` 不应大于关键测量行程

### 六、实施拆分建议

建议分四个小提交或四轮实现，避免一次改动影响所有测量流程：

| 阶段 | 内容 | 风险 | 验证 |
| --- | --- | --- | --- |
| 第 1 阶段 | 电机公共层硬限位、强制命令距离限制 | 影响所有运动入口，需要重点回归 | 编译、普通手动上/下行、目标越界、强制命令拒绝 |
| 第 2 阶段 | 油位负位置、找空气上限和超时、速度模式兜底 | 影响油位和密度跟随 | 找油、找空气、跟随、传感状态卡死模拟 |
| 第 3 阶段 | 水位下行边界、碰撞、超时 | 影响水位测量 | 水位粗找、精找、找不到水、重量异常 |
| 第 4 阶段 | 找零上限、参数校验、错误码和文档同步 | 影响标定和参数兼容 | 找零、参数异常、CPU3 错误显示和文档检查 |

每个阶段完成后都要复查是否改变 CPU2/CPU3 共享错误语义。如果只是 CPU2 内部停止策略变化，通常不需要升协议版本；如果新增共享错误码、改变 CPU3 显示或上位机可见状态，就需要按协议和版本规则同步文档。

### 七、回滚和兼容策略

为了便于现场回退，建议每个阶段保持可独立回滚：

- 公共层硬限位用独立 helper 封装，业务层只调用，不散落重复判断。
- 业务软限位尽量保留原错误码，先减少协议和 CPU3 联动改动。
- 强制命令限制可以先通过编译开关或维护模式开关控制，但绝对硬限位不建议提供关闭开关。
- 参数校验先记录日志并拒绝明显危险值；对历史设备的边界值要评估是否会导致开机后无法测量。
- 如果现场已有特殊罐型依赖较大的 `maxDownDistance`，需要先收集配置范围，再确定最大值。

### 八、实施前需要确认的问题

| 问题 | 影响 |
| --- | --- |
| 普通水位测量是否允许下行到 `tankHeight` 以下 | 决定水位能否复用探底扩展边界，默认建议不允许 |
| 强制上/下行是否必须保留现场入口 | 决定是否只做维护模式限制，还是彻底从普通命令入口隐藏 |
| 新增限位错误是否需要 CPU3 独立显示 | 决定是否新增共享错误码和协议文档 |
| `maxDownDistance` 现场最大合理值是多少 | 决定参数校验上限 |
| `max_zero_deviation_distance` 当前注释和默认值哪个代表真实需求 | 决定找零保护距离 |

## 建议验证用例

| 用例 | 预期结果 |
| --- | --- |
| 目标位置小于 0 或大于 `tankHeight` | 目标运动拒绝执行，返回参数范围错误 |
| 油位位置为负数 | 停止运动，记录负位置，返回明确低限位或位置异常 |
| 找空气时频率状态一直不是空气 | 到达 `tankHeight - 1000` 或超时后停止 |
| 水位下行时水位状态一直不翻转 | 到达最大允许下行位置或超时后停止 |
| 找零时重量零点一直不触发 | 到达上行硬限或超时后停止 |
| 普通手动下行目标低于 `blindZone` | 普通模式拒绝，维护模式按更严格流程放行 |
| 强制下行距离超过维护上限 | 拒绝执行并记录日志 |
| 重量通信中断后仍处于运动状态 | 立即停止并返回重量通信或运动保护错误 |

## 当前判断

当前程序不是完全没有限位，而是限位分散在电机公共层、业务流程和重量检测中。对“固定目标移动”和“罐底测量”来说，现有保护相对明确；对“搜索型连续运动”和“强制调试运动”来说，现有保护不够。最危险的地方是强制运动和水位下行，其次是找空气上行、找零上行和油位负位置静默钳位。

后续整改不建议只在单个业务函数里继续补丁式增加判断，而应先建立统一的电机层硬边界，再由各测量业务叠加自己的软限位和超时策略。

截至 `MAIN@db0b1322`，C-42A～C-42H 均未达到关闭条件；B-05 的全速度、长距离和故障注入证据也未补齐。
