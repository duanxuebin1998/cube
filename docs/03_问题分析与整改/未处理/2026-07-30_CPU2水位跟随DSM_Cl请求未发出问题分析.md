# CPU2 水位跟随 DSM `Cl` 通信异常问题分析

更新日期：2026-07-31

当前状态：已取得一次 CPU 日志与无线前 USART6 抓包的共同时间戳复现；确认现场至少存在“请求未发出”和“请求已发出但响应晚到”两类表现。两类故障的最终错误码相同，但不能合并归因；尚未修改固件。

## 1. 结论摘要

水位跟随进入稳定监测后，CPU2 会周期读取 DSM 水位电容。现场曾连续正常读取，随后出现三次：

```text
错误码：0x000D0003
错误名：传感器通信超时
详情：传感器无响应,cmd=Cl,len=0,uart=0x00000000,hex=
```

此前“请求未发出”事件由现场确认以下两个关键事实：

1. 抓包点位于 CPU2 USART6 与无线模块之间，即无线链路之前；故障时该串口链路没有发出 `Cl` 请求。
2. 水位跟随稳定监测期间只与 DSM 传感器通信，没有 CH9141K AT 查询、LTD/V2、安全协议等其它 UART6 业务干扰。

因此，此前“请求未发出”事件不能归因于无线模块未透传、无线链路断开或其它 UART6 协议抢占。现有源码显示，软件在报 `0x000D0003` 前已经把本次 TX DMA 判为完成，但代码没有独立证据证明 `Cl` 的两个字节确实从 USART6 TX 引脚输出。

2026-07-31 新提供的共同时间戳日志又复现了一次 `0x000D0003`，但这一次的外部证据不同：

1. 三次 `Cl` 均已出现在无线前 USART6 抓包点。
2. 前两次请求之后，在各自 500 ms 接收窗口内没有 DSM 响应。
3. 第三次请求后 646 ms 才出现一帧 `D00066.8R`，比 CPU2 打印第三次超时晚约 140 ms。
4. CH9141K AT 诊断从 19:11:14.958 才开始，晚于三次 `Cl` 失败，不能作为本次超时的前置干扰原因。

这证明相同的 `0x000D0003` 至少可由两种不同链路状态产生：

- A类：CPU2软件认为TX完成，但无线前抓包点没有 `Cl`。该类仍优先检查USART6 TX DMA、完成中断、句柄和寄存器状态。
- B类：`Cl`真实发出，但响应超过500 ms才到达。2026-07-31的19:11复现属于该类，应优先检查DSM处理停顿、无线响应链路延迟或缓冲，以及超时后迟到帧的事务隔离。

此前A类事件的最高优先级方向是：

- USART6 TX DMA、DMA2 Stream6 或 USART6 TC 完成中断的内部状态与真实引脚输出不一致。
- UART/DMA句柄或寄存器受到越界写、异常中止或状态污染。
- 现场运行固件与本次分析源码、构建产物不一致。
- USART6 内部完成，但 PC6 复用或电气链路没有形成可识别串口波形。

仅凭 `len=0,uart=0` 日志不能区分A类和B类。共同时间戳已证明19:11复现属于B类，但此前A类事件仍缺少同一时钟下的完整原始记录，两个事件都尚未定位到唯一软件或硬件根因。

## 3. 当前执行链

### 3.1 水位跟随入口

水位跟随稳定监测由以下链路执行：

```text
ProcessMeasureCmd(CMD_FOLLOW_WATER)
  -> CMD_FollowWaterLevel()
  -> FollowWaterLevelCore()
  -> MonitorWaterFollowChange()
```

`MonitorWaterFollowChange()` 在循环中执行：

```c
ret = Sensor_ReadWaterCapacitance(&cap);
CHECK_ERROR(ret);
```

读取成功后打印电容、目标、偏差、阈值和当前水位，再按 `WATER_FOLLOW_SAMPLE_MS` 等待下一轮。

### 3.2 DSM `Cl` 发送链

普通 DSM 水位电容读取链为：

```text
Sensor_ReadWaterCapacitance()
  -> Read_Water_Capacitance()
  -> UART6_SendWithRetry("Cl", ...)
  -> UART6_SendCommand("Cl", ...)
```

`UART6_SendCommand()` 当前顺序是：

1. 清空响应缓冲区。
2. 清理 UART6 残留接收数据。
3. 启动 RX DMA。
4. 调用 `HAL_UART_Transmit_DMA(&huart6, "Cl", 2)`。
5. 等待 `huart6.gState == HAL_UART_STATE_READY`，最长 100 ms。
6. 等待 RX DMA 收到换行结尾响应，最长 500 ms。
7. 响应长度为 0 时返回 `SENSOR_DEVICE_COMM_TIMEOUT`。

每轮最多重试 3 次。重试间有 `DSM_PRE_SEND_DELAY`。

## 4. 错误码反推结果

当前代码对发送阶段和接收阶段使用不同错误码。

| 失败位置 | 当前返回值 | 预期现场日志 |
| --- | --- | --- |
| `HAL_UART_Transmit_DMA()` 返回非 `HAL_OK` | `COMM_UART_TRANSFER_ERROR`，`0x00140001` | 串口或DMA传输异常 |
| 100 ms 内 `gState` 未回到 READY | `COMM_UART_TRANSFER_ERROR`，`0x00140001` | 串口或DMA传输异常 |
| UART/DMA硬件错误被检测 | `COMM_UART_TRANSFER_ERROR`，`0x00140001` | 串口或DMA传输异常 |
| TX被软件判为完成，但500 ms内没有响应 | `SENSOR_DEVICE_COMM_TIMEOUT`，`0x000D0003` | 传感器无响应 |

此前A类事件和2026-07-31的B类事件都连续出现 `0x000D0003`，而不是 `0x00140001`。按当前代码反推：

1. `HAL_UART_Transmit_DMA()` 返回了 `HAL_OK`。
2. `UART6_WaitTransmitDmaDone()` 观察到了 `huart6.gState == HAL_UART_STATE_READY`。
3. 程序随后进入了接收等待。
4. 500 ms 内没有收到任何响应字节。

这只能证明 HAL 状态机把发送判为完成，不能单靠CPU日志证明 `Cl` 已经出现在PC6引脚或抓包点。对于2026-07-31的19:11复现，外部抓包已经独立证明三次 `Cl` 真实出线；对于此前A类事件，该证据仍然缺失。

## 5. 已确认的软件诊断缺口

### 5.1 发送完成只看共享 `gState`

当前发送等待条件是：

```c
if (huart6.gState == HAL_UART_STATE_READY) {
    return NO_ERROR;
}
```

没有本次事务专用的：

- TX序号。
- TX完成标志。
- TX完成中断计数。
- DMA2 Stream6 `NDTR` 快照。
- USART6 `TC` 快照。
- 独立辅助GPIO时序标记。

因此，代码把“句柄状态为READY”和“本次两个字节真实出线”当成了同一件事。该缺口仍会阻碍A类事件定位，但2026-07-31的19:11复现已有外部出线证据，不能再把这次故障归到此缺口。

### 5.2 `uart=0`不能证明TX正常

日志里的：

```text
uart=0x00000000
```

来自最近一次记录的 HAL UART 错误码。它只能表示没有记录到 FE、NE、ORE、DMA等错误，不能证明：

- TX DMA已启动。
- `NDTR`从2递减到0。
- USART6产生了真实TXE/TC过程。
- PC6保持AF8复用。
- 抓包点出现了 `43 6C`。

### 5.3 RX清理函数使用全UART DMA停止接口

DSM代码中的 `UART6_StopDmaReceive()` 调用：

```c
HAL_UART_DMAStop(&huart6);
```

STM32 HAL 的 `HAL_UART_DMAStop()`会同时检查并停止TX和RX，不是只停止RX。该结构存在误停TX的长期风险。

不过，在用户已确认“稳定跟随期间只有DSM通信”的前提下，当前DSM正常路径中的调用时点是：

- 启动本次RX DMA之前。
- 本次收包完成或超时之后。
- 检测到命令切换时。

当前静态调用链没有发现一个会在正常 `Cl` TX进行中异步调用该函数的DSM ISR或PendSV路径。因此它是必须整改的结构风险，但现阶段不能直接定为此前A类事件的实际触发者，也没有证据表明它导致2026-07-31的B类响应晚到。

## 6. 已排除或降低优先级的方向

### 6.1 无线模块或无线链路未透传

对于此前A类事件，抓包点位于无线模块之前且现场确认故障时抓包点没有 `Cl`，因此无线透传失败不是“请求未发出”的解释。

对于2026-07-31的B类事件，三次 `Cl` 均到达无线模块前的链路，但响应晚到；无线响应链路、远端DSM处理和模块缓冲均仍在排查范围。故障后的蓝牙链路诊断只能说明诊断时刻链路可用，不能反推此前500 ms窗口内响应为何没有返回。

### 6.2 其它UART6协议抢占

现场确认水位跟随稳定监测期间只有DSM通信。2026-07-31抓包也显示，三次失败请求期间没有CH9141K AT、LTD/V2或安全协议插入；AT诊断在三次超时之后才开始。

### 6.3 通用UART自动恢复直接停止USART6

2026-07下旬增加的CPU2通用UART接收恢复只管理：

- USART1
- USART2
- UART4
- UART5

它明确不接管USART6，因此不能直接调用恢复函数停止本次DSM TX。

### 6.4 Newhall接收修改

Newhall相关修改位于UART4。USART6和DMA2 Stream6中断能够抢占该路径，目前没有发现UART4代码改写USART6句柄或DMA2 Stream6寄存器。

### 6.5 单纯USART6完成中断延迟

USART6和DMA2 Stream6当前NVIC优先级为1。若完成中断长期未执行，`gState`应保持BUSY，100 ms后返回 `0x00140001`，与本次 `0x000D0003` 不一致。

因此，单纯“中断晚到”不是A类事件的首要解释；需要检查的是“状态为何提前或错误地回到READY”。对于2026-07-31的B类事件，三次请求均已真实出线，TX完成中断延迟不解释响应晚到。

## 7. 与历史修改的关系

### 7.1 2026-05-15：从阻塞收发改为USART6 DMA

提交 `2d7309a2` 对本问题高度相关。修改前，DSM发送使用：

```c
HAL_UART_Transmit(&huart6, (uint8_t *)cmd, strlen(cmd), 100)
```

修改后改为：

```c
HAL_UART_Transmit_DMA(&huart6, (uint8_t *)cmd, strlen(cmd))
```

并新增：

- USART6 TX：DMA2 Stream6，Channel 5。
- USART6 RX：DMA2 Stream1，Channel 5。
- `DMA2_Stream6_IRQHandler()`。
- `USART6_IRQHandler()`。
- `UART6_WaitTransmitDmaDone()`。

当前“HAL返回成功、软件认为发送完成，但抓包点没有请求”的诊断盲区由这套异步发送判定产生。

这说明此前A类事件与DMA/中断改造方向高度相关，但仍不等于已经证明该提交必然触发故障。2026-07-31的B类事件中请求已经出线，不支持把TX DMA改造作为该次响应晚到的直接原因。

### 7.2 2026-06-29：USART6中断优先级调整

提交 `dc80db42` 将USART6、DMA2 Stream1和DMA2 Stream6的NVIC优先级从0调整为1。

该改动可能改变完成中断时序，但按当前错误传播逻辑，单纯延迟应进入 `0x00140001`，不能独立解释A类事件；它也不能解释B类事件中抓包点已经看到三次完整 `Cl` 后响应才晚到。

### 7.3 2026-07下旬：通用UART恢复和Newhall修改

通用UART恢复明确排除USART6；Newhall位于UART4。目前不支持把它们作为A类请求未发出或B类响应晚到的直接原因。

## 8. 当前原因排序

### 8.1 B类“请求已发出、响应晚到”

#### P1：DSM处理或无线响应链路发生瞬时停顿

19:11故障前952组成功事务的响应耗时上限为239 ms；异常时三次 `Cl` 后只有一帧响应。若该帧对应第一次请求，响应耗时为2300 ms；即使按最近的第三次请求计算，也达到646 ms。能够确认的是CPU2到无线模块方向仍在发送，而返回方向出现了远超正常分布的停顿。

当前无线前单点抓包不能继续区分：

- DSM固件在任务、中断、传感器采样或内部串口处理上暂停。
- 远端无线模块、空中链路或主机无线模块延迟转发。
- DSM已回复但响应被某一级缓冲，直到重试结束后才释放。

#### P1：迟到帧与重试事务没有隔离

`Cl` 请求和 `D...` 响应都没有事务序号。CPU2每次等待500 ms，随后延时300 ms重试；迟到响应无法判断属于哪一次请求。19:11的 `D00066.8R` 到达时第三次接收DMA已经超时停止，因此该帧不会挽救本次测量，还可能在更晚到达时污染后续UART6事务。

#### P2：固定500 ms超时对极端停顿没有容错

正常响应耗时集中在154~239 ms，说明500 ms并非正常工况下的紧边界。单纯放宽超时可能降低偶发报错，但会延长真正断链时的故障发现，并掩盖秒级停顿的根因；当前不建议只凭这一帧迟到响应直接修改超时。

### 8.2 A类“请求未发出”

#### P1：TX DMA或TC完成状态异常

需要确认故障时：

- `HAL_UART_Transmit_DMA()`是否真的把DMA2 Stream6置为EN。
- `NDTR`是否从2递减。
- DMA2 Stream6是否产生TC、TE、DME或FE。
- DMA完成后USART6是否产生真实TC。
- `gState`由哪个出口改回READY。

#### P1：UART/DMA句柄或寄存器被异常改写

重点对象：

- `huart6.gState`
- `huart6.ErrorCode`
- `hdma_usart6_tx.State`
- `hdma_usart6_tx.ErrorCode`
- `USART6->CR1`
- `USART6->CR3`
- `DMA2_Stream6->CR`
- `DMA2_Stream6->NDTR`
- `DMA2_Stream6->PAR`
- `DMA2_Stream6->M0AR`

如果存在越界写，可能出现HAL句柄已READY，但DMA或GPIO实际没有执行预期动作。

#### P1：现场固件与源码不一致

需要记录现场CPU2固件版本和HEX哈希，并与用于分析的构建产物比对。仅凭日志文本相同不能证明运行的是当前源码。

#### P2：USART6内部完成但PC6未形成波形

当前源码只在USART6初始化时把PC6/PC7配置为AF8，没有找到稳定监测期间重新配置PC6的业务路径。

若故障时：

```text
NDTR=0
USART6 TC=1
TX完成计数增加
```

但抓包点仍没有 `43 6C`，则需继续检查：

- PC6 `MODER`、`AFR[0]`、`OTYPER`、`OSPEEDR`、`PUPDR`。
- USART6 `UE`、`TE`。
- PC6到抓包点的连通性、电平和外部负载。

为继续定位B类事件，建议在条件允许时同步增加DSM端串口抓包或DSM内部时间戳日志，与现有CPU2到无线主机模块之间的抓包使用同一时钟。只有双端证据才能区分“DSM未及时处理”“空中链路延迟”和“无线模块缓冲”。

### 9.2 CPU最小状态记录

后续固件若增加诊断，建议每次TX只在RAM环形记录，不在ISR内打印：

| 字段 | 记录时点 |
| --- | --- |
| 事务序号、重试序号、`HAL_GetTick()` | 调用发送前 |
| `HAL_UART_Transmit_DMA()`返回值 | 调用返回后 |
| `gState`、`RxState`、UART ErrorCode | 调用前、调用后、等待结束 |
| DMA句柄State、ErrorCode | 调用前、调用后、等待结束 |
| `CR1.UE`、`CR1.TE`、`CR1.TCIE` | 调用前、等待结束 |
| `CR3.DMAT`、`CR3.DMAR` | 调用前、调用后、等待结束 |
| DMA2 Stream6 `EN`、`NDTR`、Channel | 调用后、等待结束 |
| USART6 `TXE`、`TC` | 调用后、等待结束 |
| TX完成中断计数 | 等待结束 |
| Stop/Abort原因和调用点 | 每次停止或中止时 |

### 9.3 B类响应链路记录

建议同步记录：

- CPU2侧每次 `Cl` 的发送、500 ms接收窗口起止和RX DMA停止时刻。
- 无线主机模块前、DSM无线从机后的同一帧双端时间戳。
- DSM接收命令、开始处理、生成响应和串口发送完成时刻。
- 故障窗口内DSM电源、电压、复位原因、看门狗和任务/中断最长占用。
- 迟到帧到达后，CPU2下一事务开始前的残留清理结果。

### 9.4 结果判定矩阵

| 复现状态 | 判断方向 |
| --- | --- |
| HAL非OK | TX启动失败；检查DMA句柄状态和错误传播 |
| `EN=0`、`NDTR=2` | DMA未启动或启动后立即被停止 |
| `EN=1`、`NDTR=2`持续不变 | USART6未产生DMA TX请求；检查DMAT、TE、UE和DMA Channel |
| `NDTR`从2降到0，但无TX完成计数 | DMA完成中断或USART6 TC链异常 |
| `NDTR=0`、TC=1、TX完成计数增加，但PC6无波形 | GPIO复用、电气链路或寄存器异常 |
| PC6有 `43 6C`，抓包工具未记录 | 复核抓包接线、阈值、方向和时间基准 |
| CPU2侧有 `Cl`，DSM侧同刻没有 `Cl` | 无线发送链路或模块缓冲 |
| DSM侧收到 `Cl`，但未在500 ms内发出 `D...` | DSM处理停顿或DSM内部串口发送异常 |
| DSM侧及时发出 `D...`，CPU2侧晚到 | 无线返回链路或模块缓冲 |
| CPU2侧500 ms内已有完整 `D...`，CPU仍报 `len=0` | CPU2 RX DMA、终止符检测或接收状态机 |

## 10. 最小A/B验证建议

### 10.1 A类TX验证

在不改变RX DMA的前提下，仅把DSM两字节命令TX临时恢复为阻塞发送：

```c
HAL_UART_Transmit(&huart6, (uint8_t *)cmd, strlen(cmd), 100)
```

9600 8N1下发送两个字节约需2.1 ms，相对500 ms采样和响应等待窗口影响较小。

判定：

- 阻塞TX长期不再复现：优先确认TX DMA、DMA2 Stream6和USART6 TC中断链。
- 阻塞TX仍出现无波形：优先检查PC6复用、USART6 UE/TE、内存越界和硬件链路。

该A/B方案只验证A类请求未发出，不解释2026-07-31的B类响应晚到。

### 10.2 B类延迟响应验证

优先在台架对DSM响应人为加入450 ms、500 ms、650 ms和2 s延迟，确认：

- 500 ms边界两侧的成功/超时行为。
- 三次重试期间迟到帧被哪一轮RX DMA接收。
- 第三次超时后迟到帧是否会残留并污染AT诊断或下一条DSM命令。
- 增加超时或退避时间是否只是降低报错，还是能稳定恢复事务边界。

上述方案目前只是验证建议，尚未获得实现授权，也未修改代码。

## 11. 后续处理顺序

1. 后续每次复现先按无线前抓包是否出现 `Cl` 分成A类或B类，不再只按 `0x000D0003`合并统计。
2. 继续保存最后正常帧、三次失败尝试、迟到帧、CPU错误和故障后诊断的共同时间戳窗口。
3. 核对现场CPU2固件版本和HEX哈希。
4. A类按TX DMA、TC、句柄、寄存器和PC6波形继续取证。
5. B类优先增加DSM端同步抓包或内部时间戳，定位停顿发生在DSM、无线去程/回程还是模块缓冲。
6. 用户确认后再选择最小诊断补丁、阻塞TX A/B固件或延迟响应故障注入版本。
7. 根因和修复完成后执行连续水位跟随、故障注入和真实硬件回归，再将本文移动到 `已闭环/`。
