## 3. 逐项详细说明

### 3.1 11-10 电机步进数错误如何检测

当前代码有两条主动产生路径。

#### 路径一：精确步数运动启动检查

1. 下发 TMC5130 相对步数运动前读取 `XACTUAL`。
2. 下发运动后每 10 ms 重读 `XACTUAL`。
3. 500 ms 内只要 `XACTUAL` 与下发前不同，就认为电机已经开始运动。
4. 500 ms 后仍完全不变，记录 `XTARGET`、`RAMPSTAT`、`GSTAT` 等诊断信息并返回 11-10。

这一路判断的是 TMC5130 内部实际位置寄存器有没有变化，不是直接比较外部 AS5145 编码轮位移。

#### 路径二：点动启动检查

点动模式启动超过 500 ms 后，如果 `MotorCtrl_IsDriverMoving()` 仍判断驱动未运动，返回 11-10。

因此 11-10 的准确含义应是“运动命令已下发，但启动宽限期内没有建立有效运动”。可能场景包括驱动未建立输出、机构卡住、目标或距离过小、驱动状态判断异常等。它不等同于 12-3“编码器检测到丢步”，后者关注电机运动与外部编码轮实际位移之间的差异。

### 3.2 11-17 与 11-21 两个电机过温故障的区别

| 对比项 | 11-17 电机驱动过温关断 | 11-21 电机驱动过温预警 |
| --- | --- | --- |
| TMC5130 状态位 | `DRV_STATUS[25] = OT` | `DRV_STATUS[26] = OTPW` |
| 硬件状态 | 已达到关断阈值，驱动功率输出被硬件关闭 | 已接近关断阈值，驱动尚未必自动关断 |
| 严重程度 | 更高 | 较低，但当前软件仍中止动作 |
| 同时出现时 | 11-17 优先 | 被 11-17 覆盖 |
| 自动恢复 | 禁止自动重跑，需先排查温度、负载和散热 | 同样禁止自动重跑 |

这两个温度状态来自 TMC5130 芯片自身的硬件诊断位，当前 CPU2 没有读取具体摄氏温度，也没有用软件温度阈值自行计算。工作簿中的“电机过温”更准确地说是“电机驱动器过温”。

### 3.3 11-24 电机等待到位超时包含哪些故障场景

当前唯一产生函数是精确步数运动 `MotorCtrl_MoveByTicksAndWait()` 的最终到位确认：

- 前置运动已经下发；
- 等待驱动停止流程已经结束；
- 随后持续读取 `XACTUAL`；
- `|XACTUAL - target_ticks| <= 1024 ticks` 才算到位；
- 超过 15 s 仍未进入该范围，返回 11-24。

当前调用场景只有：

1. 零点处下行一圈，标定首圈周长；
2. 位置源切换时下行一圈，标定当前位置局部周长；
3. 局部周长标定后反向回到切换前位置。

所以当前 11-24 不是所有普通液位、密度运动的通用到位超时。普通流程中的通信失败、命令切换、驱动健康错误会优先返回各自具体故障；只有驱动仍可读取、没有其它具体错误，但最终位置长期不到目标附近时才返回 11-24。

可能原因可归纳为：运动只完成一部分、机构卡阻或打滑、驱动力不足、目标寄存器/位置寄存器不一致、运动参数或步数模型异常。正式工作簿应补充“当前主要用于周长标定精确步数运动”的适用范围。

### 3.4 “保留”故障代码是什么意思

“保留”表示：

- 故障编号和含义已经占用并冻结，不能再拿去表示其它故障；
- CPU2/CPU3 枚举和资料可以先保留该编号；
- 当前固件没有主动产生调用点，正常设备不会自行报出；
- 以后启用时仍需补齐检测条件、错误出口、显示、恢复策略和故障注入验证。

因此可直接理解为“还未实现，预留”，但不是可以随意复用的空号。

当前共有 3 个保留项：

| 故障码 | 名称 | 当前状态 |
| --- | --- | --- |
| 12-6 | 编码器上电变化 | 未实现主动检测 |
| 15-16 | 实高偏差过大 | 未实现主动检测 |
| 21-5 | 扭力传感器饱和 | 未实现主动检测 |

如果现场出现这些编号，应先核对 CPU2 固件版本、历史表、人工故障注入或数据异常，不能直接断言当前固件真的检测到了对应故障。

### 3.5 12-11 编码器多次无效数据中的“无效数据”是什么

按名称设计，12-11 应表示“已经收到编码器帧，但该帧不能作为位置使用，又不属于已细分的校验错误、角度计算未完成或内部计算溢出”。但当前源码没有实现这样一个可到达的判定。

当前 AS5145 帧处理逻辑为：

- 全 0 或全 `0xFF`：12-1 编码器通信无响应；
- 偶校验失败：12-2 编码器校验位错误；
- `OCF = 0`：12-14 编码器状态未完成；
- `COF = 1`：12-12 编码器计算溢出；
- 上述条件都不成立：直接作为有效位置使用。

`ENCODER_INVALID_DATA` 位于错误码映射函数的最后兜底分支，但调用错误映射函数之前已经保证至少命中校验、`OCF` 或 `COF` 中的一项，所以最后兜底分支实际不可到达。当前代码也没有“连续 N 次无效后返回 12-11”的独立计数判定。

结论：工作簿把 12-11 标成“使用中”与当前源码不一致。后续需要二选一：

1. 明确定义真正的无效条件和连续次数，再实现 12-11；
2. 如果没有独立语义，将 12-11 改为保留，并避免宣称当前可以主动检测。

附带发现：`LIN` 线性报警虽然有 12-13 映射分支，但当前异常入口没有把 `LIN` 纳入错误条件，因此该分支同样需要另行复查。

### 3.6 12-15 编码器首个位置等待超时是什么故障

编码器采集启动后，CPU2 最多等待 1500 ms，只有满足以下全部条件的帧才会锁存为“首个可信位置”：

- 不是全 0 或全 `0xFF` 空总线模式；
- 偶校验正确；
- `OCF = 1`，角度计算已经完成；
- `COF = 0`，没有内部计算溢出。

1500 ms 到期仍未锁存首个可信位置时：

- 如果已经记录了 12-1、12-2、12-12 或 12-14 等具体错误，优先返回该具体错误；
- 如果没有具体底层错误可返回，才返回 12-15。

此外还有两个运动门禁会使用 12-15：

1. 上电默认命令准备执行时，编码轮记步模式尚未取得首帧；
2. 普通运动准备时，编码轮记步模式尚未取得首帧。

12-15 主要表示“启动位置盲区未结束”，不是编码器运行一段时间后突然断线。首帧一旦成功锁存，后续通信异常通常报其它具体编码器故障。

### 3.7 13-1 是谁和谁的数据校验失败

13-1 表示 CPU2 对“传感器返回帧”做本地完整性计算后，与该帧携带的校验字段不一致：

- DSM 普通响应：CPU2 计算响应内容的 BCC，与响应尾部 BCC 比较；
- DSM 水位响应：CPU2 对 `resp[0..7]` 计算 BCC，与 `resp[8]` 比较；
- LTD 二代响应：CPU2 计算响应求和值，与 `rx[7]` 比较；
- 安全传感器协议：帧 CRC 校验失败也映射为 13-1。

因此两端是“CPU2 本地计算结果”和“传感器响应帧携带的校验值”。

需要与 13-16 区分：13-16 是传感器明确报告其内部两个测量/处理单元之间的数据校验异常；13-1 是 CPU2 接收链路上的帧完整性校验失败。

### 3.8 13-2 是否应改为“振动管谐振频率异常”

正式工作簿当前名称“声波频率异常”不准确；CPU2 枚举注释、错误日志和 CPU3 显示已经分别使用“振动管频率异常”或“测量管频率异常”的口径。

建议统一名称为：**振动管频率异常**。

不建议最终名称写成“振动管谐振频率异常”，原因是 13-21 已专门表示“传感器无谐振”。建议按以下方式区分：

- 13-2：CPU2 取得了频率数值，但数值为 0、超过上限或长时间没有形成有效频率；
- 13-21：传感器自身扫频后明确报告没有找到谐振点。

当前液位频率有效范围为 `1～6500 Hz`。频率连续异常时，每轮读取 3 次；最多执行 3 轮模式切换恢复，最终仍失败时返回 13-2。

### 3.9 13-5 是否只有 DSM 传感器会报

是。当前唯一主动产生点位于 DSM 特殊响应映射：

```text
A+888.88B+888.88  ->  13-5 传感器内部通信超时
```

LTD 二代普通协议和安全传感器协议当前都没有产生 13-5 的调用点。安全协议的传感器内部故障使用更细分的 13-30、13-38 或其它专用状态码。

正式工作簿建议在“适用协议/传感器”列将 13-5 标记为“DSM 传感器特殊返回码”。

### 3.10 13-14 与一代计量仪 6-1 是否相同

不完全相同，只能说存在部分历史对应。

一代 6-1 是宽泛合并码，历史说明同时包含：

- 当前 X 角度与零点 X 角度偏差大于 9°；
- 超声传感器 Y 角度偏差大于 9°；
- 浮子传感器长距离找液位判断连续失败；
- 测水小管按频率找液位连续失败；
- 跟随角度与空气值或油中值差异异常。

当前二代 13-14 的实际主动产生点只有：

1. DSM 返回 `A+444.44B+444.44` 特殊响应；
2. 安全传感器协议读取姿态角时，传感器明确返回数据无效，或服务层判定姿态数据无效。

当前代码没有在 13-14 的产生点中直接执行一代 6-1 所列的全部“9°比较”和“连续三次找液位失败”逻辑。因此不能在对照表中写“13-14 与一代 6-1 完全相同”。更准确的写法是“部分继承一代 6-1 的姿态角异常语义；一代其它合并场景已拆分或不再由本码承担”。

### 3.11 传感器频率为 0 会报 13-21 吗

不会因为数值为 0 直接报 13-21。

当前行为为：

- 液位频率读取为 0：按无效频率重读、延时并进行模式切换恢复，最终返回 13-2；
- SI/Wartsila 密度点频率持续小于等于 0：等待流程超时后返回 13-2；
- 13-21：只在 DSM 返回 `A+111.11B+111.11` 时产生，表示传感器自身明确报告“无谐振”。

因此“频率值为 0”与“传感器明确判定无谐振”是两个不同证据层级。传感器内部无谐振可能最终表现为 0，但只要通信响应没有给出 111.11 特殊码，CPU2 就按 13-2 处理。

### 3.12 13-26 密度最大值和改为 3000 的影响

当前实际行为：

- 密度找液位路径把 `density <= 0` 或 `density > 2000.0 kg/m³` 判为 13-26；
- 连续达到无效次数门槛后停止密度找液位；
- 正式工作簿也写“超过 2000 kg/m³”；
- CPU3“密度手输值”当前范围是 `0～200000`，倍率为 100，即 `0.00～2000.00 kg/m³`。

按本次要求，目标上限记录为 **3000 kg/m³**。后续实现不能只改一处常量，至少应同步核对：

1. CPU2 的 13-26 数值判定上限：2000.0 改为 3000.0；
2. CPU3 密度手输值上限：200000 改为 300000；
3. 正式故障工作簿的故障说明和原因；
4. 菜单参数范围、状态页/协议资料和相关测试；
5. 安全传感器协议或具体传感器自身声明的密度有效范围是否允许 3000 kg/m³。

本轮只记录需求，未修改上述内容。实施前还需确认边界规则：`3000.0` 是否有效。按当前 `> 上限` 的写法，建议保留“3000.0 有效，超过 3000.0 无效”。

### 3.13 传感器安全协议独有故障码

按当前 CPU2 实际产生调用点核对，安全传感器协议独有故障码为 13-31～13-56，共 26 项。它们只在 `SAFE_SENSOR` 的安全协议客户端、服务层或适配层结果映射中产生；DSM 和 LTD 普通协议当前不会主动产生这些码。

| 故障码 | 名称 | 安全协议含义 |
| --- | --- | --- |
| 13-31 | 传感器身份不匹配 | 传感器身份与当前绑定对象不一致 |
| 13-32 | 传感器协议版本不兼容 | 协议版本不在支持范围 |
| 13-33 | 传感器模式未就绪 | 指定模式尚未准备完成 |
| 13-34 | 传感器配置代次不一致 | 配置纪元与会话中保存值不一致 |
| 13-35 | 传感器上报状态不一致 | 周期上报状态与预期不一致 |
| 13-36 | 传感器数据过期 | 数据年龄超过允许范围 |
| 13-37 | 传感器温度超限 | 传感器报告温度超出工作范围 |
| 13-38 | 传感器内部故障 | 未被其它细分类覆盖的远端内部故障 |
| 13-39 | 传感器地址不匹配 | 响应地址不是目标地址 |
| 13-40 | 传感器会话失效 | 当前会话标识不再有效 |
| 13-41 | 传感器报文序号异常 | 请求与响应序号不一致、乱序或跳变 |
| 13-42 | 传感器需要重新握手 | 对端要求重新 HELLO/能力确认 |

以下故障码虽然安全协议也会映射使用，但不是安全协议独有，不应加“安全协议独有”标记：

- 13-1 传感器数据校验失败；
- 13-2 振动管频率异常；
- 13-3 传感器通信超时；
- 13-14 传感器姿态角异常；
- 13-26 密度值异常无效；
- 13-27 传感器响应格式异常；

- 13-30 传感器自检失败。

### 3.14 14-15 的具体故障场景以及为什么放在 14 类

当前唯一产生点位于 SI Profile 完成流程：

1. SI 分布密度候选结果已经形成；
2. 设备已经回到稳定液位；
3. 准备一次性发布完整 Profile 结果；
4. 如果 `g_measurement.debug_data.motor_state != 0`，返回 14-15，不发布结果。

当前代码只检查电机状态标志是否为非零，没有在该产生点再次读取 TMC5130，也没有直接比较编码器位置是否仍变化。因此正式工作簿中“位置仍在变化”属于可能原因，不是该调用点的直接判据。

放在 14“零点与位置检测”类的依据是：它保护的是“提交结果时位置是否已经稳定可信”，责任对象是运动/位置状态，而不是密度算法本身。它与 14-12 位置数据无效、14-13 越过目标、14-14 到位偏差过大属于同一位置可信性责任域。

但从当前唯一业务入口看，它确实只发生在 SI Profile 测量结果提交阶段，所以售后人员容易认为应放在 15“测量过程”。综合兼容性和实际语义，建议：

- 保留 14-15 的编号和责任域，不做重编号；
- 将名称收窄为“SI分布结果提交时电机未停”或在说明中明确 SI Profile 场景；
- 如果以后其它测量结果提交路径也复用该保护，再把说明扩展为通用场景。
