CUBE 首轮多智能体代码审查问题清单与整改方案

审查概览

本轮共整理 34 个问题，其中 P0 3 个、P1 14 个、P2 14 个、P3 3 个。最高风险集中在三条主线：CPU2 Modbus 边界校验不足、电机安全错误被覆盖或清除、CPU3 对 CPU2 数据和外部协议的帧校验不足。

CPU2 Modbus 边界 电机失步与停机安全 命令切换状态一致性 CPU3 内外协议帧校验 显示参数保存后不生效 版本与提交门禁追溯
处理原则：先封住会造成内存破坏、错误漏报和现场误动作的 P0/P1，再处理参数语义、显示一致性、文档门禁和诊断体验。涉及 CPU2/CPU3 共享协议、参数语义或错误码传递的修复，需要同步评估 DEVICE_PROTOCOL_VERSION、CPU2/CPU3 固件版本、版本文档和回归用例。

优先级定义

P0 可能造成内存破坏、安全边界漏报、参数被错误持久化，或直接阻断现场发布的问题。建议作为第一批修复并补回归测试。
P1 可能导致测量状态误报、主机协议不可用、关键错误被吞掉、现场数据错位或用户配置不生效的问题。建议紧随 P0 处理。
P2 会降低可靠性、诊断性、兼容性或现场维护效率的问题。建议在 P0/P1 稳定后按模块排期。
P3 一致性、可维护性、文档追溯或低概率兼容问题。可以随相关模块改动一起处理。

P0 阻断级问题

P0-01 电机位移偏差检测到失步后被后续健康检查覆盖

P0
证据位置：LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_motion_api.c:545-577，调用点 LTD_MAIN_CPU2/Application/Src/measure.c:835-882。

问题原因

MotorCtrl_MoveAndWait() 在检测到实际位移与目标位移偏差超过 70% 时，将 ret 设置为 ENCODER_LOST_STEP。随后函数又立即执行 MotorDriver_SyncPositionOrCheckHealth(&stepper)，并把返回值重新赋给同一个 ret。如果驱动健康检查返回 NO_ERROR，前面已经识别出的失步错误会被覆盖。

调用层通常只根据最终返回值决定是否 SET_ERROR(ret)。因此“检测到失步”和“函数最终返回成功”之间出现冲突。

影响

大幅位移异常可能不上报、不进入故障、不触发恢复，CPU3 和外部主机看到的是正常状态。该问题属于电机安全边界漏报，现场风险高。

整改方案

  • 将位移偏差结果保存为独立变量，例如 motion_ret，驱动健康检查保存为 health_ret，不得覆盖首个具体运动错误。
  • 返回优先级建议为：运动安全错误优先，其次驱动健康错误，最后速度恢复错误。
  • 当 motion_ret == ENCODER_LOST_STEP 时，强制进入故障路径并记录错误日志；如果还需要同步驱动状态，把健康检查结果作为附加诊断信息。
  • 同步检查 MotorCtrl_MoveUp/Down、手动移动、油位/水位/密度路径是否都正确传播该返回值。

验证建议

  • 构造电机实际移动距离明显小于目标距离的仿真或 HIL 场景，确认返回 ENCODER_LOST_STEP。
  • 确认 CPU2 输入寄存器、CPU3 故障页、外部 DSM/SI 状态均能看到该错误码。
  • 补单元测试或静态测试，锁定“健康检查成功不能覆盖失步错误”。

P0-02 CPU2 FC04 输入寄存器大范围读可能写爆响应缓冲区

P0
证据位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c:137、hostcommu_modbus.c:244-260、LTD_MAIN_CPU2/Services/Modbus/hostcommu.h:8、stateformodbus.h:374。

问题原因

JudgeStartAddress() 只校验起始地址和寄存器数量是否落在 INPUTREGISTER_AMOUNT 范围内，没有限制 Modbus 单帧读寄存器数量。Compose04Package() 根据 RCV_registercnt 直接写 sendframe[3...]，响应长度为 3 + RCV_registercnt * 2。

CPU2 的 HCOM_SendBuff 只有 1000 字节，而输入寄存器总量约 2570 个。一次大范围 FC04 请求可以通过地址校验，但响应组包会超过缓冲区，并且 sendframe[2] 的 byte count 只有 1 字节，超过 255 后还会截断。

影响

外部主站或 CPU3 内部主站发出大范围读取时，CPU2 可能发生内存破坏、响应 CRC 错乱、协议失步或运行异常。该问题不应依赖主站“正常不会这么读”来规避。

整改方案

  • FC04 寄存器数量必须限制为 1..125，超限返回异常码 0x03。
  • 增加响应缓冲长度保护：5 + 2 * RCV_registercnt <= HOSTCOMMU_SENDLENGTH，包含地址、功能码、byte count、数据和 CRC。
  • 把 FC03/FC04 的数量限制统一封装，避免保持寄存器和输入寄存器口径不同。
  • 对 RCV_registercnt == 0 也要返回非法数据值，不能生成空成功响应。

验证建议

  • 增加 FC04 数量边界测试：0、1、125、126、500、全表数量。
  • 确认 126 及以上返回异常响应，且不写响应缓冲越界。
  • 用地址靠近输入寄存器末尾的合法/非法组合测试半开区间边界。

P0-03 CPU2 FC10 未校验 byte count 和实际帧长，短帧可污染并持久化参数

P0
证据位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu.c:209-320、LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c:277-337。

问题原因

CPU2 接收层只做了最小长度、地址、功能码、CRC 等基础检查。FC10 处理时解析 startAddr 和 regCount 后，Compose10Package() 没有检查 revframe[6] 是否等于 regCount * 2，也没有检查实际接收长度是否等于 9 + byteCount。

组包函数直接按 RCV_registercnt 循环读取 revframe[j + 7] 和 revframe[j + 8]。短帧情况下，读取内容可能落到 CRC 字节或 DMA 缓冲旧数据，随后写入 HoldingRegisterArray，再由 ReadDeviceParamsFromHoldingRegisters() 回灌到 g_deviceParams 并触发延迟保存。

影响

构造一个 CRC 对短帧有效的 FC10 请求，就可能把错误数据写入参数区并持久化。影响范围包括命令、罐高、密度参数、报警参数、电流输出参数等所有可写保持寄存器。

整改方案

  • 在进入 Response10Process() 前按功能码做精确长度校验。
  • FC10 规则：regCount >= 1，regCount <= 123，byteCount == regCount * 2，frameLen == 9 + byteCount。
  • 长度或 byte count 非法时返回异常码 0x03，不得调用 Compose10Package()、不得回灌参数、不得请求保存。
  • 把 Compose10Package() 改成只负责“已验证帧”的寄存器写入，函数入口用断言或显式参数说明前置条件。

验证建议

  • 构造 FC10 正常写 1/2/123 个寄存器的 golden frame。
  • 构造 byte count 少 1、多 1、帧长短、帧长长但 CRC 有效的异常帧，确认全部拒绝且参数快照不变。
  • 验证异常帧不会触发 request_device_params_save()。

P1 高优先级问题

P1-01 CPU2 保持寄存器边界 off-by-one，末尾地址可越界读写

P1
证据位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c:25-27、hostcommu_modbus.c:131、stateformodbus.h:200。

问题原因

HoldingRegisterArray 定义为 HoldingRegisterArray[HOLEREGISTER_STOP]，合法下标是 0..HOLEREGISTER_STOP-1。但 HoldingregisterAmount 被定义为 HOLEREGISTER_STOP + 1，地址校验因此允许访问 HOLEREGISTER_STOP 对应的越界位置。

影响

FC03 可越界读一个保持寄存器，FC10 可越界写一个保持寄存器。虽然越界宽度小，但位置靠近静态数据区，可能污染相邻状态或导致不可预测问题。

整改方案

  • 把保持寄存器数量定义统一为 HOLEREGISTER_STOP，不要加 1。
  • 边界判断改为半开区间：start >= base 且 start + count <= base + amount。
  • 使用无溢出的范围判断，避免 start + count - 1 在 count 为 0 时下溢。

验证建议

补边界测试：最后一个合法地址读写成功，HOLEREGISTER_STOP 地址读写返回非法地址。

P1-02 CPU2 FC03 保持寄存器读未限制 125 个寄存器，byte count 会截断

P1
证据位置：LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c:218-232。

问题原因

Compose03Package() 与 FC04 一样使用 sendframe[2] = RCV_registercnt * 2，但没有限制 RCV_registercnt <= 125。保持寄存器总长度虽然通常不会超过 1000 字节缓冲，但超过 125 后已违反标准 Modbus RTU 响应长度，超过 127 后 byte count 可能接近或超过单字节边界。

影响

外部主站或 CPU3 大块读保持寄存器时，可能收到非标准响应，造成解析错位、CRC 不一致或后续通信失步。

整改方案

  • FC03 和 FC04 共用数量校验函数，统一限制 1..125。
  • 数量非法返回异常码 0x03，地址越界返回 0x02。
  • 在文档中说明大范围读取需要拆分多帧。

验证建议

用 125 和 126 个保持寄存器分别测试，确认 125 成功、126 异常。

P1-03 多个测量命令重复调用 MeasureStart 且不检查返回值

P1
证据位置：LTD_MAIN_CPU2/Application/Src/measure.c:104、measure.c:446-467、measure.c:511、measure.c:571、measure.c:613、measure_density.c:1474、measure_waterLevel.c:1355。

问题原因

调度入口 ProcessMeasureCmd() 已经调用并检查 MeasureStart()。但多个 CMD_* 函数内部再次调用 MeasureStart();，且不保存返回值。MeasureStart() 中 MotorCtrl_Init() 失败时会返回错误，但内部调用方没有处理该错误。

影响

第二次初始化失败时，流程仍可能继续进入找水、找底、密度、重量等动作，造成基于无效电机状态的后续操作。该问题还会让错误日志和 CPU3 状态无法反映真正失败原因。

整改方案

  • 优先采用单入口初始化：只在调度层执行 MeasureStart()，删除子命令内重复调用。
  • 如果某些测试命令确实需要独立初始化，应改为 ret = MeasureStart(); SET_ERROR(ret); 并在失败时立即返回。
  • 梳理所有 MeasureStart(); 未检查调用点，明确正式命令、调试命令和测试命令的不同策略。

验证建议

模拟 MotorCtrl_Init() 返回错误，确认所有正式命令都会停在错误态，不继续执行测量动作。

P1-04 取消测量时电机停机失败只打印，仍强制进入待机

P1
证据位置：LTD_MAIN_CPU2/Application/Src/measure.c:294-314、LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_motion_api.c:840-847。

问题原因

CMD_CancelMeasurement() 在用户取消时先清命令和错误码，然后调用 MotorCtrl_SlowStop()。如果停机返回真实错误，代码只打印日志，随后仍设置 device_state = STATE_STANDBY。

影响

用户取消本身不是故障，但取消过程中的停机失败是安全问题。当前逻辑会把“停止失败”对 CPU3 和外部主站隐藏起来，现场可能以为设备已经安全待机。

整改方案

  • 先执行停机，确认停机成功后再清取消相关状态。
  • 如果 MotorCtrl_SlowStop() 返回真实错误，调用 FaultManager_SetErrorState() 或等效路径进入 STATE_ERROR。
  • 取消成功和取消失败分别记录不同日志，便于现场判断。

验证建议

注入 TMC 停机失败或通信失败，执行取消命令，确认 CPU2/CPU3/外部协议均显示具体错误而不是待机。

P1-05 STATE_SWITCH 被 SET_ERROR 吞掉后，包装函数继续写完成态

P1
证据位置：LTD_MAIN_CPU2/Application/Inc/fault_manager.h:168-178、LTD_MAIN_CPU2/Application/Src/measure.c:509-518、measure.c:569-578、measure.c:611-700、measure.c:963。

问题原因

SET_ERROR() 对 STATE_SWITCH 不进入错误路径，也不返回。水位、回零、找底、空/满载重量等命令包装层在子流程返回 STATE_SWITCH 后继续执行后续语句，最终写入 STATE_FINDWATER_OVER、STATE_STANDBY、STATE_FINDBOTTOM_OVER 等完成态。

影响

命令切换或取消发生时，CPU2 可能短暂或持续报告“完成”，CPU3 和外部主站可能将中断流程的结果当作有效结果。

整改方案

  • 在所有可能返回 STATE_SWITCH 的调用后增加显式判断：if (ret == STATE_SWITCH) return;。
  • 新增专用宏，例如 SET_ERROR_OR_SWITCH_RETURN(ret)，避免 void 包装函数遗漏。
  • 对测量完成态写入做统一保护：只有 ret == NO_ERROR 才能写完成态。

验证建议

在水位、找底、回零、密度过程中注入新命令，确认旧命令不会发布完成态或有效结果。

P1-06 区间密度点数循环变量为 int8_t，点数超过 127 有越界风险

P1
证据位置：LTD_MAIN_CPU2/Application/Src/measure_density.c:643-714、LTD_MAIN_CPU2/Application/Inc/measure_density.h:15。

问题原因

区间点数 c_num 最大被钳到 MAX_MEASUREMENT_POINTS，当前为 200。但循环变量 i 使用 int8_t。当点数大于 127 时，i++ 会溢出为负数，仍满足 i < c_num，并继续作为数组下标。

影响

配置 128 到 200 个区间密度点时，可能出现栈越界、死循环、测量卡死或结果数组污染。

整改方案

  • 循环变量改为 int 或 uint32_t。
  • 参数写入阶段限制 spreadMeasurementCount 的业务上限。
  • 明确 Wartsila/DSM/内部协议对最大密度点数的统一口径。

验证建议

补 127、128、200 三组区间密度点数测试，确认不会越界且结果点数正确。

P1-07 密度测量命令切换后，部分点位可能被当作完整剖面发布

P1
证据位置：LTD_MAIN_CPU2/Application/Src/measure_density.c:275-330、measure_density.c:821-944。

问题原因

Density_RunPoints01mm() 在已经采到有效点后，如果检测到命令切换，只执行 break。只要 valid > 0，函数最终仍返回 NO_ERROR。外层命令随后复制临时结果、置 profile_complete_latched = 1，并递增完整完成计数。

影响

新命令插入时，CPU2 可能把未测完的密度剖面发布为完整结果，外部主机和 CPU3 难以识别数据只有部分点位。

整改方案

  • 命令切换时返回 STATE_SWITCH，不要返回 NO_ERROR。
  • 如果业务允许保留部分结果，应新增 partial 或 aborted 标志，不递增完整完成计数。
  • 外部协议导出密度剖面时同步增加有效点数和完整性标志。

验证建议

在密度测量第 1 个点、第 N/2 个点后插入新命令，确认旧剖面不会被标为完成。

P1-08 扭力通信超时可被命令启动流程清掉并重置计时

P1
证据位置：LTD_MAIN_CPU2/Application/Src/app_main.c:181-227、LTD_MAIN_CPU2/Application/Src/measure.c:446-455、LTD_MAIN_CPU2/Services/Weight/weight.c:78-149。

问题原因

主循环先执行 Weight_CheckCommunicationTimeout()，但如果随后有正式命令，流程会进入 MeasureStart()。MeasureStart() 调用 fault_info_init() 清错误，再调用 weight_init()，后者把 s_weight_last_rx_tick 重置为当前 tick。接下来 1000ms 内超时检查会认为通信暂时正常。

影响

已存在的 WEIGHT_COMM_TIMEOUT 可能在新命令开始时消失，运动开始前短时间内没有有效扭力通信保护，电机可能使用旧扭力值继续动作。

整改方案

  • weight_init() 不应在未收到新帧时重置通信健康时间。
  • MeasureStart() 不应无条件清全局故障，至少不能清除仍未恢复的通信类故障。
  • 正式运动前增加扭力通信有效性门禁，要求最近一帧有效且未超时。

验证建议

断开扭力通信，等待超时后下发找底/找水/密度命令，确认命令被拒绝或进入故障，不启动运动。

P1-09 编码器类全局错误可被有效 SSI 帧或位置源策略异步清除

P1
证据位置：LTD_MAIN_CPU2/BSP/Peripherals/src/AS5145.c:143-146、AS5145.c:225-272、LTD_MAIN_CPU2/Application/Src/app_main.c:61-94、LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_driver_param.c:202-207。

问题原因

Is_Encoder_Error_Code() 使用一个连续范围判断编码器错误，范围内包含 ENCODER_LOST_STEP。任意有效 SSI 帧或电机位置源模式下的清错逻辑，都可能把该范围内全局错误清为 NO_ERROR。

影响

运行失步、编码器上电异常、运动校验失败等锁存故障可能被后台采集帧清掉。如果设备处于 STATE_ERROR，错误码被清后主循环还可能回到待机。

整改方案

  • 区分“后台 SSI 通信瞬态错误”和“运动安全锁存故障”。
  • 清错逻辑改为白名单，只允许清除明确可恢复的采集通信类错误。
  • ENCODER_LOST_STEP、位置差异过大、运动校验类错误必须由故障恢复或人工复位路径清除。

验证建议

注入失步错误后继续输入有效 SSI 帧，确认错误不会被异步清除。

P1-10 CPU3 内部 CPU2 FC04 响应未校验 byte count 和实际长度

P1
证据位置：LTD_DISPLAY_CPU3/Communication/internal/main_board_modbus/cpu2_communicate.c:414-423、LTD_DISPLAY_CPU3/Core/Src/stm32f4xx_it.c:211-245。

问题原因

UART5 IDLE 接收只要长度达到最小值就解除等待，随后 HostCommuProcess() 只做基础 CRC、地址、功能码检查。CPU2_Response04Process() 没有校验 revframe[2] == RCV_registercnt * 2，也没有根据实际长度判断循环读取是否越界。

影响

整改方案

  • 把实际接收长度传入 03/04 响应解析函数。
  • 统一检查 bytecount == RCV_registercnt * 2 和 len == 3 + bytecount + 2。
  • 解析失败时丢弃本帧并保持旧缓存，必要时置 CPU2 通信错误或增加统计计数。

验证建议

构造 CPU2 FC04 短帧、byte count 错误帧、长度多余帧，确认 CPU3 不更新测量缓存。

P1-11 Wartsila FC16 现场特殊 byteCount 兼容被误判

已闭环
证据位置：docs/01_协议与寄存器/Wartsila协议适配/2026-01-27_莆田现场Wartsila抓包协议整理.md、LTD_DISPLAY_CPU3/Communication/external/external_read_freshness.h。

问题原因

原审查只按标准 Modbus 判断，未纳入莆田现场抓包证据。现场 Wartsila 主机的 byteCount 等于 qty，但数据区仍包含 2 * qty 字节；直接改成只接受 qty * 2 会破坏现场主机兼容。

影响

只保留现场格式会拒绝标准调试工具；只保留标准格式则会拒绝真实 Wartsila 主机，并返回 FC16 异常码 0x03。两种单边实现都会造成参数或命令无法写入。

整改方案

  • 现场兼容特例：同时接受 byteCount == qty 和 byteCount == qty * 2U，禁止后续通用 Modbus 整改删除前一分支。
  • 两种格式的数据区都必须严格为 2 * qty 字节，因此 PDU 长度统一检查 6U + 2U * qty，不得按现场 byteCount 直接推导长度。
  • 保持 1 <= qty <= 123，避免请求超出 RTU 单帧合理上限。

验证建议

已补生产共享契约测试，覆盖现场格式、标准格式、单寄存器、四寄存器、最大数量、截短、超长和其它 byte count；现场命令帧 01 10 00 06 00 01 01 00 05 96 35 必须保持成功。

证据位置：LTD_MAIN_CPU2/Application/Src/measure.c:807-815。

问题原因

CMD_EnterMaintenanceMode() 进入 while(1) 后只轮询命令切换，没有延时，也没有推进主循环里的重量超时、日志、延迟保存、恢复等后台任务。

影响

维护模式期间 CPU 空转，后台状态维护停滞。长时间停留可能导致通信、日志或保存行为异常。

整改方案

  • 加入小粒度可中断延时，例如基于 AbortableDelay_CommandSwitch()。
  • 必要时在维护模式循环中调用最小后台轮询函数。
  • 更好的方案是把维护模式改为主循环状态，而不是阻塞式命令函数。

验证建议

进入维护模式后保持一段时间，确认通信超时、错误日志、延迟保存等后台任务仍能推进。

P2-13 版本追溯入口和提交门禁文件状态不一致

P2
证据位置：README.md、docs/00_构建与版本/版本总览.md、tools/check_commit_subject_versions.py、tools/git-hooks/commit-msg。

问题原因

源码版本头已显示 CPU2 V1.20.2.0、CPU3 V1.18.2.0，但 README 和部分版本文档仍停在旧版本。AGENTS 要求提交标题门禁使用 tools/git-hooks/commit-msg，但相关脚本和 hook 当前仍是未跟踪文件。

影响

新克隆仓库可能没有门禁脚本；版本入口文档误导发布、升级和现场追溯。提交检查结果也可能因为未暂存而不能证明本次改动有效。

整改方案

  • 把提交标题检查脚本、hook、测试和文档规则纳入同一提交。
  • 同步更新 README、版本总览、参数存储升级清单中的当前版本。
  • 扩展提交标题检查脚本路径覆盖：README、CMake、.gitignore、根级构建治理文件等应按跨 CPU 改动要求双版本标题。

验证建议

暂存目标文件后运行 py tools\check_commit_subject_versions.py --range origin/MAIN..HEAD 和对应 unittest，确认门禁可复现。

P2-14 Wartsila 密度点能力定义不一致，地址表 200 点但刷新只写 100 点

P2
证据位置：LTD_DISPLAY_CPU3/Communication/external/wartsila_modbus/wartsila_register_map.h:78、LTD_DISPLAY_CPU3/Communication/external/wartsila_modbus/wartsila_modbus_data_analysis.c:257-258。

问题原因

Wartsila 寄存器映射宏 REG_DENSITY_POINT_COUNT 定义为 200，但数据刷新逻辑只循环写前 100 个密度点。注释和实际能力口径也存在 100/200 不一致。

影响

主站读取第 101 到 200 点时可能得到零值或旧值；如果 CPU2 实际测量点数超过 100，外部声明和数据内容不一致。

整改方案

  • 确认 Wartsila 正式协议到底支持 100 点还是 200 点。
  • 若只支持 100 点，收窄宏、地址范围和点数上限。
  • 若支持 200 点，刷新循环改为 200，并检查响应长度和主站读取策略。

验证建议

构造 120/200 点密度剖面，读取 Wartsila 点位寄存器，确认第 101 点以后数据符合正式契约。

P3 低优先级问题

P3-01 非法 Modbus 命令值被静默消费，排障信息不足

P3
证据位置：LTD_MAIN_CPU2/Services/Modbus/dataanalysis_modbus.c:293、LTD_MAIN_CPU2/Application/Src/measure.c:425。

问题原因

Modbus 保持寄存器写入命令值后直接 cast 为 CommandType。调度入口遇到不支持命令时主要打印提示，没有设置参数错误或可观测状态。

影响

主站写错命令值时，现场只能看到命令没有执行，无法从 CPU3 或外部状态明确判断是非法命令。

整改方案

  • 命令寄存器写入时做枚举白名单校验。
  • 非法命令返回参数错误或设置可观测错误码。
  • 文档列出合法命令值和保留值处理策略。

验证建议

写入未定义命令值，确认 CPU2 不执行动作，并能通过状态或错误码看到非法命令。

P3-02 CPU2 错误日志原因表比错误码和 CPU3 显示表少

P3
证据位置：LTD_MAIN_CPU2/Services/ParamStorage/system_parameter.h:139-193、LTD_MAIN_CPU2/Services/Utilities/error_log.c:139-268、LTD_DISPLAY_CPU3/Application/display/display.c:663-807。

问题原因

CPU2 ErrorLog_GetReasonByCode() 对多个细分错误码没有专用原因，只回退为电机、设备、搜索失败等大类；CPU3 显示表中已有更细的文案。

影响

如果 CPU3 没及时显示或错误码后续被清，串口/现场日志只剩泛化原因，降低诊断效率。

整改方案

  • CPU2/CPU3 使用同源错误码原因表，或生成式检查两端覆盖率。
  • 补齐所有 enum 中业务错误码的中文原因。
  • 新增错误码时让脚本检查 CPU2 日志和 CPU3 显示表是否同步。

验证建议

遍历错误码枚举，确认 CPU2 日志和 CPU3 显示均有明确文案。

P3-03 DSM 接受地址 0 并回包，疑似不符合 Modbus 广播习惯

P3
证据位置：LTD_DISPLAY_CPU3/Communication/external/DSM_modbus/DSM_communication.c:60-61、LTD_DISPLAY_CPU3/Communication/external/DSM_modbus/DSM_SlaveModbus_modbus2.c:630。

问题原因

DSM 地址检查允许 rcvbuff[0] == 0，响应函数仍使用本机从站地址组帧回包。标准 Modbus 中地址 0 通常作为广播地址，广播写不响应，广播读也不应正常响应。

影响

多从站总线上如果主站使用广播地址，CPU3 可能参与回包，造成总线冲突。若旧上位机把 0 当普通地址使用，则改动也有兼容风险。

整改方案

  • 先确认 DSM 现场协议是否有“地址 0 当普通地址”的历史兼容要求。
  • 若按标准 Modbus，地址 0 写操作可执行但不响应，读操作不响应或直接丢弃。
  • 把广播行为写入协议文档和兼容说明。

验证建议

发送地址 0 的读/写帧，确认响应策略符合最终协议口径。

建议整改顺序

  1. 第一批：修复 P0 三项。重点是 CPU2 FC04/FC10 帧边界和电机失步错误传播，这三项影响内存安全和运动安全。
  2. 第二批：修复 P1 中的协议边界问题，包括保持寄存器 off-by-one、FC03 数量限制和 CPU3 内部 FC04 短帧校验；Wartsila FC16 已依据现场抓包改为现场/标准双格式兼容并闭环。
  3. 第三批：修复测量状态一致性，包括 MeasureStart() 重复调用、取消停机失败、STATE_SWITCH 完成态、密度部分结果完整性。
  4. 第四批：修复故障和恢复可靠性，包括扭力通信超时、编码器错误异步清除、罐底 fallback、自动恢复严格健康检查。
  5. 第五批：修复 CPU3 显示参数实际生效、FRAM 参数合法化、长标题布局和 Wartsila/DSM 协议一致性。
  6. 最后处理版本文档、提交门禁、错误文案表等追溯和维护类问题，并在提交前统一评估版本影响。

验证建议
