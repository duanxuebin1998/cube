## 1. 结论摘要

当前各 Modbus RTU 接收通道均使用 STM32 UART `IDLE` 事件直接停止 RX DMA、计算接收长度并提交整帧。UART `IDLE` 约在 1 个当前串口字符时间静默后出现，因此当前实现实际上把以下两个概念合并成了同一个约 `1T` 门限：

- 帧内字节间异常判断；
- 帧结束确认。

Modbus RTU 要求这两个门限分开：帧内字符间静默超过 `t1.5` 时，本帧应判为不完整；只有连续静默达到 `t3.5` 后，才能确认一帧结束并允许进入后续响应或下一事务。当前代码没有独立的 `t1.5`、`t3.5` 定时器，也没有统一的发送静默门禁，所以不能判定为严格满足 Modbus RTU Serial Line 时序要求。

恢复实施时，以下架构要求不依赖最终选择 RXNE 还是 RX DMA：

1. 使用双方当前均未配置的 32 位 TIM5 建立 1 MHz 微秒时基，每个端口维护独立 RTU 时序上下文。
2. 把 `t1.5` 残帧判定、`t3.5` 帧结束确认和发送静默门禁分开实现，不再把第一次 UART `IDLE` 直接当成完整帧。
3. 完整帧先固定到不可变帧槽，再由通信服务完成 CRC、地址、功能码和业务处理；CPU3 内部主站改为非阻塞事务状态机。
4. 统一 UART TC 后的 RS485 方向切换、错误恢复、动态串口重配和广播地址 0 的“不响应”语义。
5. 第一阶段保留 DSM、内部 UART5 的 `8N1` 兼容格式，避免把时序修复和物理格式不兼容混在同一次发布。

接收后端保留三条候选路线，恢复时必须先评审并冻结其中一条，不能在实现中混用：

- RXNE 逐字节时间戳：软件关系最直接，RX DMA 关闭、TX DMA 保留，可作为基准方案；
- 2 字节循环 RX DMA + HT/TC 逐字节事件：如果要求继续使用 DMA，这是可验证性优先的首选，但仍是一字节一中断；
- 大环形 RX DMA + IDLE 后 `t1.5/t3.5` 双探针：中断负载更低，逻辑上可行，但 STM32F429 没有 IDLE 硬件时间锁存，必须证明 ISR 延迟、DMA 提交抖动和边界保守区后，才可作为有条件严格方案。

需要特别区分：在 `last_byte_end+t1.5/t3.5` 直接检查 DMA `NDTR` 是错误的，因为下一字符可能尚未接收完成；把检查点延后一个 `Tchar`，即在 `IDLE+t1.5/t3.5` 做双探针，数学上可以避免这一观察时点错误，但仍不能消除 F429 软件时间锚点带来的边界不确定区。

如果只增加时序状态机、不改变寄存器、命令、状态字段、波特率和串口格式，则 CPU2/CPU3 的 `DEVICE_PROTOCOL_VERSION` 可保持不变；实际代码落地会改变两端运行行为，发布时应按最终改动提升受影响的 CPU2、CPU3 固件补丁版本。

## 3. Modbus RTU 时序要求与计算口径

### 3.1 基本定义

依据《MODBUS over Serial Line Specification and Implementation Guide V1.02》的 RTU framing 口径：

| 名称 | 含义 | 处理要求 |
| --- | --- | --- |
| `Tchar` | 发送一个完整串口字符所需时间 | 由实际数据位、校验位、停止位和波特率决定 |
| `t1.5` | 帧内最大字符间静默门限 | 字符间静默超过该门限后又继续收到字节，本帧应判为不完整 |
| `t3.5` | 帧边界最小静默时间 | 连续静默达到该门限后，才确认前一帧结束 |
| 响应超时 | 主站等待从站完整响应的应用超时 | 由设备和业务确定，不等于 `t1.5` 或 `t3.5` |
| 轮询周期 | 主站发起相邻业务请求的调度周期 | 可能远大于 `t3.5`，但不能替代收帧状态机 |

字符位数按实际线格式计算：

```text
Nbits = 1 个起始位 + 数据位 + 校验位数量 + 停止位数量
Tchar_us = Nbits × 1000000 / baud
```

常见格式：

| 格式 | 字符位数 |
| --- | ---: |
| 8N1 | 10 bit |
| 8E1 | 11 bit |
| 8O1 | 11 bit |
| 8N2 | 11 bit |

### 3.2 `t1.5/t3.5` 计算

波特率不高于 19200 bit/s 时：

```text
t1.5_us = 1.5 × Tchar_us
t3.5_us = 3.5 × Tchar_us
```

实现时应使用 64 位整数向上取整，避免整数截断让静默时间短于要求：

```text
t1.5_us = ceil(3 × Nbits × 1000000 / (2 × baud))
t3.5_us = ceil(7 × Nbits × 1000000 / (2 × baud))
```

波特率高于 19200 bit/s 时，使用规范建议的固定值：

```text
t1.5 = 750 us
t3.5 = 1750 us
```

CPU3 菜单当前支持的波特率采用 11 bit 标准字符时，对应参考值如下：

| 波特率 | `t1.5` | `t3.5` |
| ---: | ---: | ---: |
| 1200 | 13.750 ms | 32.083 ms |
| 2400 | 6.875 ms | 16.042 ms |
| 4800 | 3.438 ms | 8.021 ms |
| 9600 | 1.719 ms | 4.010 ms |
| 19200 | 0.859 ms | 2.005 ms |
| 38400 | 0.750 ms | 1.750 ms |
| 57600 | 0.750 ms | 1.750 ms |
| 115200 | 0.750 ms | 1.750 ms |

### 3.3 串口格式合规边界

Modbus Serial Line 默认使用 8E1；如果选择无校验，应使用 2 个停止位形成 11 bit 字符。因此：

- Wartsila 的 8E1 和 SI 的 8O1 符合 11 bit 字符口径；
- 内部 UART5、DSM、LTD、LH 当前使用的 8N1 属于项目或厂商兼容配置，不是严格的无校验 Modbus 11 bit 格式；
- 本次推荐先保持现有 8N1，单独记录兼容偏差；未经现场设备确认，不把 DSM 一刀切改成 8N2；
- 如果后续决定把内部 UART5 改为 8N2，必须双端协调发布并单独处理版本、升级顺序和回退策略。

### 4.2 FRAM 和人工配置影响

CPU3 上电先执行 `Cpu3_Params_LoadFromFRAM()`，再调用 `Cpu3_ReinitAllUarts()`。当前 `Cpu3_SanitizePortConfig()` 只修正非法字段，不按协议覆盖已经保存的合法物理参数。因此：

- 表中的 COM1～COM3 只是出厂默认或切换协议时的模板；
- 用户在切换协议后仍可以单独修改合法波特率、数据位、校验位和停止位；
- 时序模块必须根据 UART 最终生效配置计算，不得只根据 `COM_PROTO_*` 枚举使用固定常量；
- UART 重配完成后必须原子更新该端口时序参数并复位接收状态机；
- 当前 SI 映射资料写有“保存和加载均强制 9600 8O1”，与现有源码保留合法人工覆盖的行为不完全一致，后续应由产品决定是锁定 SI 物理参数还是修正文档口径。

## 5. 当前源码收发路径

### 5.1 CPU2 UART5 从站

当前路径：

1. `MX_UART5_Init()` 配置 115200 8N1，启用 `UART_IT_IDLE` 并启动普通模式 RX DMA。
2. `UART5_IRQHandler()` 检测到 `UART_FLAG_IDLE` 后立即清标志并停止 DMA。
3. 中断中直接读取 DMA 剩余计数、计算长度并调用 `HostCommuProcess()`。
4. `HostCommuProcess()`在中断上下文完成长度、地址、CRC、功能码和寄存器范围检查，组织响应后立即启动 TX DMA。
5. TX 完成后切回接收并重新启动 DMA。

当前没有 `t1.5/t3.5` 定时器。请求结束到响应开始的最小间隔约为 `1T + 中断延迟 + 协议处理时间`，该处理时间依赖请求内容，不能作为协议静默门禁。

### 5.2 CPU3 UART5 主站

当前路径：

1. `CPU2_CombinatePackage_Send()`组帧并调用 `sendToCPU2()`启动 TX DMA。
2. `wait_response` 置位，主流程同步等待。
3. CPU3 UART5 收到 `IDLE` 后立即停止 RX DMA；长度达到最小门限就清除 `wait_response`。
4. 主流程退出等待后调用 `HostCommuProcess()`校验并解析响应。
5. 单次等待上限 `CPU2_RESPONSE_TIMEOUT_MS = 1000 ms`。
6. 普通调度周期 `CPU2_POLL_PERIOD_MS = 100 ms`，但批量点表读取和其他连续调用不能依赖该周期充当统一帧间门禁。

1000 ms 是整笔响应超时，100 ms 是业务轮询节拍，两者均不参与字节间隔和帧边界确认。

### 5.3 CPU3 COM1～COM3 外部从站

三路外部 COM 共用 `uart_idle_rx_dma_ready()`：

1. UART `IDLE` 后立即停止 RX DMA并计算长度；
2. 只要长度大于 0，就设置 `comX_rx_ready`；
3. 主循环根据端口的协议枚举分发 DSM、Wartsila 或 SI；
4. 协议层生成响应后立即启动 TX DMA；
5. TX 完成后执行 `UART_TX_POST_DELAY_LOOP = 18000` 次空操作，再切换到接收。

该 18000 次循环：

- 位于响应发送完成之后，不是请求结束到响应开始前的 `t3.5`；
- 未按波特率计算；
- 实际时间依赖主频、编译器和优化级别；
- 只能视为未标定的 RS485 方向释放延时，不能作为 Modbus 时序依据。

### 5.4 当前硬件定时器情况

- CPU2 当前只初始化 TIM1 和 TIM4，均已用于其他业务，Modbus 未使用硬件定时器。
- CPU3 已初始化 TIM2，且仍保留“退出罐上操作状态”的历史说明；即使当前未见启动中断，也不建议直接覆盖其配置。
- CPU3 TIM3/TIM4 已用于显示刷新等业务，不建议复用为 Modbus 微秒级时序。
- CPU2、CPU3 均为 STM32F429ZGT6；TIM5 是 32 位、4 比较通道定时器。当前双方 `.ioc`、Core 和业务源码均未配置或引用 TIM5，适合作为首选候选资源，但实施前仍须完成硬件资源和历史用途复核。
- CPU2 APB1 定时器时钟为 75 MHz，CPU3 为 90 MHz；芯片定义、时钟树和 TIM5 占用情况分别可由两端 `.ioc`、`Core/Src/main.c`、`Core/Src/tim.c` 及 `Drivers/CMSIS/Device/ST/STM32F4xx/Include/stm32f429xx.h` 复核。

## 6. 当前时序计算和合规结论

以下数值按当前实际线格式和名义波特率计算；115200 实际 BRR 误差只影响小数末位，不改变结论。

| 通道/Profile | 当前约 1T 判帧 | 应用 `t1.5` | 应用 `t3.5` | 结论 |
| --- | ---: | ---: | ---: | --- |
| 内部 UART5 115200 8N1 | 0.0868 ms | 0.750 ms | 1.750 ms | 时序不满足，格式为受控兼容偏差 |
| DSM 4800 8N1 | 2.0833 ms | 3.1250 ms | 7.2917 ms | 时序不满足，格式为厂商兼容偏差 |
| Wartsila 2400 8E1 | 4.5833 ms | 6.8750 ms | 16.0417 ms | 串口格式符合，时序不满足 |
| SI 9600 8O1 | 1.1458 ms | 1.7188 ms | 4.0104 ms | 串口格式符合，时序不满足 |
| LTD 4800 8N1 | 2.0833 ms | 3.1250 ms | 7.2917 ms | 时序不满足，格式为厂商兼容偏差 |
| LH 9600 8N1 | 1.0417 ms | 1.5625 ms | 3.6458 ms | 时序不满足，格式为厂商兼容偏差 |

严格把 DSM 无校验格式改为 8N2 时，4800 baud 的 `t1.5/t3.5` 应分别为 3.4375 ms 和 8.0208 ms；本次不以该数值改变现有厂商 Profile。

当前实现带来的典型结果：

- 帧内出现 `1T～1.5T` 的合法停顿时，DMA会被提前停止，后续字节可能丢失或进入下一次接收，最终表现为 CRC 错或无响应；
- 请求结束后尚未达到 `t3.5` 就可能开始响应，严格主站或协议分析仪可能判定间隔不合格；
- CRC 正确只能减少普通连续帧的误判，不能替代 RTU 时序状态机；
- 正常主站连续发送、字节间没有明显停顿时，当前实现大概率仍能通信，这解释了“现场可用”与“严格时序不合格”可以同时存在。

## 7. 问题和风险分级

| 等级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | UART `IDLE≈1T` 被直接当成完整帧 | 合法的 `1T～1.5T` 帧内停顿会被拆帧，USB/RS485 转换器、PLC 调度抖动或低速链路更容易暴露 |
| P0 | 没有 `t3.5` 请求结束确认就允许响应 | 请求—响应间隔不可证明，严格测试、网关或多设备总线可能拒绝或误判 |
| P1 | CPU2 在 UART 中断内执行完整 Modbus 解析和组帧 | 中断执行时间随寄存器数量变化，阻塞其他中断且把业务访问放进 ISR |
| P1 | CPU3 内部轮询仍有同步等待 | 等待 CPU2 最长可阻塞 1000 ms，期间外部 COM 响应延迟需要单独验证 |
| P1 | 外部发送 pending 队列可直接续发 | 两个 ADU 存在无 `t3.5` 静默连续发送的可能，不符合一请求一响应边界 |
| P1 | 动态 UART 配置未绑定时序重算 | FRAM 或菜单改变波特率/格式后，固定时间常量会失效 |
| P1 | 8N1 与严格 11 bit 格式不一致 | 内部双端可互通，但不能宣称完整符合通用 Modbus Serial Line 格式；DSM 还受厂商要求约束 |
| P1 | CPU2、DSM 对广播地址 0 存在回包路径 | 多从站总线上可能同时响应广播并发生碰撞；Wartsila、SI 当前又直接拒绝地址 0，行为不一致 |
| P2 | 18000 次空操作未标定 | 不同编译配置下时间变化，既不能证明方向释放，也不能证明协议间隔 |
| P2 | 缺少时序错误计数 | 现场只能看到 CRC/无响应，无法区分 `t1.5` 残帧、溢出、UART 错误和响应超时 |

## 8. 根因分析

### 8.1 把硬件便利事件当成协议边界

UART `IDLE` 适合提示“串口暂时空闲”，但它不知道 Modbus `t1.5` 和 `t3.5`。当前实现为了尽快获得 DMA 长度，在第一次 `IDLE` 就停止 DMA，导致硬件约 1T 门限覆盖了两个不同的协议状态。

### 8.2 缺少传输层抽象

当前 UART/DMA、帧边界、协议校验、寄存器访问和 RS485 发送方向分散在中断、`app_main.c` 和多个协议模块中，没有统一的“RTU 帧已完成”接口。结果是 DSM、Wartsila、SI 和内部 Modbus 共用 IDLE 收帧方式，却没有共用正确的 RTU 定时语义。

### 8.3 业务超时掩盖了链路层定时缺口

1000 ms 响应超时和 100 ms 轮询周期足以让普通功能测试通过，但它们只在完整事务或业务调度层生效，不能判断帧内部的字符间隔，也不能证明请求和响应之间存在 `t3.5` 静默。

### 8.4 串口配置和协议配置可分离修改

CPU3 允许用户在选择协议后继续修改合法串口字段。该设计有现场灵活性，但也意味着不能只为 DSM/Wartsila/SI 各写一组固定 `t1.5/t3.5` 宏；定时必须从最终生效的 UART 配置派生。

### 8.5 广播语义未统一

CPU2 和 DSM 当前接受地址 0 后仍可能构造响应，Wartsila、SI 则拒绝地址 0。Modbus 广播要求从站不响应；广播读应静默忽略，受支持的广播写可以执行但同样不得返回正常或异常响应。该差异不是帧定时本身造成的，但会直接影响多设备 RTU 总线安全，建议在同一传输层整改中统一。

源码核对点为 CPU2 `Services/Modbus/hostcommu_modbus.c`、CPU3 `Communication/external/DSM_modbus/DSM_communication.c`、`Communication/external/wartsila_modbus/wartsila_modbus_communication.c` 和 `Communication/external/si_modbus/si_modbus_slave.c`。

## 9. 整改目标与非目标

### 9.1 整改目标

1. 所有有效 Modbus 通道分别实现 `t1.5` 和 `t3.5`。
2. 选定的接收后端不因 `IDLE≈1T` 提前结束接收，并能证明不会丢失协议允许的后续字节。
3. 帧内间隔超过 `t1.5` 后继续收到字节时，整帧作废且不响应。
4. 只有完整 `t3.5` 静默后才提交帧并允许响应或下一请求。
5. UART 重配后自动重算时序，无需按协议枚举维护重复常量。
6. 中断内不打印、不动态分配、不执行阻塞等待。
7. 保留现有寄存器、命令、CRC、从站地址和 1000 ms 事务超时语义；广播地址 0 统一为不响应。
8. CPU3 内部通信不再用最长 1000 ms 的同步忙等阻塞三路外部 COM 服务。
9. 提供可观测计数和逻辑分析仪验收方法。

### 9.2 本次非目标

- 不新增或调整 Modbus 寄存器地址；
- 不改变 CPU2/CPU3 共享参数和命令语义；
- 不在同一阶段修改 DSM 或内部 UART5 的 8N1；
- 不借时序整改改变已经发布的 LTD／LH 业务处理、寄存器或默认串口契约；
- 不用本次时序整改顺带重写 DSM、Wartsila、SI 的业务映射；
- 不把 1000 ms 响应超时改成字节超时；
- 不生成或维护 PDF。

## 10. 方案选型

| 方案 | 做法 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- | --- |
| A. IDLE 后固定延时 | IDLE 时仍停止 DMA，再等待到 t3.5 | 修改量小 | `1T～1.5T` 到达的合法后续字节已无法接收 | 不采用 |
| B. 按功能码/长度提前判帧 | 根据请求长度或 CRC 猜测帧结束 | 响应快 | 功能码和长度多样，异常帧、广播、厂商扩展难统一，仍缺少 t3.5 | 不作为通用方案 |
| C. 在错误时点直接查 NDTR | 在 `last_end+t1.5/t3.5` 读取 DMA 生产位置 | 改动看似较小 | 看不到已经开始但尚未完成的字符，会误判边界 | 不采用 |
| D. 2 字节循环 DMA + HT/TC + TIM5 | DMA 循环写 2 字节缓冲，HT 处理 slot0、TC 处理 slot1，每个 DMA 事件记录逐字节软件事件时间 | DMA 独占 DR；间隔分类直接；最容易做边界注入和失败封闭 | 仍是一字节一中断；软件时间受 DMA/IRQ 延迟约束，HT/TC 合并和错误恢复必须严格受控 | 保留 DMA 时首选 |
| E. 大环形 DMA + IDLE 双探针 | DMA 不停收；每次 IDLE 保存生产位置，在 `IDLE+t1.5`、`IDLE+t3.5` 比较绝对生产序号 | 连续流中断少；DMA 缓冲抗调度抖动 | F429 无 IDLE 时刻硬件锁存，存在 ISR/DMA 边界不确定区；探针队列和回绕处理复杂 | 有条件可选，先证明实时性 |
| F. RXNE 逐字节时间戳 + 1 MHz TIM5 | RXNE 记录字符完成时间，TIM5 管闭帧和发送门禁，TX 保留 DMA | 数据路径简单；间隔分类和失败恢复清晰 | 增加 RX 中断负载；RX DMA 必须关闭 | 非 DMA 基准方案 |

若项目恢复时仍要求 RX 使用 DMA，默认优先评审方案 D；若首要目标是降低连续流中断负载，再评审方案 E。方案 D 与方案 F 都需要逐字节事件和可证明的 ISR 延迟，不能把“使用 DMA”理解为“没有逐字节中断”。

STM32F429 USART 没有可直接配置为 Modbus `t1.5/t3.5` 的接收超时 `RTOR/RTOF/RTOEN` 能力；`HAL_UARTEx_ReceiveToIdle_DMA()`即使可用，IDLE 事件仍约为 `1T`，只能帮助搬运和通知，不能单独完成 RTU 帧边界判定。当前 RX 引脚和板级 EXTI/定时器捕获资源也不适合在不改板的前提下增加起始位硬件捕获，因此本文不把输入捕获列为现板首选方案。

## 11. 共同架构与候选接收后端

### 11.1 高精度时间基准

CPU2、CPU3 均为 STM32F429ZGT6，推荐新增 TIM5 并配置为：

- 32 位向上计数；
- 1 MHz 计数频率，1 tick = 1 us；
- 自动重装值 `0xFFFFFFFF`；
- 只使用内部输出比较，不占用 GPIO；
- 所有 deadline 使用无符号差值处理计数回绕。

当前时钟配置下，CPU2 APB1 定时器时钟为 75 MHz，TIM5 预分频值应为 74；CPU3 APB1 定时器时钟为 90 MHz，预分频值应为 89。实现不得直接假设主频，初始化后应以时钟树和寄存器配置复核实际 1 MHz。
1 MHz、32 位自由运行的回绕周期约为 4294.967 s，即 71 分 35 秒；所有 Modbus deadline 远小于半个回绕周期，可使用模 32 位无符号差值。

建议通道分配：

| CPU | TIM5 比较通道 | Modbus 端口 |
| --- | --- | --- |
| CPU2 | CH1 | UART5 内部从站 |
| CPU3 | CH1 | UART5 内部主站 |
| CPU3 | CH2 | USART6 / COM1 |
| CPU3 | CH3 | USART2 / COM2 |
| CPU3 | CH4 | USART3 / COM3 |

当前双方源码和 `.ioc` 均未配置或引用 TIM5；实施前仍需完成硬件资源、NVIC、历史分支和引脚复用审查。CPU3 TIM2 保留历史用途说明，不作为首选。禁止用 1 ms 的 `HAL_GetTick()` 模拟 750 us。

所选接收事件源的中断优先级应高于 TIM5 比较中断，并限制全局关中断时间。方案 D 重点评审 DMA Stream HT/TC，方案 E 重点评审 UART IDLE、DMA producer 可见性和 TIM5 探针，方案 F 重点评审 UART RXNE。按当前 NVIC 基线，可先评估 CPU2 接收事件优先级 2/TIM5 优先级 3、CPU3 接收事件优先级 0/TIM5 优先级 1；最终值必须结合 TIM1、TIM3、TIM4 等既有 ISR 预算评审。需要测量最坏接收事件入口抖动，形成 `RX_EVENT_GUARD_US`；TIM5 事件到期时若仍有未消费的接收事件或 DMA producer 变化，应延后判定或失败封闭，不能先发布帧。

CPU3 当前 UART5、USART2、USART3、USART6 及相关 DMA Stream 均配置为相同抢占优先级 0，TX 完成路径还存在 18000 次空操作。该基线不能直接证明 115200 四口逐字节事件预算；恢复实施时必须先移除 ISR/回调中的未标定长操作并重新评审 NVIC 抢占关系，之后再选择方案 D 或 F。方案 E 同样依赖可界定的 IDLE ISR 延迟，不能借由较低平均中断数跳过该评审。

### 11.2 每端口时序上下文

每个 Modbus 端口维护独立上下文，至少包括：

| 字段 | 用途 |
| --- | --- |
| UART 句柄和 TIM5 通道 | 读取字节、时间戳并安排独立 deadline |
| 接收后端及 DMA 生产位置 | 标识 RXNE、2 字节 DMA 或大环形 DMA，并保存绝对生产序号/回绕代数 |
| RX 生产缓冲和不可变完成帧槽 | ISR 写当前候选帧，通信服务只读已发布帧 |
| 端口角色 | 主站响应接收或从站请求接收 |
| 最终波特率和实际线格式 | 计算字符位数和时序 |
| `tchar_us/t15_us/t35_us` | 当前端口定时值 |
| RX 状态 | 空闲、有效候选、丢弃；帧就绪与 RX 状态分离 |
| `last_byte_end_us/idle_anchor_us` | 逐字节事件方案记录字符完成时间；双探针方案记录 IDLE 软件锚点 |
| `close_deadline_us/probe_queue/generation` | 管理安全闭帧或双探针，并防止旧事件关闭新候选帧 |
| 帧长度、序号、完成原因和 ready 标志 | 按固定顺序原子发布稳定帧 |
| `tx_end_us/tx_gate_deadline_us` | 以 UART TC 为基准控制下一 ADU |
| 诊断计数 | 成功帧、t1.5 残帧、溢出、UART 错误、超时和发送门禁次数 |

上下文、帧槽、DMA 缓冲、探针队列和 TX 缓冲均不得动态分配。UART 重配时应先停止新事务、关闭所选接收事件和 TIM5 比较事件，等待 TX TC 或执行受控中止，再重新计算时序、清状态、DMA 代数和错误标志，最后按冻结的接收后端恢复接收。

### 11.3 从 UART 最终配置计算字符位数

计算必须基于最终写入 HAL UART 的实际配置，而不是仅看协议枚举：

- 8B、无校验：8 数据位；
- 9B、带校验：实际为 8 数据位 + 1 校验位；
- 9B、无校验：实际为 9 数据位，该组合不是标准 Modbus 8 数据位，应记录配置偏差；
- 停止位按 1 或 2 计入；
- 奇校验和偶校验都计 1 个校验位。

计算结果应采用向上取整。`t3.5` 不得因取整或时钟误差变短；如需安全余量，只能在 `t3.5` 上增加一个可追溯的微秒级 guard，不能用无标定循环代替。

### 11.4 DMA 计数的正确观察时点

设上一字符结束时刻为 0、字符时间为 `Tchar`。UART IDLE 约在 `Tchar` 时出现；若下一字符在 `1.2Tchar` 开始，其静默间隔小于低速口的 `t1.5`，应作为同一帧的合法后续字符，但该字符到约 `2.2Tchar` 才完整接收并使 DMA `NDTR` 变化。

因此，在 `last_end+t1.5` 直接查 `NDTR` 会看到“无新字节”并误判；在 `last_end+t3.5` 也可能遇到字符已开始、DMA 尚未提交的情况。对 IDLE 锚点方案，正确的理论观察时刻应延后一个字符时间：

```text
probe_t15 = IDLE + t1.5 ≈ last_end + Tchar + t1.5
probe_t35 = IDLE + t3.5 ≈ last_end + Tchar + t3.5
```

该修正说明“大环形 DMA + 双探针”在逻辑上可行，并不说明任意 `DMA + IDLE + NDTR` 实现都合规；实际实现仍要处理 IDLE ISR 延迟、DMA 提交抖动、回绕、错误和探针队列耗尽。

#### 11.4.1 方案 D：2 字节循环 DMA + HT/TC 逐字节事件

每个端口配置独立的 `uint8_t dma_rx[2]` 循环 DMA 缓冲，使用字节宽度、内存地址递增、FIFO 关闭和 HT/TC 中断：

- DMA 是 UART DR 的唯一读取者，保持 `DMAR=1`、关闭 `RXNEIE`，不得让 RXNE ISR 与 DMA 竞争数据寄存器；
- NDTR 从 2 变为 1 时由 HT 事件处理 slot0，从 1 变为 0 并自动重装时由 TC 事件处理 slot1；
- DMA ISR 入口先记录 TIM5，再按 HT/TC 的确定顺序取出对应字节，并使用与 RXNE 方案相同的“字符完成事件间隔”状态机；
- UART PE/FE/NE/ORE、DMA TE/DME/FE、HT 与 TC 同时挂起、事件顺序或缓冲代数不可信时，整段候选帧失败封闭：停止发布业务帧、增加诊断计数，清理并重新同步到完整 `t3.5`；
- 闭帧期间 DMA 保持接收；候选帧与不可变完成槽分离，不能为了处理旧帧停掉 RX DMA。

该方案保留 DMA 对 DR 的搬运和 ORE 缓冲优势，但不会降低事件数量。连续满载时，单路 115200 8N1 约为 11,520 次 DMA 字节事件/s；如果 CPU3 四路都允许配置为 115200 8N1，理论最坏约 46,080 次/s。最短字符周期约 86.8 us，恢复实施前应以不高于约 43 us 的最坏服务延迟作为初始 50% 裕量目标，并用真实 NVIC 组合和长临界区测量修正。

四路最坏情况下平均约每 21.7 us 就有一个 DMA 字节事件，因此“单事件延迟小于 43 us”只证明没有明显漏服务，不能证明总 CPU 占用可接受。DMA ISR 实际执行时间还应控制在少数微秒，并使用 DWT 周期计数或等效硬件测量同时给出单次最坏执行时间、聚合占用率和突发排队深度。

HT/TC ISR 必须是固定时间、无 HAL 重启动、无 CRC/寄存器处理的轻量路径。若在最坏负载下无法证明“每个事件在下一字节覆盖前被唯一识别”，应放弃该方案或降低允许的端口负载，不能静默降级为猜测帧边界。

#### 11.4.2 方案 E：大环形 DMA + IDLE 后双探针

该方案建议每端口使用 512 字节静态循环 DMA 缓冲、FIFO 关闭和绝对生产序号，DMA 在 IDLE、HT、TC、探针和帧发布时均不停收；HT/TC 在此只用于维护回绕代数或诊断，不作为逐字节帧边界。绝对生产序号由 DMA 回绕代数和稳定的 NDTR 快照共同组成，不能只用一个会回绕的 16 位索引。若 `producer-consumer` 距离达到或超过 512、无法证明未被覆盖，必须整段失败封闭。

每次 IDLE 只建立锚点，不直接提交帧。锚点至少保存 generation、IDLE ISR 软件时间、当时绝对生产序号、当前探针阶段和一个“下一探针”deadline；第一次探针未变化时复用同一锚点并重排到第二阶段，不能把两个探针预先拆成两项。115200 下理论上约 11 个锚点可能同时处于 `t3.5` 窗口，初始可按每端口约 16 项静态队列评审；最终容量仍必须由最高波特率、最短可重复 IDLE 间隔、最坏中断屏蔽时间和队列服务延迟计算证明。如果实现选择预先插入两个独立探针项，16 项不再具有足够证明，必须重新扩容和计算。

理论状态机如下：

```text
IDLE：记录 anchor_producer，安排 IDLE+t1.5 和 IDLE+t3.5

IDLE+t1.5：
    producer 已前进 -> 存在合法时间窗内的续字节，撤销本锚点的第二探针
    producer 未前进 -> 保留锚点，等待第二探针

IDLE+t3.5：
    producer 已前进 -> 出现 t1.5～t3.5 违规续传，当前连续数据进入丢弃态
    producer 未前进 -> 在 anchor_producer 处确认旧帧边界并发布不可变帧槽
```

STM32F429 不会在硬件中锁存 IDLE 发生时刻，ISR 读到的是“IDLE 已发生后的当前时间”；DMA 的 NDTR 更新和软件快照也有有限抖动，TIM5 比较标志置位到探针 ISR 真正执行之间也可能延迟。因此锚点会存在由最坏 IDLE ISR 延迟、最坏探针 ISR 延迟、DMA 提交不确定度、IDLE/波特率量化误差、TIM5 tick 和临界区共同形成的边界保守区。只有完成以下证明后，方案 E 才能称为“有条件严格”，否则只能作为兼容性改善：

1. 测得并限制 IDLE ISR 最坏入口延迟，115200 8N1 下必须小于 1 个 86.8 us 字符时间，初始目标不高于约 43 us；
2. UART/DMA 事件优先级高于 TIM5 探针，NDTR 快照、回绕代数和内存可见性有确定顺序；
3. 对边界保守区采用失败封闭，不把不确定事件当成合法帧继续执行写操作；
4. 探针队列满、generation 失配、DMA/USART 错误、生产位置不可信或回绕歧义均丢弃候选帧并重新等待完整静默；
5. 用逻辑分析仪和可控间隔发生器覆盖 `t1.5±Δ`、`t3.5±Δ`、连续回绕、探针堆积和故意延迟 ISR，并把可声明的 Δ 写入验收记录。

F429 清 IDLE 需要读 SR 后再读 DR。在 DMA 持续接收且新字节临界到达时，该清标志序列与 DMA 读取 DR 存在必须验证的竞争窗口；实现不得把 HAL IDLE 回调时间当成硬件锁存时间，也不得在未完成边界注入前宣称该窗口无风险。若使用 `HAL_UARTEx_ReceiveToIdle_DMA()`，回调 `Size` 只是本次事件对应的 DMA 位置，不是天然的“本帧长度”，必须与绝对 producer、旧 consumer 和回绕代数组合解释。

#### 11.4.3 接收后端选择结论

| 对比项 | 方案 D：2 字节 DMA | 方案 E：大环形 DMA 双探针 | 方案 F：RXNE |
| --- | --- | --- | --- |
| RX DMA | 保留 | 保留 | 关闭 |
| 数据事件 | 每字节 HT/TC | DMA 持续搬运，按 IDLE/探针批量观察 | 每字节 RXNE |
| 边界证据 | DMA 字节完成事件时间戳 | IDLE 软件锚点 + 绝对生产序号 | RXNE 字符完成事件时间戳 |
| 中断负载 | 高 | 通常较低，恶意间隔下需队列预算 | 高 |
| 证明难度 | DMA 路线中最低 | 最高，存在 F429 软件锚点保守区 | 低 |
| 首选场景 | 必须保留 RX DMA且可接受逐字节事件 | 中断预算不足且团队能完成严格实时性证明 | 不要求 RX DMA、追求最直接实现 |

本文暂不替项目冻结接收后端。恢复实施时若“继续使用 DMA”是硬约束，先验证方案 D 的四口最坏中断预算；只有方案 D 负载不可接受且方案 E 的边界证明、静态队列和失败封闭全部可完成时，才转入方案 E。

### 11.5 逐字节事件时间戳和间隔分类

RXNE 或 2 字节 DMA 的 HT/TC 都表示一个字符已经完整接收。事件入口应尽早读取 TIM5 当前值；RXNE 路线同时读取 UART 数据，DMA 路线只读取已完成的对应内存 slot。两条路线均计算：

```text
delta_end_us = current_byte_end_us - last_byte_end_us
gap_us       = max(delta_end_us - tchar_us, 0)
```

为避免 `Tchar`、`t1.5` 分别取整后累积误差，实际比较宜直接预计算“字符完成事件门限”：

```text
delta_t15_us = ceil(Tchar + t1.5)
delta_t35_us = ceil(Tchar + t3.5)
```

不高于 19200 baud 时两者分别等价于 `2.5Tchar` 和 `4.5Tchar`；高于 19200 baud 时分别为 `Tchar + 750 us` 和 `Tchar + 1750 us`。使用 64 位分子一次向上取整，不将两个已取整值再次相加。

每端口接收状态明确为 `RX_EMPTY`、`RX_VALID`、`RX_DISCARD`，已完成帧队列与这三个接收状态分离。使用回绕安全的无符号运算，并按实际配置得出的门限分类：

| 条件 | 有效候选态处理 | 丢弃态处理 |
| --- | --- | --- |
| `RX_EMPTY` 收到首字节 | 建立新候选帧 | 不适用 |
| `gap <= t1.5` | 追加当前字节并重排闭帧 deadline | 继续丢弃并重排 deadline |
| `t1.5 < gap < t3.5` | 当前连续数据整体无效，进入丢弃态 | 保持丢弃态 |
| `gap >= t3.5` | 先发布上一候选帧，再把当前字节作为新帧首字节 | 清除旧残片，把当前字节作为新帧首字节 |

对 RXNE 和 2 字节 DMA 的逐字节事件路线，`t1.5` 不需要单独的超时 ISR：只有后续字符落在 `t1.5～t3.5` 窗口时才构成帧内间隔违规；若没有后续字符，达到完整静默后前一候选帧可以正常结束。大环形 DMA 路线必须按 11.4.2 安排独立 `t1.5` 探针。

ISR 时间戳包含有限入口抖动。代码评审和逻辑分析仪测试必须给出最大抖动，并在边界用明确的微秒容差验收；不得用宽松容差掩盖长时间关中断或高优先级 ISR 阻塞。

### 11.6 无后续字符时的安全闭帧

STM32F429 UART 没有可直接用于本方案的“下一字符起始位时间戳”。对 RXNE 和 2 字节 DMA 的逐字节事件路线，如果只在 `last_byte_end + t3.5` 闭帧，下一字符可能已经在 `t3.5` 前开始、但尚未产生完整字节事件。因此安全闭帧 deadline 采用：

```text
close_deadline_us = last_byte_end_us + t35_us + tchar_us + RX_EVENT_GUARD_US
```

默认 Profile 的相邻逐字节完成事件门限参考如下，代码仍按最终 UART 配置逐端口计算并向上取整：

| Profile | 同帧上限 `Tchar+t1.5` | 新帧下限/无后续安全闭帧（未加 guard）`Tchar+t3.5` |
| --- | ---: | ---: |
| 内部 UART5 115200 8N1 | 约 0.837 ms | 约 1.837 ms |
| DSM 4800 8N1 | 约 5.208 ms | 约 9.375 ms |
| LTD 4800 8N1 | 约 5.208 ms | 约 9.375 ms |
| LH 9600 8N1 | 约 2.604 ms | 约 4.688 ms |
| Wartsila 2400 8E1 | 约 11.458 ms | 约 20.625 ms |
| SI 9600 8O1 | 约 2.865 ms | 约 5.156 ms |

额外的 `Tchar + guard` 是接收观测延迟，不改变协议门限定义。到期处理先确认：

1. 上下文 generation 和 `last_byte_end_us` 与安排事件时一致；
2. 对应 UART 的 RXNE/错误状态和 DMA HT/TC/错误标志均没有待处理的逐字节事件；
3. `now - last_byte_end_us` 已达到 `t35_us + tchar_us + RX_EVENT_GUARD_US`。

确认边界后必须结束当前接收状态，不能因完成槽已满而无限延迟：有效候选且有槽时发布；有效候选但槽满时丢弃整帧、增加队列满计数并回到空闲；丢弃态则清残片、记录原因并回到空闲。闭帧期间不关闭所选接收引擎：如果一个新合法帧已在 `t3.5` 后开始但尚未完成，其后续逐字节事件仍能把它保存为下一帧首字节。大环形 DMA 路线不使用本 deadline，而是在第二探针确认 producer 未变化后，按锚点生产序号切分并发布。

### 11.7 RX 缓冲、发布和溢出

Modbus RTU ADU 最大长度为 256 字节。建议每端口使用一个生产缓冲和至少两个不可变完成帧槽，或容量明确的固定帧队列：

- ISR 只写生产缓冲，通信服务只读已发布槽；
- 发布顺序固定为“冻结槽 → 写长度/序号/原因 → 内存屏障 → 置 ready”；
- CPU3 只有在完整帧已发布后才能结束等待或推进事务；
- 长度达到 256 后再来字节时只增加溢出计数并进入丢弃态，绝不越界；
- 完成槽已满时丢弃新帧并计数，不覆盖尚未处理的旧帧；
- 协议层仍限制最大合法 ADU 为 256 字节。

两条 DMA 路线的循环缓冲必须放在 DMA 可访问的 SRAM，禁止放入 STM32F429 的 CCM RAM。F429 没有 D-cache，不需要 cache clean/invalidate，但 DMA 与 CPU 共享的 producer、consumer、generation、ready 和帧元数据仍应使用稳定快照、必要的 `volatile` 语义和发布内存屏障，不能依赖编译器或中断时序“碰巧正确”。

### 11.8 中断和协议处理边界

最终边界按冻结路线三选一，未选路线必须关闭：

- RXNE 路线：UART ISR 读 SR/DR、记录微秒时间、追加或丢弃字节、重排 TIM5 deadline；
- 2 字节 DMA 路线：DMA HT/TC ISR 记录微秒时间、读取确定 slot、追加或丢弃字节、重排 TIM5 deadline；UART 错误 ISR 只负责失败封闭和重同步；
- 大环形 DMA 路线：DMA 持续写环形缓冲，UART IDLE ISR 只建立锚点，TIM5 ISR 比较绝对 producer 并执行双探针状态机；
- TIM5 ISR：校验 generation、未消费事件和 producer 可见性，安全固定候选帧或清除丢弃态；
- UART TC 回调：释放 DE、切回 RX、记录 `tx_end_us`、发布 `TX_DONE`；
- 通信服务：CRC、地址、功能码、寄存器映射、响应组帧、事务推进和日志。

不建议用 `HAL_UART_Receive_IT(..., 1)` 每字节重复启动，也不得在 RX DMA 开启时同时用 RXNE ISR 读取 DR。实现必须明确 DR 的唯一拥有者：RXNE 路线使用 `DMAR=0/RXNEIE=1`，两条 DMA 路线使用 `DMAR=1/RXNEIE=0`；TX DMA 均可保留。任何 ISR 中均禁止 CRC/寄存器映射、`printf`、FRAM 保存、阻塞延时和动态内存。

当前 HAL 的 `HAL_UART_DMAStop()` 会根据状态同时检查并停止 TX 和 RX DMA，不能继续把它作为通用的发送准备、第一次 IDLE 判帧或普通错误清理工具，否则会破坏循环 RX DMA 的绝对 producer 连续性。恢复实施时必须拆分 RX/TX 生命周期：IDLE 和帧发布不停止 RX DMA；仅在 UART 重配置、不可恢复 DMA/UART 错误或明确的半双工重建流程中受控停止并重建 RX，且旧 generation 全部失效。

CPU2 当前主循环含 50 ms 延时和长测量路径。协议处理移出 ISR 后，必须增加有界通信服务点或把长流程状态机化，并规定所有工作模式下的最大服务间隔；不能简单把 ready 标志留到一个可能长时间得不到调度的主循环末尾。CPU3 外部 COM 已在主循环解析，但内部 UART5 的 1000 ms 同步等待也必须改造。

### 11.9 CPU3 非阻塞事务和恢复

CPU3 UART5 推荐事务状态机：

```text
IDLE
→ WAIT_BUS_QUIET
→ TX_ACTIVE
→ WAIT_RESPONSE
→ VALIDATE
→ COMPLETE / RETRY / RECOVERY
```

要求：

1. 响应超时从 UART TC 时刻开始，而不是从调用 `HAL_UART_Transmit_DMA()`开始；
2. 收到完整帧后先发布不可变帧槽，最后再推进事务，禁止仅写 `wait_response = false`；
3. UART 错误、CRC/长度错误、合法响应和超时使用不同完成原因；
4. 超时恢复取消旧 deadline、清理候选帧，并重新获得 `t3.5` 静默后才重试；
5. 批量点表读取使用 `start/remaining` 游标逐笔推进，不在 `while` 中同步连发；
6. 外部 COM 请求和周期轮询使用固定容量队列及明确优先级，1000 ms 等待不得饿死外部响应。

### 11.10 RS485 方向和发送门禁

1. 从站只有在请求完整发布、CRC/地址/功能码合法后才允许发送响应。
2. 主站只有在总线静默门禁满足、上一事务完成或恢复完成后才允许发送下一请求。
3. 当前 HAL 普通模式 TX DMA 在 DMA 搬运完成后先打开 UART TC 中断，直到真正 TC 才调用 `HAL_UART_TxCpltCallback()`；因此回调内可直接释放 DE、切 RX 和记录 `tx_end_us`，不需要再次忙等 TC。
4. CPU2 回调内的 TC 忙等和 CPU3 的 18000 次空操作均应删除。若收发器手册明确要求 DE 尾保持，使用 TIM5 微秒事件并定义可追溯的 `RS485_DE_RELEASE_US`。
5. pending ADU 不得在 TX 回调中直接续发；下一 ADU 从 `tx_end_us + t3.5` 重新经过发送门禁。
6. CPU3 主站在 TC 后立即打开接收，以免丢失对端字节；“及时接收”和“完整边界后发布”是两个独立动作。

### 11.11 广播地址 0

所有外部 Modbus 从站 Profile 统一遵循：

- 广播读请求：静默忽略；
- 支持的广播写请求：执行但不发送正常或异常响应；
- 不支持、CRC 错或长度错的广播：静默丢弃并可增加诊断计数；
- 经 CPU2 桥接的广播写：异步排队，不等待 CPU2 响应，也不向外部主站回包；失败仅记录诊断。

内部 UART5 若业务上不需要广播，推荐防御性忽略地址 0，并在 CPU2/CPU3 协议资料中明确。禁止保留 CPU2 或 DSM 当前“接受广播后回包”的行为。

### 11.12 诊断计数

建议每端口保留以下 RAM 计数，第一阶段只供调试和测试脚本读取，不新增共享寄存器：

- `rx_frame_ok_count`；
- `rx_t15_gap_error_count`；
- `rx_t35_complete_count`；
- `rx_crc_error_count`；
- `rx_overflow_count`；
- `rx_uart_error_count`；
- `rx_timeout_count`；
- `rx_frame_queue_full_count`；
- `rx_irq_late_count`；
- `rx_dma_event_ambiguous_count`；
- `rx_dma_wrap_error_count`；
- `rx_probe_queue_full_count`；
- `rx_probe_deadband_drop_count`；
- `rx_broadcast_silent_count`；
- `tx_guard_wait_count`；
- `tx_busy_drop_count`。

计数只能在主循环限频打印，不得在 ISR 逐帧输出。若后续需要对外发布诊断寄存器，应另立共享协议变更，不与本次时序补丁混合。

## 12. 分通道实施方案

### 12.1 CPU2 UART5 从站

建议改动：

1. 新增 CPU2 Modbus RTU transport/timing 模块，绑定 UART5、TIM5 CH1、生产缓冲和不可变完成帧槽。
2. 按已冻结路线配置 UART5 接收引擎：方案 D 使用 2 字节循环 RX DMA 和 HT/TC；方案 E 使用 512 字节循环 RX DMA、IDLE 锚点和静态探针队列；方案 F 才停用 RX DMA 并启用 RXNE。三者均启用必要的 PE/FE/NE/ORE 错误入口并保证 DR 只有一个拥有者。
3. UART/DMA/TIM5 ISR 只做时间戳或锚点、状态转换、固定容量缓冲和 deadline/probe 更新，不再直接调用 `HostCommuProcess()`。
4. TIM5 安全闭帧后由有界通信服务处理现有 0x03/0x04/0x10、CRC 和寄存器映射；内部地址 0 若无业务需求则静默忽略。
5. TX 继续使用 DMA；HAL TX 完成回调已经位于 UART TC 后，应直接释放方向并恢复已冻结的接收引擎，删除冗余 TC 忙等。
6. 在 50 ms 主循环延时和长测量/跟随/电机路径中提供有界通信服务点，或把长流程状态机化；验收需给出最大服务间隔。
7. 测量最短请求、最大读响应和 0x10 写请求的端到端响应时间，同时确认协议解析不再位于 UART/TIM5 ISR。

### 12.2 CPU3 UART5 主站

建议改动：

1. 新增 CPU3 transport 上下文，UART5 按冻结的方案 D/E/F 接收，TIM5 CH1 管理闭帧/探针和发送门禁，TX 保留 DMA。
2. 完整响应必须先交换不可变帧槽、写入长度/序号/完成原因并置 `frame_ready`，最后才推进事务；禁止只用 `wait_response = false` 发布。
3. 用非阻塞事务 FSM 替换同步忙等；`CPU2_RESPONSE_TIMEOUT_MS = 1000 ms` 保持整笔事务上限，但从 UART TC 时刻开始计时。
4. CRC、地址、功能码、响应长度和 0x10 回显校验保持现有规则，错误原因分开统计。
5. 批量密度点读取、参数刷新和连续写请求改成游标/队列逐笔推进，统一经过 transport 门禁。
6. UART TC 后立即恢复接收；严格模式仍须拒绝小于 `t3.5` 开始的旧版早响应，因此新旧混装不能作为无条件兼容承诺。
7. 超时、UART 错误和取消事务均须废止旧 generation，清理候选帧并等总线重新满足 `t3.5` 后再重试。

### 12.3 CPU3 COM1～COM3 外部从站

建议改动：

1. USART6、USART2、USART3 统一采用已冻结的接收路线，并绑定 TIM5 CH2、CH3、CH4；若使用 DMA，三个端口分别拥有独立循环缓冲、DMA 代数和错误上下文。
2. 三个端口的 UART/DMA IRQ 调用同一 transport 事件入口；第一次 IDLE 绝不直接发布帧，方案 E 只允许第二探针确认 producer 未变化后发布。
3. 完成帧通过固定槽发布后再置端口 ready 事件，接收器始终可以接收下一帧。
4. 主循环继续使用现有 DSM/Wartsila/SI 分发表，不把 RTU timing 复制进每个协议模块。
5. 协议无响应、广播或错误时保持接收；存在响应时按 TX 门禁拉起 DE，TC 后立即恢复已冻结的接收引擎。
6. 取消无间隔 pending 续发和忙时覆盖；队列满、端口忙和丢帧均有独立计数。
7. UART 重配先冻结新事务、关闭接收引擎/比较事件并处理完 TX，再执行 DeInit/Init，清 generation、DMA 代数和探针队列，按最终 HAL 配置重算时序后恢复原接收路线；不得在重配或错误恢复中擅自切换路线。

### 12.4 Profile 兼容策略

| Profile | 第一阶段建议 | 原因 |
| --- | --- | --- |
| 内部 UART5 | 保持 115200 8N1，只修时序和调度 | 避免同时引入 8N2 物理格式变化；时序严格模式仍建议双端成对升级 |
| DSM | 保持厂商要求的 4800 8N1 | 未确认 DSM 设备支持 8N2，不能为追求通用格式破坏现场兼容 |
| Wartsila | 保持 2400 8E1 | 当前格式已符合 11 bit 字符口径 |
| SI | 推荐锁定 9600 8O1，或明确修正文档为可人工覆盖 | 官方资料要求固定格式，需收敛代码与文档差异 |
| LTD | 保持 4800 8N1 和现行业务响应 | 时序整改不得改变已经发布的 LTD 功能与默认串口契约 |
| LH | 保持 9600 8N1 和现行业务响应 | 时序整改不得改变 LH 寄存器、状态投影和写入语义 |

### 12.5 CPU2/CPU3 混装和发布策略

严格新版本会拒绝在上一帧结束后不足 `t3.5` 开始的事务，而旧版本可能提前响应或连续发起请求，因此“新旧四种组合都正常”与“内部链路严格合规”不能同时无条件承诺。

| CPU2 | CPU3 | 结论 |
| --- | --- | --- |
| 旧 | 旧 | 保持现状，可通信但时序不合规 |
| 新 | 新 | 目标组合，执行全部严格时序和非阻塞事务验收 |
| 旧 | 新 | 旧 CPU2 可能早响应，严格新 CPU3 可拒绝；仅在明确兼容模式下过渡 |
| 新 | 旧 | 旧 CPU3 可能连续请求或依赖旧响应节拍；必须实测，不作保证 |

推荐 CPU2、CPU3 协调成对发布和成对回滚。如果现场必须分步升级，可设计仅限内部 UART5、带明确截止版本的编译期兼容模式；兼容模式下应记录早响应/早请求计数，并明确不能宣称该混装组合严格符合 RTU 时序。

## 15. 验证方案

### 15.1 timing 计算和状态机测试

对 1200、2400、4800、9600、19200、38400、57600、115200 以及 8N1、8E1、8O1、8N2 至少覆盖：

- 计算使用向上取整；
- 19200 边界仍按字符时间计算；
- 高于 19200 使用 750 us/1750 us；
- 逐字节事件路线的完成门限分别为 `Tchar + t1.5` 和 `Tchar + t3.5`，不能直接把完成时间差与静默门限比较；
- 逐字节事件路线的安全闭帧为 `Tchar + t3.5 + guard`；大环形 DMA 路线的探针为 `IDLE+t1.5` 和 `IDLE+t3.5`；
- TIM5 计数回绕、CCR 重装和 generation 失效；
- UART 重配、事务取消和超时恢复均中止旧 deadline；
- 空接收事件、伪比较事件和第一次 IDLE 均不得直接发布帧；双探针路线只允许第二探针确认 producer 未变化后发布；
- 1、4、8、255、256 字节帧；
- 257 字节及以上溢出；
- PE、ORE、FE、NE、RX/TX DMA TE/DME/FE 错误恢复；
- 2 字节 DMA 的 HT/TC 同时挂起、slot/代数错乱、时间戳丢失和事件覆盖均失败封闭；
- 大环形 DMA 的 NDTR 快照抖动、producer 回绕、探针队列满、IDLE 清标志并发、generation 失配均失败封闭；
- 完成槽已满、旧 TIM5 ISR 延迟、接收事件与闭帧/探针同时挂起；
- `RX_EMPTY/RX_VALID/RX_DISCARD` 全部状态转移；
- 广播读、支持的广播写、不支持的广播和异常广播均不生成响应。

### 15.2 字节间隔注入矩阵

测试工具必须能够在一帧指定字节之间插入精确间隔，不能只依赖普通 PC 串口一次性发送。表中“间隔”均指前一字符停止位结束到后一字符起始位开始的线上静默，而不是两个软件接收事件之差。

| 注入间隔 | 期望行为 |
| --- | --- |
| 连续发送、无额外间隔 | 完整接收并正常响应 |
| 0.5T、0.9T | 完整接收并正常响应 |
| `t1.5 - Δ`，低速参考 1.49T | 当前字符虽然在 t1.5 后才完成，仍并入同一帧并只响应一次 |
| `t1.5 + Δ` 且 `< t3.5` | 前后数据属于同一无效流，整帧丢弃，无写副作用、无响应 |
| 下一字符在 `t3.5 - Δ` 开始、在 t3.5 后完成 | 不得在 `last_end + t3.5` 提前闭帧；整流判无效 |
| 下一字符在 `t3.5 + Δ` 开始 | 旧帧结束，当前字符完整保留为新帧 byte0，不被吞并 |
| 最后字符后始终静默 | frame-ready 不早于 `last_end + t3.5 + Tchar`；逐字节事件路线还应包含 guard，双探针路线记录软件锚点延迟 |
| TIM5 ISR 故意延后到下一合法首字节事件之后 | 接收路径先保护旧帧边界和新 byte0，不由过期事件覆盖 |

高波特率必须按 750 us/1750 us 注入，不用 1.5/3.5 个 115200 字符的数学值代替。逐字节事件路线先测得相邻事件时间戳的最大差分抖动 `J`，边界偏移 `Δ` 必须大于 `2J + 2 个 TIM5 tick`；双探针路线的 `Δ` 还必须覆盖 IDLE ISR 最坏延迟和 DMA producer 提交不确定度。精确等号只做记录，不作为稳定接受/拒绝断言。

## 16. 验收标准

必须同时满足以下条件才能判定闭环：

1. 每个有效 Modbus RX 口的数据寄存器只有一个拥有者，运行期配置与冻结路线一致；第一次 IDLE 不直接提交帧，TX DMA 保持正常。
2. 低速端口按实际字符时间计算 t1.5/t3.5，高速端口使用 750 us/1750 us；逐字节完成事件门限或 IDLE 双探针均额外覆盖一个 `Tchar` 的接收观察时间。
3. `t1.5-Δ` 合法间隔全部接收，`t1.5+Δ～t3.5-Δ` 整流全部丢弃且无业务副作用。
4. `t3.5-Δ` 起始、t3.5 后完成的字符不会触发提前闭帧；`t3.5+Δ` 后的新帧 byte0 不丢失、不并入旧帧。
5. 无后续字符的 frame-ready 不早于 `last_end + t3.5 + Tchar`；逐字节事件路线包含经测量的 guard，双探针路线记录并约束软件锚点延迟；请求结束到响应首字节不小于 t3.5。
6. 生产缓冲与完成帧槽分离，generation、队列满、旧比较事件和 ISR 竞态均不会覆盖或重复发布帧。
7. CPU3 内部事务为非阻塞状态机；CPU2 超时、重试期间三路外部 COM 不被 1000 ms 同步等待饿死。
8. CPU2/CPU3 新/新组合严格验收通过；新旧混装完成风险定性和升级流程验证，不把非严格兼容模式计作合规。
9. DSM、Wartsila、SI 既有功能码、地址、缩放和异常响应回归通过；广播地址 0 永不产生响应。
10. CPU3 动态串口配置和 FRAM 重启后时序计算一致，所有重配/恢复路径保持冻结路线，不恢复旧的“第一次 IDLE 停 DMA 判帧”实现。
11. 最坏接收事件服务延迟小于最短字符周期且保留至少 50% 裕量；逐字节路线的边界 Δ 大于 `2J+2 tick`，双探针路线的 Δ 还覆盖 IDLE ISR 和 producer 不确定度。
12. 方案 D 不出现未处理的 HT/TC 合并、slot 覆盖或时间戳丢失；方案 E 不出现未处理的 probe 队列满、producer 回绕歧义或边界保守区误接受；所有不可信状态均失败封闭且无写副作用。
13. 双 CPU `--clean-first` 构建通过，无新增编译警告。
14. 24 小时/百万帧压力测试无新增看门狗复位、持续 ORE、DMA 事件歧义、探针耗尽、队列覆盖或通信状态机锁死。
15. 代码、流程文档、版本资料、成对升级/回滚方案和现场测试记录一致。

## 17. 协议、版本和文档影响

### 17.1 当前文档改动

本次只新增并整理分析方案、候选 DMA 路线和索引状态，不改变固件输出，因此：

### 17.2 后续时序代码落地

如果后续把内部 UART5 从 8N1 改为 8N2：

- CPU2/CPU3 必须原子升级或设计双格式迁移机制；
- `DEVICE_PROTOCOL_VERSION` 需要重点评估并更新协议变更记录；
- 协议版本本身无法在物理串口不匹配时完成在线协商，现场升级顺序必须独立设计。

## 18. 风险和回滚方案

| 风险 | 预防措施 | 回滚触发条件 |
| --- | --- | --- |
| TIM5 新资源配置错误 | 同步 `.ioc`/生成代码，复核 PSC=74/89、ARR、NVIC、ADC/DAC 触发和历史分支 | 出现定时漂移、外设触发或中断回归 |
| 逐字节接收事件负载导致 ORE/覆盖 | ISR 只做固定时间操作，接收事件优先于 TIM5，测最坏服务延迟和四口负载 | 出现持续 ORE、HT/TC 歧义、看门狗复位或最短字符周期裕量不足 |
| 2 字节 DMA 的 HT/TC 合并或时间戳丢失 | 50% 字符周期裕量、轻量 DMA ISR、事件代数校验、不可信即失败封闭 | `rx_dma_event_ambiguous_count` 持续增加或合法满载流无法稳定接收 |
| 大环 DMA 的 IDLE 锚点过晚或探针耗尽 | 测最坏 IDLE 延迟、绝对 producer、静态队列容量证明、边界保守区失败封闭 | 边界误接受、probe 队列满、producer 回绕不可证明或 IDLE 延迟超预算 |
| 时间戳/producer 抖动导致边界误判 | 记录差分抖动 J、IDLE 延迟和 DMA 提交不确定度，按路线确定 Δ 并限制长临界区 | 合法边界被拒绝或非法边界被稳定接受 |
| 安全闭帧额外 Tchar 增加响应延迟 | 按最慢 Wartsila 实测主站超时，记录解析和调度预算 | 厂商主站合法请求无响应率上升 |
| 完成帧槽满或 generation 竞态 | 双槽/固定队列、原子发布、槽满丢弃计数、延迟 ISR 测试 | 出现帧覆盖、重复响应或新 byte0 丢失 |
| CPU2 处理移出 ISR 后服务不足 | 长流程增加有界服务点或状态机化，规定最大服务间隔 | 内部响应接近/超过 1000 ms或测量期间频繁超时 |
| CPU3 非阻塞迁移状态遗漏 | 事务事件表、错误注入、批量游标和队列压力测试 | 外部主站出现新增响应超时或内部事务永久挂起 |
| 新旧版本严格时序不兼容 | 成对升级/回滚；需要时使用有截止版本的内部兼容模式 | 分步升级后内部通信中断或早时序计数持续增加 |
| 厂商主站不接受更晚响应 | 在各现场主站上先做兼容验证 | DSM/Wartsila/SI 合法请求无响应率明显上升 |
| 广播语义收敛改变旧集成行为 | 与 PLC/厂商确认广播使用方式，专项验证广播写副作用 | 现场明确依赖非标准广播回包且未完成改造 |
| 动态配置后 timing 仍用旧值 | 重配原子化并用契约脚本校验 | 重启或切换协议后出现随机拆帧 |
| pending 行为改变导致丢请求 | 统计 busy/drop，按一请求一响应回归 | 高负载下响应数量与合法请求数量不一致 |

建议实现时提供按端口的编译期开关，但正式版本必须明确启用状态，不能让现场菜单随意退回旧的 1T 判帧。各阶段使用独立提交，CPU2/CPU3 正式包成对升级和成对回滚。推荐方案不改变 FRAM 结构、寄存器和串口格式，回滚旧固件不应触发参数恢复出厂；回滚前仍须停止事务并确认总线静默。

## 20. 恢复实施条件和后续步骤

当前不执行下列步骤。重新启动本问题时，应按顺序恢复，不能直接跳到全端口代码改造：

1. 确认启动原因、目标合规等级、现场主从设备、允许的响应延迟和是否强制保留 RX DMA。
2. 使用逻辑分析仪完成四类默认 Profile 的整改前基线抓取，并保留原始波形和配置。
3. 冻结 TIM5、NVIC、接收后端、ISR/探针预算、帧槽容量和成对升级策略；若保留 DMA，先原型验证 2 字节循环 DMA 的四口最坏负载。
4. 先实现独立 timing 计算和纯 C 状态机测试：方案 D/F 验证逐字节完成时间分类与 generation，方案 E 验证绝对 producer、双探针、回绕和静态队列。
5. 双端接入 CPU2↔CPU3 UART5，完成 TC 门禁、安全闭帧/双探针和新/新严格验证；新旧组合只做风险定性。
6. 将 CPU3 UART5 同步等待改成非阻塞事务 FSM 和批量游标。
7. 再按 Wartsila、DSM、SI 顺序接入三路外部 COM，并统一广播和动态重配；低速 Wartsila 的闭帧与响应延迟最大，应优先暴露超时预算问题。
8. 完成 CPU2 协议处理 ISR 解耦和长流程有界通信服务。
9. 全部验收通过后统一升版、更新流程 HTML/SVG、协议资料、`CHANGELOG.md` 和版本测试方案。
