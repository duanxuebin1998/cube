# CPU2 全局错误报警响应滞后问题分析

更新时间：2026-06-29

范围：CPU2 `g_measurement.device_status.error_code`、主循环调度、测量命令入口、长循环测量流程、故障恢复流程，以及 CPU3 通过 Modbus 读取的状态上报。

结论：当前代码确实存在“全局错误已经产生，但测量流程仍继续执行或错误被后续流程清掉”的路径。问题不是单点函数错误，而是 `error_code` 同时承担全局故障锁存、后台诊断状态、当前命令返回值和 UI 上报字段，导致部分路径只在固定检查点响应，部分路径又会在命令开始或降级逻辑中主动清错。

## 1. 背景与关注点

现场关注的是全局错误报警不能及时响应，表现为已经出现错误后，CPU2 仍继续执行测量过程，CPU3 或上位机未能及时看到错误状态。

本次检查重点不是确认某一个错误码是否真实产生，而是确认以下机制性风险：

| 检查项 | 结论 |
| --- | --- |
| 后台检测置错后，主循环是否一定先处理错误 | 不一定。命令分支优先于空闲全局错误兜底。 |
| 命令启动时是否会保留已有全局错误 | 不一定。`MeasureStart()` 和 `fault_info_init()` 会清 `error_code`。 |
| 测量长循环是否持续检查全局错误 | 不完整。很多路径只检查命令切换或局部返回值。 |
| 自动恢复是否能弥补命令运行中的未响应 | 不能。自动恢复主要在命令返回后接管。 |
| CPU3 是否能看到被清掉的错误 | 不能。Modbus 只上报 CPU2 当前保留的 `error_code`。 |

## 2. 当前全局错误响应链路

### 2.1 全局错误字段

CPU2 的主要全局错误字段为：

- `g_measurement.device_status.error_code`
- `g_measurement.device_status.device_state`
- `g_measurement.device_status.current_command`

典型错误生产点包括：

| 模块 | 代码位置 | 行为 |
| --- | --- | --- |
| 扭力通信 | `LTD_MAIN_CPU2/Services/Weight/weight.c:120-149` | 超过 `WEIGHT_COMM_TIMEOUT_MS` 后写入 `WEIGHT_COMM_TIMEOUT`。 |
| 编码器 | `LTD_MAIN_CPU2/Services/Encoder/encoder.c:165-185` | 上电失败、通信超时或 ready 检查失败时写入编码器错误。 |
| AS5145 | `LTD_MAIN_CPU2/BSP/Peripherals/src/AS5145.c:256-260` | SSI 错误达到阈值后，非电机位置源模式下写入编码器错误。 |
| 传感器识别 | `LTD_MAIN_CPU2/Services/Sensor/sensor.c:64-69` | 非 `NO_ERROR`、非 `STATE_SWITCH` 的识别错误写入全局错误。 |
| 参数存储 | `LTD_MAIN_CPU2/Services/ParamStorage/system_parameter.c:726,825,844,904` | 地址越界或 EEPROM 失败时写入参数错误。 |
| AO 定时刷新 | `LTD_MAIN_CPU2/Services/AoOutput/ao_output.c:688-691` | 定时刷新失败且当前无错时写入 AO 错误。 |

典型清错点包括：

| 模块 | 代码位置 | 行为 |
| --- | --- | --- |
| 测量启动 | `LTD_MAIN_CPU2/Application/Src/measure.c:447,455` | `MeasureStart()` 调用 `fault_info_init()`，随后再次清 `error_code`。 |
| 故障初始化 | `LTD_MAIN_CPU2/Application/Src/fault_manager.c:247-249` | `fault_info_init()` 慢停电机并清 `error_code`。 |
| 空闲兜底 | `LTD_MAIN_CPU2/Application/Src/app_main.c:63-65` | 电机位置源下将编码器相关错误视为可忽略并清除。 |
| 扭力恢复 | `LTD_MAIN_CPU2/Services/Weight/weight.c:95-107` | 收到新帧且当前是扭力通信错误时清错。 |
| AS5145 恢复 | `LTD_MAIN_CPU2/BSP/Peripherals/src/AS5145.c:143-146` | 有效采样恢复后清编码器错误。 |
| 罐底回退 | `LTD_MAIN_CPU2/Application/Src/measure.c:619-666` | `CMD_MeasureBottom` 特定回退条件下清错并使用回退高度。 |
| 密度原型监测 | `LTD_MAIN_CPU2/Application/Src/measure_density.c:213-221` | 原型监测循环内清 `error_code`。 |

### 2.2 主循环调度顺序

`LTD_MAIN_CPU2/Application/Src/app_main.c` 的主循环顺序是本问题的核心证据之一：

1. 先执行后台检查：`MotorCtrl_PollRuntimePosition()`、`Weight_CheckCommunicationTimeout()`、`HostCommu_ProcessDeferredLogs()`。
2. 如果有串口新命令，先处理串口命令。
3. 如果 `g_deviceParams.command != CMD_NONE`，立即执行测量命令。
4. 否则才轮询自动恢复。
5. 最后才调用 `App_HandleIdleGlobalError()` 处理空闲态全局错误。

对应代码：

- `LTD_MAIN_CPU2/Application/Src/app_main.c:182-184`：后台位置和扭力通信检查。
- `LTD_MAIN_CPU2/Application/Src/app_main.c:197-203`：命令不为空时直接执行 `App_ExecuteMeasureCommand(command)`。
- `LTD_MAIN_CPU2/Application/Src/app_main.c:208-222`：命令为空时才进入自动恢复和空闲全局错误兜底。

这意味着：如果后台检查刚刚写入 `error_code`，但同一轮主循环里已有待执行命令，代码会先进入测量命令分支，而不是先进入全局错误处理分支。

### 2.3 `CHECK_ERROR` 和 `SET_ERROR` 的语义

`LTD_MAIN_CPU2/Application/Inc/fault_manager.h:122-147` 的 `CHECK_ERROR(errorcode)` 设计上会检查两类错误：

- 局部返回值 `errorcode != NO_ERROR`；
- 全局 `g_measurement.device_status.error_code != NO_ERROR`。

`LTD_MAIN_CPU2/Application/Inc/fault_manager.h:169-179` 的 `SET_ERROR(errorcode)` 用于在 `void` 命令函数里设置错误状态。

这套宏本身能处理全局错误，但它只有在流程实际调用时才生效。当前风险来自以下情况：

- 长循环只调用 `HasEffectiveCommandSwitchRequest()` 或 `CHECK_COMMAND_SWITCH()`，没有调用 `CHECK_ERROR()`。
- 长延时使用 `AbortableDelay_CommandSwitch()`，该工具只检查命令切换。
- 命令入口 `MeasureStart()` 在流程早期清掉了已存在的全局错误。

### 2.4 自动恢复接管时机

`App_ExecuteMeasureCommand()` 在 `ProcessMeasureCmd(command)` 返回后才调用 `FaultRecovery_UpdateAfterCommand(command)`：

- `LTD_MAIN_CPU2/Application/Src/app_main.c:38-48`
- `LTD_MAIN_CPU2/Application/Src/fault_recovery.c:290-327`

`FaultRecovery_Poll()` 会恢复错误状态、检查传感器和电机状态，并在成功后通知主循环重试命令：

- `LTD_MAIN_CPU2/Application/Src/fault_recovery.c:361-457`

因此自动恢复只能处理“命令已经返回并保留了错误码”的情况。如果命令内部长时间不返回，或者错误被 `MeasureStart()`、回退逻辑、恢复逻辑提前清掉，自动恢复无法及时介入。

### 2.5 CPU3 状态上报

CPU2 通过输入寄存器把状态写给 CPU3：

- `LTD_MAIN_CPU2/Services/Modbus/dataanalysis_modbus.c:500-504`

其中 `REG_DEVICE_STATUS_ERROR_CODE` 直接取自 `g_measurement.device_status.error_code`。因此 CPU3 看到的是 CPU2 当前保留的错误码，不具备追溯能力。只要 CPU2 在 CPU3 轮询前清掉错误，CPU3 就可能看不到本次报警。

## 3. 已确认的高风险路径

### 3.1 后台置错后，命令优先执行并被测量启动清掉

这是最明确的“报错后还在执行测量过程”路径。

复现逻辑：

1. 主循环开始。
2. `Weight_CheckCommunicationTimeout()` 检测扭力通信超时，写入 `WEIGHT_COMM_TIMEOUT`。
3. 当前 `g_deviceParams.command` 非空。
4. 主循环优先进入 `App_ExecuteMeasureCommand()`。
5. `ProcessMeasureCmd()` 调用 `MeasureStart()`。
6. `MeasureStart()` 调用 `fault_info_init()` 并清 `error_code`。
7. 命令继续执行，空闲全局错误兜底没有机会处理刚才的错误。

关键代码：

- `LTD_MAIN_CPU2/Application/Src/app_main.c:182-203`
- `LTD_MAIN_CPU2/Application/Src/measure.c:92-108`
- `LTD_MAIN_CPU2/Application/Src/measure.c:446-455`
- `LTD_MAIN_CPU2/Application/Src/fault_manager.c:247-249`

影响：后台错误可能短暂存在，但在测量启动阶段被清掉，导致报警不稳定、CPU3 上报缺失、自动恢复无法启动。

### 3.2 长循环和长延时只响应命令切换

`LTD_MAIN_CPU2/Services/Utilities/abortable_delay.c:13-33` 的 `AbortableDelay_CommandSwitch()` 只检查命令切换：

- 分片 `HAL_Delay()`；
- 检查 `HasEffectiveCommandSwitchRequest()`；
- 返回 `STATE_SWITCH` 或 `NO_ERROR`；
- 不检查 `g_measurement.device_status.error_code`。

这会影响多个测量路径：

| 路径 | 代码位置 | 风险 |
| --- | --- | --- |
| 单点密度读取 | `LTD_MAIN_CPU2/Application/Src/measure_density.c:1223-1461` | 循环内主要检查命令切换和局部传感器返回值，全局错误不一定即时退出。 |
| 固定点监测 | `LTD_MAIN_CPU2/Application/Src/measure_density.c:1495-1544` | 外层无限循环依赖内部返回和 `SET_ERROR(ret)`，全局异步错误可能延迟到检查点。 |
| 密度法液位闭环 | `LTD_MAIN_CPU2/Application/Src/measure_oilLevel.c:363-470` | 闭环内存在 `AbortableDelay_CommandSwitch()`，主要响应命令切换。 |
| 频率法液位闭环 | `LTD_MAIN_CPU2/Application/Src/measure_oilLevel.c:675-775` | 同样依赖命令切换延时和局部返回值。 |
| 跟随液位稳定等待 | `LTD_MAIN_CPU2/Application/Src/measure_oilLevel.c:1118-1150` | 稳定等待阶段只用 `CHECK_COMMAND_SWITCH(ret)` 处理延时返回。 |
| 精找液位等待 | `LTD_MAIN_CPU2/Application/Src/measure_oilLevel.c:1410-1510` | 初始 2 秒等待只响应命令切换。 |
| 瓦锡兰密度测后等待 | `LTD_MAIN_CPU2/Application/Src/measure.c:1032-1123` | 测后 1 秒和多次 1 秒等待只响应命令切换。 |
| 维护模式 | `LTD_MAIN_CPU2/Application/Src/measure.c:807-824` | 维护模式无限循环只检查命令切换。 |

影响：如果 AO 定时刷新、扭力通信、参数存储或其他后台路径在长循环中置错，当前命令可能继续运行到下一个 `CHECK_ERROR()`、局部函数失败、命令切换，甚至流程自然结束后才处理。

### 3.3 命令内部存在主动清错或降级继续

除 `MeasureStart()` 外，部分业务路径会主动把错误降级为继续执行：

| 路径 | 代码位置 | 行为 |
| --- | --- | --- |
| `CMD_MeasureBottom` | `LTD_MAIN_CPU2/Application/Src/measure.c:619-666` | `SearchBottom()` 失败后，在特定回退条件下使用回退高度并清 `error_code`。 |
| `CMD_WartsilaDensitySpread` | `LTD_MAIN_CPU2/Application/Src/measure.c:1098-1114` | 部分非 `PARAM_RANGE_ERROR` 的后置移动或探底失败会切到 `CMD_MONITOR_SINGLE` 并返回，没有统一进入错误状态。 |
| 密度原型监测 | `LTD_MAIN_CPU2/Application/Src/measure_density.c:213-221` | 循环中清 `error_code`，会掩盖外部错误。 |

这些路径可能是出于现场容错设计，但如果用户期望“全局错误必须停测并报警”，则当前行为与期望不一致。尤其是 `error_stop_measurement` 默认值为 1 时，`CMD_MeasureBottom` 的回退清错语义需要重新确认：

- `LTD_MAIN_CPU2/Services/ParamStorage/system_parameter.c:933-934`
- `LTD_MAIN_CPU2/Services/ParamStorage/system_parameter.c:1499-1500`

### 3.4 编码器错误存在特殊忽略策略

编码器错误在电机位置源场景下有多个特殊清除或忽略点：

- `LTD_MAIN_CPU2/Application/Src/app_main.c:63-65`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_driver_param.c:202-208`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_position_model.c:481-482,647-648,1554-1555`
- `LTD_MAIN_CPU2/BSP/Peripherals/src/AS5145.c:258-260`

这类策略本身可能是合理的：当系统使用电机位置源时，编码器通信错误不一定应该阻塞测量。但它进一步说明 `error_code` 不是纯粹的锁存故障字段，而混入了“当前模式下是否需要报警”的策略判断。

## 4. 风险分级

| 等级 | 问题 | 风险说明 |
| --- | --- | --- |
| P0 | 主循环命令分支优先于空闲全局错误处理，且 `MeasureStart()` 清错 | 可直接导致后台已置错但测量继续执行，是当前最需要先修的路径。 |
| P1 | `AbortableDelay_CommandSwitch()` 和多个长循环只检查命令切换 | 会造成全局错误响应延迟，延迟时间取决于循环周期、传感器调用和流程自然结束点。 |
| P1 | 命令内部降级逻辑清错继续 | 可能导致“有错误但 UI 不报警”，需要明确哪些失败允许降级，哪些必须全局报警。 |
| P1 | 自动恢复只在命令返回后接管 | 若命令长期运行且未检查全局错误，恢复机制无法及时介入。 |
| P2 | 电机位置源下编码器错误特殊忽略 | 需要保留策略，但应写清适用范围，避免误判为报警丢失。 |
| P2 | 测试/原型路径直接清错 | 对正式流程影响较小，但会干扰问题复现和调试。 |

## 5. 整改建议

### 5.1 可行方案总览

当前问题可以按风险和收益拆成四类方案。推荐采用方案 B，先解决已确认的主路径，再补关键长循环，避免一次性重构 `error_code` 语义。

| 方案 | 改动范围 | 优点 | 风险和不足 | 建议结论 |
| --- | --- | --- | --- | --- |
| A. 最小热修 | 只改主循环命令前门禁和 `MeasureStart()` 清错边界 | 改动小，能直接堵住“后台置错后被命令启动清掉”的路径 | 长循环中的异步错误仍可能延迟响应 | 可作为第一阶段补丁 |
| B. 分阶段低风险整改 | 方案 A + 新增全局错误可中断延时 + 关键测量长循环补检查 | 覆盖本次发现的主要风险，基本不改变协议和 CPU3 寄存器 | 需要逐个回归密度、液位、瓦锡兰和探底流程 | 推荐采用 |
| C. 严格锁存整改 | 引入活动故障、警告、最近错误等分离字段 | 长期语义最清晰，CPU3 可追溯能力更好 | 可能涉及协议、显示、参数和兼容性，改动大 | 作为后续架构优化 |
| D. 只补日志和文档 | 增加日志说明，不改变停测逻辑 | 风险最低，便于现场追踪 | 不能解决测量继续执行的问题 | 不作为正式整改方案 |

### 5.2 方案 A：最小热修

目标：先解决最明确、最容易复现的路径，即“后台检测写入全局错误后，主循环仍先执行命令，随后 `MeasureStart()` 清错”。

改动点：

| 文件 | 建议改动 | 预期行为 |
| --- | --- | --- |
| `LTD_MAIN_CPU2/Application/Src/app_main.c` | 在后台检查之后、正式命令分支之前增加命令前全局错误门禁 | 如果已有阻塞型全局错误，不进入 `App_ExecuteMeasureCommand()`。 |
| `LTD_MAIN_CPU2/Application/Src/measure.c` | `MeasureStart()` 开头检查已有阻塞型全局错误 | 已有错误时直接返回该错误，不调用 `fault_info_init()` 清错。 |
| `LTD_MAIN_CPU2/Application/Src/fault_manager.c` / `fault_manager.h` | 增加一个统一判断函数，例如 `FaultManager_IsBlockingGlobalError(error_code)` | 避免每个模块重复写 `NO_ERROR`、`STATE_SWITCH`、编码器特殊忽略等判断。 |

命令前门禁建议语义：

```c
/* 伪代码：实际实现时函数名可按现有风格调整。 */
error_code = g_measurement.device_status.error_code;
if (FaultManager_IsBlockingGlobalError(error_code) != 0U) {
    FaultManager_SetGlobalErrorState(error_code,
                                     GetShortFilename(__FILE__),
                                     __LINE__,
                                     __func__);
    g_deviceParams.command = CMD_NONE;
    g_measurement.device_status.current_command = CMD_NONE;
    process_device_params_deferred_tasks();
    HAL_Delay(50);
    return;
}
```

`MeasureStart()` 建议语义：

```c
/* 伪代码：防止命令入口无条件清掉活动故障。 */
error_code = g_measurement.device_status.error_code;
if (FaultManager_IsBlockingGlobalError(error_code) != 0U) {
    return (int)error_code;
}

fault_info_init();
```

需要保留的例外：

- `NO_ERROR` 不阻塞。
- `STATE_SWITCH` 不作为故障阻塞。
- 电机位置源下明确允许忽略的编码器错误继续按当前策略处理，但建议集中到 `FaultManager_IsBlockingGlobalError()`，不要散落在多个业务函数里。

验证重点：

- 停止扭力通信，确认 `WEIGHT_COMM_TIMEOUT` 产生后再下发测量命令，命令不会进入 `MeasureStart()`。
- CPU3 读取 `REG_DEVICE_STATUS_ERROR_CODE` 能稳定看到错误码。
- 电机位置源下 AS5145 错误仍按预期忽略，不误阻塞。

适用判断：如果需要尽快阻止“报错后又开始新测量”，方案 A 可以先做；但它不能完全解决命令已经运行期间的异步错误延迟。

### 5.3 方案 B：推荐的分阶段低风险整改

建议优先做低侵入整改，先解决“错误被命令启动清掉”和“长循环不响应”的问题。

#### 阶段 1：统一全局错误阻塞判断

新增统一判断接口，供主循环、测量启动和长循环复用。

| 文件 | 建议接口 | 说明 |
| --- | --- | --- |
| `LTD_MAIN_CPU2/Application/Inc/fault_manager.h` | `uint8_t FaultManager_IsBlockingGlobalError(uint32_t error_code);` | 只判断错误码是否应阻塞。 |
| `LTD_MAIN_CPU2/Application/Inc/fault_manager.h` | `uint32_t FaultManager_CheckGlobalAbort(const char *file, uint32_t line, const char *func);` | 检查当前全局错误，必要时进入统一错误状态并返回错误码。 |
| `LTD_MAIN_CPU2/Application/Src/fault_manager.c` | 实现以上接口 | 统一编码器特殊忽略、`NO_ERROR`、`STATE_SWITCH` 和阻塞型错误规则。 |

接口行为建议：

- `NO_ERROR` 返回不阻塞。
- `STATE_SWITCH` 返回不阻塞。
- 电机位置源下编码器错误返回不阻塞，并按现有策略清除或保留 warning，具体由后续策略决定。
- 其他错误返回阻塞。
- `FaultManager_CheckGlobalAbort()` 只在阻塞时调用 `FaultManager_SetGlobalErrorState()`，避免重复错误出口。

#### 阶段 2：在主循环进入命令分支前增加门禁

   建议位置：`LTD_MAIN_CPU2/Application/Src/app_main.c`，后台检查之后、`g_deviceParams.command != CMD_NONE` 分支之前。

   行为建议：

   - 如果 `error_code == NO_ERROR` 或 `STATE_SWITCH`，继续原流程。
   - 如果是电机位置源下明确允许忽略的编码器错误，保留现有策略。
   - 其他全局错误应优先进入 `FaultManager_SetGlobalErrorState()` 或阻止命令启动。
   - 不应让新命令进入 `MeasureStart()` 后再清错。

#### 阶段 3：收紧 `MeasureStart()` 和 `fault_info_init()` 清错边界

   当前 `fault_info_init()` 同时做慢停和清全局错误。建议拆分为：

   - 清理本次测量临时状态；
   - 清理允许清除的历史故障；
   - 保留或拒绝清除当前活动全局故障。

   短期可以先在 `MeasureStart()` 开头判断已有全局错误：如果不是 `NO_ERROR`、不是 `STATE_SWITCH`，且不是当前模式明确允许忽略的错误，则直接返回该错误，不进入清错。

建议优先避免大范围改 `fault_info_init()`，因为它被找零点、找水位、找液位、罐高和油位流程复用。第一步只在 `MeasureStart()` 入口阻断活动故障；等验证稳定后，再把 `fault_info_init()` 拆成更清晰的两个函数。

#### 阶段 4：新增全局错误可中断延时工具

   不建议直接无差别修改 `AbortableDelay_CommandSwitch()` 的行为，因为它已被传感器切模式、重量稳定、瓦锡兰流程等多个模块复用，直接改变可能影响既有语义。

   建议新增：

   - `AbortableDelay_ErrorOrCommandSwitch(total_ms, step_ms)`；
   - 或 `FaultManager_CheckAbortCondition()` 统一检查命令切换和全局错误。

   先在测量主流程和长监测循环中替换，保留底层通信、初始化和恢复流程的原工具，降低误伤。

建议返回语义：

| 返回值 | 含义 | 调用方处理 |
| --- | --- | --- |
| `NO_ERROR` | 延时完成，未发现命令切换或全局错误 | 继续原流程 |
| `STATE_SWITCH` | 检测到有效命令切换 | 按现有命令切换路径退出 |
| 其他错误码 | 检测到阻塞型全局错误 | 走 `CHECK_ERROR(ret)` 或 `SET_ERROR(ret)` |

这样调用方不用额外读取全局变量，仍保持现有错误出口风格。

#### 阶段 5：补关键长循环检查点

   优先位置：

   - `measure_density.c`：`SinglePoint_ReadSensor()`、`CMD_SinglePointMonitoring()`、原型监测循环。
   - `measure_oilLevel.c`：密度法闭环、频率法闭环、跟随液位稳定等待、精找液位等待。
   - `measure.c`：维护模式、瓦锡兰密度测后等待。

   检查方式建议统一走 `CHECK_ERROR(NO_ERROR)` 或新增的 `FaultManager_CheckGlobalAbort()`，不要各函数自行读取并处理 `error_code`。

建议先覆盖以下点位：

| 文件 | 点位 | 建议 |
| --- | --- | --- |
| `LTD_MAIN_CPU2/Application/Src/measure_density.c` | `SinglePoint_ReadSensor()` while 循环开始处 | 每轮先检查命令切换，再检查全局错误。 |
| `LTD_MAIN_CPU2/Application/Src/measure_density.c` | `AbortableDelay_CommandSwitch(SAMPLE_INTERVAL_MS, ...)` | 替换为全局错误可中断延时。 |
| `LTD_MAIN_CPU2/Application/Src/measure_density.c` | `CMD_SinglePointMonitoring()` 外层循环 | 每轮进入采样前检查全局错误。 |
| `LTD_MAIN_CPU2/Application/Src/measure_oilLevel.c` | 密度法和频率法闭环 | 在每轮闭环开始和稳定等待处检查全局错误。 |
| `LTD_MAIN_CPU2/Application/Src/measure_oilLevel.c` | `FollowOilLevel()` 稳定等待 | 延时返回非 `STATE_SWITCH` 错误时走 `CHECK_ERROR(ret)`。 |
| `LTD_MAIN_CPU2/Application/Src/measure.c` | `CMD_WartsilaDensitySpread()` 测后等待 | 1 秒和 8 秒等待均可被全局错误打断。 |

#### 阶段 6：明确回退和继续监测策略

   对以下行为需要产品/现场策略确认后再改：

   - `CMD_MeasureBottom` 在 `error_stop_measurement == 1U` 时是否仍允许使用回退高度并清错。
   - `CMD_WartsilaDensitySpread` 后置探底失败时是否允许切到固定点监测继续运行。
   - 允许继续的失败是否应该进入“警告/最近错误”字段，而不是清 `error_code`。

阶段 6 可以放在主路径修复之后，因为它涉及产品策略；但文档和测试用例需要先把现有行为列出来，避免现场误认为所有错误都会停测。

### 5.4 方案 C：长期结构调整

当前 `error_code` 过载，建议逐步拆分：

| 字段 | 建议用途 |
| --- | --- |
| `active_fault_code` | 当前必须阻塞测量并报警的锁存故障。 |
| `warning_code` | 允许继续运行但需要提示的非阻塞告警。 |
| `last_error_code` | 最近一次错误，供日志、诊断和 CPU3 追溯。 |
| `recovering_error_code` | 自动恢复上下文中的原始故障。 |

这样可以避免“为了允许某个流程继续而清掉 UI 需要看到的错误”。

长期结构调整建议单独立项，不建议和方案 A/B 混在同一次提交里完成。原因是字段拆分可能影响：

- CPU2 内部状态结构；
- CPU3 Modbus 状态读取；
- CPU3 显示页面；
- 上位机或 SI 对错误码的理解；
- 历史参数和文档兼容性。

如果后续执行方案 C，建议先定义兼容策略：保留原 `REG_DEVICE_STATUS_ERROR_CODE` 为活动阻塞故障，同时新增或复用诊断寄存器表达 `warning_code` 和 `last_error_code`。

### 5.5 推荐落地顺序

| 顺序 | 目标 | 主要文件 | 验证 |
| --- | --- | --- | --- |
| 1 | 增加统一阻塞判断接口 | `fault_manager.h`、`fault_manager.c` | 单独编译 CPU2，人工构造 `NO_ERROR`、`STATE_SWITCH`、编码器错误、普通错误路径。 |
| 2 | 主循环命令前门禁 | `app_main.c` | 扭力通信超时后下发测量命令，确认命令不启动。 |
| 3 | `MeasureStart()` 清错边界 | `measure.c` | 已有全局错误时调用任意测量命令，确认不被清错。 |
| 4 | 新增可中断延时 | `abortable_delay.h`、`abortable_delay.c` | 命令切换返回 `STATE_SWITCH`，全局错误返回对应错误码。 |
| 5 | 覆盖关键长循环 | `measure_density.c`、`measure_oilLevel.c`、`measure.c` | 单点监测、液位闭环、瓦锡兰测后等待中注入错误，确认及时退出。 |
| 6 | 梳理降级策略 | `measure.c`、后续文档 | 探底失败、瓦锡兰后置探底失败按产品策略报警或降级。 |
| 7 | 更新流程图和版本资料 | `docs/00_程序流程导航/`、`CHANGELOG.md`、版本测试方案 | 仅在实际改源码、升版或提交发布时执行。 |

### 5.6 不建议的做法

| 做法 | 原因 |
| --- | --- |
| 只在 CPU3 端增加报警判断 | CPU3 只能看到 CPU2 当前寄存器值，CPU2 已清错时无法恢复真相。 |
| 只增加更多日志 | 日志能帮助追踪，但不能阻止测量继续执行。 |
| 全局搜索后把所有 `HAL_Delay()` 都替换掉 | 影响范围过大，容易破坏通信时序和初始化时序。 |
| 直接禁止所有清 `error_code` | 扭力恢复、编码器模式切换、自动恢复成功等场景需要合法清错。 |

## 6. 验证方案

建议先做针对性台架验证，再做完整回归。

| 编号 | 场景 | 注入方式 | 期望结果 |
| --- | --- | --- | --- |
| V1 | 命令启动前已有扭力通信超时 | 停止扭力帧，等待 `Weight_CheckCommunicationTimeout()` 置错，再下发测量命令 | 命令不应进入测量启动，CPU3 可读到 `WEIGHT_COMM_TIMEOUT`，设备进入错误态或恢复态。 |
| V2 | 测量命令内部出现 AO 刷新错误 | 在单点监测或液位闭环中模拟 `AoOutput_ProcessPendingTimerRefresh()` 返回错误 | 测量循环应在一个检查周期内退出，错误码保留到 CPU3 可读。 |
| V3 | 长延时中出现全局错误 | 在瓦锡兰测后等待或跟随液位稳定等待期间注入非 `STATE_SWITCH` 错误 | 延时应被全局错误打断，而不是等待自然结束。 |
| V4 | 电机位置源下编码器错误 | 切换到电机位置源后制造 AS5145 通信错误 | 若该策略仍保留，应确认错误被忽略是预期行为，并有日志或文档说明。 |
| V5 | `CMD_MeasureBottom` 探底失败 | 构造 `SearchBottom()` 返回错误，且回退高度满足条件 | 根据最终策略确认：要么停止报警并保留错误，要么降级继续但写入非阻塞告警。 |
| V6 | 自动恢复链路 | 制造可恢复错误并等待命令返回 | `FaultRecovery_UpdateAfterCommand()` 应启动恢复，恢复期间 CPU3 可读到原始错误，恢复成功后清错并重试。 |

## 7. 建议修改优先级

1. 先修 `App_MainLoop()` 的命令前全局错误门禁，防止错误被 `MeasureStart()` 清掉。
2. 再修 `MeasureStart()` / `fault_info_init()` 清错边界，避免命令入口无条件清活动故障。
3. 新增“全局错误或命令切换均可打断”的延时/轮询工具，并替换测量长循环关键点。
4. 明确 `CMD_MeasureBottom` 和 `CMD_WartsilaDensitySpread` 的降级策略。
5. 最后再考虑拆分 `error_code` 字段，降低长期维护风险。

## 8. 待确认事项

| 问题 | 需要确认的决策 |
| --- | --- |
| 扭力通信超时是否必须立即停止所有测量 | 如果是，需把它纳入命令前门禁和长循环中断条件。 |
| AO 输出刷新失败是否属于阻塞故障 | 如果现场要求报警输出可信，则应阻塞当前测量并报警。 |
| 电机位置源下编码器错误是否完全忽略 | 若只是“不阻塞测量”，仍建议记录为 warning 或 last error。 |
| 探底失败使用回退高度是否允许清错 | 若允许，建议不要清锁存错误，而是使用单独的非阻塞告警字段表达降级。 |
| 维护模式是否要响应全局错误 | 如果维护模式用于现场调试，可保留命令切换退出；如果用于正式运行，应补全全局错误退出。 |

## 9. 本次检查结论

全局错误响应滞后的问题在当前 CPU2 代码中具有明确可达路径，尤其是“后台置错 -> 主循环优先执行命令 -> `MeasureStart()` 清错 -> 测量继续执行”这一链路。仅依赖现有 `CHECK_ERROR()` 和自动恢复机制不足以保证及时报警，因为它们分别受调用位置和命令返回时机限制。

建议下一步先按最小整改方案改 CPU2 主循环门禁和测量启动清错边界，再对密度监测、液位闭环、瓦锡兰测后等待等长流程补全全局错误中断点。整改后必须用扭力通信超时、AO 刷新失败、编码器错误、探底失败四类场景做台架验证，并确认 CPU3 寄存器读数能稳定观察到错误码。
