# CPU3 长按确认不灵敏问题分析与整改方案

更新日期：2026-06-11

## 1. 问题背景

现场现象：状态页长按确认键进入配置菜单不够灵敏，有时需要按很久，有时按住确认过程中误触其他按键会影响进入菜单。

本次分析范围为 CPU3 显示端按键输入、长按检测、菜单入口和主循环处理链路。当前已按“1.5 秒长按 + 50ms 消抖 + 目标锁定 + 释放保护”方案完成代码落地，仍需上板验证实际手感和抗干扰效果。

## 2. 当前代码链路

### 2.1 按键硬件输入

按键在 `LTD_DISPLAY_CPU3/Core/Src/gpio.c` 中配置为下降沿外部中断：

| 按键 | 引脚 | 中断 | 配置 |
| --- | --- | --- | --- |
| 下 | `PF1` | `EXTI1_IRQn` | `GPIO_MODE_IT_FALLING` |
| 确认 | `PF2` | `EXTI2_IRQn` | `GPIO_MODE_IT_FALLING` |
| 返回 | `PF3` | `EXTI3_IRQn` | `GPIO_MODE_IT_FALLING` |
| 上 | `PF4` | `EXTI4_IRQn` | `GPIO_MODE_IT_FALLING` |

当前 GPIO 配置为 `GPIO_NOPULL`。这意味着按键空闲态是否稳定完全依赖外部硬件上拉或下拉。如果硬件上拉偏弱、线缆长、面板按键抖动明显或有静电干扰，就容易出现误下降沿。

### 2.2 状态页按键进入长按检测

`LTD_DISPLAY_CPU3/Application/display/exit.c` 的 `HAL_GPIO_EXTI_Callback()` 中：

- 状态页下 `FlagofTankOpera == false`。
- 按下确认键时，清零 `button_press_counter`，设置 `button_long_press_key = LONG_PRESS_KEY_SURE`，启动 TIM1。
- 按下返回键时，同样清零 `button_press_counter`，设置 `button_long_press_key = LONG_PRESS_KEY_BACK`，启动 TIM1。
- 状态页下 `UP/DOWN` 不进入普通按键队列。

这说明当前长按检测只有一组全局状态：

```c
button_press_counter
button_long_press_key
```

所以状态页下确认长按和返回长按不能并行识别。任何新的确认/返回下降沿都会重置计数并覆盖当前长按目标。

### 2.3 TIM1 长按采样

TIM1 在 `LTD_DISPLAY_CPU3/Core/Src/tim.c` 中配置：

```c
htim1.Init.Prescaler = 17999;
htim1.Init.Period = 1000;
```

系统时钟配置为：

- `SYSCLK = 180 MHz`
- `APB2 = 90 MHz`
- `APB2TimFreq = 180 MHz`

TIM1 属于 APB2 定时器，因此 TIM1 输入时钟为 `180 MHz`。

实际采样周期计算：

```text
TIM1 counter clock = 180 MHz / (17999 + 1) = 10 kHz
TIM1 update period = (1000 + 1) / 10 kHz = 100.1 ms
REQUIRED_PRESS_COUNT = 30
触发长按时间约 = 100.1 ms * 30 = 3003 ms
```

结论：当前确认长按不是 1 秒左右，而是约 3 秒。这个时间本身就会让用户感觉不灵敏。

另外，`KEY_SURE` 入口处原来有一行重置计数器的代码被注释：

```c
// __HAL_TIM_SET_COUNTER(&htim1, 0);
```

现在启动 TIM1 时没有明确清零 `CNT`。`HAL_TIM_Base_Stop_IT()` 停止定时器不会保证计数器归零，所以第一次采样可能在 0 到 100 ms 之间浮动。这不是主要问题，但会造成长按触发时间有轻微不一致。

### 2.4 长按成立后的菜单入口

TIM1 中断确认连续按下达到阈值后，会调用：

```c
Display_RequestLongPressAction(long_press_key);
```

这个函数只设置待处理标志，不直接绘屏。真正进入菜单入口在主循环的 `Display_Task()`：

```c
Display_ProcessPendingInput();
```

`Display_ProcessPendingInput()` 会先处理长按动作，再处理普通按键队列。确认长按动作对应：

```c
FlagofTankOpera = true;
useKey();
keymenu[KEYNUM_IF_ENTER_MAINMENU].execute_opera();
```

也就是说，当前流程不是“长按确认直接进入主菜单”，而是进入一个二次确认页：

```text
是否进入罐上操作?
返回                         确认
```

这个确认页的按键权限是 `BACK` 和 `SURE`。如果进入确认页后又收到确认键普通按键，会进入主菜单；如果收到返回键普通按键，会退出罐上操作。

## 3. 根因分析

### 3.1 长按阈值实际为约 3 秒

这是最直接的体感原因。`REQUIRED_PRESS_COUNT = 30` 配合约 100 ms 定时周期，实际要求连续稳定按住约 3 秒。

源码注释写的是：

```c
#define REQUIRED_PRESS_COUNT 30  // 需要连续按下3次才触发
```

注释和实际值不一致。实际不是 3 次，而是 30 次；实际效果是约 3 秒。

如果产品定义就是“长按 3 秒”，那当前程序基本符合这个定义；如果现场期望是 1 到 1.5 秒进入配置，则当前参数过严。

### 3.2 确认键抖动会反复重置计数

当前 EXTI 回调没有软件消抖。确认键每次下降沿都会执行：

```c
button_press_counter = 0;
button_long_press_key = LONG_PRESS_KEY_SURE;
HAL_TIM_Base_Start_IT(&htim1);
```

如果确认键触点抖动、线缆干扰或静电影响导致按住期间出现新的下降沿，计数会被重新清零。表面现象就是用户已经按了很久，但程序内部计时多次重启，导致长按不触发。

这是“长按确认不灵敏”的高概率根因之一，尤其适用于机械按键、面板线较长、现场干扰较强的环境。

### 3.3 返回键误触会覆盖确认长按目标

状态页下返回键也使用同一组长按状态。按住确认时，如果返回键发生误触或干扰下降沿，会执行：

```c
button_press_counter = 0;
button_long_press_key = LONG_PRESS_KEY_BACK;
```

结果是确认长按被打断，后续 TIM1 开始检测返回键是否仍被按住。用户看到的现象可能是：

- 按确认没有进入菜单。
- 需要重新长按。
- 如果返回键误触持续成立，可能进入取消测量确认或故障原因页。

这说明当前设计没有“长按目标锁定”。长按确认开始后，其他键仍然可以覆盖目标键。

### 3.4 进入确认页后残留按键可能立刻生效

`Display_ProcessPendingInput()` 的处理顺序是：

1. 取出并处理长按动作。
2. 继续取普通按键队列。

因此长按确认触发后，程序会先显示“是否进入罐上操作?”，然后同一轮主循环继续处理已经排队或刚刚进来的普通按键。

如果此时因为按键抖动、误触或用户还在按确认键造成 `SURE` 普通按键入队，则会直接确认进入主菜单；如果是 `BACK` 入队，则会直接退出确认页。

这不是“不灵敏”的根因，但会造成入口行为不稳定：有时刚出现确认页就跳转，有时刚出现确认页又退出。

### 3.5 GPIO 无内部上拉，抗干扰依赖硬件

按键 GPIO 当前为 `GPIO_NOPULL`。如果外部电路已经提供可靠上拉，这没有问题；如果外部上拉弱、按键线悬空风险较高或静电干扰明显，下降沿误触发概率会上升。

因为当前 EXTI 只看下降沿，一次错误下降沿就可能：

- 重置确认长按计数。
- 覆盖成长按返回。
- 在菜单确认页产生普通按键误操作。

需要结合原理图和实测波形确认按键线空闲态是否稳定。

### 3.6 主循环调度不是主要问题，但会带来入口延迟

长按成立后，TIM1 中断只设置待处理标志，真正显示确认页要等 `App_MainLoop()` 调用 `Display_Task()`。

主循环空闲时有 `HAL_Delay(10)`，正常情况下这只带来约 10 ms 量级延迟。串口协议处理或显示绘制较忙时，确认页出现会延后，但通常不应造成几秒级不灵敏。

如果现场表现是“已经长按 3 秒以上，松手后过一会儿才出现确认页”，才需要进一步检查主循环是否有长时间阻塞。

## 4. 现象和根因对应表

| 现场现象 | 高概率原因 | 代码依据 |
| --- | --- | --- |
| 必须按很久才出现菜单入口 | 长按阈值实际约 3 秒 | TIM1 约 100 ms 周期，`REQUIRED_PRESS_COUNT = 30` |
| 有时按了 3 秒仍不触发 | 确认键抖动反复清零计数 | 确认键每个下降沿都清零 `button_press_counter` |
| 按确认时碰到返回后进不去 | 返回键覆盖长按目标 | 返回键也会设置 `button_long_press_key` 并清零计数 |
| 刚出现确认页就自动进入主菜单 | 确认键残留下降沿或抖动被当成普通确认 | 长按动作后继续处理普通按键队列 |
| 刚出现确认页又退出 | 返回键残留按键被确认页处理 | 确认页允许 `BACK` |
| 不同机器灵敏度差异明显 | 按键硬件上拉、触点抖动、线束干扰差异 | GPIO 配置为 `GPIO_NOPULL`，无软件消抖 |

## 5. 建议整改方案

### 5.1 第一阶段：最小改动，先解决不灵敏和误触

建议优先做以下改动：

1. 明确长按时间目标。

本次确定目标为约 1.5 秒触发，`REQUIRED_PRESS_COUNT` 设置为 `15`。如果仍要 3 秒，则至少修正注释，避免误判；如果后续希望更快，可再评估是否降到 `12`。

2. 启动长按检测时清零 TIM1 计数器。

   在启动 TIM1 前执行：

   ```c
   __HAL_TIM_SET_COUNTER(&htim1, 0);
   __HAL_TIM_CLEAR_FLAG(&htim1, TIM_FLAG_UPDATE);
   HAL_TIM_Base_Start_IT(&htim1);
   ```

   这样第一次采样时间固定，长按体感更一致。

3. 增加长按目标锁定。

   当 `button_long_press_key != LONG_PRESS_KEY_NONE` 时，状态页新的确认/返回下降沿不应覆盖当前目标键。特别是确认长按已开始时，返回键误触不应打断确认长按。

   但要允许一种例外：如果旧目标键已经释放，只是 TIM1 还没来得及采样并清掉 `button_long_press_key`，新的确认/返回下降沿应先清理旧目标再接管长按检测。否则用户先短按其它键、马上长按确认时，确认键下降沿会被旧锁吞掉，后续按住确认也不会再产生新的启动沿。

4. 增加按键消抖门限。

   每个键记录最近一次下降沿时间，低于 30 到 50 ms 的重复下降沿直接忽略。这样可以防止同一个按键抖动反复清零计数。

5. 长按触发后清空普通按键队列，并进入释放保护。

   确认长按触发并显示“是否进入罐上操作?”后，应先等待确认键释放，再允许新的 `SURE/BACK` 普通按键生效。这样可以避免抖动导致确认页自动确认或自动退出。

这一阶段改动范围集中在 `exit.c`、`exit.h`、`stm32f4xx_it.c` 和 `display.c` 的按键处理链路，不涉及 CPU2 协议和参数存储。已新增 `tools/check_cpu3_long_press_entry.py` 用于提交前检查关键约束。

### 5.2 第二阶段：把按键处理收敛成状态机

如果现场按键干扰比较严重，建议不要继续依赖“EXTI 触发后 TIM1 采样”的零散全局变量，而是改成明确状态机：

```text
IDLE
  -> DEBOUNCE_PRESS
  -> TRACK_LONG_PRESS
  -> LONG_PRESS_FIRED
  -> WAIT_RELEASE
  -> IDLE
```

状态机需要包含：

- 当前按键编号。
- 按下起始时间。
- 最近稳定状态。
- 是否已触发长按。
- 释放保护状态。
- 普通短按和长按互斥规则。

这样可以清楚定义：

- 同一时刻只跟踪一个按键。
- 长按跟踪中其他按键是否忽略。
- 长按触发后是否吞掉本次按键释放前的所有边沿。
- 菜单入口是否需要二次确认。

### 5.3 第三阶段：硬件和抗干扰确认

软件整改后仍建议做硬件确认：

1. 确认 `PF1/PF2/PF3/PF4` 是否都有外部上拉。
2. 用示波器或逻辑分析仪观察确认键按下 3 秒内是否出现多次下降沿。
3. 静电或干扰场景下观察返回键线是否有误下降沿。
4. 如果外部上拉不可靠，评估是否能把 GPIO 改成 `GPIO_PULLUP`。
5. 必要时在硬件端增加 RC 消抖或改善按键线束屏蔽。

## 6. 推荐目标参数

建议按产品体验选择一个目标：

| 目标 | 建议计数 | 体验 | 风险 |
| --- | --- | --- | --- |
| 约 1.0 秒 | `10` | 进入快 | 误触概率略高，需要消抖和释放保护 |
| 约 1.2 秒 | `12` | 进入较快 | 仍需确认现场误触 |
| 约 1.5 秒 | `15` | 本次采用，稳健 | 体感比 1.2 秒略慢 |
| 约 3.0 秒 | `30` | 当前行为 | 用户会觉得不灵敏 |

本次采用约 1.5 秒，并配合目标锁定、消抖和释放保护。单纯把 `REQUIRED_PRESS_COUNT` 降低，但不加消抖，会提高误触进入菜单的风险。

## 7. 上板验证建议

### 7.1 基础验证

1. 状态页单独长按确认，记录从按下到出现“是否进入罐上操作?”的时间。
2. 连续测试 30 次，统计失败次数和最长触发时间。
3. 出现确认页后松开确认，再短按确认，确认能进入主菜单。
4. 出现确认页后短按返回，确认能退出到状态页。

### 7.2 抖动和误触验证

1. 长按确认过程中轻触返回键，确认不会打断确认长按。
2. 长按确认过程中轻触上/下键，确认不会影响进入确认页。
3. 长按确认触发后继续按住确认键，确认不会自动越过确认页进入主菜单。
4. 长按确认触发后轻微晃动按键，确认不会自动退出确认页。

### 7.3 干扰验证

1. 在 OLED 静电恢复场景下测试长按确认。
2. 在串口通信高负载下测试长按确认。
3. 在整机线束装配状态下测试长按确认，而不是只在裸板上测试。
4. 记录确认键和返回键 GPIO 波形，确认是否存在异常下降沿。

## 8. 建议增加的诊断计数

为了避免现场只靠感觉判断，建议临时增加只计数不打印的诊断变量，并在主循环或调试菜单读取：

| 计数项 | 含义 |
| --- | --- |
| `key_sure_falling_count` | 确认键下降沿次数 |
| `key_back_falling_count` | 返回键下降沿次数 |
| `long_press_start_count` | 长按检测启动次数 |
| `long_press_reset_by_same_key_count` | 同键抖动导致重启次数 |
| `long_press_blocked_other_key_count` | 长按锁定后忽略其他键次数 |
| `long_press_release_before_trigger_count` | 未达到阈值松手次数 |
| `long_press_fired_count` | 长按成功次数 |
| `menu_entry_guard_drop_count` | 进入确认页释放保护期间丢弃按键次数 |

注意：不要在 EXTI 或 TIM1 中断里直接 `printf()`，避免中断耗时和串口阻塞影响按键行为。

## 9. 版本和兼容性影响

如果后续只调整 CPU3 按键识别逻辑：

- 影响范围：CPU3 本地 UI 操作体验。
- CPU2 协议：无影响。
- CPU2/CPU3 共享协议版本：通常不需要变化。
- CPU3 固件行为：有变化，提交发布时需要记录 CPU3 版本影响和验证结果。
- 参数存储：无影响，除非把长按时间做成可配置参数。

## 10. 结论

当前“长按确认不灵敏”不是单一问题，而是多个因素叠加：

1. 程序实际要求连续按住约 3 秒，本身偏慢。
2. 没有软件消抖，确认键抖动会反复清零计数。
3. 长按检测只有一组全局状态，返回键误触会覆盖确认长按。
4. 进入确认页后缺少释放保护，残留按键可能马上生效。
5. GPIO 配置为无内部上下拉，抗干扰依赖外部硬件。

本次落地“目标键锁定 + 旧锁释放后允许新键接管 + 50 ms 消抖 + TIM1 计数器清零 + 释放保护 + 长按阈值调整到约 1.5 秒”。这样改动范围小，能直接改善进入菜单的稳定性和体感。
