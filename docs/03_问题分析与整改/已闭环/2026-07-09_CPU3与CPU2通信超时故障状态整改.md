# CPU3与CPU2通信超时故障状态整改

日期：2026-07-09

冷启动、失败样本和恢复边界优化日期：2026-07-10

适用版本：CPU3 `V1.20.0.0`。适用范围为 CPU3 与 CPU2 内部 UART5/RS485 Modbus 通信链路，以及依赖该链路的菜单和外部协议写入口。该整改不新增共享寄存器、不改变 CPU2/CPU3 协议字段，`DEVICE_PROTOCOL_VERSION` 保持 `14`。

> 编号迁移：本文保留协议 14 当时的故障码 `0x0013000A`、屏幕编号 `19-10` 和验证记录。当前协议 15 中同一 CPU3 本机故障为 `CPU2_COMM_TIMEOUT = 0x000E000C`，屏幕显示 `14-12`；排查当前设备时应使用新编号，不能直接按本文旧码判断责任域。

## 1. 问题现象

CPU3 轮询 CPU2 时，如果 CPU2 长时间无响应、返回 CRC/地址/功能码/长度错误帧，或 UART5/TX DMA 发生传输错误，CPU3 原有实现只是不再刷新本轮 CPU2 数据。状态页仍可能展示上一帧缓存下来的位置、扭力或测量结果，现场表现为数据不更新但没有明确故障状态和故障码。

该表现会让用户误判为测量数据仍在正常刷新，因此需要在 CPU3 侧单独定义通信超时错误码，并在连续请求未获得合法响应达到阈值后进入故障状态。

## 2. 原因定位

CPU3 内部通信由 `CPU2_CombinatePackage_Send()` 组帧并同步等待 `wait_response`。单次等待超过 `CPU2_RESPONSE_TIMEOUT_MS = 1000 ms` 后，原逻辑只清除等待标志并打印超时信息，未设置 `g_measurement.device_status.device_state` 和 `g_measurement.device_status.error_code`。UART5 IDLE 中断收到长度至少 4 字节的坏帧、UART 错误回调或 TX DMA 启动失败时也会提前结束本次等待，但不会进入原超时计数。

显示侧原逻辑把 `cnt_commutoCPU2 = COMMU_ERROR_MAX` 同时当作“尚未收到首次响应”的上电哨兵和通信失败计数。新增超时置错后如果继续复用该初值，冷启动第一次 1000 ms 响应超时就会立即满足阈值并误报故障，和“连续 10 次真实超时”不一致。

根因包括：一个变量混用了“是否收到过首次有效响应”和“连续通信失败次数”两种状态；旧实现从发送成功时就递增；非法响应和底层传输错误又会绕过超时出口。此外，上电轮询原先不论请求成功与否都会推进分组，CPU2 延迟上线时可能永久漏读保持寄存器；外部 COM 持续有流量时还可能长期饿死 CPU2 轮询。

## 3. 整改内容

1. CPU3 新增本机错误码 `CPU2_COMM_TIMEOUT = 0x0013000A`，文案为“CPU2通信超时”。该名称作为兼容汇总名称保留，实际表示连续请求未获得合法响应，不能仅凭名称判断底层原因一定是纯超时。
2. CPU2 通信模块使用五个私有状态：`s_cpu2_has_status_snapshot` 记录本次上电是否收到过覆盖设备状态和错误码的 0x04 快照，`s_cpu2_has_parameter_snapshot` 记录完整保持寄存器参数是否已同步，`s_cpu2_has_protocol_snapshot` 记录当前 CPU2 连接是否已由合法 0x03 实际读回协议字段，`s_cpu2_consecutive_failure_count` 从 `0` 开始记录连续请求失败次数，`s_cpu2_comm_fault_active` 锁存等待状态帧确认的本机通信故障。
3. `CPU2_CommRecordFailure()` 统一统计“本次请求未获得合法响应”：1000 ms 响应超时、CRC/地址/功能码/长度/0x10 回显错误、UART 错误和 TX DMA 启动失败均计 1 次；发送成功本身不计数。UART ISR 只通过 `CPU2_CommNotifyUartErrorFromISR()` 置待处理标志，计数和故障状态更新仍在主循环完成。
4. 连续第 10 次请求失败达到 `CPU2_COMM_FAILURE_LIMIT = 10` 后，CPU3 本机写入：
   - `device_state = STATE_ERROR`
   - `error_code = CPU2_COMM_TIMEOUT`
5. 只有同时通过功能码、长度/字节数或 0x10 回显、CRC 和从机地址校验的响应才调用 `CPU2_CommMarkValidResponse()` 清零连续失败计数；任一合法 0x03/0x04/0x10 均可清计数，但只有覆盖设备状态和错误码的 0x04 响应才建立首次状态快照或解除故障锁存，普通 0x03/0x10 和不完整状态 0x04 不得用旧缓存清故障。独立协议快照只有覆盖 `HOLDREGISTER_DEVICEPARAM_PROTOCOL_VERSION` 的合法 0x03 才建立；通讯尝试页等待状态和当前连接协议快照均建立后才退出，避免协议未读回时短暂显示伪 `ProtoErr` 或掉线前兼容结果。普通写入口还必须等待完整保持寄存器快照并确认共享协议版本相等。
6. `CPU2_CommShouldShowStartup()` 独立决定上电/恢复同步页：冷启动第 1～9 次连续失败以及状态已到但当前连接协议字段尚未读回时仍显示“通讯尝试中...”，第 10 次转入 `CPU2_COMM_TIMEOUT` 故障页；状态和协议快照均建立后，偶发第 1～9 次失败不会退回通讯尝试页。
7. 上电保持寄存器、参数刷新和运行轮询分组只在本次请求收到合法响应后推进；通信故障恢复阶段优先请求设备状态分组。达到故障阈值时同时清除参数快照和当前连接协议快照；完整状态 0x04 解除故障后必须重新完成上电参数补读，并重新收到覆盖协议字段的合法 0x03，不能沿用掉线前协议缓存。任何已发起的非命令 FC16 未获得合法响应时，底层立即使参数快照失效并强制补读全部四组保持寄存器，覆盖 CPU2 已生效但 ACK 丢失、单参数失败和多字段部分成功场景，不依赖可能延后或不变化的 `parameter_update_flag`。CPU2 即使延迟上线，也不会把失败组误判为已读取。参数补读完成后同步刷新 Wartsila 寄存器镜像；批量参数同步跳过一次性命令字段。
8. `App_MainLoop()` 在主循环可调度时按 `CPU2_POLL_PERIOD_MS = 100 ms` 检查轮询门限，不再只在外部 COM 空闲时轮询，避免持续外部请求让断线检测永久失效；同步请求自身最多可阻塞 1000 ms，因此该门限不是实际请求间隔上限。
9. `CPU2_CommIsAvailable()` 和发送返回值共同保护 CPU2 参数读取、参数写入及普通命令下发：状态快照、完整参数快照、当前连接协议快照、共享协议版本相等和无通信故障必须同时满足；参数刷新期间及故障恢复后的重新同步阶段继续拦截普通写。`CPU2_CommCanSendCommand()` 仅对屏幕 `CMD_CANCEL_MEASUREMENT` 放宽参数快照条件，使参数刷新期间仍可停止运动，但状态快照、当前连接协议快照、协议兼容和无通信故障仍为必需；低层只对精确命令地址、2 个寄存器和取消命令放行。SI `00009 Stop` 当前映射 `CMD_MAINTENANCE_MODE`，不使用该绕过。本次请求失败后不进入“已成功”、运动监控或旧参数页面。
10. DSM FC05 动作线圈 ON、非第 6 段占位 FC16、Wartsila 命令及分布参数写入、SI FC05 ON 和 CPU2 参数 `40001~40003` 在状态/参数/当前连接协议快照未完成、共享协议不兼容、通信故障锁存或本次 CPU2 写失败时返回 Modbus 设备忙异常 `0x06`。DSM 参数快照无效期间，FC03 第 1～5 段同样返回 `0x06`，第 6 段全零占位继续正常响应。SI 的 `40010~40023` 是 CPU3 本机参数，合法写入不依赖 CPU2；SI 线圈和 CPU2 参数影子只在 CPU2 ACK 成功后提交。
11. DSM 和 Wartsila 多字段写仍按多个 CPU2 请求顺序同步。中途失败时 CPU3 会恢复写前本地参数/协议镜像，并在强制补读完成前拒绝相关回读；CPU2 端不具备批量原子回滚，失败前已被 CPU2 接受的字段可能已经生效。主站必须等待补读完成后重试并回读确认，不能把一帧异常响应解释为 CPU2 所有字段均未改变。
12. Wartsila 跨区写在参数阶段失败或命令尝试结束后都会清除命令影子；写 0 和其它协议的批量参数同步不得重放该旧命令。参数阶段失败还会恢复 CPU3 写前四参数镜像，普通命令立即被参数快照门禁阻止；完整补读前读取 `0x005A~0x005D` 返回 `0x06`，补读完成后以 CPU2 实际部分/完整生效值重建镜像。
13. DSM 分发层在地址和 CRC 通过后、调用无长度参数的 `Response01/03/04/05/16` 前校验实际 RTU 帧长。FC01/03/04/05 只接受 8 字节；FC16 要求实际长度等于 `9 + byteCount`，响应层继续校验数量与 `byteCount`。截短、超长或声明长度不一致时返回 `0x03`，避免把 CRC 或尾随字节误当参数并下发 CPU2。

## 4. 协议与版本影响

本次整改改变 CPU3 本机故障状态、状态/参数/当前连接协议快照与协议兼容门禁、菜单成功反馈、DSM 参数读门禁和 DSM/Wartsila/SI 外部写失败行为，但不修改 CPU2 发布的输入寄存器、保持寄存器、命令号或共享状态字段，因此 `DEVICE_PROTOCOL_VERSION` 保持 `14`。

CPU3 从 `V1.19.1.0` 升级到 `V1.20.0.0`：本机通信故障状态、完整同步与协议兼容写门禁和外部协议设备忙反馈属于功能级行为变化。CPU2 固件不因本项单独要求升版。

## 6. 现场复测建议

| 场景 | 预期 |
| --- | --- |
| CPU3 冷启动且 CPU2 暂未就绪，制造第 1 次请求超时 | 不置错，仍显示“通讯尝试中...”，失败计数为 1 |
| 冷启动连续制造第 2～9 次请求失败 | 均不置错，继续显示“通讯尝试中...”，计数依次累计且不提前达到故障状态 |
| 冷启动制造连续第 10 次请求失败 | CPU3 状态页进入故障显示，错误码为 `0x0013000A`，故障详情为“CPU2通信超时” |
| 分别注入 CRC、地址、功能码、长度/字节数、0x10 回显错误帧 | 每个请求按 1 次失败累计，合法响应前不会刷新通信有效状态；连续第 10 次同样置错 |
| 注入 UART5 错误或 TX DMA 启动失败 | ISR 不打印、不直接置故障；主循环按 1 次请求失败累计并恢复 UART5 接收 |
| CPU2 参数菜单进入前已累计 9 次失败，本次读取形成第 10 次 | 显示 CPU2 通讯故障提示并退出参数页，不显示旧缓存参数 |
| 命令或参数写入请求本次失败 | 不显示“已进入维护模式”等成功反馈，不进入运动监控/等待页 |
| CPU2 冷启动延迟约 7 s 后上线 | 前 7 个失败组不推进；上线后从设备状态组继续，最终完整读取 3 组输入寄存器和 4 组保持寄存器，协议版本和参数缓存正确 |
| 已经建立首次状态快照后连续制造第 1～9 次失败 | 不退回首次通讯页，不置通信超时故障；原有状态页缓存不应表现为正在刷新 |
| 阈值前恢复并收到任意合法响应 | 连续失败计数清零，后续重新从第 1 次失败累计；只有覆盖状态和错误码的 0x04 响应才结束启动页，写入口仍等待完整参数快照、当前连接协议快照和协议版本相等 |
| 第 10 次失败置错后先恢复非状态 0x03/0x04/0x10 响应 | 合法帧可清连续失败计数，但本机通信故障继续锁存，参数菜单仍不可用 |
| 第 10 次失败置错后恢复有效 0x04 状态帧 | CPU2 状态分组刷新 CPU3 缓存，通信故障锁存解除；参数和当前连接协议快照仍无效，继续显示通讯尝试页，普通写与屏幕取消均保持关闭 |
| 状态 0x04 恢复后先收到不覆盖协议字段的合法 0x03 | 只清连续失败计数，不建立当前连接协议快照；即使缓存中的旧协议值仍为 14，也不得放行屏幕取消或普通写 |
| 状态 0x04 恢复后收到覆盖协议字段且值为 14 的合法 0x03 | 建立当前连接协议快照；完整参数仍在补读时仅屏幕 `CMD_CANCEL_MEASUREMENT` 可达，普通写继续关闭 |
| 参数刷新期间从屏幕停止/取消测量 | 状态和当前连接协议快照有效、协议为 14 且无通信故障时可下发取消；SI `00009 Stop` 与其它普通命令不绕过参数门禁 |
| COM1/COM2/COM3 持续高频请求时断开 CPU2 | 主循环每轮在外部协议处理后检查 100 ms 轮询门限，外部流量不得永久饿死 CPU2；记录含同步阻塞在内的实际最坏请求间隔，连续失败达到阈值后进入通信故障，不长期返回旧缓存而无故障 |
| 状态/参数/当前连接协议快照未完成、协议不兼容或通信故障锁存时写 DSM/SI/Wartsila 的 CPU2 桥接字段 | 返回设备忙 `0x06`，不返回成功回显；SI CPU2 参数和动作影子保持原值 |
| 写 SI `40010~40023` CPU3 本机参数 | 不依赖 CPU2 在线状态；值域合法时正常保存和回读，不能被 CPU2 门禁误拦截 |
| DSM 多字段同步中途制造 CPU2 写失败并立即 FC03 回读 | FC16 返回 `0x06` 并恢复 CPU3 写前参数/寄存器镜像；补读前第 1～5 段 FC03 返回 `0x06`，第 6 段仍正常返回全 0；补读后返回 CPU2 实际部分/完整生效值 |
| DSM 发送 CRC 正确的截短/超长固定功能码或 FC16 帧 | 实际长度不符合固定 8 字节或 `9 + byteCount` 时返回 `0x03`；不得进入寄存器解析或 CPU2 参数下发 |
| DSM/Wartsila 多字段同步中途制造 CPU2 写失败 | 主站收到 `0x06`；CPU3 本地影子回滚，CPU2 失败前已 ACK 字段允许部分生效，主站等待补读后按同一目标值重试并回读确认最终一致性 |
| 菜单/DSM/SI/Wartsila 非命令 FC16 响应超时、非法或 ACK 丢失 | 失败返回前参数快照立即失效，同一主循环其它 COM 普通命令被阻止；即使 `parameter_update_flag` 不变也主动补读四组，全部成功后才重新开放 |
| Wartsila 第 1～4 个参数请求分别失败或 ACK 丢失 | 返回 `0x06`，恢复 CPU3 写前四参数镜像且不启动命令；强制补读前读 `0x005A~0x005D` 仍返回 `0x06`，补读后返回 CPU2 实际值 |
| 参数补读完成后读取并单字段写 Wartsila `0x005A~0x005D` | Wartsila 镜像先刷新为 CPU2 最新四参数；单字段写不得把其它旧镜像值覆盖回 CPU2 |
| 其它协议参数写触发批量参数同步 | `COM_NUM_DEVICEPARAM_COMMAND` 永久跳过，已消费命令不得跨协议重放 |
