# CPU2 速度 1 下行 55m 运行变慢根因分析

> 当前复核（2026-07-08）：状态：已闭环。当前 HEAD `636c4778`（CPU2 V1.21.4.0 / CPU3 V1.19.1.0）已修复编码轮速度补偿参考长度，`MotorDriver_RefreshVelocityDuringRun()` 改为通过 `MotorDriver_GetVelocityReferenceLengthMm()` 刷新业务尺带长度并统一使用 `cable_length` 计算 VMAX；对应版本测试方案已补充到 `docs/00_构建与版本/版本改动与测试/2026-07-08_CPU2_V1.21.4.0_CPU3_V1.19.1.0_编码轮速度补偿参考长度_改动与测试方案.md`。

## 结论

本次串口日志证明：速度参数 `1.00 m/min` 已经生效，运行中也触发了 `速度刷新`。问题不是“没有实时调速”，而是编码轮记步模式下，运行中速度补偿使用了错误的尺带长度来源。

具体表现是：电机初始化阶段按真实编码轮尺带长度计算出了正确的高 `VMAX`，但进入运行刷新后，`MotorDriver_RefreshVelocityDuringRun()` 在编码轮记步模式下改用 `drum.motor_distance_01mm`。该值来自 TMC5130 `XACTUAL` 的电机卷筒模型长度，当前运行中会从本段接近 `0mm` 的局部长度重新开始，而不是当前真实已下放的 `40m`、`52m` 级编码轮尺带长度。因此程序把已经下放很深的位置误算成接近空卷起点，重新采用大周长，导致 `VMAX` 被拉低，实际线速度随下放深度明显低于 1m/min。

## 正确和错误路径对照

### 初始化阶段是正确的

`MotorCtrl_Init()` 会调用 `MotorDriver_UpdateVelocityFromParams()`，该函数用的是业务侧当前尺带长度：

```c
const double Lcur_mm = (double)g_measurement.debug_data.cable_length * 0.1;
velocity = MotorDriver_ComputeUniformVelocityFromLength(Lcur_mm);
```

这解释了为什么日志初始化行能打印出真实的 `尺带=40189.8 mm | 周长=550.2 mm`，并且初始化后的旧 `VMAX=65057` 是合理的。

### 运行刷新阶段用错长度源

问题发生在 `MotorDriver_RefreshVelocityDuringRun()`：

```c
MotorDrumState drum;
MotorCtrl_UpdateDrumStateFromXActual(tmc5130, &drum);
MotorPosition_UpdatePositionFromMotorSource(&drum);
const double Lcur_mm = (g_deviceParams.position_count_mode == POSITION_COUNT_MODE_MOTOR) ?
                       ((double)g_measurement.debug_data.cable_length * 0.1) :
                       ((double)drum.motor_distance_01mm * 0.1);
```

这段逻辑在电机记步模式下使用 `g_measurement.debug_data.cable_length`，是合理的；但在编码轮记步模式下使用 `drum.motor_distance_01mm`，会脱离编码轮真实尺带长度。

`MotorPosition_UpdatePositionFromMotorSource()` 也说明了这一点：如果不是 `POSITION_COUNT_MODE_MOTOR`，它直接返回，不会把 `drum` 更新为业务位置：

```c
if ((drum == NULL) ||
    (g_deviceParams.position_count_mode != POSITION_COUNT_MODE_MOTOR)) {
    return;
}
```

因此在编码轮记步模式下：

1. 业务真实位置仍由编码轮维护，日志中的 `编码轮尺带` 和 `尺带` 是正确累计值。
2. `drum.motor_distance_01mm` 只是 TMC5130 `XACTUAL` 直接推导出的电机模型长度。
3. 后续命令或刷新配置后，`drum.motor_distance_01mm` 可能从本段局部接近 `0mm` 开始。
4. 速度补偿错误地把这个局部长度当作当前卷径长度使用。

这就是 `40189.8mm` 初始化后，第一次刷新却显示 `0.3mm` 的直接原因。

## 为什么第一段不明显，后面越来越明显

第一段从接近零点开始，真实编码轮尺带和电机模型局部长度都接近零，因此两者误差小，`VMAX` 看起来正常上升。

第二段开始时，真实尺带已经约 20m，但运行刷新按 0m 算，`VMAX` 从约 46995 降到 38635。

第三段开始时，真实尺带已经约 40m，但运行刷新仍按 0m 算，`VMAX` 从约 65057 降到 38635。深度越大，真实卷径越小，应该需要越高转速；错误长度源却不断把转速拉回浅位置口径，所以越深越慢的体感会越来越明显。

## 影响范围

确认受影响：

- 编码轮记步模式下，使用 `MotorDriver_RefreshVelocityDuringRun()` 的长距离位置运动。
- 手动下行、强制下行、罐底/水位/液位中调用位置模式长距离运动并依赖运行中恒线速补偿的路径。
- 多段连续下行或运行中刷新配置后，影响会更明显，因为 `drum.motor_distance_01mm` 更可能从局部低值重新开始。

相对不受影响或影响较小：

- 从接近零点开始的第一段短距离运动，因为局部电机长度和真实编码轮长度接近。
- 电机记步模式下的运行刷新，因为该分支使用的是 `g_measurement.debug_data.cable_length`。
- 仅关注到位距离的场景。日志显示两段 18m 的距离偏差只有约 `0.04%~0.05%`，距离控制本身没有暴露同级别问题。

## 建议整改方向

### 最小整改方向

在 `MotorDriver_RefreshVelocityDuringRun()` 中，速度补偿应使用“当前有效位置源对应的真实业务尺带长度”，而不是在编码轮模式下直接使用 `drum.motor_distance_01mm`。

建议优先方案：

1. 运行中刷新前先保证业务位置已刷新。
2. 编码轮记步模式下使用 `g_measurement.debug_data.cable_length` 作为 `Lcur_mm`。
3. 电机记步模式下继续使用电机源更新后的 `g_measurement.debug_data.cable_length`。
4. 保留 `drum.motor_distance_01mm` 作为诊断打印或电机源对比，不直接作为编码轮模式下的卷径速度补偿长度。

### 需要一起检查的边界

- `MotorDriver_RefreshVelocityDuringRun()` 当前在部分等待循环中先于 `MotorDriver_SyncPositionOrCheckHealth()` 调用，若改用业务 `cable_length`，要确认使用的是上一轮编码轮刷新值还是先刷新后计算。建议让速度补偿前的位置刷新顺序一致。
- 若后续仍需要用 `XACTUAL` 推导卷径，应使用“编码轮基准长度 + XACTUAL 相对增量”，不能直接用 `drum.motor_distance_01mm` 的绝对模型长度。
- 修改后要保留运行中 200ms 刷新周期和约 3% 写入阈值，避免频繁写 TMC5130。
