# 电机24V断电与命令切换改动整理

整理日期：2026-05-14

## 1. 背景

本轮修改围绕现场连续暴露的几类问题收口：

1. 固定点监测、液位模式稳定等待、称重稳定等待等长等待阶段不能及时响应新命令。
2. 电机 24V 运行中断电或未上电时，TMC5130 仍可能通过 SPI 读出部分寄存器，导致流程误以为电机可用。
3. 串口调试入口中有部分命令直接调用实际测量函数，绕过主循环的 `current_command`、命令切换和自动恢复上下文。
4. `STATE_SWITCH`、最终报错、自动恢复之间语义混杂，导致命令切换被当作故障打印，或同一故障链路重复打印。
5. CPU2/CPU3 固件版本独立迭代时，CPU3 读取 CPU2 版本会因为 minor 不一致提示版本不匹配，但本轮未改变跨 CPU 协议。

本轮目标是保持现有测量流程基本形态，补齐命令切换、错误传播、TMC 健康检查和自动恢复边界，让现场故障能被识别、可退出、可恢复。

## 2. 最终改动范围

### 2.1 命令切换不再作为故障打印

涉及文件：

- `LTD_MAIN_CPU2/Services/Utilities/error_log.c`
- `LTD_MAIN_CPU2/Application/Src/fault_manager.c`
- 多个测量流程文件

核心变化：

- `ErrorLog_RetryDetail()` 和 `ErrorLog_ReportDetail()` 遇到 `NO_ERROR` 或 `STATE_SWITCH` 直接返回。
- 测量流程中遇到 `STATE_SWITCH` 时作为正常控制流返回，不再打印错误重试或最终报错。
- `ErrorLog_TakeRecentReport()` 调整为用于判断最近最终报错是否已经打印，减少同一底层错误向上冒泡时重复打印。

效果：

- 用户主动下发新命令不再污染错误日志。
- 同一电机故障在多层 `CHECK_ERROR()` 中传播时，最终报错重复刷屏减少。

### 2.2 长等待统一改成可被命令切换打断

新增文件：

- `LTD_MAIN_CPU2/Services/Utilities/abortable_delay.c`
- `LTD_MAIN_CPU2/Services/Utilities/abortable_delay.h`

公共函数：

```c
uint32_t AbortableDelay_CommandSwitch(uint32_t total_ms, uint32_t step_ms);
```

语义：

- 按 `step_ms` 分片执行 `HAL_Delay()`。
- 每片延时后检查 `HasEffectiveCommandSwitchRequest()`。
- 等待完整结束返回 `NO_ERROR`。
- 检测到有效命令切换返回 `STATE_SWITCH`。
- `step_ms == 0` 时使用 50ms 默认分片。

已替换的局部重复函数：

- `MeasureDelayAbortable()`
- `DensityDelayAbortable()`
- `OilLevel_DelayAbortable()`
- `Sensor_DelayAbortable()`
- `Weight_DelayAbortable()`

主要调用场景：

- 固定点监测和密度分布取点悬停。
- 液位/密度模式切换后的稳定等待。
- 液位频率异常恢复等待。
- 空载/满载称重稳定等待。
- Wartsila 密度测量等待 CPU3 读取结果。

效果：

- 业务长等待可以在分片周期内响应新命令。
- 后续不应再新增各模块私有的 `DelayAbortable`。

### 2.3 串口正式业务命令统一走主循环入口

涉及文件：

- `LTD_MAIN_CPU2/Application/Src/measure.c`

新增函数：

```c
static uint8_t ProcessCommand_MapFormalCommand(uint8_t command_char,
                                               CommandType *formal_command);
```

当前映射：

| 串口命令 | 正式命令 |
| --- | --- |
| `I` | `CMD_BACK_ZERO` |
| `G` | `CMD_FIND_BOTTOM` |
| `K` | `CMD_FIND_OIL` |
| `R` | `CMD_MEASURE_DISTRIBUTED` |
| `W` | `CMD_FIND_WATER` |
| `O` | `CMD_SET_EMPTY_WEIGHT` |
| `P` | `CMD_SET_FULL_WEIGHT` |
| `Q` | `CMD_RESTORE_FACTORY` |

核心变化：

- 上述串口命令不再直接调用 `CMD_MeasureZero()`、`SearchBottom()`、`CMD_MeasureAndFollowOilLevel()`、`CMD_MeasurWater()` 等业务函数。
- `process_command()` 只写入 `g_deviceParams.command`，由 `App_MainLoop()` 在正式命令入口执行。
- 正式入口会统一设置 `current_command`、调用 `ProcessMeasureCmd()`，并在命令结束后进入 `FaultRecovery_UpdateAfterCommand()`。

保留不改的命令：

- `F`、`H`、`J` 是重复性测试循环，没有对应的“重复执行”正式 `CommandType`，继续作为串口调试命令保留。
- `A/B/C/D/E/M/N/T/Y/X/L` 等仍属于现场调试或展示命令，保留原串口调试路径。

效果：

- 串口第二次下发正式业务命令时，会重新经过 `MeasureStart()`、电机健康检查和自动恢复上下文。
- 串口正式命令与参数区/上位机正式命令的执行边界一致。

### 2.4 TMC5130 与电机 24V 健康检查增强

涉及文件：

- `LTD_MAIN_CPU2/Drivers/Peripherals/src/TMC5130.c`
- `LTD_MAIN_CPU2/Drivers/Peripherals/inc/TMC5130.h`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_driver_param.c`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_internal.h`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_motion_api.c`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_position_model.c`

关键变化：

- 新增 `stpr_checkDriverPowerReady()`，通过 `DRV_STATUS.CS_ACTUAL` 判断功率级是否真正建立电流。
- `stpr_checkDriverStatus()` 检查 `GSTAT/DRV_STATUS` 故障位，并在 `GSTAT == 0` 时读取 `CHOPCONF` 识别配置丢失或驱动掉电。
- 新增统一入口 `MotorDriver_CheckHealth()`，集中处理初始化状态、TMC 配置、复位/欠压/过温和功率级状态。
- `MotorCtrl_CheckDriverGstat()` 兼容旧接口，但内部改走 `MotorDriver_CheckHealth()`。
- `MotorCtrl_PollRuntimePosition()` 改为返回错误码，运行期位置同步失败可以继续做 TMC 健康检查并向上返回错误。
- `MotorPosition_SyncDebugDrumState()` 改为返回 `bool`，让调用方区分同步成功和 XACTUAL 读取异常。

识别的 24V 异常形态：

- `GSTAT=0x00000000` 且 `CHOPCONF=0x00000000`：按 TMC 配置丢失或驱动掉电处理，返回 `MOTOR_TMC_COMM_ERROR`。
- `GSTAT` 含 `uv_cp`：返回 `MOTOR_CHARGE_PUMP_UNDER_VOLTAGE`。
- `DRV_STATUS.CS_ACTUAL == 0`：返回 `MOTOR_DISABLED`。
- XACTUAL 疑似 SPI 全 0：先丢弃本次读数，在关键运动等待路径中继续做健康检查。

效果：

- 24V 未上电或运行中断电时，不再只靠 SPI 静态读成功就认为电机可运行。
- 回零点、移动等待、停止等待、运行期轮询能更早发现电机掉电或配置丢失。

### 2.5 运动流程错误传播与重复逻辑收口

涉及文件：

- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_motion_api.c`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_driver_param.c`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_internal.h`
- `LTD_MAIN_CPU2/Services/MotorControl/motor_ctrl_position_model.c`

新增内部 helper：

```c
uint32_t MotorDriver_SyncPositionOrCheckHealth(TMC5130TypeDef *tmc5130);
uint32_t MotorDriver_ReturnAfterTemporarySpeed(uint32_t ret,
                                               bool restore_needed,
                                               uint32_t restore_speed_x100);
```

当前语义：

- `MotorDriver_SyncPositionOrCheckHealth()`：先同步 XACTUAL；同步失败时做运行期健康检查；如果无法确认 TMC 故障，保持原流程继续。
- `MotorDriver_ReturnAfterTemporarySpeed()`：先恢复临时速度；原始运动已经失败时优先保留原始错误，避免“恢复默认速度失败”覆盖掉真正的 TMC/命令切换错误。

效果：

- 运动等待、停止等待、到位等待中的位置同步失败处理更一致。
- 临时速度恢复不再到处手写，错误优先级更清楚。

### 2.6 自动恢复状态机独立成模块

新增/涉及文件：

- `LTD_MAIN_CPU2/Application/Src/fault_recovery.c`
- `LTD_MAIN_CPU2/Application/Inc/fault_recovery.h`
- `LTD_MAIN_CPU2/Application/Src/app_main.c`

核心变化：

- 自动恢复状态从 `app_main.c` 拆出到 `fault_recovery.c/.h`。
- `app_main.c` 只保留主循环调度、正式命令执行、空闲错误兜底。
- 自动恢复入口按命令白名单判断是否允许恢复，不按错误类型过滤。
- 错误类型只用于决定恢复检查前是否需要额外执行 `MotorCtrl_Init()`。
- 自动恢复模块不直接调用 `ProcessMeasureCmd()`，只通过 `FaultRecoveryResult` 告诉主循环是否需要重跑命令。
- 自动恢复前不清除历史全局错误码；恢复成功后由恢复模块清理错误状态。
- 命令切换取消自动恢复时只打印普通提示，不再打错误日志。

效果：

- 电机 24V 恢复后，如果 `MotorCtrl_Init()` 能重新初始化 TMC5130，自动恢复可以继续。
- 恢复模块和主循环职责更清楚，不再互相反向调用。

### 2.7 找零点粗找保留原有重试语义

涉及文件：

- `LTD_MAIN_CPU2/Application/Src/measure_zero.c`

最终策略：

- 保留原有粗找重试/退让动作逻辑。
- `SearchZeroRough()` 返回电机错误时仍会进入粗找重试路径，下发退让动作，由运动入口再次做健康检查。
- 只修正错误覆盖顺序：只有 `SearchZeroRough()` 返回 `NO_ERROR` 后才判断“粗找后零点偏差超过阈值”。
- 避免电机/TMC 原始错误被后续“零点偏差超限”覆盖。

效果：

- 现场原有粗找重试逻辑不变。
- 第二次或后续运动下发时，仍能重新检测 TMC/电机错误。
- 错误码保留更接近真实根因。

### 2.8 传感器通信失败后的轻量滑环诊断

涉及文件：

- `LTD_MAIN_CPU2/Services/Sensor/sensor.c`
- `LTD_MAIN_CPU2/Services/Sensor/sensor.h`
- `LTD_MAIN_CPU2/Services/Sensor/wireless_communication.c`
- `LTD_MAIN_CPU2/Services/Sensor/wireless_communication.h`

核心变化：

- 新增 `WIRELESS_ProbeNode(uint8_t addr)`，只做一次最小读请求。
- `Sensor_DiagnoseCommTimeout()` 在传感器通信超时时进行轻量探测。
- 探测过程遇到命令切换返回 `STATE_SWITCH`。
- 日志能区分传感器自身无响应、滑环主机无响应、滑环从机无响应。

效果：

- 传感器通信失败时不再额外读取大量无线节点信息。
- 通信链路定位更轻量，日志更聚焦。

### 2.9 固定点监测错误传播修正

涉及文件：

- `LTD_MAIN_CPU2/Application/Src/measure_density.c`

核心变化：

- 固定点监测内部采样等待改为可打断延时。
- `Read_Density()` 读取失败后返回真实错误码，不再只打印但不置错误状态。
- 上层可以通过 `SET_ERROR()`/`CHECK_ERROR()` 进入统一故障状态。

效果：

- 固定点监测报错后可以退出。
- 读取密度失败能进入统一错误状态和自动恢复路径。

### 2.10 CPU3 版本不匹配提示规则调整

涉及文件：

- `LTD_DISPLAY_CPU3/Application/display/display_tankopera.c`

核心变化：

- CPU3 显示 CPU2 程序版本时，只用 CPU2 固件主版本 `major` 判断兼容性。
- `minor/patch/build` 只作为 CPU2/CPU3 各自固件迭代显示，不再触发版本不匹配提示。

原因：

- 本轮 CPU2 是内部故障处理、命令入口和恢复逻辑修复，没有修改 CPU2/CPU3 共享寄存器、字段含义或通信协议。
- CPU2 `V1.4.x.x` 与 CPU3 `V1.1.x.x` 不应仅因为 minor 不一致就提示协议不匹配。

效果：

- CPU2/CPU3 固件可独立小版本迭代。
- 只有主版本不一致时才提示可能不兼容。

## 4. 现场验证清单

建议按以下用例复测：

1. 固定点监测期间下发新命令，确认能退出，不把 `STATE_SWITCH` 打成错误。
2. 液位模式切换后 10s 稳定等待期间下发新命令，确认能退出等待。
3. 密度分布测取点悬停期间下发新命令，确认返回 `STATE_SWITCH`。
4. 空载/满载称重稳定等待期间下发新命令，确认能退出。
5. 电机 24V 未上电时执行回零点，确认初始化或运动前检查能报电机错误。
6. 回零点运行中断开 24V，确认能识别 TMC 配置丢失、充电泵欠压或电机被禁止。
7. 断 24V 后恢复 24V，确认自动恢复中 `MotorCtrl_Init()` 能重新初始化并继续恢复流程。
8. 串口下发 `I/G/K/R/W/O/P/Q`，确认日志显示转正式命令，并由主循环打印 `当前命令`。
9. 串口重复性测试 `F/H/J`，确认仍保留原调试循环行为。
10. CPU3 查看 CPU2 版本，确认 CPU2/CPU3 minor 不一致时不再提示 `Version mismatch`。
11. 传感器通信失败时，确认日志能区分传感器、滑环主机、滑环从机。
12. 同一电机故障向上冒泡时，确认最终报错不会重复刷屏。

## 5. 后续建议

1. 继续筛选业务长 `HAL_Delay()`，只迁移需要响应命令切换的等待，不动通信协议短延时。
2. 现场验证电机 24V 抖动场景；当前按要求没有加入冷却和去抖，如果电源反复抖动，日志仍可能频繁出现恢复失败。
3. 暂缓抽通用运动等待框架，避免一次性重构等待流程。
4. 如果未来确实修改 CPU2/CPU3 通信协议，应单独引入协议版本字段，而不是继续把固件版本 minor 当作协议兼容判断。
