# Wartsila 当前兼容情况与协议栈

更新日期：2026-07-18

实现状态：本文所称“当前源码行为”对应CPU3 V1.29.0.0。FC10自该版本起收紧为莆田现场格式唯一口径；CPU3 V1.28.0.0及更早版本不包含该收紧行为，仍按对应历史版本资料解释。

## 1. 文档目的

本文记录当前 CUBE 工程对 Wartsila/Wärtsilä/瓦锡兰 LTD 外部协议的实际兼容状态和协议栈链路。

本文只描述当前源码行为，不把现场原 Wartsila 系统的所有从站都默认视为 CUBE 已实现对象。现场抓包细节、寄存器样本和公开资料依据见 `2026-01-27_莆田现场Wartsila抓包协议整理.md`。

当前结论：

- CUBE 当前实现是 CPU3 外部串口侧的 Wartsila 地址 `1` Modbus RTU 从站兼容层。
- 当前不是完整仿真现场原 Wartsila 多从站总线。
- 地址 `1` 的基本状态读取、参数下发、命令下发、分布点表框架和同代点阵提交门禁已经具备。
- 仍存在分布点表容量、完成状态、扩展读块、状态细分和多地址响应等兼容缺口。

## 2. 当前协议边界

| 项目 | 当前实现 |
| --- | --- |
| 协议位置 | CPU3 外部通信侧 |
| 外部协议形态 | Modbus RTU |
| 默认串口参数 | `2400 8E1` |
| 默认接入串口 | COM2、COM3 默认配置为 Wartsila |
| 从站地址 | 使用全局 `SlaveAddress`，默认 `0x01` |
| 已支持功能码 | `0x03` 读保持寄存器；`0x10` 写多个保持寄存器 |
| 当前目标 | 兼容 Wartsila 主 LTD/密度分布控制与结果区，即现场抓包地址 `1` |
| 非当前目标 | 默认不仿真抓包中的地址 `2`、`3`、`4` 辅助节点 |

代码依据：

- 协议枚举：`LTD_DISPLAY_CPU3/Application/system_param/com_port_config.h`
- Wartsila 默认串口参数：`LTD_DISPLAY_CPU3/Application/system_param/cpu3_comm_display_params.c`
- 从站地址：`LTD_DISPLAY_CPU3/Communication/common/address.c`
- 协议分发入口：`LTD_DISPLAY_CPU3/Application/app_main.c`
- Wartsila 协议实现：`LTD_DISPLAY_CPU3/Communication/external/wartsila_modbus/`

## 3. 当前协议栈链路

### 3.1 外部主机到 CPU3

```text
Wartsila 主机
  -> CPU3 外部串口 COM2/COM3
  -> app_main.c 根据串口配置选择协议
  -> COM_PROTO_WARTSILA
  -> proto_wartsila_process()
  -> modbus_rtu_process()
```

入口关系：

| 层级 | 代码位置 | 当前行为 |
| --- | --- | --- |
| 串口配置 | `cpu3_comm_display_params.c` | Wartsila 协议带出 `2400 8E1`；COM2/COM3 默认 Wartsila |
| 协议枚举 | `com_port_config.h` | `COM_PROTO_WARTSILA = 1` |
| 协议分发 | `app_main.c` | `COM_PROTO_WARTSILA` 映射到 `proto_wartsila_process()` |
| Wartsila 入口 | `app_main.c` | `proto_wartsila_process()` 直接调用 `modbus_rtu_process()` |
| RTU 解析 | `wartsila_modbus_communication.c` | 校验地址、CRC、功能码和寄存器范围 |

### 3.2 `0x03` 读路径

```text
外部主机 0x03 请求
  -> modbus_rtu_process()
  -> 地址必须等于 SlaveAddress
  -> CRC 校验
  -> DeviceParams_StoreToRegisters(g_holding_regs)
  -> DSMToWartsila(&g_measurement, &wxl)
  -> handle_0x03()
  -> 从 g_holding_regs 组 RTU 响应
```

关键点：

- 每次 `0x03` 读取前都会从 `g_measurement` 刷新 Wartsila 保持寄存器缓存。
- 对外响应来自 `g_holding_regs`，不是直接读 CPU2。
- CPU2 测量结果需要先经 CPU2/CPU3 内部 Modbus 同步到 CPU3 的 `g_measurement`。
- `0x03` 请求不含 `byteCount`；响应按现场抓包和标准 Modbus 使用 `byteCount=2*qty`，不得套用下述 Wartsila `0x10` 写请求特例。

### 3.3 `0x10` 写路径

```text
外部主机 0x10 请求
  -> modbus_rtu_process()
  -> handle_0x10()
  -> 写入 g_holding_regs
  -> modbus_on_holding_written(start, qty)
  -> DeviceParams_LoadFromRegisters(g_holding_regs)
  -> WartsilaToDSM(&wartsila_deviceParams, &g_deviceParams)
  -> CPU2_CombinatePackage_Send(...)
  -> CPU2 执行命令或保存参数
```

当前 `0x10` 仅接受莆田现场 Wartsila 特殊格式：

```text
现场格式：[addr][10][startHi][startLo][qtyHi][qtyLo][byteCount=qty][data: 2*qty bytes][crcLo][crcHi]
```

> **Wartsila 莆田现场专用格式：不得改回标准 Modbus FC10。** 所有 Wartsila 命令和参数写帧的 `byteCount` 必须等于 `qty`，实际数据区仍为 `2*qty` 字节；标准 `byteCount=2*qty` 必须返回非法数据值 `0x03`。现场格式仍须严格校验实际 PDU 长度 `6+2*qty`。

- 当前 `pdata = &pdu[6]` 的数据起点是正确的，因为当前 PDU 定义包含功能码。
- 莆田现场格式的数据区长度、寄存器大端顺序、CRC 和地址范围校验保持不变；只有 `byteCount` 字段采用 `qty` 口径。

### 3.4 CPU2 业务执行和结果回读

```text
CPU3 收到 Wartsila 命令/参数
  -> 写 CPU2 保持寄存器或命令寄存器
  -> CPU2 执行 Wartsila 分布测量/回零点/固定点监测
  -> CPU2 更新 g_measurement
  -> CPU3 内部 Modbus 轮询 CPU2 输入寄存器
  -> CPU3 更新本地 g_measurement
  -> 外部 Wartsila 读 0x03 时输出最新缓存
```

分布测量完成后的点表同步链路：

- CPU2 先写点数、来源、完成锁存和全部点阵，再以完成计数作为最后发布边沿。
- CPU3 观察到新的有效完成头后，候选同步期间恢复上一份已确认点阵；没有历史快照时公开点阵保持清零。
- CPU3 私有读取“前头部 -> N 个点 -> 后头部”，只有完成计数、点数、来源和锁存在前后头部完全一致时，才在临界区一次提交 `g_measurement`、公开输入寄存器和完成态；N 点后的旧尾部同时清零。
- 完整候选提交前，CPU3 把 `STATE_WARTSILA_DENSITY_OVER` 临时映射回 `STATE_WARTSILA_DENSITY_MEASURING`；提交后才恢复 CPU2 原始完成态。该门禁不等于已经修正 Wartsila `0x0007` 的完成状态字，后者仍单独存在 `0x0C60` 与现场候选 `0x2840` 的偏差。
- 单块失败按 `100/300/1000 ms` 重试，耗尽后等待 `500 ms` 从前头部开始下一整轮，最多三轮；任一时刻 `20 s` 无进展进入 `20-13`，同一完成代际在 `2 s` 后自动重试，成功后清除本机同步故障。

上述软件门禁已关闭“新完成头与旧/部分点阵同时公开”的已知静态缺口；它不能替代真实 Wartsila 主机、RS485 时序和分块故障注入。当前也仍只对外填充前 100 点。

## 5. 命令兼容情况

| Wartsila 写入地址 | 写入值 | 当前内部命令 | 当前状态 |
| --- | --- | --- | --- |
| `0x0006` | `5` | `CMD_WARTSILA_DENSITY_RANGE` | 已支持，执行 Wartsila 分布测量 |
| `0x0006` | `4` | `CMD_BACK_ZERO` | 已支持，执行回零点 |
| `0x0006` | `3` | `CMD_MONITOR_SINGLE` | 已支持，执行固定点监测 |
| `0x005A~0x005D` | 参数组 | 写入 Wartsila 分布测量参数 | 已支持 |

当前写入后的处理逻辑：

- `0x10` 写入范围只有覆盖 `0x0006` 或 `0x005A~0x005D` 时才桥接 CPU2；其它保持寄存器只更新 Wartsila 本地寄存器池，不再误发四个分布参数。
- 覆盖 CPU2 桥接地址且状态快照、完整参数快照或当前连接协议快照尚未建立、共享协议不兼容、参数刷新未完成或通信故障已锁存时，CPU3 在写本地寄存器池前返回设备忙异常 `0x06`。
- 覆盖 `0x005A~0x005D` 时，CPU3 从本地寄存器池解析四个分布参数，并通过四次 CPU2 写请求顺序下发；任一次失败都把原正常回显覆盖为设备忙 `0x06`，恢复 CPU3 写入前的四参数镜像，并立即使 CPU2 参数快照失效、强制补读全部四组保持寄存器。该补读不依赖 `parameter_update_flag`，用于覆盖 CPU2 已生效但 ACK 丢失、首字段失败和中途部分成功。
- 参数快照重新确认前，覆盖 `0x005A~0x005D` 的 `0x03` 读取也返回设备忙 `0x06`；补读完成后才以 CPU2 实际部分/完整生效值重建寄存器镜像，不能把未确认目标值伪装成成功回读。
- 覆盖 `0x0006` 且命令非 0 时，本地命令影子只消费一次：无论 CPU2 ACK 成功或失败都在本次尝试后清零，失败时仍向主站返回 `0x06`，避免后续写 0 重放旧命令。同一帧同时覆盖参数区和命令区时，先同步四个参数，再下发命令，避免测量命令使用旧参数启动。

兼容风险：

- 莆田抓包主要写 `0x0006` 和 `0x005A~0x005D`，当前能覆盖。
- 四个分布参数和命令通过多个 CPU2 请求顺序同步，不是原子事务。若中途失败，主站会收到 `0x06`，失败前已被 CPU2 接受的字段可能已生效；CPU3 先恢复写前镜像并关闭普通命令门禁，随后强制补读 CPU2 实际值。主站必须等待补读完成，再按相同目标值重试并回读确认。
- 外部主机不应把跨命令区和参数区的大范围写作为常规操作；如果确需使用，必须按“参数先于命令”口径验收，并覆盖中途失败场景。

## 6. 状态字兼容情况

当前状态字由 `AubonState_To_WartsilaWorkState()` 将 CUBE 内部 `DeviceState` 转换成 Wartsila `0x0007` 工作状态。

### 6.1 当前已映射

| CUBE 内部状态 | 当前输出 | 抓包/表格含义 |
| --- | --- | --- |
| `STATE_SPTESTING` | `0x0044` | 固定点监测中 |
| `STATE_WARTSILA_DENSITY_START` | `0x0C64` | 开始密度分布测量 |
| `STATE_WARTSILA_DENSITY_MEASURING` | `0x0C60` | 向上运行，密度分布测量中 |
| `STATE_WARTSILA_DENSITY_OVER` | `0x0C60` | 当前代码仍输出测量中 |
| `STATE_RUNTOPOINTING` | `0x0840` | 向下运动到固定点监测 |
| `STATE_BACKZEROING` | `0x0860` | 提浮子/回零点中 |
| `STATE_STANDBY` | `0x2068` | 零点待机 |
| `STATE_ERROR` | `0x0820` | 异常或传感器拔出类状态 |

### 6.2 当前明确不一致

`STATE_WARTSILA_DENSITY_OVER` 当前输出 `0x0C60`，但源码注释和抓包状态表均指向完成态应为 `0x2840`。

影响：

- 外部主机可能认为设备仍在密度分布测量中。
- 外部主机可能延迟或不触发分布结果读取。
- 和抓包中完成后状态序列不一致。

### 6.3 当前未覆盖的抓包状态

| 抓包状态 | 含义 | 当前情况 |
| --- | --- | --- |
| `0x0864` | 接收到提浮子指令 | 未单独映射 |
| `0x2860` | 提浮子向上运行，气相 | 未单独映射 |
| `0x2848` | 在零点收到分布测量 | 未单独映射 |
| `0x1840` | 下行到最低点，界面附近 | 未单独映射 |
| `0x2840` | 空气中、下行；密度测量完成 | 注释有记录，但当前完成态未输出 |

是否必须补齐这些状态，取决于现场主机是只看大流程状态，还是严格按原 Wartsila 状态字判断步骤。

## 7. 分布点表兼容情况

当前分布点表对外格式：

| 字段 | 寄存器偏移 | 当前含义 |
| --- | --- | --- |
| 点位置 | `base + 0` | `temperature_position / 10`，单位 mm |
| 密度 | `base + 1` | `kg/m3 x10` |
| 温度 | `base + 2` | 现有温度偏移口径 |
| 保留 | `base + 3` | 0 |
| 保留 | `base + 4` | 0 |
| 保留 | `base + 5` | 0 |

其中：

```text
base = 0x0064 + i * 6
i = 0..N-1
```

当前矛盾：

- CPU2 `MAX_MEASUREMENT_POINTS = 200`。
- CPU3 `g_measurement.density_distribution.single_density_data` 支持 200 点。
- Wartsila 寄存器图 `REG_DENSITY_POINT_COUNT = 200`。
- Wartsila 外部临时结构 `wartsila_DeviceParameters.dens_points[100]` 只支持 100 点。
- `DSMToWartsila()` 和 `DeviceParams_StoreToRegisters()` 只循环 100 点。

结论：

- 点表结构方向正确。
- 点数小于等于 100 时，当前具备基本兼容能力。
- 点数超过 100 时，当前不完整兼容。
- 莆田抓包中出现过 114 点，因此该问题不是理论问题。

## 8. 多地址兼容边界

现场抓包存在地址 `1`、`2`、`3`、`4`：

- 地址 `1`：主 LTD/密度分布控制与结果区。
- 地址 `2`、`4`：辅助数据块，存在 `0x00C8/17` 和多组 `33` 寄存器块。
- 地址 `3`：存在设备 ID 类读取，例如 `0x001E/5` 返回 ASCII 编号。

当前 CUBE 行为：

- `modbus_rtu_process()` 只接受 `addr == SlaveAddress`。
- 默认 `SlaveAddress = 0x01`。
- 其它地址不会响应。

当前判断：

- 如果现场改造方案是让上位机只把原地址 `1` 指向 CUBE，则当前单地址架构成立。
- 如果现场上位机仍按原 Wartsila 总线轮询地址 `2`、`3`、`4`，则当前不兼容。
- 后续需要根据现场主机配置确认是否做多地址仿真、地址别名或明确放弃辅助地址响应。

## 9. 当前兼容结论

### 9.1 可以认为已兼容

- Wartsila 协议作为 CPU3 外部协议选项接入。
- Wartsila 默认串口参数 `2400 8E1`。
- 地址 `1` 基本 Modbus RTU 地址、CRC、`0x03`、`0x10` 流程。
- 所有 Wartsila 命令和参数写入仅接受非标准 `0x10 byteCount=qty` 帧，实际数据区为 `2*qty` 字节。
- `0x0006` 命令下发到 CPU2。
- `0x005A~0x005D` 分布测量参数下发到 CPU2。
- CPU2 桥接写在链路不可用或本次下发失败时返回设备忙 `0x06`；参数写结果不确定时恢复写前镜像、关闭参数门禁并强制补读，未确认期间四参数读也返回 `0x06`；其它地址写入不触发 CPU2。
- CPU2 分布结果只有在前后头部同代且 N 个点读取完整后才一次提交；候选期间保留上一代公开点阵并门禁完成态，最终失败发布 `20-13`，同代恢复成功后自动清除。
- `0x0000~0x000F` 主状态区的主要字段。
- `0x0050~0x0053` 分布概要字段。
- `0x0064` 起分布点表的基本结构。

### 9.2 可以认为部分兼容

- 工作状态字：覆盖主要状态，但完成态和若干中间态不完整。
- 分布点表：结构兼容，但容量当前实际只有 100 点。
- 温度/频率倍率：当前有输出，但需要结合现场主机解析复核。
- 液位字段：当前来自 `density_distribution.Density_oil_level`，依赖 CPU2 测量链路及时刷新。

### 9.3 当前不兼容或未实现

- 地址 `2`、`3`、`4` 多从站仿真。
- 地址 `1` 的 `0x0032/23` 扩展块语义。
- 地址 `1` 的 `0x06A4/6` 扩展块。
- 分布点数超过 100 的完整输出。
- Wartsila 完成态 `0x2840`。

## 10. 修复优先级建议

| 优先级 | 项目 | 原因 |
| --- | --- | --- |
| P0 | 将 Wartsila 点表输出从 100 点扩展到 200 点 | 当前与 CPU2/CPU3 数据结构和抓包 114 点场景冲突 |
| P0 | 将 `STATE_WARTSILA_DENSITY_OVER` 映射为现场完成态，优先复核 `0x2840` | 影响主机判断测量完成和读取结果 |

确认莆田现场格式进入命令处理链路并回显起始地址和数量；标准格式、截短、超长或其它 `byteCount` 均返回 `0x03`，且不写寄存器、不下发 CPU2。

6. 复放地址 `1` 的 `0x0032/23` 和 `0x06A4/6`，确认主机是否要求有效响应。
7. 在外部主机持续交替读取 `0x0007`、`0x0050` 和 `0x0064` 点表时，分别注入单块失败、整轮失败、20 秒无进展、CPU2 重启和同代恢复；确认候选期间只看到上一代完整点阵或空快照，不出现新完成头配旧/部分点阵，最终失败进入 `20-13`，恢复后一次切换到完整新代际。
8. 分别在状态/参数/当前连接协议快照未完成、共享协议不兼容、通信故障锁存和本次 CPU2 ACK 失败时写 `0x0006`、`0x005A~0x005D`，确认主站收到设备忙 `0x06`，而非成功回显。
9. 写不包含 `0x0006/0x005A~0x005D` 的其它合法保持寄存器，确认只更新本地寄存器池，不触发四个 CPU2 参数请求。
10. 在四参数顺序同步的第 1～4 个请求分别注入 TX 失败、超时、非法响应或 ACK 丢失，确认立即恢复 CPU3 写前镜像、参数快照失效、同轮其它 COM 普通命令被阻止，且即使 `parameter_update_flag` 不变也主动补读四组。
11. 在上述失败后立即读取 `0x005A~0x005D`，确认返回 `0x06`；补读全部成功后再次读取，确认返回 CPU2 实际部分/完整生效值。主站再按目标值重试并回读到一致，不能要求失败前已生效字段自动回滚。

13. 让 `0x0006` 非零命令下发失败，再单独向 `0x0006` 写 0，确认旧命令影子已清除且 CPU2 不会重放上一次命令；主站若要重试，必须重新写入原非零命令。
