# CPU3 外部 COM 协议切换帧与上位机使用说明

## 1. 文档目的

本文说明如何通过上位机向 CPU3 的 COM1、COM2 或 COM3 发送统一管理帧，把当前端口切换到以下任一外部协议：

- DSM。
- Wartsila。
- LTD。
- SI。

管理帧由 CPU3 在当前业务协议解析前优先识别，因此应用层帧格式不依赖端口当前运行的业务协议。上位机只要使用端口当前的串口物理参数发出合法管理帧，就可以请求切换目标协议。

如果上位机不知道当前串口物理参数，可使用仓库内的自动工具依次轮询四组标准参数。本文同时给出自动工具、手工串口工具和自研上位机三种使用方式。

本功能具有以下边界：

- 只修改收到管理帧的当前 COM 口，不修改另外两个外部 COM 口。
- 只修改 CPU3 本机通信参数，不修改 CPU2 参数。
- 不改变 CPU2/CPU3 共享协议版本 `DEVICE_PROTOCOL_VERSION`。
- 继续复用现有 CPU3 参数存储结构，不改变 `CPU3_PARAM_VERSION`。
- 管理帧没有身份认证，不能替代现场网络访问控制。

## 2. 快速使用

### 2.1 使用前准备

准备以下环境：

1. 已包含协议切换功能的 CPU3 固件。
2. 一只支持目标波特率和奇偶校验的 USB-RS485 适配器。
3. 正确连接目标 CPU3 COM 口的 RS485 A、B，必要时连接通信参考地。
4. Windows 上可使用的 Python 3。
5. 已知设备从站地址，默认示例使用站号 `1`。

安装 Python 串口依赖：

```powershell
py -m pip install pyserial
```

查看计算机当前串口：

```powershell
py -m serial.tools.list_ports
```

以下示例假设 USB-RS485 适配器是 `COM5`，设备从站地址是 `1`。

### 2.2 一条命令完成切换

切换为 DSM：

```powershell
py tools\cpu3_protocol_switch.py --port COM5 --address 1 --target dsm
```

切换为 Wartsila：

```powershell
py tools\cpu3_protocol_switch.py --port COM5 --address 1 --target wartsila
```

切换为 LTD：

```powershell
py tools\cpu3_protocol_switch.py --port COM5 --address 1 --target ltd
```

切换为 SI：

```powershell
py tools\cpu3_protocol_switch.py --port COM5 --address 1 --target si
```

工具会自动完成以下动作：

1. 生成目标协议对应的 8 字节切换请求。
2. 依次用四组标准串口参数寻找设备。
3. 每组参数默认发送 2 次，每次等待 300 ms。
4. 忽略 USB-RS485 适配器可能产生的本地请求回显。
5. 收到设备独立 ACK 后停止扫描。
6. 等待 1.2 秒，让 CPU3 完成 FRAM 保存和 UART 重初始化。
7. 使用目标协议标准参数重新打开串口。
8. 再次发送管理帧并检查 ACK，确认目标串口参数已经可通信。

只有工具输出以下文字并返回退出码 `0`，才表示自动切换与目标参数复验均成功：

```text
切换成功并已在目标参数验证：<目标协议和串口参数>
```

## 3. 协议与标准串口参数

### 3.1 目标协议编码

| 目标协议值 | 工具参数 | 协议 | 切换后的标准串口参数 |
| ---: | --- | --- | --- |
| `0` | `dsm` | DSM | 4800 8N1 |
| `1` | `wartsila` | Wartsila | 2400 8E1 |
| `2` | `ltd` | LTD | 115200 8N1 |
| `5` | `si` | SI | 9600 8O1 |

其中：

- `8N1` 表示 8 数据位、无校验、1 停止位。
- `8E1` 表示 8 数据位、偶校验、1 停止位。
- `8O1` 表示 8 数据位、奇校验、1 停止位。

切换帧只携带目标协议，不允许单独指定波特率、数据位、校验位或停止位。切换到不同协议时，CPU3自动应用上表中的整组标准参数，避免形成没有约定的参数组合。

### 3.2 自动扫描顺序

不知道端口当前参数时，工具固定按照以下顺序扫描：

1. DSM：4800 8N1。
2. Wartsila：2400 8E1。
3. LTD：115200 8N1。
4. SI：9600 8O1。

每组参数收到完整独立 ACK 后立即停止扫描，不会继续向其它参数组合发送请求。

当前 CPU3 菜单仍允许人工单独调整串口物理字段。如果现场参数已被改成上述四组以外的组合，自动工具无法发现该端口。此时需要使用已知的自定义参数手工发帧，或者先通过本机菜单恢复为标准配置。

### 3.3 相同协议请求的行为

如果目标协议与端口当前协议相同，CPU3仍会返回正常 ACK，便于上位机做幂等重试；不会重复执行协议切换。

需要特别注意：如果当前协议已经等于目标协议，但物理参数曾被人工改成非标准组合，相同协议请求不会强制把物理参数恢复成标准值。此类情况应通过本机菜单修正物理参数，或先切换到另一个协议再切回目标协议。

## 4. 管理帧定义

### 4.1 请求帧

统一切换请求固定为 8 字节：

```text
[从站地址] [0x46] [0x4C] [0x54] [0x44] [目标协议] [CRC低] [CRC高]
```

| 偏移 | 长度 | 字段 | 固定值或说明 |
| ---: | ---: | --- | --- |
| 0 | 1 | 从站地址 | CPU3 当前 `SlaveAddress`，范围 `1~247`；不支持广播地址 `0` |
| 1 | 1 | 功能码 | `0x46`，项目自定义管理功能码 |
| 2 | 1 | Magic 1 | `0x4C`，ASCII `L` |
| 3 | 1 | Magic 2 | `0x54`，ASCII `T` |
| 4 | 1 | Magic 3 | `0x44`，ASCII `D` |
| 5 | 1 | 目标协议 | `0=DSM`、`1=Wartsila`、`2=LTD`、`5=SI` |
| 6 | 2 | CRC16 | Modbus RTU CRC16，覆盖偏移 `0~5`，低字节在前、高字节在后 |

发送时必须连续发送完整 8 字节，不要自动追加回车、换行或其它结束符。

### 4.2 正常 ACK

合法请求返回独立的 6 字节 ACK：

```text
[从站地址] [0x46] [0x00] [目标协议] [CRC低] [CRC高]
```

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 1 | 从站地址 | 与请求地址相同 |
| 1 | 1 | 功能码 | `0x46` |
| 2 | 1 | 状态 | `0x00` 表示请求已接受 |
| 3 | 1 | 目标协议 | 与请求目标协议相同 |
| 4 | 2 | CRC16 | 覆盖偏移 `0~3`，低字节在前、高字节在后 |

ACK 使用切换前的旧串口参数发送。上位机必须先在旧参数下完整接收 ACK，再关闭旧串口配置并等待设备重配。

ACK 表示“设备已识别并接受请求，且 ACK 已经发出”，不等价于“FRAM 保存和目标 UART 重初始化已经完成”。最终成功必须满足以下至少一项：

- 在目标标准参数下再次收到匹配 ACK。
- 在目标标准参数下收到目标业务协议的正确响应。

### 4.3 本地回显与真实 ACK 的区别

部分 USB-RS485 适配器会把主机刚发送的字节回送到接收缓冲区。本地回显等于原始 8 字节请求：

```text
[地址] 46 4C 54 44 [目标协议] [CRC低] [CRC高]
```

设备真实 ACK 是不同的 6 字节帧：

```text
[地址] 46 00 [目标协议] [CRC低] [CRC高]
```

上位机只能把地址、功能码、状态、目标协议和 CRC 全部匹配的 6 字节 ACK 判定为成功。看到原始 8 字节请求只能说明适配器产生了回显，不能证明 CPU3 收到请求。

### 4.4 非法目标协议异常帧

目标协议为 `3`、`4` 或其它未实现值时，CPU3返回 Modbus 异常帧：

```text
[从站地址] [0xC6] [0x03] [CRC低] [CRC高]
```

其中：

- `0xC6` 是功能码 `0x46 | 0x80`。
- `0x03` 表示非法数据值。
- 收到该异常帧后，上位机不应继续等待设备切换。

### 4.5 不应答和非管理帧情况

| 输入情况 | CPU3 管理帧处理行为 |
| --- | --- |
| 地址、功能码或 Magic 不匹配 | 不作为管理帧处理，后续行为由当前业务协议决定 |
| 帧长度不是 8 字节 | 不作为管理帧处理 |
| 地址、功能码和 Magic 已匹配，但 CRC 错误 | 静默丢弃，不返回异常，也不交给当前业务协议 |
| 目标协议未实现 | 返回 `0xC6/0x03` 异常帧，不修改配置 |
| 合法目标协议 | 返回独立 ACK；目标不同于当前协议时进入延迟切换流程 |

## 5. 站号 1 Golden Frame

### 5.1 合法目标协议

| 目标协议 | 请求帧 | 正常 ACK |
| --- | --- | --- |
| DSM | `01 46 4C 54 44 00 EC 45` | `01 46 00 00 E0 0D` |
| Wartsila | `01 46 4C 54 44 01 2D 85` | `01 46 00 01 21 CD` |
| LTD | `01 46 4C 54 44 02 6D 84` | `01 46 00 02 61 CC` |
| SI | `01 46 4C 54 44 05 2C 46` | `01 46 00 05 20 0E` |

### 5.2 非法目标协议

站号 1、目标协议值 `3`：

```text
请求：01 46 4C 54 44 03 AC 44
异常：01 C6 03 33 A1
```

修改从站地址或目标协议后必须重新计算 CRC，不能直接复用站号 1 的 CRC 字节。

## 6. 命令行工具详细说明

### 6.1 命令格式

```powershell
py tools\cpu3_protocol_switch.py `
  --port <串口号> `
  --address <站号> `
  --target <dsm|wartsila|ltd|si> `
  [--attempts <次数>] `
  [--timeout <秒>] `
  [--settle <秒>]
```

查看内置帮助：

```powershell
py tools\cpu3_protocol_switch.py --help
```

### 6.2 参数说明

| 参数 | 是否必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `--port` | 是 | 无 | Windows 串口名，例如 `COM5` |
| `--target` | 是 | 无 | 目标协议：`dsm`、`wartsila`、`ltd`、`si` |
| `--address` | 否 | `1` | CPU3 从站地址，合法范围 `1~247` |
| `--attempts` | 否 | `2` | 每组当前参数以及目标参数复验的发送次数，必须大于 0 |
| `--timeout` | 否 | `0.3` | 每次发送后等待匹配 ACK 的秒数，必须大于 0 |
| `--settle` | 否 | `1.2` | 收到旧参数 ACK 后等待设备应用新参数的秒数，不能为负数 |

线路较长、USB 转换器延迟较大或 CPU2 通信处于异常超时时，可适当提高等待值：

```powershell
py tools\cpu3_protocol_switch.py `
  --port COM5 `
  --address 1 `
  --target si `
  --attempts 3 `
  --timeout 0.5 `
  --settle 1.5
```

不建议把 `--settle` 调小到 1 秒以内。CPU3 主循环可能正在等待 CPU2 同步响应，现有单次等待最长约 1 秒。

### 6.3 正常输出示例

从 DSM 参数切换到 SI 的典型输出：

```text
切换帧：01 46 4C 54 44 05 2C 46
预期应答：01 46 00 05 20 0E
尝试当前参数：DSM 4800 8N1
  第 1 次收到独立 ACK，设备已接受切换。
切换成功并已在目标参数验证：SI 9600 8O1
```

### 6.4 工具退出码

| 退出码 | 含义 | 建议处理 |
| ---: | --- | --- |
| `0` | 已收到旧参数 ACK，并在目标参数下复验成功 | 可以继续使用目标业务协议通信 |
| `1` | 四组参数均未收到 ACK，或旧参数收到 ACK 后目标参数复验失败 | 检查线路、站号、等待时间和 CPU3 配置 |
| `2` | 参数非法、缺少 `pyserial`，或命令行用法错误 | 修正运行环境或参数后重新执行 |

串口不存在、串口被占用或访问被拒绝时，工具会打印“串口访问失败”。如果所有扫描尝试均失败，最终退出码为 `1`。

## 7. 使用通用串口工具手工切换

没有 Python 环境时，可以使用支持十六进制发送和奇偶校验配置的串口工具。

### 7.1 已知当前参数

以“站号 1、切换到 SI”为例：

1. 用端口当前物理参数打开串口。
2. 选择十六进制发送与十六进制显示。
3. 关闭自动追加回车、换行和其它结束符。
4. 清空接收窗口。
5. 连续发送 `01 46 4C 54 44 05 2C 46`。
6. 忽略可能出现的相同 8 字节本地回显。
7. 确认收到真实 ACK `01 46 00 05 20 0E`。
8. 关闭旧参数串口，至少等待 1.2 秒。
9. 使用 SI 标准参数 9600 8O1 重新打开串口。
10. 再次发送同一管理帧，确认仍能收到 `01 46 00 05 20 0E`。
11. 最后发送一条 SI 业务查询帧，确认业务协议响应正确。

### 7.2 不知道当前参数

按照以下四组参数依次执行发送步骤，每组建议尝试 2 次：

1. 4800 8N1。
2. 2400 8E1。
3. 115200 8N1。
4. 9600 8O1。

收到真实独立 ACK 后立即停止扫描，进入目标参数复验。不要把请求原帧回显当成设备 ACK。

## 8. CPU3 内部切换时序

### 8.1 正常时序

| 阶段 | CPU3 行为 | 上位机行为 |
| ---: | --- | --- |
| 1 | 在当前协议分发前识别管理帧 | 使用端口当前参数发送 8 字节请求 |
| 2 | 校验地址、长度、功能码、Magic、目标协议和 CRC | 等待 6 字节独立 ACK |
| 3 | 只在 RAM 中暂存目标协议 | 仍保持旧串口参数 |
| 4 | 使用旧参数发送独立 ACK | 完整接收并校验 ACK |
| 5 | DMA 最后一帧发送完成后只标记待应用状态 | 关闭旧串口配置并等待至少 1.2 秒 |
| 6 | 暂停目标端口 RX DMA，避免旧参数数据进入新协议 | 不继续用旧参数发送业务帧 |
| 7 | 主循环应用目标协议和标准参数 | 等待设备重配置 |
| 8 | 保存 FRAM并立即读回校验 | 不把旧参数 ACK直接当成最终成功 |
| 9 | 只重初始化收到请求的当前 COM 口 | 用目标标准参数重新打开串口 |
| 10 | 在新参数下恢复 RX DMA | 重发管理帧或业务查询进行复验 |

### 8.2 异常时序

- ACK DMA 启动失败：CPU3取消待切换状态，恢复旧参数接收，不修改协议。
- ACK DMA 续发失败：CPU3取消待切换状态，清理发送状态并恢复旧参数接收。
- ACK 发送期间发生 UART 错误：CPU3取消尚未完成的切换并恢复接收。
- FRAM 写后读回校验失败：CPU3恢复旧端口配置，尝试把旧配置回写 FRAM，并按旧参数恢复接收。
- 目标 UART 重初始化失败：上位机目标参数复验不会通过，应通过本机菜单或重新上电检查当前配置。

## 9. 自研上位机推荐流程

### 9.1 最小状态机

建议上位机实现以下状态：

```text
生成请求和预期 ACK
        |
        v
按四组标准参数逐组扫描
        |
        +-- 仅收到请求回显 ----------> 忽略并继续等待
        |
        +-- 超时 --------------------> 重试或下一组参数
        |
        +-- 收到异常帧 --------------> 终止并报告目标协议非法
        |
        +-- 收到匹配独立 ACK
                    |
                    v
             关闭旧串口并等待
                    |
                    v
             使用目标参数重新打开
                    |
                    v
             重发管理帧或业务查询
                    |
                    +-- 成功 ----------> 切换完成
                    +-- 失败 ----------> 报告切换后验证失败
```

### 9.2 ACK 判定条件

至少同时检查：

1. 帧长度为 6 字节。
2. 从站地址等于请求地址。
3. 功能码等于 `0x46`。
4. 状态等于 `0x00`。
5. 目标协议等于本次请求目标。
6. Modbus RTU CRC16正确。

接收缓冲区可能同时包含本地回显、噪声字节和真实 ACK。解析器应在字节流中寻找完整匹配 ACK，不能只比较第一帧或只检查功能码。

### 9.3 重试和幂等性

- 相同目标请求可重复发送，正常情况下不会造成参数持续变化。
- 每组标准参数建议重试 2 次，不建议无限重试。
- 一旦在某组旧参数下收到匹配 ACK，应停止其它参数扫描。
- 收到 ACK 后不要立即使用目标参数发送，应保留设备应用窗口。
- 目标参数复验失败时，不要直接宣告成功；应提示现场检查或读取本机菜单配置。

## 10. 常见问题排查

| 现象 | 可能原因 | 建议检查 |
| --- | --- | --- |
| 打不开串口 | COM 号错误、串口被其它程序占用、权限问题 | 使用 `py -m serial.tools.list_ports` 确认端口，关闭其它串口软件 |
| 接收窗口只出现与请求相同的 8 字节 | USB-RS485 本地回显，设备没有真实应答 | 检查 A/B 接线、站号、当前参数和固件版本；不要判定成功 |
| 四组标准参数全部无 ACK | 站号错误、A/B 反接、端口不是目标 COM、现场使用自定义参数、固件不支持 | 核对站号和端口，通过本机菜单查看物理参数 |
| 收到 `01 C6 03 ...` | 目标协议值未实现 | 只使用 `0`、`1`、`2`、`5` |
| 旧参数收到 ACK，但目标参数复验失败 | 等待不足、FRAM 校验失败并回滚、UART 重初始化失败、目标参数设置错误 | 把 `--settle` 提高到 1.5 秒，检查 CPU3 日志和本机菜单 |
| 重启后恢复旧协议 | 切换未真正持久化或使用了不支持该功能的固件 | 重新执行并确认目标参数复验；检查 FRAM 和固件版本 |
| 通信偶发成功 | RS485终端匹配、偏置、接地或干扰问题 | 检查终端电阻、屏蔽、参考地和线缆长度，适当增加超时 |
| 自动工具失败，但菜单设置后正常 | 当前物理参数不在四组标准扫描范围内 | 恢复标准参数或使用已知自定义参数手工发送管理帧 |
| 相同协议请求收到 ACK但参数没有归一化 | 当前协议已等于目标协议，固件按幂等请求处理 | 用菜单修正物理参数，或先切到其它协议再切回 |

## 11. 安全与兼容边界

### 11.1 安全边界

- CRC16只能检查传输差错，不能证明发送方身份。
- 任意能够访问目标 RS485链路并知道站号的设备都可能发送管理帧。
- 现场存在未授权访问风险时，应通过物理隔离、网关访问控制、维护模式或后续认证机制限制管理帧入口。
- 不建议在正常业务高峰期反复扫描和切换协议。

### 11.2 兼容性边界

- 该功能属于 CPU3 外部协议扩展，不新增 CPU2 命令、共享寄存器、共享状态或共享参数字段。
- CPU2/CPU3 共享协议版本 `DEVICE_PROTOCOL_VERSION` 保持不变。
- CPU3继续使用 `Cpu3CommAndDisplayParams.com1/com2/com3` 保存配置，参数存储结构版本保持不变。
- 旧 CPU3 固件不识别该管理帧时，可能静默丢弃，也可能由当前业务协议接收后拒绝；上位机应以是否收到独立 ACK作为功能支持判据。
- 新 ACK 与 8 字节请求格式不同。只接受“原请求回显”的旧上位机逻辑不适用于当前实现。

## 12. 联调与验收清单

### 12.1 基础功能

- [ ] 从 DSM 当前参数切换到 Wartsila、LTD 和 SI。
- [ ] 从 Wartsila 当前参数切换到 DSM、LTD 和 SI。
- [ ] 从 LTD 当前参数切换到 DSM、Wartsila 和 SI。
- [ ] 从 SI 当前参数切换到 DSM、Wartsila 和 LTD。
- [ ] 对四个协议分别重复发送相同目标请求，确认 ACK稳定且通信不中断。
- [ ] 切换后重新上电，确认目标协议和物理参数保持。
- [ ] 确认只修改收到请求的当前 COM 口，另外两个 COM 口参数不变。

### 12.2 异常与边界

- [ ] 使用错误站号发送，确认不会被判定为切换成功。
- [ ] 修改请求 CRC，确认 CPU3不返回管理帧 ACK。
- [ ] 使用目标值 `3`，确认收到 `0xC6/0x03` 异常帧。
- [ ] 使用带本地回显的 USB-RS485适配器，确认原请求回显不会被判定为成功。
- [ ] ACK 后立即使用目标参数发送，验证上位机不会因等待不足误判。
- [ ] 注入 FRAM 写入或读回失败，确认设备恢复旧配置且目标参数复验失败。
- [ ] 注入 UART DMA 发送失败，确认配置不发生切换。
- [ ] 检查长线、干扰和不同 USB-RS485适配器下的重试与超时行为。

### 12.3 通过标准

完整通过应同时满足：

1. 旧参数下收到与目标一致且 CRC 正确的独立 ACK。
2. 等待设备重配后，目标标准参数下可以再次收到独立 ACK或目标业务响应。
3. CPU3重新上电后仍保持目标协议。
4. 非目标 COM 口没有被重初始化或修改配置。
5. 请求原帧回显、错误 CRC和错误地址均不会导致上位机误报成功。
