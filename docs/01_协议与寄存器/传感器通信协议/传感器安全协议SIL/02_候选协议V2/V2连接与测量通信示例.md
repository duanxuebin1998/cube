# V2 连接与测量通信示例

文档状态：精简候选版联调示例，未实现、未形成认证证据。

对应协议：[传感器安全通信协议 V2 精简候选版](传感器安全通信协议V2.md)。

示例日期：2026-08-07。

> 本文回答“CPU2 发什么、传感器回什么、整个测量过程怎样进行”。示例字节可用于评审和后续 golden frame 输入，但正式机器契约冻结前不能作为量产常量。

## 1. 最短流程

```text
控制阶段，双向：
CPU2 -> DM4    HELLO
CPU2 <- DM4    HELLO_RSP，新 session_id
CPU2 -> DM4    START_STREAM
CPU2 <- DM4    START_STREAM_RSP，完整回显

安全运行阶段，单向：
CPU2 <- DM4    ACTIVE_REPORT，stream_seq=1
CPU2 <- DM4    ACTIVE_REPORT，stream_seq=2
CPU2 <- DM4    ACTIVE_REPORT，stream_seq=3
...            CPU2 不查询、不 ACK、不发送同步帧

退出阶段，双向：
CPU2 -> DM4    STOP_STREAM
CPU2 <- DM4    STOP_STREAM_RSP
                DM4 静默，旧 session_id 失效
```

这里的“单向通信”只指安全运行阶段。建立会话、启动和停止仍是 CPU2 发起的双向控制通信。

## 2. 示例固定条件

### 2.1 节点和 Profile

| 项 | 示例值 | 说明 |
| --- | --- | --- |
| CPU2 地址 | `0x01` | 唯一控制发起方 |
| DM4 地址 | `0x10` | 本次唯一活动端点 |
| 预留端点 B | `0x11` | 本流程全程静默 |
| 协议版本 | `0x02` | V2 |
| DM4 `sensor_type` | `0x01` | 静态配置 |
| `profile_id` | `0x01` | `DM4_RUNTIME_V1` |
| `profile_version` | `0x01` | 初版 |
| `safety_function_id` | `0x01` | 密度/黏度功能 |
| 必需字段掩码 | `0x1FC4` | 示例静态契约 |

### 2.2 会话和配置

| 项 | 示例值 | 说明 |
| --- | --- | --- |
| `host_nonce` | `0x01020304` | CPU2 每次 HELLO 生成的新鲜非零值 |
| `sensor_nonce` | `0xA1B2C3D4` | DM4 每次 HELLO 生成的新鲜非零值 |
| `session_id` | `0x01020304A1B2C3D4` | 高 32 位为 host nonce，低 32 位为 sensor nonce |
| `device_id` | `0x444D340000000001` | 示例设备身份，线上小端发送 |
| `profile_contract_crc32` | `0x89ABCDEF` | 仅为演示占位值 |
| `profile_config_crc32` | `0xB41AB6B0` | 由本示例静态 Profile 规范化计算 |
| `safety_param_crc32` | `0x11223344` | 仅为演示占位值 |
| `profile_catalog_crc32` | `0x59FAC335` | 由按 DM4 `sensor_type=0x01` 过滤后的示例目录规范化计算 |

`profile_contract_crc32` 和 `safety_param_crc32` 尚不是正式项目值，因此由它们派生的配置摘要和帧 CRC 也只是自洽示例值。

本例按正文目录规则形成一个 16 字节输入：`catalog_version=1`、`entry_count=1`，随后是 DM4 的 12 字节生产模板条目。其完整小端字节为：

```text
01 00 01 00 01 01 01 2C 01 00 C4 1F B0 B6 1A B4
```

对该序列计算 CRC32C 得到 `profile_catalog_crc32=0x59FAC335`。增加其它 `sensor_type` 的模板前先过滤，因此不会改变这个 DM4 目录向量。

### 2.3 静态时序

| 项 | 示例值 |
| --- | ---: |
| 上报周期 | 500 ms |
| 允许相邻 SOF 间隔 | 450～550 ms |
| START 响应后首帧超时 | 150 ms |
| STOP 发起窗口 | 150 ms |
| 总线空闲保护 | 5 ms |
| 停止后静默确认 | 700 ms |
| 最大数据年龄 | 750 ms |

这些值由双方编译期 Profile 固定，不在 START 时动态协商。

本例的 `transaction_seq=1/2/3` 分别对应 HELLO、START 和 STOP 三次实际发送。V2 不原字节重发控制请求；HELLO 超时必须使用新的 `host_nonce` 和新事务序号，START/STOP 结果不确定则使用新 HELLO 清场。

## 3. 上电和清场

CPU2 上电后先保持接收并监听至少 700 ms。若总线上出现任何未知主动发送，CPU2 不进入安全运行。

在总线确认空闲后，CPU2 可以依次向已配置端点发送 HELLO。一个完整合法的 HELLO 对传感器具有“先停止旧流，再建立新会话”的语义，因此 CPU2 重启后不需要知道传感器是否还保留旧状态。

本例仅启动 DM4。端点 B 即使完成 HELLO，也只能保持 `CONTROL_READY`，不能主动发送运行帧。

## 4. 第一步：HELLO

### 4.1 CPU2 发送 HELLO 请求

控制字段：

```text
frame_type          = 0xC1
src_id              = 0x01
dst_id              = 0x10
protocol_version    = 0x02
command             = 0x01
transaction_seq     = 1
result_code         = 0
session_id          = 0
payload_version     = 1
expected_sensor_type= 0x01
host_nonce          = 0x01020304
```

完整 32 字节帧：

```text
A5 5A C1 20 01 10 02 01 01 00 00 00 00 00 00 00
00 00 00 00 01 01 00 00 04 03 02 01 82 37 6C EF
```

末尾 `82 37 6C EF` 是小端 CRC32C，即 `0xEF6C3782`。

### 4.2 DM4 处理 HELLO

DM4 收到完整合法请求后按顺序执行：

1. 取消任何尚未发送的旧运行帧，停止旧流。
2. 使旧 `session_id` 失效。
3. 检查目的地址、协议版本和期望传感器类型。
4. 生成新的非零 `sensor_nonce=0xA1B2C3D4`。
5. 建立 `session_id=0x01020304A1B2C3D4`。
6. 进入 `CONTROL_READY`，但仍不主动上报。

### 4.3 DM4 返回 HELLO 成功响应

响应附带设备身份和按 DM4 `sensor_type` 过滤后的 Profile 目录摘要：

```text
frame_type           = 0xC2
src_id               = 0x10
dst_id               = 0x01
command              = 0x01
transaction_seq      = 1
result_code          = 0
session_id           = 0x01020304A1B2C3D4
payload_version      = 1
sensor_type          = 0x01
sensor_state         = CONTROL_READY(0x01)
device_id            = 0x444D340000000001
profile_catalog_crc32= 0x59FAC335
```

完整 40 字节帧：

```text
A5 5A C2 28 10 01 02 01 01 00 00 00 D4 C3 B2 A1
04 03 02 01 01 01 01 00 01 00 00 00 00 34 4D 44
35 C3 FA 59 66 BB B3 00
```

末尾 CRC32C 为 `0x00B3BB66`。

### 4.4 CPU2 的 HELLO 门禁

CPU2 只有在以下条件全部成立时记录新会话：

- 响应 CRC、固定长度、地址、协议版本、命令和事务序号均正确；
- `sensor_type`、`device_id` 和静态端点配置一致；
- `sensor_state=CONTROL_READY`；
- 会话高 32 位等于本次 `host_nonce`，低 32 位非 0；
- 完整会话未在近期会话保留集合中出现；
- `profile_catalog_crc32` 与 CPU2 按当前端点 `sensor_type=0x01` 过滤后的登记值一致；CPU2 中其它传感器类型的注册项不参与本次摘要。

任一条件失败，CPU2 不发送 START，DM4 继续保持静默。

## 5. 第二步：START_STREAM

### 5.1 Profile 配置摘要的来源

密度/黏度示例对以下 28 字节计算 CRC32C：

```text
02 01 01 01 01 2C C4 1F F4 01 C2 01 26 02 96 00
96 00 05 00 BC 02 EE 02 EF CD AB 89
```

对应字段依次为协议版本、传感器类型、Profile、功能、负载长度、必需字段、周期、间隔上下限、首帧超时、停止窗口、总线空闲保护、静默确认、最大年龄和 Profile 契约摘要。计算结果：

```text
profile_config_crc32 = 0xB41AB6B0
```

这使 CPU2 和 DM4 能在 4 字节内核对双方是否使用同一份静态运行契约。

### 5.2 CPU2 发送 START_STREAM

```text
frame_type          = 0xC1
command             = 0x20
transaction_seq     = 2
session_id          = 0x01020304A1B2C3D4
payload_version     = 1
profile_id          = 0x01
profile_version     = 0x01
safety_function_id  = 0x01
profile_config_crc32= 0xB41AB6B0
safety_param_crc32  = 0x11223344
```

完整 36 字节帧：

```text
A5 5A C1 24 01 10 02 20 02 00 00 00 D4 C3 B2 A1
04 03 02 01 01 01 01 01 B0 B6 1A B4 44 33 22 11
5D E2 B9 58
```

末尾 CRC32C 为 `0x58B9E25D`。

### 5.3 DM4 返回 START_STREAM 成功响应

DM4 只有在会话、Profile、功能、配置摘要、安全参数摘要、测量模式和自检状态全部匹配时才返回 `OK`。成功响应必须逐字节回显 12 字节 START 负载，不允许私自修改周期、阈值或功能。

完整 36 字节帧：

```text
A5 5A C2 24 10 01 02 20 02 00 00 00 D4 C3 B2 A1
04 03 02 01 01 01 01 01 B0 B6 1A B4 44 33 22 11
CD 56 08 6E
```

末尾 CRC32C 为 `0x6E0856CD`。

### 5.4 双方切换状态

```text
DM4：成功响应最后一个 CRC 字节发送完成
     -> 进入 FIRST_REPORT_PENDING
     -> 首帧 SOF 必须在 150 ms 内开始发送
     -> 发送 stream_seq=1 的首帧并进入 UPLINK_ACTIVE

CPU2：完整验证 START 响应
      -> 设置 active_endpoint_id=0x10
      -> 进入 RX_ONLY_ACTIVE
      -> 关闭所有常规发送入口
      -> 接收DMA持续工作，可无缝承接背靠背到达的首帧
```

如果 START 响应丢失，DM4 可能已经启动，但 CPU2 不能采用任何运行数据。CPU2 应在确认总线空闲后用新的 `host_nonce`、新的事务序号和新的 HELLO 安全停止该流并重新建立会话，不能用原会话重复 START。

## 6. 第三步：DM4 主动上报

### 6.1 示例首帧

示例首帧关键值：

```text
frame_type           = 0xA2
frame_len            = 92
src_id/dst_id        = 0x10 / 0x01
sensor_type          = 0x01
profile/function     = 0x01 / 0x01
session_id           = 0x01020304A1B2C3D4
stream_seq           = 1
sample_counter       = 500
data_age_ms          = 20
profile_config_crc32 = 0xB41AB6B0
safety_param_crc32   = 0x11223344
safety_status        = 0x007F
safety_diag          = 0x0000
field_valid_mask     = 0x1FFF
signal_quality       = 95
```

完整 92 字节帧：

```text
0000: A5 5A A2 5C 10 01 02 01 01 01 01 00 D4 C3 B2 A1
0010: 04 03 02 01 01 00 00 00 F4 01 00 00 14 00 00 00
0020: B0 B6 1A B4 44 33 22 11 7F 00 00 00 FF 1F 5F 00
0030: A4 01 90 01 00 00 04 00 E2 04 00 00 90 7F 4F 00
0040: B2 89 00 00 E6 09 80 42 01 00 D2 04 00 00 D7 05
0050: 00 00 C0 5D 7D 00 B5 FF D2 81 7A 2F
```

末尾 CRC32C 为 `0x2F7A81D2`。

该帧包含的 DM4 Profile 数据为：

| 字段 | 原始值 | 换算值 |
| --- | ---: | ---: |
| `software_version_x100` | 420 | 4.20 |
| `storage_version_x100` | 400 | 4.00 |
| `dm4_status_raw` | `0x00040000` | 保留原 DM4 状态语义 |
| `magnetic_zero_mv` | 1250 | 1.250 V |
| `level_frequency_hz_x1000` | 5,210,000 | 5210.000 Hz |
| `water_capacitance_pf_x1000` | 35,250 | 35.250 pF |
| `temperature_c_x100` | 2534 | 25.34 ℃ |
| `density_kg_m3_x100` | 82,560 | 825.60 kg/m³ |
| `dynamic_viscosity_cp_x100` | 1234 | 12.34 cP |
| `kinematic_viscosity_cst_x100` | 1495 | 14.95 cSt |
| `supply_voltage_mv` | 24,000 | 24.000 V |
| `angle_x_deg_x100` | 125 | 1.25° |
| `angle_y_deg_x100` | -75 | -0.75° |

### 6.2 CPU2 是否采用该帧

CPU2 必须先把整帧解析到临时对象，再统一执行门禁。只有下列检查全部通过，才原子替换安全快照：

1. 帧类型、92 字节固定长度和 CRC32C 正确。
2. 地址、类型、Profile、版本和安全功能与当前活动端点一致。
3. `session_id` 与 START 会话完全一致。
4. 首帧 `stream_seq=1`；后续每帧严格加 1。
5. `sample_counter` 严格前进且增量合理。
6. 相邻 SOF 间隔在 450～550 ms。
7. 两个配置摘要与 START 记录一致。
8. 必需状态位已置位，拒绝诊断位未置位。
9. 必需字段有效、质量合格、数值范围和变化率合格。
10. 发送端年龄与 CPU2 本地累计年龄均未超限。

任一项失败，整帧不更新安全快照；不能只采用其中看似正常的密度或温度字段。

### 6.3 后续周期

```text
t = 150 ms   DM4 -> CPU2  ACTIVE_REPORT，stream_seq=1（本示例恰在首帧超时上限发送）
t = 650 ms   DM4 -> CPU2  ACTIVE_REPORT，stream_seq=2
t = 1150 ms  DM4 -> CPU2  ACTIVE_REPORT，stream_seq=3
...
```

运行期间 CPU2 不发送任何内容。DM4 不等待 ACK，也不重发旧快照。若没有新的完整快照，或出现禁止继续上报的内部故障，DM4 进入 `FAULT_SILENT`；CPU2 由本地接收超时撤销安全数据。

## 7. 第四步：STOP_STREAM

### 7.1 CPU2 先撤销快照

CPU2 在业务要求停止或切换端点时，先将当前安全快照标记为不可用。然后等待当前帧尝试结束以及至少 5 ms 总线空闲，再在 150 ms 停止窗口内发送 STOP。

### 7.2 CPU2 发送 STOP_STREAM

```text
frame_type      = 0xC1
command         = 0x21
transaction_seq = 3
session_id      = 0x01020304A1B2C3D4
payload         = 空
```

完整 24 字节帧：

```text
A5 5A C1 18 01 10 02 21 03 00 00 00 D4 C3 B2 A1
04 03 02 01 96 05 CB CB
```

末尾 CRC32C 为 `0xCBCB0596`。

### 7.3 DM4 返回 STOP_STREAM 成功响应

DM4 停止后续报告，返回无负载响应：

```text
A5 5A C2 18 10 01 02 21 03 00 00 00 D4 C3 B2 A1
04 03 02 01 9D 3D 52 3D
```

末尾 CRC32C 为 `0x3D523D9D`。响应发送完成后，DM4 使当前会话失效并进入 `INACTIVE_SILENT`。

CPU2 验证响应后继续监听 700 ms。只有静默确认通过，才清除 `active_endpoint_id`，允许建立下一条会话。

## 8. 切换到另一种功能传感器

假设端点 B 地址为 `0x11`，功能可能是电导率或含水率。它不能复用 DM4 的类型、Profile 或负载定义。切换流程为：

```text
1. 撤销 DM4 安全快照
2. STOP_STREAM(0x10)
3. 验证 STOP 响应并确认 0x10 静默
4. HELLO(0x11)，使用 B 的 expected_sensor_type
5. 核对 B 的 device_id、目录摘要和新 session_id
6. START_STREAM(0x11)，使用 B 自己的 Profile 和配置摘要
7. 验证响应后 CPU2 进入 RX_ONLY_ACTIVE
8. 只接收 B 的 ACTIVE_REPORT
```

在 B 正式设计前，只预留公共机制，不预留猜测性的业务字段。B 必须有独立的：

- `sensor_type`；
- `profile_id/profile_version`；
- Profile 负载布局、单位、倍率和范围；
- 必需字段、质量、诊断和变化率规则；
- `profile_contract_crc32`、`profile_config_crc32`；
- 真实链路、时序和故障注入证据。

## 9. 典型异常通信

### 9.1 START 配置摘要错误

```text
CPU2 -> DM4  START_STREAM，profile_config_crc32 错误
DM4  -> CPU2 CTRL_RSP_V2，result_code=CONFIG_MISMATCH，空负载
DM4             保持 CONTROL_READY，不上报
CPU2            不进入 RX_ONLY_ACTIVE
```

### 9.2 START 响应丢失

```text
CPU2 -> DM4  START_STREAM
DM4  -> CPU2 START_STREAM_RSP 在线路中丢失
DM4             可能进入主动流
CPU2            因未验证成功响应，不采用运行帧
CPU2 -> DM4  在空闲窗口发送新的 HELLO
DM4             安全停止旧流，建立全新会话
```

### 9.3 运行帧跳号

```text
已接受 stream_seq=10
下一帧 stream_seq=12
CPU2：拒绝整帧，撤销当前安全快照，进入恢复
```

V2 初版不允许通过“可能只是丢了一帧”继续使用数据，因为无法证明丢失原因及中间样本状态。

### 9.4 运行期出现另一个源

```text
活动端点：0x10
收到合法 ACTIVE_REPORT，src_id=0x11
CPU2：不采用任一端点数据，报告总线级互斥故障
```

这不是普通错帧，而是“任一时刻最多一个发送端”不变量被破坏。

### 9.5 STOP 无响应

CPU2 已撤销安全快照，但不能仅凭 STOP 超时就认为旧端点已停止，也不能立即启动端点 B。应继续保持禁止新流，并按整机安全设计选择新的 HELLO 清场、硬件隔离或进入安全状态。

## 10. CRC 复核约定

所有示例使用 CRC32C Castagnoli：

```text
反射多项式  = 0x82F63B78
初值        = 0xFFFFFFFF
结果异或    = 0xFFFFFFFF
输出字节序  = 小端
覆盖范围    = 从 frame_type（偏移 2）到负载最后一字节
```

标准自检向量：

```text
CRC32C("123456789") = 0xE3069283
```

正式冻结前，应由独立实现从本文逐帧提取字节并重算 CRC，禁止手工复制后只检查尾部数值。

## 11. 本示例没有证明的内容

- 未证明正式 `profile_contract_crc32` 和 `safety_param_crc32`；
- 未证明固定点转换、范围、变化率和质量阈值；
- 未证明 9600 bps、目标线长和最坏环境下的时序；
- 未证明 CPU2 与传感器端实现符合状态机；
- 未证明故障注入、覆盖率、独立验证和安全需求追踪；
- 未证明整机已满足 SIL2/SC3。

因此，本示例的准确表述是“按 V2 精简候选协议构造并完成数学自洽检查的通信示例”。
