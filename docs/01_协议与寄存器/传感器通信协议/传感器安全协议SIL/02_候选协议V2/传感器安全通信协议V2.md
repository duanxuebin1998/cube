# 传感器安全通信协议 V2 精简候选版

文档状态：待评审、未实现、未形成认证证据。

线上候选版本：`protocol_version=0x02`。

文档修订：2026-08-08，在补充用户需求追踪和标准依据的基础上，进一步冻结会话不重复、独立超时失效、模板准入、参数维护边界、FTTI 和 CRC32C 充分性门禁。
适用目标：CPU2 可连接 1～2 个不同功能的安全相关传感器，但任一时刻最多只有一个传感器主动上报。首个已定义的运行数据格式模板用于 DM4；另一传感器可能是电导率、含水率或其它尚未设计的传感器。

> 本文只说明按 SIL2 安全通信原则设计的候选协议。协议设计、代码、测试或构建均不能单独证明整机已经满足 SIL2/SC3。

## 1. 一页结论

V2 精简版把安全运行核心收敛为三条控制命令和一种运行帧：

```text
HELLO
START_STREAM
ACTIVE_REPORT
STOP_STREAM
```

核心行为如下：

1. 控制阶段双向通信；安全运行阶段 CPU2 完全静默，只接收唯一活动传感器的周期上报。
2. `HELLO` 建立新的 64 位会话，并安全终止该端点可能残留的旧主动流。
3. `START_STREAM` 同时完成数据格式模板选择、配置核对和启动授权，不再拆成 CONFIGURE 与 ARM 两步。
4. 每种模板的周期、允许抖动、启动延时、停止窗口和最大年龄都提前写入双方固件，不在每次连接时动态协商。
5. 运行帧保留地址、传感器类型、模板编号、会话、序号、采样计数、数据年龄、配置签名、状态、诊断、有效字段和 CRC32C。
6. 运行公共头由旧草案的 52 字节缩减为 44 字节；DM4 运行帧由 100 字节缩减为 92 字节。
7. CPU2 使用独立于收帧事件的本地定时门禁；即使总线完全无新字节，快照到期也必须立即失效。
8. 参数维护正式排除在 V2 安全核心之外；任何影响安全输出的参数提交都必须终止会话、更新摘要并重新 HELLO。

精简不是删除安全机制，而是删除重复身份、动态组合和中间状态，降低 SC3 需求追踪、代码分支和测试组合数。

需求追踪结论：V2 的单向范围、多传感器互斥、可扩展数据格式模板、精简原则和参数维护边界已经落入协议。V2 安全核心不再保留“是否加入维护子协议”的开放选择；独立维护协议的具体帧和命令属于另一份协议的设计任务。

截至本次修订，建议用户重点确认以下四个评审结论：

1. “单向通信”严格限定为 START 成功后的安全运行阶段；进入、退出和恢复仍由 CPU2 发起双向控制。
2. 两个端点代表不同安全测量功能，协议只保证公共通信机制可扩展，不把第二端点当作 DM4 冗余副本。
3. 任一时刻最多一个端点主动上报；未确认旧端点静默前，不允许启动另一个端点。
4. DM4 参数 0～12 已进入 DM4 运行数据模板；参数 0～159 的维护不属于 V2 安全核心，后续不得在 V2 中补入通用读写命令。

### 2.2 本版冻结的结构性决定

| 项目 | V2 精简规则 |
| --- | --- |
| 已配置端点数 | 1～2 |
| 同时活动端点数 | 0 或 1 |
| 物理层基线 | 9600 bps、8N1、半双工 RS485 |
| 控制命令 | `HELLO`、`START_STREAM`、`STOP_STREAM` |
| 控制帧最大长度 | 64 字节 |
| 运行帧最大长度 | 120 字节，44 字节公共头＋最多 72 字节模板数据＋4 字节 CRC |
| 完整性校验 | CRC32C Castagnoli |
| 数据格式模板选择 | CPU2 和传感器固件预先写入同一份模板表；线上只发送模板编号、版本和安全功能编号 |
| 会话 | 每次 HELLO 建立新的 64 位 `session_id`；双端会话因子在安全寿命内不得重复，一次 START 只使用一次 |
| 运行期应答 | 无 ACK、无查询、无同步、无重发请求 |
| 超时失效 | 由 CPU2 本地单调时钟和独立超时任务触发，不依赖下一帧到达 |
| 参数维护 | 不属于 V2 安全核心，只能在无安全会话时由独立维护协议处理 |

### 2.3 尚待冻结

- 整机安全功能 FTTI、超时后的具体整机安全状态。
- 第二传感器的 `sensor_type`、模板字段、单位、倍率、范围和诊断。
- 两个端点的生产地址、设备身份分配和可选/必需角色。
- DM4 正式 `profile_contract_crc32`、安全参数清单和正式参数摘要。
- DM4 各安全功能最终质量阈值、物理范围、变化率范围、拒绝诊断掩码和诊断位—字段有效性矩阵。
- 通信残余危险失效率预算、链路错误模型和 CRC32C 对最大帧长及实际帧率的定量充分性结论。
- 真实传感器、目标线长、最坏环境下的时序和误码证据。

这些开放项不改变公共状态机和帧结构。第二传感器的开放项只阻止该传感器模板发布；DM4 模板自身的摘要、参数清单、阈值、范围和诊断规则缺少任一项时，DM4 模板不得进入生产模板白名单，也不得建立安全流。FTTI、危险失效率预算和真实链路证据未关闭前，V2 仍不能形成 SIL2 符合性结论。

### 2.4 标准依据和采用层级

V2 的直接功能安全基础是 IEC 61508 系列。IEC 61784-3 和 IEC 62280 用来补充安全通信的设计思想与失效分类，但不能未经适用性确认就写成产品直接符合的规范。正式认证前必须由整机安全计划和认证机构确认适用标准、版本、修订件及精确条款号。

| 标准或依据 | 在 V2 中的采用层级 | 本卷采用的主题 | 不得越界的结论 |
| --- | --- | --- | --- |
| IEC 61508-1:2010 | 直接基础 | 整体安全生命周期、安全需求、验证确认、修改和配置管理 | 协议需求必须进入整机 SRS 和追踪矩阵；本卷不能独立确定目标 SIL |
| IEC 61508-2:2010 | 直接基础 | E/E/PE 安全相关系统的诊断、故障检测、故障反应和安全状态 | CRC、序号或超时存在，不等于已经达到 SIL2；仍需 FTTI、诊断覆盖和安全状态证据 |
| IEC 61508-3:2010 | 直接基础 | 软件安全生命周期、需求、架构、接口、编码、验证和支持系统能力的措施 | 固定帧和状态机只能提供设计输入；SC3 还需要双端软件生命周期、独立评审、验证覆盖和配置管理证据 |
| IEC 61784-3:2021+AMD1:2024 | 安全通信设计参考 | black channel、端到端安全通信层和安全通信规范（标准原文称 Profile）的通用思想 | V2 是自研 RS485 协议，未经适用产品标准和认证机构确认，不声明符合某个 IEC 61784-3 CPF/FSCP |
| IEC 62280:2014 | 通信失效模型参考 | 损坏、删除、插入、重复、乱序、延迟和伪装等不可信传输失效 | 该标准面向铁路应用；本卷只借用失效分类，不声明产品符合 IEC 62280 |
| 整机危害分析、SRS 和认证计划 | 最终裁决依据 | 目标 SIL、通信危险失效率预算、FTTI、最大数据年龄、安全状态和独立性 | 这些输入尚未冻结前，只能称为“按 SIL2 安全通信原则设计的候选协议” |

本卷把 SIL2 和 SC3 作为两个不同的判断轴：

| 判断轴 | 正确含义 | V2 当前能够提供什么 | 当前不能声称什么 |
| --- | --- | --- | --- |
| SIL2 | 整机安全功能的安全完整性目标，必须结合随机硬件失效、系统性失效、SRS、FTTI、安全状态和验证证据判断 | 提供通信错误检测、数据拒绝、会话恢复和证据追踪所需的协议机制 | 不能由协议字段、文档、代码或局部测试单独证明整机达到 SIL2 |
| SC3 | 安全相关要素的系统能力目标，重点依赖符合 IEC 61508 生命周期的系统性故障避免和控制证据 | 通过固定接口、简单状态机、固件内置数据格式模板、防御性校验和可追踪测试降低实现与验证难度 | 不能只因架构简单或测试通过就声称 CPU2、传感器端或协议要素已经达到 SC3 |

因此，V2 的准确目标表述是：“为目标 SIL2 安全功能和 SC3 系统能力目标提供可实现、可验证的安全通信设计输入。”是否最终接受该目标，仍由整机安全分配、双端实现证据和认证评估决定。

公开标准入口已于 2026-08-08 通过 IEC Webstore 重新核对：[IEC 61508-1:2010](https://webstore.iec.ch/en/publication/5515)、[IEC 61508-2:2010](https://webstore.iec.ch/en/publication/5516) 和 [IEC 61508-3:2010](https://webstore.iec.ch/en/publication/5517) 的页面稳定日期均为 2027；[IEC 61784-3:2021+AMD1:2024 CSV](https://webstore.iec.ch/en/publication/92494) 为 Edition 4.1，稳定日期为 2029；[IEC 62280:2014](https://webstore.iec.ch/en/publication/6749) 为 Edition 1.0，稳定日期为 2028。该核对说明本文所列版本在本次修订日仍是可用基线，不替代公司受控标准原文，也不免除认证前再次确认版本、修订件和适用条款的责任。

## 3. 相对旧 V2 草案的精简

| 旧草案 | 精简版 | 安全影响 |
| --- | --- | --- |
| `CONFIGURE_ACTIVE_UPLINK`＋`ARM_ACTIVE_UPLINK` | 合并为 `START_STREAM` | 仍要求响应完整回显并在响应后延时启动 |
| `GET_ACTIVE_UPLINK` | 删除 | HELLO 返回端点状态；运行期禁止查询 |
| `bus_session_id`＋`sensor_session_id`＋`stream_id`＋`uplink_epoch` | 单个 64 位 `session_id` | 同时包含 CPU2 和传感器新鲜因子，禁止复用 |
| 动态协商 7 个时序参数 | 固件内置模板中的固定时序 | 减少参数组合和双方理解偏差 |
| 线上动态下发字段表 | 固件内置模板白名单＋`profile_catalog_crc32` | 白名单中不存在的组合直接拒绝，降低运行解析复杂度 |
| `config_epoch`＋多个配置字段 | `profile_config_crc32`＋`safety_param_crc32` | 分别绑定协议配置和实际安全参数 |
| 32 位状态＋32 位诊断 | 16 位状态＋16 位诊断 | 当前定义只使用 7 位和 14 位，保留位仍强制为 0 |
| 52 字节运行公共头 | 44 字节运行公共头 | 保留显式源、目的、类型和全部必要安全门禁 |

由于旧 V2 草案从未实现或冻结，本次仍使用 `protocol_version=0x02`。若确认已有外部样机按旧草案实现，必须将精简版提升为新的协议版本，不能依靠帧长差异隐式兼容。

## 4. 安全不变量

以下规则是协议不变量，不得由项目配置关闭：

1. 任一时刻 `active_endpoint_count <= 1`。
2. 只有 CPU2 可以发起控制事务；不使用广播 START。
3. 同一条总线任一时刻最多一个未完成控制事务。
4. CPU2 只有在完整合法的 `START_STREAM_RSP` 后才能进入 `RX_ONLY_ACTIVE`。
5. `RX_ONLY_ACTIVE` 期间 CPU2 不发送任何查询、ACK、同步或维护命令。
6. 活动传感器每个周期最多发送一帧最新完整快照，不重发旧快照。
7. 任一帧门禁失败都不得更新安全快照，不采用部分字段。
8. 快照有效期由 CPU2 本地单调时钟独立监管；无新帧、无新字节或收帧任务阻塞都不能延后失效。
9. STOP 或 HELLO 重建后，旧 `session_id` 永久失效；在设备规定的安全寿命内禁止产生相同会话值。
10. 双端会话序号必须先可靠递增并持久化，再用于发送 HELLO 请求或响应；零值、回绕、存储损坏、写入失败或无法证明未重复时禁止建立安全会话。
11. 参数、数据格式模板、时序或安全功能配置变化后，旧会话和旧配置签名立即失效。
12. 旧端点未停止并确认静默前，CPU2 不得启动另一个端点。
13. 收到非活动端点的合法运行帧属于总线级互斥故障。
14. 恢复后必须使用新会话、新鲜样本和重新核对的配置签名，禁止恢复故障前缓存。

## 5. 节点、地址和传感器类型

```text
                         半双工 RS485
CPU2 0x01  ────────────────┬────────────────────
                            │
                    端点 A 0x10
                            │
                    端点 B 0x11

安全运行时 A 或 B 至多一个发送
```

| 地址 | 对象 | 候选规则 |
| --- | --- | --- |
| `0x01` | CPU2 | 唯一控制发起方和安全数据接收方 |
| `0x10` | 端点 A | 候选生产地址 |
| `0x11` | 端点 B | 候选生产地址，必须与 A 不同 |
| `0xFF` | 广播 | V2 安全核心禁止广播 START |
| `0x00` | 未分配 | 不继承非安全协议“0 为广播”的语义 |

传感器类型候选分配：

| `sensor_type` | 含义 | 状态 |
| --- | --- | --- |
| `0x00` | 无效/未配置 | 禁止建立安全服务 |
| `0x01` | DM4 | 候选分配，待评审冻结 |
| `0x02`～`0xEF` | 后续正式传感器类型 | 受控注册，不得复用 |
| `0xF0`～`0xFF` | 保留 | V2 初版拒绝 |

CPU2 为每个端点预先配置期望地址、`sensor_type`、`device_id`、允许使用的数据格式模板和 `profile_catalog_crc32`。运行帧仍显式携带源地址、目的地址和传感器类型，避免依赖线路拓扑猜测身份。

## 6. 固件内置数据格式模板

协议字段名中继续使用英文 `profile`。本文面向评审说明时把它称为“数据格式模板”或“模板”。它不是 MCU 寄存器，也不是传感器联网后执行的在线注册。

可以把模板理解为双方固件中预先放好的一张“数据表格说明书”：它规定某类传感器发送哪些数据、每个数据放在哪个字节、使用什么单位、多久发送一次。CPU2 和传感器必须内置同一份说明书，运行时只核对模板编号，不临时下载或修改字段表。

| 原术语或字段 | 通俗含义 |
| --- | --- |
| Profile | 一种传感器的一套固定运行数据格式；同一模板可以服务一个或多个安全测量功能 |
| 静态 | 模板在固件编译时确定，安全运行中不能临时改变 |
| 注册 | 把模板及其编号加入 CPU2 和传感器双方固件的白名单 |
| `profile_catalog_crc32` | 整份模板白名单的校验摘要，用于确认双方白名单一致 |
| `profile_config_crc32` | 当前一个模板详细规则的校验摘要，用于确认字段和时序一致 |

### 6.1 模板唯一编号

每份模板由下面四项共同确定：

```text
(sensor_type, profile_id, profile_version, safety_function_id)
```

| 字段 | 通俗含义 | DM4 示例 |
| --- | --- | --- |
| `sensor_type` | 是哪一种传感器 | `0x01` 表示 DM4 |
| `profile_id` | 使用该传感器的哪张数据模板 | `0x01` 表示 DM4 运行数据模板 |
| `profile_version` | 这张模板是第几个版本 | `0x01` 表示模板 V1 |
| `safety_function_id` | 这次数据用于哪个安全测量功能 | `0x01` 表示密度/黏度，`0x02` 表示液位/测水 |

- `profile_id=0x00` 和 `safety_function_id=0x00` 无效。
- 固件编译时冻结负载长度、字段偏移、类型、倍率、范围、必需字段和时序。
- 运行期不使用 TLV、可选字段、可变数组或动态字段目录。
- 模板白名单中不存在的编号组合必须拒绝，不能根据相同帧长猜测解析。
- 字段含义、类型、有符号/无符号、倍率或有效位发生不兼容变化时，必须提升 `profile_version`。

### 6.2 新模板最低准入内容

每增加一种传感器模板，至少必须确定：

1. 模板唯一编号和固定负载长度。
2. 字段偏移、类型、单位、倍率、范围、保留值和无效值。
3. `field_valid_mask` 位映射和各安全功能的必需字段掩码。
4. 周期、允许抖动、启动延时、停止窗口、静默确认和最大年龄。
5. 状态、诊断、自检、质量和变化率对字段有效性的影响矩阵。
6. 进入 `safety_param_crc32` 的参数 ID 清单和规范化编码。
7. 正常、边界、错误、重启和 golden frame 测试向量。

上述内容必须形成受控机器契约，并生成正式 `profile_contract_crc32`、`profile_config_crc32` 和参数 ID 规范化规则。缺少任一项时，该模板只能保留为设计候选，不得加入 `profile_catalog_crc32` 对应的生产模板白名单：START 选择未准入模板时返回 `PROFILE_MISMATCH`；模板已准入但当前规则摘要或参数摘要不一致时返回 `CONFIG_MISMATCH`。禁止使用默认阈值、空参数清单、“全部字段有效”或“忽略未知诊断”等临时规则启动安全流。

模板数据超过 72 字节、有效字段组超过 16 个或一个周期需要多帧时，必须评审新的协议版本，不能私自扩展 V2。

## 7. 状态机

### 7.1 CPU2 状态

```text
OFFLINE
  │ HELLO，核对身份、目录和新会话
  ▼
CONTROL_READY
  │ START_STREAM，完整验证响应
  ▼
RX_ONLY_ACTIVE
  │ CPU2完全静默，唯一端点周期上报
  │
  ├─ 正常停止 ───────> EXITING_RX_ONLY ── STOP/静默确认 ──> OFFLINE
  ├─ 端点/数据错误 ──> ENDPOINT_RECOVERING ── HELLO重建 ──> CONTROL_READY
  └─ 错源/碰撞/占线 ─> BUS_RECOVERING
```

`STOP_STREAM` 成功并确认静默后，当前会话失效。下一次测量必须重新 HELLO，不复用旧会话。

### 7.2 传感器状态

| 状态 | 行为 |
| --- | --- |
| `INACTIVE_SILENT` | 默认状态，不主动发送，只接受本地址控制帧 |
| `CONTROL_READY` | HELLO 已建立新会话，可接受一次 START |
| `START_DELAY` | START 响应已经发送，等待当前模板规定的启动延时 |
| `UPLINK_ACTIVE` | 按本地周期发送一帧新安全快照 |
| `FAULT_SILENT` | 会话、配置或内部安全错误，停止发送 |

传感器重启后必须进入 `INACTIVE_SILENT`，不得从非易失参数自动恢复主动上报。

### 7.3 HELLO 的安全停止语义

完整合法且寻址正确的 HELLO 可以在 `INACTIVE_SILENT`、`CONTROL_READY`、`UPLINK_ACTIVE` 或 `FAULT_SILENT` 状态处理：

1. 取消尚未发送的后续运行帧。
2. 使旧会话失效。
3. 生成新的 64 位 `session_id`。
4. 返回 HELLO 响应并进入 `CONTROL_READY`。

因此 CPU2 重启或未知旧流恢复时不需要知道旧会话即可安全停止指定端点。HELLO 只能停止服务，不会在没有 START 的情况下启动发送；随机通信错误仍由地址、长度、字段约束和 CRC32C 检出。

## 8. 公共编码和 CRC

| 项 | V2 规则 |
| --- | --- |
| 字节序 | 所有多字节整数小端 |
| 运行测量编码 | 固定宽度整数和明确倍率，不直接发送 IEEE 754 浮点 |
| 完整性校验 | CRC32C Castagnoli |
| 所有 `*_crc32` 摘要字段 | 使用本节同一套 CRC32C 参数，只允许规范化输入序列不同；不得混用 IEEE CRC-32 |
| 反射实现多项式 | `0x82F63B78` |
| 初值/结果异或 | `0xFFFFFFFF` / `0xFFFFFFFF` |
| CRC 输出顺序 | 小端 |
| 保留字段 | 发送为 0；接收路径遇到非 0 时拒绝 |

控制帧和运行帧的 CRC32C 均从偏移 2 的 `frame_type` 覆盖到负载最后一个字节，不覆盖两个 SOF 字节和 CRC 字段自身。

CRC32C 用于随机通信错误检测，不是密码学认证。若威胁模型包含主动伪造，必须增加认证、访问控制或物理隔离。

CRC32C 保持为 V2 唯一的帧完整性校验，不再叠加第二套 CRC，但它必须通过定量发布门禁。每个生产模板发布前，至少应结合最大 120 字节帧、该模板每小时最大安全帧数、规定安全寿命、链路位错误和突发错误模型、CRC32C 对目标帧长的检出能力，以及整机分配给通信的残余危险失效率预算完成论证。论证还必须覆盖 `profile_catalog_crc32`、`profile_config_crc32`、`profile_contract_crc32` 和 `safety_param_crc32` 的错误组合或碰撞风险，不能只分析帧尾 CRC。地址、序号、会话、时间和多个 CRC32C 字段只有在独立性得到证明时才能作为附加降低因子；不得直接用 `2^-32`、把同一算法形成的多个摘要视为相互独立，或把多个理论概率简单相乘宣称充分。论证未通过时，该模板不得进入生产模板白名单。

## 9. 帧类型

| 帧 | `frame_type` | 方向 | 长度 | 用途 |
| --- | ---: | --- | ---: | --- |
| `CTRL_REQ_V2` | `0xC1` | CPU2 -> 单端点 | 24～64 字节 | HELLO、START、STOP 请求 |
| `CTRL_RSP_V2` | `0xC2` | 单端点 -> CPU2 | 24～64 字节 | 对应控制响应 |
| `ACTIVE_REPORT_V2` | `0xA2` | 活动传感器 -> CPU2 | 48～120 字节 | 运行期唯一主动上报帧 |

V2 不定义同步帧、双时隙帧、数据 ACK 或运行期参数查询。V1 的 `FAST_REPORT_FRAME(frame_type=0xA1)` 不得作为 V2 安全输入。

## 10. 控制帧

### 10.1 20 字节控制头

| 偏移 | 字段 | 长度 | 类型 | 说明 |
| ---: | --- | ---: | --- | --- |
| 0 | `sof0` | 1 | u8 | 固定 `0xA5` |
| 1 | `sof1` | 1 | u8 | 固定 `0x5A` |
| 2 | `frame_type` | 1 | u8 | 请求 `0xC1`，响应 `0xC2` |
| 3 | `frame_len` | 1 | u8 | `20 + payload_len + 4` |
| 4 | `src_id` | 1 | u8 | 发送方地址 |
| 5 | `dst_id` | 1 | u8 | 被寻址端点 |
| 6 | `protocol_version` | 1 | u8 | 固定 `0x02` |
| 7 | `command` | 1 | u8 | 命令值 |
| 8 | `transaction_seq` | 2 | u16 | 请求非 0，响应原样回显 |
| 10 | `result_code` | 1 | u8 | 请求固定 0，响应给出结果 |
| 11 | `reserved0` | 1 | u8 | 固定 0 |
| 12 | `session_id` | 8 | u64 | HELLO 请求固定 0，其它控制绑定当前会话 |
| 20 | `payload` | N | bytes | 由命令和方向确定固定长度 |
| 20+N | `frame_crc32c` | 4 | u32 | CRC32C |

接收端通过 `frame_len - 24` 得到负载长度，并必须与命令定义的固定长度完全一致。禁止忽略尾部多余字节或接受截断负载。

### 10.2 控制命令

| 命令 | 值 | 请求负载 | 成功响应负载 | 作用 |
| --- | ---: | ---: | ---: | --- |
| `HELLO` | `0x01` | 8 字节 | 20 字节 | 安全停止旧流、核对身份并建立新会话 |
| `START_STREAM` | `0x20` | 12 字节 | 12 字节 | 核对数据格式模板和配置后启动唯一流 |
| `STOP_STREAM` | `0x21` | 0 字节 | 0 字节 | 停止当前流并使会话失效 |

错误响应负载固定为 0 字节。错误响应仍回显命令、事务序号和可用的当前会话；CPU2 不得因错误响应更新控制状态。

### 10.3 结果码

| 值 | 名称 | 含义 |
| ---: | --- | --- |
| `0x00` | `OK` | 请求完整执行 |
| `0x01` | `UNSUPPORTED_VERSION` | 不支持协议版本 |
| `0x02` | `UNKNOWN_COMMAND` | 未定义命令 |
| `0x03` | `INVALID_LENGTH` | 固定长度不匹配 |
| `0x04` | `INVALID_STATE` | 当前状态不允许执行 |
| `0x05` | `SESSION_MISMATCH` | 会话不匹配或已失效 |
| `0x06` | `PROFILE_MISMATCH` | 模板编号、版本、安全功能或模板白名单不匹配 |
| `0x07` | `CONFIG_MISMATCH` | 当前模板详细规则或安全参数摘要不匹配 |
| `0x08` | `IDENTITY_MISMATCH` | 地址、类型或设备身份不匹配 |
| `0x09` | `BUSY` | 已有未完成控制事务 |
| `0x0A` | `INTERNAL_FAULT` | 传感器内部安全故障 |
| `0x0B` | `RESERVED_NONZERO` | 保留字段或保留位非 0 |
| `0x0C`～`0xFF` | 保留 | V2 初版拒绝 |

SOF、地址、最小长度或 CRC 错误的帧不返回响应，避免对噪声和错址帧产生总线发送。

## 11. HELLO

### 11.1 HELLO 请求负载

| 负载偏移 | 字段 | 长度 | 类型 | 规则 |
| ---: | --- | ---: | --- | --- |
| 0 | `payload_version` | 1 | u8 | 固定 1 |
| 1 | `expected_sensor_type` | 1 | u8 | CPU2 静态配置的期望类型，不使用通配值 |
| 2 | `reserved0` | 2 | u16 | 固定 0 |
| 4 | `host_nonce` | 4 | u32 | CPU2 掉电保持的会话序号，先递增并可靠写入后使用，非 0 |

HELLO 控制头中的 `session_id` 固定为 0。

### 11.2 HELLO 成功响应负载

| 负载偏移 | 字段 | 长度 | 类型 | 规则 |
| ---: | --- | ---: | --- | --- |
| 0 | `payload_version` | 1 | u8 | 固定 1 |
| 1 | `sensor_type` | 1 | u8 | 端点正式类型 |
| 2 | `sensor_state` | 1 | u8 | 成功后固定 `CONTROL_READY=0x01` |
| 3 | `reserved0` | 1 | u8 | 固定 0 |
| 4 | `device_id` | 8 | u64 | 生产唯一身份，非 0 |
| 12 | `sensor_boot_counter` | 4 | u32 | 传感器启动身份或等价单调值 |
| 16 | `profile_catalog_crc32` | 4 | u32 | 当前固件内置模板白名单的校验摘要 |

HELLO 响应头携带新 `session_id`：

```text
session_id[63:32] = host_nonce
session_id[31:0]  = sensor_nonce
```

`host_nonce` 和 `sensor_nonce` 的字段名保持不变，但 V2 不允许仅用普通随机数生成它们。二者必须分别来自 CPU2 和传感器掉电保持、单调递增的 32 位会话序号，或经过安全评审并能证明在设备规定安全寿命内不重复的等价机制：

1. 发送方必须先计算下一值，通过冗余存储、完整性校验、写后读回和磨损均衡等措施可靠持久化，再把该值放到线上；即使发送后立即掉电，该值也不得再次使用。
2. 允许会话序号跳号，不允许为 0、回退或回绕。达到 `0xFFFFFFFF` 前必须停止建立新安全会话并进入受控维护或更换流程。
3. 存储副本不一致、完整性错误、写入失败、无法判断最后已用值或无法证明未重复时，CPU2 不得发送有效 HELLO；传感器在请求其余字段合法时返回 `INTERNAL_FAULT` 和零会话，并保持安全流未建立或静默。
4. 恢复、重新烧录、维修换板和生产初始化不得把已使用的会话序号恢复为旧值；相关初始化和更换规则必须进入配置管理。

这里的“安全寿命”必须由整机 SRS、维护策略和会话频率共同给出可计算上限，不能仅以“通常不会用完”为理由接受 32 位回绕。若产品寿命、最坏 HELLO 次数和维护策略不能证明序号空间充足，应在协议冻结前重新评审会话字段宽度或安全初始化机制。

传感器响应时以其已可靠提交的会话序号作为 `sensor_nonce`。CPU2 必须检查高 32 位等于本次已提交的 `host_nonce`、低 32 位非 0，且完整 64 位未在本机保留的历史窗口中出现；历史窗口检查用于附加诊断，不替代双端持久化不重复机制。`sensor_boot_counter` 同样必须来自可诊断的启动身份或等价单调值，不能把普通易失启动次数当作重放防护。

`profile_catalog_crc32` 不用于动态下载字段表，只用于确认 CPU2 和传感器内置的模板白名单完全一致。

## 12. START_STREAM

### 12.1 请求和成功响应负载

请求与成功响应使用同一 12 字节负载，响应必须逐字节回显：

| 负载偏移 | 字段 | 长度 | 类型 | 规则 |
| ---: | --- | ---: | --- | --- |
| 0 | `payload_version` | 1 | u8 | 固定 1 |
| 1 | `profile_id` | 1 | u8 | 模板编号 |
| 2 | `profile_version` | 1 | u8 | 模板版本 |
| 3 | `safety_function_id` | 1 | u8 | 选择该模板服务的安全测量功能 |
| 4 | `profile_config_crc32` | 4 | u32 | 当前模板、功能、必需字段和时序的校验摘要 |
| 8 | `safety_param_crc32` | 4 | u32 | 当前安全参数集摘要 |

传感器只有在以下条件全部满足时才返回 `OK`：

- 当前状态为 `CONTROL_READY`，控制头会话与 HELLO 会话一致。
- 传感器类型、模板编号、模板版本和安全功能必须存在于双方固件的模板白名单中。
- `profile_config_crc32` 与本地静态契约一致。
- `safety_param_crc32` 与当前已提交安全参数一致。
- 测量模式、自检、采集链和必需配置允许进入安全运行。

成功响应最后一个 CRC 字节发送完成后，传感器进入 `START_DELAY`。CPU2 完整验证成功响应后进入 `RX_ONLY_ACTIVE`，此后不再发送任何帧。

每个 HELLO 会话只允许一次成功 START。STOP、HELLO 重建、故障或重启后必须使用新会话。

### 12.2 当前模板详细规则摘要

`profile_config_crc32` 对以下 26 字节规范化序列计算 CRC32C：

| 顺序 | 字段 | 类型 |
| ---: | --- | --- |
| 1 | `protocol_version` | u8 |
| 2 | `sensor_type` | u8 |
| 3 | `profile_id` | u8 |
| 4 | `profile_version` | u8 |
| 5 | `safety_function_id` | u8 |
| 6 | `payload_len` | u8 |
| 7 | `required_field_mask` | u16 |
| 8 | `report_period_ms` | u16 |
| 9 | `min_inter_report_ms` | u16 |
| 10 | `max_inter_report_ms` | u16 |
| 11 | `start_delay_ms` | u16 |
| 12 | `stop_window_ms` | u16 |
| 13 | `silence_confirm_ms` | u16 |
| 14 | `max_data_age_ms` | u16 |
| 15 | `profile_contract_crc32` | u32 |

所有字段小端串联，不包含结构体填充。`profile_contract_crc32` 覆盖模板的字段布局、类型、单位、倍率、范围、状态/诊断映射、质量算法和规范化规则。

### 12.3 模板白名单摘要

`profile_catalog_crc32` 对双方固件内置的模板白名单按以下规则计算：

1. `catalog_version(u16)`。
2. `entry_count(u16)`。
3. 按 `(sensor_type, profile_id, profile_version, safety_function_id)` 升序排列的固定 12 字节条目：

```text
sensor_type(u8)
profile_id(u8)
profile_version(u8)
payload_len(u8)
safety_function_id(u8)
reserved0(u8=0)
required_field_mask(u16)
profile_config_crc32(u32)
```

只有通过第 6.2 节最低准入检查和第 8 章 CRC32C 定量发布门禁的模板条目，才允许进入这里的生产模板白名单。尚未冻结阈值、范围、诊断矩阵、参数 ID 清单、规范化编码或正式摘要的候选模板不得参与 `entry_count` 和 `profile_catalog_crc32` 计算。

模板白名单摘要改变时，CPU2 必须拒绝建立安全流，直到双方固件和机器契约重新配套。START 请求的编号组合不在生产白名单时返回 `PROFILE_MISMATCH`；编号存在但 `profile_config_crc32` 或 `safety_param_crc32` 不匹配时返回 `CONFIG_MISMATCH`。两类失败都只允许发送对应错误响应，响应后必须保持主动上报静默且不得进入 `START_DELAY`。

## 13. STOP_STREAM

STOP 请求和成功响应均无负载，控制头必须绑定当前 `session_id`。

CPU2 正常停止时：

1. 先撤销当前安全快照。
2. 等待当前帧或帧尝试结束，并确认总线空闲至少 `bus_idle_guard_ms`。
3. 在当前模板规定的 `stop_window_ms` 内发送 STOP。
4. 传感器取消后续报告，返回 STOP 响应。
5. 传感器在响应发送完成后使当前会话失效并进入 `INACTIVE_SILENT`。
6. CPU2 验证响应并观察 `silence_confirm_ms`，确认静默后清除活动端点。

若运行帧损坏，CPU2 可以在 UART 空闲持续时间达到 `bus_idle_guard_ms` 后认定本次帧尝试结束，不要求 CRC 正确后才允许执行安全停止。DM4 候选 `bus_idle_guard_ms=5 ms`。

STOP 超时、错误响应或静默期内仍有运行帧时，CPU2 不得启动另一个端点；应使用 HELLO 安全重建、硬件隔离或进入整机安全状态。

### 15.3 固定点和字段有效性

- Float32 到固定点的舍入、饱和、最小值和最大值必须写入 DM4 模板规则。
- NaN、无穷、溢出或超范围时必须清除对应有效位并置诊断。
- 软件版本和存储版本只辅助一致性检查，不作为安全测量值。
- CPU2 只有在 `(field_valid_mask & required_field_mask) == required_field_mask` 时才可使用对应安全功能。
- 未被当前安全功能要求的字段仍必须按固定布局发送，但不能绕过自身类型、保留值和帧级 CRC 检查。

### 15.4 DM4 状态字

## 16. DM4 候选静态时序

| 项 | 候选值 | 说明 |
| --- | ---: | --- |
| `report_period_ms` | 500 ms | 相邻 SOF 目标间隔 |
| `min_inter_report_ms` | 450 ms | CPU2 本地时间下限 |
| `max_inter_report_ms` | 550 ms | 超过后当前流失效 |
| `start_delay_ms` | 150 ms | START 响应发送完成到首帧 SOF |
| `stop_window_ms` | 150 ms | 帧尝试结束后 CPU2 发起停止的窗口 |
| `bus_idle_guard_ms` | 5 ms | 发送 STOP/HELLO 前的总线空闲时间 |
| `silence_confirm_ms` | 700 ms | STOP/HELLO 后的静默确认时间 |
| `max_data_age_ms` | 750 ms | 还必须小于安全功能 FTTI |

这些值写入 DM4 模板，不在 START 中动态改变。认证前必须结合晶振误差、任务调度、方向切换、线缆和 FTTI 重新计算。

CPU2 必须使用本地单调时钟和独立于 UART 收帧事件的安全超时任务维护快照截止时间。`rx_sof_time` 是 CPU2 检测到已接受帧 SOF 的本地时间，`rx_complete_time` 是该帧完整接收并通过全部门禁的本地时间。每次原子接受新快照时计算：

```text
frame_interval_deadline = rx_sof_time + max_inter_report_ms
data_age_deadline = rx_sof_time + max_data_age_ms - data_age_ms
snapshot_expire_time = min(frame_interval_deadline, data_age_deadline)
```

若 `data_age_ms >= max_data_age_ms`、时间计算溢出或截止时间在原子发布前已经到达，则当前帧直接拒绝。发布后即使没有收到任何新字节，安全超时任务也必须在 `snapshot_expire_time` 到达时立即撤销快照；坏帧、错源帧、解析中断和普通诊断接收均不得刷新截止时间。定时器分辨率、调度迟到和时钟容差必须计入最坏检测时间。

协议设计发布还必须满足整机分配的时间门禁：

```text
T_comm_detect_max
+ T_cpu2_reaction_max
+ T_safe_state_max
<= FTTI
```

其中 `T_comm_detect_max` 从通信失效或危险数据产生时刻计到 CPU2 撤销快照，包含帧周期、数据年龄、传输、定时器分辨率、调度迟到和时钟容差；`T_cpu2_reaction_max` 从撤销快照计到发出整机安全动作；`T_safe_state_max` 是执行机构达到定义安全状态的最长时间。500/550/750 ms 只保留为 DM4 候选模板值，未通过该不等式和整机 FTTI 分配前不得作为正式安全参数发布。

## 17. 安全参数维护边界

本版正式冻结：V2 安全核心只包含 `HELLO`、`START_STREAM`、主动上报和 `STOP_STREAM`，不定义、不预留通用参数读取、写入、分页、游标或提交命令。DM4 参数 0～159 的维护由无安全会话时使用的独立维护协议处理；该维护协议可继承正式 DM4 参数语义，但不属于本卷，不能把维护响应解释为 V2 安全数据。

独立维护协议必须满足以下与 V2 的接口约束：

1. 只能在无活动安全会话时执行。
2. 安全相关写入使用暂存、范围/权限校验、原子提交、掉电保护和失败回滚。
3. 实际影响安全输出的参数按稳定参数 ID 清单规范化，计算 `safety_param_crc32`。
4. 任何可能影响安全输出的写入一经尝试，传感器就必须保持安全会话无效；只有提交结果明确成功、摘要重新计算并通过自检后，才允许后续重新建立安全会话。
5. 提交成功后立即使旧会话、旧参数摘要、旧报告和旧 START 结果永久失效；提交失败或结果不确定时同样不得恢复旧会话。
6. CPU2 必须清除缓存的安全快照和旧摘要，重新 HELLO，并使用新的安全参数摘要执行 START。
7. 维护协议返回的数据不得直接作为 V2 安全测量输入。

参数 65 的“定时发送/交互通信”不得启动 V2 主动上报；只有合法 `START_STREAM` 可以启动安全流。

## 18. 进入、运行和退出流程

### 18.1 上电和恢复清场

1. CPU2 保持接收，监听至少 `silence_confirm_ms`。
2. CPU2 在总线空闲窗口依次向已配置地址发送 HELLO。
3. 任一端点收到 HELLO 后停止旧流并返回新会话。
4. CPU2 核对地址、类型、设备身份、启动计数、模板白名单摘要和会话新鲜度。
5. 未配置或可选端点无响应时，协议层将其记录为不可用；是否允许其它安全功能继续由整机安全需求决定。

### 18.2 启动唯一端点

1. CPU2 确认本地 `active_endpoint_id=NONE`。
2. 选择目标端点、数据格式模板和安全测量功能。
3. 取得期望 `profile_config_crc32` 和 `safety_param_crc32`。
4. 发送 `START_STREAM`，完整核对成功响应及逐字节回显。
5. CPU2 设置唯一活动端点并进入 `RX_ONLY_ACTIVE`。
6. 传感器等待 `start_delay_ms` 后发送 `stream_seq=1` 的首帧。

CPU2 在接受 START 成功响应时立即设置独立首帧截止时间：

```text
first_frame_deadline = start_rsp_complete_time
                     + start_delay_ms
                     + max_inter_report_ms
```

首帧必须在截止时间前完整通过所有门禁；到期时无论 UART 是否收到新字节，CPU2 都必须撤销当前流并进入恢复。错误帧和部分帧不能延长截止时间。

### 18.3 安全运行

- CPU2 不发送任何帧。
- 上报周期按连续两个帧 SOF 的 CPU2 本地时间计算。
- CPU2 独立安全超时任务持续监管首帧、帧间隔和数据年龄截止时间，不等待下一帧触发检查。
- 每个周期只发送一帧最新完整快照。
- 没有新快照或存在全局安全故障时，传感器进入 `FAULT_SILENT`，不得重发旧快照。
- `stream_seq` 每实际发送一帧加 1；`sample_counter` 必须对应新采样并严格前进。
- 序号在 `0xFFFFFFFF` 前必须停止并建立新会话，不允许在会话内回绕。
- CPU2 不发送 ACK，传感器不因未收到 ACK 而重发。

### 18.4 正常退出和切换

1. CPU2 先撤销当前安全快照并进入 `EXITING_RX_ONLY`。
2. 在帧尝试结束和总线空闲保护后发送 STOP。
3. 传感器停止、响应并使会话失效。
4. CPU2 验证响应并观察静默确认时间。
5. 只有确认静默后才允许 HELLO 和 START 另一个端点。

## 19. CPU2 数据采用门禁

一帧只有在以下条件全部满足时，才可原子更新安全快照：

1. SOF、`frame_type=0xA2`、总长度和当前模板规定的长度正确。
2. CRC32C 正确，所有保留字段和保留位为 0。
3. 源地址等于唯一活动端点，目的地址、协议版本和传感器类型正确。
4. 模板编号、模板版本和安全功能与 START 记录一致。
5. 64 位 `session_id` 与当前会话完全一致。
6. `stream_seq` 严格等于上一帧加 1，不重复、回退、跳号或回绕。
7. `sample_counter` 严格前进并满足当前模板规定的最大允许增量。
8. 相邻帧 SOF 的本地间隔位于允许范围。
9. `profile_config_crc32` 和 `safety_param_crc32` 与 START 记录一致。
10. 必需公共状态位全部为 1，公共诊断满足当前模板规定的拒绝掩码。
11. 模板数据、有效掩码、物理范围、变化率和质量满足当前模板规则。
12. CPU2 以本地 SOF 时间计算的有效年龄未超过 `max_data_age_ms`，且本模板最坏通信检测时间满足整机 FTTI 分配。

```text
effective_age_ms = saturate_u32(data_age_ms + (now_monotonic - rx_sof_time))
```

`data_age_ms` 已表示快照完成到发送 SOF 的年龄，因此本地增量必须从 `rx_sof_time` 计算，不能从 `rx_complete_time` 计算而漏掉整帧传输时间。CPU2 不得只信任发送端年龄。任一门禁失败时不得更新安全快照；可以更新隔离的非安全诊断缓存，但不得采用部分解析结果。

## 20. 错误和恢复

| 场景 | 处理 |
| --- | --- |
| 普通 CRC、截断或字段错误 | 丢弃整帧，不 ACK，不更新快照 |
| 独立截止时间到期，且没有任何新字节 | 立即撤销安全快照并进入恢复，不等待下一帧 |
| 相邻帧间隔超过上限或数据年龄到期 | 当前流立即失效并进入恢复，坏帧不得刷新截止时间 |
| `stream_seq` 重复、回退或跳号 | 当前流立即失效，使用 HELLO 重建 |
| `sample_counter` 不前进 | 判定数据冻结，立即撤销快照 |
| 地址、类型、模板编号/版本、会话或配置变化 | 立即拒绝并使用 HELLO 重建 |
| 收到非活动端点合法帧 | 互斥不变量破坏，作为总线级故障 |
| 两个源交替、碰撞或持续占线 | 撤销总线全部安全输入，禁止启动新端点 |
| 活动传感器重启 | 传感器默认静默；CPU2 超时并重新 HELLO |
| CPU2 重启 | 先监听，在空闲窗口逐端点 HELLO 清场，再建立新会话 |
| STOP 失败 | 不启动其它端点；HELLO 重建、隔离或进入安全状态 |

普通坏帧被丢弃后，发送端序号仍会前进，下一帧会暴露序号缺口，因此当前流随即失效。该策略偏向确定性和安全完整性，不以通信可用性换取隐式重同步。

持续占线、无法形成控制窗口或无法安全停止端点时，协议恢复能力已经耗尽，必须在 FTTI 内进入整机定义的安全状态或执行独立隔离。任何恢复和重试时间都不得延后安全快照撤销，也不得使第 16 章的 FTTI 不等式失效。

## 21. 9600 bps 时序预算

按 8N1、每字节 10 bit：

| 帧 | 长度 | 纯线时间 |
| --- | ---: | ---: |
| HELLO 请求 | 32 B | 约 33.3 ms |
| HELLO 成功响应 | 44 B | 约 45.8 ms |
| START 请求/响应 | 36 B | 约 37.5 ms |
| STOP 请求/响应 | 24 B | 约 25.0 ms |
| DM4 运行上报 | 92 B | 约 95.8 ms |
| 最大运行上报 | 120 B | 约 125.0 ms |

500 ms 周期下，DM4 上报占线约 19.2%，最大运行帧占线 25.0%。DM4 帧完成后到下一目标 SOF 仍约有 404 ms，可覆盖 5 ms 空闲保护、150 ms 停止窗口和控制帧传输。

## 22. 与 V1、非安全协议和旧 V2 草案的关系

| 对象 | 关系 |
| --- | --- |
| V1 安全协议 | 独立线上版本；V2 不把 V1 运行帧作为安全输入 |
| DM4 非安全 8 字节帧 | 只提供参数、状态和维护语义，不作为 V2 安全运行帧 |
| DM4 参数编号 | V2 的 DM4 运行数据模板保留参数 0～12 的业务语义 |
| 旧 V2 草案 | 被本精简候选版替代；旧 52 字节公共头和 CONFIGURE/ARM 流程不再作为实现输入 |
| CPU2/CPU3 `DEVICE_PROTOCOL_VERSION` | 本协议仅位于 CPU2 与传感器之间时不自动提升 |

V2 与 V1 不自动回退。CPU2 必须根据明确的端点配置和协议版本选择客户端，不能在安全会话失败后静默降级为非安全协议。

## 23. SIL2/SC3 设计追踪

### 23.1 判断口径和当前结论

本章回答四个不同问题，评审时不得合并成一句“满足 SIL2/SC3”：

| 判断问题 | 当前结论 | 判断边界 |
| --- | --- | --- |
| V2 是否覆盖安全通信常见失效 | 候选设计已覆盖主要失效类别 | 已定义端到端完整性、身份、会话、序号、时间、配置、快照和互斥门禁；仍需机器契约和故障注入证明 |
| V2 公共帧和状态机是否还需要继续增加命令或字段 | 当前不需要 | 会话不重复、独立失效定时、模板失败关闭、参数边界和 CRC32C 充分性已经转化为发布门禁；新增字段不能替代这些门禁的关闭证据 |
| V2 是否足以证明整机 SIL2 | 否 | 协议只能撤销不可信数据，整机还必须定义安全功能、FTTI、安全状态、危险失效率预算、硬件诊断和端到端反应 |
| V2 是否足以证明 SC3 | 否 | 协议结构有利于 SC3，但还缺双端软件安全生命周期、独立评审、覆盖率、配置管理、工具和变更证据 |

当前设计结论是：V2 公共帧、命令集和核心状态机已经具备进入正式评审冻结的条件，没有发现必须通过增加复杂握手、动态协商、多流或第二套 CRC 才能关闭的功能安全通信缺口。但“公共协议设计可冻结”不等于“DM4 模板可发布”，更不等于“已满足 SIL2/SC3”。DM4 模板准入、整机安全分配、双端实现和验证证据仍必须分别关闭。

| 模板生产准入 | 规则已关闭 | 所有字段、阈值、诊断、参数清单、摘要、测试向量和 CRC32C 论证齐全才可进入生产白名单 | DM4 具体准入内容尚未全部冻结；第二传感器模板未设计 |
| 参数维护边界 | 已关闭 | V2 不增加通用维护命令；独立维护只能在无安全会话时进行，安全相关写入使旧会话和摘要失效 | 独立维护协议另行设计和验证，不阻塞公共 V2 帧冻结 |
| CRC32C 完整性策略 | 机制已关闭，定量结论未关闭 | 保持单一 CRC32C；禁止用 `2^-32` 直接宣称充分；不通过预算论证则模板不准入 | 链路错误模型、最大帧率、安全寿命、分配预算和受控计算 |
| SIL2/SC3 最终结论 | 未关闭 | 本卷只提供目标 SIL2/SC3 的安全通信设计输入 | 整机 SRS、双端生命周期、诊断覆盖、独立评审、真实链路、故障注入和认证接受 |

因此，本轮优化后的准确判断是：V2 的公共协议设计已经不存在需要通过增加报文字段才能弥补的已知基础缺口，可以提交正式设计评审；但 DM4 生产模板和 SIL2/SC3 符合性仍未关闭，当前仍不得启动正式安全流或使用“完全满足 SIL2/SC3”的表述。

### 23.6 尚未关闭的 SIL2/SC3 证据

| 未关闭项 | 当前已有内容 | 认证前必须关闭的内容 | 对当前结论的影响 |
| --- | --- | --- | --- |

| FTTI 和安全状态 | V2 能撤销安全快照并停止接受数据 | 从故障发生到执行器达到定义安全状态的最大时间、锁存和恢复规则 | 当前时序只能称候选值 |

| 会话序号持久化 | 已冻结双端先递增、可靠提交后使用和异常失败关闭规则 | 冗余存储、写后读回、磨损寿命、断电点、维修换板和生产初始化的实现与验证 | 未验证前不能证明重启后会话不重复 |
| 模板生产准入 | 已定义完整性检查和失败关闭规则 | DM4 正式摘要、参数清单、阈值、范围、诊断矩阵、测试向量和准入评审记录 | 当前 DM4 候选模板不得进入生产白名单 |

| 传感器硬件与采集链 | 协议可承载自检和采集诊断 | ADC、频率测量、供电、时钟、存储、采样冻结和共因失效证据 | 协议不能证明测量源本身安全 |

| 独立性、配置和工具 | 版本轴、摘要和变更边界已定义 | 独立评审/验证安排、配置基线、变更控制、工具使用与适用的工具可信度论证 | 不能仅凭开发者自测声称 SC3 |
| 机器契约和双端一致性 | 人工字段表和通信示例已存在 | 受控生成源、golden frame、双端对拍、边界值和错误帧全集 | 尚不能证明线上解释完全一致 |

| 标准适用性和认证接受度 | 采用 IEC 61508 主题，参考 IEC 61784-3/IEC 62280 | 受控标准版本、精确条款映射、适用产品标准和认证机构书面结论 | 当前只能使用“按安全通信原则设计”表述 |

SC3 不是由协议字段自动获得。每个安全机制仍需对应安全需求、双端实现、独立评审、配置管理、验证覆盖和认证证据；上述证据必须绑定最终协议、数据格式模板、CPU2 固件和传感器固件配置基线，任何安全相关变更都要执行影响分析并重跑受影响验证。

## 24. 最低验证矩阵

### 24.1 机器契约和 golden frame

- 控制头固定 20 字节，运行公共头固定 44 字节。
- HELLO 请求 32 字节、成功响应 44 字节。
- START 请求/成功响应 36 字节，STOP 请求/成功响应 24 字节。
- DM4 运行帧固定 92 字节，最大运行帧 120 字节。
- 所有偏移连续，多字节字段小端，CRC32C 覆盖范围一致。
- 模板准入检查能证明缺少阈值、范围、诊断矩阵、参数清单、正式摘要或测试向量的条目不会进入生产白名单。
- CRC32C 定量论证绑定最大帧长、模板帧率、安全寿命、错误模型、全部 `*_crc32` 摘要用途和通信危险失效率预算，不使用未经证明的独立性假设。

### 24.2 控制和会话

- HELLO 在所有传感器状态下只产生安全停止和新会话，不会启动上报。
- host nonce 错误回显、零 sensor nonce、重复会话和旧会话控制均拒绝。
- CPU2 和传感器会话序号在每个持久化写入点掉电后均不重复；冗余副本损坏、写入失败、序号回退和回绕均禁止建立安全会话。
- START 使用错误模板编号、错误模板版本、错误功能、错误白名单摘要、错误模板规则摘要或错误参数摘要时均返回规定错误响应，且不启动主动上报。
- START 成功响应丢失时 CPU2 不采用后续数据，并通过 HELLO 恢复。
- STOP 正常、超时、错误响应和响应丢失均覆盖。

### 24.3 运行帧

- CRC 错、截断、超长、保留位非 0、错误地址、错误类型和错误模板编号/版本。
- 会话重放、序号重复/跳号/回退/回绕、采样冻结和数据年龄越界。
- 在完全无新字节、持续坏帧和接收任务阻塞三种情况下，独立截止时间均按最坏时间撤销快照；坏帧不能延长有效期。
- 有效年龄从 SOF 本地时间而非整帧接收完成时间计算，92 字节 DM4 帧和 120 字节最大帧的线时间均计入。
- 状态、诊断、有效字段、范围、变化率和质量所有边界。
- 非活动端点发送、两个端点交替、碰撞和持续占线。

### 24.4 真实链路和安全证据

- 9600 bps 短线、目标最长线缆、最坏方向切换和时序抖动。
- CPU2 重启、传感器重启、断线、短路、掉电和恢复。
- 长稳、环境、故障注入、FTTI 和残余错误率论证。
- 分别记录 `T_comm_detect_max`、`T_cpu2_reaction_max`、`T_safe_state_max`，并证明最坏和不超过每个安全功能的 FTTI。
- CPU2、传感器端、机器契约、测试和安全需求双向追踪。

## 25. 当前实施状态

本文只完成精简候选协议设计，尚未实现或验证：

- CPU2 V2 控制帧、64 位会话、固件内置模板表和单活动端点状态机；
- CPU2 与传感器双端掉电保持会话序号、异常失败关闭和安全寿命管理；
- CPU2 独立快照失效定时、SOF 时间戳和 FTTI 分段计时；
- 传感器端 HELLO 安全停止、START、STOP 和本地周期上报；
- DM4 安全快照、固定点编码、正式模板规则摘要和生产白名单准入；
- 第二功能传感器类型和运行数据模板；
- 机器契约、golden frame、主机测试和固件构建；
