# 两个不同功能传感器同总线安全通信协议优化设计

更新日期：2026-08-03

状态：待评审设计，未修改固件、线上机器契约、golden frame、固件版本或 CPU2/CPU3 共享协议版本。

适用对象：一个 CPU2 主站在同一条半双工 RS485 总线上连接两个功能不同的安全相关传感器。本文不讨论两个相同传感器的批量发现，也不把两个传感器默认解释为冗余安全通道。

## 1. 结论和推荐基线

首版采用“双端点主站轮询 Profile”，复用现有安全通信协议 V1 的控制帧、CRC32C、HELLO、会话、配置摘要、测量响应、数据年龄和参数维护语义：

1. CPU2 是总线上唯一命令发起方。
2. 两个传感器使用固定且不同的节点地址，建议分别为 `0x10` 和 `0x11`。
3. 每个传感器拥有独立的身份、HELLO 会话、事务序号、配置摘要、测量快照、数据年龄、故障和恢复上下文。
4. 整条总线同一时刻最多存在一个未完成控制事务；两个端点不能并发发送。
5. 首版安全输入只使用有地址的请求/响应，不允许两个传感器自由执行 `PERIODIC_UPLINK`。
6. 一个端点失败只撤销该端点的安全快照；UART6、RS485 收发器、线缆或总线持续占用属于总线级故障，必须同时评估两个端点的安全反应。
7. 两个传感器的实际功能不写死在公共帧头中，由端点配置的期望 `sensor_type` 和必需能力掩码进行约束。

该方案优先降低协议和传感器端改动量，并使总线时序、故障隔离和 FTTI 可以按两个固定端点做穷举验证。

## 2. 与现有 V1 的关系

### 2.1 保持不变的线上契约

只要以下内容不变，控制帧仍使用 `protocol_version=0x01`：

- `CTRL_FRAME` 和 `FAST_REPORT_FRAME` 的字段、偏移、长度和小端字节序。
- CRC32C 参数及覆盖范围。
- `src_id`、`dst_id`、`session_id`、`seq`、`sensor_id` 和 `safety_param_crc` 的含义。
- HELLO 挑战、配置摘要、模式切换、测量读取、自检和参数维护命令负载。
- 同一会话只允许一个未完成事务、响应必须精确匹配地址/命令/序号/会话的规则。

双端点能力首先定义为 CPU2 系统拓扑 Profile，不直接改写 V1 的字节帧。单端点产品可以把端点表容量配置为 1，继续使用现有行为。

### 2.2 必须重新评审或升版的情况

出现下列任一情况时，不能仅以“CPU2 内部调度变化”处理：

| 变化 | 版本处理 |
| --- | --- |
| 新增或改变控制帧/快报字段、偏移、CRC 范围 | 提升安全通信协议版本 |
| 改变已有命令负载 | 提升对应 `payload_version`；不兼容时同时提升协议版本 |
| 新增必须由传感器解释的角色、调度或同步字段 | 增加受控命令/能力并评估协议版本 |
| 引入多节点自由周期上报或 TDMA 快报 | 定义新 `frame_type` 或安全通信协议 V2 |
| 双端点状态或数据暴露给 CPU3/外部协议 | 单独评估并同步 CPU2/CPU3 `DEVICE_PROTOCOL_VERSION` |
| 参数目录增加新功能传感器专属项 | 提升参数目录版本，地址只追加、不移动、不复用 |

## 3. 系统拓扑和责任边界

```text
CPU2
  |
  +-- UART6 / RS485 总线管理器（全局唯一事务所有者）
        |
        +-- 端点 A：地址 0x10，功能角色 A，独立 V1 会话和安全快照
        |
        +-- 端点 B：地址 0x11，功能角色 B，独立 V1 会话和安全快照
```

### 3.1 CPU2 职责

- 保存两个端点的受控配置和运行态。
- 串行调度所有控制事务，禁止两个端点同时获得发送权。
- 按端点分别执行 HELLO、配置摘要确认、模式确认、测量、过期撤销和恢复。
- 对响应执行帧级、地址、身份、会话、事务、能力、配置、状态、诊断和数据年龄检查。
- 将端点级故障与总线级故障分开上报。
- 在任一安全功能的 FTTI 到期前完成快照撤销和整机安全动作。

### 3.2 传感器职责

- 只响应 `dst_id` 与自身固定节点地址一致的请求。
- 未被点名时保持接收，不发送普通测量帧、错误帧或调试文本。
- 响应必须回显 CPU2 地址、当前会话、请求命令和事务序号。
- 不得因收到其它端点请求而改变测量模式、会话、配置或快报状态。
- 本端故障不得通过持续驱动总线、无界重发或迟到补发阻塞另一个端点。

### 3.3 物理层边界

共享 RS485 会引入共同线缆、收发器、终端/偏置、电源耦合和总线持续占用等公共原因风险。如果两个传感器构成相互独立或冗余的安全通道，必须优先评估独立 UART/隔离 RS485 分支；未经独立性分析，不能用一条共享总线证明冗余成立。

## 4. 端点身份和配置

### 4.1 固定地址表

首版不增加广播发现和动态地址分配：

| 节点 | 建议地址 | 说明 |
| --- | ---: | --- |
| CPU2 | `0x01` | 唯一主站 |
| 端点 A | `0x10` | 功能角色 A；实际功能待产品配置确认 |
| 端点 B | `0x11` | 功能角色 B；实际功能待产品配置确认 |
| 未分配 | `0x00` | 不得用于正常控制响应 |
| 广播/保留 | `0xFF` | 首版不用于会产生响应的安全命令 |

地址应在生产或受控维护阶段写入并回读确认。CPU2 启动后发现地址、身份或能力与配置不一致时，不得自动接受“当前在线设备”，必须保持对应端点未激活并记录身份不匹配。

### 4.2 端点配置项

CPU2 每个端点至少配置：

| 配置项 | 含义 |
| --- | --- |
| `node_id` | 固定 RS485 安全协议节点地址 |
| `expected_sensor_type` | HELLO 必须返回的功能类型 |
| `expected_sensor_id` | 可选的指定设备唯一标识；绑定后禁止被其它设备替换 |
| `required_capabilities` | 该功能角色启动所必需的能力位集合 |
| `allowed_measure_modes` | 该端点允许使用的测量模式集合 |
| `poll_period_ms` | 正常测量轮询周期 |
| `max_data_age_ms` | 对应安全功能允许的最大数据年龄 |
| `request_timeout_ms` | 单次请求等待响应的上限 |
| `recovery_policy` | 恢复次数、锁存和人工确认策略 |

### 4.3 能力按角色校验

现有单端点实现把密度、液位和组合测量能力合并为一个全局必需掩码。双功能端点不得继续采用“一台传感器必须具备全部能力”的判断，应按端点分别配置：

```text
端点 A 必需能力 = 产品定义的功能 A 能力集合
端点 B 必需能力 = 产品定义的功能 B 能力集合
```

端点只允许执行其已声明且配置允许的命令。端点 A 的能力缺失不能由端点 B 的能力补齐，也不能把两个不同采样时刻的数据拼成一个传感器的组合快照。

## 5. 会话和事务模型

### 5.1 每端点独立状态

每个端点分别保存：

- 当前和最近一次 `session_id`。
- `sensor_id`、传感器启动计数和会话计数。
- `next_seq`、当前未完成命令和事务序号。
- `safety_param_crc`、能力、倍率、标定和参数目录版本。
- 测量模式、`sample_counter`、数据年龄和安全快照。
- 周期流状态；首版必须保持停用。
- 最近底层错误、恢复次数和最终故障状态。

端点 A 重新 HELLO 时不得清除或复用端点 B 的会话；CPU2 重启计数可以全局共用，但每个 HELLO 必须使用新的 nonce，并把目标地址和传感器身份纳入接受检查。

### 5.2 全局总线不变量

1. 总线管理器是 UART6 发送、接收 DMA 和方向控制的唯一所有者。
2. 总线上同一时刻最多一个未完成控制事务，即使两个端点各自没有 pending，也必须先取得全局发送权。
3. 当前事务等待端点 A 时，来自端点 B 的任何完整帧都不能更新端点 B 数据；应作为非预期源帧记录并按策略判断总线污染或迟到帧。
4. 响应只有在 `src_id`、`dst_id`、`cmd`、`seq`、`session_id`、`sensor_id`、CRC 和负载全部通过后才能提交。
5. 超时或坏帧结束后必须释放 DMA/busy、清理当前事务边界并执行保护间隔，才能调度另一端点。
6. 迟到响应不得被下一端点事务接受；事务完成时间戳和接收时间戳必须用于二次拒绝超期帧。

## 6. 总线调度和公平性

### 6.1 推荐调度方式

两个固定端点采用静态循环调度，安全功能截止时间更短的端点可以获得更高频率，但调度表必须可静态审查：

```text
轮次开始
  -> 端点 A 到期检查和一次测量请求
  -> 总线保护间隔
  -> 端点 B 到期检查和一次测量请求
  -> 总线保护间隔
  -> 执行到期快照检查和安全动作调度
轮次结束
```

不得在一个端点超时后连续完成全部三次重试再服务另一个端点。推荐策略是：

- 当前请求失败后立即撤销该端点本次安全快照，并保留最具体错误原因。
- 将有限恢复安排到独立恢复时隙，且恢复不能阻塞另一端点的安全截止时间。
- 副作用命令结果不确定时，继续禁止跨新会话自动重放。
- 参数分页、导出、自检等维护操作只能使用明确预留的维护时隙。

### 6.2 优先级规则

按以下顺序获得总线：

1. 已检测故障对应的安全状态动作所需通信；前提是该动作确实依赖通信且不会延迟本地安全输出。
2. 即将到达最大数据年龄或 FTTI 截止点的安全测量。
3. 正常周期安全测量。
4. 有界恢复和状态确认。
5. 参数读取、版本查询和诊断维护。
6. 参数写入、提交和完整参数导出；仅在受控维护状态执行。

日志输出、调试打印和非关键显示更新不得占用总线安全截止时间预算。

## 7. 测量快照和跨端点数据

### 7.1 独立快照

两个端点分别发布双缓冲安全快照，每份快照至少携带：

- 端点索引、节点地址、`sensor_type` 和 `sensor_id`。
- 会话和配置身份。
- `sample_counter`、接收时间戳和有效年龄。
- 测量模式、状态、诊断和信号质量。
- 本端点的业务测量值。

端点 A 的有效数据不得覆盖端点 B 的失败状态；端点 B 恢复也不得自动恢复端点 A。

### 7.2 组合使用两个端点数据

若上层安全功能需要同时使用 A、B 两个传感器的数据，必须定义系统级组合快照规则：

```text
age_A <= max_age_A
age_B <= max_age_B
abs(rx_time_A - rx_time_B) <= max_skew_ms
session/config/status/diagnostic 均有效
```

`max_skew_ms` 必须由 SRS 根据过程变化速度给出。CPU2 只能在上述条件同时满足时生成组合有效标志；不能仅因两份单端点快照各自未过期就认为它们可以联合参与同一安全计算。

## 8. 周期上报策略

### 8.1 首版规则

双端点总线 Profile 首版禁止安全相关 `PERIODIC_UPLINK`：

- 两个传感器不得按各自定时器自由发送快报。
- CPU2 不向任一端点下发进入周期上报的安全控制配置。
- 当前固定 44 字节快报仍保留给单端点产品或非安全实验，不作为双端点首版安全输入。

这样可以避免主动上报碰撞、时钟漂移、下行控制窗口冲突和错过时隙后的迟到补发。

### 8.2 后续高性能扩展

只有请求/响应无法满足已冻结的节点数、数据年龄和 FTTI 时，才评估以下扩展：

- 新增有地址的紧凑快速读取命令，由 CPU2 令牌触发，传感器仍不主动竞争总线。
- 或定义带超帧、时隙、调度纪元、时钟漂移和错时隙丢弃规则的 TDMA 快报。

上述扩展会改变命令或快报语义，必须建立新机器契约、golden frame 和故障注入矩阵，不属于本首版 Profile。

## 9. 时序和容量预算

### 9.1 预算公式

最坏轮询周期至少包括：

```text
T_round_worst =
    sum(T_request_i + T_response_i + T_process_i + T_turnaround_i + T_guard_i)
  + T_failed_slot_budget
  + T_scheduler_jitter
  + T_safety_action_dispatch
```

每个安全功能必须满足：

```text
T_round_worst <= min(max_data_age_i, FTTI_i - T_safe_action_i)
```

如果不满足，应减少帧长或节点负载、缩短处理时间、提高经 200 米验证的波特率、拆分物理总线，不能通过延长数据有效期掩盖容量不足。

### 9.2 9600 bps 初步估算

现有协议卷给出的 `READ_MEAS_COMBO` 请求加响应约 120 字节，9600 bps、8N1 纯线时间约 125 ms。两个端点各完成一次同等规模请求的纯线时间约 250 ms，尚未包括：

- RS485 DE/RE 建立和释放。
- 帧间保护间隔。
- 传感器处理和调度抖动。
- 坏帧、静默和恢复。
- CPU2 快照发布及整机安全动作。

当前默认单次请求超时 300 ms。若对故障端点连续尝试三次，单端点可能占用约 900 ms，容易阻塞另一安全功能；因此双端点首版必须采用“一次正常时隙 + 独立恢复时隙”，并由 SRS 决定恢复预算。

### 9.3 准入条件

进入实现前必须冻结：

| 输入 | 端点 A | 端点 B |
| --- | --- | --- |
| 实际传感器功能 | 待确认 | 待确认 |
| 期望 `sensor_type` | 待确认 | 待确认 |
| 必需能力位 | 待确认 | 待确认 |
| 正常轮询周期 | 待 SRS | 待 SRS |
| 最大数据年龄 | 待 SRS | 待 SRS |
| FTTI | 待 SRS | 待 SRS |
| 安全状态和锁存条件 | 待 SRS | 待 SRS |
| 是否参与跨端点组合计算 | 待确认 | 待确认 |

## 10. 参数维护和配置一致性

### 10.1 每端点独立参数身份

- `safety_param_crc`、`config_epoch`、倍率、标定版本和参数目录版本均按端点保存。
- 端点 A 提交参数后，只撤销端点 A 的会话和快照；是否需要同时停止端点 B 由整机维护流程决定，不能由通信层默认推断。
- CPU2 必须在端点 A 新 HELLO 和配置摘要确认后才能恢复 A；不得用 B 的配置摘要证明 A 有效。

### 10.2 完整参数分页

现有 115 项完整参数读取在 9600 bps 下纯线时间下限约 6.7 s，实际预算约 7 到 10 s。共享总线存在安全测量时，首版禁止连续占用总线完成整表读取。可选策略只有：

1. 整机进入受控维护安全状态后独占总线执行；或
2. 将分页拆入受控维护时隙，每次最多读取一页，并证明不会突破两个端点的安全截止时间。

参数写入和提交必须在整机维护权限、审计、掉电保护和回滚条件关闭后执行。

## 11. 故障隔离和恢复

### 11.1 端点级故障

以下故障只作用于当前端点：

- 地址、身份、会话、序号或配置不匹配。
- 当前传感器返回远端错误、状态/诊断无效或数据过期。
- 当前请求超时、CRC 错或负载错误，且 UART6 总线仍可服务另一端点。

处理要求：撤销当前端点快照、保留具体原因、调度对应安全功能，不清除另一端点会话，不把另一端点数据复制为替代值。

### 11.2 总线级故障

以下情况按总线级故障处理：

- UART6、DMA 或 RS485 收发器不可恢复失败。
- 总线持续占用、短路、偏置/终端异常或无法释放 DE。
- 同一请求收到多个重叠响应，或出现无法隔离的串线/地址冲突。
- 连续两个端点均出现底层物理错误，且证据指向共同链路。

总线级故障必须分别撤销 A、B 快照并触发各自安全功能的安全状态。若两个功能不能接受同一总线故障同时失效，应改用物理隔离通道。

### 11.3 恢复

- 每个端点独立重新 HELLO、核对配置摘要和模式。
- 恢复前按 SRS 要求取得规定数量的连续有效新快照。
- 总线级恢复必须先证明 UART/DMA/方向控制和静默边界正常，再逐端点恢复。
- 恢复次数、锁存、人工复位和降级行为由 SRS 定义；恢复不能延长旧快照有效期。

## 12. CPU2 计划改造边界

本节只定义后续实现方向，不表示当前源码已经具备双端点能力。

### 12.1 可复用模块

- 帧编解码、CRC32C 和固定偏移校验。
- 单端点 `SensorSafeSessionContext`、client、service 和 monitor 语义。
- UART6 单次交换、时间戳、错误分类和重同步能力。
- HELLO、配置摘要、测量、自检和参数分页接口。

### 12.2 必需新增或重构

| 组件 | 计划职责 |
| --- | --- |
| 总线管理器 | 全局事务所有权、端点选择、方向控制、保护间隔、超时收口和公平调度 |
| 端点表 | 固定两个端点的地址、期望类型、能力、周期、年龄、FTTI 和安全功能映射 |
| 服务上下文数组 | 把当前单例服务改为每端点一个上下文，禁止跨端点共享会话和快照 |
| 能力 Profile | 用每端点必需能力掩码替代全局固定能力合集 |
| 端点故障投影 | 区分 A 故障、B 故障和总线故障，并映射到对应安全功能 |
| 组合快照 | 仅在 SRS 要求时增加跨端点最大时间差和共同有效标志 |
| 诊断计数 | 按端点和总线分别记录请求、响应、超时、CRC、恢复及分母 |

当前 `SAFE_SENSOR=14` 和单个 `sensorType` 只能表达“当前传感器驱动类型”，不能直接代表两个独立端点。后续实现必须先决定双端点配置存放位置、兼容迁移和 CPU3 是否需要知道第二端点，不能简单复用一个字段覆盖两台设备。

## 13. 传感器端计划要求

两个传感器可以实现不同的业务命令子集，但必须共同实现：

- V1 帧头、CRC32C、地址、HELLO、会话和标准错误响应。
- `GET_STATUS`、`GET_CONFIG_DIGEST` 及本端配置身份。
- 与自身功能对应的模式和测量命令。
- `sensor_id`、启动计数、会话计数、采样计数和数据年龄。
- 本端硬件诊断、故障状态和恢复边界。
- 非本端地址静默、无界重发禁止、迟到响应抑制和总线释放。

传感器不得声明未实现的能力；未知或不支持命令应返回受控错误，不能返回格式近似但语义不完整的数据。

## 14. 兼容和迁移

1. 单端点 V1 产品继续使用一个端点配置，不启用双端点调度。
2. 双端点 CPU2 启动时按配置顺序分别 HELLO；A 失败不自动把 B 当作 A，也不自动扫描其它地址替代。
3. 两个端点都必须使用兼容的物理层参数；若波特率、校验位或协议族不同，不应直接共享同一无隔离串口配置。
4. 首版不允许安全 V1 与会主动输出文本/广播响应的旧协议设备混挂在同一安全总线上。
5. 若后续需要动态更换设备，必须增加受控绑定/解绑、身份确认、维护权限和审计流程。

## 15. 验证矩阵

### 15.1 主机和契约测试

- A、B 分别完成 HELLO、配置摘要、能力门禁和测量。
- A、B 地址、身份、会话、序号和配置上下文不能交叉接受。
- 全局只允许一个事务；并发请求明确返回 busy/pending。
- A 超时、CRC 错、迟到帧和重放不影响 B 的会话和快照。
- B 恢复不恢复 A；总线级故障同时撤销两端点。
- 端点能力子集合法；缺失本角色必需能力时只拒绝对应端点。
- 参数分页不突破另一端点截止时间；容量、缺页、重复和目录漂移继续拒绝整表。
- 单端点配置回归现有 55 个控制向量、7 个快报向量和旧协议回退契约。

### 15.2 台架和故障注入

| 场景 | 关键证据 |
| --- | --- |
| 两个真实传感器短线轮询 | 原始 HEX、地址、身份、时序、版本、轮询周期和快照时间差 |
| 200 米两节点 RS485 | 线缆/终端/偏置、总帧数、错误分母、最坏轮询周期和恢复次数 |
| A 断电/复位，B 正常 | A 快照撤销和安全动作；B 周期、数据和会话不被破坏 |
| B 发送迟到/坏帧 | 当前事务拒绝、总线清理、A 后续事务仍正常 |
| 节点地址配置错误 | 重叠响应或错源检测，禁止接受任一不确定响应 |
| 总线持续占用/短路 | A、B 同时失效、总线级故障记录和整机安全状态时间线 |
| 参数维护占用 | 维护操作不突破另一端点 FTTI；否则必须进入整机维护安全状态 |
| CPU2 重启和传感器分别重启 | 两个端点分别建立新会话，旧会话/旧快照均被拒绝 |

### 15.3 通过边界

文档、机器契约、主机测试和构建通过只证明设计及 CPU2 软件边界。必须取得两个真实传感器、目标线缆、故障注入、最坏时序、公共原因和端到端安全动作证据后，才能把双端点状态从“待评审/待实现”提升为“台架验证完成”；最终 SIL 结论仍由整机安全评估和认证机构给出。

## 16. 实施前待确认项

1. 端点 A、B 的实际传感器名称和功能。
2. 两个传感器是否都属于安全相关输入，是否构成冗余或独立安全通道。
3. 两端点固定地址、`sensor_type` 和必需能力位。
4. 各自轮询周期、最大数据年龄、FTTI、安全状态、锁存和恢复条件。
5. 是否需要把两个端点的数据做同一安全计算，以及允许的最大采样时间差。
6. 两个传感器能否统一使用 9600 bps、8N1、相同电气和方向控制时序。
7. 参数维护能否让整机进入安全维护状态，还是必须在线分时执行。
8. CPU3、外部 Modbus 和显示是否需要分别暴露两个端点的状态、身份和测量值。
9. 共享总线故障是否可接受；若不可接受，改用两个独立或隔离通信通道。

上述项目未确认前，只能开展协议文档、PC 模拟器和静态调度预算工作，不应开始冻结固件接口或对外宣称双端点安全链路已经完成。
