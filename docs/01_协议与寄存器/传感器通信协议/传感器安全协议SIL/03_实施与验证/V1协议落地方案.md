# 传感器安全通信协议 V1 落地方案

**Goal:** 将《传感器安全通信协议 V1》落地为 CPU2、传感器端、测试工具和 SIL 证据可同步推进的实施方案。

**Architecture:** 采用分层协议栈：字节流传输层只负责点对点 UART6/RS485 收发，帧层负责 CRC32C、长度、字节序和字段偏移，会话层负责 HELLO 挑战、`session_id`、u32 `seq`、规范化 `safety_param_crc` 和 u16 `config_epoch`，安全监控层负责本地有效年龄、状态诊断、序号连续性和安全快照撤销。周期上报使用固定 44 字节 `FAST_REPORT_FRAME`，控制命令使用 `CTRL_FRAME`；SRS 未明确要求周期上报作为安全输入时，默认采用主站请求响应。

**Tech Stack:** C11、STM32 HAL UART/DMA、RS485 9600 bps、Python 3 验证脚本、Markdown 认证证据。

**V2扩展：** 不同功能传感器的单活动端点纯单向方案见《传感器安全通信协议 V2》。V2 当前待评审、未实现；本实施方案中标记为“已完成”的项目仍只证明单端点 V1 CPU2 设备侧范围。

---

## 1. 落地边界

本方案是新协议落地的长期执行依据。实现按任务逐步修改源码，任何一步完成后都要能单独构建、测试和回退；旧 DSM/LTD 协议路径在新协议通过联调和安全门禁前持续保留。

本方案不构成 SIL 符合性声明。P0 门禁未关闭前，只允许开展原型和协议工具工作，不允许在设计评审、测试报告或对外资料中表述为“已满足 SIL”：

- 整机风险分析已经确定目标安全功能和目标 SIL。
- SRS 已定义最大数据年龄、FTTI、安全状态、锁存/恢复条件和通信危险失效率预算。
- 已确认适用产品标准，并由认证机构接受自研 black channel 安全通信层的评估路线。
- 已明确链路是一个 CPU2 对一个传感器的点对点 RS485；多点总线另行设计仲裁和时隙。

正式协议源文件：

- `docs/01_协议与寄存器/传感器通信协议/传感器安全协议SIL/01_现行协议V1/传感器安全通信协议V1.md`

本方案覆盖范围：

- CPU2 新协议栈实现。
- 传感器端最小实现要求。
- 9600 bps、200 米 RS485 联调和实时性验证。
- golden frame、故障注入和长稳测试。
- SIL 认证资料需要同步保留的证据。

本方案不覆盖：

- CPU3、Modbus、SI7000 或外部协议的寄存器兼容改造。只有当新传感器状态需要暴露给 CPU3 或外部系统时，才进入对应协议目录和 `DEVICE_PROTOCOL_VERSION` 评估。
- 协议内密钥认证。主动攻击、无线开放接入或非受控接入风险由系统安全方案补充。
- PDF 同步。Markdown 是权威正文，PDF 不作为实施阻塞项。

## 2. 总体实施顺序

实施顺序必须先测试工具、再纯协议栈、再 UART 接入、再业务接入、最后硬件联调。这样可以避免把 CRC、字节序、状态机和业务测量问题混在一起。

| 阶段 | 目标 | 主要输出 |
| --- | --- | --- |
| P0 安全需求与协议冻结 | 冻结 SRS 输入、字段、命令、错误码、失效反应和验收口径 | 认证路线确认、SRS接口表、协议卷复核记录、字段冻结清单 |
| P1 golden frame | 先生成跨端一致的标准帧 | JSON 向量、Python 校验脚本 |
| P2 CPU2 纯协议栈 | 不依赖 UART 的编解码和校验 | `sensor_safe_*` 帧层和会话层 |
| P3 CPU2 UART6 传输 | 接入 9600 bps RS485 半双工收发 | UART6 transport、超时和收发窗口 |
| P4 CPU2 业务适配 | 提供当前测量流程可调用的新服务接口 | 新协议 client、快报缓存、双向读数 |
| P5 传感器端实现 | 传感器按最小状态机实现协议 | 控制帧命令、44 字节快报、退出上报 |
| P6 联调验证 | 覆盖正常、异常、长稳和 200 米链路 | 测试记录、波形/日志、故障注入结果 |
| P7 安全论证资料 | 形成可追溯证据包，不做未经评估的 SIL 声明 | 需求追踪、CRC残余错误率、诊断覆盖、验证矩阵、残余风险说明 |

当前执行状态（2026-07-13）：P1 至 P4 的 CPU2 设备侧范围已落地，包括 55 个控制帧、7 个快报帧、参数摘要机器契约，纯协议栈，UART6 传输，FRAM 启动身份，client/service/monitor，完整参数表自动分页，`MEASURE_READY` 状态、饱和诊断计数、能力门禁、`SAFE_SENSOR=14` 业务适配和 DSM/LTD 回退。每次 HELLO 后增加配置摘要复核，副作用命令的模糊响应禁止跨新会话自动重放，FRAM 平台 SPI 错误可向上阻断，UART 可越过合法长度但不完整的伪前缀。LTD 旧参数码 0 到 114 的安全参数 ID、名称、类型、权限、倍率和单位映射已经冻结，CPU2 服务层会逐项核对固定 115 项；P5 传感器端参数表代码尚未实现。P6 已完成七组主机测试和四个 GCC `-fanalyzer` 单元，并完成 CPU2 clean-first 构建；真实传感器、200 米链路、掉电注入和控制窗口台架尚未执行。P0 中整机 SRS 与认证路线门禁仍未关闭，因此当前代码不得作为“已满足 SIL”的发布依据。

本方案的复选框按证据更新：`[x]` 只表示对应 CPU2、工具或主机测试动作已有源码/命令证据，不代表真实硬件、传感器端或 SIL 门禁通过。混合条目会在正文中明确仍待验证的另一侧边界。

## 3. CPU2 文件结构建议

安全协议文件统一放在 `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/`，与 DSM、LTD、无线配对和通用传感器业务入口隔离。当前 `LTD_MAIN_CPU2/CMakeLists.txt` 使用 `file(GLOB_RECURSE SERVICE_SOURCES ... Services/*.c)`，子目录 `.c` 文件会自动进入 CMake 构建；CMake 与 STM32CubeIDE 均显式加入 `Services/Sensor/SafeProtocol` 头文件搜索路径。

| 文件 | 职责 |
| --- | --- |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_types.h` | 协议常量、命令枚举、状态位、错误码、字段偏移、固定长度 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_crc32c.h` | CRC32C API 声明 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_crc32c.c` | CRC32C Castagnoli 软件实现和测试向量入口 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_frame.h` | 控制帧和快报帧编解码 API |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_frame.c` | 小端读写、控制帧封包、控制帧解包、快报帧解包 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_session.h` | CPU2 会话、事务、上报流状态结构 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_session.c` | `session_id`、`seq`、`safety_param_crc`、`config_epoch`、`stream_seq` 校验 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_monitor.h` | 安全快照、有效年龄、状态诊断和故障反应接口 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_monitor.c` | 使用本地单调时钟撤销过期快照，按 SRS 输出恢复/故障请求 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_transport_uart6.h` | UART6/RS485 传输接口 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_transport_uart6.c` | 半双工发送、DMA 接收、快报帧扫描、超时处理 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_client.h` | CPU2 上层可调用的新协议服务 API |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_client.c` | `HELLO`、`SET_MEASURE_MODE`、`READ_MEAS_COMBO`、`SET_COMM_MODE`、`GET_STATUS` 等命令 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_service.h` | 当前 `sensor.h` 业务接口的适配层 |
| `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/sensor_safe_service.c` | 将新协议测量结果转换成当前测量流程需要的 `float` 或 RAW 值 |

执行原则：

- 新协议栈不改旧 `dsm_sensor_communication.c` 和 `ltd_sensor_communication.c` 的协议逻辑。
- 初期通过编译开关或运行时传感器类型选择新旧协议，便于回退。
- 业务层可以先保留 `Read_Density()` 等旧接口作为桥接，CPU2 上层重做后再直接调用 `SensorSafeClient_*`。
- 旧源码可能是 GBK/936，修改 `.c/.h` 前必须确认编码；新增文件建议使用 UTF-8，但不得把旧文件无意转码。
- C/C++ 注释统一使用 `/* ... */`，不得新增 `//` 注释。

### 7.4 故障注入矩阵

| 类别 | 注入方式 | 期望结果 |
| --- | --- | --- |
| 数据损坏 | 翻转任意 bit | CRC 错，丢弃 |
| 截断 | 少发 1 到 10 字节 | 长度或超时失败，丢弃 |
| 粘包 | 两帧连续无间隔 | 能按 SOF 和长度重新同步 |
| 错地址 | 改 `src_id` 或 `dst_id` | 丢弃，不更新数据 |
| 旧会话 | 使用旧 `session_id` | 丢弃 |
| 重放 | 重复旧 `stream_seq` | 丢弃，安全上报流失效 |
| 丢帧 | 跳过一个 `stream_seq` | 当前帧不进入安全输入，安全上报流失效并重新启动 |
| 冻结 | `sample_counter` 不前进 | 当前已实现数据无效；最大增量异常待 SRS 冻结采样率约束后实现 |
| 配置变化 | 改 `config_epoch` | 丢弃并重新确认配置 |
| 数据过期 | `data_age_ms` 超限 | 不作为安全相关输入 |
| 本地延迟 | 接收后延迟消费或阻塞任务 | `effective_age_ms` 超限，旧快照原子失效 |
| HELLO 重放 | 回放旧响应或篡改 challenge 回显 | 不建立会话 |
| 停用后 HELLO 重放 | 建立会话后停用安全协议，再回放停用前 `session_id` | 回放历史仍有效，不建立旧会话；新会话号可建立 |
| 首次快报静默 | 进入 ACK 后在 `start_after_ms + accepted_max_silent_ms` 截止点前不发快报，并给 Poll 传入更长超时；另注入底层越过截止点后才返回成功帧 | 实际等待裁剪到剩余预算；截止点返回 `DATA_STALE`，迟到成功帧也被拒绝，流失效 |
| 周期短轮询与后续静默 | 合法快报后先执行小于剩余预算的短轮询超时，再在下一次轮询提供合法帧；随后超过最近合法帧的最大静默 | 短轮询只返回传输超时且流保持；下一帧被接受；最终截止点返回 `DATA_STALE` 并使流失效 |
| 控制窗口 | 临界时刻发送 46 字节退出请求并叠加最大调度抖动 | 100 ms 窗口内完整接收；否则按静默和恢复策略失效 |
| 参数提交掉电 | 在写入、回读和有效标记切换阶段分别复位 | 只加载最后一个完整有效副本，旧流失效 |
| 传感器故障 | `DATA_VALID=0` 或诊断位置位 | 不更新安全相关测量值 |

## 9. 版本、提交和流程文档影响

普通实现阶段不主动升 CPU2/CPU3 固件版本。提交或发布前按最终 diff 判断：

- 只新增协议文档和工具，不改变固件输出：通常不升级固件版本。
- CPU2 新增协议栈但未启用：评估 CPU2 固件版本，通常不改变 CPU2/CPU3 共享 `DEVICE_PROTOCOL_VERSION`。
- CPU2 默认启用新传感器协议：必须升级 CPU2 固件版本，并更新 `CHANGELOG.md` 和版本改动与测试方案。
- 新状态、诊断或测量值暴露到 CPU3/Modbus/SI7000：必须评估 `DEVICE_PROTOCOL_VERSION`，同步 CPU2/CPU3 协议文档和变更记录。
- `SAFE_SENSOR=14` 复用现有 `sensorType` 字段，`DeviceParameters` 结构大小和 `DEVICE_PARAM_VERSION=3` 均不变，升级不会仅因本改动恢复出厂参数；旧固件不识别值 14，降级前必须把传感器类型恢复为旧固件支持的类型，且旧固件不能驱动安全协议传感器。
- 若最终 diff 改变传感器通信流程、命令分发、测量结果上报或异常恢复路径，必须同步 `docs/00_程序流程导航/CPU2/09_传感器与无线通信.html` 及对应业务流程图。

## 11. 关键风险和控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| CRC32C 参数不一致 | 两端互不兼容 | Python golden frame 先行，C 端逐帧对拍 |
| 快报偏移错误 | CPU2 解析出错误密度或温度 | 固定偏移宏，禁止结构体强转 |
| 周期上报占满 9600 bps 链路 | 影响退出命令和实时性 | 安全输入默认主站轮询；启用周期上报时采用 1000 ms 周期和不小于 100 ms 的 `accepted_control_guard_ms` |
| 会话或序号复用 | 旧响应或旧上报被误接受 | HELLO challenge 回显，u32 序号同一会话禁止回绕，预计溢出前重新 HELLO |
| `sample_counter` 冻结未发现 | 使用冻结数据 | 当前已实现 u32 计数严格前进和本地有效年龄；采样率最大增量门禁待 SRS 提供定量边界 |
| 配置变化后仍按旧倍率解释 | 产生危险测量值 | `safety_param_crc` 和 `config_epoch` 双重绑定 |
| 配置 CRC 两端口径不同 | 错配置未检出或无法通信 | 固定规范化字节流、独立 Python golden vector、禁止结构体内存求 CRC |
| 50 ms 控制窗口不足 | 退出命令截断或碰撞 | 9600 bps 最小 100 ms，实测方向切换和最大调度抖动 |
| 只相信传感器数据年龄 | 传感器冻结时旧值仍显示新鲜 | CPU2 本地单调时钟计算饱和 `effective_age_ms`，叠加状态和计数检查 |
| 旧协议路径被误破坏 | 现场旧传感器不可用 | 新协议独立文件，旧路径保留，启用条件显式 |
| 旧源码编码被转码 | 中文注释或字符串乱码 | 改旧 `.c/.h` 前确认编码，避免全文件重写 |
| 认证资料滞后 | 实现完成后无法追溯 | 每批次同步 golden frame、测试记录和评审结论 |

## 12. 最小可交付定义

第一轮可交付必须同时满足：

- P0 已冻结目标安全功能、SRS接口、FTTI、通信危险失效率预算和认证路线；否则交付只能标记为非认证原型。
- CPU2 能通过带 challenge 回显的新协议完成 `HELLO`、`SET_MEASURE_MODE(DENSITY)`、`READ_MEAS_COMBO`。
- CPU2 能进入 `PERIODIC_UPLINK`，接收连续 `REPORT_MEAS_FAST`，并正常退出后继续双向通信。
- 快报固定 44 字节，9600 bps 下 1000 ms 周期稳定。
- CRC 错、长度错、非零保留字段、地址错、HELLO 重放、旧会话、旧流、跳号、`config_epoch` 错、传感器年龄或本地有效年龄超限均不会更新安全相关测量值。
- 安全快照撤销到整机安全动作的实测时间小于 SRS FTTI，恢复前完成重新握手、摘要确认和规定数量的连续有效快照。
- 旧 DSM/LTD 协议路径仍可回退。
- golden frame、故障注入记录、长线测试记录和标准追踪矩阵同步归档。
