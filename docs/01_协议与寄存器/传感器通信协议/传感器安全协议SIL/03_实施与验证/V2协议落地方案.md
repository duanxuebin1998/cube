# 传感器安全通信协议 V2 落地方案

更新日期：2026-08-18

文档状态：实施设计，待协议评审通过后执行

对应协议：[传感器安全通信协议V2](../02_候选协议V2/传感器安全通信协议V2.md)

## 1. 目标和结论

本方案把 V2 候选协议拆成 CPU2、传感器端、机器契约、测试工具、台架验证和安全证据六条可执行工作线。实现目标是：

- CPU2 可配置 1～2 个不同功能的安全相关传感器。
- 任一时刻最多一个端点进入 `UPLINK_ACTIVE`。
- HELLO、START、STOP 和切换恢复阶段允许 CPU2 与指定传感器双向控制；参数维护由无安全会话时的独立维护协议处理，不进入 V2 控制面。
- 安全运行阶段只有活动传感器向 CPU2 周期主动上报，CPU2 的协议发送路径被软件门禁禁止。
- 首个生产 Runtime Profile 为 `DM4_RUNTIME_V1`；第二功能传感器只预留注册能力，不预设类型值和业务字段。
- V1 与现有非安全传感器协议在 V2 完成联调和发布批准前继续保留，V2 不以覆盖 V1 的方式直接上线。

推荐采用“V2 独立协议栈 + 复用已验证公共能力 + 明确版本选择”的落地方式。CRC32C、UART6 基础收发、会话序号持久化和现有业务适配经验可以复用；V1 的 `0xA1` 快报解析、单端点会话结构和 `StartPeriodic/PollPeriodic` 语义不能直接当作 V2 实现。

本方案不是 SIL2/SC3 符合性声明。代码、主机测试、构建或台架通过只能形成对应层级证据，不能替代整机 SRS、FTTI、硬件诊断覆盖、独立评审和认证活动。

## 2. 实施边界

### 2.1 本方案覆盖

- V2 控制帧和 `ACTIVE_REPORT_V2` 的机器可读契约。
- CPU2 的 V2 帧层、端点上下文、Profile 注册表、总线状态机和安全快照门禁。
- CPU2 在安全运行阶段的发送禁止、超时、错源、碰撞、重启和切换处理。
- DM4 `DM4_RUNTIME_V1` 的固定点转换、状态映射、有效掩码和参数摘要。
- 传感器端默认静默、HELLO 安全清场、START、主动上报、STOP 和故障静默要求。
- 第二功能传感器的扩展接口和准入流程，不包含其尚未确定的业务 Profile。
- golden frame、主机测试、短线/长线、故障注入、长稳和安全证据记录要求。
- V1/V2/非安全协议兼容、版本选择和回退边界。

### 2.2 本方案暂不覆盖

- 第二传感器的测量原理、字段、单位、倍率、范围和诊断设计。
- CPU3、Modbus 或其它对外协议的数据映射。只有 V2 数据确需跨 CPU 发布时才单独评估。
- 密钥认证、加密或主动攻击防护。CRC32C 只处理随机通信错误。
- 整机最终安全动作的具体执行代码；该动作必须由 SRS 和整机安全架构指定。
- PDF 生成或同步。

## 4. 当前实现基线和 V2 差异

2026-08-18 核对的 CPU2 工作树中，V1 安全协议模块正从 `LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/` 移动到 `LTD_MAIN_CPU2/Services/Sensor/Protocols/Dm4/Safe/`，且处于 staged/unstaged 混合重构状态；当前线上安全协议常量仍是 `protocol_version=0x01`，周期快报仍是 `frame_type=0xA1`、44 字节。本方案不修改或接管该并行源码重构。

| 能力 | V1当前基础 | V2处理方式 |
| --- | --- | --- |
| CRC32C | 已有 Castagnoli 实现 | 复用实现，新增V2覆盖范围向量 |
| 小端读写 | 已有帧层辅助 | 复用算法，V2独立偏移表 |
| 控制事务 | 已有单会话请求—响应 | 扩展为逐端点上下文，保持全总线单事务 |
| 会话新鲜度 | CPU2已有启动身份和nonce能力 | 以双端掉电保持会话序号形成单个64位会话，不在线重复发送启动计数 |
| V1快报 | `0xA1`、固定44字节 | 不复用解析结果；新增 `0xA2`、44字节公共头和Profile负载 |
| 周期监控 | 单端点流和快照 | 新增全局活动端点、Profile门禁和本地帧间隔监控 |
| UART6传输 | 支持控制交换和帧接收 | 增加控制/只接收/恢复三种传输模式及TX硬门禁 |
| 业务适配 | `SAFE_SENSOR=14`和旧接口桥接 | 保留入口，内部改为从V2快照按Profile取数 |
| 参数服务 | V1分页和受控写入 | V2不定义参数命令；独立维护协议只能在无安全会话时运行，并使旧摘要和会话失效 |
| 多端点 | 未实现 | 新增最多两个端点的独立身份和配置上下文 |

执行前必须再次读取当时的最终源码和暂存区。本文记录的是实施设计，不能覆盖后续并行修改形成的新事实。

## 5. 总体软件架构

建议在现有目录下新增 V2 子目录，避免大范围移动或改写 V1：

```text
LTD_MAIN_CPU2/Services/Sensor/Protocols/Dm4/Safe/
├─ sensor_safe_crc32c.*                 复用公共CRC32C实现
├─ 现有V1文件                           保持V1行为
└─ V2/
   ├─ sensor_safe_v2_types.h            V2常量、结构和错误枚举
   ├─ sensor_safe_v2_frame.h/.c         控制帧和0xA2运行帧编解码
   ├─ sensor_safe_v2_profile.h/.c       Profile注册、查找和公共契约校验
   ├─ sensor_safe_v2_profile_dm4.h/.c   DM4负载解析和业务门禁
   ├─ sensor_safe_v2_endpoint.h/.c      单端点身份、会话和配置上下文
   ├─ sensor_safe_v2_bus.h/.c           单活动端点和总线状态机
   ├─ sensor_safe_v2_monitor.h/.c       时序、年龄、序号和快照发布
   ├─ sensor_safe_v2_client.h/.c        HELLO、START、STOP和恢复
   ├─ sensor_safe_v2_service.h/.c       对业务层的稳定服务接口
   └─ sensor_safe_v2_transport_uart6.h/.c
                                         UART6模式、接收扫描和发送门禁
```

文件名是实施建议，最终以代码评审为准。不得为了共享少量函数先重构全部 V1 文件；应先通过窄接口复用 CRC32C 和平台时钟等稳定能力。

### 5.1 分层依赖

```text
业务测量流程
    │
V2 service / 兼容适配层
    │
V2 bus manager ───── Profile registry ───── DM4 Profile
    │                         │
V2 client / endpoint          │
    │                         │
V2 frame / monitor ───────────┘
    │
V2 UART6 transport
    │
HAL UART/DMA/RS485
```

依赖方向必须自上而下。帧层不得调用业务测量，Profile解析不得控制UART，故障管理器不得反向驱动协议状态机。

## 6. CPU2核心数据模型

### 6.1 端点配置表

CPU2保存固定容量为2的端点表，不使用动态内存。每个槽至少包含：

- 配置状态和端点地址。
- `sensor_type`、`device_id` 和制造身份。
- 当前64位 `session_id`、最近 `host_nonce`、近期失效会话集合和会话序号持久化诊断。
- 静态 Profile 键：类型、ID、版本、安全功能ID和固定长度。
- 按该端点 `sensor_type` 过滤的 `profile_catalog_crc32`，以及 `profile_config_crc32` 和 `safety_param_crc32`。
- 允许模式、`required_field_mask`、诊断拒绝掩码和质量阈值。
- 最近控制事务结果、最近故障原因和诊断计数。

端点槽只表示“已配置/已识别”，不表示该端点有权发送。

### 6.2 全局总线上下文

全局只能有一份总线上下文，至少包含：

- CPU2状态机状态。
- `active_endpoint_index`，取值为 `NONE/0/1`。
- 当前 `session_id`、Profile键和两个配置摘要。
- 从静态Profile取得的标称周期、最短/最长帧间隔、首帧超时、停止窗口、总线空闲保护、静默确认和最大年龄。
- 上一帧SOF时间、接收完成时间、上一`stream_seq`和`sample_counter`。
- 静默确认开始时间和连续静默时长。
- UART占线、错源、碰撞、TX阻断和接收错误计数。
- 当前安全快照的双缓冲或等效原子发布对象。

### 6.3 Profile注册表

Profile注册表是只读编译期表，每一项至少包含：

- Profile键、固定负载长度和 Profile 契约摘要。
- 解析函数和负载校验函数。
- 物理范围、变化率和质量检查入口。
- 公共诊断整帧拒绝掩码。
- `required_field_mask` 允许集合。
- 安全参数摘要清单版本。
- Profile名称和受控版本信息。
- 按 `sensor_type` 生成目录摘要所需的生产准入标志；其它传感器类型不得参与本端点目录摘要。

生产代码不允许根据 `sensor_type` 后再猜测负载长度；必须使用 `(sensor_type, profile_id, profile_version, safety_function_id)` 精确命中唯一注册项。

## 7. 必须在代码中固化的不变量

| 编号 | 不变量 | 推荐代码门禁 |
| --- | --- | --- |
| I-01 | 活动端点数量只能为0或1 | 全局状态只保存单一索引，不使用位图启动多个端点 |
| I-02 | 未确认旧端点静默前不得START新端点 | START入口统一检查状态和静默证据 |
| I-03 | `RX_ONLY_ACTIVE`期间CPU2不得发送 | transport发送API在该模式直接拒绝并计数 |
| I-04 | 未成功START端点必须静默 | 传感器状态机默认态和异常态都关闭发送 |
| I-05 | V1帧不得进入V2快照 | 只接受 `frame_type=0xA2` 和版本 `0x02` |
| I-06 | 一帧门禁失败不得部分发布 | 解析到临时对象，全部通过后一次发布 |
| I-07 | 故障后不得沿用旧快照 | 任一流失效事件立即撤销发布代际 |
| I-08 | 参数提交后旧流失效 | `safety_param_crc32`变化即停止并重建新会话 |
| I-09 | 传感器重启不得自动恢复主动发送 | 非易失配置不保存活动态 |
| I-10 | CPU2重启不得直接START | 先监听，再用HELLO安全停止旧流并建立新会话 |
| I-11 | 同一总线只有一个控制事务 | bus manager统一发起和收尾控制事务 |
| I-12 | 保留字段或保留位非0即拒绝 | 帧层和Profile层分别检查 |
| I-13 | 目录摘要只覆盖当前端点传感器类型 | 生成前按 `sensor_type` 过滤并断言所有条目类型一致 |
| I-14 | 线上安全测量不直接发送浮点 | 编码前检查有限值、范围、舍入和固定点可表示性 |

这些不变量应同时进入静态契约、主机测试和代码评审清单，不能只写在协议文档中。

## 8. CPU2状态机落地

### 8.1 状态定义

建议状态如下：

| 状态 | CPU2允许动作 | 禁止动作 |
| --- | --- | --- |
| `OFFLINE` | 监听、初始化、逐端点HELLO | 发布安全数据、START |
| `CONTROL_READY` | 单事务HELLO、对唯一目标START | 参数维护、接受运行帧为安全输入、启动第二端点 |
| `RX_ONLY_ACTIVE` | 仅接收、门禁、发布和本地监控 | 任何协议发送 |
| `EXITING_RX_ONLY` | 撤销快照，在受控窗口STOP | 发布新安全快照、START新端点 |
| `ENDPOINT_RECOVERING` | 停止旧流、重建目标端点会话 | 使用故障前缓存 |
| `BUS_RECOVERING` | 撤销全部输入、确认占线/错源和隔离 | START任一端点 |
| `SAFE_LOCKED` | 等待明确复位或上层安全恢复批准 | 自动恢复为活动态 |

### 8.2 关键事件和转换

| 当前状态 | 事件 | 守卫条件 | 动作 | 下一状态 |
| --- | --- | --- | --- | --- |
| `OFFLINE` | 初始化完成 | 总线连续静默或已用HELLO停止旧流 | 清空快照，逐端点建立新会话 | `CONTROL_READY` |
| `CONTROL_READY` | START响应合法 | 会话、Profile和摘要回显完全一致 | 设置活动端点并切RX-only | `RX_ONLY_ACTIVE` |
| `CONTROL_READY` | START超时/模糊 | 无可信最终响应 | 不假定静默，进入恢复 | `ENDPOINT_RECOVERING` |
| `RX_ONLY_ACTIVE` | 合法首帧/后续帧 | 全部门禁通过 | 原子发布快照 | `RX_ONLY_ACTIVE` |
| `RX_ONLY_ACTIVE` | 任一运行帧门禁失败 | CRC、序号、会话、配置、时序或数据不合格 | 撤销快照并记录具体原因 | `ENDPOINT_RECOVERING`或`BUS_RECOVERING` |
| `RX_ONLY_ACTIVE` | 超时/序号/会话/配置错误 | 任一流不变量失败 | 立即撤销快照 | `ENDPOINT_RECOVERING` |
| `RX_ONLY_ACTIVE` | 非活动端点帧/碰撞/占线 | 总线级异常 | 撤销全部输入并禁止START | `BUS_RECOVERING` |
| `RX_ONLY_ACTIVE` | 请求切换/退出 | 完整帧后进入控制窗口 | 先撤销快照 | `EXITING_RX_ONLY` |
| `EXITING_RX_ONLY` | STOP响应合法且静默期通过 | 无后续帧 | 清活动端点和失效会话 | `OFFLINE` |
| `EXITING_RX_ONLY` | 无响应或静默失败 | 旧端点可能仍发送 | 禁止新START | `BUS_RECOVERING` |
| 恢复态 | 恢复证据满足 | 身份、Profile、摘要、静默均重新确认 | 建立新会话，不恢复旧快照 | `CONTROL_READY` |
| 任意状态 | 上层安全锁存 | SRS定义条件 | 终止发送、撤销快照 | `SAFE_LOCKED` |

状态转换必须集中实现；上层业务、Profile解析器和UART回调不得直接修改 `active_endpoint_index`。

## 9. UART6和RS485传输层改造

### 9.1 三种传输模式

V2 transport 至少提供：

1. `CONTROL_TXRX`：允许一个受控请求—响应事务。
2. `RX_ONLY_ACTIVE`：持续接收运行帧，所有发送API返回明确的本地状态错误。
3. `RECOVERY_CONTROL`：快照已撤销，仅允许bus manager发起STOP、HELLO或明确的恢复控制。

普通业务层不能直接切换模式，模式切换只由bus manager执行。

### 9.2 RX-only发送硬门禁

在 `RX_ONLY_ACTIVE` 中：

- 同步发送、DMA发送、重试发送和旧协议探测入口均必须被禁止。
- 阻断尝试只记录计数和待主循环输出的诊断，不得在ISR中打印。
- 发生本地误发送请求时立即撤销当前安全快照，按实现错误进入受控恢复或安全锁存。
- 不能依赖“上层正常情况下不会调用发送”作为安全措施。

### 9.3 接收扫描

接收器应支持：

- 在任意字节边界寻找 `A5 5A`。
- 先读取长度字段，再等待完整帧；长度不合法时逐字节重同步。
- 协议最大只接收120字节V2运行帧；实现缓冲区容量可以向上对齐，但必须拒绝线上长度大于120字节的运行帧。
- 区分完整坏CRC帧、截断帧、超长帧、UART错误和接收超时。
- 对合法但非活动源的V2帧保留总线级诊断证据。
- 在识别候选帧第一个SOF字节时锁存 `rx_sof_time`，并与最终解析到的同一帧绑定；另行记录 `rx_complete_time`，有效年龄必须从SOF时间计算。
- UART framing/noise/overrun、DMA溢出、缓冲覆盖或SOF时间戳丢失均使当前候选帧无效，且不得刷新任何安全截止时间。
- 单调时间优先使用至少64位计数；只能使用32位回绕计数时，比较窗口必须小于半个计数空间并使用经过证明的模运算。
- START响应接收完成后不得停收或重启DMA；解析器必须支持成功响应与首个运行帧背靠背进入接收缓冲。若目标硬件必须保留最小间隔，应回到协议评审新增摘要字段，不得在两端代码中约定未受控延时。

### 9.4 ISR边界

UART/DMA中断只允许记录字节、长度、时间戳、错误标志和事件；CRC、Profile解析、日志和状态恢复放在主循环或受控任务中执行。中断路径禁止 `printf`、动态分配、阻塞等待和重型日志。

## 10. V2帧层实施

### Task F1：冻结常量和偏移

输出：

- `protocol_version=0x02`。
- 控制命令 `HELLO=0x01`、`START_STREAM=0x20`、`STOP_STREAM=0x21`。
- `frame_type=0xA2`。
- 20字节控制头；44字节运行公共头、最大72字节Profile负载、4字节CRC和120字节总长。
- 所有偏移、状态位、诊断位、错误码和保留掩码。

通过条件：编译期断言证明HELLO请求/响应为32/40字节、START为36字节、STOP为24字节、DM4运行帧为92字节、最大运行帧为120字节，且字段连续无重叠。

### Task F2：控制帧V2编解码

控制帧实现必须：

- 严格区分V1和V2版本。
- 检查源/目的地址、消息类型、命令、长度、序号、会话、保留字段和CRC。
- 全总线每次实际发送分配新的非零事务序号；HELLO超时使用新的 `host_nonce`，START/STOP结果不确定时使用新HELLO，禁止原字节重发旧请求。
- 只在完整响应通过后更新端点状态。
- 返回可区分的长度、CRC、地址、版本、命令、会话、配置和远端结果错误。

### Task F3：主动上报帧解码

解码顺序固定为：

1. 边界、SOF和总长。
2. `frame_type`、协议版本、目的地址。
3. CRC32C和公共保留位。
4. 活动源、类型、Profile和负载长度。
5. 单一64位会话。
6. 序号、样本计数、帧间隔和年龄。
7. Profile配置摘要、安全参数摘要、状态和诊断。
8. Profile解析、有效位、范围、变化率和质量。
9. 原子发布。

任一步失败都丢弃临时对象，不得留下部分更新。

## 11. 端点和控制事务实施

### 11.1 逐端点HELLO

CPU2按配置地址逐个建立端点上下文：

- 检查传感器唯一身份没有与另一个槽重复。
- 检查V2能力、按当前 `sensor_type` 过滤的Profile目录摘要和当前 `CONTROL_READY` 状态。
- 为每个端点保存独立64位 `session_id`，不得跨槽复用。
- HELLO完整合法时必须先停止该端点可能残留的旧流，再建立新会话。
- 发现两个地址声明同一唯一身份时拒绝建立安全服务。

### 11.2 `START_STREAM`

client从只读Profile注册表取得契约，计算或读取 `profile_config_crc32`，并与当前 `safety_param_crc32` 一起发送。传感器响应必须逐字节回显12字节负载；CPU2不接受隐式夹紧或私自替换周期。若本地契约不同，应返回明确错误并保持静默。

START入口统一检查：

- bus manager处于 `CONTROL_READY`。
- `active_endpoint_index=NONE`。
- 其它端点已确认静默。
- 当前端点身份、Profile、参数摘要和模式仍与配置一致。
- 没有未完成控制事务。

START响应不完整、超时或CRC错误属于“活动状态不确定”，不能简单当作启动失败后立即尝试另一个端点。必须进入恢复，并使用新的 `host_nonce`、新事务序号和新HELLO安全停止目标端点可能已开始的发送。

### 11.3 `STOP_STREAM`

STOP前先撤销安全快照。只有在协议定义的控制窗口和总线空闲保护满足后发送；响应合法后仍需完成连续静默确认。STOP失败、响应模糊或静默失败都禁止START其它端点。

## 12. CPU2数据采用和快照发布

### 12.1 临时解析对象

每帧先解析到栈上或固定工作缓冲，不直接写业务全局变量。临时对象至少包含公共头、Profile解析结果、接收时间、有效年龄和具体拒绝原因。

### 12.2 门禁结果

建议将门禁结果分为：

- `ACCEPT`：允许发布新的安全快照。
- `DROP_FRAME`：单帧损坏，当前快照不刷新；是否立即恢复由序号和FTTI策略决定。
- `INVALIDATE_STREAM`：当前流身份、时序、序号、配置或数据一致性失效。
- `INVALIDATE_BUS`：错源、碰撞、占线或互斥不变量失效。
- `LOCK_SAFE_STATE`：实现错误、无法隔离发送或SRS规定的锁存故障。

### 12.3 原子发布

发布采用双缓冲、代际号或等效机制：

1. 在非公开缓冲完成全部字段转换。
2. 写入接收时间、有效年龄、Profile身份和发布代际。
3. 在临界区内只切换活动缓冲索引。
4. 读取方再次检查发布代际、当前bus状态和本地年龄。

撤销时先推进发布代际并标记无效，再进入恢复，保证业务层不能继续读取故障前缓存。

## 13. DM4 Runtime Profile实施

### 13.1 Profile契约

Batch A评审冻结后，`DM4_RUNTIME_V1` 固定：

- `sensor_type=0x01`。
- `profile_id=0x01`。
- `profile_version=1`。
- `payload_len=44`。
- Profile字段和偏移与V2协议第11章一致。

`profile_contract_crc32` 由受控生成工具基于字段名、偏移、宽度、类型、signedness、单位、倍率、合法范围、有效位和保留值的规范化记录生成，不手工填写。

### 13.2 固定点转换

传感器端和CPU2测试模型必须共用同一书面规则：

- 传感器内部可以使用 Float32 计算，但线上字段只使用固定宽度整数；CPU2仅在整帧通过后换算为内部工程浮点值。
- 明确倍率、四舍五入方式、半值处理和负数转换。
- 明确最小/最大可表示值。
- NaN、正负无穷、未定义转换、溢出和超范围不允许饱和成看似有效的测量值。
- 无效字段清除对应 `field_valid_mask` 并置关联诊断。
- CPU2解析后再做一次物理范围和变化率检查。

### 13.3 状态和诊断映射

必须形成独立矩阵，至少覆盖：

- `dm4_status_raw` 各测量模式和阶段。
- Bit16姿态异常、Bit17测水异常和Bit18电压正常的极性。
- 哪些状态使整帧无效，哪些只使部分字段无效。
- 公共 `safety_status/safety_diag` 与DM4原始状态的对应关系。
- `field_valid_mask` 每一位的清除条件。

矩阵冻结后由传感器端负责生成公共诊断和有效位，CPU2按同一受控表复核；CPU2不得自行猜测未定义组合。

### 13.4 安全参数摘要

参数摘要实施顺序：

1. 从DM4实际安全计算链路识别参数68～159中被使用的项目。
2. 冻结参数ID、类型、倍率、规范化字节序和清单版本。
3. 生成 `safety_param_crc32` 正常、换序、缺项、重复和单值变化向量。
4. 参数提交采用暂存、完整校验、原子提交和写后验证。
5. 提交成功后更新 `safety_param_crc32`、使当前会话失效、停止主动流并要求重新HELLO。

不能用“连续参数68～159全部计算”替代真实使用清单，也不能漏掉内部未通过非安全协议暴露但参与安全计算的参数。

## 14. 第二功能传感器扩展方法

V2首轮生产实现只注册DM4。为了证明架构不是把DM4字段硬编码进公共层，主机测试可使用不分配生产 `sensor_type` 的测试Profile，验证不同负载长度、有效掩码和解析器能够通过同一注册接口运行。该测试Profile不得进入产品注册表或线上协议。

未来增加电导率、含水率或其它传感器时，必须单独完成：

1. 传感器安全功能和危险分析。
2. 正式分配 `sensor_type` 和静态 Profile 注册键。
3. 字段、单位、倍率、范围、变化率、无效值和诊断定义。
4. 必需字段掩码和整帧拒绝掩码。
5. 安全参数摘要清单。
6. golden frame、边界向量和故障注入。
7. Profile注册评审和版本记录。

新增Profile只允许增加新的注册项和解析器，不得修改公共状态机来为特定传感器增加隐式例外。

## 15. 传感器端实施要求

传感器端仓库和MCU尚未确定，正式实施前需指定源码入口、负责人、编译器和安全开发流程。最小任务如下。

### Sensor Task 1：默认静默

- 上电、复位、看门狗恢复和会话丢失后进入 `INACTIVE_SILENT`。
- 发送使能默认关闭。
- 非易失参数不能让设备自动恢复 `UPLINK_ACTIVE`。
- 参数65等非安全通信配置不能控制V2主动上报。

### Sensor Task 2：控制帧和会话

- 只响应本地址、合法版本、合法会话和合法CRC的控制帧。
- 同一时刻只处理一个控制事务。
- 支持会话序号先持久化后使用；采用预留区间时先提交高水位，重启后跳过整段剩余值，禁止复用。
- 未授权端点不得发送错误响应或测试帧污染总线。

### Sensor Task 3：Profile和参数摘要

- 固定DM4 Profile契约。
- 按本机 `sensor_type` 生成生产Profile目录摘要，不纳入其它传感器类型。
- 生成原子测量快照、`sample_counter` 和 `safety_param_crc32`。
- 形成状态、诊断和有效掩码，不把CPU2当作传感器内部诊断的替代者。

### Sensor Task 4：START

- 从静态Profile验证类型、功能、固定时序、Profile配置摘要和安全参数摘要。
- START成功响应发送完成后进入 `FIRST_REPORT_PENDING`；首帧SOF不得早于响应完成，并必须在 `first_report_timeout_ms` 内开始发送。
- 首帧 `stream_seq=1`，后续每实际发送一帧加1。

### Sensor Task 5：主动上报

- 每周期最多发送一帧最新完整快照。
- 不因没有ACK而重发。
- 无新快照、全局安全故障或组帧错误时进入静默或 `FAULT_SILENT`，不得重复旧快照。
- 记录本地周期误差、缓冲错误和未授权发送诊断。

### Sensor Task 6：STOP和退出

- 在控制窗口接收合法STOP后立即取消后续发送。
- 仅在发送已停止且状态完成切换后返回响应。
- STOP响应发送完成后使会话失效并进入默认静默态。
- 无法停止发送时进入硬件可实现的安全隔离或故障静默路径。

### Sensor Task 7：参数提交和掉电

- 使用暂存、范围/权限检查、原子提交、掉电保护和写后验证。
- 失败回滚到上一套完整参数。
- 影响安全计算的提交必须改变安全参数摘要、使旧会话失效，且不能继续旧流。

### Sensor Task 8：自检和故障注入接口

- 提供受控测试方式触发CRC、序号、冻结、时序、错源、内部采集和发送禁止故障。
- 测试接口在生产版本中必须受控，不得成为未授权发送入口。

## 16. CPU2业务接入

### 16.1 探测和选择

在V2正式启用前保持现有安全V1、非安全多参数和DSM路径。推荐增加明确的协议选择策略：

- 配置指定V2时，只按受控V2端点表建立服务，不把随机V1/非安全响应当作V2。
- 自动探测如需保留，V2探测失败必须完整释放UART6和状态后才能进入旧协议探测。
- 任何旧协议探测不得在 `RX_ONLY_ACTIVE` 中执行。

### 16.2 业务读取接口

业务层只读取已发布的V2快照，不在每次测量调用中发送查询。建议提供：

- 获取当前活动传感器和Profile身份。
- 读取DM4完整安全快照。
- 按安全功能读取密度/黏度或液位/测水所需字段。
- 查询快照年龄、状态、诊断和最近拒绝原因。
- 请求进入、退出或切换活动端点。

读取接口必须返回“无活动端点、快照无效、数据过期、Profile不支持、字段不完整、总线故障”等不同结果，不压缩成通用通信失败。

### 16.3 与CPU3的边界

第一阶段不改变CPU2/CPU3共享结构。若后续必须向CPU3显示活动传感器类型、V2诊断或新测量值，应单独盘点字段布局、两端消费者和 `DEVICE_PROTOCOL_VERSION`，不能因为CPU2内部新增V2就自动提升共享协议。

## 17. 错误、日志和恢复

### 17.1 错误分类

至少区分：

- 控制事务超时或传输错误。
- 帧边界、长度、CRC和保留位错误。
- 地址、版本、身份、会话、Profile和配置错误。
- 序号、采样冻结、帧间隔和数据年龄错误。
- 非活动端点发送、碰撞、占线和本地误发送。
- Profile字段、状态、诊断、范围、变化率和质量错误。
- 参数摘要或提交错误。
- 恢复失败和安全锁存。

底层具体原因必须向上保留。正常退出、用户切换和已确认的STOP不是故障。

### 17.2 日志边界

- ISR只记录，不打印。
- 过程重试使用统一“错误重试”口径，恢复成功使用“重试成功”。
- 最终故障由统一故障出口报告，不在多个协议层重复上报。
- 日志记录活动端点、状态、会话、流、序号和具体拒绝原因，但不得打印未受控敏感数据。

### 17.3 恢复策略

- 普通单帧CRC错误不刷新快照；是否立即撤销流由严格序号和FTTI预算共同决定。
- 序号、会话、配置、错源和超时错误立即撤销流。
- 恢复必须重新确认静默、身份、Profile、摘要和新鲜样本。
- START或STOP结果模糊时不得盲目重发副作用命令。
- 总线级故障不得降级为只恢复单端点后继续使用。

- DM4每个字段的最小、最大、负值、舍入、溢出、NaN/无穷来源和有效位缺失。
- `safety_param_crc32` 正常、换序、缺项、重复和单参数变化。
- 事务序号初值、跳过0、`0xFFFF`回绕、重复/迟到响应，以及HELLO、START、STOP不原字节重发规则。
- `profile_config_crc32` 的28字节输入完整覆盖首帧超时、停止窗口、总线空闲保护和静默确认。

## 19. 主机测试计划

### 19.1 纯帧层

- 逐字段偏移、长度和小端编码。
- CRC32C覆盖范围和输出顺序。
- 控制帧与运行帧的V1/V2隔离。
- 所有错误出口不修改输出对象。

### 19.2 Profile注册

- 精确 `(sensor_type, profile_id, profile_version, safety_function_id)` 命中。
- 目录摘要先按端点 `sensor_type` 过滤；增加其它传感器类型不改变现有端点摘要。
- 未知类型、未知版本、错长度和错契约CRC拒绝。
- DM4和仅用于测试的第二Profile通过同一公共路径。
- 注册表重复项由编译期或静态检查阻止。

### 19.3 总线状态机

- 端点A活动、端点B活动、无端点活动。
- 连续START两个端点时第二个被本地阻止。
- STOP失败和静默失败后不能START新端点。
- START模糊响应进入恢复，而不是直接切换。
- CPU2重启时旧端点仍发送的恢复路径。
- 传感器重启后静默和重新建立会话。

### 19.4 RX-only门禁

- 每个可能的发送API在 `RX_ONLY_ACTIVE` 中都返回阻断。
- 旧协议探测、PING、独立维护协议和恢复重试路径不能绕过门禁。
- ISR或DMA完成回调不能触发隐式续发。
- 本地误发送尝试撤销快照并记录诊断。

### 19.5 快照和时序

- 首帧超时、周期过短/过长、边界等于、抖动和本地时钟回绕。
- START成功响应与首个运行帧背靠背输入，证明无字节丢失、无错误拼帧且首帧SOF时间戳正确。
- SOF时间戳与帧绑定、UART framing/noise/overrun、DMA溢出和时间戳丢失均覆盖，坏帧不刷新截止时间。
- `stream_seq`重复、回退、跳号和回绕策略。
- `sample_counter`冻结、跳变和发送序号前进但样本不前进。
- 发送端年龄、本地排队年龄和二者饱和相加。
- 发布后读取时再次过期的二次拒绝。

### 19.6 DM4数据

- 13个字段的固定点、范围、变化率和有效位。
- 两组安全功能候选必需掩码。
- 原始状态合法/非法组合和诊断影响矩阵。
- 参数摘要变化后旧流立即失效。

### 19.7 静态分析

- 编解码、状态机、monitor、transport和DM4解析分别执行GCC `-fanalyzer`或项目认可工具。
- 检查数组边界、整数溢出、空指针、未初始化、死状态和不可达错误出口。
- 扫描安全相关C/C++新增注释只使用 `/* ... */`。

## 20. 实机和链路验证

### 20.1 PC仿真先行

使用两个逻辑端点仿真器验证互斥、错源、碰撞和切换。仿真器必须能独立控制地址、会话、序号、周期、CRC、截断和发送时机。

### 20.2 单端点短线

- DM4 HELLO、START、首帧、连续运行和STOP。
- CPU2 TX/RX方向切换和START响应到首帧的间隔。
- CPU2在主动阶段线路上没有发送字节。
- 掉电、复位、断线和恢复后传感器默认静默。

### 20.3 双端点同总线

- A活动时B保持静默，B活动时A保持静默。
- A到B、B到A切换必须经过STOP和静默确认。
- 未授权端点发送、两个端点同时发送和持续占线时撤销全部安全输入。
- 故障后不能通过简单重试误启动第二端点。

### 20.4 目标最长线缆

至少记录：

- 线缆长度、型号、终端电阻、偏置、拓扑和节点位置。
- 波特率、示波器/逻辑分析仪采样率和触发条件。
- 最坏帧时间、首帧超时、周期抖动和控制窗口。
- CRC错误、UART错误、丢帧、重同步和恢复时长。
- 最坏情况下从故障发生到安全状态的总时间。

### 20.5 长稳

- 单端点连续运行。
- A/B周期性受控切换。
- 温度、供电和电磁环境组合。
- 统计帧数、坏帧、序号缺口、重同步、恢复、错源和误发送阻断次数。

## 21. 故障注入矩阵

| 类别 | 注入 | CPU2预期 | 传感器预期 |
| --- | --- | --- | --- |
| 完整性 | 单bit、多bit、CRC、截断、拼接 | 不发布坏帧 | 不适用或记录本地发送错误 |
| 时序 | 提前、迟到、抖动、静默 | 撤销流并在FTTI内安全处理 | 本地时序诊断或静默 |
| 序号 | 重复、回退、跳号、冻结 | 流失效 | 不重发旧帧 |
| 身份 | 错地址、错类型、错Profile、旧会话 | 拒绝并恢复 | 非本地址不响应 |
| 配置 | 错Profile摘要、错参数摘要、参数提交中断 | 撤销旧流 | 原子回滚或新摘要 |
| 互斥 | 非活动端点发送、双发送、占线 | 总线级故障，禁止新START | 未授权端点应自停 |
| 重启 | CPU2重启、活动端点重启、非活动端点重启 | 先监听和确认静默 | 重启后默认静默 |
| 采集 | 固定值、固定计数、NaN、越界、低质量 | Profile门禁拒绝 | 清有效位并置诊断 |
| 传输 | UART溢出、DMA错误、方向控制失败 | 撤销流并保留具体错误 | 停止或故障静默 |
| 退出 | STOP丢失、响应损坏、静默期仍发送 | 禁止切换 | 停止发送或进入故障静默 |

每项记录前置条件、注入方法、观测点、期望状态、实际时间、通过标准、原始日志和哈希。

## 22. 分批实施计划

### Batch A：P0评审和机器契约冻结

输出：P0决策表、协议评审记录、V2/DM4 JSON向量生成器。

退出条件：P0-01～P0-23 中影响实现的项目已有明确状态；未知项不会被代码常量默认为已批准。

### Batch C：端点上下文和总线状态机

输出：两个端点槽、单活动端点状态机、START/STOP守卫和恢复模型。

### Batch D：UART6 RX-only传输

### Batch E：CPU2 client、monitor和service

输出：HELLO、START、STOP、快照发布和业务读取API。

### Batch F：DM4传感器端

输出：默认静默、原子快照、DM4 Profile、HELLO/START/STOP、周期发送和参数摘要。

退出条件：CPU2主动阶段零发送、首帧和周期满足冻结窗口、故障前后快照行为正确。

### Batch H：双端点和切换联调

输出：A/B互斥、切换、错源、碰撞和占线证据。

退出条件：任何失败路径都不能形成两个活动端点，静默未确认时不能启动新端点。

### Batch I：最长线缆、环境、长稳和故障注入

退出条件：FTTI、最大年龄和恢复时间有可追溯测量证据。

输出：需求追踪、独立评审、验证矩阵、残余危险失效率论证和发布边界。

退出条件：认证路线和发布门禁批准；未通过项明确阻止相应安全声明。

Batch之间可以准备但不能越过退出条件直接宣布后续阶段完成。特别是CPU2原型完成不能替代传感器端和真实链路证据。

## 23. 版本、兼容和回退

### 23.1 版本轴

分别管理：

- 传感器安全协议版本：V1=`0x01`，V2候选=`0x02`。
- DM4 Runtime Profile版本：`DM4_RUNTIME_V1`。
- CPU2固件版本。
- 各传感器固件版本。
- CPU2/CPU3 `DEVICE_PROTOCOL_VERSION`。
- CPU2参数存储版本和V2端点配置版本。

一个版本轴变化不能自动代替其它版本轴的评估。

### 23.2 V1/V2共存

- V1和V2解析器按明确版本分发，未知版本拒绝。
- V1 `0xA1` 快报不得进入V2快照。
- V2上线初期保留V1回退，但回退只能在V2完全停用、UART释放和总线静默后进行。
- 不允许在一个活动会话内自动从V2降级到V1继续使用旧数据。

### 23.3 参数存储

若生产需要持久化两个端点的地址、类型和Profile，应使用带版本、长度、CRC和A/B副本的独立配置块，或在现有参数结构中实施有审查的迁移。无论采用哪种方式，都不得持久化“当前正在主动上报”状态。

是否改变 `DEVICE_PARAM_VERSION` 取决于最终存储方案；文档阶段不预判“不需要升版”。

### 23.4 CPU2/CPU3共享协议

V2仅在CPU2内部使用时不自动提升 `DEVICE_PROTOCOL_VERSION`。如果新增活动端点、Profile、诊断或测量字段需要CPU3消费，必须两端同步设计、升版、构建和验证。

### 23.5 回退策略

- 每个Batch保持可单独撤销，不移动或删除V1实现。
- 通过编译开关或受控运行配置选择V2，生产默认值由发布评审决定。
- V2失败后只允许回到已知安全状态，再由明确流程选择V1或非安全协议；不能在同一故障会话中静默降级。

## 24. 安全证据和SC3要求

每个实现任务至少形成：

- 需求ID到设计、代码、测试和结果的双向追踪。
- 代码评审记录，重点检查状态机、不变量、边界、整数和错误出口。
- 工具版本、命令、HEAD、index/worktree状态和源文件指纹。
- 主机测试、构建、台架、长线和故障注入分层记录。
- 未执行项、失败项和残余风险。
- Profile和参数清单的配置管理记录。
- 独立评审和问题关闭记录。

SC3重点不只是增加CRC字段，还包括开发流程、独立性、验证深度、配置管理、变更控制和工具可信度。所有证据必须绑定最终源码和协议指纹，源码变化后旧证据按影响范围重新执行。

## 28. 建议评审顺序

用户评审时建议按以下顺序，不必一次确认全部实现细节：

1. 先确认单活动端点、运行期纯单向和切换失败禁止启动新端点。
2. 再确认CPU2状态机、RX-only发送硬门禁和CPU2重启处理。
3. 再确认候选周期、帧间隔、最大年龄、首帧超时、总线空闲保护和静默确认时间。
4. 再确认DM4字段、必需掩码、状态诊断和参数摘要清单。
5. 最后确认威胁模型、版本、持久化、传感器端仓库、硬件隔离和认证路线。

完成前四项后可以冻结Batch A并开始机器契约和CPU2纯协议栈；未确认的项目必须继续标为候选，不写入生产常量。
