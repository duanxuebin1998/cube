### 1.2 本协议解决什么

- CPU2 与传感器之间的内部通信。
- 双向请求响应通信：CPU2 发起请求，传感器返回响应。
- 单向周期上报通信：CPU2 先用双向命令切入，传感器定时上报当前密度、温度、频率和诊断状态。
- 从单向上报切回双向通信：CPU2 发送退出命令，传感器确认后停止上报，双方继续使用同一会话做双向命令。
- 为 SIL 功能安全认证准备通信层证据，包括失效模式、防护措施、验证矩阵和标准映射。

### 1.3 本协议不解决什么

- 不定义 CPU2/CPU3 共享 Modbus 寄存器。
- 不定义 CPU3 外部 SI7000、Wartsila、DSM Modbus 协议。
- 不定义整机安全功能的目标 SIL 等级；目标 SIL 必须来自整机风险分析和 SRS。
- 不替代整机 SRS、硬件诊断、软件生命周期、网络安全威胁建模和认证机构评估。

在整机 SRS 尚未冻结目标 SIL、故障容忍时间、最大数据年龄、通信危险失效率预算和安全状态之前，本协议只能称为“安全通信设计输入”，不得在设计评审、测试报告或对外资料中表述为“已满足 SIL”或“已通过 SIL 认证”。IEC 61784-3 和 IEC 62280 在本文中用于设计主题参考；自研协议是否可按 black channel 安全通信层评估，必须由适用产品标准和认证机构确认。

### 1.4 最终协议基线一页规格

| 项 | 最终规则 |
| --- | --- |
| 帧格式 | 控制帧 `CTRL_FRAME` + 周期快报帧 `FAST_REPORT_FRAME` |
| 最大帧长 | 控制帧 `frame_len <= 128`；快报帧固定 44 字节 |
| 字节序 | 小端序 |
| 数值表示 | 固定宽度整数，物理小数用 `_x100`、`_x1000` 等倍率表达；倍率和单位由 `scale_version` 管理 |
| 完整性校验 | CRC32C Castagnoli；控制帧覆盖 `protocol_version` 到 `payload` 末尾，快报帧覆盖 `frame_type` 到 `config_epoch` 末尾 |
| 会话 | `HELLO` 使用 CPU2 启动计数和一次性随机数发起挑战；响应必须回显挑战并建立新的 `session_id` |
| 双向事务 | CPU2 同一时刻只保留一个未完成请求；u32 `seq` 只允许与当前未完成请求的 `cmd` 精确匹配 |
| 周期上报 | 同一会话只允许一个 `stream_id` 激活；u32 `stream_seq` 检测丢失、重复和乱序，安全输入不接受跳号后直接续用 |
| 数据新鲜度 | 每帧测量数据携带 u32 `sample_counter` 和 `data_age_ms`；CPU2 还必须使用本地单调时钟计算有效年龄 |
| 配置一致性 | 控制帧携带规范化计算的 `safety_param_crc`，快报帧携带 u16 `config_epoch`；倍率或单位变化后旧流立即失效 |
| 物理链路 | 基线仅支持 CPU2 与单个传感器的点对点 200 米 RS485 半双工链路；多点总线必须另行定义仲裁和时隙 |
| 主动攻击边界 | 本基线面向受控内部链路；若存在无线、开放网络或非受控接入，必须在系统层增加 IEC 62443 认证/授权/完整性保护，不能只依赖 CRC |
| 参数写入 | 不在普通测量流程中自动写参数；参数修改必须进入维护流程 |

### 1.5 最终命令边界

本协议一次性定义最终基线，不再规划阶段版本。为降低传感器实现复杂度，最终基线只保留认证和运行必须的命令，调试抓取、独立状态上报、链路控制保留命令不进入安全通信基线。

| 类别 | 命令 | 说明 |
| --- | --- | --- |
| 基础链路 | `HELLO`、`PING`、`GET_STATUS`、`GET_CONFIG_DIGEST`、`RESET_SESSION` | 建立会话、确认链路、读取诊断、确认配置一致性和恢复会话 |
| 双向测量 | `SET_MEASURE_MODE`、`READ_MEAS_COMBO`、`READ_LEVEL_FREQ`、`READ_WATER_CAP`、`READ_GYRO`、`READ_POWER` | 覆盖当前需要保留的传感器业务对象 |
| 单向上报 | `SET_COMM_MODE`、`REPORT_MEAS_FAST` | 受控进入周期上报，退出后继续双向通信 |
| 参数维护 | `READ_PARAM`、`WRITE_PARAM`、`COMMIT_PARAM` | 参数读写必须走维护流程 |
| 自检维护 | `RUN_SELF_TEST`、`READ_SELF_TEST_RESULT` | 用于认证证据、开机/维护自检和诊断追踪 |

最终命令边界仍必须保留通用帧头、CRC32C、会话号、事务号、数据年龄、采样计数、状态位和诊断位。可以不实现旧协议中的调试抓取类能力，但不能删除这些安全通信防护字段。

### 1.6 旧协议参考结论

旧协议只作为业务对象输入，不作为新协议的通信机制基础。

| 来源 | 可参考内容 | 不继承内容 |
| --- | --- | --- |
| DSM 一代文本协议 | 密度模式、液位模式、传感器 ID、版本、电压、密度/温度/频率组合、水位电容、姿态角 | ASCII 命令、换行结束、BCC、文本解析 |
| LTD/V2 8 字节协议 | 软件版本、存储版本、传感器状态、电压、液位频率、温度、密度、动力粘度、运动粘度、45 度/22.5 度参考频率、参数读写 | 8 字节固定帧、低 8 bit 累加和、单参数多次读取、`0xFF` 粗粒度失败 |

设计结论：

- 新协议保留业务对象，不保留旧帧格式。
- 温度、密度、频率应优先使用同一采样快照；双向读取使用完整组合结构，9600 bps 周期上报使用紧凑结构。
- 所有测量值采用整数倍率，不直接传 float。
- 每帧带状态、诊断、数据年龄和采样计数。
- 周期上报必须受 CPU2 控制，不能由传感器任意异步输出。

## 2. 术语和字段命名

### 2.1 术语解释

| 术语 | 在本文中的含义 | 为什么重要 |
| --- | --- | --- |
| SIL | Safety Integrity Level，安全完整性等级。本文只为 SIL 认证准备通信层证据，不单独声明协议已经取得 SIL 认证 | 避免把“按 SIL 思路设计”和“已经通过 SIL 认证”混为一谈 |
| 安全功能 | 设备为了避免危险状态而必须正确执行的功能，例如使用有效密度、温度或液位数据参与控制 | 协议只服务于安全功能，最终 SIL 等级还取决于整机安全需求、硬件、软件和验证证据 |
| SRS | Safety Requirements Specification，安全需求规格 | SIL 评估需要从安全需求追溯到设计、实现和测试 |
| E/E/PE | Electrical/Electronic/Programmable Electronic，电气/电子/可编程电子系统 | IEC 61508 用该术语描述由硬件和软件组成的安全相关系统 |
| black channel | 黑通道。把 UART、无线、滑环、DMA 或中间转发链路都当作不可信传输，只假设它能搬运字节，不假设它可靠或安全 | 本协议必须在自身层面处理损坏、丢失、重复、乱序、延迟和错设备等问题 |
| 安全通信层 | 位于业务数据和底层传输之间的协议防护层，包括地址、长度、序号、会话、CRC、超时和状态检查 | 即使底层链路不是安全总线，也能给安全相关数据增加可验证的防护 |
| 帧 | 一次完整传输单元，从 `sof0` 开始，到 `safety_crc` 结束 | 接收端必须先确认一整帧合法，才能使用负载数据 |
| 负载 | `payload` 字段中的命令数据或测量数据 | 不同命令使用不同负载结构，通用帧头保持一致 |
| SOF | Start Of Frame，帧起始标记。本文使用 `sof0=0xA5`、`sof1=0x5A` | 用来在连续字节流中找到帧边界 |
| CRC32C | Castagnoli 多项式的 32 bit CRC | 用于检测传输损坏、截断和拼接错误；CRC 不是认证码，不能防主动伪造 |
| 认证码 | 用密钥生成的完整性校验值，例如 MAC 或签名类机制 | 当存在主动攻击、无线接入或非受控接入风险时，仅靠 CRC 不够 |
| 小端序 | 多字节整数低字节先传输 | CPU2 和传感器必须按同一字节序解释字段 |
| 整数倍率 | 用整数承载小数，例如 `temperature_c_x100=2534` 表示 25.34 degC | 避免 float 字节序、NaN、编译器差异和跨平台解释不一致 |
| `session_id` | 会话号。一次 `HELLO` 挑战响应后生成，后续双向通信和单向上报都携带 | 防止上电前旧帧、旧响应或旧上报被当成当前数据；不能把会话号当作认证码 |
| `seq` | u32 双向请求响应事务号，由 CPU2 在请求中递增，响应必须带回同一值 | 防止响应错配、重复响应和乱序响应；同一会话内不得回绕复用 |
| `stream_id` | 单向周期上报流 ID，由 CPU2 启动上报时分配 | 退出上报后，旧 `stream_id` 的帧必须失效，避免旧流继续被使用 |
| `stream_seq` | u32 单向周期上报序号，每条上报递增 | 用于发现周期上报丢帧、重复或乱序；同一会话内不得回绕复用 |
| `sample_counter` | u32 传感器采样计数，同一采样周期的组合数据使用同一计数 | 用于判断温度、密度、频率是否来自同一次采样，并避免低 16 bit 频繁回绕 |
| `data_age_ms` | 数据年龄，表示该负载中的测量值距离实际采样已经过去多少毫秒 | 用于防止旧数据、缓存数据或冻结数据被当成实时数据 |
| `safety_param_crc` | 安全参数集 CRC，覆盖影响数据解释的能力、倍率、标定版本和关键配置 | 防止 CPU2 按旧倍率或旧标定解释新数据 |
| `capability_flags` | 能力位，表示传感器支持哪些协议能力 | CPU2 按能力启用功能，不能靠猜测使用未声明字段 |
| `status_flags` | 状态位，表示本帧数据是否有效、是否稳定、模式是否匹配等 | CPU2 必须先看状态位，再决定数据是否能参与控制 |
| `diag_flags` | 诊断位，表示传感器检测到的硬件、算法、配置或通信异常 | 用于故障定位、报警和诊断覆盖率统计 |
| golden frame | 已知输入、已知输出的标准测试帧 | 用于确认 CPU2 和传感器对字节序、长度、CRC、字段倍率的理解完全一致 |
| HIL | Hardware In the Loop，硬件在环测试 | 用真实硬件或半实物环境验证协议在异常链路和真实时序下的行为 |
| 故障注入 | 人为制造 CRC 错、丢帧、重复、乱序、延迟、错误地址等异常 | 用于证明协议能检测并处理通信失效 |

### 2.2 字段命名读法

| 命名形式 | 例子 | 读法 |
| --- | --- | --- |
| `_x100`、`_x1000` | `temperature_c_x100`、`frequency_hz_x1000` | 字段值是物理量乘以 100 或 1000 后的整数 |
| `_crc` | `safety_param_crc`、`param_crc` | CRC 校验值，不是加密认证码 |
| `_flags` | `status_flags`、`diag_flags` | 位图字段，每一 bit 表示一个独立状态 |
| `_id` | `session_id`、`stream_id`、`sensor_id` | 标识符，用于绑定会话、上报流或设备 |
| `_seq` | `seq`、`stream_seq` | 序号，用于检测重复、丢失和乱序 |

线上数据不得使用 float、double 或字符串表达工程值。所有小数物理量必须先按字段名或单位倍率表放大为整数，接收端通过 `scale_version`、字段命名和本协议表格还原工程单位。

## 3. SIL 依据和设计理由

### 3.1 标准映射口径

### 3.2 总体设计原则

| 原则 | 为什么这样设计 | 标准映射 |
| --- | --- | --- |
| black channel | UART、无线透传、滑环和 DMA 都可能损坏、延迟、重复或丢失数据，不能信任底层链路 | IEC 61784-3 安全通信 profile/black channel；IEC 62280 不可信传输系统 |
| 二进制固定头 + 可变负载 | 比文本协议更容易做边界检查、长度检查、版本兼容和自动化测试 | IEC 61508-3 软件架构和接口可验证性 |
| CRC32C 覆盖关键字段和负载 | 当前累加和/BCC 不足以覆盖安全相关数据完整性要求 | IEC 61508-2 诊断；IEC 62280 数据损坏防护 |
| 会话号 + 事务号 | 防止旧响应、重复响应、跨命令响应和上电前旧帧被误用 | IEC 62280 重复、乱序、延迟和重放类防护 |
| 源/目的/传感器 ID 绑定 | 防止串线、错设备响应、错误节点伪装成传感器 | IEC 62280 伪装和地址错误防护 |
| 数据年龄 + 采样计数 | 防止旧数据、冻结数据和缓存数据被当成实时安全输入 | IEC 61508-2 诊断覆盖；IEC 62280 延迟防护 |
| 整数倍率 | 避免 float 字节序、NaN、编译器差异和跨平台解释不一致 | IEC 61508-3 明确接口和数据表示 |
| 组合读数 | 温度、密度、频率来自同一采样周期，减少跨采样不一致 | IEC 61508-3 数据一致性和接口需求 |
| 单向上报受控进入/退出 | 周期上报提高实时性，但必须防止误触发、无法退出和旧流继续生效 | IEC 61508-2 安全状态；IEC 62280 插入、重复和延迟防护 |
| 配置 CRC | 能力、倍率、标定版本变化时，CPU2 不能继续按旧解释使用数据 | IEC 61508-1 配置管理；IEC 61508-3 需求和接口一致性 |

### 3.3 传感器端复杂度控制

SIL 相关设计不是把协议做得越复杂越好，而是让风险防护、实现难度和验证证据保持平衡。传感器程序资源通常更紧，最终基线按以下边界设计：

| 约束 | 最终规则 | 设计理由 |
| --- | --- | --- |
| 帧大小 | 控制帧 `frame_len <= 128`，快报帧固定 44 字节 | 传感器可使用固定收发缓冲区，便于做边界检查和资源评估 |
| 分片 | 不支持分片和重组 | 避免传感器维护复杂重组状态，所有业务数据必须放入单帧 |
| 并发请求 | 不支持流水线请求；CPU2 等待响应或超时后再发下一条请求 | 传感器只需保存当前事务或最近一次可重发响应 |
| 周期上报流 | 同一会话只允许一个 `stream_id` 激活 | 传感器不用维护多流调度，CPU2 也更容易判断静默和丢帧 |
| 上报缓存 | 推荐只保留最新一帧，不累计历史队列 | 安全判断依赖新鲜数据，历史队列反而增加延迟风险 |
| 负载格式 | 不使用嵌套 TLV、字符串和可变长度数组 | 降低解析分支，减少长度错误和内存越界风险 |
| 字节序和类型 | 全部使用小端整数和固定宽度类型 | C 端实现直接、可测，避免 float 和编译器差异 |
| 参数写入 | 测量流程中不自动写参数，参数写入必须走维护流程 | 防止普通通信抖动影响安全相关配置 |
| 认证码 | 不放入本安全通信基线 | 当前目标是内部受控链路的功能安全通信；主动攻击场景由系统安全通道覆盖，避免传感器端引入密钥生命周期复杂度 |
| 错误恢复 | 传感器只做本地状态回退和错误响应，复杂恢复策略由 CPU2 决策 | CPU2 资源更充足，也更接近整机安全状态控制 |

## 4. 通信模型

### 4.0 物理链路前提

本协议面向传感器到设备约 200 米 RS485 半双工链路，当前项目波特率为 9600 bps。该链路必须按长线低速场景设计，不能假设 19200 bps、38400 bps 或 115200 bps 长期可靠。

| 项 | 规则 |
| --- | --- |
| 项目设计基线 | 9600 bps |
| 拓扑 | 一个 CPU2 对一个传感器的点对点链路；本基线不允许多个传感器无仲裁地主动上报 |
| 可选较高速率 | 19200 或 38400 bps，需经过现场线缆、终端电阻、偏置、电磁环境和误码测试确认 |
| 不作为默认基线 | 19200 bps 及以上，除非硬件和现场验证证明可靠 |
| 通信方式 | 半双工，同一时刻只有一端发送 |
| 周期上报下行窗口 | 传感器除自身发送快报期间外必须保持接收；每帧 CRC 发送结束后立即进入确定的控制窗口 |

设计含义：协议必须优先减少周期上报帧长度和交互次数。低速长线下，实时性主要由字节数、波特率、半双工方向切换、静默间隔和异常重试决定，而不是由 MCU 编码解码时间决定。

物理层设计输入必须在硬件和 SRS 中冻结：线缆类型和屏蔽接地方式、两端终端电阻、空闲偏置、隔离和浪涌/ESD能力、允许节点数、DE/RE建立与释放时间、UART `ORE/FE/NE/PE/BREAK` 的处理方式、工作温度和 EMC 等级。长线验收必须记录总字节数、总帧数、CRC错、短帧、UART硬件错误、静默超时、重试和恢复次数，并由通信危险失效率预算给出通过门限；“连续运行 24 小时没有报错”不能单独作为 SIL 充分性证据。

### 4.1 节点角色

| 节点 | 角色 | 默认 ID |
| --- | --- | --- |
| CPU2 | 主控、会话发起方、双向命令发起方、周期上报控制方 | `0x01` |
| 传感器 | 从设备、测量数据提供方、周期上报发送方 | `0x10` |

### 4.2 传输模式

| 值 | 名称 | 说明 |
| --- | --- | --- |
| `0x00` | `REQUEST_RESPONSE` | 双向请求响应模式；CPU2 发请求，传感器响应 |
| `0x01` | `PERIODIC_UPLINK` | 单向周期上报模式；传感器按周期向 CPU2 发送测量报告 |

传输模式和测量模式必须分开：传输模式解决数据如何传输，测量模式解决传感器当前采什么。单向上报不是新的测量对象，它只是密度等测量数据的传输方式。

安全功能默认使用 CPU2 主动发起的 `REQUEST_RESPONSE`，因为点对点半双工链路的请求、响应和超时边界更容易证明。只有当 SRS 明确要求周期主动上报作为安全输入，并证明控制窗口、最大静默和退出失败反应均满足 FTTI 时，才允许 `PERIODIC_UPLINK` 更新安全快照；否则周期上报只能进入与安全控制隔离的非安全监测缓存。

### 4.3 测量模式

| 值 | 名称 | 说明 |
| --- | --- | --- |
| `0x00` | `IDLE` | 待机 |
| `0x01` | `DENSITY` | 密度测量模式 |
| `0x02` | `LEVEL` | 液位频率模式 |
| `0x03` | `WATER_CAP` | 水位电容模式 |
| `0x04` | `GYRO` | 姿态角模式 |
| `0x05` | `BOTTOM` | 罐底/底部检测模式 |
| `0x7E` | `SELF_TEST` | 自检中 |
| `0x7F` | `FAULT` | 故障状态 |

### 4.4 会话、事务和上报流

| 对象 | 规则 |
| --- | --- |
| 会话 | CPU2 上电或链路恢复后发送 `HELLO`，`session_id=0`；传感器只有在校验挑战后才响应新的 `session_id`；后续所有双向命令和周期上报帧均携带该 `session_id` |
| 会话挑战 | 每次 `HELLO` 都必须使用新的 `cpu_nonce`；响应必须回显 `cpu_boot_counter` 和 `cpu_nonce`，CPU2 在接受响应前逐项精确匹配 |
| 会话生成 | `session_id` 必须绑定 CPU2/传感器 ID、双方启动计数、`cpu_nonce` 和传感器本次启动内单调递增的 `sensor_session_counter`；同一传感器启动周期内不得重复。CPU2 还必须拒绝与最近一次已接受会话相同的非零 `session_id`，即使其它 HELLO 字段看似已更新。CRC32C 可用于无密钥场景的确定性混合，但会话号不是认证码 |
| 停用边界 | CPU2 因安全协议探测失败、旧协议回退或传感器类型切换而停用安全协议时，只清除当前会话、事务、流和测量运行态；本次 CPU2 启动内最近已接受的 `sensor_boot_counter`、`sensor_session_counter` 和非零 `session_id` 必须保留，下一次安全协议探测仍据此拒绝回放 |
| 双向事务 | CPU2 每发起一个新双向请求，u32 `seq` 加 1；传感器响应必须回显请求 `seq` 和 `cmd`；预计回绕前必须重新 `HELLO` |
| 请求重试 | CPU2 重试同一请求时，可使用同一 `seq` 并置 `RETRY_FRAME` |
| 幂等保护 | 传感器收到重复的无副作用请求，可返回缓存响应；对 `SET_MEASURE_MODE`、`SET_COMM_MODE`、`WRITE_PARAM` 等有副作用命令，必须用 `seq` 做幂等保护 |
| 周期上报 | 周期上报负载必须携带独立的 `stream_id` 和 `stream_seq`，不用普通请求 `seq` 表示上报顺序 |

周期上报快报帧关键字段如下。快报帧利用原保留空间将 `stream_seq` 和 `sample_counter` 扩展为 u32，仍保持固定 44 字节，从协议层删除运行期频繁回绕分支。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `stream_id` | u16 | CPU2 启动周期上报时分配 |
| `stream_seq` | u32 | 传感器每发一帧递增，从 1 开始；同一会话内不得回绕复用 |
| `sample_counter` | u32 | 传感器完整采样计数；同一会话内不得回绕复用 |
| `data_age_ms` | u16 | 数据从采样到发送的年龄 |

### 4.5 CPU2 启动身份持久化约束

`cpu_boot_counter` 不是普通业务参数。CPU2 使用独立 FRAM 双副本保存启动身份记录，不复用 `DeviceParameters`，也不随恢复出厂参数清零：

| 项 | 冻结实现约束 |
| --- | --- |
| A 副本地址 | `0x1100` |
| B 副本地址 | `0x1140` |
| 单槽空间 | `0x40` 字节；当前有效记录 20 字节，其余空间保留为 0xFF |
| 记录字段 | magic、记录版本、记录长度、generation、`boot_counter`、CRC32C |
| 更新顺序 | 每次读写完整 `0x40` 字节；按 generation 奇偶选择主槽，写后回读校验，再镜像另一槽；保留区任一字节不是 0xFF 时该槽无效 |
| I/O 失败边界 | SPI 命令、地址、数据任一阶段返回非 `HAL_OK`，或访问越界、回读不一致时，均返回存储错误并禁止建立安全会话；不得把预清零缓冲误判为首次启动 |
| 双槽单调性 | 两槽均通过结构和 CRC 校验时，generation 较大的记录必须具有严格更大的 `boot_counter`；同 generation 不同启动计数，或较新 generation 携带相同/更小启动计数，均判定记录冲突，禁止选择较新槽继续 HELLO |
| 单槽损坏 | 使用合法副本递增并修复双副本 |
| 双槽非空损坏 | 初始化失败，禁止静默把启动计数恢复为 1，禁止发起 HELLO |
| nonce 来源 | 优先 STM32F429 硬件 RNG；失败时可使用带明确诊断的确定性后备混合值，后备值不得宣称具备密码学安全性 |

该地址分配属于 CPU2 本地实现契约，不进入线上帧，也不改变协议版本 `0x01`。若后续调整 FRAM 地址、记录布局或掉电写入策略，必须同步更新参数存储流程文档和掉电故障注入用例。

## 5. 帧格式和接收校验

所有多字节字段采用小端序。基线版本的保留字段和保留位必须发送 0；安全相关接收路径遇到非 0 保留值时必须按版本或参数错误拒绝，不能静默接受未知语义。最终协议使用两类固定帧：控制帧用于双向命令、参数、自检和完整读取；快报帧用于 9600 bps 周期上报。两类帧都必须通过 CRC32C、会话、地址或流标识、序号、数据年龄和状态诊断校验后才能使用。

### 5.1 控制帧 `CTRL_FRAME`

控制帧用于 `REQ`、`RSP` 和 `ERR`，承载会话建立、模式切换、双向读数、参数维护和自检维护。控制帧不用于周期测量上报。

| 偏移 | 字段 | 长度 | 类型 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | `sof0` | 1 | u8 | 固定 `0xA5` |
| 1 | `sof1` | 1 | u8 | 固定 `0x5A` |
| 2 | `protocol_version` | 1 | u8 | 最终基线 `0x01` |
| 3 | `header_len` | 1 | u8 | 最终基线 `28` |
| 4 | `frame_len` | 2 | u16 | 从 `sof0` 到 CRC 末尾的总长度 |
| 6 | `src_id` | 1 | u8 | 源节点 ID |
| 7 | `dst_id` | 1 | u8 | 目的节点 ID |
| 8 | `msg_type` | 1 | u8 | 消息类型 |
| 9 | `cmd` | 1 | u8 | 命令号 |
| 10 | `flags` | 2 | u16 | 协议标志 |
| 12 | `seq` | 4 | u32 | 双向请求响应事务号；同一会话内不得回绕复用 |
| 16 | `session_id` | 4 | u32 | 会话号 |
| 20 | `sensor_id` | 4 | u32 | 传感器数字 ID；未知时为 0 |
| 24 | `safety_param_crc` | 4 | u32 | 安全参数集 CRC |
| 28 | `payload` | N | bytes | 负载 |
| 28 + N | `safety_crc` | 4 | u32 | CRC32C |

`payload_len = frame_len - header_len - 4`。控制帧最大 `frame_len <= 128`。

### 5.2 周期快报帧 `FAST_REPORT_FRAME`

快报帧用于 `REPORT_MEAS_FAST`，固定 44 字节，不带 `header_len`、`sensor_id`、`safety_param_crc`、通用响应前缀或可变负载。`sensor_id` 和 `safety_param_crc` 在 `HELLO`、`GET_CONFIG_DIGEST` 和 `SET_COMM_MODE` 阶段由控制帧确认；若配置变化，传感器必须停止当前上报流或置诊断，CPU2 不得继续使用旧流数据。

| 偏移 | 字段 | 长度 | 类型 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | `sof0` | 1 | u8 | 固定 `0xA5` |
| 1 | `sof1` | 1 | u8 | 固定 `0x5A` |
| 2 | `frame_type` | 1 | u8 | 固定 `0xA1`，表示 `FAST_REPORT_FRAME` |
| 3 | `frame_len` | 1 | u8 | 固定 `44` |
| 4 | `src_id` | 1 | u8 | 源节点 ID |
| 5 | `dst_id` | 1 | u8 | 目的节点 ID |
| 6 | `stream_state` | 1 | u8 | 高 4 bit 测量模式，低 4 bit 通信/上报状态 |
| 7 | `session_id` | 4 | u32 | 会话号 |
| 11 | `stream_id` | 2 | u16 | 当前上报流 ID |
| 13 | `stream_seq` | 4 | u32 | 周期上报序号；同一会话内不得回绕复用 |
| 17 | `sample_counter` | 4 | u32 | 完整采样计数；同一会话内不得回绕复用 |
| 21 | `data_age_ms` | 2 | u16 | 数据年龄 |
| 23 | `status_flags16` | 2 | u16 | 快报状态位，映射第 6.3 节低 16 bit |
| 25 | `diag_flags16` | 2 | u16 | 快报诊断位，映射第 6.3 节低 16 bit |
| 27 | `temperature_c_x100` | 2 | i16 | 温度 |
| 29 | `density_kg_m3_x100` | 4 | i32 | 密度 |
| 33 | `frequency_hz_x1000` | 4 | u32 | 主频率 |
| 37 | `signal_quality` | 1 | u8 | 0..100 |
| 38 | `config_epoch` | 2 | u16 | 配置纪元，`safety_param_crc` 变化时递增；同一会话内不得回绕复用 |
| 40 | `safety_crc` | 4 | u32 | CRC32C |

快报帧压缩的是测量编码宽度，不压缩安全语义。`stream_seq`、`sample_counter` 和 `config_epoch` 在同一会话内均不得回绕复用；任一字段预计溢出前，传感器必须停止上报并要求重新 `HELLO`。`config_epoch` 是 `safety_param_crc` 的快报映射：CPU2 在进入上报前记录当前 `safety_param_crc` 和 `config_epoch`，快报中 `config_epoch` 不一致时必须丢弃数据并重新查询配置。快报帧字段不按 C 结构体自然对齐设计，收发双方必须按字节偏移逐字段编码和解码，不得直接将串口缓冲区强制转换为结构体。

`stream_state` 的冻结编码为 `((measure_mode & 0x0F) << 4) | comm_mode`。快报只允许 `IDLE(0x0)`、`DENSITY(0x1)`、`LEVEL(0x2)`、`WATER_CAP(0x3)`、`GYRO(0x4)`、`BOTTOM(0x5)` 出现在高 4 bit，低 4 bit 必须为 `PERIODIC_UPLINK(0x1)`。传感器进入 `SELF_TEST` 或 `FAULT` 前必须停止当前快报流，并通过控制帧状态、诊断和错误码报告；不得把 `0x7E`、`0x7F` 截断后塞入高 4 bit。

快报的协议内在取值也属于帧采用门禁：`signal_quality` 必须在 0..100；状态位和诊断位的保留 bit 必须为 0。帧层只负责拒绝编码范围和保留位错误，会话层还必须要求 `STREAM_ACTIVE=1`，拒绝 `STREAM_LOSS_DETECTED`、`STREAM_BUFFER_OVERFLOW`、全局失效诊断以及当前测量模式对应的通道诊断；安全快照发布接口必须再次执行同样的语义核对，不能依赖调用方一定先经过会话层。

### 5.3 CRC32C

| 项 | 值 |
| --- | --- |
| 算法 | CRC32C Castagnoli |
| 正向多项式 | `0x1EDC6F41` |
| 反射实现多项式 | `0x82F63B78` |
| 初值 | `0xFFFFFFFF` |
| 结果异或 | `0xFFFFFFFF` |
| 控制帧计算范围 | 从 `protocol_version` 到 `payload` 末尾，不含 SOF，不含 `safety_crc` |
| 快报帧计算范围 | 从 `frame_type` 到 `config_epoch` 末尾，不含 SOF，不含 `safety_crc` |
| 输出字节序 | 小端 |

CRC32C 用于检测损坏、截断和拼接错误。CRC 不是认证码，若威胁模型包含主动攻击，还需要认证机制。

### 5.4 消息类型和标志位

消息类型：

下列 `msg_type` 只用于控制帧。快报帧使用固定 `frame_type=0xA1`，不再携带 `msg_type` 字段。

| 值 | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| `0x01` | `REQ` | CPU2 -> 传感器 | 请求 |
| `0x81` | `RSP` | 传感器 -> CPU2 | 正常响应 |
| `0xC1` | `ERR` | 传感器 -> CPU2 | 错误响应 |
| `0xA0` | 保留 | 无 | 不用于基线周期上报；周期上报统一使用 `FAST_REPORT_FRAME(frame_type=0xA1)` |

标志位：

| bit | 名称 | 含义 |
| --- | --- | --- |
| 0 | `ACK_REQUIRED` | 请求要求响应 |
| 1 | `SAFETY_RELEVANT` | 帧承载安全相关数据或诊断 |
| 2 | `RETRY_FRAME` | 重发帧 |
| 3 | `CONFIG_CHANGED` | 配置变化，需要重新握手 |
| 4 | `COLD_START` | 节点冷启动或会话重建 |
| 5 | `ERROR_PRESENT` | 存在错误或诊断异常 |
| 6 | 保留 | 发送 0；基线接收端遇到 1 时拒绝 |
| 7 | `STOP_STREAM_REQUEST` | 请求停止周期上报 |
| 8 | `PARAM_WRITE` | 参数写入相关帧 |
| 9..15 | 保留 | 发送 0；基线接收端遇到非 0 时拒绝 |

V1 请求标志组合同时属于冻结契约：所有请求置 `ACK_REQUIRED`；`GET_CONFIG_DIGEST`、`SET_MEASURE_MODE`、所有安全测量读取、进入周期上报、`RUN_SELF_TEST` 和 `READ_SELF_TEST_RESULT` 还必须置 `SAFETY_RELEVANT`；`WRITE_PARAM`、`COMMIT_PARAM` 置 `PARAM_WRITE`；退出周期上报置 `STOP_STREAM_REQUEST`；HELLO 置 `COLD_START`。同一事务的第二次及后续发送追加 `RETRY_FRAME`，其它未定义组合不得由实现自行增加。golden frame 生成器和 CPU2 client 测试逐字节约束这些组合。

### 5.5 接收端最小校验顺序

传感器接收控制帧请求时按下列顺序处理：

1. 找到 `SOF`。
2. 检查 `frame_len` 是否在范围内。
3. 收满一帧后计算 CRC32C。
4. 检查 `dst_id`、`protocol_version`、`header_len`。
5. 检查保留字段和保留标志位均为 0。
6. 除 `HELLO` 外，检查 `session_id` 和 `safety_param_crc`。
7. 检查 `cmd` 是否支持、负载长度是否匹配。
8. 执行业务处理并生成响应。
9. 任一步失败时，不得使用负载中的测量值或参数值。

CRC、长度或 SOF 校验失败时，接收端不得依据该帧中不可信的地址、命令和序号发送错误响应，只做静默丢弃和本地诊断计数。只有在完整性、地址、会话和事务字段均可信后发现业务参数错误，才允许发送 `ERR` 响应。`BAD_CRC` 用于本地统计和测试注入结果，不作为对 CRC 错帧的在线应答。

CPU2 使用控制帧响应中的测量数据前必须满足：

1. SOF、长度和最大帧长合法。
2. CRC32C 正确。
3. `src_id`、`dst_id`、`sensor_id` 匹配。
4. `session_id` 匹配当前会话。
5. 双向响应的 `seq` 和 `cmd` 匹配当前请求。
6. `safety_param_crc` 与握手时一致。
7. `result_code == OK`。
8. `DATA_VALID == 1`。
9. `DATA_STALE == 0`。
10. `MODE_MATCH == 1`。
11. CPU2 使用本地单调时钟计算 `effective_age_ms = data_age_ms + (now_ms - rx_timestamp_ms)`，结果未超过当前安全功能允许值；计算必须饱和，禁止整数回绕。
12. `sample_counter` 相对上一次已接受快照严格前进，增量符合采样率和请求周期约束。
13. 数据物理范围、变化率和诊断位满足上层业务规则。

CPU2 使用快报帧测量数据前必须满足：

1. SOF、固定长度 44 和 `frame_type=0xA1` 合法。
2. CRC32C 正确。
3. `src_id` 和 `dst_id` 与当前 CPU2 和传感器节点匹配。
4. `session_id` 匹配当前会话。
5. `stream_id` 匹配当前上报流。
6. `stream_seq` 必须恰好等于上一已接受值加 1；重复、后退或跳号均使当前安全上报流失效。
7. `sample_counter` 必须严格前进；最大允许增量必须由 SRS 根据传感器采样率和上报周期给出后再启用，未冻结该上限前不得伪造经验阈值或宣称已完成增量合理性验证。
8. `config_epoch` 与进入上报时记录值一致。
9. `DATA_VALID == 1`。
10. `DATA_STALE == 0`。
11. 快报状态中的测量模式和通信状态符合 CPU2 期望，且 `STREAM_ACTIVE=1`、`STREAM_LOSS_DETECTED=0`。
12. 状态/诊断保留位为 0，`STREAM_BUFFER_OVERFLOW=0`，全局失效诊断和当前测量模式对应的通道诊断均未置位。
13. `signal_quality` 在 0..100，CPU2 使用本地单调时钟计算的 `effective_age_ms` 未超过当前安全功能允许值。
14. 数据物理范围、变化率和由 SRS 分配的质量阈值满足上层业务规则。

任一条件失败，数据不得作为安全相关输入使用。可以保留显示缓存，但必须标识为过期或无效。安全上报流出现序号跳号后进入 `RECOVERING`，不得用后续连续帧自行恢复；必须重新执行 `SET_COMM_MODE` 或 `HELLO` 建立新的流。非安全监测功能若希望跳号后接受最新值，必须使用与安全输入隔离的缓存和明确的非安全接口。

状态位：

| bit | 名称 | 含义 |

状态和诊断位必须按当前测量模式使用固定判定表，不能由调用点自行解释：

- `DATA_VALID=0`、`DATA_STALE=1`、`MODE_MATCH=0`、`MODE_SETTLING=1` 或 `CONFIG_MISMATCH=1` 时，所有安全测量值无效。
- `SELF_TEST_FAILED`、`PARAM_CRC_ERROR`、`CALIBRATION_INVALID`、`ADC_OR_TIMER_ERROR` 或 `INTERNAL_COMM_ERROR` 置位时，所有安全测量值无效并进入故障处理。
- 当前测量模式对应的通道错误置位时，该模式数据无效；非当前模式的通道错误可以保留用于维护诊断，但不得误伤当前模式，具体矩阵必须进入 SRS 和单元测试。
- 周期快报的 `STREAM_LOSS_DETECTED` 或 `STREAM_BUFFER_OVERFLOW` 置位时，当前安全快照无效；不得仅依赖下一帧序号看似连续而忽略发送端已报告的流故障。
- `LOW_SIGNAL_QUALITY`、`VALUE_CLAMPED`、电源或温度范围异常的失效级别和阈值必须由 SRS 固定，禁止仅凭 `signal_quality` 的显示值临时判断。
- 快报只传低 16 bit，因此任何未来新增的安全关键状态或诊断必须优先分配在 bit 0..15；若低位不足，必须定义新的快报 `frame_type`，不能把安全关键位只放在控制帧高 16 bit。

| 3 | `CAP_WATER_CAP` | 支持水位电容 |

| 5 | `CAP_BOTTOM` | 支持罐底/底部检测 |

| `accepted_max_silent_ms` | u16 | 实际最大静默时间 |
| `accepted_stream_id` | u16 | 实际上报流 ID |
| `accepted_control_guard_ms` | u16 | 实际控制窗口，9600 bps 下不得小于 100 ms |
| `accepted_config_epoch` | u16 | 本次上报流绑定的配置纪元 |
| `start_after_ms` | u16 | 确认后多久开始上报 |
| `reserved` | u16 | 保留 |

`control_guard_ms` 的下限必须按最坏控制请求计算：`ceil(max_control_request_bytes * 10 * 1000 / baud) + t_direction_switch_ms + t_scheduler_jitter_ms + t_clock_tolerance_ms`。当前 `SET_COMM_MODE` 请求为 46 字节，9600 bps、8N1 的纯线上时间约 47.9 ms，因此 50 ms 不具备足够裕量；本基线在 9600 bps 下规定最小值为 100 ms。控制窗口从每个快报帧最后一个 CRC 字节发送完成后开始，传感器除自身发送期间外持续监听。CPU2 未观察到完整合法快报或无法确认窗口相位时，不得盲发退出命令，应先按最大静默策略使安全数据失效，再执行链路恢复。

CPU2 接受进入周期上报的响应后，必须以响应接收时间为周期流起点。第一帧合法快报的最晚接收时刻为“周期流起点 + `start_after_ms` + `accepted_max_silent_ms`”，后续每帧的最晚接收时刻为“最近一帧合法快报接收时间 + `accepted_max_silent_ms`”。接收调用的等待时间必须裁剪到剩余静默预算，调用方给出的更长超时不得越过该截止点；传输层即使因调度抖动在截止点后返回成功，CPU2 仍必须按实际接收时间戳拒绝该迟到帧。截止前一次较短的轮询超时只返回传输超时并保留当前流，允许后续合法快报继续；到达截止点仍无合法快报时返回数据过期、立即使流和快照失效并进入恢复。

### 6.5 数值表示和倍率版本

通信层只传固定宽度整数，不传 float、double、ASCII 数字或带单位字符串。CPU2 应用层负责把整数换算成工程值。

| 场景 | 规则 |
| --- | --- |
| 快报帧 | 使用本卷固定倍率，必须保持短帧稳定；倍率变化必须更新 `scale_version`、`safety_param_crc` 和 `config_epoch` |
| 完整测量读取 | 使用字段名固定倍率和 `payload_version`，新增字段优先通过新的 `payload_version` 管理 |
| 参数读写 | 使用 `param_type`、`scale`、`unit_id` 和 `param_crc` 描述参数值 |
| 单位或倍率变化 | 必须改变 `scale_version`，并纳入 `safety_param_crc` 计算 |
| CPU2 解释数据 | 必须先确认 `safety_param_crc` 或 `config_epoch` 一致，再按对应倍率表换算 |

最终基线单位倍率表：

| 字段 | 线上类型 | 工程单位 | 倍率 | 示例 |

### 6.8 参数模型

#### 6.8.1 CRC 规范化字节流

`safety_param_crc` 和 `param_crc` 必须使用第 5.3 节相同的 CRC32C 参数。CRC 输入不是 C 结构体内存镜像，不包含编译器填充，必须按下列小端字段顺序逐字节序列化：

`param_crc` 单项记录：

| 顺序 | 字段 | 类型 |
| ---: | --- | --- |
| 1 | `param_schema_version` | u16 |
| 2 | `param_id` | u16 |
| 3 | `param_index` | u16 |
| 4 | `param_type` | u8 |
| 5 | `access` | u8 |
| 6 | `scale` | i16 |
| 7 | `unit_id` | u16 |
| 8 | `value_i64` | i64 |

`safety_param_crc` 参数集：

1. 先序列化固定头：`digest_schema_version(u16)`、`sensor_type(u16)`、`sensor_id(u32)`、`capability_flags(u32)`、`scale_version(u16)`、`calibration_version(u16)`、`param_table_version(u16)`、`safety_record_count(u16)`。
2. 只追加会影响安全相关测量解释、诊断阈值或安全反应的参数记录。
3. 参数记录按 `(param_id, param_index)` 升序排列，每条使用上表 `param_crc` 的规范化字段，但不追加该条记录的 CRC 值。
4. 不包含运行计数、时间戳、保留字段、结构体填充、非安全调试参数和通信统计计数。
5. 字段集合、类型、单位、倍率或排序规则发生变化时，必须递增对应 schema/version，使旧摘要必然失配。

协议工具必须为单参数、空安全参数集、最大参数集、负数 i64、倍率边界和字段顺序错误分别生成 golden vector。禁止发送端和接收端直接对本机 C 结构体求 CRC。

参数类型编码：

| `param_type` | 名称 | `value_i64` 约束 |
| ---: | --- | --- |
| `0x01` | `BOOLEAN` | 只能为 0 或 1 |
| `0x02` | `UNSIGNED` | 非负整数，实际工程值再应用 `scale` |
| `0x03` | `SIGNED` | 有符号整数，实际工程值再应用 `scale` |
| `0x04` | `ENUM` | 非负枚举值，枚举含义由受控参数表定义 |
| `0x05` | `BITMASK` | 非负位掩码，位含义由受控参数表定义 |

`access` 为位掩码：bit0=`READ`、bit1=`WRITE`，其它位固定为 0。通过 `READ_PARAM` 或 `READ_PARAM_PAGE` 返回的记录必须置 `READ`；只读参数为 `0x01`，可读写参数为 `0x03`。CPU2 遇到未知类型、未知访问位、未声明可读、布尔值越界或无符号类型负值时必须拒绝整项；`unit_id` 的具体单位枚举必须由 LTD 完整参数映射表冻结，不允许按软件内存类型临时推断。

参数 ID 分区：

| 范围 | 用途 |
| --- | --- |
| `0x0000..0x00FF` | 系统和通信参数 |
| `0x0100..0x01FF` | 密度测量参数 |
| `0x0200..0x02FF` | 温度补偿参数 |
| `0x0300..0x03FF` | 液位参数 |
| `0x0400..0x04FF` | 水位电容参数 |
| `0x0500..0x05FF` | 姿态和罐底参数 |
| `0x1000..0x1072` | LTD/V2 参数码 0 到 114 的完整兼容映射 |
| `0x8000..0x8FFF` | 只读诊断和统计计数 |

`READ_PARAM` 请求：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `param_id` | u16 | 参数 ID |
| `param_index` | u16 | 表项索引，无表项时 0 |

`READ_PARAM` 响应：

`param_crc` 规范化记录中的 `param_schema_version` 固定使用当前会话 HELLO 和 `GET_CONFIG_DIGEST` 返回的 `param_table_version`。传感器不得为单项参数另行使用未发布的 schema 版本；CPU2 发现版本不一致或按该版本重算 CRC 失败时，必须拒绝该参数值并重新建立会话。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `param_id` | u16 | 参数 ID |
| `param_index` | u16 | 表项索引，无表项时 0 |
| `param_type` | u8 | 数据类型 |

| `scale` | i16 | 十进制倍率，例如 -2 表示 x0.01 |
| `unit_id` | u16 | 单位枚举 |
| `value_i64` | i64 | 参数值 |
| `param_crc` | u32 | 参数项 CRC |

`READ_PARAM` 作为兼容和定点诊断入口保留，整机业务同步全部 LTD 参数时不要求调用方逐项读取。CPU2 上层只调用一次公开的 `SensorSafeAdapter_ReadAllParams`；适配层进入 service 后，由 client 在内部使用 `READ_PARAM_PAGE` 自动翻页。

`READ_PARAM_PAGE` 请求：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `start_index` | u16 | 按 `(param_id, param_index)` 升序排列后的起始序号，首帧固定为 0 |
| `max_items` | u8 | 本页最多返回项数，范围 1 到 3；CPU2 基线固定请求 3 |
| `reserved` | u8 | 固定为 0 |
| `expected_param_table_version` | u16 | 当前 HELLO 和 `GET_CONFIG_DIGEST` 已确认的参数表版本 |
| `expected_total_count` | u16 | 首帧固定 `0xFFFF` 表示未知；后续页必须回填首帧返回的总数 |

`READ_PARAM_PAGE` 响应的公共前缀之后追加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `total_count` | u16 | 当前完整逻辑参数表的记录总数，基线最大 256 |
| `next_index` | u16 | 下一页起始序号，必须等于本次 `start_index + item_count` |
| `item_count` | u8 | 本页实际记录数，范围 0 到 3 |
| `page_flags` | u8 | bit0=`LAST_PAGE`；其余位固定为 0 |
| `items` | `item_count * 22` 字节 | 依次使用 `READ_PARAM` 响应中的完整参数记录格式 |

分页一致性规则：

1. 传感器公开的全部稳定标量参数、标定参数、配置参数和允许读取的诊断参数都必须进入同一逻辑表；禁止把 RAM、Flash 或 C 结构体地址直接作为协议地址。数组或标定表使用同一 `param_id` 和不同 `param_index` 展开为多条记录。
2. 参数表按 `(param_id, param_index)` 严格升序，禁止重复、乱序和跨页回退。`start_index` 是该稳定排序中的序号，不是存储地址。
3. 控制负载上限为 96 字节。公共响应 20 字节、分页头 6 字节、三条完整记录 66 字节，总计 92 字节，因此基线每页最多 3 项。
4. 非末页必须至少返回一项且 `next_index < total_count`；末页必须满足 `next_index == total_count`。只有空参数表允许首帧返回 `item_count=0`、`total_count=0` 和 `LAST_PAGE=1`。
5. 同一次全表读取期间，`param_table_version`、控制帧头 `safety_param_crc` 和 `total_count` 必须保持不变。发生参数提交或表结构变化时必须拒绝旧分页请求并要求重新 HELLO，不能混合新旧页。
6. CPU2 必须逐项重算 `param_crc`，检查页内和跨页严格升序、游标前进、总数不变、末页闭合及调用方容量。任一页失败时整次参数表结果无效；容量不足时返回所需 `total_count`，不得把首帧部分结果当作完整表使用。
7. V1 测量入口的必需能力仍为 `CAP_DENSITY | CAP_LEVEL | CAP_MEAS_COMBO`。`CAP_PARAM_RW` 只门禁参数维护和完整表读取：未声明时 CPU2 仍可激活安全测量服务，但完整表接口在发帧前返回“不支持”；声明后若远端对 `READ_PARAM_PAGE` 返回 `UNSUPPORTED_COMMAND`，本次完整表读取失败，但不得让已经激活的 V1 测量入口下线。CPU2 不退化为 115 次 `READ_PARAM` 单读。

LTD/V2 完整参数映射冻结规则：

- 本映射对应 `param_table_version=2`。旧协议参数码连续覆盖十进制 0 到 114，共 115 项；安全协议固定使用 `param_id = 0x1000 + legacy_param_code`，因此首项为 `0x1000`，末项为 `0x1072`，`param_index` 固定为 0。
- 旧参数码 0 到 19 为只读基本信息、测量输出和原始量，`access=READ(0x01)`；参数码 20 到 114 位于旧表“参数（可读可写）”区域，安全协议返回 `access=READ|WRITE(0x03)`，写入仍必须经过 `WRITE_PARAM + COMMIT_PARAM` 维护事务。

## 7. 单向周期上报专项规则

周期上报不是无条件可信的广播数据。CPU2 必须维护上报流状态。

| 项 | 约束 |
| --- | --- |
| 启动 | 必须由 `SET_COMM_MODE(PERIODIC_UPLINK)` 启动，并得到 ACK |
| 上报内容 | 固定上报 `REPORT_MEAS_FAST` |
| 上报周期 | 由 CPU2 请求，传感器可返回实际采用值 |
| 最大静默 | 第一帧按 `start_after_ms + accepted_max_silent_ms`，后续帧按最近合法帧接收时间加 `accepted_max_silent_ms` 计算截止点；等待必须裁剪到剩余预算，超过截止点无有效帧即判定上报中断 |
| 序号 | `stream_seq` 必须严格连续；重复、回退或跳号使安全上报流失效并进入恢复 |
| 数据冻结 | `sample_counter` 必须严格前进；最大允许增量待 SRS 按采样率和上报周期冻结后实施 |
| 周期流自诊断 | `STREAM_ACTIVE` 必须置位，`STREAM_LOSS_DETECTED` 和 `STREAM_BUFFER_OVERFLOW` 必须清零 |
| 退出 | 必须由 CPU2 发 `SET_COMM_MODE(REQUEST_RESPONSE)` 并得到 ACK |
| 退出失败 | 连续 3 次退出失败后会话失效，停止使用上报数据 |
| 双向恢复 | 退出成功后同一 `session_id` 继续普通双向通信 |

长线 RS485 下，上报帧不得夹带参数表、自检结果、原始调试量或可由双向维护命令读取的数据。周期上报只传安全判断和实时显示必需字段，避免低波特率下总线占用过高。

快报通过 CRC、地址、会话、流 ID、序号、样本计数、配置纪元和模式连续性校验后，即视为一帧“协议合法快报”，应推进 `stream_seq`/`sample_counter` 期望值并刷新通信静默基准。若其状态位、诊断位、质量或 `data_age_ms` 随后判定数据无效，CPU2 仍不得发布或保留安全快照；该帧只证明通信链路未静默，不能证明安全测量数据可用。这样既避免连续的明确故障上报被误记为链路静默，也不会让故障数据进入安全输入。

### 7.1 进入周期上报

1. CPU2 发送 `SET_COMM_MODE(PERIODIC_UPLINK)`。
2. 传感器返回 `RSP`，确认周期、静默时间、`stream_id` 和配置纪元；通用前缀必须为期望测量模式、`PERIODIC_UPLINK`、`MODE_MATCH=1`、`STREAM_ACTIVE=1`，且不得声明稳定中或配置不匹配。
3. CPU2 以进入响应的接收时间启动首次快报静默计时，转入接收上报状态；任何接收等待不得越过 `start_after_ms + accepted_max_silent_ms` 截止点。
4. 传感器在 `start_after_ms` 后发送 `REPORT_MEAS_FAST`；CPU2 接受首帧后改以最近合法快报接收时间计算后续 `accepted_max_silent_ms` 截止点。

### 7.2 退出周期上报

1. CPU2 在上报期间发送 `SET_COMM_MODE(REQUEST_RESPONSE)`。
2. CPU2 在一帧合法快报结束后、`accepted_control_guard_ms` 窗口内发送命令；传感器除自身发送期间外持续接收。
3. 传感器停止发送 `REPORT_MEAS_FAST`。
4. 传感器返回 `RSP`，确认已回到 `REQUEST_RESPONSE`；通用前缀必须保留期望测量模式、`MODE_MATCH=1`，清除 `STREAM_ACTIVE`、稳定中和配置不匹配，追加负载中的周期、静默、流 ID、控制窗口和启动延迟必须清零，配置纪元必须保持进入上报时的值，保留字段必须为 0。
5. CPU2 继续使用同一 `session_id` 发送普通双向命令。

正常退出不重新 `HELLO`，因为会话没有失效；`stream_id` 失效即可阻断旧上报流。若退出失败，才判定会话失效并重新 `HELLO`。

### 7.3 上报期间允许的下行控制

传感器在周期上报期间必须保留确定性的接收窗口。每个上报周期内必须预留协商后的 `accepted_control_guard_ms`，用于接收 CPU2 的退出命令、状态查询或紧急停止上报命令；9600 bps 下不得接受小于 100 ms 的值。周期上报期间只允许：

- `SET_COMM_MODE(REQUEST_RESPONSE)`。
- `PING`。
- `RESET_SESSION`。

其它命令需要先退出上报。

| `session_id` | `0x23070301` | `HELLO` 后建立的示例会话号 |

### 8.1 上电握手

1. CPU2 发送 `HELLO` 请求。

   | 类别 | 关键字段 |
   | --- | --- |
   | 帧头 | `src_id=0x01`，`dst_id=0x10`，`msg_type=REQ`，`cmd=HELLO`，`flags=ACK_REQUIRED`，`seq=1`，`session_id=0`，`sensor_id=0`，`safety_param_crc=0` |
   | 负载 | `cpu_protocol_min=1`，`cpu_protocol_max=1`，`cpu_node_id=0x01`，`cpu_boot_counter=25`，`cpu_nonce=0x6A135724` |

2. 传感器校验 `SOF`、长度、CRC、地址和协议版本后，返回 `HELLO` 响应。

   | 类别 | 关键字段 |
   | --- | --- |
   | 帧头 | `src_id=0x10`，`dst_id=0x01`，`msg_type=RSP`，`cmd=HELLO`，`seq=1`，`session_id=0x23070301`，`sensor_id=0x12345678`，`safety_param_crc=0x89ABCDEF` |
   | 通用前缀 | `result_code=OK`，`measure_mode=IDLE`，`comm_mode=REQUEST_RESPONSE`，`status_flags=0`，`diag_flags=0`，`sample_counter=0`，`data_age_ms=0`，`payload_version=1`，`data_quality=100` |
   | 追加负载 | `selected_protocol=1`，`sensor_node_id=0x10`，`sensor_sw_version=<传感器版本>`，`sensor_boot_counter=<启动计数>`，`sensor_session_counter=<本次启动内会话计数>`，`echo_cpu_boot_counter=25`，`echo_cpu_nonce=0x6A135724`，`new_session_id=0x23070301`，`capability_flags=CAP_DENSITY + CAP_MEAS_COMBO + CAP_PERIODIC_UPLINK + CAP_POWER`，`scale_version=<倍率版本>`，`calibration_version=<标定版本>`，`param_table_version=<参数表版本>`，`digest_schema_version=1` |

3. CPU2 先确认响应回显的 `cpu_boot_counter`、`cpu_nonce` 与本次挑战一致，`sensor_session_counter` 没有重复，且新 `session_id` 非零、不同于最近一次已接受值，再保存 `session_id`、`sensor_id`、`capability_flags`、`scale_version` 和 `safety_param_crc`。后续控制帧必须带同一组值；快报帧必须带与该配置绑定的 `config_epoch`，直到重新 `HELLO` 或重新进入上报。

传感器端实现要点：`HELLO` 是唯一允许 `session_id=0` 的正常业务命令；其它命令在未建会话时返回 `BAD_SESSION` 或直接拒绝。

### 8.2 双向读取密度组合数据

1. CPU2 切换到密度测量模式。

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=SET_MEASURE_MODE`，`seq=2`，`session_id=0x23070301`，`safety_param_crc=0x89ABCDEF` |
   | 请求负载 | `target_mode=DENSITY`，`mode_option=0` |
   | 响应负载 | `result_code=OK`，`accepted_mode=DENSITY`，`settle_time_ms=800`，`mode_counter=1` |

2. 在 `settle_time_ms` 到达前，传感器可返回 `MODE_SETTLING`，CPU2 不使用测量值参与安全判断。

3. CPU2 发送组合读取。

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=READ_MEAS_COMBO`，`seq=3`，`session_id=0x23070301` |
   | 请求负载 | `read_mask=0`，表示读取默认组合 |
   | 响应通用前缀 | `result_code=OK`，`measure_mode=DENSITY`，`comm_mode=REQUEST_RESPONSE`，`status_flags=DATA_VALID + MODE_MATCH`，`diag_flags=0`，`sample_counter=1024`，`data_age_ms=30`，`payload_version=1`，`data_quality=98` |
   | 响应测量值 | `temperature_c_x100=2534`，`density_kg_m3_x100=99876`，`frequency_hz_x1000=123456789`，`signal_quality=930` |

4. CPU2 接收后按固定顺序判断：CRC 正确、地址正确、`session_id` 匹配、`seq=3` 匹配、`cmd=READ_MEAS_COMBO` 匹配、`safety_param_crc` 匹配、`DATA_VALID` 和 `MODE_MATCH` 置位、`DATA_STALE` 未置位，并以本地单调时钟计算的 `effective_age_ms` 未超过 SRS 限值。

传感器端实现要点：组合响应应先从测量任务复制一份快照，再编码响应，避免温度、密度和频率来自不同采样周期。

### 8.3 切入单向周期上报

1. CPU2 使用双向命令启动周期上报。

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=SET_COMM_MODE`，`seq=4`，`session_id=0x23070301`，`flags=ACK_REQUIRED + SAFETY_RELEVANT` |
   | 请求负载 | `target_comm_mode=PERIODIC_UPLINK`，`report_cmd=REPORT_MEAS_FAST`，`reserved0=0`，`period_ms=1000`，`max_silent_ms=3000`，`stream_id=0x1201`，`control_guard_ms=100` |

2. 传感器确认进入上报模式。

   | 类别 | 关键字段 |
   | --- | --- |
   | 响应帧头 | `msg_type=RSP`，`cmd=SET_COMM_MODE`，`seq=4`，`session_id=0x23070301` |
   | 响应负载 | `result_code=OK`，`comm_mode=PERIODIC_UPLINK`，`status_flags=DATA_VALID + MODE_MATCH + STREAM_ACTIVE`，`accepted_comm_mode=PERIODIC_UPLINK`，`accepted_report_cmd=REPORT_MEAS_FAST`，`accepted_period_ms=1000`，`accepted_max_silent_ms=3000`，`accepted_stream_id=0x1201`，`accepted_control_guard_ms=100`，`accepted_config_epoch=<当前配置纪元>`，`start_after_ms=100` |

3. CPU2 保存 `accepted_stream_id`、`accepted_control_guard_ms` 和 `accepted_config_epoch`；传感器在 `start_after_ms` 后开始发送 `REPORT_MEAS_FAST`。该上报使用固定 44 字节 `FAST_REPORT_FRAME`，不使用控制帧头和通用响应前缀。

   | 上报帧 | 关键字段 |
   | --- | --- |
   | 第 1 帧 | `frame_type=0xA1`，`frame_len=44`，`src_id=0x10`，`dst_id=0x01`，`stream_state=<DENSITY+PERIODIC>`，`session_id=0x23070301`，`stream_id=0x1201`，`stream_seq=1`，`sample_counter=1025`，`data_age_ms=25`，`config_epoch=<当前配置纪元>` |
   | 第 2 帧 | `stream_id=0x1201`，`stream_seq=2`，`sample_counter=1026`，`data_age_ms=24`，`config_epoch=<当前配置纪元>` |
   | 第 3 帧 | `stream_id=0x1201`，`stream_seq=3`，`sample_counter=1027`，`data_age_ms=26`，`config_epoch=<当前配置纪元>` |

4. CPU2 每收到一帧都重新检查 CRC、`src_id`、`dst_id`、`session_id`、`stream_id`、`stream_seq`、`sample_counter`、`config_epoch`、`data_age_ms`、`signal_quality`、`STREAM_ACTIVE`、流故障状态和当前模式通道诊断。任何一项失败，都不得更新安全相关测量值。

传感器端实现要点：单向周期上报不是永久禁止 CPU2 下行控制。传感器仍需要在 `control_guard_ms` 窗口或接收中断中识别 `SET_COMM_MODE(REQUEST_RESPONSE)`，以便退出上报。

### 8.4 退出单向上报并继续双向通信

1. CPU2 在上报期间发送退出命令。

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=SET_COMM_MODE`，`seq=5`，`session_id=0x23070301`，`flags=ACK_REQUIRED + STOP_STREAM_REQUEST` |
   | 请求负载 | `target_comm_mode=REQUEST_RESPONSE`，`report_cmd=0`，`reserved0=0`，`period_ms=0`，`max_silent_ms=0`，`stream_id=0x1201`，`control_guard_ms=0` |

2. 传感器停止当前 `stream_id=0x1201` 的上报，并返回确认。

   | 类别 | 关键字段 |
   | --- | --- |
   | 响应帧头 | `msg_type=RSP`，`cmd=SET_COMM_MODE`，`seq=5`，`session_id=0x23070301` |
   | 响应负载 | `result_code=OK`，`comm_mode=REQUEST_RESPONSE`，`accepted_comm_mode=REQUEST_RESPONSE`，`accepted_stream_id=0`，`status_flags=DATA_VALID + MODE_MATCH` |

3. CPU2 收到退出响应后，保留同一 `session_id`，继续发送普通双向命令。例如读取电源：

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=READ_POWER`，`seq=6`，`session_id=0x23070301` |
   | 响应负载 | `result_code=OK`，`voltage_mv=<传感器供电电压>`，`power_status=<电源状态>` |

4. 如果退出响应之后仍收到旧 `stream_id=0x1201` 的 `REPORT_MEAS_FAST` 快报帧，CPU2 必须丢弃，不得更新测量值。若退出命令超时，同一事务最多发送 3 次，即首次发送加 2 次置 `RETRY_FRAME` 的重发；仍失败则判定链路或传感器状态异常，重新 `HELLO` 或进入整机安全状态。

### 8.5 异常通信示例

| 场景 | 示例 | 接收方处理 |
| --- | --- | --- |
| CRC 错 | 任意帧 `safety_crc` 校验失败 | 丢弃帧，不使用负载；可记录 `BAD_CRC` 统计 |
| 响应超时 | CPU2 发 `READ_MEAS_COMBO(seq=7)` 后超过当前波特率对应普通请求超时无响应 | CPU2 用同一 `seq=7` 重发，并置 `RETRY_FRAME`；数据是否可用先按 `data_age_ms` 和安全功能响应时间判定 |
| 重复请求 | 传感器收到同一 `seq` 的重复 `READ_MEAS_COMBO` | 无副作用命令可返回最近一次响应；写参数类命令不得靠重复帧重复提交 |
| 旧会话帧 | 收到 `session_id` 不是当前会话的响应或上报 | 直接丢弃，不更新状态和数据 |
| 上报丢帧 | CPU2 期望 `stream_seq=11`，实际收到 `stream_seq=12` | 当前帧不进入安全输入，安全上报流失效并重新启动；非安全监测缓存可按独立策略更新 |
| 上报静默 | 超过 `max_silent_ms` 未收到合法 `REPORT_MEAS_FAST` 快报帧 | 置数据无效，尝试退出上报或重新 `HELLO` |
| 配置变化 | 帧头 `safety_param_crc` 与 CPU2 记录值不同 | 拒绝使用数据，执行 `GET_CONFIG_DIGEST` 或重新 `HELLO` |
| 模式不匹配 | CPU2 期望 `DENSITY`，响应为 `LEVEL` 或 `MODE_MATCH` 未置位 | 不使用测量值，重新设置测量模式或上报故障 |

## 9. 状态机、超时和兼容

### 9.1 CPU2 状态

| 状态 | 说明 | 允许动作 |
| --- | --- | --- |
| `OFFLINE` | 未建立会话 | `HELLO` |
| `SESSION_READY` | 会话建立，默认双向模式 | `GET_STATUS`、`SET_MEASURE_MODE`、读数、参数读写 |
| `MEASURE_READY` | 测量模式稳定 | 双向读数或启动周期上报 |
| `PERIODIC_ACTIVE` | 周期上报运行中 | 接收 `REPORT_MEAS_FAST`、退出上报、保活 |
| `RECOVERING` | 通信或诊断异常恢复 | `PING`、`RESET_SESSION`、`HELLO` |
| `FAULT` | 最终故障 | 停止使用数据，等待安全策略处理 |

### 9.2 传感器状态

| 状态 | 说明 | 允许动作 |
| --- | --- | --- |
| `BOOT` | 上电初始化 | 等待 `HELLO` |
| `READY` | 会话已建立 | 响应双向命令 |
| `SETTLING` | 模式切换稳定中 | 响应状态，不输出有效测量 |
| `MEASURING` | 正常采样 | 响应读数或进入周期上报 |
| `STREAMING` | 周期上报中 | 发送上报，接收退出命令 |
| `SELF_TEST` | 自检中 | 限制普通读数 |
| `FAULT` | 内部故障 | 返回错误响应和诊断 |

### 9.2.1 安全反应契约

协议层只负责宣布“安全数据有效/无效”，不能自行定义整机执行器位置。每个使用传感器数据的安全功能必须在 SRS 中定义安全状态、过程安全时间和故障容忍时间间隔 FTTI，并满足下列强制规则：

1. 任一关键完整性、会话、事务、配置、年龄、状态或诊断校验失败时，CPU2 在当前调度周期内原子地撤销安全快照有效标志；旧值不得继续以“最后一次有效值”参与安全控制。
2. 从故障被检测到到整机达到安全状态的总时间，包括任务调度、重试、日志、执行器动作和机械过程，必须小于对应安全功能的 FTTI。
3. 通信重试只能用于恢复可用性，不得延长安全数据有效期，也不得阻塞安全状态动作。
4. `RECOVERING` 返回安全数据有效状态前，至少完成新的 HELLO 挑战响应、配置摘要一致性检查、模式确认和由 SRS 规定数量的连续有效新快照；自检或硬件诊断要求不得被通信恢复绕过。
5. 自动恢复次数、锁存条件、人工复位条件、降级模式和执行器安全输出由 SRS 明确，并通过端到端故障注入验证。

### 9.3 超时和重试

200 米 RS485 长线下，实时性必须按 9600 bps 预算。下表按 8N1 串口 10 bit/字节估算，仅计算线上传输时间，未包含收发方向切换、驱动使能延时、调度延时和传感器处理时间。

| 帧或事务 | 字节数估算 | 9600 bps | 19200 bps | 38400 bps |
| --- | ---: | ---: | ---: | ---: |
| `REPORT_MEAS_FAST` 快报帧 | 固定 44 B | 约 46 ms | 约 23 ms | 约 12 ms |
| `READ_MEAS_COMBO` 请求 + 响应 | 约 120 B | 约 125 ms | 约 63 ms | 约 32 ms |
| `SET_COMM_MODE` 请求 + 响应 | 约 110 B | 约 115 ms | 约 57 ms | 约 29 ms |

实时性结论：

- 9600 bps 是当前项目设计基线，周期上报推荐不小于 1000 ms。
- 1000 ms 周期下，`REPORT_MEAS_FAST` 线上占用约 4.6%；500 ms 周期下约 9.2%，还需叠加方向切换、静默间隔和 CPU2 偶发下行命令。
- 500 ms 周期在 9600 bps 下可以配置，但应只用于明确需要更快刷新且现场误码率验证通过的场景。
- 19200 或 38400 bps 可用于更高实时性，但必须通过现场线缆和电磁环境测试确认后才能作为项目配置。
- 控制逻辑不得同步阻塞等待 3 次完整重试后才判定数据失效；数据是否可用必须优先由 `data_age_ms`、`sample_counter`、状态位、诊断位和 `max_silent_ms` 判断。
- 异常重试属于通信恢复流程，不属于安全相关数据继续可用的依据。

| 项 | 建议值 |
| --- | --- |
| 普通请求超时 | 9600 bps 下 300 ms；维护命令可放宽 |
| 普通请求重试 | 3 次 |
| 模式切换响应超时 | 1000 ms |
| 模式稳定等待 | 以 `settle_time_ms` 为准，上层设置最大值 |
| 周期上报周期 | 500 到 5000 ms；200 米 RS485 推荐不小于 1000 ms |
| 周期上报最大静默 | 不小于 `period_ms * 3` |
| 退出周期上报发送上限 | 同一事务最多 3 次发送：首次 1 次 + `RETRY_FRAME` 重发 2 次 |
| 自检超时 | 由传感器声明，上层设置最大值 |

所有超时和重试总耗时必须纳入安全功能响应时间预算。若安全功能要求更短响应时间，应在 SRS 中重新定义波特率、上报周期、最大数据年龄、重试次数和安全状态。

### 9.4 版本和兼容

| 项 | 规则 |
| --- | --- |
| `protocol_version` | 帧格式不兼容时递增 |
| `payload_version` | 单个命令负载结构变化时递增 |
| `safety_param_crc` | 能力位、倍率、传感器 ID、标定版本或安全相关配置变化时更新 |
| `scale_version` | 单位倍率表变化时递增，并纳入 `safety_param_crc` |
| `config_epoch` | u16 快报配置纪元，跟随 `safety_param_crc` 安全相关变化递增或重新分配；同一会话内不得回绕，预计溢出前必须停止上报并重新 HELLO |
| u32 序号和计数 | `seq`、`stream_seq`、`sample_counter` 同一会话内不得回绕复用；预计溢出前必须停止业务并重新 HELLO |
| 保留字段 | 发送 0；基线安全接收路径遇到非 0 时拒绝，不能把未知扩展静默解释为旧语义 |
| 新命令 | 未来新增可选命令必须通过能力位声明；V1 的 `READ_PARAM_PAGE` 与既有 `READ_PARAM/WRITE_PARAM/COMMIT_PARAM` 共用可选 `CAP_PARAM_RW`，远端仍可对不支持的命令返回 `UNSUPPORTED_COMMAND` |
| 新上报字段 | 基线快报固定 44 字节；新增快报字段必须定义新的 `frame_type`，若走控制帧完整读取则递增 `payload_version`，不得让同一快报帧变长 |

本次 `READ_PARAM_PAGE` 不改变控制帧头、CRC 覆盖、已有命令值或已有命令负载，因此线上 `protocol_version` 继续使用 `0x01`。兼容边界由可选能力和标准错误响应收敛：没有 `CAP_PARAM_RW` 的原 V1 传感器仍可完成测量探测；声明该能力但不实现分页命令的旧端点会让完整表接口收到 `UNSUPPORTED_COMMAND`，但不会被 CPU2 从已激活的测量服务中踢出，也不会触发 115 次单读回退。需要完整参数导出的新 LTD 传感器固件必须同时声明该能力并实现 115 项映射。该变化只发生在 CPU2 与传感器之间，不修改 CPU2/CPU3 共享字段、寄存器、命令或状态，因此不触发 `DEVICE_PROTOCOL_VERSION`；也不改变 `DeviceParameters` 持久化结构和 `DEVICE_PARAM_VERSION`。

## 10. 实现架构建议

### 10.1 传感器端推荐层次

| 层次 | 传感器端职责 | 实现建议 |
| --- | --- | --- |
| 字节接收 | 查找 `SOF`、累计长度、限制最大帧长 | 状态机实现，超长立即丢弃 |
| 帧校验 | 校验 `frame_len`、地址、版本、CRC32C | 先校验再解析负载 |
| 会话检查 | 管理 `session_id`、`seq`、`safety_param_crc` | 只保存当前会话和最近事务 |
| 命令分发 | 按 `cmd` 调用处理函数 | 使用静态命令表，未知命令返回 `UNSUPPORTED_COMMAND` |
| 测量快照 | 读取同一采样周期的温度、密度、频率和诊断 | 先复制快照，再编码响应或上报 |
| 上报调度 | 按 `period_ms` 周期发送 `REPORT_MEAS_FAST` | 单定时器、单 `stream_id`、单 `stream_seq` |

### 10.2 CPU2 已实现分层

CPU2 已围绕本协议建立独立服务层，旧 DSM/LTD 文件不承担 V1 解析：

| 实现模块 | 已实现职责 |
| --- | --- |
| `sensor_safe_crc32c` / `sensor_safe_frame` | CRC32C、固定偏移编码、控制帧和快报帧严格解码 |
| `sensor_safe_session` | HELLO、会话、u32 事务序号、快报连续性和重放边界 |

### 10.3 CPU2 兼容和启用边界

- CPU2 持久化传感器类型新增 `SAFE_SENSOR=14`。识别顺序固定为 CH9141 链路检查、安全协议 HELLO、LTD/V2、DSM 一代；安全 HELLO 失败必须释放 UART6 后继续旧协议探测。
- 安全协议停用或回退只清运行态，不清本次 CPU2 启动内的传感器启动计数、会话计数和最近会话号历史；后续重新探测不得接受停用前会话号的回放。
- `SAFE_SENSOR=14` 仅用于 CPU2 传感器驱动选择。CPU2 仍通过既有 u32 `sensorType` 字段原样同步，CPU3 只缓存和打印该数值，不按传感器枚举分支消费；本次未改变共享字段地址、宽度、布局、命令、状态或双方消费语义，因此 `DEVICE_PROTOCOL_VERSION` 保持 15，CPU3 固件不升版。若后续 CPU3 或外部协议开始解释 14 的业务含义，届时必须按共享协议变化同步升版并补充协议变更记录。
- 周期快报默认只进入隔离快照，不自动替代现有安全控制输入。只有 SRS 明确允许且 FTTI、最大静默、退出失败反应均有台架证据时，业务层才可显式消费。
- 快照发布和读取当前限定在 CPU2 主循环单调度域；双缓冲用于避免半写数据，不等同于跨 ISR/任务的通用无锁队列。若后续引入并发消费者，必须增加受评审的临界区或原子内存顺序并重新做并发测试。
- 每次初始或恢复 HELLO 成功后，CPU2 必须立即执行 `GET_CONFIG_DIGEST` 并与 HELLO 身份逐字段核对；摘要不一致、读取失败或配置纪元为 0 时不得把服务置为活动。
- 只读事务因传输或协议错误失败后，允许一次新 HELLO、配置摘要复核和一次原业务重试；副作用命令在响应不确定时禁止跨新会话自动重放，并记录恢复阻断计数。只有可信 `ERR` 明确返回 `BAD_SESSION` 或 `CONFIG_MISMATCH`，证明原事务被拒绝时，副作用命令才允许进入同一单次恢复边界。只有业务重试成功才记录为恢复成功，最终失败仍交由现有 `fault_manager` 统一置错。
- 可信 `ERR` 中的 `BAD_SESSION` 或 `CONFIG_MISMATCH` 表示当前会话/配置身份已经失效，CPU2 必须进入同一单次 HELLO 恢复边界；`PARAM_CRC_ERROR`、硬件、自检、电源和温度错误仍作为远端故障上报，不得用自动重握手掩盖。
- 周期流活动时，普通测量请求不得隐式触发 HELLO 或在未确认的控制窗口发送；调用方必须先通过专用退出接口结束上报，退出失败则撤销快照并进入恢复/安全状态。
- CPU2 client 维护饱和诊断计数，分别记录控制请求、实际发送、同事务重发、可信响应、传输失败、协议拒绝、CRC 拒绝、地址拒绝、远端错误、快报接收和快报接受；UART6 transport 另行记录 `PE/NE/FE/ORE/DMA/BREAK`、硬件错误总数、超时和短帧。长稳记录必须同时保留事件数和发送/接收分母。
- `MEASURE_READY` 已作为实际会话状态实现。只有模式回显正确、`MODE_MATCH=1` 且 `MODE_SETTLING=0`、配置无不一致时才进入该状态或启动周期流；缺少密度、液位、组合读任一整机必需能力时，不得把设备识别为可用安全传感器。

## 11. 验证和认证追踪

### 11.1 SIL 通信满足性结论

本协议作为内部受控链路上的安全通信层，设计目标覆盖 IEC 62280 所列常见通信失效类型，并参照 IEC 61784-3 black channel 思路设置主要防护措施；这不是对上述标准的符合性声明。是否满足目标 SIL，不能由协议文档单独判定，还必须结合适用产品标准、整机 SRS、硬件失效率、诊断覆盖率、软件生命周期、验证记录和认证机构解释。

当前结论：

| 分类 | 结论 |
| --- | --- |
| 通信失效检测 | 协议设计已覆盖损坏、删除、重复、乱序、延迟、伪装、错配置和旧数据使用 |
| 传感器端可实现性 | 协议已按固定帧长、单请求、单上报流、无分片、无 TLV、无动态队列简化 |
| SIL 认证资料 | 协议卷可作为通信层设计输入，但还不是完整认证包 |
| 主动攻击/网络安全 | 不在协议本体内闭环；若链路有无线、开放网络或非受控接入，必须增加 IEC 62443 系统安全措施 |

#### 11.3.1 通信残余危险失效率论证

认证资料不得直接把 CRC 宽度换算为 `2^-32` 后宣称充分。至少应针对控制帧最大 128 字节和固定 44 字节快报分别给出：链路误码和突发错误模型、每小时安全相关帧数、CRC32C 对目标帧长的汉明距离或已验证错误覆盖、长度/地址/会话/序号等附加防护的独立性、软件系统性错误和共因失效假设。通信残余贡献可用下式作为预算框架，但每一概率项必须有分析或测试依据：

`lambda_DU_comm = N_safety_frames_per_hour * P_undetected_per_frame * P_dangerous_given_undetected`

计算结果必须小于整机 SRS 分配给传感器通信链路的危险失效率预算，并保留足够裕量。24 小时无错误长稳只能证明基本稳定性，不能替代该定量论证；需要使用确定性故障注入、CRC特性分析、边界值穷举/抽样和现场 BER/EMC 数据共同支撑。

### 11.4 复杂度优化检查

在满足通信安全要求的前提下，已经做出的简化如下：

| 优化项 | 处理结果 | 为什么可简化 |
| --- | --- | --- |
| 删除分片/重组 | 最大 128 字节单帧承载全部业务负载 | 当前测量和维护负载均可放入单帧，分片会显著增加状态机复杂度 |
| 删除多路并发事务 | CPU2 同一时刻只保留一个未完成请求 | 内部传感器链路不需要吞吐优先，安全性和可验证性更重要 |
| 删除多上报流 | 同一会话只允许一个 `stream_id` | 用户只要求一个单向周期上报模式，多流会增加退出和静默判断复杂度 |
| u32 序号复用原保留空间 | `seq` 使用原控制头保留位，`stream_seq` 和 `sample_counter` 使用原快报保留字节 | 快报仍固定 44 字节，同时删除频繁 u16 回绕分支 |
| 安全输入优先主站轮询 | SRS 未明确要求主动周期上报时，安全控制默认使用 `REQUEST_RESPONSE`；周期上报可用于隔离的非安全实时监测 | 点对点半双工主站轮询时序更确定，可删除主动发送碰撞和退出窗口依赖 |
| 安全运行与参数维护隔离 | 参数写入只允许在整机安全状态和受控维护流程执行 | 减少运行安全路径的副作用和需要认证的软件分支 |
| 删除调试抓取命令 | 不在安全通信基线中定义原始 AD/内部调试量读取 | 调试数据不应被安全功能使用，另建非安全维护通道更清晰 |
| 删除独立状态上报 | 不定义单独的状态周期上报帧 | `REPORT_MEAS_FAST` 已携带通用状态和诊断前缀，避免两个上报流口径不一致 |
| 删除链路保留消息 | 不定义额外链路控制消息类型 | `PING`、`RESET_SESSION` 已覆盖保活和恢复 |
| 删除协议内认证码 | 不在本协议内定义密钥认证字段和能力位 | 当前目标是内部受控功能安全通信；主动攻击场景应由系统安全通道和密钥生命周期覆盖 |
| 保留参数维护但不进入测量流程 | `WRITE_PARAM`/`COMMIT_PARAM` 独立维护流程 | 满足配置管理，同时避免测量链路中出现配置副作用 |

不建议继续简化的点：

| 不建议删除项 | 原因 |
| --- | --- |
| `session_id` | 删除后旧帧、上电前残留帧和重放类失效难以阻断 |
| `seq` | 删除后双向响应错配、重复响应和乱序响应难以验证 |
| `stream_id`/`stream_seq` | 删除后无法证明单向上报退出后旧流不会被误用 |
| `safety_param_crc` | 删除后倍率、标定或能力变化后 CPU2 可能按旧解释使用数据 |
| `data_age_ms`/`sample_counter` | 删除后旧数据、缓存数据和冻结数据难以诊断 |
| `status_flags`/`diag_flags` | 删除后 CPU2 无法区分数据无效、模式未稳定、低质量和硬件诊断异常 |

### 11.6 golden frame 机器契约

协议 V1 的权威机器契约已生成。当前共 55 个控制帧向量和 7 个快报向量，已纳入 CPU2 主机测试；传感器端仍需使用同一 JSON 对拍：

- 帧向量：`golden_frames/sensor_safe_protocol_v1.json`。
- 参数摘要向量：`golden_frames/sensor_safe_param_digest_v1.json`。
- 确定性生成器：`tools/sensor_safe_protocol_vectors.py`。
- 契约检查器：`tools/check_sensor_safe_protocol_contract.py`。

机器契约同时显式保存帧常量、全部控制/快报字段偏移、消息类型、命令、测量/通信模式、控制标志、状态位、诊断位、能力位、线上错误码和允许掩码。契约检查器会解析 CPU2 `sensor_safe_types.h` 并逐项比较数值和受控符号集合，避免 C 侧新增、删除或改错枚举后仍因样例帧覆盖不足而漏检。

冻结范围如下；新增实现用例可以扩充向量，但不得在不变更协议版本的情况下改写已有有效向量：

- `HELLO` 请求和响应，以及旧响应重放、nonce 不回显、启动计数不匹配和会话计数重复。
- 控制事务失败后的新 nonce HELLO、新 `session_id`、恢复配置摘要复核和单次只读业务重试恢复帧。
- `PING`、`GET_STATUS`、`RESET_SESSION` 请求和响应。
- `SET_MEASURE_MODE(DENSITY)` 请求和响应。
- `READ_MEAS_COMBO` 请求和响应。
- `SET_COMM_MODE(PERIODIC_UPLINK)` 请求和响应。
- `REPORT_MEAS_FAST` 固定 44 字节连续 3 帧。
- `SET_COMM_MODE(REQUEST_RESPONSE)` 退出上报请求和响应。
- `SET_COMM_MODE(PERIODIC_UPLINK)` 字段越界响应。
- `READ_LEVEL_FREQ`、`READ_WATER_CAP`、`READ_GYRO`、`READ_POWER` 正常响应。
- `GET_CONFIG_DIGEST`、`READ_PARAM`、`WRITE_PARAM`、`COMMIT_PARAM` 正常响应和配置 CRC 变化响应。
- `READ_PARAM_PAGE` 首帧三项、末帧两项、总数回填、下一序号和 `LAST_PAGE` 闭合。
- `RUN_SELF_TEST`、`READ_SELF_TEST_RESULT` 正常和失败响应。
- CRC 错、长度错、字段越界、非零保留字段、地址错、序号错、会话错、配置 CRC 错、快报 `config_epoch` 错。
- `param_crc` 与 `safety_param_crc` 规范化字节流、字段换序、结构体填充和参数原子提交掉电恢复。
- 温度、密度、频率、电压、信号质量的倍率边界值和 golden frame 工程值换算。
- 周期上报丢帧、重复、回退、静默超时和退出失败。

### 11.7 验证矩阵

| 测试类别 | 测试项 | 预期结果 |
| --- | --- | --- |
| 帧解析 | SOF 错、长度错、超最大帧长 | 丢弃帧，不使用负载 |
| 完整性 | 单 bit、多 bit、截断、拼接 | 静默丢弃并记录本地 `BAD_CRC` 统计，不对不可信帧发送响应 |
| 字段边界 | 周期、静默时间、`stream_id`、通信模式或上报命令枚举越界 | 返回 `BAD_ARGUMENT`，保持原通信模式 |
| 会话 | 旧 `session_id`、重复的新 `session_id`、错误 `sensor_id`、旧 HELLO 响应、nonce/启动计数/会话计数不匹配，以及停用后重新探测时回放停用前会话号 | 帧无效，不使用数据，不建立会话；停用边界不清回放历史 |
| CPU2 启动身份 | SPI 命令/地址/数据阶段失败、保留区非 0xFF、双槽 CRC 均正确但较新 generation 携带相同或更小 `boot_counter` | 返回存储错误或记录冲突，禁止递增或发起 HELLO；单合法副本仍按冻结策略修复镜像 |
| 双向事务 | `seq` 错、`cmd` 错、重复请求、HELLO 后配置摘要不一致、副作用命令响应不确定 | 响应不匹配或幂等返回；摘要不一致不激活服务；副作用命令不跨新会话自动重放 |
| 周期上报 | 正常进入、连续上报、正常退出 | 切入上报，退出后继续双向通信 |
| 快报帧解析 | `frame_type` 错、固定长度错、`src_id` 或 `dst_id` 错 | 丢弃帧，不更新测量值 |
| 周期上报异常 | 丢帧、重复、回退、序号接近溢出、`sample_counter` 冻结、首次快报超时、后续静默超时、截止前短轮询超时、底层在截止点后返回成功帧、缺少 `STREAM_ACTIVE`、流丢失或缓冲溢出诊断、当前通道诊断 | 协商截止点到达时数据立即无效，迟到成功帧也不得采用；截止前短轮询超时保留当前流；连续性通过但状态/诊断无效的帧只刷新通信静默基准，不发布快照；其它流异常使流失效或在溢出前主动重新 HELLO；计数最大增量待 SRS 冻结后补测 |
| 本地年龄 | 延迟处理、任务阻塞、本地时钟回绕边界、`data_age_ms` 加法溢出 | 使用饱和运算得到 `effective_age_ms`，超限数据无效 |
| 控制窗口 | 46 字节退出请求、方向切换、最大调度抖动、时钟误差、临界窗口发送 | 9600 bps 下协商窗口不小于 100 ms，无碰撞且可确定退出 |
| UART6 传输软件 | 接收 DMA/发送顺序、控制帧和快报提取、噪声、非法长度前缀、合法长度但不完整的伪前缀、短帧超时、满缓冲、RX/TX 启动失败、中止、`PE/NE/FE/ORE/DMA/BREAK` | 主机 HAL 桩下先开接收再发送，只越过后方存在 CRC 正确完整帧的阻塞前缀，返回分类错误且所有异常出口释放 DMA/busy；真实 DE/RE 和 DMA 时序仍由台架验证 |
| 数据有效性 | `DATA_STALE`、`MODE_SETTLING`、低质量 | 不更新安全相关数据 |
| 单位倍率 | `scale_version` 变化、倍率表不一致、整数边界值换算 | 拒绝旧数据或按新倍率表正确换算 |
| 配置一致性 | 能力位变化、倍率变化、配置 CRC 变化、快报 `config_epoch` 变化 | 重新 `HELLO` 或拒绝使用数据 |
| 自检诊断 | 自检失败、电源异常、通道异常 | 对应诊断位和错误码置位 |
| 长稳 | 周期上报 24 小时以上，并记录总帧数和全部错误分母 | 无序号异常、无缓存溢出、无错误状态误报；结果只作为稳定性证据，不替代危险失效率论证 |

### 11.8 待认证前确认项

1. 目标安全功能和目标 SIL 等级。
2. 每个安全功能允许的最大数据年龄和最大响应时间。
3. 周期上报是否作为安全输入，还是只作为普通实时监测输入。
4. 无线链路是否纳入 IEC 62443 主动攻击威胁模型。
5. CRC32C 对最大帧长和目标危险失效率的充分性论证。
6. 传感器端是否能提供启动计数、采样计数、参数 CRC 和自检诊断。
7. 认证机构是否接受本协议按 black channel 自研安全通信层评估。
