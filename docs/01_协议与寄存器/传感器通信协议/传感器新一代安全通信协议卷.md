# 传感器新一代安全通信协议卷

更新日期：2026-07-03

本文是 CPU2 与传感器之间的新一代内部安全通信协议最终基线。CPU2 上层后续将按本协议重新适配；旧 DSM 一代文本协议和 LTD/V2 8 字节协议只作为业务对象参考，不继承旧帧格式、旧校验和旧异常模型。

正式认证时应以公司采购的受控标准文本为准。本文只做条款主题级映射，不复制 IEC、ISO 或其它受版权保护标准原文，也不声明本协议单独取得 SIL 认证。

### 1.2 本协议解决什么

- CPU2 与传感器之间的内部通信。
- 双向请求响应通信：CPU2 发起请求，传感器返回响应。
- 单向周期上报通信：CPU2 先用双向命令切入，传感器定时上报当前密度、温度、频率和诊断状态。
- 从单向上报切回双向通信：CPU2 发送退出命令，传感器确认后停止上报，双方继续使用同一会话做双向命令。
- 为 SIL 功能安全认证准备通信层证据，包括失效模式、防护措施、验证矩阵和标准映射。

### 1.3 本协议不解决什么

- 不定义 CPU2/CPU3 共享 Modbus 寄存器。
- 不定义 CPU3 外部 SI7000、Wartsila、DSM Modbus 协议。
- 不定义整机安全功能的目标 SIL 等级；目标 SIL 必须来自整机风险分析和 SRS。
- 不替代整机 SRS、硬件诊断、软件生命周期、网络安全威胁建模和认证机构评估。

### 1.4 最终协议基线一页规格

| 项 | 最终规则 |
| --- | --- |
| 帧格式 | 控制帧 `CTRL_FRAME` + 周期快报帧 `FAST_REPORT_FRAME` |
| 最大帧长 | 控制帧 `frame_len <= 128`；快报帧固定 44 字节 |
| 字节序 | 小端序 |
| 数值表示 | 固定宽度整数，物理小数用 `_x100`、`_x1000` 等倍率表达；倍率和单位由 `scale_version` 管理 |
| 完整性校验 | CRC32C Castagnoli；控制帧覆盖 `protocol_version` 到 `payload` 末尾，快报帧覆盖 `frame_type` 到 `fast_reserved` 末尾 |
| 会话 | `HELLO` 建立 `session_id`，后续双向响应和单向上报都携带 |
| 双向事务 | CPU2 同一时刻只保留一个未完成请求；传感器响应回显 `seq` 和 `cmd` |
| 周期上报 | 同一会话只允许一个 `stream_id` 激活；快报帧用 `stream_seq` 检测丢失、重复和乱序 |
| 数据新鲜度 | 每帧测量数据携带 `sample_counter` 和 `data_age_ms` |
| 配置一致性 | 控制帧携带 `safety_param_crc`，快报帧携带 `config_epoch`；倍率或单位变化后 CPU2 不得继续按旧规则解释数据 |
| 物理链路 | 面向约 200 米 RS485 半双工链路，实时性预算不得依赖高波特率 |
| 主动攻击边界 | 本基线面向受控内部链路；若存在无线、开放网络或非受控接入，必须在系统层增加 IEC 62443 认证/授权/完整性保护，不能只依赖 CRC |
| 参数写入 | 不在普通测量流程中自动写参数；参数修改必须进入维护流程 |

### 1.5 最终命令边界

本协议一次性定义最终基线，不再规划阶段版本。为降低传感器实现复杂度，最终基线只保留认证和运行必须的命令，调试抓取、独立状态上报、链路控制保留命令不进入安全通信基线。

| 类别 | 命令 | 说明 |
| --- | --- | --- |
| 基础链路 | `HELLO`、`PING`、`GET_STATUS`、`GET_CONFIG_DIGEST`、`RESET_SESSION` | 建立会话、确认链路、读取诊断、确认配置一致性和恢复会话 |
| 双向测量 | `SET_MEASURE_MODE`、`READ_MEAS_COMBO`、`READ_LEVEL_FREQ`、`READ_WATER_CAP`、`READ_GYRO`、`READ_POWER` | 覆盖当前需要保留的传感器业务对象 |
| 单向上报 | `SET_COMM_MODE`、`REPORT_MEAS_FAST` | 受控进入周期上报，退出后继续双向通信 |
| 参数维护 | `READ_PARAM`、`WRITE_PARAM`、`COMMIT_PARAM` | 参数读写必须走维护流程 |
| 自检维护 | `RUN_SELF_TEST`、`READ_SELF_TEST_RESULT` | 用于认证证据、开机/维护自检和诊断追踪 |

最终命令边界仍必须保留通用帧头、CRC32C、会话号、事务号、数据年龄、采样计数、状态位和诊断位。可以不实现旧协议中的调试抓取类能力，但不能删除这些安全通信防护字段。

### 1.6 旧协议参考结论

旧协议只作为业务对象输入，不作为新协议的通信机制基础。

| 来源 | 可参考内容 | 不继承内容 |
| --- | --- | --- |
| DSM 一代文本协议 | 密度模式、液位模式、传感器 ID、版本、电压、密度/温度/频率组合、水位电容、姿态角 | ASCII 命令、换行结束、BCC、文本解析 |
| LTD/V2 8 字节协议 | 软件版本、存储版本、传感器状态、电压、液位频率、温度、密度、动力粘度、运动粘度、45 度/22.5 度参考频率、参数读写 | 8 字节固定帧、低 8 bit 累加和、单参数多次读取、`0xFF` 粗粒度失败 |

设计结论：

- 新协议保留业务对象，不保留旧帧格式。
- 温度、密度、频率应优先使用同一采样快照；双向读取使用完整组合结构，9600 bps 周期上报使用紧凑结构。
- 所有测量值采用整数倍率，不直接传 float。
- 每帧带状态、诊断、数据年龄和采样计数。
- 周期上报必须受 CPU2 控制，不能由传感器任意异步输出。

## 2. 术语和字段命名

### 2.1 术语解释

| 术语 | 在本文中的含义 | 为什么重要 |
| --- | --- | --- |
| SIL | Safety Integrity Level，安全完整性等级。本文只为 SIL 认证准备通信层证据，不单独声明协议已经取得 SIL 认证 | 避免把“按 SIL 思路设计”和“已经通过 SIL 认证”混为一谈 |
| 安全功能 | 设备为了避免危险状态而必须正确执行的功能，例如使用有效密度、温度或液位数据参与控制 | 协议只服务于安全功能，最终 SIL 等级还取决于整机安全需求、硬件、软件和验证证据 |
| SRS | Safety Requirements Specification，安全需求规格 | SIL 评估需要从安全需求追溯到设计、实现和测试 |
| E/E/PE | Electrical/Electronic/Programmable Electronic，电气/电子/可编程电子系统 | IEC 61508 用该术语描述由硬件和软件组成的安全相关系统 |
| black channel | 黑通道。把 UART、无线、滑环、DMA 或中间转发链路都当作不可信传输，只假设它能搬运字节，不假设它可靠或安全 | 本协议必须在自身层面处理损坏、丢失、重复、乱序、延迟和错设备等问题 |
| 安全通信层 | 位于业务数据和底层传输之间的协议防护层，包括地址、长度、序号、会话、CRC、超时和状态检查 | 即使底层链路不是安全总线，也能给安全相关数据增加可验证的防护 |
| 帧 | 一次完整传输单元，从 `sof0` 开始，到 `safety_crc` 结束 | 接收端必须先确认一整帧合法，才能使用负载数据 |
| 负载 | `payload` 字段中的命令数据或测量数据 | 不同命令使用不同负载结构，通用帧头保持一致 |
| SOF | Start Of Frame，帧起始标记。本文使用 `sof0=0xA5`、`sof1=0x5A` | 用来在连续字节流中找到帧边界 |
| CRC32C | Castagnoli 多项式的 32 bit CRC | 用于检测传输损坏、截断和拼接错误；CRC 不是认证码，不能防主动伪造 |
| 认证码 | 用密钥生成的完整性校验值，例如 MAC 或签名类机制 | 当存在主动攻击、无线接入或非受控接入风险时，仅靠 CRC 不够 |
| 小端序 | 多字节整数低字节先传输 | CPU2 和传感器必须按同一字节序解释字段 |
| 整数倍率 | 用整数承载小数，例如 `temperature_c_x100=2534` 表示 25.34 degC | 避免 float 字节序、NaN、编译器差异和跨平台解释不一致 |
| `session_id` | 会话号。一次 `HELLO` 握手后生成，后续双向通信和单向上报都携带 | 防止上电前旧帧、旧响应或旧上报被当成当前数据 |
| `seq` | 双向请求响应事务号，由 CPU2 在请求中递增，响应必须带回同一值 | 防止响应错配、重复响应和乱序响应 |
| `stream_id` | 单向周期上报流 ID，由 CPU2 启动上报时分配 | 退出上报后，旧 `stream_id` 的帧必须失效，避免旧流继续被使用 |
| `stream_seq` | 单向周期上报序号，每条上报递增 | 用于发现周期上报丢帧、重复或乱序 |
| `sample_counter` | 传感器采样计数，同一采样周期的组合数据使用同一计数 | 用于判断温度、密度、频率是否来自同一次采样 |
| `data_age_ms` | 数据年龄，表示该负载中的测量值距离实际采样已经过去多少毫秒 | 用于防止旧数据、缓存数据或冻结数据被当成实时数据 |
| `safety_param_crc` | 安全参数集 CRC，覆盖影响数据解释的能力、倍率、标定版本和关键配置 | 防止 CPU2 按旧倍率或旧标定解释新数据 |
| `capability_flags` | 能力位，表示传感器支持哪些协议能力 | CPU2 按能力启用功能，不能靠猜测使用未声明字段 |
| `status_flags` | 状态位，表示本帧数据是否有效、是否稳定、模式是否匹配等 | CPU2 必须先看状态位，再决定数据是否能参与控制 |
| `diag_flags` | 诊断位，表示传感器检测到的硬件、算法、配置或通信异常 | 用于故障定位、报警和诊断覆盖率统计 |
| golden frame | 已知输入、已知输出的标准测试帧 | 用于确认 CPU2 和传感器对字节序、长度、CRC、字段倍率的理解完全一致 |
| HIL | Hardware In the Loop，硬件在环测试 | 用真实硬件或半实物环境验证协议在异常链路和真实时序下的行为 |
| 故障注入 | 人为制造 CRC 错、丢帧、重复、乱序、延迟、错误地址等异常 | 用于证明协议能检测并处理通信失效 |

### 2.2 字段命名读法

| 命名形式 | 例子 | 读法 |
| --- | --- | --- |
| `_x100`、`_x1000` | `temperature_c_x100`、`frequency_hz_x1000` | 字段值是物理量乘以 100 或 1000 后的整数 |
| `_crc` | `safety_param_crc`、`param_crc` | CRC 校验值，不是加密认证码 |
| `_flags` | `status_flags`、`diag_flags` | 位图字段，每一 bit 表示一个独立状态 |
| `_id` | `session_id`、`stream_id`、`sensor_id` | 标识符，用于绑定会话、上报流或设备 |
| `_seq` | `seq`、`stream_seq` | 序号，用于检测重复、丢失和乱序 |

线上数据不得使用 float、double 或字符串表达工程值。所有小数物理量必须先按字段名或单位倍率表放大为整数，接收端通过 `scale_version`、字段命名和本协议表格还原工程单位。

## 3. SIL 依据和设计理由

### 3.1 标准映射口径

正式认证时应复核精确条款号、标准版本、修订件和认证机构解释。本文采用条款主题级映射，用于协议规划和内部评审。

| 标准 | 采用章节/主题 | 对协议的要求 | 本协议对应设计 |
| --- | --- | --- | --- |
| IEC 61508-1:2010 | 第 7 章整体安全生命周期；安全需求、验证确认、修改和配置管理相关主题 | 安全相关通信必须能追溯到安全需求、验证计划和配置管理 | 定义协议版本、能力位、配置 CRC、验证矩阵、golden frame、残余风险 |
| IEC 61508-2:2010 | 第 7 章 E/E/PE 安全相关系统实现；诊断、故障检测、安全状态相关主题 | 通信链路失效不能直接导致未检测危险输出，必须有诊断和故障反应 | CRC、超时、序号、会话、数据年龄、诊断位、错误码、安全状态策略 |
| IEC 61508-3:2010 | 第 7 章软件安全生命周期；软件安全需求、架构设计、模块设计、验证相关主题 | 软件实现必须有明确需求、接口、异常处理和验证证据 | 分层架构、命令表、负载表、状态机、错误码、单元/集成/故障注入测试 |
| IEC 61784-3:2021+AMD1:2024 | 功能安全现场总线、black channel、安全通信 profile 相关主题 | 底层传输可视为不可信，安全性由安全通信层提供 | 将 UART/无线/滑环视为 black channel；在协议层实现源/目的、序号、CRC、时间约束 |

### 3.2 总体设计原则

| 原则 | 为什么这样设计 | 标准映射 |
| --- | --- | --- |
| black channel | UART、无线透传、滑环和 DMA 都可能损坏、延迟、重复或丢失数据，不能信任底层链路 | IEC 61784-3 安全通信 profile/black channel；IEC 62280 不可信传输系统 |
| 二进制固定头 + 可变负载 | 比文本协议更容易做边界检查、长度检查、版本兼容和自动化测试 | IEC 61508-3 软件架构和接口可验证性 |
| CRC32C 覆盖关键字段和负载 | 当前累加和/BCC 不足以覆盖安全相关数据完整性要求 | IEC 61508-2 诊断；IEC 62280 数据损坏防护 |
| 会话号 + 事务号 | 防止旧响应、重复响应、跨命令响应和上电前旧帧被误用 | IEC 62280 重复、乱序、延迟和重放类防护 |
| 源/目的/传感器 ID 绑定 | 防止串线、错设备响应、错误节点伪装成传感器 | IEC 62280 伪装和地址错误防护 |
| 数据年龄 + 采样计数 | 防止旧数据、冻结数据和缓存数据被当成实时安全输入 | IEC 61508-2 诊断覆盖；IEC 62280 延迟防护 |
| 整数倍率 | 避免 float 字节序、NaN、编译器差异和跨平台解释不一致 | IEC 61508-3 明确接口和数据表示 |
| 组合读数 | 温度、密度、频率来自同一采样周期，减少跨采样不一致 | IEC 61508-3 数据一致性和接口需求 |
| 单向上报受控进入/退出 | 周期上报提高实时性，但必须防止误触发、无法退出和旧流继续生效 | IEC 61508-2 安全状态；IEC 62280 插入、重复和延迟防护 |
| 配置 CRC | 能力、倍率、标定版本变化时，CPU2 不能继续按旧解释使用数据 | IEC 61508-1 配置管理；IEC 61508-3 需求和接口一致性 |

### 3.3 传感器端复杂度控制

SIL 相关设计不是把协议做得越复杂越好，而是让风险防护、实现难度和验证证据保持平衡。传感器程序资源通常更紧，最终基线按以下边界设计：

| 约束 | 最终规则 | 设计理由 |
| --- | --- | --- |
| 帧大小 | 控制帧 `frame_len <= 128`，快报帧固定 44 字节 | 传感器可使用固定收发缓冲区，便于做边界检查和资源评估 |
| 分片 | 不支持分片和重组 | 避免传感器维护复杂重组状态，所有业务数据必须放入单帧 |
| 并发请求 | 不支持流水线请求；CPU2 等待响应或超时后再发下一条请求 | 传感器只需保存当前事务或最近一次可重发响应 |
| 周期上报流 | 同一会话只允许一个 `stream_id` 激活 | 传感器不用维护多流调度，CPU2 也更容易判断静默和丢帧 |
| 上报缓存 | 推荐只保留最新一帧，不累计历史队列 | 安全判断依赖新鲜数据，历史队列反而增加延迟风险 |
| 负载格式 | 不使用嵌套 TLV、字符串和可变长度数组 | 降低解析分支，减少长度错误和内存越界风险 |
| 字节序和类型 | 全部使用小端整数和固定宽度类型 | C 端实现直接、可测，避免 float 和编译器差异 |
| 参数写入 | 测量流程中不自动写参数，参数写入必须走维护流程 | 防止普通通信抖动影响安全相关配置 |
| 认证码 | 不放入本安全通信基线 | 当前目标是内部受控链路的功能安全通信；主动攻击场景由系统安全通道覆盖，避免传感器端引入密钥生命周期复杂度 |
| 错误恢复 | 传感器只做本地状态回退和错误响应，复杂恢复策略由 CPU2 决策 | CPU2 资源更充足，也更接近整机安全状态控制 |

## 4. 通信模型

### 4.0 物理链路前提

本协议面向传感器到设备约 200 米 RS485 半双工链路，当前项目波特率为 9600 bps。该链路必须按长线低速场景设计，不能假设 19200 bps、38400 bps 或 115200 bps 长期可靠。

| 项 | 规则 |
| --- | --- |
| 项目设计基线 | 9600 bps |
| 可选较高速率 | 19200 或 38400 bps，需经过现场线缆、终端电阻、偏置、电磁环境和误码测试确认 |
| 不作为默认基线 | 19200 bps 及以上，除非硬件和现场验证证明可靠 |
| 通信方式 | 半双工，同一时刻只有一端发送 |
| 周期上报下行窗口 | 传感器必须在上报周期内预留接收窗口，避免 CPU2 无法退出上报 |

设计含义：协议必须优先减少周期上报帧长度和交互次数。低速长线下，实时性主要由字节数、波特率、半双工方向切换、静默间隔和异常重试决定，而不是由 MCU 编码解码时间决定。

### 4.1 节点角色

| 节点 | 角色 | 默认 ID |
| --- | --- | --- |
| CPU2 | 主控、会话发起方、双向命令发起方、周期上报控制方 | `0x01` |
| 传感器 | 从设备、测量数据提供方、周期上报发送方 | `0x10` |

### 4.2 传输模式

| 值 | 名称 | 说明 |
| --- | --- | --- |
| `0x00` | `REQUEST_RESPONSE` | 双向请求响应模式；CPU2 发请求，传感器响应 |
| `0x01` | `PERIODIC_UPLINK` | 单向周期上报模式；传感器按周期向 CPU2 发送测量报告 |

传输模式和测量模式必须分开：传输模式解决数据如何传输，测量模式解决传感器当前采什么。单向上报不是新的测量对象，它只是密度等测量数据的传输方式。

### 4.3 测量模式

| 值 | 名称 | 说明 |
| --- | --- | --- |
| `0x00` | `IDLE` | 待机 |
| `0x01` | `DENSITY` | 密度测量模式 |
| `0x02` | `LEVEL` | 液位频率模式 |
| `0x03` | `WATER_CAP` | 水位电容模式 |
| `0x04` | `GYRO` | 姿态角模式 |
| `0x05` | `BOTTOM` | 罐底/底部检测模式 |
| `0x7E` | `SELF_TEST` | 自检中 |
| `0x7F` | `FAULT` | 故障状态 |

### 4.4 会话、事务和上报流

| 对象 | 规则 |
| --- | --- |
| 会话 | CPU2 上电或链路恢复后发送 `HELLO`，`session_id=0`；传感器响应新 `session_id`；后续所有双向命令和周期上报帧均携带该 `session_id` |
| 会话生成 | `session_id` 应在传感器每次冷启动或 CPU2 重新握手时变化；若无硬件随机数，可由传感器启动计数、传感器 ID、CPU2 握手序号和固定盐值混合生成 |
| 双向事务 | CPU2 每发起一个新双向请求，`seq` 加 1；传感器响应必须回显请求 `seq` 和 `cmd` |
| 请求重试 | CPU2 重试同一请求时，可使用同一 `seq` 并置 `RETRY_FRAME` |
| 幂等保护 | 传感器收到重复的无副作用请求，可返回缓存响应；对 `SET_MEASURE_MODE`、`SET_COMM_MODE`、`WRITE_PARAM` 等有副作用命令，必须用 `seq` 做幂等保护 |
| 周期上报 | 周期上报负载必须携带独立的 `stream_id` 和 `stream_seq`，不用普通请求 `seq` 表示上报顺序 |

周期上报快报帧关键字段如下。完整双向响应仍使用通用前缀中的 u32 `sample_counter`；周期快报为压缩帧，只传输低 16 bit，并按模 65536 判断连续性。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `stream_id` | u16 | CPU2 启动周期上报时分配 |
| `stream_seq` | u16 | 传感器每发一帧递增，从 1 开始，按模 65536 判断 |
| `sample_counter` | u16 | 传感器采样计数低 16 bit，按模 65536 判断 |
| `data_age_ms` | u16 | 数据从采样到发送的年龄 |

## 5. 帧格式和接收校验

所有多字节字段采用小端序。保留字段发送 0，接收端不得依赖保留字段做业务判断。最终协议使用两类固定帧：控制帧用于双向命令、参数、自检和完整读取；快报帧用于 9600 bps 周期上报。两类帧都必须通过 CRC32C、会话、地址或流标识、序号、数据年龄和状态诊断校验后才能使用。

### 5.1 控制帧 `CTRL_FRAME`

控制帧用于 `REQ`、`RSP` 和 `ERR`，承载会话建立、模式切换、双向读数、参数维护和自检维护。控制帧不用于周期测量上报。

| 偏移 | 字段 | 长度 | 类型 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | `sof0` | 1 | u8 | 固定 `0xA5` |
| 1 | `sof1` | 1 | u8 | 固定 `0x5A` |
| 2 | `protocol_version` | 1 | u8 | 最终基线 `0x01` |
| 3 | `header_len` | 1 | u8 | 最终基线 `28` |
| 4 | `frame_len` | 2 | u16 | 从 `sof0` 到 CRC 末尾的总长度 |
| 6 | `src_id` | 1 | u8 | 源节点 ID |
| 7 | `dst_id` | 1 | u8 | 目的节点 ID |
| 8 | `msg_type` | 1 | u8 | 消息类型 |
| 9 | `cmd` | 1 | u8 | 命令号 |
| 10 | `flags` | 2 | u16 | 协议标志 |
| 12 | `seq` | 2 | u16 | 双向请求响应事务号 |
| 14 | `session_id` | 4 | u32 | 会话号 |
| 18 | `sensor_id` | 4 | u32 | 传感器数字 ID；未知时为 0 |
| 22 | `safety_param_crc` | 4 | u32 | 安全参数集 CRC |
| 26 | `header_reserved` | 2 | u16 | 保留 |
| 28 | `payload` | N | bytes | 负载 |
| 28 + N | `safety_crc` | 4 | u32 | CRC32C |

`payload_len = frame_len - header_len - 4`。控制帧最大 `frame_len <= 128`。

### 5.2 周期快报帧 `FAST_REPORT_FRAME`

快报帧用于 `REPORT_MEAS_FAST`，固定 44 字节，不带 `header_len`、`sensor_id`、`safety_param_crc`、通用响应前缀或可变负载。`sensor_id` 和 `safety_param_crc` 在 `HELLO`、`GET_CONFIG_DIGEST` 和 `SET_COMM_MODE` 阶段由控制帧确认；若配置变化，传感器必须停止当前上报流或置诊断，CPU2 不得继续使用旧流数据。

| 偏移 | 字段 | 长度 | 类型 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | `sof0` | 1 | u8 | 固定 `0xA5` |
| 1 | `sof1` | 1 | u8 | 固定 `0x5A` |
| 2 | `frame_type` | 1 | u8 | 固定 `0xA1`，表示 `FAST_REPORT_FRAME` |
| 3 | `frame_len` | 1 | u8 | 固定 `44` |
| 4 | `src_id` | 1 | u8 | 源节点 ID |
| 5 | `dst_id` | 1 | u8 | 目的节点 ID |
| 6 | `stream_state` | 1 | u8 | 高 4 bit 测量模式，低 4 bit 通信/上报状态 |
| 7 | `session_id` | 4 | u32 | 会话号 |
| 11 | `stream_id` | 2 | u16 | 当前上报流 ID |
| 13 | `stream_seq` | 2 | u16 | 周期上报序号，回绕后继续递增判定 |
| 15 | `sample_counter` | 2 | u16 | 采样计数低 16 bit，回绕规则同 `stream_seq` |
| 17 | `data_age_ms` | 2 | u16 | 数据年龄 |
| 19 | `status_flags16` | 2 | u16 | 快报状态位，映射第 6.3 节低 16 bit |
| 21 | `diag_flags16` | 2 | u16 | 快报诊断位，映射第 6.3 节低 16 bit |
| 23 | `temperature_c_x100` | 2 | i16 | 温度 |
| 25 | `density_kg_m3_x100` | 4 | i32 | 密度 |
| 29 | `frequency_hz_x1000` | 4 | u32 | 主频率 |
| 33 | `signal_quality` | 1 | u8 | 0..100 |
| 34 | `config_epoch` | 1 | u8 | 配置纪元，`safety_param_crc` 变化时递增 |
| 35 | `fast_reserved` | 5 | bytes | 保留，发送 0，接收忽略 |
| 40 | `safety_crc` | 4 | u32 | CRC32C |

快报帧压缩的是编码宽度，不压缩安全语义。`stream_seq`、`sample_counter` 使用 u16 时，CPU2 必须按模 65536 判断连续性，不能简单用有符号差值。`config_epoch` 是 `safety_param_crc` 的快报映射：CPU2 在进入上报前记录当前 `safety_param_crc` 和 `config_epoch`，快报中 `config_epoch` 不一致时必须丢弃数据并重新查询配置。快报帧字段不按 C 结构体自然对齐设计，收发双方必须按字节偏移逐字段编码和解码，不得直接将串口缓冲区强制转换为结构体。

### 5.3 CRC32C

| 项 | 值 |
| --- | --- |
| 算法 | CRC32C Castagnoli |
| 正向多项式 | `0x1EDC6F41` |
| 反射实现多项式 | `0x82F63B78` |
| 初值 | `0xFFFFFFFF` |
| 结果异或 | `0xFFFFFFFF` |
| 控制帧计算范围 | 从 `protocol_version` 到 `payload` 末尾，不含 SOF，不含 `safety_crc` |
| 快报帧计算范围 | 从 `frame_type` 到 `fast_reserved` 末尾，不含 SOF，不含 `safety_crc` |
| 输出字节序 | 小端 |

CRC32C 用于检测损坏、截断和拼接错误。CRC 不是认证码，若威胁模型包含主动攻击，还需要认证机制。

### 5.4 消息类型和标志位

消息类型：

下列 `msg_type` 只用于控制帧。快报帧使用固定 `frame_type=0xA1`，不再携带 `msg_type` 字段。

| 值 | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| `0x01` | `REQ` | CPU2 -> 传感器 | 请求 |
| `0x81` | `RSP` | 传感器 -> CPU2 | 正常响应 |
| `0xC1` | `ERR` | 传感器 -> CPU2 | 错误响应 |
| `0xA0` | 保留 | 无 | 不用于基线周期上报；周期上报统一使用 `FAST_REPORT_FRAME(frame_type=0xA1)` |

标志位：

| bit | 名称 | 含义 |
| --- | --- | --- |
| 0 | `ACK_REQUIRED` | 请求要求响应 |
| 1 | `SAFETY_RELEVANT` | 帧承载安全相关数据或诊断 |
| 2 | `RETRY_FRAME` | 重发帧 |
| 3 | `CONFIG_CHANGED` | 配置变化，需要重新握手 |
| 4 | `COLD_START` | 节点冷启动或会话重建 |
| 5 | `ERROR_PRESENT` | 存在错误或诊断异常 |
| 6 | 保留 | 发送 0，接收忽略 |
| 7 | `STOP_STREAM_REQUEST` | 请求停止周期上报 |
| 8 | `PARAM_WRITE` | 参数写入相关帧 |
| 9..15 | 保留 | 发送 0 |

### 5.5 接收端最小校验顺序

传感器接收控制帧请求时按下列顺序处理：

1. 找到 `SOF`。
2. 检查 `frame_len` 是否在范围内。
3. 收满一帧后计算 CRC32C。
4. 检查 `dst_id`、`protocol_version`、`header_len`。
5. 除 `HELLO` 外，检查 `session_id` 和 `safety_param_crc`。
6. 检查 `cmd` 是否支持、负载长度是否匹配。
7. 执行业务处理并生成响应。
8. 任一步失败时，不得使用负载中的测量值或参数值。

CPU2 使用控制帧响应中的测量数据前必须满足：

1. SOF、长度和最大帧长合法。
2. CRC32C 正确。
3. `src_id`、`dst_id`、`sensor_id` 匹配。
4. `session_id` 匹配当前会话。
5. 双向响应的 `seq` 和 `cmd` 匹配当前请求。
6. `safety_param_crc` 与握手时一致。
7. `result_code == OK`。
8. `DATA_VALID == 1`。
9. `DATA_STALE == 0`。
10. `MODE_MATCH == 1`。
11. `data_age_ms` 未超过当前安全功能允许值。
12. 数据物理范围、变化率和诊断位满足上层业务规则。

CPU2 使用快报帧测量数据前必须满足：

1. SOF、固定长度 44 和 `frame_type=0xA1` 合法。
2. CRC32C 正确。
3. `src_id` 和 `dst_id` 与当前 CPU2 和传感器节点匹配。
4. `session_id` 匹配当前会话。
5. `stream_id` 匹配当前上报流。
6. `stream_seq` 按模 65536 单调递增。
7. `sample_counter` 未长期冻结，按模 65536 判断。
8. `config_epoch` 与进入上报时记录值一致。
9. `DATA_VALID == 1`。
10. `DATA_STALE == 0`。
11. 快报状态中的测量模式和通信状态符合 CPU2 期望。
12. `data_age_ms` 未超过当前安全功能允许值。
13. 数据物理范围、变化率和诊断位满足上层业务规则。

任一条件失败，数据不得作为安全相关输入使用。可以保留显示缓存，但必须标识为过期或无效。

### 6.5 数值表示和倍率版本

通信层只传固定宽度整数，不传 float、double、ASCII 数字或带单位字符串。CPU2 应用层负责把整数换算成工程值。

| 场景 | 规则 |
| --- | --- |
| 快报帧 | 使用本卷固定倍率，必须保持短帧稳定；倍率变化必须更新 `scale_version`、`safety_param_crc` 和 `config_epoch` |
| 完整测量读取 | 使用字段名固定倍率和 `payload_version`，新增字段优先通过新的 `payload_version` 管理 |
| 参数读写 | 使用 `param_type`、`scale`、`unit_id` 和 `param_crc` 描述参数值 |
| 单位或倍率变化 | 必须改变 `scale_version`，并纳入 `safety_param_crc` 计算 |
| CPU2 解释数据 | 必须先确认 `safety_param_crc` 或 `config_epoch` 一致，再按对应倍率表换算 |

最终基线单位倍率表：

| 字段 | 线上类型 | 工程单位 | 倍率 | 示例 |
| --- | --- | --- | --- | --- |
| `temperature_c_x100` | i16 或 i32 | degC | x100 | `2534` 表示 25.34 degC |
| `density_kg_m3_x100` | i32 | kg/m3 | x100 | `99876` 表示 998.76 kg/m3 |
| `frequency_hz_x1000` | u32 | Hz | x1000 | `123456789` 表示 123456.789 Hz |
| `freq_45_hz_x1000` | u32 | Hz | x1000 | 45 度参考频率 |
| `freq_225_hz_x1000` | u32 | Hz | x1000 | 22.5 度参考频率 |
| `level_frequency_hz_x1000` | u32 | Hz | x1000 | 液位频率 |
| `capacitance_pf_x10` | i32 | pF | x10 | 水位电容 |
| `angle_x_deg_x100` | i32 | deg | x100 | 姿态角 |
| `angle_y_deg_x100` | i32 | deg | x100 | 姿态角 |
| `voltage_mv` | u32 | mV | x1 | 供电电压 |
| `data_age_ms` | u16 | ms | x1 | 数据年龄 |
| `signal_quality` | u8 或 u16 | percent or per-mille | 快报 0..100，完整帧 0..1000 | 信号质量 |

`scale_version` 是单位倍率表版本，不是软件版本。只要任何安全相关字段的单位、倍率、范围或解释方式变化，就必须更新 `scale_version`，并使 `safety_param_crc` 变化。快报帧中的 `config_epoch` 必须跟随该变化，使旧快报流失效。

`WRITE_PARAM` 响应：

| 字段 | 类型 | 说明 |

## 7. 单向周期上报专项规则

周期上报不是无条件可信的广播数据。CPU2 必须维护上报流状态。

| 项 | 约束 |
| --- | --- |
| 启动 | 必须由 `SET_COMM_MODE(PERIODIC_UPLINK)` 启动，并得到 ACK |
| 上报内容 | 固定上报 `REPORT_MEAS_FAST` |
| 上报周期 | 由 CPU2 请求，传感器可返回实际采用值 |
| 最大静默 | 超过 `max_silent_ms` 无有效帧，判定上报中断 |
| 序号 | `stream_seq` 重复、回退或异常跳变不得使用 |
| 数据冻结 | `sample_counter` 长期不变不得使用 |
| 退出 | 必须由 CPU2 发 `SET_COMM_MODE(REQUEST_RESPONSE)` 并得到 ACK |
| 退出失败 | 连续 3 次退出失败后会话失效，停止使用上报数据 |
| 双向恢复 | 退出成功后同一 `session_id` 继续普通双向通信 |

长线 RS485 下，上报帧不得夹带参数表、自检结果、原始调试量或可由双向维护命令读取的数据。周期上报只传安全判断和实时显示必需字段，避免低波特率下总线占用过高。

### 7.1 进入周期上报

1. CPU2 发送 `SET_COMM_MODE(PERIODIC_UPLINK)`。
2. 传感器返回 `RSP`，确认周期、静默时间和 `stream_id`。
3. CPU2 转入接收上报状态。
4. 传感器在 `start_after_ms` 后发送 `REPORT_MEAS_FAST`。

### 7.2 退出周期上报

1. CPU2 在上报期间发送 `SET_COMM_MODE(REQUEST_RESPONSE)`。
2. 传感器在 `control_guard_ms` 窗口内接收该命令。
3. 传感器停止发送 `REPORT_MEAS_FAST`。
4. 传感器返回 `RSP`，确认已回到 `REQUEST_RESPONSE`。
5. CPU2 继续使用同一 `session_id` 发送普通双向命令。

正常退出不重新 `HELLO`，因为会话没有失效；`stream_id` 失效即可阻断旧上报流。若退出失败，才判定会话失效并重新 `HELLO`。

### 7.3 上报期间允许的下行控制

传感器在周期上报期间必须保留接收窗口。每个上报周期内必须预留 `control_guard_ms`，用于接收 CPU2 的退出命令、状态查询或紧急停止上报命令。周期上报期间只允许：

- `SET_COMM_MODE(REQUEST_RESPONSE)`。
- `PING`。
- `RESET_SESSION`。

其它命令需要先退出上报。

## 8. 通信流程示例

本节采用字段级写法，用于说明通信顺序和接收侧判断，不是可直接发送的十六进制帧。实际实现和 golden frame 必须按第 5 章编码 `frame_len`、小端字节序和 `safety_crc`。

示例公共条件：

| 项 | 示例值 | 说明 |
| --- | --- | --- |
| CPU2 节点 ID | `0x01` | 请求发起方 |
| 传感器节点 ID | `0x10` | 响应和上报发送方 |
| `sensor_id` | `0x12345678` | 示例传感器 ID |
| `selected_protocol` | `0x01` | 最终基线协议 |
| `safety_param_crc` | `0x89ABCDEF` | 示例安全参数集 CRC |
| `session_id` | `0x23070301` | `HELLO` 后建立的示例会话号 |

### 8.1 上电握手

1. CPU2 发送 `HELLO` 请求。

   | 类别 | 关键字段 |
   | --- | --- |
   | 帧头 | `src_id=0x01`，`dst_id=0x10`，`msg_type=REQ`，`cmd=HELLO`，`flags=ACK_REQUIRED`，`seq=1`，`session_id=0`，`sensor_id=0`，`safety_param_crc=0` |
   | 负载 | `cpu_protocol_min=1`，`cpu_protocol_max=1`，`cpu_node_id=0x01`，`cpu_boot_counter=25`，`cpu_nonce=0x6A135724` |

2. 传感器校验 `SOF`、长度、CRC、地址和协议版本后，返回 `HELLO` 响应。

   | 类别 | 关键字段 |
   | --- | --- |
   | 帧头 | `src_id=0x10`，`dst_id=0x01`，`msg_type=RSP`，`cmd=HELLO`，`seq=1`，`session_id=0x23070301`，`sensor_id=0x12345678`，`safety_param_crc=0x89ABCDEF` |
   | 通用前缀 | `result_code=OK`，`measure_mode=IDLE`，`comm_mode=REQUEST_RESPONSE`，`status_flags=0`，`diag_flags=0`，`sample_counter=0`，`data_age_ms=0`，`payload_version=1`，`data_quality=100` |
   | 追加负载 | `selected_protocol=1`，`sensor_node_id=0x10`，`sensor_sw_version=<传感器版本>`，`sensor_boot_counter=<启动计数>`，`new_session_id=0x23070301`，`capability_flags=CAP_DENSITY + CAP_MEAS_COMBO + CAP_PERIODIC_UPLINK + CAP_POWER` |

3. CPU2 保存 `session_id`、`sensor_id`、`capability_flags`、`scale_version` 和 `safety_param_crc`。后续控制帧必须带同一组值；快报帧必须带与该配置绑定的 `config_epoch`，直到重新 `HELLO` 或重新进入上报。

传感器端实现要点：`HELLO` 是唯一允许 `session_id=0` 的正常业务命令；其它命令在未建会话时返回 `BAD_SESSION` 或直接拒绝。

### 8.2 双向读取密度组合数据

1. CPU2 切换到密度测量模式。

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=SET_MEASURE_MODE`，`seq=2`，`session_id=0x23070301`，`safety_param_crc=0x89ABCDEF` |
   | 请求负载 | `target_mode=DENSITY`，`mode_option=0` |
   | 响应负载 | `result_code=OK`，`accepted_mode=DENSITY`，`settle_time_ms=800`，`mode_counter=1` |

2. 在 `settle_time_ms` 到达前，传感器可返回 `MODE_SETTLING`，CPU2 不使用测量值参与安全判断。

3. CPU2 发送组合读取。

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=READ_MEAS_COMBO`，`seq=3`，`session_id=0x23070301` |
   | 请求负载 | `read_mask=0`，表示读取默认组合 |
   | 响应通用前缀 | `result_code=OK`，`measure_mode=DENSITY`，`comm_mode=REQUEST_RESPONSE`，`status_flags=DATA_VALID + MODE_MATCH`，`diag_flags=0`，`sample_counter=1024`，`data_age_ms=30`，`payload_version=1`，`data_quality=98` |
   | 响应测量值 | `temperature_c_x100=2534`，`density_kg_m3_x100=99876`，`frequency_hz_x1000=123456789`，`signal_quality=930` |

4. CPU2 接收后按固定顺序判断：CRC 正确、地址正确、`session_id` 匹配、`seq=3` 匹配、`cmd=READ_MEAS_COMBO` 匹配、`safety_param_crc` 匹配、`DATA_VALID` 和 `MODE_MATCH` 置位、`DATA_STALE` 未置位、`data_age_ms` 未超过 SRS 限值。

传感器端实现要点：组合响应应先从测量任务复制一份快照，再编码响应，避免温度、密度和频率来自不同采样周期。

### 8.3 切入单向周期上报

1. CPU2 使用双向命令启动周期上报。

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=SET_COMM_MODE`，`seq=4`，`session_id=0x23070301`，`flags=ACK_REQUIRED + SAFETY_RELEVANT` |
   | 请求负载 | `target_comm_mode=PERIODIC_UPLINK`，`report_cmd=REPORT_MEAS_FAST`，`reserved0=0`，`period_ms=1000`，`max_silent_ms=3000`，`stream_id=0x1201`，`control_guard_ms=50` |

2. 传感器确认进入上报模式。

   | 类别 | 关键字段 |
   | --- | --- |
   | 响应帧头 | `msg_type=RSP`，`cmd=SET_COMM_MODE`，`seq=4`，`session_id=0x23070301` |
   | 响应负载 | `result_code=OK`，`comm_mode=PERIODIC_UPLINK`，`status_flags=DATA_VALID + MODE_MATCH + STREAM_ACTIVE`，`accepted_comm_mode=PERIODIC_UPLINK`，`accepted_report_cmd=REPORT_MEAS_FAST`，`accepted_period_ms=1000`，`accepted_max_silent_ms=3000`，`accepted_stream_id=0x1201`，`start_after_ms=100` |

3. 传感器在 `start_after_ms` 后开始发送 `REPORT_MEAS_FAST`。该上报使用固定 44 字节 `FAST_REPORT_FRAME`，不使用控制帧头和通用响应前缀。

   | 上报帧 | 关键字段 |
   | --- | --- |
   | 第 1 帧 | `frame_type=0xA1`，`frame_len=44`，`src_id=0x10`，`dst_id=0x01`，`stream_state=<DENSITY+PERIODIC>`，`session_id=0x23070301`，`stream_id=0x1201`，`stream_seq=1`，`sample_counter=1025`，`data_age_ms=25`，`config_epoch=<当前配置纪元>` |
   | 第 2 帧 | `stream_id=0x1201`，`stream_seq=2`，`sample_counter=1026`，`data_age_ms=24`，`config_epoch=<当前配置纪元>` |
   | 第 3 帧 | `stream_id=0x1201`，`stream_seq=3`，`sample_counter=1027`，`data_age_ms=26`，`config_epoch=<当前配置纪元>` |

4. CPU2 每收到一帧都重新检查 CRC、`src_id`、`dst_id`、`session_id`、`stream_id`、`stream_seq`、`sample_counter`、`config_epoch`、`data_age_ms`、状态位和诊断位。任何一项失败，都不得更新安全相关测量值。

传感器端实现要点：单向周期上报不是永久禁止 CPU2 下行控制。传感器仍需要在 `control_guard_ms` 窗口或接收中断中识别 `SET_COMM_MODE(REQUEST_RESPONSE)`，以便退出上报。

### 8.4 退出单向上报并继续双向通信

1. CPU2 在上报期间发送退出命令。

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=SET_COMM_MODE`，`seq=5`，`session_id=0x23070301`，`flags=ACK_REQUIRED + STOP_STREAM_REQUEST` |
   | 请求负载 | `target_comm_mode=REQUEST_RESPONSE`，`report_cmd=0`，`reserved0=0`，`period_ms=0`，`max_silent_ms=0`，`stream_id=0x1201`，`control_guard_ms=0` |

2. 传感器停止当前 `stream_id=0x1201` 的上报，并返回确认。

   | 类别 | 关键字段 |
   | --- | --- |
   | 响应帧头 | `msg_type=RSP`，`cmd=SET_COMM_MODE`，`seq=5`，`session_id=0x23070301` |
   | 响应负载 | `result_code=OK`，`comm_mode=REQUEST_RESPONSE`，`accepted_comm_mode=REQUEST_RESPONSE`，`accepted_stream_id=0`，`status_flags=DATA_VALID + MODE_MATCH` |

3. CPU2 收到退出响应后，保留同一 `session_id`，继续发送普通双向命令。例如读取电源：

   | 类别 | 关键字段 |
   | --- | --- |
   | 请求帧头 | `msg_type=REQ`，`cmd=READ_POWER`，`seq=6`，`session_id=0x23070301` |
   | 响应负载 | `result_code=OK`，`voltage_mv=<传感器供电电压>`，`power_status=<电源状态>` |

4. 如果退出响应之后仍收到旧 `stream_id=0x1201` 的 `REPORT_MEAS_FAST` 快报帧，CPU2 必须丢弃，不得更新测量值。若退出命令超时，CPU2 重试 3 次；仍失败则判定链路或传感器状态异常，重新 `HELLO` 或进入整机安全状态。

### 8.5 异常通信示例

| 场景 | 示例 | 接收方处理 |
| --- | --- | --- |
| CRC 错 | 任意帧 `safety_crc` 校验失败 | 丢弃帧，不使用负载；可记录 `BAD_CRC` 统计 |
| 响应超时 | CPU2 发 `READ_MEAS_COMBO(seq=7)` 后超过当前波特率对应普通请求超时无响应 | CPU2 用同一 `seq=7` 重发，并置 `RETRY_FRAME`；数据是否可用先按 `data_age_ms` 和安全功能响应时间判定 |
| 重复请求 | 传感器收到同一 `seq` 的重复 `READ_MEAS_COMBO` | 无副作用命令可返回最近一次响应；写参数类命令不得靠重复帧重复提交 |
| 旧会话帧 | 收到 `session_id` 不是当前会话的响应或上报 | 直接丢弃，不更新状态和数据 |
| 上报丢帧 | CPU2 期望 `stream_seq=11`，实际收到 `stream_seq=12` | 标记上报丢失，按 SRS 决定是否继续使用最新数据或进入恢复流程 |
| 上报静默 | 超过 `max_silent_ms` 未收到合法 `REPORT_MEAS_FAST` 快报帧 | 置数据无效，尝试退出上报或重新 `HELLO` |
| 配置变化 | 帧头 `safety_param_crc` 与 CPU2 记录值不同 | 拒绝使用数据，执行 `GET_CONFIG_DIGEST` 或重新 `HELLO` |
| 模式不匹配 | CPU2 期望 `DENSITY`，响应为 `LEVEL` 或 `MODE_MATCH` 未置位 | 不使用测量值，重新设置测量模式或上报故障 |

## 9. 状态机、超时和兼容

### 9.1 CPU2 状态

| 状态 | 说明 | 允许动作 |
| --- | --- | --- |
| `OFFLINE` | 未建立会话 | `HELLO` |
| `SESSION_READY` | 会话建立，默认双向模式 | `GET_STATUS`、`SET_MEASURE_MODE`、读数、参数读写 |
| `MEASURE_READY` | 测量模式稳定 | 双向读数或启动周期上报 |
| `PERIODIC_ACTIVE` | 周期上报运行中 | 接收 `REPORT_MEAS_FAST`、退出上报、保活 |
| `RECOVERING` | 通信或诊断异常恢复 | `PING`、`RESET_SESSION`、`HELLO` |
| `FAULT` | 最终故障 | 停止使用数据，等待安全策略处理 |

### 9.2 传感器状态

| 状态 | 说明 | 允许动作 |
| --- | --- | --- |
| `BOOT` | 上电初始化 | 等待 `HELLO` |
| `READY` | 会话已建立 | 响应双向命令 |
| `SETTLING` | 模式切换稳定中 | 响应状态，不输出有效测量 |
| `MEASURING` | 正常采样 | 响应读数或进入周期上报 |
| `STREAMING` | 周期上报中 | 发送上报，接收退出命令 |
| `SELF_TEST` | 自检中 | 限制普通读数 |
| `FAULT` | 内部故障 | 返回错误响应和诊断 |

### 9.3 超时和重试

200 米 RS485 长线下，实时性必须按 9600 bps 预算。下表按 8N1 串口 10 bit/字节估算，仅计算线上传输时间，未包含收发方向切换、驱动使能延时、调度延时和传感器处理时间。

| 帧或事务 | 字节数估算 | 9600 bps | 19200 bps | 38400 bps |
| --- | ---: | ---: | ---: | ---: |
| `REPORT_MEAS_FAST` 快报帧 | 固定 44 B | 约 46 ms | 约 23 ms | 约 12 ms |
| `READ_MEAS_COMBO` 请求 + 响应 | 约 120 B | 约 125 ms | 约 63 ms | 约 32 ms |
| `SET_COMM_MODE` 请求 + 响应 | 约 110 B | 约 115 ms | 约 57 ms | 约 29 ms |

实时性结论：

- 9600 bps 是当前项目设计基线，周期上报推荐不小于 1000 ms。
- 1000 ms 周期下，`REPORT_MEAS_FAST` 线上占用约 4.6%；500 ms 周期下约 9.2%，还需叠加方向切换、静默间隔和 CPU2 偶发下行命令。
- 500 ms 周期在 9600 bps 下可以配置，但应只用于明确需要更快刷新且现场误码率验证通过的场景。
- 19200 或 38400 bps 可用于更高实时性，但必须通过现场线缆和电磁环境测试确认后才能作为项目配置。
- 控制逻辑不得同步阻塞等待 3 次完整重试后才判定数据失效；数据是否可用必须优先由 `data_age_ms`、`sample_counter`、状态位、诊断位和 `max_silent_ms` 判断。
- 异常重试属于通信恢复流程，不属于安全相关数据继续可用的依据。

| 项 | 建议值 |
| --- | --- |
| 普通请求超时 | 9600 bps 下 300 ms；维护命令可放宽 |
| 普通请求重试 | 3 次 |
| 模式切换响应超时 | 1000 ms |
| 模式稳定等待 | 以 `settle_time_ms` 为准，上层设置最大值 |
| 周期上报周期 | 500 到 5000 ms；200 米 RS485 推荐不小于 1000 ms |
| 周期上报最大静默 | 不小于 `period_ms * 3` |
| 退出周期上报重试 | 3 次 |
| 自检超时 | 由传感器声明，上层设置最大值 |

所有超时和重试总耗时必须纳入安全功能响应时间预算。若安全功能要求更短响应时间，应在 SRS 中重新定义波特率、上报周期、最大数据年龄、重试次数和安全状态。

### 9.4 版本和兼容

| 项 | 规则 |
| --- | --- |
| `protocol_version` | 帧格式不兼容时递增 |
| `payload_version` | 单个命令负载结构变化时递增 |
| `safety_param_crc` | 能力位、倍率、传感器 ID、标定版本或安全相关配置变化时更新 |
| `scale_version` | 单位倍率表变化时递增，并纳入 `safety_param_crc` |
| `config_epoch` | 快报帧配置纪元，跟随 `safety_param_crc` 安全相关变化递增或重新分配；若 8 bit 纪元即将回绕，必须停止当前上报流，并通过 `RESET_SESSION` 或 `HELLO` 建立新 `session_id` 后重新分配 |
| 保留字段 | 发送 0，接收忽略 |
| 新命令 | 必须通过能力位声明 |
| 新上报字段 | 基线快报固定 44 字节；新增快报字段必须定义新的 `frame_type`，若走控制帧完整读取则递增 `payload_version`，不得让同一快报帧变长 |

## 10. 实现架构建议

### 10.1 传感器端推荐层次

| 层次 | 传感器端职责 | 实现建议 |
| --- | --- | --- |
| 字节接收 | 查找 `SOF`、累计长度、限制最大帧长 | 状态机实现，超长立即丢弃 |
| 帧校验 | 校验 `frame_len`、地址、版本、CRC32C | 先校验再解析负载 |
| 会话检查 | 管理 `session_id`、`seq`、`safety_param_crc` | 只保存当前会话和最近事务 |
| 命令分发 | 按 `cmd` 调用处理函数 | 使用静态命令表，未知命令返回 `UNSUPPORTED_COMMAND` |
| 测量快照 | 读取同一采样周期的温度、密度、频率和诊断 | 先复制快照，再编码响应或上报 |
| 上报调度 | 按 `period_ms` 周期发送 `REPORT_MEAS_FAST` | 单定时器、单 `stream_id`、单 `stream_seq` |

### 10.2 CPU2 后续适配建议

后续 CPU2 上层重做时，建议直接围绕本协议建立新的传感器服务层：

| 层次 | 职责 |
| --- | --- |
| `sensor_transport` | UART/DMA/无线链路收发 |
| `sensor_frame` | 帧同步、CRC、编码和解码 |
| `sensor_session` | `HELLO`、会话、序号、配置 CRC |
| `sensor_command` | 双向请求响应命令 |
| `sensor_stream` | 周期上报接收、静默超时和退出控制 |
| `sensor_data_model` | 把协议数据转换为 CPU2 业务对象 |
| `sensor_safety_monitor` | 数据年龄、诊断位、冻结、变化率和故障策略 |

这样 CPU2 上层可以重新兼容该协议，而不用被旧 DSM/LTD 分支结构约束。

## 11. 验证和认证追踪

### 11.1 SIL 通信满足性结论

本协议作为内部受控链路上的安全通信层，已经覆盖 IEC 62280 常见通信失效类型和 IEC 61784-3 black channel 思路所要求的主要防护措施。是否“完全满足 SIL 认证”，不能只由协议文档单独判定；还必须结合整机 SRS、目标 SIL、硬件失效率、诊断覆盖率、软件生命周期、验证记录和认证机构解释。

当前结论：

| 分类 | 结论 |
| --- | --- |
| 通信失效检测 | 协议设计已覆盖损坏、删除、重复、乱序、延迟、伪装、错配置和旧数据使用 |
| 传感器端可实现性 | 协议已按固定帧长、单请求、单上报流、无分片、无 TLV、无动态队列简化 |
| SIL 认证资料 | 协议卷可作为通信层设计输入，但还不是完整认证包 |
| 主动攻击/网络安全 | 不在协议本体内闭环；若链路有无线、开放网络或非受控接入，必须增加 IEC 62443 系统安全措施 |

### 11.2 已满足的通信安全点

| 要求主题 | 协议满足点 | 证据位置 |
| --- | --- | --- |
| 数据损坏检测 | SOF、长度、最大帧长和 CRC32C 覆盖头部关键字段与负载 | 第 5 章 |
| 删除/丢失检测 | 双向请求超时、周期上报最大静默、`stream_seq` 连续性检查 | 第 7、9、11 章 |
| 插入/多余帧处理 | `src_id`、`dst_id`、`sensor_id`、`session_id`、`cmd`、`seq` 均需匹配 | 第 4、5 章 |
| 重复/重放处理 | `session_id`、`seq`、`stream_id`、`stream_seq` 阻断旧会话、旧事务和旧上报流 | 第 4、7、8 章 |
| 乱序处理 | 双向响应必须回显请求 `seq` 和 `cmd`；周期上报 `stream_seq` 单调递增 | 第 4、5、8 章 |
| 延迟/旧数据处理 | 每帧测量值携带 `data_age_ms` 和 `sample_counter` | 第 5、6、8 章 |
| 伪装/错设备处理 | 帧头绑定源/目的节点、传感器 ID 和安全参数 CRC | 第 5 章 |
| 配置一致性 | `scale_version`、`safety_param_crc`、`config_epoch`、`GET_CONFIG_DIGEST`、参数提交后新 CRC | 第 5、6 章 |
| 数据有效性 | `DATA_VALID`、`DATA_STALE`、`MODE_MATCH`、诊断位和质量值共同判定 | 第 5、6 章 |
| 安全状态触发 | 任一关键校验失败时数据不得作为安全相关输入使用 | 第 5、7、9 章 |
| 可测试性 | golden frame、故障注入、长稳和边界测试清单 | 第 11 章 |
| 可实现性 | 单请求事务、单上报流、固定最大帧长、无分片、无动态队列和固定 44 字节快报帧 | 第 3、5、10 章 |

快报帧的压缩只改变字段编码方式，不删除安全语义。`src_id`、`dst_id`、`session_id`、`stream_id`、`stream_seq`、`sample_counter`、`data_age_ms`、状态位、诊断位和 CRC32C 仍在快报帧内直接存在；`sensor_id` 和 `safety_param_crc` 由控制帧建立会话和进入上报时绑定，快报帧用 `config_epoch` 做运行期配置一致性检查。认证资料中必须把这种映射关系纳入需求追踪和测试用例。

### 11.3 未满足或需系统级补证项

| 项 | 当前状态 | 需要补充的证据或决策 |
| --- | --- | --- |
| 目标 SIL 等级 | 协议不能单独定义 | 整机风险分析、SRS 和安全功能分配 |
| 最大允许数据年龄 | 协议提供 `data_age_ms`，但阈值未定 | 每个安全功能在 SRS 中定义最大数据年龄和响应时间 |
| CRC32C 充分性 | 协议选定 CRC32C，但未完成定量论证 | 结合最大帧长、误码率、危险失效率目标做 CRC 覆盖充分性说明 |
| 诊断覆盖率 | 协议定义诊断位和错误码，但未给出 DC 统计 | 故障注入测试、诊断覆盖率估算和残余风险说明 |
| 传感器硬件诊断 | 协议能承载诊断，但不证明硬件自检能力 | 传感器 ADC、频率测量、电源、存储、时钟等自检设计和测试 |
| 软件生命周期 | 协议文档不能替代 IEC 61508-3 生命周期证据 | 需求、设计、编码规范、评审、单元测试、集成测试、配置管理记录 |
| 主动攻击防护 | 协议不内置认证码和密钥管理 | 若链路非受控或有无线/网络入口，按 IEC 62443 增加认证、授权、密钥和安全通道 |
| 现场参数修改控制 | 协议定义维护流程，但未定义权限流程 | 维护权限、操作审计、参数备份、回滚和现场确认流程 |
| 认证机构接受度 | 尚未确认 | 认证机构是否接受本协议按 black channel 自研安全通信层评估 |

### 11.4 复杂度优化检查

在满足通信安全要求的前提下，已经做出的简化如下：

| 优化项 | 处理结果 | 为什么可简化 |
| --- | --- | --- |
| 删除分片/重组 | 最大 128 字节单帧承载全部业务负载 | 当前测量和维护负载均可放入单帧，分片会显著增加状态机复杂度 |
| 删除多路并发事务 | CPU2 同一时刻只保留一个未完成请求 | 内部传感器链路不需要吞吐优先，安全性和可验证性更重要 |
| 删除多上报流 | 同一会话只允许一个 `stream_id` | 用户只要求一个单向周期上报模式，多流会增加退出和静默判断复杂度 |
| 删除调试抓取命令 | 不在安全通信基线中定义原始 AD/内部调试量读取 | 调试数据不应被安全功能使用，另建非安全维护通道更清晰 |
| 删除独立状态上报 | 不定义单独的状态周期上报帧 | `REPORT_MEAS_FAST` 已携带通用状态和诊断前缀，避免两个上报流口径不一致 |
| 删除链路保留消息 | 不定义额外链路控制消息类型 | `PING`、`RESET_SESSION` 已覆盖保活和恢复 |
| 删除协议内认证码 | 不在本协议内定义密钥认证字段和能力位 | 当前目标是内部受控功能安全通信；主动攻击场景应由系统安全通道和密钥生命周期覆盖 |
| 保留参数维护但不进入测量流程 | `WRITE_PARAM`/`COMMIT_PARAM` 独立维护流程 | 满足配置管理，同时避免测量链路中出现配置副作用 |

不建议继续简化的点：

| 不建议删除项 | 原因 |
| --- | --- |
| `session_id` | 删除后旧帧、上电前残留帧和重放类失效难以阻断 |
| `seq` | 删除后双向响应错配、重复响应和乱序响应难以验证 |
| `stream_id`/`stream_seq` | 删除后无法证明单向上报退出后旧流不会被误用 |
| `safety_param_crc` | 删除后倍率、标定或能力变化后 CPU2 可能按旧解释使用数据 |
| `data_age_ms`/`sample_counter` | 删除后旧数据、缓存数据和冻结数据难以诊断 |
| `status_flags`/`diag_flags` | 删除后 CPU2 无法区分数据无效、模式未稳定、低质量和硬件诊断异常 |

### 11.5 标准要求到设计项追踪

| 标准要求主题 | 失效/风险 | 本协议设计项 | 验证证据 |
| --- | --- | --- | --- |
| IEC 61508-1 安全生命周期和需求追踪 | 设计无需求来源，认证证据断裂 | 第 1 章需求追踪、第 3 章标准映射、本章追踪矩阵 | SRS、设计评审、需求追踪表 |
| IEC 61508-1 配置管理 | 传感器能力、倍率、标定变化后 CPU2 仍按旧规则解释 | `scale_version`、`safety_param_crc`、`config_epoch`、`protocol_version`、`payload_version` | 配置变化测试、版本兼容测试 |
| IEC 61508-2 诊断和故障反应 | 通信错误导致危险数据被使用 | CRC、超时、序号、会话、状态位、诊断位 | 故障注入、诊断覆盖率说明 |
| IEC 61508-2 安全状态 | 传感器故障后继续输出有效数据假象 | `DATA_VALID`、`DATA_STALE`、`FAULT`、错误码 | 自检失败、数据过期、故障状态测试 |
| IEC 61508-3 软件架构 | 协议解析、业务解释和安全判断混在一起 | 建议分层：transport/frame/session/command/stream/data/safety | 架构评审、单元测试 |
| IEC 61508-3 接口明确性 | 字段单位、字节序、类型不明确 | 小端序、整数倍率、控制帧负载表、快报固定帧表、单位表 | golden frame、边界值测试 |
| IEC 61784-3 black channel | 底层链路不可信 | 安全通信层覆盖地址、命令或帧类型、长度、序号、负载和 CRC | 损坏、丢帧、重复、乱序测试 |
| IEC 62280 数据损坏防护 | bit 错、短帧、粘包被误解析 | SOF、控制帧长度、快报固定长度、最大帧长、CRC32C | CRC 错、长度错、粘包测试 |
| IEC 62280 删除/丢失防护 | 帧丢失后 CPU2 使用旧数据 | 请求超时、最大静默、数据年龄 | 丢帧、静默超时测试 |
| IEC 62280 重复/重放防护 | 旧帧或重复帧被当作新数据 | `session_id`、`seq`、`stream_id`、`stream_seq` | 重复帧、旧会话、旧上报流测试 |
| IEC 62280 乱序防护 | 后到的旧响应覆盖新响应 | 命令回显、事务号匹配、上报序号单调 | 乱序响应、跨命令响应测试 |
| IEC 62280 延迟防护 | 长延迟数据被当实时值 | `data_age_ms`、最大静默、采样计数 | 延迟注入、冻结数据测试 |
| IEC 62280 伪装防护 | 错节点或错传感器响应 | `src_id`、`dst_id`、`sensor_id`、配置 CRC、`config_epoch` | 地址替换、传感器 ID 替换测试 |
| IEC 62443 网络安全补充 | 主动攻击伪造合法 CRC 帧 | 本协议不以 CRC 替代认证；主动攻击场景由系统安全通道和访问控制覆盖 | 威胁建模、认证/授权/密钥管理测试 |

### 11.6 推荐 golden frame 范围

正式实现前应生成以下 golden frame，并纳入 CPU2 和传感器端共同测试：

- `HELLO` 请求和响应。
- `PING`、`GET_STATUS`、`RESET_SESSION` 请求和响应。
- `SET_MEASURE_MODE(DENSITY)` 请求和响应。
- `READ_MEAS_COMBO` 请求和响应。
- `SET_COMM_MODE(PERIODIC_UPLINK)` 请求和响应。
- `REPORT_MEAS_FAST` 固定 44 字节连续 3 帧。
- `SET_COMM_MODE(REQUEST_RESPONSE)` 退出上报请求和响应。
- `SET_COMM_MODE(PERIODIC_UPLINK)` 字段越界响应。
- `READ_LEVEL_FREQ`、`READ_WATER_CAP`、`READ_GYRO`、`READ_POWER` 正常响应。
- `GET_CONFIG_DIGEST`、`READ_PARAM`、`WRITE_PARAM`、`COMMIT_PARAM` 正常响应和配置 CRC 变化响应。
- `RUN_SELF_TEST`、`READ_SELF_TEST_RESULT` 正常和失败响应。
- CRC 错、长度错、字段越界、地址错、序号错、会话错、配置 CRC 错、快报 `config_epoch` 错。
- 温度、密度、频率、电压、信号质量的倍率边界值和 golden frame 工程值换算。
- 周期上报丢帧、重复、回退、静默超时和退出失败。

### 11.7 验证矩阵

| 测试类别 | 测试项 | 预期结果 |
| --- | --- | --- |
| 帧解析 | SOF 错、长度错、超最大帧长 | 丢弃帧，不使用负载 |
| 完整性 | 单 bit、多 bit、截断、拼接 | CRC 错，返回或记录 `BAD_CRC` |
| 字段边界 | 周期、静默时间、`stream_id`、通信模式或上报命令枚举越界 | 返回 `BAD_ARGUMENT`，保持原通信模式 |
| 会话 | 旧 `session_id`、错误 `sensor_id` | 帧无效，不使用数据 |
| 双向事务 | `seq` 错、`cmd` 错、重复请求 | 响应不匹配或幂等返回 |
| 周期上报 | 正常进入、连续上报、正常退出 | 切入上报，退出后继续双向通信 |
| 快报帧解析 | `frame_type` 错、固定长度错、`src_id` 或 `dst_id` 错 | 丢弃帧，不更新测量值 |
| 周期上报异常 | 丢帧、重复、回退、`stream_seq` 回绕、`sample_counter` 冻结、静默超时 | 数据无效或进入恢复/故障 |
| 数据有效性 | `DATA_STALE`、`MODE_SETTLING`、低质量 | 不更新安全相关数据 |
| 单位倍率 | `scale_version` 变化、倍率表不一致、整数边界值换算 | 拒绝旧数据或按新倍率表正确换算 |
| 配置一致性 | 能力位变化、倍率变化、配置 CRC 变化、快报 `config_epoch` 变化 | 重新 `HELLO` 或拒绝使用数据 |
| 自检诊断 | 自检失败、电源异常、通道异常 | 对应诊断位和错误码置位 |
| 长稳 | 周期上报 24 小时以上 | 无序号异常、无缓存溢出、无错误状态误报 |

### 11.8 待认证前确认项

1. 目标安全功能和目标 SIL 等级。
2. 每个安全功能允许的最大数据年龄和最大响应时间。
3. 周期上报是否作为安全输入，还是只作为普通实时监测输入。
4. 无线链路是否纳入 IEC 62443 主动攻击威胁模型。
5. CRC32C 对最大帧长和目标危险失效率的充分性论证。
6. 传感器端是否能提供启动计数、采样计数、参数 CRC 和自检诊断。
7. 认证机构是否接受本协议按 black channel 自研安全通信层评估。
