## 当前链路概览

### 初始化识别链路

`App_Init()` 中调用 `DetectSensorType()`。

当前识别顺序：
1. 先查询 CH9141K 蓝牙主机状态和蓝牙从机连接状态，确认蓝牙透传链路可用。
2. 尝试 多参数传感器通信协议 V3.0 协议，当前使用 `MULTIPARAM_V3_Read_SensorID()` 读取传感器编号。
3. 多参数传感器通信协议 V3.0 失败后尝试 DSM 一代协议，当前使用 `Read_VibrationTube_ID()` 读取 `CN` 振动管编号，并解析数字部分写入 `g_deviceParams.sensorID`。
4. DSM 一代识别成功后仍调用 `DSM_EnableDensityMode()`，保持原初始化后处于密度模式的行为。

当前结果：
- 初始化可以顺便写入 `g_deviceParams.sensorID`。
- `sensorType` 与 `sensorID` 一起保存到 FRAM。
- 不新增参数字段，不改变 CPU2/CPU3 参数布局。

### UART6 底层收发

当前三类 UART6 链路均已调整为 DMA 收发：
- DSM 一代文本协议：先启动接收 DMA，再发送 DMA，按换行符 `0x0A` 识别帧结束。
- 多参数传感器通信协议 V3.0 固定 8 字节协议：先启动 8 字节接收 DMA，再发送 DMA，收满 8 字节后做校验和协议语义检查。
- 蓝牙主机/从机连接判断：进入 CH9141K AT 状态查询，读取 `AT+BLEMODE?`、`AT+BLESTA?` 和连接 MAC。

这已经解决了“发送完成后才打开接收导致快速回包丢帧头”的主要时序风险。

### 蓝牙主机/从机链路

无线通信与 多参数传感器通信协议 V3.0 传感器共用 8 字节协议格式：
- 地址区分主机/从机，当前常用地址为 `1` 和 `2`。
- `WirelessPairing_CheckBluetoothLink()` 用于初始化阶段确认蓝牙主机可查询、蓝牙从机已连接。
- 运行期传感器通信超时时，`Sensor_DiagnoseCommTimeout()` 会调用 `WirelessPairing_CheckBluetoothLink()`，用于归因是传感器无响应、蓝牙主机异常还是蓝牙从机未连接。

## 已经比较合理的点

1. UART6 主接收路径已从逐字节轮询改为 DMA 收发。

   发送前先启动接收 DMA，可以避免快速应答丢头；固定 8 字节协议和文本协议都按自身帧边界处理。

2. 命令切换能打断通信等待。

   DSM、多参数传感器通信协议 V3.0、无线链路的发送等待、接收等待和重试循环里都有 `HasEffectiveCommandSwitchRequest()` 检查，命令切换不会被当作通信故障。

3. 无线链路有主机/从机分级诊断。

   传感器通信超时后，不再只报一个泛化传感器超时，而是会继续查询蓝牙主机/从机连接状态，能定位链路层故障。

4. 初始化识别已能读取传感器编号。

   多参数传感器通信协议 V3.0 直接读数值编号；DSM 一代从 `CN` 字符串中提取数字部分。现场查看参数时能直接看到识别到的传感器编号。

5. DSM 一代 `Cl` 电容响应已有固定帧校验。

   已检查长度、帧头、结尾、数值字段和 BCC，可避免短帧或异常帧被解析成有效电容值。

## 仍可优化的问题

### P1：多参数传感器通信协议 V3.0 初始化识别只读编号，可能不兼容旧传感器

当前 多参数传感器通信协议 V3.0 识别从原来的读温度改为读 `R0x16` 传感器编号。这样可以顺便保存编号，但有一个兼容风险：
- 如果某些旧 多参数传感器通信协议 V3.0 传感器支持温度读取，但不支持 `0x16` 编号参数，初始化会误判 多参数传感器通信协议 V3.0 协议失败。

建议：
- 保持编号读取为首选。
- 如果 `MULTIPARAM_V3_Read_SensorID()` 返回 `SENSOR_DEVICE_REPORTED_ERROR` 或格式/参数不匹配，可以 fallback 到 `MULTIPARAM_V3_Read_Temperature()` 做协议识别。
- fallback 成功时 `sensorType` 仍保存为 LTD_SENSOR，`sensorID` 保持原值或写 0，并打印“编号未读取”。

收益：
- 保留新需求：能读编号时自动保存。
- 避免因旧传感器无编号寄存器导致整机无法识别。

### P1：DSM 一代编号数字解析缺少溢出保护

当前 DSM 一代 `CN` 返回字符串会提取所有数字并写入 `uint32_t sensorID`。

风险：
- 如果返回异常长数字串，`value = value * 10 + digit` 可能溢出。
- 溢出后编号会变成错误值，但仍可能被保存。

建议：
- 解析前加入 `UINT32_MAX` 边界检查。
- 溢出时返回 `SENSOR_RESP_FORMAT_ERROR`，不保存编号。

收益：
- 避免异常帧或协议变化污染持久化参数。

### P1：DMA 停止函数命名和实际行为不完全一致

当前 `UART6_StopDmaReceive()`、`MULTIPARAM_V3_StopDmaReceive()` 内部调用的是 `HAL_UART_DMAStop(&huart6)`；旧 `WIRELESS_StopDmaReceive()` 随无线主机/从机 8 字节协议模块移除，当前蓝牙状态查询由 CH9141K AT 接口负责。

注意：
- HAL 的 `HAL_UART_DMAStop()` 会停止当前 UART 关联的 DMA，实际可能同时影响 TX/RX。
- 当前调用点大多是在 TX 完成后或错误退出时，逻辑上可接受。
- 但函数名写的是“StopReceive”，后续维护者可能误以为只停止 RX。

建议：
- 后续统一改名为 `UART6_StopDmaTransfer()` 或拆成明确的 `AbortTxRxDma` 语义。
- 注释写清楚“该调用会释放 UART6 当前 DMA 收发状态”。

收益：
- 减少后续维护误用，尤其是未来如果引入后台持续接收或 DMA TX 并发策略。

### P2：三个协议文件存在重复的 UART6 DMA 等待逻辑

当前 DSM 一代、多参数传感器通信协议 V3.0、无线文件内各自实现了：
- 停止 DMA
- 读取 DMA 已接收长度
- 等待 TX DMA 完成
- 等待 RX DMA 定长或终止符

这有利于第一轮低风险落地，但长期会带来问题：
- 修复 UART6 DMA 错误处理时要改三处。
- 超时策略和错误码归类容易逐渐分叉。
- 日后增加 DMA 半传输/空闲中断时重复成本高。

建议：
- 第二轮可以抽一个 `uart6_sensor_dma.c/.h` 小模块。
- 对外提供：
  - `UART6Sensor_TransceiveFixed8()`
  - `UART6Sensor_TransceiveUntilTerminator()`
  - `UART6Sensor_DrainUntilIdle()`
- 协议层只保留组帧、校验和业务错误映射。

收益：
- 让 UART6 的 DMA 生命周期只有一个维护点。
- 方便统一记录硬件错误、DMA 状态和原始帧详情。

### P2：无线初始化探测偏重，启动阶段耗时和日志较多

`Sensor_ProbeWirelessLink()` 当前调用 `WirelessPairing_CheckBluetoothLink()`：
- 对主机读取软件版本。
- 对主机读取电压。
- 对从机读取软件版本。
- 对从机读取电压。

每个读取内部都有多次重试和错误日志。初始化阶段如果链路异常，可能会等待较久并产生较多错误重试日志。

建议：
- 初始化阶段先用 `WirelessPairing_CheckBluetoothLink()` 查询 CH9141K 状态，只确认蓝牙主机可查询且蓝牙从机已连接。
- 版本和电压作为成功后的信息读取，可失败降级为 warning，不阻断传感器类型识别。
- 或保留当前完整读取，但把初始化阶段的重试次数配置为较小值。

收益：
- 缩短启动时间。
- 避免无线节点信息读取失败影响传感器协议识别。

### P2：无线链路错误归因还可以更细

当前 `Sensor_MapWirelessProbeError()` 只把 `SENSOR_DEVICE_COMM_TIMEOUT` 映射为主机/从机超时错误码；格式错误、BCC 错误、设备返回错误会原样返回。

问题：
- 如果 CH9141K AT 状态查询返回格式错误，最终故障码会保留具体响应格式错误；如果主机不可查询或从机未连接，会映射为蓝牙主机/从机错误。

建议：
- 为蓝牙主机/从机增加更细的错误映射：
  - 主机 BCC/格式错误
  - 从机 BCC/格式错误
  - 主机设备返回错误
  - 从机设备返回错误
- 如果错误码资源有限，可先在 `ErrorLog_WarnDetail()` 的详情中写入“节点：主机/从机 + 原始错误码”。

收益：
- 现场定位更直接，尤其是滑环或无线模块异常时。

### P2：DSM 一代编号保存丢失前后缀

当前系统参数 `sensorID` 是 `uint32_t`，DSM 一代编号字符串如 `N2009924H` 只能保存数字部分 `2009924`。

这是当前“不改协议/不改参数布局”的合理折中，但要明确限制：
- 完整字符串前缀和后缀不会保存。
- 如果未来需要 CPU3 显示完整编号，需要新增字符串参数或新增专用显示字段，这会影响参数存储、Modbus 映射和 CPU2/CPU3 协议。

建议：
- 当前版本文档中注明“DSM 一代仅保存数字部分”。
- 若现场必须看完整编号，再单独规划协议变更。

### P3：DMA TX 完成等待依赖 `huart6.gState`

当前 TX DMA 完成等待通过 `huart6.gState == HAL_UART_STATE_READY` 判断。

这在 HAL 当前用法下可以工作，但可维护性一般：
- 读状态不是事件驱动。
- 如果后续 HAL 行为或中断优先级变化，等待逻辑不如显式完成标志直观。

建议：
- 后续可增加 `HAL_UART_TxCpltCallback()` 中的 UART6 发送完成标志。
- 等待函数检查该标志，而不是直接看 `gState`。

收益：
- 发送完成条件更明确，调试时也更容易观察。

### P3：调试打印仍可能影响通信时序

`DEBUG_DSM`、`DEBUG_WIRELESS` 下会打印发送、接收和解析信息。现场打开调试时，USART1 打印可能拉长主循环时间。

建议：
- 默认关闭高频协议调试打印。
- 需要现场抓包时再启用。
- 对初始化阶段和错误详情保留摘要打印即可。

收益：
- 降低调试打印对 UART6 通信时序、命令切换响应和看门狗喂狗节奏的影响。

## 建议实施顺序

第一轮，建议优先做：
1. 多参数传感器通信协议 V3.0 编号读取失败 fallback 到温度识别。
2. DSM 一代编号数字解析增加溢出保护。
3. 把 DMA Stop 函数注释或命名改清楚。

第二轮，建议做：
1. 抽取 UART6 DMA 共用收发模块。
2. 优化初始化无线探测为轻量探测。
3. 蓝牙主机/从机错误归因细化到详情或专用错误码。

第三轮，视现场需求决定：
1. 是否保存 DSM 一代完整字符串编号。
2. 是否把 TX DMA 完成等待改为回调标志。
3. 是否增加 UART6 通信统计计数，如超时次数、BCC 错误次数、硬件错误次数、最近一次原始帧。

## 推荐验证项

代码验证：
- `git diff --check`
- `cmake --build build\\LTD_MAIN_CPU2`
- `py tools\\check_version_bumped.py`

现场验证：
1. 正常 多参数传感器通信协议 V3.0 传感器：上电后能识别为 LTD，`sensorID` 写入实际编号。
2. 不支持编号寄存器的旧 多参数传感器通信协议 V3.0 传感器：若增加 fallback，应能识别为 LTD，编号保持 0 或旧值，并打印编号读取失败提示。
3. DSM 一代传感器：上电后能读取 `CN`，保存数字部分编号，并仍进入密度模式。
4. 断开或关闭蓝牙主机模块：上电识别应报蓝牙主机通信异常。
5. 关闭蓝牙从机或取消连接：上电识别应报蓝牙从机未连接。
6. 断开传感器但保留无线链路：应能区分无线链路正常、传感器无响应。
7. 连续命令切换：通信等待期间切换命令应返回 `STATE_SWITCH`，不进入最终故障。
