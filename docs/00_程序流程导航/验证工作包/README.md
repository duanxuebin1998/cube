# 验证工作包

本目录保存核心流程专项验证工作包。工作包把机器发现的专项证据缺口转成可执行任务，但工作包建立、证据登记和缺口关闭只表示“专项资料关系完整”，不表示台架、实机或现场验证已经通过。

## 稳定关系

每份工作包只用以下三个稳定标识参与治理关系：

- `gap-*`：交付证据缺口稳定 ID；
- `cpu2_*` / `cpu3_*`：核心流程键；
- `ev-*`：验证证据稳定 ID。

业务链路关系继续由 `业务链路清单.json` 派生，工作包不复制链路清单。流程与工作包的专项关系继续只维护在 `流程证据清单.json`，证据身份继续只维护在 `验证证据登记清单.json`。

## 四层验证口径

| 验证层 | 目的 | 不能替代 |
| --- | --- | --- |
| 自动 | 校验静态契约、主机测试、文档关系和可构建性 | 台架时序、硬件响应、现场工况 |
| 台架 | 在可控输入与可观测接口下验证分支、异常和恢复 | 整机真实负载、长期运行、现场环境 |
| 实机 | 在目标 CPU、传感器、执行器和显示硬件上验证闭环 | 现场安装差异和生产工况 |
| 现场 | 在真实安装、介质、网络和操作流程下确认最终表现 | 不适用 |

每个用例都必须写明前置条件、操作步骤、观测位置、停止条件、预期结果和通过标准。任一停止条件触发时立即结束当前用例，保存原始日志，不用后续成功覆盖此前失败。

## 结果回写与关闭

工作包创建后保持 `cube-validation-result.status = pending`。实际执行时，先把每次用例运行追加到 `../验证运行登记清单.json`，由台账绑定操作者、环境、固件基线、Git revision 和原始记录 SHA-256；再根据用例当前边界更新同一份工作包的执行日期、环境、来源、固件基线、结果状态和摘要。

只有以下四项同时成立，才允许把工作包解释为已执行闭环：

1. `验证证据登记清单.json` 已登记稳定证据 ID；
2. `流程证据清单.json` 已建立流程专项关系；
3. 工作包中的 `cube-validation-result` 已按真实执行结果更新；
4. `交付证据缺口处置清单.json` 已追加合法关闭事件并关联该证据 ID。

当前 5 份工作包完成了前两项和缺口关系闭环，但 `验证运行登记清单.json` 仍为 0 次真实运行，25 个计划用例全部待执行。五份工作包结果继续保持 `pending`，因此仍应进入验证执行队列。
