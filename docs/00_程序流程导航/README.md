# 程序流程导航

更新日期：2026-07-12

本目录是整机程序流程的统一入口，用于从业务链路视角串起 CPU3 交互、CPU2 执行、协议通信、状态回读和故障处理。CPU2/CPU3 单侧详细流程已并入本目录下的 `CPU2/` 和 `CPU3/`。

## 文件说明

| 文件 | 用途 |
| --- | --- |
| `index.html` | CPU2/CPU3 程序流程统一入口，按整机业务、CPU2、CPU3 和专题流程跳转 |
| `流程排查入口.md` | 显式登记测量、通信、参数、故障、版本五类现场问题及流程入口，供预览站派生连续调查路径 |
| `流程文档长期优化路线图.md` | 约束后续优化优先级，优先推进系统分层、业务链路、证据可信度和单一数据源 |
| `业务链路清单.json` | 跨 CPU 业务链路和六类业务闭环的唯一结构化定义，供正式导航生成器和本机预览站共同读取 |
| `流程证据清单.json` | 八条核心链路涉及的流程页证据定义，统一登记固件基线、主源码、核对状态和验证资料 |
| `验证结果元数据规范.md` | 定义验证资料中的机器可读执行结果、固件基线和证据新鲜度判定，不复制测试正文 |
| `验证证据登记清单.json` | 为所有被引用正式验证资料分配稳定 ID、资料类型和声明验证层，不复制流程或链路关系 |
| `交付证据覆盖说明.md` | 说明稳定身份、流程专项关系、业务链路覆盖和已选基线覆盖的保守判定口径 |
| `交付证据缺口处置清单.json` | 为机器发现的专项证据缺口保存稳定 ID、责任人和不可覆盖的人工状态历史 |
| `交付证据缺口处置说明.md` | 说明机器事实与人工处置分层、六种生命周期状态、关闭条件和操作方式 |
| `验证工作包/` | 保存核心流程专项验证工作包，统一定义自动、台架、实机、现场四层可执行矩阵和真实结果回写边界 |
| `验证运行登记清单.json` | 以稳定运行 ID 追加登记工作包用例的真实执行、固件基线、Git revision 和原始记录 SHA-256 |
| `验证运行台账说明.md` | 说明计划、运行与结论三层事实边界，用例级状态派生、追加方式和完整性门禁 |
| `验证批次登记清单.json` | 以稳定批次 ID 冻结验证范围、固件基线、责任、窗口、退出条件和追加式里程碑事件 |
| `验证批次与里程碑决策说明.md` | 定义批次生命周期、运行覆盖闸门以及接受、拒绝和带例外接受的保守决策口径 |
| `角色化任务入口与导航说明.md` | 约束现场排查、开发变更、测试执行、交付决策四类首选入口、两次选择规则和证据生命周期侧栏 |
| `任务上下文连续性与工程搜索说明.md` | 定义可分享 URL 上下文字段、深层页面返回与下一步、六类工程语义搜索和自动门禁 |
| `页面权威性与责任治理说明.md` | 定义正式源与派生层、五类显式责任、六类持续治理检查和四层证据边界 |
| `治理事项处置清单.json` | 以稳定治理身份追加记录责任接手、正式动作、外部等待和机器事实清零后的关闭事件 |
| `治理事项闭环说明.md` | 定义“发现事实 → 责任接手 → 正式动作 → 机器清零”的关闭链、生命周期和六类关闭契约 |
| `交付证据基线清单.json` | 显式登记可审计的交付证据基线及当前选择，不按日期、文件名或版本标题自动推断 |
| `交付证据基线说明.md` | 说明基线保存条件、Git revision 绑定、兼容迁移和历史对比口径 |
| `交付证据基线生命周期说明.md` | 定义当前、已替代、停用、仅审计状态及责任人、正式说明和决策 revision 事件链 |
| `交付证据退化策略.json` | 以稳定机器字段定义“必须阻断”“需要解释”“仅记录”三类退化规则和策略版本 |
| `交付证据退化例外清单.json` | 记录精确绑定规则、基线和当前 Git revision 的豁免或解释，默认保持为空 |
| `交付证据退化策略说明.md` | 说明退化判定、例外约束、稀疏趋势和 Python/站点双实现一致性检查 |
| `流程图网站嵌入格式规范.md` | 约束流程 HTML 的独立阅读、站内嵌入、内联 SVG、响应式和可访问性格式 |
| `跨CPU业务链路.html` | 按液位、水位、密度、参数、故障、外部协议等业务链路串联 CPU3 与 CPU2 处理路径 |
| `SI协议分布测量程序流程.html` | SI Profile 分布测量跨 CPU 专题流程，覆盖外部触发、自动调度、CPU2 点位生成、采样、状态和寄存器输出 |
| `LNG计量仪系统框图.html` | 按整机拓扑、硬件连接、CPU2/CPU3 数据闭环、外部协议、测量执行和安全恢复整理的系统框图 |
| `LNG计量仪设备说明书.html` | LNG 计量仪设备结构、测量流程、通信接口、参数维护和故障处理说明 |

## 阅读建议

1. 不知道从哪查时，先看 `流程排查入口.md`，按现场问题类型进入。
2. 已经知道要查整机链路、CPU2 执行细节还是 CPU3 交互细节时，打开 `index.html` 或 `跨CPU业务链路.html`。
3. 如果流程变化涉及入口、状态机、命令分发、异常出口、通信链路或显示/参数交互，需要同步更新本目录入口和对应 CPU2/CPU3 流程页。

## 维护规则

- 本目录保存跨 CPU 导航、整机链路、系统框图、设备说明以及 CPU2/CPU3 单侧流程正文。
- HTML 当前作为流程阅读页保留；若新增长期维护的说明，应在 `docs/` 内补 Markdown 索引，由本地文档站同步展示，不在 `docs-site/` 维护第二份正文。
- `CPU2/assets/` 和 `CPU3/assets/` 只保存流程 HTML 使用的样式和交互脚本，不作为独立文档入口，也不放业务说明。
- 日常运行 `py tools\check_flow_docs.py` 检查正式源契约；需要查看最终站内结构时，再在 `docs-site/` 运行 `npm run check`。
- `py tools\update_flow_navigation.py` 默认只检查导航是否过期；确认待更新清单后才使用 `--write`，生成器只写真实变化并以原子替换保护现有文件。
- 核心流程页的固件基线、源码入口、关键语义和验证资料只在 `流程证据清单.json` 登记；固件升版、源码/验证资料路径失效或已登记符号从源码消失时，生成器和预览站检查会直接失败，禁止在 18 个页面中手工复制维护。
- 每条业务链路必须在 `业务链路清单.json` 覆盖入口触发、跨层分发、核心执行、状态回读、异常出口和验证证据六类闭环角色；闭环角色只能引用该链路已登记的正式流程页，核心执行必须包含 CPU2 页面。
- 本机预览站的“流程检索与治理工作台”只从上述两份清单生成，负责按 CPU、业务链路、可信状态、固件基线和证据类型筛选，并展示孤立页面、异常重复、断链、过期核对和证据路径等治理结果，不作为新的业务资料源。
- 本机预览站的“版本证据时间轴”从 `流程证据清单.json` 的专项验证路径、`docs/00_构建与版本/版本改动与测试/` 的正式资料和 Git 历史派生，区分当前事实与历史证据，并提供“版本资料 → 流程/业务链路”的反向索引；它不复制历史正文，也不新增第三份事实源。
- 本机预览站的“历史流程差异阅读”读取上述关键版本事件的 Git 固件差异，再按当前 `sourcePaths` 和 `sourceSymbols` 回溯流程影响，分开展示版本资料明确关系、当前证据映射、五类变化和未映射源码；它用于旧版本定位，不作为旧版本完整行为快照。
- 本机预览站的“现场问题排查”只读取 `流程排查入口.md` 中显式登记的五类调查类型和链接，再从业务链路、流程证据、版本时间轴与历史差异派生五步调查路径；缺少正式关系时保持为空，不按标题关键词猜测补齐。
- 本机预览站的“当前变更风险联动”复用源码影响分析，把候选流程投影到上述五类现场调查，并按相同流程或完全相同的关键语义关联历史事件和验证资料；它只提供测试范围建议，未映射源码和无法投影的流程保持显式可见，不自动判定故障。
- 本机预览站的“变更验证矩阵”继续复用当前变更风险结果，把五类调查、受影响流程、关键语义、自动检查、台架资料和现场确认组织成可执行清单；只有正式资料同时具备测试矩阵和明确通过标准时才标记为可执行，缺少专项证据或源码映射时保持显式缺口。
- 正式验证结果只写在被清单引用的 Markdown 资料中，并按 `验证结果元数据规范.md` 提供隐藏 JSON；`py tools\check_validation_result_metadata.py` 允许历史资料暂未结构化，但会阻止已添加元数据却存在语法、字段、日期、状态或基线错误的资料。
- 每份被流程证据清单引用的正式验证资料必须在 `验证证据登记清单.json` 中具有唯一稳定 ID；资料改名时保留 ID 并可登记旧路径别名，禁止用路径哈希或文件名临时生成长期身份。
- `验证证据登记清单.json` 只维护身份、资料类型和声明验证层；流程与资料关系继续只维护在 `流程证据清单.json`，链路与流程关系继续只维护在 `业务链路清单.json`，执行结果继续只维护在正式资料元数据中。
- `py tools\check_delivery_evidence_coverage.py` 要求身份登记精确覆盖当前引用资料，并生成流程、链路和已选基线覆盖报告；共享基线不得替代专项流程证据，声明验证层不得解释为已执行或已通过。
- 每个机器发现的专项证据缺口必须在 `交付证据缺口处置清单.json` 中有唯一稳定记录；人工状态只记录责任和决策，不修改机器覆盖事实，也不替代正式执行结果。
- `py tools\check_delivery_evidence_gaps.py` 对账当前缺口与追加式事件历史；机器缺口存在时禁止标记 `closed`，机器缺口消失时活动状态必须及时闭环，关闭事件还必须关联真正覆盖该流程的稳定证据 ID。
- `验证工作包/` 中每份正式工作包必须显式声明稳定缺口 ID、流程键和证据 ID，并包含自动、台架、实机、现场四层的前置条件、操作步骤、观测位置、停止条件、预期结果和通过标准；`py tools\check_validation_work_packages.py` 同时核对正文、结果元数据、专项关系和缺口关闭事件。
- 工作包关系闭环不等于测试通过；新建工作包先保持 `cube-validation-result.status = pending`，只有实际执行并保存可追溯记录后才按真实边界更新为 `partial`、`passed` 或 `failed`。
- 真实执行必须追加到 `验证运行登记清单.json`；运行只能引用工作包矩阵中已有用例，验证层必须一致，执行时间必须含时区，原始记录必须位于 `docs/` 下并登记 SHA-256，PDF 不进入运行完整性契约。
- 同一用例最后追加的运行作为当前结果，旧运行继续保留；`py tools\check_validation_runs.py` 会从用例当前结果派生工作包状态，并阻止运行台账与 `cube-validation-result.status` 漂移。
- 使用 `py tools\register_validation_run.py ... --dry-run` 先验证登记内容，确认后去掉 `--dry-run` 原子追加；工具不自动生成运行身份、测试结果或原始记录，也不替负责人批准交付。
- 零散运行只有纳入 `验证批次登记清单.json` 的冻结范围后，才能作为某次版本、台架、实机、现场或发布候选里程碑的决策输入；批次只引用稳定用例和运行 ID，不复制测试正文或原始记录。
- 本机预览站首页按 `角色化任务入口与导航说明.md` 只保留四类任务的唯一首选入口；系统流程地图和完整索引作为辅助入口保留，治理页面按证据生命周期分组，不再全部平铺。
- 四类任务从首页进入后，角色、业务链路、核心流程、固件基线和验证范围只通过 URL 保持；深层页面按 `任务上下文连续性与工程搜索说明.md` 提供相关返回路径与推荐下一步，不使用浏览器私有存储保存任务状态。
- 本机预览站的“工程语义搜索”只从正式问题索引、业务链路、流程证据、证据身份、版本事件和验证队列派生六类定位记录；右上角全文搜索继续保留，搜索命中不等于资料新鲜、测试通过或允许交付。
- 核心流程页和“责任治理队列”按 `页面权威性与责任治理说明.md` 展示正式来源、显式责任和未确认边界；六类检查清零时仍保留，未知责任不得填入默认负责人，队列状态不得解释为测试结论或交付批准。
- 当前治理事实与人工处置按 `治理事项闭环说明.md` 分层：机器事实存在但无事件时显示 `unclaimed`；责任接手、执行、外部等待和关闭只追加到 `治理事项处置清单.json`，不得在派生页面维护完成开关。
- `py tools\check_governance_items.py` 校验正式治理事件链；重新同步后的站点门禁继续对账当前事实指纹和关闭动作。活动事项失去机器事实时必须补关闭事件，已关闭事项重新出现时必须形成新一轮接手事件。
- `py tools\check_validation_batches.py` 强制批次合法转换和关闭边界：可决策或关闭事件必须覆盖全部冻结用例，接受必须全部通过，拒绝必须有失败，带例外接受必须有正式例外说明；批次关闭仍不替代发布批准。
- 使用 `py tools\manage_validation_batch.py create ... --dry-run` 创建前核对冻结范围，使用 `transition ... --dry-run` 核对事件；去掉 `--dry-run` 后才会原子追加，旧事件不得覆盖。
- 交付历史只读取 `交付证据基线清单.json` 中显式选择的基线；正式基线必须绑定完整 40 位 Git revision，并且只能从干净工作区的当前证据快照保存，未选择时预览站必须显示“未建立基线”。
- 保存基线使用 `py tools\save_delivery_evidence_baseline.py --id <基线-id> --label "<说明>" --owner "<负责人>" --explanation "docs/<正式说明>.md" --select`；有未提交修改时工具必须拒绝保存。`py tools\check_delivery_evidence_baselines.py` 负责校验清单、基线文件、生命周期、schema、路径和 revision 一致性。
- 每个基线必须以不可覆盖的事件链记录 `current`、`superseded`、`retired` 或 `audit-only` 状态；保存、选择、替代和停用都绑定负责人、正式说明与完整决策 revision，状态不根据日期推断。
- 默认趋势只纳入 `current` 和 `superseded`；`retired` 与 `audit-only` 继续保留完整审计，但不参与当前比较或默认趋势。
- 基线只保存关系、状态、路径和版本事实，不复制测试正文；新增或移除数量不自动解释为风险升降，未知 schema 直接失败，破坏性字段变化必须增加显式迁移。
- 退化门禁只读取 `交付证据退化策略.json` 已登记的稳定字段；没有显式基线时必须显示“未评估”，不得把当前值与零比较或把零条命中显示为通过。
- 阻断规则只覆盖可证明的治理退化；未映射源码、验证队列和专项证据缺口的数量增长进入“需要解释”，流程数量、结构化结果和固件基线变化只记录，不作为风险评分。
- 例外必须在 `交付证据退化例外清单.json` 中绑定规则、基线和完整当前 Git revision，并提供负责人、说明和正式资料路径；revision 或基线变化后自动失效，不能替代测试或批准。
- `py tools\check_delivery_evidence_regression.py` 校验正式策略、例外和稀疏趋势；`docs-site` 的 `npm run check` 会先重新同步，再核对 Python 与站点生成的门禁结果完全一致。
- 同一流程页承担不同闭环角色属于允许的合理复用；只有同一链路内内容完全相同的重复步骤才作为异常阻断。
- `py tools\check_flow_impact.py` 默认分析 CPU2、CPU3 和正式流程导航三个受控范围，先按已登记源码入口反推文件级候选流程，再从 Git 差异识别关键函数、状态、命令、寄存器和异常出口；本地审计输出和其他无关资料不计入指标，提交前使用 `--staged`。
- `--strict` 只阻止“关键语义已命中但流程页或证据清单未同步”的流程。只命中文件、注释专属变化、未配置语义或无法取得差异内容时保持提示，不自动判定为流程变化。
- 证据清单改动只确认实际落入对应 `pageKey` 对象的流程，修改其他页面的证据不能替受影响流程解除待复核状态。
- `sourceSymbols` 必须按已有 `sourcePaths` 分组登记；每个符号包含 `name`、`kind` 和 `label`，`kind` 仅允许 `function`、`state`、`command`、`register`、`error-exit`。生成器会确认符号真实存在于源码。
- 未映射到核心流程的固件源码只作为人工判断提示；确认其确实改变核心流程时，应先把对应源码入口和必要的关键语义补入 `流程证据清单.json`，再更新正式流程页。
- 更新流程入口后，同步检查 `docs/README.md`、`docs/00_程序流程导航/CPU2/README.md`、`docs/00_程序流程导航/CPU3/README.md`。
