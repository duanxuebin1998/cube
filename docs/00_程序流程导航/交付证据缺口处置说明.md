# 交付证据缺口处置说明

## 目的

缺口处置生命周期用于回答“机器已经发现哪些专项证据缺口、谁负责跟进、当前处于什么状态、依据哪次正式决策变化”。它不改变缺口事实，也不把人工状态冒充为验证结果。

## 单一来源边界

| 事实 | 唯一来源 |
| --- | --- |
| 当前是否缺专项证据 | `流程证据清单.json` 与 `验证证据登记清单.json` 的自动覆盖计算 |
| 缺口涉及哪些业务链路 | `业务链路清单.json` 的自动投影 |
| 缺口责任、状态与决策历史 | `交付证据缺口处置清单.json` |
| 验证资料身份 | `验证证据登记清单.json` |
| 实际执行结果 | 正式 Markdown 中的 `cube-validation-result` |

处置清单只保存稳定缺口 ID、核心流程键和追加式事件，不复制业务链路、测试步骤、覆盖关系或执行结果。

## 生命周期状态

- `new`：机器已发现缺口，尚未完成人工认领；
- `claimed`：责任人已确认，正在形成处置计划；
- `in-progress`：专项资料或验证工作正在执行；
- `waiting-external`：等待台架、实机、现场窗口、供应商资料或其它外部条件；
- `closed`：流程已获得正式专项证据关系，机器缺口已经消失；
- `not-applicable`：经正式说明确认该流程不需要独立专项证据，保留机器缺口但不伪造覆盖。

首个事件必须为 `new`。状态变化只能追加事件，不能覆盖旧事件；`closed` 后再次出现同一缺口时以新的 `new` 事件重开。

## 每个事件的责任字段

- `owner`：当前处置责任角色或负责人；
- `explanationPath`：`docs/` 下存在的正式 Markdown，说明本次状态决策；
- `decisionRevision`：作出决策时对应的完整 40 位小写 Git revision；
- `relatedEvidenceIds`：与本次处置直接相关的稳定 `ev-*` 身份，可为空；关闭时必须至少关联一份真正覆盖该流程的专项证据。

## 自动对账规则

1. 当前机器缺口必须在处置清单中有唯一记录。
2. 机器仍报告缺口时，人工状态不能为 `closed`。
3. 机器缺口已经消失时，人工状态不能仍停留在 `new`、`claimed`、`in-progress` 或 `waiting-external`。
4. `not-applicable` 不会消除机器缺口，只表示已经形成正式人工边界。
5. 关闭事件关联的证据 ID 必须存在，并且当前确实与该流程形成专项关系。

## 操作方式

检查清单、状态历史与机器缺口是否一致：

```powershell
py tools\check_delivery_evidence_gaps.py
```

追加一次生命周期事件：

```powershell
py tools\manage_delivery_evidence_gap.py claimed `
  --id gap-cpu2-05-specific-evidence `
  --owner "测量验证" `
  --explanation "docs/00_构建与版本/版本改动与测试/<正式说明>.md" `
  --decision-revision <40位revision>
```

需要关联证据时可重复传入 `--evidence-id`。工具会先校验状态迁移和当前机器事实，再原子写回正式清单。
