# 流程文档长期优化路线图

更新日期：2026-07-11

## 长期目标

把程序流程文档建设成可从现场现象快速进入、能跨 CPU 追踪、能回到源码与版本证据、并可由生成工具稳定维护的工程知识地图。后续优化以“更快定位和更可靠追溯”为标准，不再以逐页装饰或零散样式修补为主线。

## 优先级原则

1. 先解决信息架构和业务链路，再处理单页细节。
2. 先建立整机层、CPU 层、子流程层和证据层的关系，再增加新的流程页。
3. 业务事实只维护在 `docs/` 或受控结构化数据中；`docs-site/` 只负责展示。
4. 可访问性、嵌入契约和链接完整性继续由自动门禁守住，不作为每轮人工优化的主要投入。
5. 不逐页手工复制公共导航、提示和样式；公共能力进入生成器、共享资源或同步器。

## 阶段路线

| 阶段 | 核心结果 | 状态 |
| --- | --- | --- |
| 0. 入口收敛 | 首页收敛为系统流程地图、现场问题排查和完整索引三种入口；核心链路按入口、分发、执行、证据展示 | 已完成 |
| 1. 单一链路数据源 | 八条业务链路集中到 `业务链路清单.json`，正式 HTML 与预览站共同读取并校验 | 已完成 |
| 2. 流程页证据头 | 每个核心流程页明确上游、下游、源码入口、适用固件版本和验证资料，减少“图能看但结论无法确认” | 已完成 |
| 3. 核心业务闭环 | 为八条核心链路补齐 CPU3 入口、CPU2 执行、状态回读、异常出口和测试证据，消除断链 | 已完成 |
| 4. 检索与治理 | 让核心流程可按 CPU、业务链路、版本、可信状态和证据类型过滤，并自动报告孤立页面、异常重复、断链和过期证据 | 已完成 |
| 5. 变更影响联动 | 从源码改动反推受影响流程、业务链路和验证资料，在日常检查、预览站和提交前提示流程复核范围 | 已完成 |
| 6. 语义级影响识别 | 从文件级映射继续收敛到函数、状态机和协议符号级别，区分流程变化与普通实现改动 | 下一阶段 |

## 阶段 1 完成结果

- 液位、水位、密度、读取部件参数、AO/HART、参数、故障和外部协议八条链路只维护一份结构化定义。
- `tools/update_flow_navigation.py` 和 `docs-site/scripts/sync-content.mjs` 共同读取 `业务链路清单.json`，脚本内不再复制业务步骤。
- Python 生成器检查正式流程页键和文件是否存在；预览站同步器检查地图结构，站点链接门禁检查最终地址。
- 新增或调整业务链路时，正式入口页、跨 CPU 链路页和本机预览由同一份清单生成并保持幂等。

## 阶段 2 完成结果

- `流程证据清单.json` 完整覆盖八条业务链路涉及的 18 个核心 CPU2/CPU3 页面，集中登记可信状态、核对日期、固件基线、主源码和验证资料。
- 18 个核心页面由导航生成器统一注入证据头，上游、下游继续由关系数据生成，不在页面中手工复制公共证据信息。
- 本机预览站直接读取同一清单，在系统流程地图展示整体验证覆盖率和每条链路的证据覆盖率。
- Python 与 Node 检查共同阻止核心页面漏登记、源码/验证资料路径失效、证据越出正式目录和固件基线过期。

## 阶段 3 完成结果

- `业务链路清单.json` 升级为闭环契约，八条链路必须同时覆盖入口触发、跨层分发、核心执行、状态回读、异常出口和验证证据，共计 48/48 个闭环角色。
- 液位、水位、密度、读取部件参数和 AO 五条链路显式接入 CPU2 统一故障管理页，不再只在执行页文字中隐含异常去向。
- AO 链路补入 CPU3 内部 Modbus 写入和 ACK 核对节点，补齐菜单参数到 CPU2 参数生效之间的跨 CPU 断点。
- 正式跨 CPU 链路页和本机系统流程地图共同展示六类闭环角色；系统地图同时保留页面证据覆盖率，区分“链路完整”与“页面可信”。
- Python 与 Node 门禁阻止缺失闭环角色、闭环引用非正式步骤、核心执行未进入 CPU2，以及验证页未核对等退化。

## 阶段 4 完成结果

- 本机预览站新增“流程检索与治理工作台”，18 个核心流程可按 CPU、八条业务链路、可信状态、固件基线和证据类型组合筛选，并可搜索页面名、源码路径和闭环角色。
- 工作台页面完全由 `业务链路清单.json` 和 `流程证据清单.json` 生成，不新增第二份业务数据；筛选条件写入地址栏，可保留或共享当前检索视图。
- 自动治理报告统一检查孤立页面、证据漏登记、闭环缺口、异常重复、上游/下游断链、核对时效、固件基线和证据路径。
- 同一页面在一条链路内承担不同职责时登记为“合理复用”，只有内容完全相同的重复步骤才作为异常，避免把跨角色复用误报为治理问题。
- Python 导航生成器和 Node 站点同步器共同执行治理规则；正式 HTML 生成、预览站构建和测试继续由同一批结构化数据约束。

## 阶段 5 完成结果

- 新增 `tools/check_flow_impact.py`，从现有两份正式清单动态建立“29 个源码入口 → 18 个核心流程页 → 8 条业务链路 → 验证资料”的反向索引，不维护第三份映射表。
- 支持分析当前工作区、暂存区、指定 Git 范围或显式文件清单，并提供文本和 JSON 输出；严格模式只阻止“已明确命中核心源码入口但未同步流程页或证据清单”的情况。
- 未登记到核心流程的固件源码单独列为人工判断项，不自动归入某条业务链路，避免把普通驱动、测试或实现改动误报为流程变化。
- `py tools/check_docs.py` 已加入反向索引和当前工作区影响检查；`py tools/check_version_bumped.py` 在存在暂存内容时同步输出暂存区流程影响摘要。
- 本机流程工作台新增“最近同步时的工作区影响”区块，直接展示固件源码数、受影响流程、受影响链路和待复核流程，并提供实时 CLI 与提交前命令入口。
- 影响分析只读 Git 状态，不改源码、不自动修改流程文档、不自动升版，也不改变暂存区。

## 阶段 6 目标

- 在高风险核心源码入口中登记关键函数、状态变量、命令、寄存器和异常出口符号。
- 从 Git diff 提取实际变化的函数或契约符号，区分注释/局部实现变化与入口、状态机、分发、回读或异常路径变化。
- 只有语义级变更命中流程契约时才建议严格阻断，进一步减少文件级映射带来的人工复核范围。
- 优先覆盖跨 CPU 通信、测量总入口、故障管理、参数生效和外部协议五类高风险链路，不追求一次覆盖所有底层文件。

## 长期衡量指标

- 从首页进入任一核心业务流程不超过两次选择。
- 八条核心链路都有明确的入口、CPU3、CPU2、结果和证据去向。
- 八条核心链路的六类闭环角色保持 48/48 覆盖。
- 核心流程页不存在无法回到上游、下游或总览的孤立页面。
- 18 个核心流程可从单一工作台按 CPU、业务链路、固件基线和证据类型筛选。
- 治理报告的阻断问题保持为 0，合理复用与异常重复分开统计。
- 已登记源码入口的改动可自动反推核心流程、业务链路和验证资料，未映射固件源码保持显式可见。
- 导航生成、流程格式、内部链接和正式源边界检查全部自动通过。
- 固件流程变化时，受影响流程页和证据资料可由同一份链路清单定位。

## 暂不投入的方向

- 不继续逐个调整阴影、圆角、焦点环或单张流程图的局部配色，除非出现明显可用性回归。
- 不为预览站复制第二份业务正文。
- 不恢复旧 `site/`，不把 `docs-site/` 变成正式业务资料源。
- 不生成或维护 PDF，除非用户明确点名。
