# 流程文档长期优化路线图

更新日期：2026-07-12

## 长期目标

把程序流程文档建设成可从现场现象快速进入、能跨 CPU 追踪、能回到源码与版本证据、并可由生成工具稳定维护的工程知识地图。后续优化以“更快定位和更可靠追溯”为标准，不再以逐页装饰或零散样式修补为主线。

## 优先级原则

1. 先解决信息架构和业务链路，再处理单页细节。
2. 先建立整机层、CPU 层、子流程层和证据层的关系，再增加新的流程页。
3. 业务事实只维护在 `docs/` 或受控结构化数据中；`docs-site/` 只负责展示。
4. 可访问性、嵌入契约和链接完整性继续由自动门禁守住，不作为每轮人工优化的主要投入。
5. 不逐页手工复制公共导航、提示和样式；公共能力进入生成器、共享资源或同步器。

| 3. 核心业务闭环 | 为八条核心链路补齐 CPU3 入口、CPU2 执行、状态回读、异常出口和测试证据，消除断链 | 已完成 |
| 4. 检索与治理 | 让核心流程可按 CPU、业务链路、版本、可信状态和证据类型过滤，并自动报告孤立页面、异常重复、断链和过期证据 | 已完成 |
| 5. 变更影响联动 | 从源码改动反推受影响流程、业务链路和验证资料，在日常检查、预览站和提交前提示流程复核范围 | 已完成 |
| 6. 语义级影响识别 | 从文件级映射继续收敛到函数、状态机和协议符号级别，区分流程变化与普通实现改动 | 已完成 |
| 7. 版本证据时间轴 | 把流程基线、版本改动与测试资料和 Git 范围串成可回溯时间轴，回答“何时、为何、由哪次改动改变” | 已完成 |
| 8. 历史流程差异阅读 | 在不复制当前流程正文的前提下，形成关键版本间的流程变化摘要和可定位差异，支持旧版本现场回溯 | 已完成 |
| 9. 现场回溯路径闭环 | 把现场现象、核心业务链路、历史版本差异和验证证据串成可复用的调查路径，减少跨页面人工拼接 | 已完成 |
| 10. 变更到现场风险联动 | 从当前源码改动反推可能受影响的现场调查类型和验证路径，让知识门户从事后回溯继续前移到变更预防 | 已完成 |
| 11. 变更验证矩阵 | 把受影响调查类型、业务链路、关键语义和验证资料组织成可执行检查矩阵，明确自动检查、台架验证和现场确认边界 | 已完成 |
| 12. 验证结果回写与证据新鲜度 | 让执行结果回到正式验证资料，并自动提示证据过期、流程基线变化和缺少复验的风险 | 已完成 |
| 13. 验证执行队列与覆盖趋势 | 把失败、需复验、部分完成、待执行、未记录和缺专项证据收敛为风险排序的执行队列，并区分历史迁移欠账与当前版本真实缺口 | 已完成 |
| 14. 变更闭环与交付就绪证据包 | 把当前变更、受影响流程、执行队列、正式结果和未验证边界汇总为单一交付视图，明确“还能做什么、缺什么证据、是否具备交付条件” | 已完成 |
| 15. 交付证据基线与历史对比 | 保存可审计的交付证据基线，并在后续变更中比较新增影响、已关闭缺口和新出现未知项 | 已完成 |
| 16. 基线退化门禁与趋势治理 | 把历史对比转成可配置的退化策略和稀疏趋势视图，明确哪些变化必须阻断、哪些只提示、哪些需要人工解释 | 已完成 |
| 17. 基线生命周期与责任闭环 | 为基线建立替代、停用、责任人和保留边界，使长期趋势不会被过期或重复基线污染 | 已完成 |
| 18. 稳定证据身份与覆盖关系 | 用稳定 ID 连接正式验证资料、核心流程、业务链路和已选基线，显式保留专项覆盖缺口 | 已完成 |
| 19. 交付证据缺口处置生命周期 | 把机器缺口与人工责任、追加式状态历史和正式决策依据分层管理 | 已完成 |
| 20. 缺口验证工作包 | 把已认领缺口转成可执行、可回写、可由正式证据关闭的验证工作包 | 已完成 |
| 21. 真实验证运行台账 | 为工作包用例建立追加式运行身份、原始记录完整性和用例级结果派生，严格区分计划与真实执行 | 已完成 |
| 22. 验证批次与里程碑决策 | 把多次用例运行组织成明确批次，冻结范围、基线、责任和退出条件，为版本或现场里程碑提供可审计决策输入 | 已完成 |
| 23. 角色化任务入口与导航收敛 | 将流程、排查、验证和交付页面按现场、开发、测试、交付四类任务重新组织，降低治理页面增长后的选择成本 | 规划中 |

## 阶段 1 完成结果

- 液位、水位、密度、读取部件参数、AO/HART、参数、故障和外部协议八条链路只维护一份结构化定义。
- `tools/update_flow_navigation.py` 和 `docs-site/scripts/sync-content.mjs` 共同读取 `业务链路清单.json`，脚本内不再复制业务步骤。
- Python 生成器检查正式流程页键和文件是否存在；预览站同步器检查地图结构，站点链接门禁检查最终地址。
- 新增或调整业务链路时，正式入口页、跨 CPU 链路页和本机预览由同一份清单生成并保持幂等。

## 阶段 2 完成结果

- `流程证据清单.json` 完整覆盖八条业务链路涉及的 18 个核心 CPU2/CPU3 页面，集中登记可信状态、核对日期、固件基线、主源码和验证资料。
- 18 个核心页面由导航生成器统一注入证据头，上游、下游继续由关系数据生成，不在页面中手工复制公共证据信息。
- 本机预览站直接读取同一清单，在系统流程地图展示整体验证覆盖率和每条链路的证据覆盖率。
- Python 与 Node 检查共同阻止核心页面漏登记、源码/验证资料路径失效、证据越出正式目录和固件基线过期。

## 阶段 3 完成结果

- `业务链路清单.json` 升级为闭环契约，八条链路必须同时覆盖入口触发、跨层分发、核心执行、状态回读、异常出口和验证证据，共计 48/48 个闭环角色。
- 液位、水位、密度、读取部件参数和 AO 五条链路显式接入 CPU2 统一故障管理页，不再只在执行页文字中隐含异常去向。
- AO 链路补入 CPU3 内部 Modbus 写入和 ACK 核对节点，补齐菜单参数到 CPU2 参数生效之间的跨 CPU 断点。
- 正式跨 CPU 链路页和本机系统流程地图共同展示六类闭环角色；系统地图同时保留页面证据覆盖率，区分“链路完整”与“页面可信”。
- Python 与 Node 门禁阻止缺失闭环角色、闭环引用非正式步骤、核心执行未进入 CPU2，以及验证页未核对等退化。

## 阶段 4 完成结果

- 本机预览站新增“流程检索与治理工作台”，18 个核心流程可按 CPU、八条业务链路、可信状态、固件基线和证据类型组合筛选，并可搜索页面名、源码路径和闭环角色。
- 工作台页面完全由 `业务链路清单.json` 和 `流程证据清单.json` 生成，不新增第二份业务数据；筛选条件写入地址栏，可保留或共享当前检索视图。
- 自动治理报告统一检查孤立页面、证据漏登记、闭环缺口、异常重复、上游/下游断链、核对时效、固件基线和证据路径。
- 同一页面在一条链路内承担不同职责时登记为“合理复用”，只有内容完全相同的重复步骤才作为异常，避免把跨角色复用误报为治理问题。
- Python 导航生成器和 Node 站点同步器共同执行治理规则；正式 HTML 生成、预览站构建和测试继续由同一批结构化数据约束。

## 阶段 5 完成结果

- 新增 `tools/check_flow_impact.py`，从现有两份正式清单动态建立“29 个源码入口 → 18 个核心流程页 → 8 条业务链路 → 验证资料”的反向索引，不维护第三份映射表。
- 支持分析当前工作区、暂存区、指定 Git 范围或显式文件清单，并提供文本和 JSON 输出；严格模式只阻止“已明确命中核心源码入口但未同步流程页或证据清单”的情况。
- 未登记到核心流程的固件源码单独列为人工判断项，不自动归入某条业务链路，避免把普通驱动、测试或实现改动误报为流程变化。
- `py tools/check_docs.py` 已加入反向索引和当前工作区影响检查；`py tools/check_version_bumped.py` 在存在暂存内容时同步输出暂存区流程影响摘要。
- 本机流程工作台新增“最近同步时的工作区影响”区块，直接展示固件源码数、受影响流程、受影响链路和待复核流程，并提供实时 CLI 与提交前命令入口。
- 影响分析只读 Git 状态，不改源码、不自动修改流程文档、不自动升版，也不改变暂存区。

## 阶段 6 完成结果

- `流程证据清单.json` 在原有 `sourcePaths` 内可选登记 `sourceSymbols`，集中描述关键函数、状态、命令、寄存器和异常出口，不新增第三份业务映射。
- 已优先覆盖测量命令总入口、故障管理、CPU2/CPU3 内部通信、CPU2/CPU3 参数生效、菜单下发以及 LTD、DSM、Wartsila、SI 外部协议等高风险边界；同时补齐 DSM 真正的分发/响应源码和统一外部协议切换帧入口。
- Python 和 Node 校验共同阻止语义路径越出 `sourcePaths`、符号名或类型无效、重复登记以及源码中不存在的符号，避免清单逐渐失真。
- 影响分析从 Git 零上下文差异提取实际代码行和函数上下文，注释专属差异不触发关键语义；命中文件但未命中已登记语义时只作为候选提示。
- `--strict` 只阻止“关键语义已命中但流程页或证据清单未同步”的情况，文件级候选、未配置语义和无法取得差异内容保持显式可见但不误阻断。
- 复核确认从“证据清单任意改动”收紧到具体 `pageKey` 对象；其他流程的清单调整不能替当前受影响流程解除待复核状态。
- 流程工作台同时显示文件级候选流程、语义命中流程、命中关键符号和严格待复核数，并可按符号名或中文语义说明检索流程。

## 阶段 7 完成结果

- 本机预览站新增“版本证据时间轴”，集中展示当前 CPU2/CPU3 固件基线、核心流程核对日期、历史改动与测试方案以及 Git revision range。
- 时间轴直接从 `流程证据清单.json` 的 `validationPaths` 派生，按版本资料文件名解析日期、CPU2/CPU3 版本和主题，再读取 Git 首次引入提交；没有新增第三份业务映射。
- “当前事实”和“历史版本证据”分区展示：当前基线仍以证据清单和当前源码为准，历史资料只说明当时的改动与验证，不替代当前流程结论。
- 同一版本资料被多个流程引用时只生成一个事件，并反向汇总受影响流程和八条业务链路，避免在页面上重复堆叠相同历史正文。
- 18 个核心流程都获得稳定的历史锚点，明确展示当前基线、首次证据和最近证据；没有专项历史资料的流程保持显式为空，不使用推测补齐。
- 首页、流程工作台、完整索引和侧栏共同接入时间轴；版本资料正文仍维护在 `docs/00_构建与版本/版本改动与测试/`，预览站只生成关系视图。

## 阶段 8 完成结果

- 本机预览站新增“历史流程差异阅读”，只处理正式流程证据清单已引用的关键版本事件，不为每次提交生成完整历史站点。
- 每个事件读取版本资料首次引入提交的真实 CPU2/CPU3 固件差异，再用当前 `流程证据清单.json` 的源码入口和 `sourceSymbols` 回溯影响，没有新增第三份业务映射。
- 版本资料明确关联的流程与 Git 差异按当前证据映射出的流程并排展示，重合、仅文档关联和仅源码回溯三种关系保持可区分，不把自动映射覆盖正式版本资料。
- 差异统一拆成入口/命令、状态与执行、异常出口、协议语义、验证证据五类；没有命中的类别显示为零，不用推断填补。
- 已映射与未映射的历史固件源码分别列出；无法解析 Git 范围、只命中文件和未映射源码均保持显式可见，不猜测归入核心流程。
- 页面明确标注这是“当前证据映射下的历史回溯”，不是旧版本完整源码行为的永久快照；结论仍需结合正式版本方案和必要的旧源码审阅。
- 首页、版本证据时间轴、流程工作台、完整索引和侧栏共同接入历史差异入口；共享版本资料继续只生成一个事件。

## 阶段 9 完成结果

- `流程排查入口.md` 为 13 类现场现象显式登记测量、通信、参数、故障、版本五类调查类型；分类只负责组织入口，不复制业务链路或历史结论。
- 本机预览站把每类问题统一展开为“确认现场现象 → 锁定业务链路 → 阅读当前流程 → 核对历史差异 → 回到验证证据”五步调查路径，减少在多个入口页之间人工拼接。
- 业务链路按现有六类闭环角色计算相关度并选取高关联入口；当前流程来自问题索引显式链接，历史事件只使用版本资料与流程的明确关系，验证资料继续来自流程证据清单。
- 版本类调查明确不绑定单一业务链路，先进入版本总览和参数存储升级清单，再核对全部关键版本事件与正式测试资料。
- 页面集中显示 5 类调查、13 类现场现象、8 条业务链路和 10 个关键历史事件；五类路径都可直接进入当前流程、历史差异和正式证据。
- Node 测试同时约束五类调查类型完整、非法分类失败、关系从现有清单派生以及最终页面包含五条连续调查路径；缺少正式关系时仍保持为空，不按标题关键词猜测补齐。

## 阶段 10 完成结果

- 新增“当前变更风险联动”页面，复用现有源码入口和关键语义分析，把候选流程继续投影到测量、通信、参数、故障、版本五类现场调查路径。
- 流程工作台和现场问题排查页都显示当前变更摘要，并可连续进入受影响流程、业务链路、历史相似事件和验证资料；首页与侧栏提供一级入口。
- 现场分类只使用 `流程排查入口.md` 的显式流程关系；历史相似只使用相同流程或完全相同的关键语义，不新增源码到问题类型的独立映射，也不按标题关键词猜测。
- 未映射固件源码和无法投影到现场分类的候选流程保持显式可见；预览建议与 `check_flow_impact.py --strict` 严格门禁分层，页面只用于缩小复核和测试范围。
- 站点同步只扫描 CPU2、CPU3 和正式流程导航范围，避免临时输出目录放大工作区指标；Node 契约覆盖风险投影、历史精确关联、页面生成与导航入口。

## 阶段 11 完成结果

- 本机预览站新增“变更验证矩阵”，把当前工作区影响投影为测量、通信、参数、故障、版本五行调查矩阵，并并排展示受影响流程、关键语义、自动检查、台架与证据、现场确认五类执行信息。
- 当前矩阵从 11 个候选流程和 18 个关键语义派生 4 项自动检查；验证资料继续读取正式流程证据清单和版本方案，不新增第二份测试正文。
- 9 份相关验证资料按内容契约分类，只有同时具备可执行测试矩阵和明确通过标准的资料才标记为可执行；当前 1 份满足条件，其余资料明确显示“只有通过标准”或“仅供参考”。
