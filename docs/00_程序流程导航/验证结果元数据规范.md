# 验证结果元数据规范

## 1. 目的

版本改动与测试方案仍是验证步骤、通过标准和原始证据的唯一正文来源。本规范只在被 `流程证据清单.json` 引用的 Markdown 资料中增加一段隐藏 JSON，用于回答三个跨文档问题：验证实际执行到什么程度、结果对应哪一版固件、当前流程是否已经晚于这份证据。

元数据不复制测试矩阵，不自动推测“通过”，也不替代台架记录、现场记录或 Git 证据。流程与资料、关键语义的关系继续只维护在 `流程证据清单.json`；资料稳定身份和声明验证层只维护在 `验证证据登记清单.json`。

## 2. 标准格式

把以下注释放在文档标题和更新日期之后、正文第一节之前：

```md
<!-- cube-validation-result
{
  "schemaVersion": 1,
  "status": "partial",
  "executedAt": "2026-07-11",
  "environment": "Windows PowerShell；ARM GNU/CMake/Ninja；主机 GCC；Python 3",
  "source": "本文第 7 节测试矩阵与第 10 节构建和检查证据",
  "firmwareBaseline": {
    "cpu2": "V1.22.0.0",
    "cpu3": "V1.21.0.0"
  },
  "summary": "自动测试和构建已通过，实机与现场项目仍待执行。"
}
-->
```

同一资料只能有一个 `cube-validation-result` 注释块。JSON 必须使用双引号，不能包含尾随逗号或 Markdown 注释。

## 3. 字段契约

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `schemaVersion` | 是 | 当前固定为整数 `1` |
| `status` | 是 | 只能是 `passed`、`failed`、`partial`、`pending` |
| `executedAt` | 是 | 实际执行或最近一次结果汇总日期，格式为 `YYYY-MM-DD` |
| `environment` | 是 | 写明能解释结果边界的构建、主机、台架或现场环境 |
| `source` | 是 | 指向本文具体章节、记录编号或其它可追溯证据，不写空泛的“已验证” |
| `firmwareBaseline` | 是 | 至少包含 `cpu2` 或 `cpu3`，版本格式必须为 `Vx.x.x.x` |
| `summary` | 是 | 一句话写清已完成范围和仍未完成范围 |

状态含义：

- `passed`：资料内的适用测试项已经全部按通过标准执行并通过，不存在仍待执行的适用项。
- `failed`：至少一项已执行测试未达到通过标准，问题尚未闭环。
- `partial`：只完成了部分自动、台架、实机或现场项目；已完成部分可以有真实结果，但整份方案不能标为通过。
- `pending`：已经确定验证范围，但尚未形成可引用的执行结果。

## 4. 新鲜度判定

本机预览站读取元数据后，按以下顺序保守判定：

1. `failed` 始终显示“失败待处理”，不因日期更新而掩盖失败。
2. `pending` 显示“待执行”；`partial` 显示“部分完成”。
3. 元数据中的任一固件基线与 `流程证据清单.json` 当前基线不一致，显示“需要复验”。
4. 资料的 `executedAt` 早于它所覆盖任一核心流程的 `reviewedAt`，显示“需要复验”。
5. `passed` 但正文没有可执行测试矩阵或明确通过标准，显示“需要复验”，不能作为新鲜通过证据。
6. 只有 `passed` 同时满足结构、日期和固件基线要求时，才显示“新鲜通过”。
7. 没有元数据的历史资料显示“未记录”；即使正文出现“已执行”文字，也不从自然语言猜测结果。

共享基线和专项资料必须分开展示。共享资料可以说明仓库通用门禁或版本基线，但不能替代某个流程缺失的专项验证。

## 5. 检查与维护流程

- 日常运行 `py tools\check_validation_result_metadata.py`；该检查也包含在 `py tools\check_docs.py` 中。
- 历史资料可以暂时没有元数据，不因此阻断；一旦加入标记，JSON 语法、必填字段、日期、状态和版本格式必须全部合法。
- 完成新一轮测试后，先更新正式资料中的执行证据，再更新元数据；不要只改状态。
- 流程或固件变化导致旧证据过期时，不改写历史结果。新增验证记录或补充同一方案的复验章节，再把元数据更新到真实的新结果。
- `docs-site/` 只生成新鲜度视图，不保存验证结论，也不作为 Git 正式资料来源。
- 资料重命名时不得更换其稳定证据 ID；在 `验证证据登记清单.json` 更新当前路径并按需保留旧路径别名，使历史基线仍能回到同一份证据身份。

## 6. 当前迁移策略

先为证据充分、执行边界明确的最新版本方案补元数据；其余历史资料保持“未记录”，按后续真实复验逐步迁移。禁止为了提高覆盖率批量把包含“已执行”字样的旧资料标成 `passed`。
