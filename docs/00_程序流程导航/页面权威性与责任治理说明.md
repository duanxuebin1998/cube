# 页面权威性与责任治理说明

更新日期：2026-07-12

## 目的

本说明定义程序流程页面的权威来源、责任边界和治理队列口径，避免“页面已核对”被误读为“测试已通过”，也避免未映射源码、待执行用例、空批次或空基线分散在多个页面后无人负责。

## 单一权威来源

- `docs/` 是唯一正式文档源，流程正文、关系清单、验证工作包、运行记录、批次和交付基线都在该目录维护。
- `docs-site/` 是本机派生预览层，只负责同步、浏览、搜索、聚合和自动检查，不保存第二份业务关系或批准结论。
- `流程证据清单.json` 的 `governancePolicy` 是页面权威性与责任策略的唯一结构化来源；治理队列只从现有正式清单和当前工程事实派生。

## “已核对”的严格含义

“已核对”只表示流程页已按当前源码入口、关键语义、正式业务关系和固件基线完成静态复核。它不表示：

- 自动、台架、实机或现场用例已经真实运行；
- 已形成冻结范围、责任、窗口和退出条件明确的验证批次；
- 已建立可用于历史比较的交付证据基线；
- 已批准发布、现场放行或交付。

深层核心流程页必须同时展示正式来源与派生方式、内容责任、最近核对日期、适用固件基线、主源码入口、验证资料和未确认边界。

## 五类显式责任

| 责任 ID | 责任人 | 责任范围 |
| --- | --- | --- |
| `cpu2` | CPU2 固件责任人 | CPU2 源码行为、流程关系、状态与异常出口 |
| `cpu3` | CPU3 固件责任人 | CPU3 交互、通信、显示、参数与异常反馈 |
| `validation` | 测试执行责任人 | 自动、台架、实机、现场用例的真实运行与原始记录 |
| `delivery` | 交付决策责任人 | 验证批次、交付基线、退化解释与人工决策 |
| `docs` | 文档治理责任人 | 正式来源、关系映射、核对日期与派生页面一致性 |

未知项目不得猜测默认负责人。无法归入上述责任范围的项目应使生成或检查失败，由正式策略先补充边界。

## 六类持续治理检查

| 检查 | 机器事实 | 责任方向 | 清零含义 |
| --- | --- | --- | --- |
| 过期核对 | 最近核对日期超出策略窗口 | 文档治理与对应固件责任 | 当前无需重新核对，不代表测试通过 |
| 未映射源码 | 当前固件改动未映射到核心流程 | 文档治理与对应 CPU 责任 | 当前改动均可判断流程影响 |
| 缺专项证据 | 核心流程缺少专项验证关系 | 文档治理与对应 CPU 责任 | 关系完整，不代表真实执行 |
| 无真实运行 | 计划用例没有追加式运行记录 | 测试执行责任 | 有运行记录后仍需看真实结果 |
| 无验证批次 | 没有冻结验证范围和退出条件 | 测试执行责任 | 有批次不代表批次已接受 |
| 无交付基线 | 没有显式选择历史比较起点 | 交付决策责任 | 有基线不代表允许交付 |

六类检查必须始终显示。数量为零时标记为“当前清零”，不得隐藏检查，也不得把空白区域解释为完成。

截至 2026-07-12 当前派生快照为 9 个责任项：7 个决策阻断和 2 个需治理事项。六类检查数量分别为过期核对 0、未映射源码 12、缺专项证据 0、无真实运行 25、无验证批次 1、无交付基线 1。12 个未映射源码按 CPU2/CPU3 聚合为两个需人工判断的责任项；它们不是已确认的流程缺陷。25 个待执行用例按五份工作包形成五个真实运行阻断项。

## 四层证据边界

1. 静态核对：证明页面、源码入口、关键语义和正式关系已经复核。
2. 真实运行：证明工作包中的用例确实执行，并有稳定运行 ID 和原始记录。
3. 验证批次：冻结完整用例范围、固件基线、责任、窗口和退出条件，形成可审计里程碑。
4. 交付决策：基于批次、基线、退化解释和例外资料，由责任人作出显式人工判断。

上一层不能替代下一层。治理队列只分配责任、事实来源和下一步，不生成测试通过或交付批准。

## 生成与门禁

- `tools/update_flow_navigation.py --write` 从 `流程证据清单.json` 更新 18 个核心流程页的统一证据头，不手工复制责任策略。
- 本机预览站生成 `/start/governance-queue/` 和 `/data/governance-queue.json`，按责任组展示来源、当前事实、下一步和受影响对象。
- `docs-site/scripts/check-governance-queue.mjs` 检查六类状态持续存在、责任来自显式策略、18 个核心流程页字段完整，以及页面不产生未经证据支持的正向结论。
- `npm run check` 会重新同步后执行治理门禁；正式源与派生层、责任策略或证据边界漂移时失败关闭。
- `治理事项处置清单.json` 只追加责任接手和正式处置事件；关闭链、事实指纹和六类动作契约由 `治理事项闭环说明.md` 定义，不复制运行、批次、基线或流程关系。

## 维护规则

- 调整责任名称、范围、核对窗口或未确认边界时，只修改 `流程证据清单.json` 的 `governancePolicy`，并同步更新本说明。
- 上述当前数量是 2026-07-12 的工作区快照；日常状态以重新同步生成的 `/data/governance-queue.json` 为准，不手工回写本说明中的历史数字。
- 新增治理类型前必须先定义机器事实、责任来源、下一步和清零含义；不得只增加一个没有处置闭环的告警数字。
- 关闭治理项必须改变其权威事实来源，例如补映射、登记真实运行、创建批次或选择基线；不得在派生页面中手工隐藏。
- 当前事实存在但无正式事件时必须显示为“待接手”；活动事件对应的机器事实清零后必须追加关闭，已关闭事实再次出现时保留旧关闭依据并显示“重新出现”。
