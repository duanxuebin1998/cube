# 验证运行台账说明

验证运行台账把“已经写好测试计划”和“测试确实执行过”分开管理。正式来源是 `验证运行登记清单.json`；清单为空时，只能得出“尚无真实运行记录”，不能得出通过结论。

## 三层事实边界

| 层级 | 正式来源 | 能证明什么 | 不能替代什么 |
| --- | --- | --- | --- |
| 计划 | `验证工作包/` 中的可执行测试矩阵 | 用例、验证层、步骤、观测点和通过标准已定义 | 真实执行、原始数据和签字 |
| 运行 | `验证运行登记清单.json` | 哪个用例在什么基线、环境和时间执行，原始记录是否保持完整 | 工作包整体通过、交付批准 |
| 结论 | 工作包中的 `cube-validation-result` | 根据当前用例运行边界汇总出的工作包状态 | 发布安全、现场放行和负责人批准 |

## 追加式登记规则

- 每次运行使用稳定且唯一的 `run-...` ID；已有记录不得覆盖、复用或改写。
- `evidenceId` 必须引用正式验证工作包，`caseId` 和 `layer` 必须与该工作包矩阵一致。
- 同一用例允许多次运行。清单中最后追加的一次是该用例的当前结果，之前运行继续保留审计价值。
- `executedAt` 必须是含时区的 ISO 8601 时间，`decisionRevision` 必须是 40 位小写 Git revision。
- 原始记录只允许放在 `docs/` 下；PDF 不进入此契约。每份记录登记 SHA-256，内容变化后校验立即失败。
- 允许的单次结果是 `passed`、`failed`、`partial`、`blocked`。阻塞与部分完成都不能视为通过。
- 登记工具只追加调用者显式提供的事实，不自动制造运行 ID、结果或原始记录。

## 工作包状态派生

| 用例当前边界 | 工作包派生状态 |
| --- | --- |
| 没有任何用例运行 | `pending` |
| 任一用例当前为 `failed` | `failed` |
| 所有计划用例当前均为 `passed` | `passed` |
| 其余已有运行，包括 `partial`、`blocked` 或尚有待执行用例 | `partial` |

派生状态必须与工作包中的 `cube-validation-result.status` 一致。当前登记清单为空，因此五份验证工作包继续保持 `pending`。

## 登记与检查

先保存真实的日志、表格、文本记录或其他非 PDF 原始资料，再登记运行：

```powershell
py tools\register_validation_run.py `
  --id run-cpu2-05-wl-b01-20260712-01 `
  --evidence-id ev-wp-cpu2-05-water-level `
  --case-id WL-B01 `
  --layer bench `
  --outcome passed `
  --executed-at 2026-07-12T14:30:00+08:00 `
  --operator "测试负责人" `
  --environment "CPU2 水位台架，真实探头与空载电机" `
  --cpu2 V1.22.0.0 --cpu3 V1.21.0.0 `
  --revision 6dad8cd634a2cf576a77b78bf4b12fe14d60103e `
  --summary "三次重复运行终态、方向和位置结果一致" `
  --record docs/05_测试记录/对应原始记录.md `
  --dry-run
```

去掉 `--dry-run` 后才会原子追加。追加完成后，根据用例边界更新对应工作包的 `cube-validation-result`，再运行：

```powershell
py tools\check_validation_runs.py
py tools\check_docs.py
```

本机站点同步后可在“真实验证运行台账”页面查看计划用例、已运行用例、当前结果和仍待执行的验证层。

## 从运行进入验证批次

单次运行合法只证明一个用例在特定环境下形成了可追溯结果。需要判断一轮版本、台架、实机、现场或发布候选验证是否完整时，应在 `验证批次登记清单.json` 中冻结范围，并按 `验证批次与里程碑决策说明.md` 追加生命周期和关闭结论。未进入批次的零散运行不得解释为完整里程碑。
