2. 功能域业务总览 SVG

CPU3 主循环是显示端的调度中心。它不是 RTOS 任务，而是单个 while(1) 中按固定优先级轮询不同业务。

3.1 上电初始化到主循环

把 main() 中的 CubeMX 外设初始化和 App_Init 的应用初始化串起来，区分硬件层初始化和 CPU3 应用状态初始化。

应用初始化Application/app_main.c:367-381 显示 Logo、初始化 RTC、从 FRAM 读取 CPU3 本机参数、重配串口、初始化 DSM 通信。

3.2 App_MainLoop 调度优先级

主循环先处理串口重配置、SI 周期任务、显示和三路外部 COM；完成这些工作后检查 CPU2 的 100 ms 调度门限。门限能防止持续外部流量永久饿死轮询，但同步请求自身仍可阻塞 1000 ms。

调度顺序Application/app_main.c:387-539 依次处理串口重配、SI 周期任务、Display_Task 和 COM1/COM2/COM3，再检查 CPU2 的 100 ms 调度门限。
门限边界Application/app_main.c:529-538 只在主循环可继续运行时检查门限；CPU2 同步请求执行期间不保证实际轮询间隔，did_work 为 0 时仅延时 1 ms。
协议分发Application/app_main.c:342-360 根据端口参数选择 DSM/Wartsila/SI/LTD 协议处理函数。

4. 问题点与优化建议

1. CPU2 轮询是同步阻塞等待响应

CPU2_CombinatePackage_Send 内部使用 CPU2_RESPONSE_TIMEOUT_MS=1000ms 同步等待 wait_response；轮询期间外部 COM 和显示刷新都会被主循环阻塞。

建议：把 CPU2 轮询改成非阻塞状态机，发送完成、接收完成和超时分别推进状态。

Communication/internal/main_board_modbus/cpu2_communicate.c:621

2. 100 ms 门限不是实时最大轮询间隔

持续外部流量不会再永久饿死 CPU2 轮询，但外部协议处理发生在门限检查前，CPU2 同步请求本身也可阻塞 1000 ms，因此实际请求起始间隔可能明显超过 100 ms。

建议：把 CPU2 请求改成非阻塞状态机，并在持续外部流量和断线场景记录实际最坏轮询间隔。

Application/app_main.c:387-539

3. 1 ms 空闲节拍的实机负载尚未量化

主循环空闲延时由约 100 ms 缩短为 1 ms 后，显示任务、SI 自动调度和 RTC 检查频率明显提高；静态检查和构建不能证明 CPU 占用、OLED 刷新或看门狗余量满足现场要求。

建议：在空闲、持续外部流量、CPU2 离线和菜单刷新场景记录 CPU 占用、OLED/RTC 访问频率和看门狗状态。

Application/app_main.c:387-539

4. 串口重配依赖三路端口完全空闲

g_cpu3_uart_reinit_pending 在任一端口收发忙或 pending 时直接返回，如果端口持续有流量，重配可能长期不生效。

建议：显示重配等待状态，增加超时或维护窗口机制，避免用户以为参数已应用。

Application/app_main.c:182-221

5. 启动延时固定 1000ms

App_Init 最后固定 HAL_Delay(1000)，没有和外设实际就绪状态绑定。

建议：如果现场启动时间敏感，可以改为检测显示/串口/CPU2 首次响应条件。

Application/app_main.c:379-381
