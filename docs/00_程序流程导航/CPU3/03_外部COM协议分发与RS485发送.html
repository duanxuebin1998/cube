外部 COM 是 CPU3 对上位系统的主要入口。统一管理帧不依赖当前业务协议，未命中管理帧时才按端口配置选择业务协议。

3.1 三路 COM 收帧与协议分发

COM1/COM2/COM3 都先识别统一管理帧；命中后直接生成独立 ACK 或异常响应，未命中才读取当前协议并进入 DSM/Wartsila/SI/LTD 业务处理器。

统一管理帧入口Application/app_main.c:552 先调用 ProtocolSwitchFrame_Process；命中后不再进入当前业务协议。
切换帧解析Communication/common/protocol_switch_frame.c:45 校验固定帧、站号、目标协议和 CRC，并生成与请求不同的独立 ACK 或异常响应。
业务协议表Application/app_main.c:330-340 g_handlers 将 DSM、Wartsila、SI、LTD 分别绑定到处理函数；仅管理帧未命中时使用。

3.2 挂起串口重配安全点

CPU3 菜单或参数写入可能只置位 UART 重配请求；真正重配在 App_MainLoop 开头执行，且必须确认三路外部 COM 没有接收就绪、发送忙和 pending 待发帧。

安全条件Application/app_main.c:182-205 cpu3_apply_uart_reinit_if_pending 依次检查接收 ready、发送 busy 和 pending_len。
调度位置Application/app_main.c:398-405 App_MainLoop 在 Display_Task 和 COM 分发之前先处理挂起重配。
重配动作Application/system_param/cpu3_comm_display_params.c:790 Cpu3_ReinitAllUarts 根据本机通信参数重配三路外部 COM。

3.3 DMA 发送、pending 队列与回接收

发送通道忙时只缓存一帧 pending；续发失败会取消待切换状态。切换 ACK 最后一帧完成后，中断只标记 APPLY 并保持 RX 停止，主循环再保存并重配当前端口。

发送完成Application/app_main.c:795 TxCplt 回调先续发 pending；最后一帧完成后才把切换状态标记为 APPLY。
主循环应用Application/app_main.c:478 在非中断上下文保存目标协议、套用标准串口参数并只重配当前端口。
错误恢复Application/app_main.c:662-700 ErrorCallback 对三路外部 COM 和 UART5 分别恢复。

4. 问题点与优化建议

1. pending 队列只有一帧且覆盖旧帧

外部请求密集时，新响应会覆盖旧 pending，虽然有覆盖计数，但上位机只会丢响应。

建议：将单帧 pending 改成环形队列，或在忙时直接返回设备忙异常帧。

Application/app_main.c:226-279

2. 协议号依赖枚举连续作为数组下标

g_handlers 用 COM_PROTO_* 作为数组下标，若枚举不连续或后续新增值未同步表项，会进入不回包路径。

建议：改成 switch 分发或增加编译期断言/默认错误响应。

Application/app_main.c:318-360

3. UART_TX_POST_DELAY_LOOP 是固定空转延时

发送完成后用固定 NOP 循环等待 RS485 电平方向恢复，和主频/优化级别相关。

建议：优先使用 TC 标志或定时器，固定循环只作为最后兜底。

Application/app_main.c:18-31

4. 串口重配可能被持续外部流量推迟

重配只在三路接收 ready、发送 busy 和 pending 都为空时执行；如果外部请求持续不断，g_cpu3_uart_reinit_pending 会一直保留。

建议：增加重配延期计数或维护窗口，在现场能看到串口参数已保存但尚未生效的原因。

Application/app_main.c:182-205
