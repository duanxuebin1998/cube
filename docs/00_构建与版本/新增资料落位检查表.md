# 新增资料落位检查表

更新日期：2026-06-27

本文用于新增、移动或重命名文档资料前快速判断放置位置、维护来源和需要同步的索引。它是人工检查表，不改变 skill 生成版本文档、固件升版、`CHANGELOG.md` 或程序流程图更新规则。

## 使用边界

- 正式文档源只有 `docs/`。
- 不新增、不恢复 `LTD_MAIN_CPU2/docs/` 或 `LTD_DISPLAY_CPU3/docs/`。
- `docs-site/` 只作为本地预览工具，不作为资料来源，不纳入 Git 跟踪。
- `tmp/` 只作为本地渲染、抽取或检查缓存，不作为资料来源，不纳入 Git 跟踪。
- 默认不生成、不检查、不同步 PDF；只有明确交付 PDF 时才处理。
- 版本发布仍按既有 skill 规则新增 `docs/00_构建与版本/版本改动与测试/` 文档，并同步 `CHANGELOG.md`、协议记录和必要流程资料。

## 第一步：先判断来源

| 新资料来源 | 处理方式 |
| --- | --- |
| skill 生成的新版本文档 | 保持生成到 `docs/00_构建与版本/版本改动与测试/`；本表只用于提交后补索引或补引用 |
| 人工新增 Markdown | 先按业务域落位，再更新对应 README 或专题索引 |
| 移动或重命名既有资料 | 先搜索旧路径引用，再更新迁移映射表和入口索引 |
| 外部原始资料、芯片手册、标准文档 | 放到对应 `00_原始资料/`、`00_外部资料/` 或芯片手册目录；不要改写原件 |
| 现场附件、表格、日志、压缩包 | 放到对应测试、问题、协议或界面目录；README 必须说明用途和权威性 |

## 第二步：按业务域落位

| 资料主题 | 首选位置 | 同步检查 |
| --- | --- | --- |
| CPU2/CPU3 程序流程、状态机、业务链路 | `docs/00_程序流程导航/` | `流程排查入口.md`、CPU2/CPU3 流程 README、相关 HTML/SVG |
| 构建说明、版本发布、参数存储升级、故障码 | `docs/00_构建与版本/` | `版本总览.md`、`CPU2参数存储升级清单.md`、故障码 README |
| CPU2/CPU3 共享协议、寄存器、DSM、SI | `docs/01_协议与寄存器/` | `CPU2_CPU3协议变更记录.md`、协议 README、相关源表说明 |
| 新需求、未实现方案、已实现需求依据 | `docs/02_需求与计划/` | 已实现/未实现 README，必要时回链版本方案 |
| 问题现象、原因分析、整改方案、风险复查 | `docs/03_问题分析与整改/` | `问题专题索引.md`、关联测试记录、必要流程页 |
| CPU3 菜单、状态页、显示文案、屏幕资料 | `docs/04_界面与菜单/` | 菜单 README、状态矩阵、字库和显示空间检查记录 |
| 实测记录、联调结果、串口日志、现场附件 | `docs/05_测试记录/` | 版本验证/问题复测/现场记录 README，回链问题或版本资料 |
| SIL、MISRA/CERT、功能安全外部资料 | `docs/06_SIL功能安全认证/` | SIL README、外部资料 README、`资料用途矩阵.md` |
| 硬件原理图、芯片手册、固件硬件对照 | `docs/07_硬件原理图/` | 硬件 README、原始资料 README、固件硬件对照文档 |

## 第三步：按文件类型定维护口径

| 文件类型 | 默认定位 | 必须补充的说明 |
| --- | --- | --- |
| `.md` | 可维护正文 | 写清依据、版本范围、验证方式和未确认项 |
| `.html` | 流程图、结构图或历史阅读页 | README 标明阅读入口；长期结论回到 Markdown |
| `.xlsx` | 参数表、寄存器表、故障码表或状态矩阵 | README 标明是否是维护表、对应代码和冲突时权威来源 |
| `.docx` | 确认稿、菜单稿、现场记录或历史源文件 | README 标明是否只读，必要时补 Markdown 摘要 |
| `.pdf` | 外部资料、原始图纸、标准、芯片手册或导出版 | 默认只读；同主题 Markdown 存在时写清以 Markdown 为准 |
| `.DAT`、`.txt`、`.zip` | 原始日志、外部包或现场证据 | 保留原始性；README 写清采集时间、对象和结论归属 |

## 第四步：判断要不要更新索引

| 情况 | 需要更新 |
| --- | --- |
| 新增一级或二级业务入口 | 对应目录 `README.md` |
| 新增版本发布资料 | `版本总览.md` 可后补；不得阻塞 skill 正常生成版本文档 |
| 新增附件或源表 | `附件与源文件清单.md` 或所在目录 README |
| 新增流程页或流程跳转 | `docs/00_程序流程导航/README.md`、`流程排查入口.md` |
| 新增问题闭环资料 | `docs/03_问题分析与整改/问题专题索引.md` |
| 新增 SIL 外部资料 | 所在外部资料 README，必要时更新 `资料用途矩阵.md` |
| 移动或重命名资料 | `文档库迁移映射表.md` 和所有旧路径引用 |

## 第五步：提交前最小复核

1. 确认新资料没有放入 CPU2/CPU3 子项目 `docs`。
2. 用 `rg` 搜索旧路径、旧文件名和关键标题，确认活文档入口已经更新。
3. 如果新增附件不是 Markdown，在 README 写清用途、权威性和是否维护。
4. 如果涉及协议、参数、显示、版本或安全边界，同步检查对应专项文档和 `CHANGELOG.md`。
5. 资料迁移、目录整理或链接修改后，运行 `py tools\check_docs.py` 做仓库本地快速自检；该脚本不生成文档，也不改变 skill 的版本文档生成规则。
6. 运行 `git diff --check -- <目标文件>` 检查行尾空白和冲突标记。
7. 准备提交大批量迁移时，再运行 `py tools\check_docs_staging.py` 检查暂存区一致性；普通新增资料或 skill 生成版本文档不需要先跑它。
8. 需要本地预览时，在 `docs-site/` 运行 `npm run check`；构建结果不提交。

## 不应做的事

- 不因为新增资料而手工维护 `docs-site/src/content/docs/` 或 `docs-site/public/archive/`。
- 不把 `tmp/` 里的渲染、截图、抽取文本或 PDF 处理缓存当作正式资料提交。
- 不恢复旧 `site/` 站点输出或旧静态站生成脚本作为维护入口。
- 不把人工索引当作版本发布的强制前置条件。
- 不批量删除外部 PDF、DOCX、XLSX 或现场原始记录。
- 不把同一主题拆到多个业务目录；必须拆分时，在 README 写清主入口。
