## 暂存建议

当前工作区存在大量 `MM`、`AM` 和重命名状态。提交前不要直接沿用旧暂存区，应按最终提交范围重新检查，只暂存已确认属于本次提交的目标文件：

1. 先确认本次是否只提交文档迁移，不混入固件代码、工具脚本或临时目录变更。
2. 若提交文档迁移，应包含 `AGENTS.md` 仓库级边界、`docs/` 下迁移后的目标文件、对应 README、治理索引、`.gitignore` 中 `docs-site/` 和 `site/` 忽略规则，以及旧 `LTD_MAIN_CPU2/docs/`、`LTD_DISPLAY_CPU3/docs/` 删除/重命名记录。
3. 不暂存 `docs-site/` 生成内容、`site/` 旧输出、`tmp/` 临时渲染或 PDF 处理缓存，也不恢复旧静态站脚本。
4. 不暂存或修改 `C:\Users\admin\.codex\skills`，本次文档整理不依赖 skill 本体变更。
5. 如果同一文件显示 `MM` 或 `AM`，提交前先运行 `py tools\check_docs_staging.py --closure-plan` 看从当前状态到最终复核的顺序路线和每步通过口径，再运行 `--decision-checklist` 看总决策顺序，再运行 `--final-check` 看当前能否进入最终暂存前人工确认，再运行 `--remaining-checklist` 看剩余阻塞收口分组和人工决策分组，需要保存当前状态快照时运行 `--write-local-audit` 生成 `tmp/docs-migration-audit.md`，再运行 `--staging-plan` 看手动收口顺序，再运行 `--gate-matrix` 看必须收口、可随迁移、必须单独判断和后续版本文档输出区边界，再运行 `--submit-plan` 看文档迁移、固件/构建、版本/发布记录、后续版本文档输出区和本地输出清理的拆分批次，再运行 `--audit` 看提交范围分组，再运行 `--summary` 看总体数量和“建议处理顺序”，再运行 `--mixed-plan` 按治理文档和固件相关文档分组制定收口动作，再运行 `--mixed-matrix` 逐项核对分类、已暂存/未暂存规模和建议处理动作，再运行 `--mixed-resolution-check` 确认分批模板完整覆盖全部混合文件，再运行 `--mixed-boundary-check` 确认治理文档进入迁移候选且固件相关混合文档已从纯文档迁移候选排除，再运行 `--submit-boundary-check` 确认 `migration-submit` 候选未混入固件/构建、版本/发布记录、后续版本文档输出区、本地输出或其他路径，再运行 `--mixed-closure-audit` 汇总混合文件覆盖率、提交边界和版本输出契约状态，再运行 `--version-output-contract` 确认后续版本文档输出区不进入本次迁移候选且不影响 skill 继续生成新方案，再运行 `--mixed-resolution-plan` 生成分批核对模板；其中治理文档批次可给出 `git add`，固件相关混合文档只输出 diff 核对命令、不自动给出 `git add`；最后运行 `--mixed-details` 查看完整“已暂存/未暂存”增删规模；需要逐个复制检查命令时运行 `--mixed-commands`，用输出的 `git diff --cached -- <file>` 和 `git diff -- <file>` 确认暂存内容包含最新整理结果。
6. `py tools\check_docs_staging.py` 是提交前专用检查，不放入日常 `py tools\check_docs.py`，避免影响 skill 后续生成新版本文档；当前工作区混合状态下它会提示风险，只有治理文档混合项已收口、固件相关混合文档已分离判断、最终目标范围已按人工确认暂存后才应通过。
7. 该检查只读 Git 状态，不生成、不移动、不删除文档；普通 skill 版本提交只需继续把新方案写入 `docs/00_构建与版本/版本改动与测试/`，不需要先整理人工索引或运行迁移暂存检查。
8. 提交范围建议中的“建议随迁移提交保留删除记录”用于旧 CPU docs 和旧静态站脚本删除；“本地输出清理记录，提交前确认是否单独处理”用于 `docs-site/`、`site/` 或 `tmp/` 的已暂存删除，不代表后续版本文档生成需要处理这些本地目录。
9. 需要复制路径清单时使用 `--list`：`mixed-docs-governance` 对应可随文档迁移收口的混合治理文档，`mixed-firmware-docs` 对应需随固件改动判断的混合文档，`migration-submit` 对应本次文档迁移提交候选集合且会排除 `mixed-firmware-docs` 中的已知固件相关文档和 `version-outputs` 中的后续版本文档输出区，`migration-add` 对应实际可传给 `git add --pathspec-from-file` 的现存文档迁移路径和文档检查工具，`docs-migration` 对应正式文档迁移主体，`docs-check-tools` 对应本次新增检查工具，`migration-removals` 对应旧 CPU docs 和旧静态站脚本删除记录，`firmware-or-build` 对应源码、流程生成脚本和构建相关路径，`release-records` 对应 `CHANGELOG.md`、`CHANGELOG.pdf` 这类版本/发布记录路径，`version-outputs` 对应 `docs/00_构建与版本/版本改动与测试/` 下由版本提交流程或 skill 生成的新方案，`other` 对应仍未归类的路径；`--list` 的退出码固定为 0，仅表示路径清单已输出，迁移是否收口仍看 `--summary` 或完整检查。
10. 需要生成可复制暂存模板时使用 `--stage-commands`；若仍有 `AM/MM` 混合文件，该模板会先输出 `--mixed-plan` 分组收口计划、`--mixed-matrix` 逐项矩阵、`--mixed-resolution-check` 覆盖率预检、`--mixed-boundary-check` 混合文件提交边界检查、`--submit-boundary-check` 迁移候选边界检查、`--mixed-closure-audit` 收口审计、`--version-output-contract` 版本输出契约检查、`--mixed-resolution-plan` 分批核对模板和 `--mixed-details` 诊断命令，其中治理文档批次可暂存，固件相关混合文档只核对 diff、不自动给出 `git add`。随后模板会先输出 `--remaining-checklist`，用于在路径文件和 `git add --pathspec-from-file` 前复核是否仍有阻塞收口项或人工决策项，再输出 `--write-local-audit` 生成 `tmp/docs-migration-audit.md` 本地快照；如果当前存在固件/构建、版本/发布记录、后续版本文档输出区或其他路径，模板会先输出对应 `--list` 核对命令，再创建 `tmp/`、导出 `migration-add` 路径文件，并给出 `git add --pathspec-from-file=tmp\docs-migration-add.paths` 暂存可执行候选集合的命令。命令本身不会自动执行，执行前仍需人工确认混合文件和非迁移路径已经分离；包含旧 CPU docs/旧静态站脚本删除记录的 `migration-submit` 只用于审计，不直接作为 `git add` 输入。
11. 提交范围审计中的“固件或构建相关路径”“版本或发布记录路径”“后续版本文档输出区路径”和“其他路径”需要单独判断是否属于本次提交；不要因为它们出现在工作区就自动混入文档迁移提交。

## 不作为阻塞项

- `py tools\check_docs.py` 只用于文档迁移和目录整理复核；其中同名 Markdown/PDF、人工索引新鲜度和 README 超过 60 行只做提示，不改变 skill 后续生成版本文档的规则。

- 文档整理本身不要求升级 CPU2/CPU3 固件版本。
- 默认不重新生成 PDF；除非明确需要交付 PDF。
- 外部 PDF、DOCX、XLSX、DAT、ZIP 附件不因未转换成 Markdown 而阻塞提交，但必须在 README 或附件清单中说明用途和权威性。
