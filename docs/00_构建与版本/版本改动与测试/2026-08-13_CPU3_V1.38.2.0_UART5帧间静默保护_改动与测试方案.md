# CPU3 V1.38.2.0 UART5帧间静默保护改动与测试方案

## 1. 文档目的和适用版本

本文用于复核和验证CPU3到CPU2内部UART5 Modbus相邻事务帧间静默保护。适用CPU3版本为`V1.38.2.0`，基线为`V1.38.1.1`；CPU2保持`V1.39.1.0`。

## 2. 版本与兼容性

- CPU3：`V1.38.1.1 -> V1.38.2.0`（PATCH）。
- CPU2：保持`V1.39.1.0`。
- 共享协议：`DEVICE_PROTOCOL_VERSION=33`，不变。
- 参数存储：CPU2 `DEVICE_PARAM_VERSION=3`、CPU3 `CPU3_PARAM_VERSION=0x0007`，均不变；参数结构、字段偏移、CRC和FRAM布局不变，升级不会恢复出厂或清除现场参数。
- 兼容性：不改变FC03、FC04、FC10帧形、寄存器、命令、ACK或异常响应；只增加CPU3主站发起下一事务前的时序保护，CPU2无需修改。

程序流程资料在本机同步更新，不纳入Git：CPU3内部通信页需要在统一发送步骤中体现“等待上一响应后的3 ms毫秒门限，再切发送方向”。

## 4. 详细改动

### 4.1 统一保证相邻事务帧间静默

- 源码位置：`cpu2_communicate.c`的`CPU2_CombinatePackage_SendWire()`、`CPU2_WaitInterframeGap()`和`sendToCPU2()`；调用链为周期轮询/外部写入到统一UART5发送入口。
- 改前问题：上一笔CPU2响应结束后，下一笔参数FC10可能立即切换RS485发送方向并启动TX DMA；现场原CPU2板在该边界偶发无ACK，CPU3等待1秒后使参数快照失效并显示“正在读取参数”。
- 具体改法：响应等待退出后记录`HAL_GetTick()`；下一笔事务在切发送方向前等待节拍差达到3 ms。首次事务没有有效历史时刻，直接发送。
- 必查边界：首次事务、正常响应、超时、UART错误、节拍回绕、周期读取后紧接FC10、参数FC10后紧接命令FC10以及CPU2断链恢复。
- 通过标准：所有发送路径先完成统一等待再切方向；修复后物理层上一响应结束至下一请求起始不少于1.75 ms。

### 4.2 保持失败与重试语义

- 源码位置：`CPU2_CombinatePackage_SendWire()`既有响应超时、失败记录、参数快照失效和恢复逻辑。
- 改前问题：若通过自动重发FC10规避丢ACK，可能在CPU2已经执行但ACK丢失时重复写入或重复动作。
- 具体改法：不增加FC10自动重发，不改变1秒响应超时、连续失败计数、参数补读和命令确认位；只修正请求前的总线静默边界。
- 必查边界：CPU2已执行但ACK丢失、合法异常响应、接收长度0、参数快照已经失效时的本地Busy，以及恢复后的首次事务。
- 通过标准：既有通信超时和带参事务契约继续通过；失败时仍按原规则返回Busy或失败，不重复发送动作命令。

## 5. 数据流和异常闭环

外部LTD带参命令先经CPU3写参数槽FC10，ACK成功后再写命令寄存器FC10。每笔板间事务统一执行“等待帧间门限→切发送方向→启动TX DMA→等待响应→解析或超时→记录响应结束时刻”。参数写失败仍使完整参数快照失效，随后本地Busy和“正在读取参数”提示语义不变。

## 6. 测试环境与前置条件

- 静态与构建：Windows、Python、CMake、Ninja、ARM GCC。
- 台架：原故障CPU2 V1.39.1.0协议33、CPU3 V1.38.2.0协议33候选、COM5 LTD地址129/4800 8N1、COM12 CPU3打印115200 8N1。
- 波形：同步观察CPU3 UART5 TX、CPU3方向脚、CPU2 UART5 RX和CPU2方向脚。

## 10. 风险与未验证项

- 毫秒级ST-LINK采样没有观察到失败FC10且CPU2未生成ACK，但不能绝对证明物理线上未出现短帧；根因仍需逻辑分析仪闭环。
- 原CPU2与新CPU2表现不同，说明板级裕量影响复现概率；当前不能确定收发器、方向控制、供电、终端偏置、焊接或时钟中的具体硬件层原因。
- 尚未烧写最终CPU3候选，也未执行RS485压力、长期运行、故障注入、现场或SIL验证。构建和静态契约只证明源码形状与可编译性。
