## 1. 文档目的与当前结论

本版本处理两类运行时缺口：CPU2 TIM4原约2秒节拍使IWDG在一次中断重叠后只能等待较长时间再补喂；CPU2持久参数FC10入口缺少基于完整运行上下文的最终写权限裁决，CPU3屏幕、LH和通用桥接的预检查规则也不统一。

当前代码把CPU2监督节拍细化为250毫秒，同时以8分频保持继电器、AO和UART恢复业务约2秒周期；持久参数写入改为“CPU3保守预检查、CPU2最终裁决”，持续态、未知态、活动/待执行命令和自动故障恢复期间均拒绝。双端clean-first构建和相关静态契约已通过，但尚未完成目标板IWDG时序、真实FRAM故障和各外部协议写入矩阵测试。

## 4. 详细改动

### 4.1 CPU2 IWDG监督节拍细化并保持原业务周期

- 源码位置：`Core/Src/tim.c`的`MX_TIM4_Init()`、`Core/Src/stm32f4xx_it.c`的`TIM4_IRQHandler()`及`LTD_MAIN_CPU2.ioc`；链路为`TIM4更新事件 -> RETTOBASE判定 -> IWDG刷新/业务8分频`。
- 改前问题：TIM4约2秒触发一次；一次与其它ISR瞬时重叠会跳过喂狗，下一次补喂要再等待约2秒，接近标称约4秒IWDG窗口，时钟偏差和中断抖动可能压缩余量。
- 具体改法：TIM4 `Period`由10000改为1249，形成约250毫秒节拍；新增`CPU2_TIM4_BUSINESS_DIVIDER=8`和计数器。每个250毫秒节拍只在`RETTOBASE`表明没有其它活动ISR时刷新IWDG；继电器、AO刷新请求和UART恢复仅每8次执行一次，继续保持约2秒周期。
- 必查边界：计数0/7/8、计数回卷、瞬时ISR重叠、持续高优先级ISR占用、LSI快慢角、正常长业务、继电器延时、AO保持和UART恢复超时。
- 通过标准：源码和IOC均为`Period=1249`；业务分频常量为8；clean-first构建通过；目标板上TIM4约250毫秒，三类业务约2秒，瞬时重叠后能在后续健康节拍补喂，持续ISR占用不能被TIM4继续掩盖。

### 4.2 CPU2持久参数写入最终运行上下文门禁

- 源码位置：`Services/ParamStorage/system_parameter.h`的`DeviceState_AllowsPersistentParamWrite()`和`DeviceContext_AllowsPersistentParamWrite()`；`Services/Modbus/hostcommu_modbus.c`的`PersistentParamWriteRuntimeAllowed()`与`Response10Process()`；`Application/Src/fault_recovery.c`的`FaultRecovery_IsActive()`。
- 改前问题：只要FC10地址和值形状通过，持久参数候选即可进入后续应用和保存；设备运行、命令排队或自动故障恢复期间缺少统一最终裁决，可能在非空闲上下文改变运行参数。
- 具体改法：只显式列出待机和确认空闲的完成态；持续态、预留态和未来新增状态默认拒绝。普通完成态还要求`current_command==CMD_NONE`、待执行`g_deviceParams.command==CMD_NONE`且`error_code==NO_ERROR`；`STATE_ERROR`忽略具体错误码，但必须命令队列为空且`FaultRecovery_IsActive()==false`。拒绝时FC10返回`0x90/0x06`，不进入参数候选应用。
- 必查边界：待机、每个白名单完成态、`STATE_FLOWOIL`、`STATE_FOLLOW_WATERING`、`STATE_SPTESTING`、保留态、未知态、当前命令非空、待执行命令非空、普通完成态带错误码、错误态恢复活动/停止、非持久命令和AO仿真写。
- 通过标准：所有持久参数写均经过CPU2最终门禁；拒绝响应为标准设备忙`0x06`，RAM参数、寄存器镜像、硬件副作用和FRAM保存代次均不变化；非持久命令/仿真写不被错误套用此门禁。

### 4.3 CPU3屏幕、通用桥接和LH使用同源保守预检查

- 源码位置：`Application/system_param/system_parameter.h`的状态白名单；`Application/display/display_tankopera.c`的`state_allows_param_write()`；`Communication/internal/main_board_modbus/cpu2_communicate.c`的`CPU2_CombinatePackage_Send()`；`Communication/external/lh_modbus/lh_modbus_slave.c`的LH FC10入口和持久化等待。
- 改前问题：屏幕使用“待机或任意0x80xx且排除少数持续态”的开放规则，未来新增0x80xx状态可能被默认放行；通用桥接可绕过屏幕规则；LH又只接受待机，三条路径口径不一致。
- 具体改法：CPU3复制与CPU2一致的显式状态白名单，屏幕和LH调用同一helper；通用CPU2写接口由直发Wire改走公共入口，对触及持久参数的范围执行预检查。CPU3只负责按最近状态快照提前拒绝明显不安全请求，CPU2仍根据命令队列、错误码和自动恢复做最终裁决。
- 必查边界：CPU3快照新鲜/滞后、CPU2通信不可用、白名单完成态、持续态、错误态、未来未知态、菜单写、LTD/DSM/Wärtsilä/SI桥接和LH单字段FC10。
- 通过标准：三条CPU3路径对白名单状态结论一致；未知和持续态不发送持久参数写；CPU3预检放行但CPU2上下文不允许时仍由CPU2返回失败，CPU3/外部主机不得报告成功。

### 4.4 LH错误态参数修正与持久化确认边界

- 源码位置：`Communication/external/lh_modbus/lh_modbus_slave.c`的`lh_write_holding_field()`、`lh_handle_write_holding()`和`lh_wait_parameter_persisted()`。
- 改前问题：LH只接受待机，并且写入ACK后只要CPU2仍处于错误态且错误码非零就立即失败；这会阻断“自动恢复已停止、命令队列空闲时修改持久参数以排除配置问题”的维护路径。
- 具体改法：LH入口改用状态白名单；写入后不再仅凭错误态提前终止，而是继续以CPU2是否接受写、持久化完成代次是否变化、目标字段回读是否一致作为结果依据。
- 必查边界：错误态且恢复活动、错误态且恢复停止、CPU2拒绝、CPU2 ACK后FRAM失败、完成代次超时、回读一致/不一致、同值重写。
- 通过标准：恢复活动时CPU2最终拒绝；真正空闲错误态可用合法参数修正；LH只有在完成代次推进且回读一致时返回成功，通信失败、超时或回读不一致仍失败。

### 4.5 全量问题资料去重和状态统一

- 文档位置：`docs/03_问题分析与整改/未处理/`的全量总账、专项报告和README，以及`docs/03_问题分析与整改/问题专题索引.md`。
- 改前问题：不同历史报告使用P0/P1、CUBE日期编号和文字状态，重复问题可能被多次计数；部分代码已落地项仍被写成完全未处理，台架缺口与代码缺口混在一起。
- 具体改法：用C-01～C-45作为代码问题稳定编号，R-01～R-05记录受控偏差/待决策，B-01～B-10记录硬件和证据缺口，F-01～F-21记录已关闭或明确不整改项；专项报告和索引改为引用稳定编号，并保留历史快照边界。
- 必查边界：同一根因跨多个专项报告、代码已改但未台架、历史文档中的旧版本事实、HTML阅读版与Markdown维护源、PDF是否误纳入。
- 通过标准：Markdown链接无缺失；索引可回到权威条目；“代码已改待验证”不写成“已闭环”；未跟踪PDF不进入暂存区。

## 5. 跨CPU写入闭环

```text
屏幕 / LH / DSM / Wärtsilä / SI / LTD
  -> CPU3识别是否触及CPU2持久参数
  -> CPU3按最近设备状态白名单做保守预检查
  -> CPU2接收FC10并识别持久参数范围
  -> CPU2按状态、当前命令、待执行命令、错误码、自动恢复上下文最终裁决
     -> 拒绝：0x90/0x06，不应用、不请求保存
     -> 放行：沿用现有候选解析、运行态应用、保存请求和ACK语义
  -> LH额外等待保存完成代次变化并回读目标字段一致
```

CPU3预检查不是权限证明。CPU3状态快照可能滞后，因此任何CPU3放行都必须再次经过CPU2最终门禁；CPU2拒绝结果必须沿调用链返回，不能被菜单或外部协议转换成成功。

## 9. 风险与未验证项

1. 250毫秒TIM4只缩短监督采样和补喂间隔，不等于CPU2已有完整主循环健康票据；线程态阻塞仍不能仅靠`RETTOBASE`识别。
2. CPU3只掌握最近一次CPU2状态快照，无法判断CPU2当前命令队列和自动故障恢复是否已经变化；安全性依赖CPU2最终门禁。
3. 错误态允许修正参数是有条件的维护能力，不表示错误已清除；参数写成功后仍需按故障恢复规则重新验证设备。
4. 普通CPU2 FC10仍沿用现有“请求保存后ACK”语义；LH额外等待保存代次并回读。FRAM失败时CPU2 RAM可能已是新值但重启恢复旧值，此残余风险未由本次门禁修复。
5. 当前证据为静态契约、文档检查和双端构建，不构成真实RS485、FRAM、IWDG、AO、继电器或现场PLC闭环。
