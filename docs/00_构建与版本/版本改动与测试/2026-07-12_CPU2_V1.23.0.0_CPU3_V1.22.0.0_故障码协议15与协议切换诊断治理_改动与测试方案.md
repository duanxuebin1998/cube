# CPU2 V1.23.0.0 / CPU3 V1.22.0.0 故障码协议15与协议切换诊断治理改动与测试方案

## 1. 文档目的和适用版本

本文用于复核和验证本次整机版本提交，适用CPU2 `V1.23.0.0`、CPU3 `V1.22.0.0`和CPU2/CPU3共享协议15。本文件随本次提交纳入，提交哈希以Git记录为准。

## 2. 版本与兼容性

- CPU2：`V1.22.0.0 -> V1.23.0.0`（新增故障诊断能力，MINOR）。
- CPU3：`V1.21.0.0 -> V1.22.0.0`（新增协议切换与故障显示能力，MINOR）。
- 共享协议：`14 -> 15`。既有故障码按责任域重编号，协议15与14及更早版本的故障数值解释不兼容，CPU2/CPU3必须成对升级。
- CPU2参数存储：`DEVICE_PARAM_VERSION` 保持3；`DeviceParameters`结构、`struct_size`、FRAM A/B槽和CRC范围不变，不会因本次升级恢复出厂参数。现场升级前仍应导出参数，升级后复核关键测量、传感器和AO参数。
- CPU3本机参数存储布局不变；协议切换保存沿用既有存储结构，新增写后读回校验。

## 3. 提交范围

- CPU2：故障管理与恢复、测量入口、TMC5130、AD5421、AO输出、电机控制、参数存储、传感器/无线通信和错误日志。
- CPU3：外部COM分发、协议切换帧、本机通信参数保存/重配、故障显示和共享故障码定义。
- 工具：故障码及专项契约、协议切换主机测试、流程导航、交付证据、验证工作包、运行台账、批次、治理事项、交付基线与跨版本知识治理。
- 文档：故障码治理、协议变更、外部COM切换、流程HTML/SVG、验证证据清单和版本发布资料。
- 排除项：`outputs/`、`build/`、`docs-site/`及PDF生成物不进入提交。

## 4. 详细改动

### 4.1 共享故障码升级到协议15

- 源码位置：CPU2和CPU3 `system_parameter.h` 的 `ErrorCode`、`DEVICE_PROTOCOL_VERSION`；消费链路为CPU2故障出口到共享寄存器，再到CPU3显示。
- 改前问题：故障码历史分类交叉、跳号且部分底层原因只能映射为大类错误，CPU2和CPU3难以按责任域一致定位。
- 具体改法：固定11至19九个责任域，新增 `MOTOR_TMC_CONFIG_LOST`、`COMM_UART_TRANSFER_ERROR`、`WIRELESS_RESP_FORMAT_ERROR`、`AD5421_FAULT_STATUS_ERROR`，并将CPU3本机 `CPU2_COMM_TIMEOUT` 调整为 `0x000E000C`。
- 必查边界：协议14/15混用、保留码、非故障状态、CPU3本机码与CPU2共享码重名、上位机按旧数值解析。
- 通过标准：双端协议值均为15；契约脚本确认77个CPU2共享枚举和1个CPU3本机码一致；混用时CPU3不得把旧值按新表显示。

### 4.2 TMC5130运行期诊断与配置丢失

- 源码位置：`TMC5130.c/.h`、`motor_ctrl_driver_param.c`、`motor_ctrl_motion_api.c`、`fault_manager.c`和`fault_recovery.c`。
- 改前问题：SPI阶段、上电复位残留、运行期复位和关键寄存器配置丢失缺少可追溯快照，现场只能看到通用驱动失败。
- 具体改法：记录SPI阶段和寄存器快照，区分初始化期复位残留与运行期复位/欠压/配置丢失；配置丢失进入统一故障出口并允许既有电机恢复策略处理。
- 必查边界：上电首次检查、运动中复位、欠压、SPI读写失败、重复相同快照、恢复后再次故障。
- 通过标准：相应场景返回精确错误码，运动链停止，主循环日志包含阶段和快照，恢复成功后不遗留错误状态。

### 4.3 AD5421与AO延迟诊断

- 源码位置：`ad5421.c/.h`、`ao_output.c/.h`和主循环调用点 `App_MainLoop`。
- 改前问题：AD5421主动故障状态、总线访问和回读失败归因不足；ISR/PendSV直接打印存在阻塞和重入风险。
- 具体改法：增加总线访问、控制寄存器回读和故障寄存器快照；中断只记录待处理状态，主循环统一打印、恢复并对持续相同故障去重。
- 必查边界：断环、主动报警、回读 `0xFFFF`、SPI失败、故障持续、恢复后再次触发、AO禁用状态。
- 通过标准：中断调用链无新增打印；故障码区分访问、回读和主动状态；持续故障不刷屏，恢复和复发均有可追溯日志。

### 4.4 传感器、无线、参数和测量错误归因

- 源码位置：`dsm_sensor_communication.c`、`ltd_sensor_communication.c`、`ch9141_at.c`、`wireless_pairing.c`、`measure*.c`、`system_parameter.c`和`error_log.c/.h`。
- 改前问题：UART/DMA失败、无线响应格式异常和业务超时可能被压缩成通用通信失败，最终日志难以对应实际责任域。
- 具体改法：保留最后一次有效底层错误码并向上传递，格式错误与超时分离，统一错误名称、原因、模块和最终出口。
- 必查边界：空响应、短帧、CRC/格式异常、超时、DMA启动失败、多次重试后成功、最终失败和用户取消。
- 通过标准：每条失败链只产生一个最终故障出口；重试成功打印恢复，最终失败保留具体错误码，非故障退出不进入错误日志。

### 4.5 CPU3统一外部协议切换帧

- 源码位置：`protocol_switch_frame.c/.h` 的 `ProtocolSwitchFrame_Process`，`app_main.c` 的暂存/发送完成/应用状态机，`cpu3_comm_display_params.c` 的保存和单端口重配。
- 改前问题：外部端口缺少在未知当前协议参数下统一切换协议的管理帧，直接改参数可能导致ACK尚未发完就切换波特率。
- 具体改法：新增功能码 `0x46`、魔术字 `LTD`和CRC校验；合法请求在旧参数下发送ACK，发送完成回调只标记APPLY，主循环保存FRAM并只重配目标COM；同协议目标只ACK。
- 必查边界：错误CRC、非法目标、同协议目标、TX忙、DMA启动失败、单帧pending、三路COM独立切换和ACK完成前不得应用。
- 通过标准：异常帧不改配置；合法ACK完整发送后才保存和重配；其它端口通信参数不变；同协议请求无FRAM写和UART重配。

### 4.6 CPU3参数持久化和失败回滚

- 源码位置：`Cpu3_Params_SaveToFRAM`、`Cpu3Local_WriteValueChecked`、`cpu3_restore_protocol_switch_port_config`和`Cpu3_ReinitPortUart`。
- 改前问题：FRAM写入缺少写后读回确认，协议切换持久化失败时运行态和存储态可能不一致。
- 具体改法：保存前判重，写入后重新读取并校验CRC和参数区；失败时恢复旧配置镜像、尝试回写FRAM并按旧参数恢复目标端口。
- 必查边界：内容未变化、首次写入、读回CRC错误、参数区不一致、回滚写入再次失败和无效端口。
- 通过标准：未变化不重复写；成功保存读回一致；失败后目标端口保持旧协议，其它端口不受影响，并输出明确失败日志。

### 4.7 CPU3故障显示同步

- 源码位置：`display.c` 的故障码分派和CPU3 `system_parameter.h` 的枚举。
- 改前问题：协议15新增和重编号故障若未同步显示，会出现错误类别或原因文本不一致。
- 具体改法：补齐TMC配置丢失、UART传输、无线格式、AD5421主动故障和CPU2通信超时的显示映射。
- 必查边界：未知/保留码、协议不匹配、CPU3本机通信故障和共享故障码。
- 通过标准：已定义码显示责任域和原因一致；未知码保持安全兜底；字库检查454字符一致、缺字0。

### 4.8 流程与交付证据治理

- 源码位置：`update_flow_navigation.py`、`check_docs.py`及交付证据、工作包、运行台账、批次、治理事项、知识快照和基线相关工具与JSON清单。
- 改前问题：流程页、验证证据和发布结论之间缺少统一机器门禁；部分新子脚本在Windows管道模式下产生中文乱码，`ZoneInfo`在无tzdata环境不可用。
- 具体改法：将流程清单升级到schema 2并加入责任人、固件基线和验证关系；聚合各治理检查；显式向子进程传递UTF-8输出环境；上海时区在缺少IANA数据时回退到UTC+8。
- 必查边界：schema版本不一致、固件基线过期、未登记证据、重复批次/月度快照、并发写入、Windows无tzdata和子进程中文输出。
- 通过标准：`check_docs.py`全部阶段通过且中文可读；真实清单与测试夹具均使用schema 2；CPU2 V1.23.0.0 / CPU3 V1.22.0.0基线同步到全部派生流程页。

## 5. 跨模块闭环

1. CPU2底层驱动或通信模块产生精确错误码。
2. 业务层保留最后有效原因，`fault_manager`执行唯一最终故障出口。
3. CPU2通过共享寄存器发布协议15故障值。
4. CPU3仅在共享协议版本严格相等时消费，并按协议15映射显示。
5. 外部主机可通过统一切换帧改变CPU3目标端口协议；ACK完成后才保存和重配。
6. 流程导航、协议记录、验证工作包和交付证据门禁共同约束发布资料与代码版本一致。

## 9. 风险与未验证项

- 自动检查不能替代RS485收发方向、DMA完成中断和ACK后重配的实机时序验证。
- TMC5130掉电/复位、AD5421主动故障和FRAM故障回滚仍需硬件故障注入。
- 协议15改变既有故障码数值；上位机、日志分析工具和售后资料必须同步新表。
- `outputs/`含大量本地生成物和依赖目录，明确不进入Git提交。
