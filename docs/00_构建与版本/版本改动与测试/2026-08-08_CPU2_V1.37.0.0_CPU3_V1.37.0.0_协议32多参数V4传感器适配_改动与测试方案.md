# CPU2 V1.37.0.0 / CPU3 V1.37.0.0 协议32多参数V4传感器适配改动与测试方案

## 1. 文档目的和适用范围

本文对应CPU2 `V1.37.0.0`、CPU3 `V1.37.0.0`和CPU2/CPU3共享协议32，供代码复核、固件构建、DM4台架联调和降级操作使用。本文件随本次提交纳入，提交哈希以Git记录为准。

本次交付实现通用的“多参数V4传感器”，DM4是当前首个设备。V4与多参数传感器通信协议V3.0不兼容；真实目标板、RS485和传感器联调尚未执行，静态检查和构建不能替代设备证据。

参数存储兼容性：

- `DeviceParameters`结构大小、字段偏移、`struct_size`、magic、CRC范围、FRAM A/B地址和单槽容量均不变；升级不会恢复出厂或清除其它现场参数。
- 新固件允许在现有`sensorType`字段持久化15，没有新增字段或复用保留字段。
- 协议32与31的CPU2/CPU3组合不得混搭；现有严格相等门禁应在启动同步阶段拒绝不匹配组合。
- CPU3对外LTD Modbus与板间通信共用同一共享寄存器契约。协议32外部可见变化包括FC03传感器类型15、FC03协议版本32，以及FC04 `0x0120~0x0127`四项Float32结果；外部主机和调试工具必须按协议32更新地址表及调试块长度。
- 降级前必须先用V4固件或外部工具把传感器参数65写为1并读回，确认设备恢复8字节交互方式；再把`sensorType=15`改为旧固件可识别的类型。未完成时禁止直接烧写旧固件。

## 4. 详细改动

### 4.1 多参数V3命名统一

- 源码位置：`Services/Sensor/multiparam_v3_communication.c/.h`及调用方。
- 改前问题：LTD V3通信实现仍大量使用`DSM_V2_*`函数、变量和类型名，容易与传统DSM协议或V4实现混淆。
- 具体改法：文件、接口、类型、状态和注释统一改为`MULTIPARAM_V3_*`口径；保留V3线上命令、寄存器和应答格式。
- 必查边界：全仓不再存在业务代码引用`DSM_V2_`；V3探测、密度、液位、水位、姿态和部件参数路径仍可链接。
- 通过标准：旧符号扫描为0，CPU2 clean-first构建通过，V3静态调用链未转入V4或DSM分支。

### 4.2 V4主动64字节帧

- 源码位置：`multiparam_v4_communication.c/.h`的主动流接收、CRC、固定字段和快照发布入口。
- 改前问题：CPU2没有V4帧格式、流重同步、序号诊断和多参数快照。
- 具体改法：按地址0、协议4.0、类型、参数数、总长度及CRC16/MODBUS校验64字节帧；解析13项最新值、模式相关频率、状态字和序号，只有完整合法帧才发布。
- 必查边界：前导噪声、半帧、粘连、CRC错误、固定字段错误、地址错误、重复、跳号、乱序和`FFFF→0000`。
- 通过标准：坏帧不更新快照或最后有效时间；合法帧逐帧增加更新代次并保留序号诊断。

### 4.3 UART6中断、PendSV和恢复

- 源码位置：`Core/Src/stm32f4xx_it.c`、`Core/Src/usart.c`、`Application/Src/app_main.c`及V4通信层。
- 改前问题：主循环存在阻塞测量流程，若主动帧只在主循环解析，500 ms数据可能无法及时更新；交互命令与主动帧还可能争用半双工DMA。
- 具体改法：UART6中断只收集事件并调度PendSV；PendSV完成V4解包、校验和快照赋值。停止DMA、交互事务、状态切换和`STATE_SWITCH`出口均恢复必要接收状态。
- 必查边界：主循环阻塞、DMA正在接收、主动帧抢占8字节等待、坏帧、AT占用、命令切换和连续两帧。
- 通过标准：合法主动帧无需主循环轮询即可更新快照；中断不执行打印、浮点业务或阻塞等待；事务结束后UART6可继续接收。

### 4.4 参数65半双工交互窗口

- 源码位置：V4通信层的方式切换、窗口仲裁和交互事务入口。
- 改前问题：主动上报与主机下行共用RS485半双工链路，直接发送可能撞上下一主动帧；参数65持久化，不应在每次读取前后反复写入。
- 具体改法：在有效主动帧后等待20 ms进入20～100 ms窗口，必要时写参数65关闭主动方式，执行D/S/L/M或寄存器事务后恢复；单次交互总上限3 s。主动帧抢占时先发布该帧，再到下一窗口重试。
- 必查边界：20 ms前、100 ms后、主动帧抢占、8字节应答丢失、对端已切换但本地超时、3 s到期、重复命令和`STATE_SWITCH`。
- 通过标准：主动帧不被当作8字节应答；窗口外不强发；参数65只在目标方式变化时写入，超时有确定错误出口。

### 4.5 密度/液位模式与测水/磁零点控制

- 源码位置：`sensor.c`、`measure_oilLevel.c`、`multiparam_v4_measurement.c`及统一传感器接口。
- 改前问题：旧模式口径把测水和磁零点混同为测量模式，且无法区分参数4的频率含义。
- 具体改法：只保留密度模式和液位模式；参数4在液位模式表示液位频率，在密度模式表示密度谐振频率。测水与磁零点通过L/M控制对应使能/关闭，并在应答不确定时读取状态字复核。
- 必查边界：D/S切换、L/M开关、L/M互斥未知、应答丢失、主动/交互两种方式和模式不符快照。
- 通过标准：频率按当前模式解释；测水/磁零点不改变频率语义；L/M不盲目重复翻转。

### 4.6 主动与交互两条测量路径

- 源码位置：`multiparam_v4_measurement.c/.h`、`measure.c`及密度、液位、部件参数调用方。
- 改前问题：现有流程依赖请求/响应，不能像扭力传感器一样直接消费主动帧；把停流/恢复塞入每个旧流程会造成重复切换。
- 具体改法：新增V4主动专用过程直接消费最新快照；双向通信适配现有密度、液位、水位、姿态、黏度和部件参数过程，两条路径复用统一业务数据但独立占用UART6。
- 必查边界：启动时尚无帧、持续更新、旧帧超时、模式变化、断流恢复、主动与交互切换和命令取消。
- 通过标准：主动过程不为普通测量反复写参数65；交互过程仍获得明确应答；同一时刻只有一条路径占用UART6。

### 4.7 识别顺序与命令门禁

- 源码位置：`sensor.c/.h`的`DetectSensorType`及`measure.c`命令准入判断。
- 改前问题：未知类型曾默认走V3；过宽的“必须在线”门禁会阻止回零、纯运动、维护或标定类命令。
- 具体改法：识别先被动监听V4主动帧，再检查蓝牙、安全协议、V4交互、V3和DSM；未知类型明确失败。命令按真实业务依赖判断，回零和其它纯运动流程允许传感器离线，附加传感器通道在无有效传感器时跳过。
- 必查边界：每种传感器单独在线、全部离线、V4主动/交互、协议噪声、取消、回零、运动、维护和测量命令。
- 通过标准：协议不串扰；回零不被传感器离线门禁拦截；真正需要测量数据的命令仍拒绝无有效传感器状态。

### 4.8 调试数据追加

- 源码位置：`Application/Inc/test.h`、`Application/Src/test.c`及CPU2 Modbus调试数据发布。
- 改前问题：CPU2调试快照和CPU3对外LTD FC04无法观察V4主动接收的磁零点电压、动力黏度、运动黏度和传感器供电电压。
- 具体改法：在既有调试数据尾部追加四个Float32字段，对应`0x0120~0x0127`；CPU3同步扩展调试轮询块并写入共享快照，LTD外部从站通过`CPU2_CommReadInputSnapshot()`直接返回同一份已确认数据。既有字段地址不移动，调试块末端从`0x0120`扩展为`0x0128`。
- 必查边界：无有效V4帧、合法帧、模式切换、Float32高字在前、旧调试项、CPU2断线、协议不匹配、参数/运行快照未建立及刷新中。
- 通过标准：旧调试字段顺序和地址不变；FC04 `0x0120~0x0127`依次得到磁零点电压、动力黏度、运动黏度、供电电压；快照不可用时返回异常`0x06`，不返回旧数据。

### 4.9 CPU3类型15同步与显示

- 源码位置：CPU3 `system_parameter.c/.h`、`stateformodbus.h`、`dataanalysis_modbus.c`和`device_param_sync.c`。
- 改前问题：CPU3不认识类型15，可能显示未知或把未知值在参数同步中写回CPU2。
- 具体改法：新增相同枚举值及“多参数V4”文本；未知值保留原始数值并告警，参数批量同步拒绝回写未知类型。
- 必查边界：类型15、所有既有类型、未知最大值、协议不匹配和参数刷新。
- 通过标准：协议32两端一致显示类型15；未知值不被静默替换或写回；协议31/32组合由版本门禁拒绝。

### 4.10 协议卷与实现口径同步

- 源码位置：DM4协议卷、LTD共享Modbus协议卷与全量寄存器表、历史版本说明、计划、协议索引、共享协议变更记录和`CHANGELOG.md`。
- 改前问题：原始工作簿、V3/LTD命名、主动帧结论和提交阶段版本口径分散；LTD正式资料仍停留在协议31，未说明板间新增Input会直接成为LTD外部FC04字段。
- 具体改法：统一名称为“多参数V4传感器”，明确V3.0与V4.0不兼容、R01存储版本用作协议版本、主动/交互帧、参数65、模式和硬件未验证边界；同步LTD协议32组合、类型15、四项FC04地址、字段统计和快照Busy语义。
- 必查边界：版本号、协议号、参数存储、回退步骤、文档链接和原始资料来源。
- 通过标准：正式文档与最终源码一致，链接无缺失，不把静态分析写成真实设备或SIL验证。

## 5. 跨模块数据流与异常闭环

主动链路：`UART6接收中断 -> PendSV -> 64字节校验/解包 -> V4运行快照与代次 -> 主动测量过程 -> CPU2调试/业务结果 -> CPU2 Input寄存器 -> CPU3已确认快照 -> LTD外部FC04`。

交互链路：`现有测量流程 -> 统一传感器接口 -> 参数65窗口仲裁 -> V4 8字节事务 -> 状态字/参数结果 -> 既有测量计算 -> 必要时恢复主动方式`。

异常闭环：坏帧只累计错误且不刷新快照；主动帧抢占先发布再重试窗口；事务超时恢复UART6；模式控制应答不确定时读状态字；协议不匹配由CPU2/CPU3严格版本门禁拦截；旧帧超时不得继续作为最新测量值。

## 8. 复杂时序验证

### 8.1 主动帧抢占交互窗口

1. 参数65置0，确认DM4每约500 ms上报一帧。
2. CPU2接收合法帧后等待20 ms，准备发送交互命令。
3. 在CPU2发送前注入下一主动帧，记录UART方向、PendSV代次和交互重试时间。
4. 确认主动帧完整发布，CPU2未把其误判为8字节应答。
5. CPU2在下一合规窗口发送命令，3 s内得到结果或明确超时并恢复接收。

### 8.2 命令切换与阻塞主循环

1. 进入V4主动测量过程并让主循环处于阻塞等待。
2. 连续发送三帧，确认快照代次和最后有效时间仍更新。
3. 下发取消或新正式命令，观察`STATE_SWITCH`出口。
4. 确认必要UART接收已恢复，新命令及时取得执行权，旧事务不继续占用DMA。

### 8.3 降级演练

1. 记录现场参数和当前`sensorType=15`。
2. 写参数65为1并读回8字节应答，断电重启后再次确认不主动上报。
3. 将传感器类型改为旧固件可识别值并确认持久化。
4. 烧写旧固件，确认CPU2/CPU3协议匹配后再进行旧协议识别。
5. 任一步失败都停止降级，不以清参或反复烧写代替确认。
