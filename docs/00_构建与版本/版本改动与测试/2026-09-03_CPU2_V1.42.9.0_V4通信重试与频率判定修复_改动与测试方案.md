# CPU2 V1.42.9.0 V4通信重试与频率判定修复改动与测试方案

## 1. 文档目的和适用版本

- CPU2：`V1.42.8.0 -> V1.42.9.0`（PATCH）。
- CPU3：保持`V1.40.1.0`。
- 适用链路：DM4 V4交互读取、部件参数刷新、主动/交互异常包打印、液位频率读取与运动等待、自动恢复检查。
- 本文件随本次提交纳入；提交哈希以Git记录为准。

## 2. 协议和参数存储兼容性

- `DEVICE_PROTOCOL_VERSION`保持35；不改变CPU2/CPU3共享寄存器、命令、状态、字段或CPU3对外LTD标准Modbus共享区。
- DM4 V4帧格式、参数地址、R/W/D/S/L/M功能码和错误码不变。通信重试只改变CPU2本地执行次数、日志和耗时，不要求传感器协议升级。
- 幂等读取及可安全重复的D/S模式命令只对超时、UART传输、响应格式、BCC和地址不匹配最多尝试3次；`STATE_SWITCH`、调用条件、流状态、模式不匹配及业务数据异常不在协议层重试。
- 参数写入保持单次写命令，写应答失败后使用读回确认；L/M等非幂等命令仍为单次下发，避免重复执行远端动作。
- CPU2 `DEVICE_PARAM_VERSION`保持3；`DeviceParameters`、`struct_size`、字段偏移、CRC范围和FRAM布局不变。升级不恢复出厂、不清除现场参数，无需迁移或补默认值。

## 3. 本次提交范围

### 3.1 V4幂等通信错误最多尝试3次并逐次打印原包

- 源码位置：`LTD_MAIN_CPU2/Services/Sensor/Protocols/Dm4/V4/multiparam_v4_interactive.c`的`MULTIPARAM_V4_TransceiveIdempotent`；`multiparam_v4_diagnostics.c`的`MULTIPARAM_V4_PrintTransactionFailureAttempt`和`MULTIPARAM_V4_PrintFailurePackets`；对应声明位于`multiparam_v4_communication.h`和`multiparam_v4_internal.h`。
- 改前问题：V4读取虽然存在三次循环，但各类返回码没有明确区分是否可重试，也没有在每次通信失败后输出对应TX/RX原包和尝试序号，现场难以确认是哪一包导致失败。
- 具体改法：仅将超时、UART传输、响应格式、BCC和地址不匹配列为可重试通信错误；每次失败后打印TX、实收RX、失败阶段、UART状态和`尝试=n/3`，第三次后返回最后错误。后续尝试成功时记录恢复日志。同一事务增加打印去重，避免协议层和业务层重复输出。
- 必查边界：首次成功、第二/第三次成功、连续三次同类或不同类通信错误、空RX、短帧、错误地址、BCC错误、命令切换、非重试错误、tick回绕和UART所有权切换。
- 通过标准：五类可重试通信错误最多产生三次真实发送，每次失败均有对应包；成功立即停止后续发送；非重试错误不额外发送；返回码保持最后一次真实结果。

### 3.2 主动与交互模式统一提供失败包证据

- 源码位置：`LTD_MAIN_CPU2/Services/Sensor/sensor_comm_diagnostics.c/.h`的`SensorComm_PrintFailurePackets`；`multiparam_v4_diagnostics.c`的主动帧和交互事务分流；`part_diagnostics.c`的`PartDiagnostics_ReportV4Failure`。
- 改前问题：交互读取失败只在上层打印最后事务，主动模式没有对应发送事务且缺少匹配的原始帧；多层调用还可能重复打印。
- 具体改法：确认当前已识别为DM4 V4后再输出证据。交互模式优先使用当前事务TX/RX且自动去重；主动模式优先打印错误码匹配且不早于最后有效快照的异常帧，否则打印最近有效主动帧，没有原帧时明确长度0。
- 必查边界：V3/DSM、未识别、主动异常帧早于/晚于快照、交互事务尚未实际发送、业务拒绝频率和`SENSOR_DATA_STALE`。
- 通过标准：只在DM4 V4线程态失败路径打印；不发送额外探测包、不改变错误码；交互事务不重复，主动模式不把旧异常帧误归因于新快照。

### 3.3 读取部件参数复用相同通信重试

- 源码位置：`LTD_MAIN_CPU2/Application/Src/diagnostics/part_diagnostics.c`的状态、密度、分析参数和水位电容读取；底层经`MULTIPARAM_V4_ReadParamRaw`进入幂等事务。
- 改前问题：上层只能看到一次最终错误，无法确认部件参数读取是否进入协议重试，也无法获得主动/交互模式一致的失败包。
- 具体改法：保持原有部件读取顺序和返回码，仅把失败包输出收口到`SensorComm_PrintFailurePackets`。交互参数读取沿用底层最多3次通信尝试；`SENSOR_DATA_STALE`仍表示当前数据未更新，不打印为通信故障。
- 必查边界：状态读取、密度/温度/频率、水位电容、分析参数、主动数据未更新、模式切换失败和命令切换。
- 通过标准：部件参数的五类交互通信错误按底层最多尝试3次；未稳定/未更新数据不触发通信错误包；原有首个真实错误继续向上返回。

### 3.4 频率0等待与非零越界业务判定

- 源码位置：`multiparam_v4_measurement.c`的`MULTIPARAM_V4_MeasurementReadLevelFrequency`；`oil_level_common.c`的`OilLevel_ReadFrequencySample`和`OilLevel_ReadValidatedFrequencyInternal`；`oil_level_frequency.c`与`oil_level_step_search.c`的运动读取路径。
- 改前问题：V4测量层把0或越界频率直接归为`SONIC_FREQ_ABNORMAL`，导致0这个“当前未稳定”状态一次即报错，上层也无法统一执行三次业务判定。
- 具体改法：交互和主动路径收到0时返回`NO_ERROR`并输出频率0，不刷新调试频率。非零可解码样本原样返回，由液位业务层按`1..6500 Hz`判断。静止校验遇0只等待下一样本且不增加错误计数；运动闭环和步进判定遇0先停机、清稳定状态并等待。非零越界每轮连续计数3次后才进入原有有限模式恢复，搜索流程继续受统一超时约束。
- 必查边界：`0`、`1`、`6500`、`6501`、`6600`、`6601`、普通负值和`INT32_MIN`；主动/交互、静止/运动、搜索超时和跟随无超时路径。
- 通过标准：0不会直接产生频率异常且运动停止；`1..6500 Hz`正常进入业务；非零越界不由V4测量层首次报错，液位层完成连续计数；真实通信错误仍立即返回底层错误。

### 3.5 自动恢复检查有界退出并保留首次错误

- 源码位置：`LTD_MAIN_CPU2/Application/Src/diagnostics/fault_recovery.c`的`FaultRecoveryContext`、`FaultRecovery_HandleCheckFailure`、`FaultRecovery_Start`和`FaultRecovery_Poll`。
- 改前问题：电机初始化或部件检查持续失败时，每秒重复检查但没有独立上限；后续检查错误还会覆盖首次触发自动恢复的原因。
- 具体改法：分别保存首次触发错误和最近错误；恢复检查失败使用独立计数，达到配置的自动恢复上限后保持`STATE_ERROR`、停止恢复并打印首次/最终错误。检查成功后清检查失败段，再按原业务重跑计数决定是否重跑原命令。
- 必查边界：电机错误触发、通信错误触发、检查间歇成功、连续失败到上限、业务重跑失败、达到业务上限和新命令取消。
- 通过标准：连续检查失败不会无限轮询；首次触发错误不被覆盖；检查次数和业务重跑次数互不混用；新命令仍能立即取消恢复。
