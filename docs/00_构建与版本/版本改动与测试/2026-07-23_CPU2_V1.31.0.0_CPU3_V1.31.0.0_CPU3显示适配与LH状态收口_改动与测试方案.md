# CPU2 V1.31.0.0 / CPU3 V1.31.0.0 CPU3显示适配与LH状态收口改动与测试方案

日期：2026-07-23
适用分支：`MAIN`
改动前提交基线：`46f5d6344a9699a12167d5cf807f1c8af0d4498f`
提交状态：本文件随本次版本改动提交，最终提交哈希以Git记录为准

## 1. 目的与当前结论

本版本对协议27已发布的维护、继电器和LH能力补齐CPU3可视闭环：屏幕可根据有效快照进入或退出维护，可清除全部继电器锁存，状态栏能区分维护、AO仿真及快照失效，继电器页能显示动作禁用和最终逻辑动作。LH设备状态改为白名单投影，不再把LH手册未定义的CPU2内部状态原值暴露给外部主机。

本次不修改CPU2业务、共享寄存器布局、参数结构、命令号或外部串口默认值。CPU2保持V1.31.0.0，CPU3因显示行为和LH对外状态语义变化升级到V1.31.0.0；共享协议保持27。

## 3. 固件改动

### 3.1 维护菜单和命令显示闭环

- 源码位置：`LTD_DISPLAY_CPU3/Application/display/display_tankopera.c` 的 `menu_debug_system()`、`screen_operation_is_no_para_command()`、`dtm_operaname()`、`dtm_operaname_short()`、`ifsendcmd()`和`cmd_nopara_process()`；操作码定义位于 `display_tankopera.h`。
- 改前问题：协议27已提供CPU2命令118/119，但CPU3系统维护菜单只有进入维护入口；菜单无法根据CPU2真实维护状态切换退出，也缺少清全部锁存的名称、确认、发送和返回闭环。CPU2快照失效时若继续按旧值判断，可能把未知状态误当成可操作。
- 具体改法：CPU3增加本地操作码1005/1006，分别映射CPU2命令118和119；系统维护菜单只在完整快照有效时根据 `maintenance_mode_active` 选择进入或退出，快照无效时显示“维护状态未知/MNT Unavailable”并禁用下发。三个命令都使用专用中英文二次确认页，无参命令分类由单一helper统一消费。
- 必查边界：普通/维护/快照无效、确认/取消、重复确认、返回键、发送失败、CPU2 ACK失败、菜单刷新期间状态变化、操作码与共享命令号碰撞、中文/英文宽度。
- 通过标准：未知态不发送命令；普通态只提供进入，维护态只提供退出；清锁存只发送命令119一次；取消不产生副作用；屏幕只表述“指令已发送”，最终执行结果必须由后续CPU2快照或错误码确认。

### 3.2 状态栏和继电器运行态

- 源码位置：`LTD_DISPLAY_CPU3/Application/display/display.c` 的 `DIS_Equipment()`；`display_tankopera.c` 的 `relay_status_state_of()`、`display_relay_status_row()`和`menu_relay_status()`。
- 改前问题：状态栏不能同时表达维护和AO仿真，快照失效后可能退回普通显示；不同长度徽标切换会残留旧像素。继电器页只展示报警计算字段，缺少协议27新增的动作禁用和最终逻辑动作，断链时还可能继续显示旧缓存。
- 具体改法：徽标优先级固定为“已确认维护后快照失效”→“维护+AO仿真”→“维护”→“AO仿真”，并清理右侧四列和旧行；仅在新完整快照明确关闭维护后清除维护记忆。K1～K4新增Block/Action字段，快照无效时所有运行态显示 `N/A`。
- 必查边界：四种徽标及普通态、中英文切换、状态页换行、字符串变长/变短、维护中断链/恢复、仿真开关变化、K1～K4动作位、人工禁用、NO/NC配置和快照无效。
- 通过标准：每种组合只留下当前徽标且无残影；已确认维护后断链显示“维护?”而不是普通；继电器页与CPU2快照中的屏蔽和逻辑动作位一致，断链统一 `N/A`；文档不得把逻辑动作写成GPIO或物理触点反馈。

### 3.3 “求”字模

- 源码位置：`LTD_DISPLAY_CPU3/Application/display/display.c` 的 `StockMap` 与 `WordStock2`。
- 改前问题：新增菜单/提示使用“求”字，但字库没有对应索引和14×14点阵，真机显示会缺字或错误索引到相邻字符。
- 具体改法：在 `StockMap` 末尾增加“求”，并在 `WordStock2` 相同索引追加用户提供的28字节14×14点阵；不从其它字体推测或替换。
- 必查边界：UTF-8/GBK文本映射、字符索引与点阵注释顺序、数组长度、黑白位序、左右/上下偏移、相邻末尾字符和所有OLED字符串缺字扫描。
- 通过标准：`font_check.py`验证索引一致且OLED字符串缺字为0；真机逐笔画与用户提供字模一致，无镜像、错位或相邻字串位。

### 3.4 LH设备状态投影

- 源码位置：`LTD_DISPLAY_CPU3/Communication/external/lh_modbus/lh_modbus_slave.c` 的 `lh_translate_device_state()`及 `lh_build_input_registers()`。
- 改前问题：LH输入寄存器曾直接暴露CPU2内部 `DeviceState`；SI、Wärtsilä、屏幕专用或以后新增状态不在LH手册定义范围内，主机可能把未知内部码误解释为LH业务状态。
- 具体改法：显式白名单保留LH手册支持的基础状态，并将水位标定 `0x0026/0x8026`、罐高标定 `0x0028/0x8028` 映射到LH约定值；其它内部状态统一投影为 `STATE_STANDBY`。CPU2枚举和板间共享字段不变。
- 必查边界：所有白名单基础态、两个标定态及其完成态、错误位、SI/Wärtsilä/屏幕专用态、保留态、未来未知值和CPU2快照失效。
- 通过标准：LH主机只能看到手册定义状态或待机兜底，未定义内部码不得原值透出；板间原始状态和其它外部协议行为不受该投影函数影响。

## 8. 风险与未验证边界

1. 屏幕快照、按键、OLED残影和中英文宽度只有在真实面板上才能最终验收；静态检查和构建不证明显示效果。
2. “请求已发送”不是CPU2最终动作成功证明；必须同时观察CPU2快照、错误码、GPIO和物理触点。
3. `relay_alarm_action_mask` 不是物理触点反馈。NO/NC反相、继电器驱动、线圈和触点故障仍需硬件台架验证。
4. LH白名单投影改变了旧CPU3对未定义内部状态的可见值；需使用LH现场主机或参考实现覆盖所有已定义码和未定义默认分支。
5. 本版本共享协议不变，但仍需CPU2 V1.31.0.0 / CPU3 V1.31.0.0交叉烧写和长稳，不能只凭双端分别构建成功宣称整机验收完成。
