# CPU2 V1.22.0.0 / CPU3 V1.21.0.0 LTD 共享 Modbus、串口命令严检及流程门禁改动与测试方案

更新日期：2026-07-11

## 1. 文档目的和适用版本

本文覆盖当前代码提交中的三组改动：CPU3 对外 LTD 共享 Modbus、CPU2 USART1 串口命令收帧与严格解析、程序流程文档影响门禁及可访问性增强。测试人员可据此完成代码复核、主机侧自动检查和后续实机/PLC 联调。

| 项目 | 旧版本 | 新版本 | 升级级别 |
| --- | --- | --- | --- |
| CPU2 固件 | V1.21.6.0 | V1.22.0.0 | MINOR |
| CPU3 固件 | V1.20.0.0 | V1.21.0.0 | MINOR |
| CPU2/CPU3 共享协议 | 14 | 14 | 不变 |
| CPU2 参数存储版本 | 3 | 3 | 不变 |
| CPU3 本机参数版本 | 0x0006 | 0x0006 | 不变 |

升 MINOR 的原因：CPU2 增加正式可用的串口命令解析、查询和停止能力；CPU3 的 `COM_PROTO_LTD` 从占位不回包变为实际支持 FC03/FC04/FC10。两侧都有新增功能，但没有改变 CPU2/CPU3 共享寄存器契约。

## 2. 协议和参数存储兼容性

- `DEVICE_PROTOCOL_VERSION` 保持 14。LTD 外部从站直接复用现有 CPU2/CPU3 共享保持寄存器、输入寄存器、命令值和 32 位高字在前线序，没有新增、删除、移动或重新解释共享字段。
- CPU2 `DEVICE_PARAM_VERSION` 保持 3；`DeviceParameters` 字段顺序、结构大小、`struct_size`、magic、FRAM A/B 地址和 CRC 覆盖范围均未修改。
- 从 CPU2 V1.21.6.0 升级到 V1.22.0.0 不会因本次改动恢复出厂参数。FRAM 本身 A/B 均损坏或 CRC 错误仍按既有异常路径恢复出厂，不属于本次升级变化。
- CPU3 本机参数版本保持 `0x0006`；原先已把 COM 口配置为 LTD 的设备升级后会开始对外回包，属于行为启用，不需要重建 CPU3 FRAM。
- CPU2 串口命令是本地 USART1 调试接口，不属于板间共享协议；旧合法命令继续保留，但带尾随垃圾、越界值或不完整参数的历史宽松输入会被拒绝。

## 4. 逐小点详细改动清单

### 4.1 USART1 中断只转交接收字节

- 源码位置：`Core/Src/stm32f4xx_it.c` 的 `USART1_IRQHandler()`，调用 `SerialCommand_RxByteFromIsr()`。
- 改前问题：中断直接维护全局文本缓冲区并识别 CRLF，收帧、缓冲和业务入口耦合；超长帧只停止追加，可能把截断前缀当作命令。
- 具体改法：移除 ISR 中的全局 `received_buffer/buffer_index` 拼帧逻辑；DMA IDLE 取得字节后逐字节交给串口命令模块，中断不打印、不执行命令。
- 必查边界：DMA 一次包含半帧、完整帧、多字节；CRLF/LF；主循环尚未消费上一帧；超长后继续输入。
- 通过标准：ISR 只调用收帧器和重新启动 DMA；构建中无旧缓冲区未定义引用；中断路径没有 `printf` 或业务动作。

### 4.2 定长串口收帧状态机

- 源码位置：`serial_command_parser.c` 的 `SerialCommandRx_Init()`、`SerialCommandRx_PushByte()`。
- 改前问题：正文超过 63 字节后没有整帧丢弃语义，存在截断前缀被执行的风险。
- 具体改法：新增 64 字节定长状态、长度和 `discarding` 标志；忽略 CR，以 LF 结束；达到容量后丢弃直到 LF，再返回 `SERIAL_COMMAND_RX_TOO_LONG`。
- 必查边界：0 字节空行、63 字节正文、64 字节正文、连续超长帧、超长后下一条合法命令。
- 通过标准：63 字节及以内可形成 READY；64 字节及以上整帧不进入解析；下一条 HELP 可恢复为 READY。

### 4.3 ISR 超长事件延后到主循环报告

- 源码位置：`serial_command.c` 的 `SerialCommand_RxByteFromIsr()`、`SerialCommand_ProcessReady()`、`SerialCommand_ReportTooLong()`。
- 改前问题：如果在中断中报告错误会引入阻塞和不可控时序；如果不报告，现场无法知道命令被丢弃。
- 具体改法：ISR 只置 `s_serial_command_too_long_ready/new_command_ready`；主循环输出 `ERR reason=CMD_TOO_LONG max=63`。
- 必查边界：超长事件与普通 READY 互斥；报告后标志清除；报告期间新数据不得覆盖当前帧。
- 通过标准：源码扫描确认 ISR 不调用打印；超长 C 测试得到 TOO_LONG，随后合法帧可正常接收。

### 4.4 主循环复制帧后再开放接收

- 源码位置：`serial_command.c` 的 `SerialCommand_ProcessReady()`，入口在 `app_main.c` 的 `App_MainLoop()`。
- 改前问题：直接处理共享接收缓冲可能被下一次 ISR 覆盖；串口新命令与待恢复命令可能竞争。
- 具体改法：主循环先取消故障自动恢复，复制完整 64 字节本地帧，补末尾 NUL，再清 `new_command_ready` 并解析本地副本。
- 必查边界：ISR 在复制前、复制中和清标志后的时序；上一帧处理耗时；自动恢复已挂起。
- 通过标准：处理函数只使用栈上副本；接收就绪前 ISR 不修改共享帧；串口命令优先取消待恢复动作。

### 4.5 正式单字母命令必须完整匹配

- 源码位置：`serial_command_parser.c` 的 `SerialCommandParser_IsFormalPrefix()`、`SerialCommandParser_Parse()`。
- 改前问题：旧逻辑只看首字符，`Qxxxx`、`Ixxxx` 可能误触发恢复出厂或电机动作。
- 具体改法：I/G/K/R/W/O/P/Q 只有第二字节为 NUL 才归类 FORMAL；同前缀但有尾随字符统一归类 INVALID。
- 必查边界：单字符合法命令、尾随数字/空格/字母、空命令、未知首字符。
- 通过标准：I、Q 返回 FORMAL；Ixxxx、Qxxxx 返回 INVALID；未知命令返回 UNSUPPORTED。

### 4.6 正式命令继续走统一主循环

- 源码位置：`serial_command.c` 的 `SerialCommand_MapFormalCommand()`、`SerialCommand_Process()`。
- 改前问题：串口入口若直接执行业务动作会绕过 `current_command`、命令切换、故障恢复和统一错误出口。
- 具体改法：解析通过后只把正式字符映射为现有 `CommandType` 并写入 `g_deviceParams.command`。
- 必查边界：未知映射、已有命令执行中、新命令切换、自动恢复待执行。
- 通过标准：正式命令返回 ACK 后由主循环后续执行；解析模块不直接调用测量、电机或恢复出厂函数。

### 4.7 新增通用 STOP

- 源码位置：`serial_command_parser.c` 的 STOP 分类；`serial_command.c` 的 STOP 分发。
- 改前问题：不同手动/循环测试依赖各自停止入口，命令面板缺少统一安全停止按钮。
- 具体改法：完整匹配 `STOP` 后写入 `CMD_CANCEL_MEASUREMENT`，复用统一取消、慢停和待机路径。
- 必查边界：正式测量、B/BE 循环、手动运动、已待机、STOP 带尾随字符。
- 通过标准：STOP 返回 ACK 并挂起取消命令；STOPX 不执行；最终停机行为由既有取消路径完成。

### 4.8 新增四个只读查询命令

- 源码位置：`serial_command.c` 的 `SerialCommand_PrintHelp/Version/Status/Error()`。
- 改前问题：现场需要从多个日志推断版本、协议、参数版本、当前状态和错误，缺少稳定查询入口。
- 具体改法：新增 HELP、VER?、STAT?、ERR?；打印 CPU2 固件、协议、参数版本、状态、当前/待执行命令和统一错误解释。
- 必查边界：错误码为 0、未知错误码、查询期间电机运动、查询命令尾随字符。
- 通过标准：四条命令均先 ACK 后输出查询结果；不调用 `MeasureStart()`、不改参数、不启动电机。

### 4.9 数值命令执行完整语法和范围检查

- 源码位置：`serial_command_parser.c` 的 `ParseUnsigned()`、`ParseDecimal()`、`ParseA/Ao/B/Bj/Be()`。
- 改前问题：旧 `atoi`/前缀分发可能接受尾随垃圾、0 距离、越界速度或倍率，随后进入运动/输出函数。
- 具体改法：逐字符解析十进制整数/小数并要求游标到 NUL；A/B/BE/BJ/BJP、AO 电流、速度和倍率按协议范围校验。
- 必查边界：0、最大值、溢出、缺数字、只有小数点、尾随字符、速度 0.10/6.00 和 6.01、倍率 1/20/21、AO 320/2400。
- 通过标准：协议卷列出的合法命令均归类 TEST；越界和尾随垃圾均为 INVALID，未进入旧动作分发器。

### 4.10 无线名称和固定调试命令严格匹配

- 源码位置：`serial_command_parser.c` 的 `ParseSp()` 和 `exact_test_commands[]`。
- 改前问题：SP、T、Y、C 等旧入口按前缀分支，拼写错误可能仍调用初始化或测试动作。
- 具体改法：SPS/SPR/SPC 精确匹配；SPN 名称限制 1～17 字节；固定测试命令使用白名单全文匹配。
- 必查边界：空名称、17/18 字节名称、T1/T1abc、YM/YMabc、C/Cabc。
- 通过标准：合法白名单进入 TEST；已知前缀的错误格式进入 INVALID；未登记命令进入 UNSUPPORTED。

### 4.11 旧测试分发器增加二次门禁

- 源码位置：`test.c` 的 `Test_ProcessSerialCommand()`。
- 改前问题：其它调用方如果直接调用旧测试分发器，仍可能绕过新解析入口。
- 具体改法：函数开头再次调用 `SerialCommandParser_Parse()`，只有 KIND_TEST 才进入 AO、无线、电机和循环测试分支。
- 必查边界：NULL、空串、正式命令、查询命令、尾随垃圾、合法测试命令。
- 通过标准：非 TEST 一律返回 0；合法 TEST 保持既有动作和返回口径。

### 4.12 `process_command()` 收口为兼容包装

- 源码位置：`measure.c` 的 `process_command()`。
- 改前问题：正式命令映射、测试分发和串口打印混在测量主文件，后续扩展容易继续放宽入口。
- 具体改法：移除测量文件内的本地正式命令映射，兼容入口统一调用 `SerialCommand_Process()`。
- 必查边界：旧声明和调用仍能链接；新模块通过 CMake glob 纳入构建；无重复全局缓冲定义。
- 通过标准：CPU2 clean-first 构建通过；旧 `received_buffer/buffer_index` 引用清零；`new_command_ready` 只有新模块定义。

### 4.13 CPU2 串口命令面板生成和一致性检查

- 源码位置：`tools/generate_cpu2_serial_command_panel.py` 和正式 JSON 配置。
- 改前问题：命令按钮由人工维护，容易遗漏 STOP/查询、使用高风险距离或出现配置与固件语法漂移。
- 具体改法：生成 10 组 67 个按钮，固定字段、顺序、文本发送和 100 ms 延迟；高风险恢复出厂单独分组。
- 必查边界：必备五条系统命令、组内重复 payload、字段缺失、组数和按钮数变化、生成结果漂移。
- 通过标准：`--check` 输出 PASS，确认 10 组 67 个按钮与生成器完全一致。

### 4.14 CPU3 LTD 协议接入外部 COM 分发表

- 源码位置：`Application/app_main.c` 的 `proto_ltd_process()` 和 `g_handlers[]`；`CMakeLists.txt` 的 include 路径。
- 改前问题：菜单可选择 LTD，但处理器是 `proto_no_reply` 占位，外部主机只会超时。
- 具体改法：新增 LTD 从站模块和分发包装，将 `COM_PROTO_LTD` 绑定真实处理函数，并把头文件目录加入构建。
- 必查边界：COM1/COM2/COM3 任一选择 LTD、其它协议表项不变、无响应帧时接收恢复。
- 通过标准：CPU3 clean-first 构建包含 `ltd_modbus_slave.c.obj`；契约脚本找到 LTD 分发表连接。

### 4.15 LTD RTU 地址和 CRC 门禁

- 源码位置：`ltd_modbus_slave.c` 的 `ltd_get_slave_address()`、`ltd_modbus_process()`。
- 改前问题：占位实现没有帧级校验；新增协议必须避免对其它从站或坏 CRC 回包。
- 具体改法：使用系统 `SlaveAddress`，非法配置回退 1；地址不匹配和 CRC 错误保持静默。
- 必查边界：地址 1/247、配置 0/248、广播 0、CRC 错误、最短帧。
- 通过标准：地址不匹配/CRC 错误时 `tx_len=0`；合法地址和 CRC 才进入功能码处理。

### 4.16 LTD FC03 读取保持寄存器快照

- 源码位置：`ltd_handle_read()`、`CPU2_CommReadHoldingSnapshot()`。
- 改前问题：直接从未确认本地结构回包会暴露默认值、旧值或写请求影子。
- 具体改法：范围合法后由 CPU2 通信层先检查状态/参数/协议快照和通信故障，再从已确认 `g_deviceParams` 生成保持寄存器并复制。
- 必查边界：数量 0/1/125/126、窗口末端、快照未建立、协议不匹配、通信故障、参数补读中。
- 通过标准：有效快照返回标准 FC03；不可用返回 `0x83/0x06`；越界返回 `0x83/0x02`。

### 4.17 LTD FC04 读取输入寄存器快照

- 源码位置：`ltd_handle_read()`、`CPU2_CommReadInputSnapshot()`。
- 改前问题：状态缓存未建立或 CPU2 掉线时回旧状态会让外部主机误判设备仍在线。
- 具体改法：只从最近一次合法 CPU2 响应形成的 `InputRegisterArray` 复制；统一受 `CPU2_CommIsAvailable()` 门禁。
- 必查边界：状态快照未建立、通信故障锁存、数量和末端地址、CPU2 恢复但参数/协议尚未补齐。
- 通过标准：全部门禁满足才返回 FC04 数据；任一不满足返回 `0x84/0x06`。

### 4.18 LTD FC10 标准长度和 32 位对齐校验

- 源码位置：`ltd_handle_write()`。
- 改前问题：共享参数均为 32 位，允许奇数地址/数量会只改半个字段；声明字节数和实际帧长不一致会越界或误读 CRC。
- 具体改法：限制 2～122 个且为偶数的寄存器，起始地址必须为偶数，`byteCount=count*2`，RTU 总长必须为 `9+byteCount`。
- 必查边界：count 0/2/122/123、奇数起始地址、奇数数量、byteCount 不符、截短、超长、窗口末端。
- 通过标准：格式错误返回 `0x90/0x03`，地址越界返回 `0x90/0x02`，不调用 CPU2 写网关。

### 4.19 CPU3 将寄存器对转换为本机 32 位值

- 源码位置：`CPU2_CommWriteHoldingRegisters()`。
- 改前问题：外部 Modbus 的高字/低字序列不能直接当本机 `uint32_t[]` 使用，否则数值和线序会颠倒。
- 具体改法：每两个 16 位寄存器组合为 `(high << 16) | low`，再调用既有 `CPU2_CombinatePackage_Send()` 负责板间线序。
- 必查边界：最大 122 寄存器、NULL、0、奇数地址/数量、超窗口、命令值 0/正常/保留值。
- 通过标准：契约脚本确认写网关存在且使用既有发送入口；CPU3 构建无栈数组越界警告。

### 4.20 CPU2 ACK 决定外部 FC10 成功或设备忙

- 源码位置：`CPU2_CommWriteHoldingRegisters()` 和 `ltd_handle_write()`。
- 改前问题：CPU3 若在 CPU2 未确认时先回成功，会造成主站认为参数/命令已生效。
- 具体改法：只有 `CPU2_CombinatePackage_Send()` 返回 true 才回显起始地址和数量；门禁、超时、非法 ACK 或写失败统一返回设备忙 `0x06`。
- 必查边界：CPU2 离线、协议不匹配、响应超时、ACK CRC/地址/功能码/回显错误、正常 ACK。
- 通过标准：正常返回 `01 10 ...`；失败返回 `01 90 06 ...`，不会返回伪成功。

### 4.21 参数写成功后强制补读确认

- 源码位置：`CPU2_CommRequestParameterRefresh()`、`PollingInputData()`。
- 改前问题：即使 ACK 成功，CPU2 仍可能对参数执行归一化；直接保留请求影子不能代表 CPU2 最终值。
- 具体改法：除“仅写命令字段”外，成功写入也关闭参数快照并设置主动全量补读；补读完成前 LTD 读取返回设备忙。
- 必查边界：单字段参数、多字段参数、CPU2 归一化、补读期间重复读写、补读失败后恢复。
- 通过标准：参数写成功后 `s_cpu2_parameter_refresh_requested` 触发从索引 0 补读；外部只能在确认完成后读到最终值。

### 4.22 命令字段单独写入的快照处理

- 源码位置：`CPU2_CommWriteHoldingRegisters()` 的 `command_only` 分支。
- 改前问题：命令是瞬时字段，按参数路径关闭整份快照会造成不必要的长时间读门禁；不更新镜像又可能短暂回读旧命令。
- 具体改法：仅当起始地址为命令且数量为 2 时，在 CPU2 ACK 后更新 `g_deviceParams.command` 和保持寄存器镜像，不触发参数全量补读。
- 必查边界：命令与参数跨区写、命令写失败、命令保留值、随后 CPU2 状态轮询。
- 通过标准：纯命令 ACK 后保持快照可用；任何写失败仍返回设备忙；混合写按参数补读路径处理。

### 4.23 LTD 异常码和 golden frame 契约

- 源码位置：`ltd_modbus_slave.h`、`tools/check_ltd_modbus_contract.py`。
- 改前问题：没有稳定自动契约时，功能码、异常码、CRC、协议版本或 ACK 闭环容易后续漂移。
- 具体改法：集中定义 03/04/10 和 01/02/03/06；增加 11 组请求、成功响应和异常响应参考帧及源码正则检查。
- 必查边界：非法功能、非法地址、非法值、设备忙、CPU2/CPU3 协议版本不一致。
- 通过标准：脚本输出 `[OK]`；CPU2 和 CPU3 协议版本都为 14；所有参考帧 CRC 一致。

### 4.24 流程影响反向索引

- 源码位置：`tools/check_flow_impact.py`、`docs/00_程序流程导航/流程证据清单.json`、`业务链路清单.json`。
- 改前问题：固件提交是否需要更新流程页依赖人工记忆，容易遗漏跨 CPU 入口和验证资料。
- 具体改法：按源码路径反查核心流程页、业务链路和验证资料；支持工作区、暂存区、revision range、显式文件、JSON 和 strict 模式。
- 必查边界：版本头不算业务源码、未映射源码只提示、命中页面未更新、证据清单本身更新、重复 page key 和断链。
- 通过标准：当前清单构建 18 个核心流程、8 条业务链路；单元测试覆盖命中、未命中、strict 复核和证据清单确认。

### 4.25 版本门禁联动流程影响检查

- 具体改法：版本检查运行时调用当前 Python 执行 `check_flow_impact.py --staged`，转发 stdout/stderr，分析失败时使版本门禁失败。
- 必查边界：脚本缺失、清单 JSON 无效、子进程非零、没有固件源码、已有版本错误与流程错误同时出现。
- 通过标准：对应单元测试确认命令固定使用 `--staged`，失败能传播到主门禁。

### 4.26 流程 HTML 表格和 SVG 可访问性契约

- 具体改法：表格增加可聚焦 viewport、caption/hint ARIA 关联和方向键滚动；SVG 标记 `aria-hidden/focusable=false`，由外层 viewport 关联描述；统一脚本放在 body 最后；CPU3 生成器直接输出相同契约，避免重新生成后退回旧属性和旧脚本位置。
- 必查边界：无表格页、多表格 ID、相对资源路径、重复属性、viewport 缺提示、脚本重复、生成两遍是否产生差异。

## 5. 跨模块数据流和异常闭环

### 5.1 LTD 读取

`外部 COM RTU 帧 -> CPU3 端口分发 -> ltd_modbus_process -> 地址/CRC/长度/范围校验 -> CPU2_CommRead*Snapshot -> CPU2_CommIsAvailable -> 已确认数组 -> 标准 FC03/FC04 响应`

任一 CPU2 快照、协议或通信门禁失败：`CPU2_CommRead*Snapshot=false -> LTD 0x06 -> 外部主机等待补读并重试`。

### 5.2 LTD 写入

`外部 FC10 -> byteCount/实际长度/偶数对齐 -> 16 位寄存器对合成 uint32_t -> CPU2_CombinatePackage_Send -> CPU2 合法 ACK -> 命令镜像更新或参数快照失效补读 -> 外部成功响应`

CPU2 未确认：`发送/ACK 失败 -> 不提交本地成功影子 -> LTD 0x06 -> 主机重试并回读`。

### 5.3 CPU2 串口命令

`USART1 DMA IDLE -> ISR 逐字节收帧 -> READY/TOO_LONG 标志 -> 主循环复制 -> 严格分类 -> ACK/ERR -> 正式命令挂主循环或合法测试动作/只读查询`

非法命令：`解析 INVALID/UNSUPPORTED -> ERR -> 不调用 MeasureStart、不改 g_deviceParams.command、不执行测试动作`。

## 8. 复杂场景分步验证

### 8.1 CPU2 断线期间 LTD 读写和恢复

1. CPU2/CPU3 正常上电，等待状态、参数、协议快照全部建立。
2. FC03/FC04 各读一次并保存成功响应。
3. 断开 UART5 或关闭 CPU2，持续发起请求直到 CPU3 锁存通信故障。
4. 确认 FC03、FC04、FC10 都返回 `0x06`，不返回断线前快照或伪成功。
5. 恢复 CPU2，观察状态快照、参数全量补读和协议版本 14 依次重建。
6. 补读期间继续请求，应仍返回 `0x06`；全部完成后恢复正常数据。

通过标准：断线时不暴露旧数据；恢复必须重新建立完整门禁；正常响应只能在确认完成后恢复。

### 8.2 参数写成功、ACK 丢失和最终回读

1. 选一个安全、可回读且 CPU2 可能归一化的参数，记录原值。
2. 正常 FC10 写入，确认 CPU2 ACK 后外部回成功，CPU3 立即关闭参数快照。
3. 补读完成前连续 FC03，确认返回 `0x06`。
4. 补读完成后读取，确认值等于 CPU2 实际值而不是请求影子。
5. 注入 ACK 丢失或错误回显，确认外部 FC10 返回 `0x06`；恢复通信后等待强制补读并读取最终值。

通过标准：无论 ACK 成功或丢失，最终展示值都来自补读；CPU3 不用未确认请求值伪装成功。

### 8.3 串口高速输入、超长和 STOP

1. 发送 VER?、STAT?，保存基线。
2. 发送合法手动小距离命令，确认 ACK 和动作。
3. 动作期间发送 STOP，确认主循环取消路径生效。
4. 发送 64 字节以上命令并以 LF 结束，确认只有 TOO_LONG，没有任何前缀动作。
5. 紧接着发送 HELP，确认接收状态恢复。
6. 一次性高速发送两行，记录单槽接收器是否丢弃第二行，作为现场工具节流依据。

通过标准：超长不执行；STOP 可中止；恢复后下一帧正常；工具按“一次一条、等 ACK/ERR”约束运行。

### 8.4 流程门禁闭环

1. 仅暂存一个已登记的固件源码，不暂存对应流程页。
2. 运行 strict 影响检查，确认报告受影响页面并失败。
3. 暂存对应流程页或更新证据清单后重跑。
4. 运行版本门禁，确认其自动输出暂存区流程影响报告。
5. 运行导航生成器检查两次，确认第二次没有变化。

通过标准：缺失流程复核能被阻止；补齐后通过；生成器保持幂等。

## 11. 风险与未验证项

- LTD 尚未使用真实 PLC 和 RS485 收发器验证；串口参数、长帧时序、主站重试间隔和现场噪声下 CRC 行为仍需实机确认。
- CPU2 单次同步写最长可能等待既有 1000 ms 响应超时；外部主站超时必须大于设备内部等待或允许收到稍后的 `0x06`。
- 参数 FC10 不是跨字段事务；CPU2 可能在通信失败前已应用部分字段，最终状态只能以恢复后的全量补读为准。
- CPU2 串口接收为单帧槽；上一帧未取走时 ISR 丢弃后续字节。命令面板必须一次发送一条并等待 ACK/ERR，不能批量粘贴多行。
- 忽略 CR 的收帧策略用于兼容 CRLF；现场应继续使用规范 CRLF 或 LF，不应在命令正文中插入 CR。
- STOP 是否能立即退出取决于具体旧测试循环是否检查命令切换；已登记循环具备检查点，但仍需逐个台架验证最大响应时延。
- 流程 HTML 可访问性已通过结构契约和单元测试，尚未用真实读屏软件和多浏览器逐页复核。
