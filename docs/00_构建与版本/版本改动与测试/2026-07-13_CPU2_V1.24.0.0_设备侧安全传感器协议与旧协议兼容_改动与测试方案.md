# CPU2 V1.24.0.0 设备侧安全传感器协议与旧协议兼容改动与测试方案

## 1. 文档目的和适用版本

本文用于复核和验证 CPU2 新一代安全传感器协议设备侧实现。适用固件为 CPU2 `V1.24.0.0`，CPU3 保持 `V1.22.0.0`。本文随本次提交纳入，提交哈希以 Git 记录为准。

本次结论限定为“CPU2 设备侧代码、协议机器契约和主机测试已实现并通过列出的验证”，不表示传感器端已交付，不表示真实 200 米链路已验证，也不表示整机满足或通过任何 SIL 认证。

## 2. 版本与兼容性

- CPU2：`V1.23.0.0 -> V1.24.0.0`，新增设备侧协议能力，升级 MINOR。
- CPU3：保持 `V1.22.0.0`，没有 CPU3 源码变化。
- CPU2/CPU3 共享协议：`DEVICE_PROTOCOL_VERSION=15`，保持不变。
- 不升级共享协议的依据：`sensorType` 的地址、宽度和 u32 布局不变；CPU3 只原样缓存、同步和打印该值，不按 `SAFE_SENSOR=14` 做分支消费；本次没有新增共享命令、状态、寄存器或双方消费语义。
- CPU2 参数存储：`DEVICE_PARAM_VERSION=3`，保持不变；`DeviceParameters`、`struct_size`、FRAM A/B 地址、元信息和 CRC 范围不变，从 V1.23.0.0 升级不会恢复出厂参数。
- 传感器安全通信协议：线上版本保持 V1；`READ_PARAM_PAGE(0x63)` 是由 `CAP_PARAM_RW` 单独声明的兼容扩展，没有该能力的原 V1 传感器仍可激活并执行既有测量。
- 降级边界：旧 CPU2 固件不识别 `SAFE_SENSOR=14`，降级前应将传感器类型恢复为旧固件支持的 DSM 或 LTD 类型并记录现场配置。
- 旧协议：DSM、LTD/V2 源文件和业务入口均保留，自动识别在安全协议失败后继续执行 LTD/V2 和 DSM 探测。

## 4. 详细改动点

### 4.1 固定帧、CRC32C 和严格解码

- 源码位置：`sensor_safe_crc32c.*`、`sensor_safe_frame.*`、`sensor_safe_types.h`。
- 改前问题：旧协议没有冻结的新一代安全帧头、CRC32C、固定快报长度和保留位门禁，无法对重复、乱序、错误长度和字段错位形成统一机器契约。
- 具体改法：实现控制帧固定偏移编码/解码、44 字节快报、CRC32C、SOF、协议/负载版本、保留位、地址、命令、长度和质量字段检查；拒绝非零保留字段和范围外质量值。
- 必查边界：零长度、最大控制负载、短头、长帧、错误 SOF、错误 CRC、错误地址、错误协议版本、错误固定快报长度、非零保留位。
- 通过标准：55 个控制 golden vector 和 7 个快报 vector 全部通过；CPU2 C 常量和 JSON 字段偏移一致。

### 4.2 HELLO、会话和序号连续性

- 源码位置：`sensor_safe_session.*`、`sensor_safe_client.*` 的 HELLO、事务和周期流处理。
- 改前问题：旧协议不能证明响应属于当前请求/当前启动周期，也没有冻结的事务重试和周期流重复、跳号、乱序拒绝规则。
- 具体改法：会话绑定双方 ID、启动计数、nonce 和传感器会话计数；请求使用 u32 `seq`，同事务重发复用序号并置重试标记；周期流使用独立 `stream_seq`，拒绝重复、乱序、跨会话和过期样本。
- 必查边界：首个序号、最大序号、回绕前停止、重复响应、错误命令回显、旧会话回放、HELLO 身份字段变化、周期首帧和跳号。
- 通过标准：主机测试对上述异常均返回明确协议错误，失败帧不更新安全测量快照。

### 4.3 启动身份和 FRAM A/B 双副本

- 源码位置：`sensor_safe_identity.*`、`sensor_safe_identity_platform.*`。
- 改前问题：CPU2 缺少跨掉电单调启动计数和可复核 nonce 来源，无法把安全会话绑定到本次真实启动。
- 具体改法：在独立 FRAM 地址维护 0x40 字节 A/B 记录，包含 generation、boot counter、CRC 和 0xFF 保留区；加载合法较新副本、递增后写入另一槽并回读；优先硬件 RNG，失败时使用带来源标志的确定性后备 nonce。
- 必查边界：双槽空白、单槽损坏、双槽 CRC 错、generation 新但 boot counter 不增、SPI 命令/地址/数据阶段失败、写后回读不一致、RNG 失败。
- 通过标准：合法副本可恢复并修复镜像；单调性冲突和 I/O 错误阻止 HELLO；所有 SPI 出口释放片选。

### 4.4 UART6 DMA 传输和 CH9141 仲裁

- 源码位置：`sensor_safe_transport_uart6.*`、`ch9141_at.c`。
- 改前问题：新协议与 CH9141 共用 UART6，若 DMA、超时、取消或 AT 切换边界未统一清理，可能遗留 busy、误收旧帧或阻断旧协议探测。
- 具体改法：先启动 DMA 接收再发送，按 SOF/长度提取控制帧或 44 字节快报；对噪声、非法长度和伪前缀重同步；超时、取消、RX/TX 启动失败和硬件错误统一释放状态；进入 CH9141 AT 前主动 Abort。
- 必查边界：PE/NE/FE/ORE、DMA 错误、BREAK、短帧、满缓冲、合法长度但未收全的伪前缀、后续完整帧、命令切换取消、TX/RX 启动失败。
- 通过标准：UART6 产品源文件主机桩测试全部通过；异常后下一事务可启动；旧 LTD/DSM 探测仍可继续。

### 4.5 服务、能力和配置摘要门禁

- 源码位置：`sensor_safe_service.*`、`sensor_safe_client.*`。
- 改前问题：仅 HELLO 成功不能证明传感器当前配置和整机所需能力一致；模糊结果命令自动重放可能造成重复副作用。
- 具体改法：HELLO 后立即读取并逐字段核对配置摘要；密度、液位和组合读能力为整机必需能力；只读事务允许至多一次新 HELLO 和一次业务重试；副作用命令只有可信 `BAD_SESSION` 或 `CONFIG_MISMATCH` 明确证明未执行时才进入单次恢复。
- 必查边界：摘要读取失败、摘要字段不一致、配置纪元 0、缺少必需能力、传输模糊失败、普通远端错误、周期流活动期间普通请求。
- 通过标准：摘要不一致和能力不足不激活服务；模糊副作用结果不跨会话重放；最终失败交给既有故障出口。

### 4.6 安全快照和时效撤销

- 源码位置：`sensor_safe_monitor.*` 及 service 周期流入口。
- 改前问题：周期快报若直接覆盖业务变量，半写、过期、错模式或诊断异常数据可能被误用。
- 具体改法：使用双缓冲发布完整快照；分别判断通信活性、传感器样本年龄和 CPU2 本地年龄；模式、状态、质量、诊断、流故障或超时异常立即撤销有效性并清零输出。
- 必查边界：首次快报、连续快报、错模式、低质量、状态异常、流跳号、过期、错误后恢复、计数饱和。
- 通过标准：任何门禁失败都不会发布有效安全值；恢复前必须重新满足会话和连续有效数据条件。

### 4.7 旧业务适配和自动识别回退

- 源码位置：`sensor_safe_legacy_adapter.*`、`sensor.c`。
- 改前问题：直接改写现有 DSM/LTD 文件会放大回归范围；安全探测失败若不释放 UART6 或不保留原始原因，会影响旧设备识别和故障定位。
- 具体改法：新增独立适配层映射既有错误码和测量接口；识别顺序为蓝牙链路、安全 HELLO、LTD/V2、DSM；安全失败主动 Deactivate；最终错误选择同时纳入 safe/LTD/DSM 三路结果并优先保留具体非超时错误。
- 必查边界：安全传感器成功、非安全设备无响应、错误 CRC、格式错误、安全失败后 LTD 成功、安全和 LTD 失败后 DSM 成功、三路均失败、命令切换取消。
- 通过标准：`SAFE_SENSOR=14` 只在安全成功时保存；旧设备仍能被原路径识别；失败日志序号为 1/4 至 4/4；最终错误不丢失安全协议具体原因。

### 4.8 生产测量、回零和诊断分发

- 源码位置：`measure_oilLevel.c`、`measure_zero.c`、`test.c`、`sensor.c`。
- 改前问题：新增传感器类型若只完成探测，液位、密度、回零能力和串口诊断仍会误走 LTD/V2 分支。
- 具体改法：液位频率和密度读取分发到安全适配器；水位电容和姿态按 HELLO 能力分别判断；回零只在相应能力存在时读取；读取部件参数按能力填充；串口通信诊断新增安全协议组合读取。
- 必查边界：仅水位电容能力、仅姿态能力、两者均无、服务未激活、读取超时、无效数据、旧 DSM 和 LTD 设备。
- 通过标准：安全设备走声明能力对应接口；不支持的辅助能力被跳过或返回参数错误，不误阻断其它测量；旧协议分支不变。

### 4.9 安全代码中文注释与审计约束

- 源码位置：`LTD_MAIN_CPU2/Services/Sensor/SafeProtocol/` 的 21 个 `.c/.h` 文件，重点为 `sensor_safe_client.c`、`sensor_safe_session.c`、`sensor_safe_transport_uart6.c` 和 `sensor_safe_identity.c`。
- 改前问题：初版实现的大部分新增函数没有中文函数注释，关键安全判断缺少“为什么拒绝、为什么恢复或为什么必须失效”的维护依据，不符合项目 skill 对新增函数和复杂分支的注释要求。
- 具体改法：为全部函数定义补充中文用途、调用场景或关键约束；为线格式、同序号重试、可信 ERR、防重放、FRAM 双副本、UART6 清理、参数分页、周期静默预算、参数提交后重建会话和旧协议回退增加就地说明；所有 C/C++ 注释使用 `/* ... */`。
- 必查边界：检查没有 `//`、UTF-8 中文无替换字符或 `??`、注释不声称未实现能力、去除注释和空白后执行代码与整改前暂存版本一致。
- 通过标准：函数定义注释覆盖检查无遗漏；双斜杠扫描为 0；注释前后语义源码比较一致；主机测试、`-fanalyzer` 和 CPU2 clean-first 构建继续通过。

### 4.10 LTD 完整参数表分页读取

- 源码位置：`sensor_safe_types.h` 的分页常量和 `READ_PARAM_PAGE(0x63)`；`sensor_safe_client.*` 的 `SensorSafeClient_ReadAllParams`；`sensor_safe_service.*` 的 `SensorSafeService_ReadAllParams` 和固定映射校验；`sensor_safe_legacy_adapter.*` 的 `SensorSafeAdapter_ReadAllParams`。
- 改前问题：原 V1 只具备按 ID 读取单项参数的底层接口，CPU2 无法用一次业务调用取得 LTD 的 115 项完整参数；若由上层发起 115 次单读，会放大往返次数、暴露部分表并增加调用复杂度。
- 具体改法：新增每页最多三项的 `READ_PARAM_PAGE`，client 在一次逻辑调用内自动完成 39 页读取，固定核对参数表版本 2、首帧总数、后续总数一致、游标前进、末页、保留标志、页内/跨页严格升序和逐项 CRC；service 再核对 115 项 `param_id=0x1000..0x1072`、`param_index=0`、类型、读写权限、`scale` 和 `unit_id`；adapter 统一映射容量不足和恢复日志。没有 `CAP_PARAM_RW` 时仅完整表接口返回不支持，不影响原 V1 测量，也不回退为 115 次单读。
- 必查边界：调用方容量小于 115、无参数能力、未知参数表版本、短表或长表、总数跨页漂移、空的非末页、游标停滞、非零保留标志、页内乱序、跨页重复、末页提前或缺失、单项 CRC 错、第一页以后失败和只读恢复一次。
- 通过标准：容量不足时不发帧且 `value_count_out=115`；任一分页或元数据校验失败时整表不发布且计数归零；115 项真实规模在 39 页后一次性返回，所有地址、解释元数据和 CRC 与冻结映射一致。

## 5. 数据流和异常闭环

1. 上电先检查 CH9141 蓝牙链路，确认 UART6 可进入传感器探测。
2. CPU2 通过安全 HELLO 建立身份绑定会话，并读取配置摘要确认能力和参数身份。
3. 安全探测成功后保存 `SAFE_SENSOR=14`；失败则释放传输状态并继续 LTD/V2、DSM 探测。
4. 生产测量通过旧业务适配层调用安全 client/service；帧、会话、摘要、模式、质量或时效任一门禁失败时不更新有效测量。
5. 上电同步或维护导出显式调用 `SensorSafeAdapter_ReadAllParams` 时，client 自动读取 39 页，service 完成固定 115 项解释校验后才一次性发布整表；生产测量循环不会自动触发该长事务。
6. 只读事务按受控边界尝试一次恢复；副作用事务的模糊结果不自动重放。
7. 适配层将结果映射为既有错误码并记录重试/恢复；最终失败仍由现有 `fault_manager` 统一处理。
8. CPU3 只接收既有 u32 `sensorType` 和现有测量结果，不参与安全传感器协议解析。
