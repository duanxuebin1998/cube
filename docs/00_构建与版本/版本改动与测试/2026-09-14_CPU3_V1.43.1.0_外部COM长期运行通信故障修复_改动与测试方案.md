# CPU3 V1.43.1.0 外部 COM 长期运行通信故障修复改动与测试方案

## 1. 文档目的和适用版本

本方案对应 MAIN 分支的 CPU3 `V1.43.1.0` 固件。CPU2 配套版本保持 `V1.44.0.0`。目标是修复外部 COM 启动保护状态在 `HAL_GetTick()` 长期运行回绕后可能重新变为未就绪，导致 COM1/COM2/COM3 不再处理协议帧的问题。

本次提交只改变 CPU3 外部 COM 启动保护状态的判定和版本资料，不改变 CPU2 程序、CPU2/CPU3 共享协议字段、外部协议帧格式、参数地址或参数存储布局。

## 4. 详细改动清单

### 4.1 外部 COM 就绪状态跨 tick 回绕保持有效

- 源码位置：`LTD_DISPLAY_CPU3/Application/app_main.c` 的 `s_external_ports_start_tick`、`s_external_ports_ready` 和 `cpu3_external_ports_startup_ready()`；调用链为 `App_Init()` -> `App_MainLoop()` -> `cpu3_uart_rx_recovery_task()`/COM1～COM3 协议分发。
- 改前问题：初始化完成后保存未来截止 tick，并用 `(int32_t)(HAL_GetTick() - 截止tick) >= 0` 判断。长期运行跨 32 位 tick 回绕时，已达到保护时间的端口可能再次被判为未就绪，主循环仍运行但不再消费外部 COM 接收帧，现场表现为电流和屏幕正常、通信无响应。
- 具体改法：初始化完成后保存 `s_external_ports_start_tick = HAL_GetTick()`；每轮用 `(uint32_t)(HAL_GetTick() - s_external_ports_start_tick) >= CPU3_EXTERNAL_PORT_STARTUP_GUARD_MS` 判断经过时间；条件满足后置位 `s_external_ports_ready` 并保持为真。`App_Init()` 重新进入时先清零锁存状态，再在三路外部串口初始化完成后重新开始计时。
- 必查边界：启动后 0 ms、999 ms、1000 ms 和更晚时刻；`HAL_GetTick()` 在 `0xFFFFFFFF -> 0` 回绕前后；主循环继续运行但外部端口未就绪；三路端口同时有帧；重复调用就绪判断；重新执行 `App_Init()`；保护期间 CPU2 板间通信、屏幕和日志任务不得被阻塞。
- 通过标准：保护期内不消费 COM1/COM2/COM3 协议帧；达到 1000 ms 后开始消费；tick 回绕后 `s_external_ports_ready` 不回退；屏幕任务和 CPU2 轮询持续执行；源码中不再使用旧的有符号截止 tick 判断。

### 4.2 CPU3 补丁版本和发布资料同步

- 源码位置：`LTD_DISPLAY_CPU3/Application/app_version.h`、`CHANGELOG.md`、售后版本记录和本方案。
- 改前问题：行为修复若沿用旧版本号，会使现场无法区分包含回绕修复的程序包。
- 具体改法：CPU3 `V1.43.0.0` 升为 `V1.43.1.0`；CPU2 保持 `V1.44.0.0`；协议和两端参数存储版本保持原值。售后表新增最新记录，改动点使用现场可理解的现象和修复描述。
- 必查边界：版本头四个字段与字符串一致；CHANGELOG、测试方案和售后表版本一致；协议37、CPU2 参数存储版本3、CPU3 参数版本0x0007 均未误升；升级说明不要求清参数。
- 通过标准：版本脚本识别 CPU3 PATCH 升版；三份发布资料均写出 `V1.43.1.0` 和 `V1.44.0.0` 配套关系；提交标题包含双端版本号。

## 5. 跨模块数据流和异常闭环

1. `App_Init()` 记录 CPU3 启动时间并初始化显示、RTC、FRAM 参数、三路外部串口和 DSM 通信。
2. 三路外部串口初始化完成后记录 `s_external_ports_start_tick`，启动保护窗口为 1000 ms。
3. `App_MainLoop()` 每轮先报告看门狗进度，再计算外部 COM 就绪状态；保护期间仍执行 UART 接收异常恢复、显示、CPU2 板间轮询和日志任务。
4. 就绪后，COM1/COM2/COM3 各消费一帧接收数据，按现有协议处理器生成响应，DMA 发送完成回调按既有路径恢复接收。
5. UART 错误、接收溢出、发送失败和协议处理失败仍沿用原错误统计和恢复路径；本次不把通信错误改成“成功”，也不修改看门狗喂狗逻辑。

## 6. 测试环境和前置条件

- 主机：Windows，CMake + Ninja + `arm-none-eabi-gcc`。
- 固件：CPU3 `V1.43.1.0` Debug，CPU2 配套 `V1.44.0.0`。
- 构建目录：`build/LTD_DISPLAY_CPU3`，使用独立 CPU3 子工程 clean-first 构建。
- 台架：CPU3 三路外部 COM 接入可配置的 RS485 主站，能够连续发送有效请求、记录响应和时间戳；另接 CPU2 板间通信和 OLED 观察点。
- 诊断：保留 CPU3 启动保护日志、端口收发统计、UART 错误统计和发送完成计数；需要时在测试固件中提供可控 tick 回绕注入，不把注入宏带入发布构建。

## 8. 复杂场景分步验证

### 8.1 长时间运行和回绕场景

1. 上电并确认启动日志打印 `V1.43.1.0`、协议37以及外部 COM 初始化完成。
2. 在保护窗口内发送 COM3 合法请求，确认不会因为初始化阶段而执行协议响应，同时确认 OLED 刷新和 CPU2 板间状态继续变化。
3. 保护结束后持续发送 COM3 请求，记录每一笔请求、响应、响应时间、发送完成计数和 UART 错误计数。
4. 让 tick 跨过 32 位回绕，或在受控测试固件中将 tick 起点设到回绕前，重复发送请求并检查 `s_external_ports_ready` 不回退。
5. 继续运行至 24 h，期间加入短时断链、恢复、重复请求和三口并行流量，确认一次异常不会造成永久停收。
6. 测试结束读取看门狗复位原因、端口统计和日志；任何复位、永久无响应或统计停止均判定失败并保留原始记录。

### 8.2 发送完成和接收恢复场景

1. 主站按 COM3 当前协议发送会产生短响应和长响应的请求。
2. 在 DMA 发送期间发送下一帧请求，确认单帧 pending 队列及发送完成回调按现有逻辑工作。
3. 在最后一帧发送完成后立即发送下一帧，确认方向控制恢复接收，后续帧仍能被消费。
4. 记录发送完成回调次数与响应数量；计数单调增加且无永久 busy 即通过。
