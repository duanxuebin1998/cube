# CPU2 V1.36.4.0 DSM与UART6通信修复改动与测试方案

## 1. 文档目的和适用范围

本文记录CPU2从V1.36.3.0升级到V1.36.4.0时，DSM一代文本通信、CH9141K AT/透传交接、无线状态查询错误传播以及无丢步日志读取节流的实际代码变化和验证方法。

本次只修改CUBE CPU2，不修改DSM传感器端程序，不改变CPU3固件，不引入新的自动协议探测步骤。本文随本次提交纳入，提交哈希以Git记录为准。

## 4. 详细改动

### 4.1 建立DSM命令级固定帧规格

- 源码位置：`dsm_sensor_communication.c`的`DsmCommandFrameSpec`、`s_dsm_frame_specs`、`DSM_GetExpectedFrameLength()`和`UART6_WaitTextReceiveDma()`。
- 改前问题：旧接收路径遇到首个`0x0A`就结束；当原始BCC恰好为`0x0A`时，`CN`或`Cb`会被提前截断并报格式或BCC错误。`CV/Cv`没有CRLF，会一直等到超时。
- 具体改法：为`CL/CB/CD/CV/Cv/CN/CK/Cb/Cd/Ch/Cl`登记正常长度、错误长度、帧类型和日志操作名；数据命令收到首字节`A`时按19字节错误帧接收，其余按正常长度接收；DMA额外保留一个字节用于发现已经进入缓冲区的超长帧。
- 必查边界：BCC为`0x00/0x0A/0x0D`、零字节、全长度短一字节、超长一字节、无CRLF版本帧、19字节错误帧和未知命令。
- 通过标准：合法帧不因BCC内容提前结束；短帧和超长帧返回格式错误；`CV/Cv`六字节帧能在事务层完成，不改变生产探测顺序。

### 4.2 严格校验ACK、字段、BCC和CRLF

- 源码位置：`dsm_sensor_communication.c`的`DSM_ValidateFixedFrame()`、`DSM_IsSevenDigitInteger()`、`DSM_IsSevenDigitValue()`、`DSM_IsSignedSevenDigitValue()`和`DSM_ParseSevenByteFloat()`。
- 改前问题：模式ACK只判断响应是否包含`%`；数值使用`atof/strtod`直接从帧内地址继续读取，原始BCC为ASCII数字时可能被继续消费；中间版本错误地要求`Cd`频率必须带小数点。
- 具体改法：`CL/CB/CD`只接受精确`25 0D 0A`；正常数据帧逐字节校验标签、七字节字段、BCC和CRLF；`Cd`频率允许六位整数或小数，密度和温度必须带一个小数点；数值复制到八字节本地缓冲区后限长解析。
- 必查边界：额外`%`、缺少CRLF、错误标签、频率`+000000`、密度或温度无小数点、BCC为数字字符、NaN/Inf文字和字段错位。
- 通过标准：现场帧`F+000000D+0000.0T+26.590`通过；异常ACK和错位帧不能进入业务解析。

### 4.3 锁存UART6硬件错误

- 源码位置：`dsm_sensor_communication.c`的`UART6_StopDmaReceive()`、`UART6_TakeHardwareError()`和事务完成检查。
- 改前问题：停止DMA会清除`huart6.ErrorCode`，最后几个字节附近的FE、NE、ORE或PE可能被误报为格式/BCC错误，日志中的`uart`字段仍为0。
- 具体改法：停止DMA前后把HAL错误位合并到本事务快照；协议解析前消费锁存值；收到硬件错误后禁止部分数据继续进入协议解析。
- 必查边界：接收中错误、最后字节附近错误、停止DMA过程中新增错误、无数据超时和部分帧超时。
- 通过标准：契约检查确认锁存顺序存在；目标板错误注入时应返回UART传输错误并保留非零HAL位图。

### 4.4 完整映射DSM错误并改进日志

- 源码位置：`dsm_sensor_communication.c`的`s_dsm_response_errors`、`DSM_MapErrorResponse()`和`UART6_SendWithRetry()`。
- 改前问题：错误6、7满足正常倾角格式，可能被当作`666.66°/777.88°`；所有DSM重试日志都显示“读取液位”。
- 具体改法：错误6、7映射为`SENSOR_REMOTE_INTERNAL_ERROR`；错误帧必须是精确19字节并具有CRLF；重试、恢复和失败日志的操作名来自当前命令规格。
- 必查边界：错误1至9、未知16字节载荷、低电压`E/e`编号帧、不同命令的重试和恢复日志。
- 通过标准：错误6、7不进入角度解析；`CN/CD/Cd/Ch/Cl`日志分别显示真实业务操作。

### 4.5 建立CH9141K与DSM共用UART6的交接状态机

- 源码位置：`ch9141_at.h/.c`的`CH9141Uart6LinkState`、`CH9141_AT_GetUart6LinkState()`、`CH9141_AT_CompleteTransparentHandoff()`、`CH9141_AT_RecoverRssiQuery()`和AT发送/恢复路径。
- 改前问题：AT退出或复位后的排空过程可以被命令切换打断；函数返回后UART6可能永久停在`NOT_READY`或仍有异步RSSI文本，随后DSM模式切换连续返回`0x000D0021`。
- 具体改法：显式维护`TRANSPARENT_READY/ENTERING_AT/AT_ACTIVE/RECOVERING/NOT_READY`；AT退出、复位和强制恢复使用不可中断的最终交接；恢复步骤保留第一个具体错误，只有完整排空成功才发布`TRANSPARENT_READY`。
- 必查边界：正常AT退出、半ACK、无ACK、命令切换、RSSI关闭失败、AT退出失败、HAL abort失败、持续异步文本和恢复后二次DSM访问。
- 通过标准：交接未完成时DSM不能抢占；失败状态可在下一次DSM事务前进行一次有界恢复，不会无限恢复或永久锁死。

### 4.6 无线状态查询和部件参数读取传播交接错误

- 源码位置：`wireless_pairing.c`的连接状态查询/打印/扫描收尾；`sensor.c`的`Sensor_UpdateWirelessRssiForPartParams()`和`Sensor_ReadPartParamsInternal()`。
- 改前问题：RSSI关闭、AT退出或透明交接失败后仍可能继续读传感器；部件参数流程会打印失败但把返回值改回`NO_ERROR`。
- 具体改法：无线流程检查强制恢复和透明交接结果并保存具体错误；部件参数流程在透明传输未确认时立即返回错误，停止后续DSM访问。
- 必查边界：未连接、RSSI无有效数值但交接成功、恢复失败、命令切换、查询错误和原始错误优先级。
- 通过标准：只有UART6已确认恢复透明传输时才能继续读传感器；RSSI数值无效与链路交接失败得到不同结果。

### 4.7 避免无丢步日志连续占用UART6

- 源码位置：`motor_ctrl_lost_step_detect.c`的`MotorLostStep_NoDetectRuntimeLogUpdate()`。
- 改前问题：密度读取前更新周期时间戳；若一次UART事务耗时较长，返回时下一周期可能已到，主循环会立即再次读取。
- 具体改法：在`Read_Density()`阻塞调用结束后用新的`HAL_GetTick()`更新周期起点。
- 必查边界：快速成功、三次重试、模式恢复、通信超时和命令切换。
- 通过标准：下一轮间隔从本次读取结束时开始计算，慢事务结束后不立即再次占用UART6。

## 5. 跨模块数据流和异常闭环

```text
部件参数/测量请求
  -> WirelessPairing进入CH9141K AT状态
  -> RSSI关闭、AT退出或模块复位
  -> CompleteTransparentHandoff确认UART6透明链路
  -> DSM事务检查链路状态
       READY：按命令启动定长DMA
       NOT_READY：执行一次有界恢复后重试
       其它AT状态：返回模式未就绪，禁止抢占
  -> 固定长度、字段、BCC、CRLF和UART错误校验
  -> 正常数据/远端错误/本地通信错误向上传递
  -> ErrorLog按真实命令记录
```

## 8. 复杂场景验证步骤

### 8.1 正常设备综合验证

1. 记录CPU2启动打印、HEX文件名和SHA-256。
2. 冷启动设备，确认蓝牙主从机连接正常。
3. 连续执行`SC`20次，记录`CN`编号、`CD`成功和`Cd`数据。
4. 执行密度、油位、水位和倾角业务流程；没有测水探针时将水位流程明确标记为未测试。
5. 检查错误日志操作名是否分别对应编号、模式、频率、密度温度、倾角和电容读取。

### 8.2 断链与恢复

1. 在设备静止且允许断链的条件下断开蓝牙链路。
2. 执行一次`SC`或部件参数读取，保存预期通信失败日志。
3. 恢复蓝牙连接，等待连接状态稳定。
4. 再次执行`SC`，确认发生一次有界恢复或直接进入透明就绪。
5. 重复5轮；任何一轮持续返回`0x000D0021`或需要重启CPU2才能恢复均判定失败。

### 8.3 特殊BCC和硬件错误

普通传感器不能稳定主动制造BCC特殊值、非法ACK、错误6/7或UART FE/NE/ORE。这些边界由静态契约覆盖，但目标板硬件证据仍需可控串口应答器或故障注入环境；未执行时不得登记为实机通过。
