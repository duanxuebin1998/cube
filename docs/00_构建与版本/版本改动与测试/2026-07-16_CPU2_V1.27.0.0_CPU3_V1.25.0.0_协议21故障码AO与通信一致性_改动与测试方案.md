# CPU2 V1.27.0.0 / CPU3 V1.25.0.0 协议21故障码、AO与通信一致性改动与测试方案

## 1. 文档目的和提交状态

本文记录协议19、协议20在未单独发布的前提下，随协议21统一形成正式双端固件组合的全部行为变化、兼容性、测试方法、已执行验证和残余风险。适用固件为CPU2 V1.27.0.0、CPU3 V1.25.0.0，双端必须成对升级。

本文件随本次提交纳入，提交哈希以Git记录为准。源码、正式文档和本机流程资料已经按当前工作区整理；真实4～20 mA负载、HART主站、PLC、RS485、FRAM掉电故障和完整实机故障注入仍属于未验证项。

### 2.1 CPU2参数存储升级边界

- `DEVICE_PARAM_VERSION`保持3，`DeviceParameters`的总大小和持久化头不变，因此从V1.26.0.0升级不会仅因版本号清空现场参数。
- 原连续13个AO参数槽原位解释为`AoOutputConfig`。`migrate_ao_params_runtime()`按旧协议标记迁移合法的输出使能、液位量程、上电电流、故障电流和调试电流，其余新语义字段填入当前默认值。
- `normalize_ao_params_runtime()`和写参数校验负责限制枚举、量程、电流、阻尼和故障模式；输出源改变时同步生成对应过程量的默认量程。
- 现场升级前仍应导出AO参数；升级后核对工作模式、电流模式、输出源、0%/100%量程、故障电流、上电电流和仿真电流。不得把协议19/20镜像直接与协议21设备混用。

## 4. 详细改动点

### 4.1 协议19共享故障码治理

- 源码位置：双端`system_parameter.h`的故障枚举；CPU2 `error_log.c`及各测量、传感器、电机、AD5421/TMC5130产生路径；CPU3 `display.c`的详情显示和DSM错误投影。
- 改前问题：多类硬件、参数、测量计划和通信失败共用宽泛错误码，现场只能看见“大类失败”，无法稳定区分停机原因、恢复条件和历史编号代次。
- 具体改法：CPU2/CPU3同步当前共享数值与语义，拆分无线扫描/名称、传感器安全协议、参数存储、测量计划、罐高/水位、运动到位、AD5421和TMC5130等原因；同步名称、原因、详情文本、自动恢复分类和外部协议映射，历史编号冻结。
- 必查边界：双端数值一致、名称/原因覆盖、共享码与CPU3本机码边界、未知码兜底、协议18与21混搭、历史日志解释。
- 通过标准：静态清单无重复和缺失；CPU2产生的共享码在CPU3显示同一编号与原因；协议不匹配时不进入普通运行态。

### 4.2 自动恢复成功判定

- 源码位置：`LTD_MAIN_CPU2/Application/Src/fault_recovery.c`的`FaultRecovery_UpdateAfterCommand()`、`FaultRecovery_Poll()`及健康检查分支。
- 改前问题：部件健康检查通过或收到`STATE_SWITCH`可能被提前当成业务命令恢复成功，导致上下文清理和“重试成功”日志早于真实命令结果。
- 具体改法：健康检查只决定是否具备重跑条件；仅被恢复调度的原业务命令返回`NO_ERROR`时清理上下文并记录恢复成功；`STATE_SWITCH`只取消恢复，失败保留最后一次具体错误码并按次数处理。
- 必查边界：健康检查成功但业务失败、健康检查失败、命令切换、达到重试上限、非恢复白名单命令、初始化期与运行期电机错误。
- 通过标准：日志中的“重试成功”与原业务命令成功一一对应；取消不打印恢复成功；最终失败仍进入统一故障出口。

### 4.3 AO 13槽配置重构和旧值迁移

- 源码位置：CPU2 `system_parameter.h`的`AoOutputConfig`，`system_parameter.c`的`migrate_ao_params_runtime()`、`normalize_ao_params_runtime()`和写参数校验；双端Modbus映射文件。
- 改前问题：旧13槽只覆盖开关、液位量程和少量电流值，无法表达工作模式、电流模式、过程源、反向量程、阻尼、故障策略和仿真。
- 具体改法：13槽原位重解释为工作模式、电流模式、输出源、SIL/WHG预留、固定电流、0%/100%对应值、阻尼、故障模式、故障电流、错误级别、上电电流和仿真电流；按旧协议标记做一次兼容迁移和归一化。
- 必查边界：非法枚举、0%等于100%、反向量程、负值、储罐液位/空高/水位源切换、旧协议标记丢失、A/B槽只有一份有效。
- 通过标准：合法旧值被保留，新字段补默认值；非法组合被拒绝或归一化；非AO现场参数不变且不恢复出厂。

### 4.4 AO运行态、HART与AD5421闭环

- 源码位置：`ao_output.c`的`AoOutput_CommitRuntime()`、`AoOutput_SelectTarget()`、`AoOutput_UpdateInternal()`、`AoOutput_ProcessDeferredDiagnostics()`；`hart.c`；`ad5421.c/.h`。
- 改前问题：AO配置、过程样本、目标电流、最近成功下发电流和驱动诊断状态可能跨时刻读取；HART可在非从站模式应答；驱动访问、初始化、断环恢复和错误日志边界不完整。
- 具体改法：运行态和过程样本用短临界区整体发布；支持普通/NE/US/固定电流、反向量程、阻尼、故障回退、上电值和仿真旁路；AO禁用时拒绝直接开启仿真，从输出模式切为禁用时清除非持久化仿真状态；HART仅在HART从站模式应答，使用最后一次成功下发电流和真实量程百分数；AD5421增加访问门控、控制寄存器写后校验、故障寄存器读取、节流诊断和主循环延后日志/恢复。
- 必查边界：4/20 mA端点、反向量程、无效过程样本、故障保持/设值、断环/重接、过温、低压、SPI失败、定时器与主循环并发、HART模式切换。
- 通过标准：公开运行态字段来自同一提交；非HART模式不应答HART业务；驱动错误不在ISR直接打印；恢复后重新输出最后目标，控制与故障寄存器状态和诊断结果一致。

### 4.5 CPU3 AO五组菜单、成对写和失败回滚

- 源码位置：`display_tankopera.c/.h`的`menu_ao_channel()`、`menu_ao_range()`、`menu_ao_fault()`、`menu_ao_runtime()`、`menu_ao_diagnostic()`、`ao_write_range_pair()`和`ao_write_output_source()`；`device_param_sync.c`。
- 改前问题：AO项平铺、单位和值域不足，量程两端或输出源切换可能只写一半；CPU2拒绝、超时或补读失败后CPU3仍可能显示候选值。
- 具体改法：按通道、量程、故障、运行态和模拟五组组织；补选项、单位、只读和保护确认；量程成对写，输出源连同新默认量程整体写；仅CPU2 ACK和强制补读成功后提交，失败恢复旧运行态。
- 必查边界：0%/100%相等、源切换、通信首次失败、CPU2拒绝、补读失败、仿真开关失败、中文/英文长度、四行返回路径。
- 通过标准：失败后参数、运行态和页面一致回滚；成功后双端13槽一致；运行态页能区分无效输入、比例、最近成功下发电流和仿真状态，不把命令值解释为DAC或物理环路回读。

### 4.6 协议21固定点结果代际一致性

- 源码位置：CPU2 `measure_density.c`的`SinglePoint_PublishStableResult()`及两个公开入口，CPU2 `stateformodbus.h`/`dataanalysis_modbus.c`；CPU3 `cpu2_communicate.c`的`CPU2_PollFixedPointSnapshotHandshake()`和`CPU2_CommitFixedPointSnapshot()`。
- 改前问题：单点测量与固定点监测各六个32位结果可在CPU3跨帧读取期间更新，公开缓存可能混入两个采样轮次。
- 具体改法：CPU2每组六字段在短临界区整体写完并执行内存屏障后递增对应代际；新增`0x0A44`测量完成代际和`0x0A46`监测样本代际，`REG_ENG=0x0A48`。CPU3按“代际前读—24寄存器私有读取—代际后读”执行，两个代际完全一致才原子提交公开缓存和`g_measurement`。
- 必查边界：两次代际之间恰好发布、任一帧超时、代际变化、首次上电、通信恢复、32位代际回绕、命令切换。
- 通过标准：候选变化或读取失败不改公开结果；成功提交的12个32位字段与两个代际属于同一观察窗口；契约脚本和双端地址静态断言通过。

### 4.7 CPU2内部通信首次失败即失效并完整重同步

- 源码位置：CPU3 `cpu2_communicate.c`的`CPU2_InvalidatePublicSnapshotFreshness()`、`CPU2_CommRecordFailure()`、`PollingInputData()`和可用性接口。
- 改前问题：连续10次失败前仍可能把旧状态、旧参数或旧测量结果提供给外部协议；恢复后不同快照的完成时刻不一致。
- 具体改法：首次请求失败即关闭状态、参数、协议和固定点快照新鲜度，同时保留连续10次才置`CPU2_COMM_TIMEOUT`的报警阈值；恢复顺序重新读取状态、协议、参数和固定点快照，全部就绪后开放运行态。
- 必查边界：第1次和第10次失败、UART错误、坏帧、协议不匹配、参数写失败、恢复期间外部读取、再次断链。
- 通过标准：首次失败后CPU2派生读取返回Busy而非旧值；第10次才形成通信超时故障；恢复完成前命令和运行态门禁不开放。

### 4.8 DSM和SI读取新鲜度分类

- 源码位置：新增`external_read_freshness.h`；DSM `DSM_DataAnalysis_modbus2.c`、`DSM_SlaveModbus_modbus2.c`、`DSM_communication.c`；SI `si_modbus_slave.c`。
- 改前问题：CPU3本地静态字段与CPU2派生字段共用宽泛可用性判断，CPU2断链时可能返回旧运行态，或反过来阻断本地静态信息。
- 具体改法：按请求范围判断本地静态、CPU2状态、参数和测量数据依赖；混合范围只要包含失效的CPU2字段，整帧返回Busy；DSM特殊响应映射为具体传感器错误。
- 必查边界：纯本地范围、纯CPU2范围、跨边界混合范围、首个字段和末字段、数量0/越界、通信恢复。
- 通过标准：本地静态字段在CPU2断链时仍可读；任何包含失效CPU2字段的请求不返回部分旧数据；DSM错误含义可定位。

### 4.9 Wärtsilä点表、签名、FC10和命令边界

- 源码位置：`wartsila_register_map.h`、`wartsila_modbus_data_analysis.c/.h`、`wartsila_modbus_communication.c`的FC03、`modbus_on_holding_written()`、`ForwardParamsToLowerDevice()`和命令影子清理。
- 改前问题：点表长度、短结果尾部、签名读取长度、FC10长度和命令值缺少统一严检，CPU2断链时还可能返回旧运行态。
- 具体改法：可靠点表固定100点；长结果截断，短结果先清完整点表再填有效点；版本签名固定20寄存器；FC10校验`byteCount=2*quantity`和完整PDU；命令只接受0、3、4、5；字段按本地静态、参数和运行态分类新鲜度。
- 必查边界：0/1/99/100/101/200点、连续长短两轮、签名19/20/21寄存器、FC10短帧/长帧/奇数byteCount、非法命令、转发失败。
- 通过标准：点100以外不暴露；短轮次尾部全0；非法长度或命令返回Modbus异常；CPU2派生范围失效时返回Busy。

### 4.10 UART DMA+IDLE错误优先

- 源码位置：新增`uart_idle_frame_gate.h`及`stm32f4xx_it.c`的外部UART中断处理。
- 改前问题：IDLE与`PE/FE/NE/ORE`同次出现时可能先发布长度，把带硬件错误的帧交给协议解析器，再由HAL处理错误。
- 具体改法：使用同一SR快照分类；任何错误位优先于IDLE，错误组合交HAL中止和恢复，只有无错误的IDLE事件才计算并发布DMA帧长度。
- 必查边界：纯IDLE、每个单独错误、错误+IDLE、DMA满缓冲、空帧、连续错误后的首个正常帧。
- 通过标准：错误组合事件不增加协议待处理长度；HAL恢复后正常IDLE帧只发布一次；ISR中不新增打印或阻塞。

### 4.11 LTD CPU3本机参数段

- 源码位置：`ltd_modbus_slave.c/.h`的`ltd_read_cpu3_holding()`、`ltd_write_cpu3_holding()`和总分发。
- 改前问题：LTD外部Modbus只能访问CPU2参数，CPU3本机配置缺少受控读取和持久写入口。
- 具体改法：新增`0x0200`本机保持寄存器段；FC03读取CPU3当前有效参数；FC10一次仅允许写一个完整32位、可写且非UART的字段，执行元数据值域校验、FRAM写后读回和异常响应。原CPU2段继续依赖CPU2快照和ACK。
- 必查边界：奇数起始地址、数量不是2、只读字段、UART字段、越界值、FRAM失败、跨CPU2/CPU3段请求。
- 通过标准：合法本机字段重启后保持；非法或持久化失败返回异常且运行态不残留候选值；CPU2段语义不变。

### 4.12 测量计划、罐高/水位和电机边界

- 源码位置：CPU2 `measure_oilLevel.c`、`measure_waterLevel.c`、`measure_tank_height.c`、`measure_density.c`、`measure_zero.c`、`wartsila_density_measurement.c`和`Services/MotorControl/`本次变更文件。
- 改前问题：部分参数缺失、容量不足、调用条件、到位/停止、标定失败和点动越界共用通用码；0.1 mm点动容差容易因量化和机构回差误报。
- 具体改法：按真实原因返回具体错误码并保留底层错误；点动越界容差调整为1.0 mm；运动停止、目标位置、驱动参数和尺带拟合边界同步收敛。
- 必查边界：空参数、最大点数、罐高/水位临界值、正反向点动0.9/1.0/1.1 mm、到位但未停止、命令切换、底层通信失败。
- 通过标准：调用方能得到具体错误；1.0 mm容差内不误报，超过容差仍阻断；停止和目标位置状态保持一致。

### 4.13 FRAM A/B和无线名称诊断

- 源码位置：CPU2 `system_parameter.c`的双槽加载/保存与电机位置恢复；`ch9141_at.c`、`wireless_pairing.c`、`sensor.c`及通信适配文件。
- 改前问题：参数/位置未初始化与真实通信失败可能混淆；无线未发现、重复名称和非法名称难以区分。
- 具体改法：A/B快照继续校验magic、版本、结构大小和CRC，区分空白、单槽有效、双槽损坏与通信失败；无线名称匹配分别返回未发现、重复和非法名称错误。

- 通过标准：单有效槽可恢复并修复冗余；双损坏不伪装成未初始化；无线错误码与扫描结果一一对应。

## 5. 跨CPU与外部协议闭环

1. CPU2按协议21发布状态、参数、AO运行态、故障码、固定点结果和两个代际。
2. CPU3首次上电或任一请求失败后关闭公开快照，依次完成状态、协议、参数和固定点三阶段读取。
3. 固定点读取只在代际前后相等时一次提交；外部DSM、SI、Wärtsilä和LTD按字段来源检查所需快照。
4. CPU3菜单写AO参数时等待CPU2 ACK并补读；CPU2归一化参数后驱动AO运行态，AD5421控制/故障寄存器状态与诊断结果再投影给CPU3显示和HART。
5. 任一链路失败时，CPU2派生外部读取返回Busy，写路径回滚候选；连续10次CPU2通信失败才形成通信超时故障。
