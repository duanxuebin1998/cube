## 维护规则

- 新增方案按日期、版本和主题命名，主题应能直接说明真实改动对象。
- 本目录是后续版本提交和 skill 生成新方案的正式输出区；新增方案后可先完成版本提交，`版本总览.md`、治理清单和人工索引允许后补。
- 方案固定使用正式归档骨架：`版本变化`、`协议版本/兼容性`、`参数存储兼容性`、`本次改动点`、`影响范围`、`重点测试项`、`回归范围`、`已执行验证`、`未验证风险`。
- `重点测试项` 默认使用表格，列为 `测试项`、`前置条件`、`步骤`、`预期结果`、`通过标准`，便于现场按项勾选。
- 复杂故障、并发时序、协议兼容或多步骤实测项可在表格后增加 `复杂项详细测试步骤` 章节；该章节只展开需要逐步执行的项目，不替代表格。
- 每份方案必须写明参数存储兼容性：CPU2 `DEVICE_PARAM_VERSION` 是否变化、`DeviceParameters` 结构大小是否变化、升级是否会恢复出厂参数，以及需要现场备份或重新下发的参数范围。
- 版本提交标题必须包含 CPU2/CPU3 固件版本号；整机、文档、工具或跨 CPU 改动统一写 `（CPU2 Vx.x.x.x / CPU3 Vy.y.y.y）`，单 CPU 改动至少写对应 CPU 版本。改写历史、amend 或推送前运行 `py tools\check_commit_subject_versions.py --range origin/MAIN..HEAD`。
- 提交标题门禁脚本为 `tools/check_commit_subject_versions.py`，本地 `commit-msg` 钩子位于 `tools/git-hooks/commit-msg`。新克隆或 hooksPath 丢失时执行 `git config core.hooksPath tools/git-hooks` 后再提交。
- 协议语义、寄存器地址、参数范围、默认值、显示行为或外部协议行为变化时，同步更新 `../README.md`、`../../01_协议与寄存器/CPU2_CPU3协议变更记录.md`、`../../../CHANGELOG.md` 和相关业务目录索引。
