# CPU2 V1.36.0.0 / CPU3 V1.36.0.0 协议31扭力温度与标定修复改动与测试方案

更新日期：2026-07-29

## 1. 文档目的和适用版本

本文记录协议31首个正式固件组合的实现范围、兼容边界、可执行测试、已完成验证和未验证风险，供代码复核、台架验证和发布追溯使用。

| 项目 | 变更前 | 变更后 |
| --- | --- | --- |
| CPU2固件 | `V1.35.0.0` | `V1.36.0.0` |
| CPU3固件 | `V1.35.0.0` | `V1.36.0.0` |
| CPU2/CPU3共享协议 | `DEVICE_PROTOCOL_VERSION=30` | `DEVICE_PROTOCOL_VERSION=31` |
| CPU2参数存储 | `DEVICE_PARAM_VERSION=3` | `DEVICE_PARAM_VERSION=3` |
| CPU3本机参数存储 | V7 / `0x0007` | V7 / `0x0007` |

协议31改变输入寄存器`0x0116~0x0117`的字段解释，CPU2和CPU3必须使用V1.36.0.0严格配套。协议30及更早程序不能按“扭力模块温度”解释原占位槽，由现有严格协议版本门禁阻止混用。

## 2. 参数存储兼容性

- `DeviceParameters`结构、`struct_size`、magic、CRC范围、参数FRAM A/B地址和单槽容量均不变。
- `torque_temperature_bits`位于运行期`DebugData`，不进入CPU2参数FRAM；本次不复用`DeviceParameters`保留字段。
- CPU3只增加共享快照消费和OLED显示，不改变本机参数结构或FRAM版本。
- 从V1.35.0.0升级到V1.36.0.0不会因本次改动恢复出厂或清除现场参数。
- 现场升级前仍应按常规记录关键标定与AO配置；升级后核对双端协议31匹配、罐高/水位罐高、AO输出源和量程，不需要因本次版本主动重新下发全部参数。

## 4. 详细改动清单

### 4.1 Newhall协议卷归档

- 源码位置：`docs/01_协议与寄存器/传感器通信协议/Newhall称重传感器协议/`及上级README。
- 改前问题：CUBE正式文档库缺少Newhall独立称重主控的完整UART帧、字段和BCC依据，后续接入只能依赖外部源目录。
- 具体改法：归档19200 8N1、`0x81/0x82/0x83`帧、查询命令、主动上报、字段字节序、BCC、源码来源哈希、已实现/未实现边界和联调矩阵。
- 必查边界：外部源目录无Git元数据、物理电气层未知、称重字段单位/符号、温度落后一轮、首帧0 ℃及真实抓包未验证。
- 通过标准：文档链接有效，来源哈希和协议字段可复核；文档明确区分Newhall源码事实、CUBE当前实现和硬件待验证项。

### 4.2 Newhall候选帧统一有效性门禁

- 源码位置：`LTD_MAIN_CPU2/Core/Src/stm32f4xx_it.c`的`UART4_NewhallFrameIsValid()`和`UART4_UpdateWeightFromFrame()`。
- 改前问题：旧逻辑只要DMA候选数据超过20字节就更新重量并调用`Weight_MarkFrameReceived()`；帧头、固定长度和BCC只保护温度，坏帧可以更新重量、刷新通信存活并清除超时。
- 具体改法：统一要求长度恰好22字节、帧头`CC 03 83`且前21字节异或等于第21字节BCC；校验失败立即返回，校验成功后按重量、接收时间、温度顺序更新。
- 必查边界：小于22字节、21字节截断、超过22字节粘连、错误帧头、错误BCC、合法帧、连续坏帧和坏帧后恢复。
- 通过标准：所有坏帧均不改变重量/滤波输入/温度，不调用`Weight_MarkFrameReceived()`且不能清除通信超时；合法帧保持原重量计算并刷新接收时间。

### 4.3 扭力模块温度解析与共享字段语义

- 源码位置：CPU2 `stm32f4xx_it.c`、`weight.c`、`system_parameter.h/.c`、`stateformodbus.h`和`dataanalysis_modbus.c`；CPU3对应共享结构、寄存器和解析文件。
- 改前问题：`0x0116~0x0117`对应的`weight_param`只有自赋值、上传和打印，没有真实生产者或业务消费，名称和语义均为未启用占位。
- 具体改法：从合法`0x83`帧偏移15～18按大端组合IEEE754 float32原始位；指数全1时拒绝更新，上电/初始化发布安静NaN；双端字段改为`torque_temperature_bits`，宏改为`REG_DEBUG_TORQUE_TEMPERATURE_BITS`。
- 必查边界：25 ℃、0 ℃、负温、正负零、NaN、正负无穷、超范围有限值、字节序颠倒和重新初始化。
- 通过标准：寄存器地址仍为`0x0116~0x0117`且轮询块长度不变；双端协议版本均为31；旧字段、旧宏和无效适配函数在目标源码中为0处。

### 4.4 扭力标定等待页温度显示

- 源码位置：`LTD_DISPLAY_CPU3/Application/display/display_tankopera.c`的`debug_weight_temperature_x100()`、`debug_weight_draw_temperature()`和等待页刷新。
- 改前问题：获取空载/满载扭力期间只显示状态和实时扭力，现场无法查看扭力模块自身温度。
- 具体改法：把共享原始位安全复制为float，拒绝NaN、无穷和超出`-999.99~999.99 ℃`的值；等待页第二行显示两位小数温度，第三行保持实时扭力，第四行保持返回。
- 必查边界：两个获取状态、完成态自动返回、错误态退出、负温、边界值、无效值、中文/英文和4行布局。
- 通过标准：有效值稳定显示两位小数，无效值显示`--.--`；页面状态、扭力行和返回路径不变。

### 4.5 读取部件参数完成页温度显示

- 源码位置：`LTD_DISPLAY_CPU3/Application/display/display.c`的`Display_GetTorqueTemperatureX100()`、参数有效项计算和结果分页绘制。
- 改前问题：读取部件参数完成态没有扭力模块温度，用户只能进入扭力标定页面查看。
- 具体改法：只在`DISPLAY_RESULT_CONTEXT_READ_PARAMETER`中增加“扭温”项目，复用同一共享原始位和有效性范围；无效值占位也固定占一项，保持分页序号稳定。
- 必查边界：读取进行中、读取完成、页面翻页、其它测量结果上下文、无效值、负温、中英文标签和刷新。
- 通过标准：仅`STATE_READPARAMETEROVER`结果分页显示扭温；读取进行中不提前显示旧结果；其它结果页不增加该项。

### 4.6 水位标定命令切换立即退出

- 源码位置：`LTD_MAIN_CPU2/Application/Src/measure_waterLevel.c`的`CMD_CalibrateWaterLevel()`调用`SearchWaterLevel()`后的返回处理。
- 改前问题：`SearchWaterLevel()`返回`STATE_SWITCH`表示新命令已接管，但通用`SET_ERROR(ret)`忽略该状态，旧标定仍可能继续修正和保存结果。
- 具体改法：识别`STATE_SWITCH`后立即返回，不进入旧标定结果提交；水位罐高实际变化后调用`normalize_ao_params_after_write()`同步AO动态范围。
- 必查边界：正常标定、STOP、新命令切换、搜索失败、AO来源为水位且罐高缩小、非水位AO来源。
- 通过标准：命令切换后旧流程不再写水位标定结果或完成态；正常成功路径保持原保存行为，相关AO量程不因旧上限阻塞后续命令。

### 4.7 FC10候选AO配置写区间感知校验

- 源码位置：`LTD_MAIN_CPU2/Services/ParamStorage/system_parameter.c/.h`的`prepare_ao_params_for_write()`和`LTD_MAIN_CPU2/Services/Modbus/hostcommu_modbus.c`的FC10调用点。
- 改前问题：历史AO配置非法时，即使FC10只写无关参数，也会被候选AO全量严格校验阻塞并返回参数超范围。
- 具体改法：传入`start_addr/reg_count`判断本次写区间是否触及AO；未触及AO、AO内容不变且动态上限不变时放行无关写入；触及AO或上限变化时保持默认回退和严格校验。
- 必查边界：AO区间前后相邻地址、跨界写、寄存器数量0、AO同值非法写、输出源切换、罐高导致动态上限变化、无关参数写。
- 通过标准：无关写不再被历史非法AO阻塞；AO同值非法写仍返回Modbus异常`0x03`；合法AO写和源切换保持原成功语义。

### 4.8 零值罐高标定延迟提交

- 源码位置：`LTD_MAIN_CPU2/Application/Src/measure_tank_height.c`的`SearchBottom()`、`ApplyBottomEncoderCorrection()`和`GetBottomEncoderCorrectionTankHeight()`。
- 改前问题：零值液位标定在安全抬升前就写入新罐高和位置；若抬升失败，RAM中会留下半生效标定结果。简单延迟全局写入又会让编码器罐底修正误用旧罐高。
- 具体改法：先保存候选罐高和有效标志；编码器修正显式接收候选罐高；只有安全抬升成功后才提交`calibrated_liquid_level`、`tankHeight`、AO归一化和位置刷新。
- 必查边界：非零液位、零值液位、候选罐高0、编码器修正覆盖参数、抬升成功、抬升失败、命令切换和电机错误。
- 通过标准：抬升失败时全局罐高、标定液位、AO和位置刷新均不提交；成功时提交一次且编码器修正使用候选罐高保持原目标。

### 4.9 版本、协议和发布资料

- 源码位置：双端`app_version.h`、`CHANGELOG.md`、版本总览、协议记录、共享Modbus协议卷和本文。
- 改前问题：协议31实现仍使用V1.35.0.0，与协议30首发版本重复，无法从固件版本区分；协议31首个正式组合尚未确定。
- 具体改法：双端MINOR升级到V1.36.0.0，协议31记录首个正式组合；补齐兼容性、存储、测试、风险和提交范围；`CHANGELOG.pdf`保持原文件。
- 必查边界：双端版本宏/字符串、协议版本严格相等、参数存储版本、CHANGELOG标题、版本方案文件名、PDF排除状态和提交标题。
- 通过标准：源码、文档、HEX文件名和提交标题版本一致；`check_version_bumped.py`及提交标题版本门禁通过。

## 5. 跨模块数据流和异常闭环

```text
Newhall UART4候选数据
  -> 22字节 + CC 03 83 + BCC统一门禁
  -> 合法帧更新重量 / Weight_MarkFrameReceived / 温度原始位
  -> CPU2输入寄存器0x0116~0x0117
  -> CPU3协议31快照解析
  -> 扭力标定等待页或读取部件参数完成页
  -> 有效值两位小数 / 无效值--.--
```

```text
水位标定
  -> SearchWaterLevel()
  -> STATE_SWITCH: 立即退出，不提交旧结果
  -> 正常成功: 更新水位罐高并归一化AO

零值罐高标定
  -> 保存候选罐高
  -> 候选罐高参与编码器修正
  -> 安全抬升
  -> 成功: 提交罐高/AO/位置
  -> 失败: 保持旧全局配置
```

## 9. 风险与未验证项

- Newhall温度字节序、首帧0 ℃、温度落后一轮和电气层仅有协议资料/源码静态依据，尚无真实UART4抓包。
- 温度通信超时后不会自动置NaN；读取部件参数也不证明温度来自本轮命令。这两项已在协议记录中列为用户明确暂缓的问题。
- UART4仍把一次IDLE取得的数据块视为候选整帧；统一门禁能拒绝半帧/粘连，但尚未实现持续字节流重同步。
- AO校验、命令切换和零值罐高提交需要真实Modbus、电机、FRAM和4～20 mA台架验证。
