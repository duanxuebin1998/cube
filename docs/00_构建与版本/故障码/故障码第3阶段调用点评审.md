# 故障码第 3 阶段调用点评审

更新日期：2026-07-11

## 评审范围

本文承接 `当前程序故障代码清单.md` 中标出的 8 项第 3 阶段候选故障码，对当前源码调用点做语义复查。本文只给出整理结论和后续改动方向，不修改固件行为、不改故障码数值、不调整 CPU2/CPU3 协议映射。

统一表中的“源码使用次数”仍作为基线统计口径；本文的调用点说明用于判断语义是否过宽、是否可统一归类、是否值得拆分。

## 总体结论

第 3 阶段不建议直接批量改源码。当前 8 项候选码已经进入 CPU2 日志、CPU3 显示和协议资料，直接重命名或改枚举会引入兼容风险。更稳妥的顺序是先按调用点补齐语义分桶，再按影响面选择少量高价值改动。

建议分成三类处理：

| 处理类型 | 对象 | 原因 | 下一步 |
| --- | --- | --- | --- |
| 收窄兜底 | `PARAM_ADDRESS_OVERFLOW`、`OTHER_PERIPHERAL_CONFIG_ERROR` | 名称和实际调用语义偏差最大，继续新增调用会让定位越来越困难 | 先禁止新增滥用，新增日志上下文；下一轮再改调用点 |
| 按责任域回收 | `SENSOR_RESP_FORMAT_ERROR`、`SENSOR_DEVICE_COMM_TIMEOUT`、`MEASUREMENT_POSITION_ERROR` | 通用码混入无线、UART、运动控制等不同责任域 | 先梳理边界映射，优先复用已有专用码 |
| 小范围拆分 | `AD5421_READFAULT_ERROR`、部分 `MOTOR_TMC_COMM_ERROR` | 调用点集中，拆分收益明确 | 在 CPU2/CPU3 同步准备充分后实施 |

## `PARAM_ERROR`

### 当前调用语义

`PARAM_ERROR` 当前不是单一“参数错误”，而是多个层次的通用错误出口：

| 语义分桶 | 代表调用点 | 说明 |
| --- | --- | --- |
| 用户配置缺失或配置值无效 | `LTD_MAIN_CPU2/src/measure.c:40`、`LTD_MAIN_CPU2/src/measure_oilLevel.c:473`、`LTD_MAIN_CPU2/src/measure_waterLevel.c:1365` | 例如罐高标定为 0、密度目标未配置、固定频率未配置或超范围 |
| 内部 API 参数非法 | `LTD_MAIN_CPU2/src/ad5421.c:176`、`LTD_MAIN_CPU2/src/sensor.c:728`、`LTD_MAIN_CPU2/src/measure_tank_height.c:805` | 多数是空指针、输出参数为空或内部调用前置条件不满足 |
| 电机位置模型和运动规划异常 | `LTD_MAIN_CPU2/src/motor_ctrl_motion_api.c:1340`、`LTD_MAIN_CPU2/src/motor_ctrl_position_model.c:107`、`LTD_MAIN_CPU2/src/motor_ctrl_tape_fit.c:53` | 覆盖方向非法、位移换算失败、位置模型输入非法、胶带拟合参数非法等 |
| 预留或不支持模式 | `LTD_MAIN_CPU2/src/measure_oilLevel.c:1134`、`LTD_MAIN_CPU2/src/measure_oilLevel.c:1435` | 预留超声测量方法被选中时返回通用参数错误 |
| 恢复策略分类 | `LTD_MAIN_CPU2/src/fault_recovery.c:67` | 当前被归入不可恢复类，说明后续拆分需要重新审视恢复策略 |

### 判断

该码使用面广，短期不适合直接拆成多个新码后全量替换。它的问题不在于“不能复用”，而在于同一枚故障码同时代表用户配置、内部调用、运动模型和不支持模式，现场定位时需要依赖日志上下文。

### 建议

| 阶段 | 动作 | 影响 |
| --- | --- | --- |
| 文档阶段 | 在统一表和清单中保留 `PARAM_ERROR`，但标注 4 个子语义：配置缺失、调用非法、运动模型参数异常、不支持模式 | 无固件影响 |
| 代码准备阶段 | 对高频路径补充日志上下文，例如配置项名、输入值、测量模式、电机目标位置 | 不改变故障码，只提高定位能力 |
| 代码拆分阶段 | 如确需新增码，可考虑 `PARAM_CONFIG_MISSING`、`PARAM_CALL_INVALID`、`MOTOR_POSITION_PARAM_ERROR` | 需要 CPU2/CPU3 枚举、显示、日志、协议资料同步 |

优先不要把所有 `PARAM_ERROR` 一次性拆完。建议先处理用户配置缺失类，因为它最接近现场可操作原因；内部 API 参数非法类可先留日志，不一定需要用户可见新码。

## `PARAM_ADDRESS_OVERFLOW`

### 当前调用语义

`PARAM_ADDRESS_OVERFLOW` 名称指向“地址越界”，但当前调用点中只有少数是真正的参数地址或存储边界问题，大量调用实际是空指针、输出参数非法或缓冲区参数非法。

| 语义分桶 | 代表调用点 | 说明 |
| --- | --- | --- |
| 真实地址/存储越界 | `LTD_MAIN_CPU2/src/system_parameter.c:751`、`LTD_MAIN_CPU2/src/system_parameter.c:850` | 参数存储写入或地址计算失败，和名称匹配 |
| 输出参数为空 | `LTD_MAIN_CPU2/src/measure_density.c:177`、`LTD_MAIN_CPU2/src/measure_oilLevel.c:1058`、`LTD_MAIN_CPU2/src/wartsila_density_measurement.c:99` | 由内部调用者传入空输出指针触发 |
| 通信封装入参非法 | `LTD_MAIN_CPU2/src/dsm_sensor_communication.c:234`、`LTD_MAIN_CPU2/src/ltd_sensor_communication.c:121`、`LTD_MAIN_CPU2/src/ch9141_at.c:331` | 多为响应缓冲区、长度指针或解析输出为空 |
| 电机驱动接口参数非法 | `LTD_MAIN_CPU2/src/TMC5130.c:576` | 例如 `tmc5130` 或输出 `ticks` 为空 |
| 无线配对辅助参数非法 | `LTD_MAIN_CPU2/src/wireless_pairing.c:899` | 与地址越界没有直接关系 |

### 判断

这是本轮最需要治理的“名称和实际语义不一致”故障码之一。继续把空指针或输出参数非法报成地址越界，会让日志含义失真，也会影响后续统计。

### 建议

| 阶段 | 动作 | 影响 |
| --- | --- | --- |
| 立即约束 | 后续新增调用只允许真实地址、参数存储边界、参数区越界继续使用该码 | 无兼容风险 |
| 低风险调整 | 空指针、输出参数非法先改为 `PARAM_ERROR`，并补日志说明具体指针或参数名 | CPU2 行为码会变化，需要按调用点评估 |
| 高质量拆分 | 新增 `PARAM_CALL_INVALID` 或 `PARAM_OUTPUT_ARG_INVALID`，专门承载内部 API 调用错误 | 需要双端同步和测试 |

优先建议先在文档和代码审查规则里把 `PARAM_ADDRESS_OVERFLOW` 收窄为“真实参数地址或存储边界问题”。是否新增内部调用错误码，可以等日志补齐后再定。

## `SENSOR_RESP_FORMAT_ERROR`

### 当前调用语义

该码覆盖 DSM 文本协议、LTD V2 帧协议和无线 AT 响应解析，语义范围较宽。

| 语义分桶 | 代表调用点 | 说明 |
| --- | --- | --- |
| DSM 文本响应格式错误 | `LTD_MAIN_CPU2/src/dsm_sensor_communication.c:392`、`LTD_MAIN_CPU2/src/dsm_sensor_communication.c:549`、`LTD_MAIN_CPU2/src/sensor.c:395` | 响应长度、数字格式、百分号字段、密度/温度帧格式不符合预期 |
| LTD V2 协议字段不匹配 | `LTD_MAIN_CPU2/src/ltd_sensor_communication.c:341`、`LTD_MAIN_CPU2/src/ltd_sensor_communication.c:423` | 功能码、参数、帧结构不匹配 |
| UART 硬件或 DMA 异常 | `LTD_MAIN_CPU2/src/dsm_sensor_communication.c:284`、`LTD_MAIN_CPU2/src/ltd_sensor_communication.c:181` | 当前有些 UART error 或 DMA 启动失败也落到格式错误 |
| 部分响应超时 | `LTD_MAIN_CPU2/src/dsm_sensor_communication.c:289`、`LTD_MAIN_CPU2/src/ltd_sensor_communication.c:187` | 收到部分字节但未形成完整帧时返回格式错误；完全无字节时通常返回超时 |
| 无线 AT 响应解析错误 | `LTD_MAIN_CPU2/src/wireless_pairing.c:1022`、`LTD_MAIN_CPU2/src/wireless_pairing.c:1235` | `BLEMODE`、`BLESTA`、MAC、RSSI、扫描结果字段解析失败 |

### 判断

格式错误可以继续作为“传感器响应内容不符合协议”的大类，但不宜再承载 UART 硬件失败和无线 AT 解析失败。无线链路已经有 `WIRELESS_HOST_COMM_TIMEOUT`、`WIRELESS_SLAVE_COMM_TIMEOUT` 等专用码，后续应逐步减少通用传感器码在无线模块中的直接暴露。

### 建议

| 阶段 | 动作 | 影响 |
| --- | --- | --- |
| 文档阶段 | 将该码标注为“传感器协议响应格式错误”，无线 AT 解析作为历史兼容调用 | 无固件影响 |
| 代码准备阶段 | 对 UART error、DMA 启动失败、部分帧超时分别补日志原因 | 不改码，降低误判 |
| 代码整理阶段 | DSM/LTD 格式错误继续使用该码；无线 AT 解析失败优先映射到无线责任域；UART 硬件失败考虑独立通信硬件错误或复用现有通信错误码 | 需要回归通信流程 |

如要拆分，建议优先区分三类：协议字段格式错误、底层 UART/DMA 异常、无线 AT 响应解析错误。

## `MOTOR_TMC_COMM_ERROR`

### 当前调用语义

`MOTOR_TMC_COMM_ERROR` 目前是 TMC5130 相关失败的恢复大类，包含读写寄存器、配置状态和运行期状态检查。

| 语义分桶 | 代表调用点 | 说明 |
| --- | --- | --- |
| 寄存器写失败 | `LTD_MAIN_CPU2/src/TMC5130.c:74`、`LTD_MAIN_CPU2/src/motor_ctrl_driver_param.c:172` | 初始化、停止、清状态、写目标位置等操作失败 |
| 寄存器读失败 | `LTD_MAIN_CPU2/src/TMC5130.c:405`、`LTD_MAIN_CPU2/src/TMC5130.c:775`、`LTD_MAIN_CPU2/src/motor_ctrl_driver_param.c:723` | 读取 `XACTUAL`、`GSTAT`、`DRV_STATUS`、目标位置等失败 |
| 驱动配置丢失或读回异常 | `LTD_MAIN_CPU2/src/TMC5130.c:782` | 读回 `CHOPCONF` 为 0 或读失败时按通信/配置异常处理 |
| 运动过程依赖失败 | `LTD_MAIN_CPU2/src/motor_ctrl_motion_api.c:1529`、`LTD_MAIN_CPU2/src/motor_ctrl_motion_api.c:1612` | 运动规划或等待到位过程中底层驱动访问失败 |
| 恢复策略分类 | `LTD_MAIN_CPU2/src/fault_recovery.c:45`、`LTD_MAIN_CPU2/src/measure_zero.c:66` | 当前归入电机驱动恢复路径 |

### 判断

该码虽然语义较宽，但恢复策略上属于一个清晰的大类：TMC 驱动通信或寄存器访问不可用。现场处理通常也会先进入电机驱动恢复。因此短期不建议直接把它从对外故障码层拆散。

### 建议

| 阶段 | 动作 | 影响 |
| --- | --- | --- |
| 立即保留 | 对外继续使用 `MOTOR_TMC_COMM_ERROR` 作为 TMC 访问失败大类 | 保持兼容 |
| 日志增强 | 记录读/写方向、寄存器名、访问阶段、底层返回值 | 不改变协议，收益高 |
| 可选拆分 | 如现场需要区分，可新增 `MOTOR_TMC_REG_READ_ERROR`、`MOTOR_TMC_REG_WRITE_ERROR`、`MOTOR_TMC_CONFIG_LOST` | 影响电机恢复策略和 CPU3 显示 |

如果后续只做一项改动，建议先补日志而不是新增枚举。该码关联运动控制，任何行为码调整都需要 CPU2 构建、关键运动流程回归和故障恢复路径复查。

## `SENSOR_DEVICE_COMM_TIMEOUT`

### 当前调用语义

该码主要表示设备无响应或等待完整响应超时。

| 语义分桶 | 代表调用点 | 说明 |
| --- | --- | --- |
| DSM 主链路无响应 | `LTD_MAIN_CPU2/src/dsm_sensor_communication.c:275`、`LTD_MAIN_CPU2/src/dsm_sensor_communication.c:450` | DMA 接收没有收到任何有效响应，或七位值读取无响应 |
| LTD V2 主链路无响应 | `LTD_MAIN_CPU2/src/ltd_sensor_communication.c:174`、`LTD_MAIN_CPU2/src/ltd_sensor_communication.c:302` | 固定帧接收超时且无完整响应 |
| 发送完成等待超时 | `LTD_MAIN_CPU2/src/dsm_sensor_communication.c:203`、`LTD_MAIN_CPU2/src/ltd_sensor_communication.c:97` | UART DMA 发送等待超时 |
| CH9141/无线 AT 无完整响应 | `LTD_MAIN_CPU2/src/ch9141_at.c:491`、`LTD_MAIN_CPU2/src/ch9141_at.c:574` | AT 层无完整响应，部分路径后续再映射为无线专用码 |
| 无线模块边界映射 | `LTD_MAIN_CPU2/src/wireless_pairing.c:556` | 将通用传感器超时映射成 `WIRELESS_HOST_COMM_TIMEOUT` |

### 判断

在 DSM/LTD 主传感器链路中，该码语义基本准确。问题主要在无线/CH9141 AT 层：底层临时返回通用传感器超时，再由上层决定是否映射为无线专用码。这个模式可以保留，但边界必须清楚。

### 建议

| 阶段 | 动作 | 影响 |
| --- | --- | --- |
| 保留主语义 | DSM/LTD 设备完全无响应继续使用该码 | 保持兼容 |
| 边界整理 | 无线模块对外状态优先使用 `WIRELESS_HOST_COMM_TIMEOUT` 或 `WIRELESS_SLAVE_COMM_TIMEOUT` | 需要检查无线配对和诊断显示 |
| 日志补充 | 区分 TX 等待超时、RX 无字节、RX 部分帧超时、AT 无完整响应 | 不改变故障码 |

不建议新增一个新的“通用通信超时”码。当前已有传感器和无线专用码，重点是边界映射一致。

## `OTHER_PERIPHERAL_CONFIG_ERROR`

### 当前调用语义

该码原本像是系统兜底中的外设配置错误，但当前实际承载了多类不相干问题。

| 语义分桶 | 代表调用点 | 说明 |
| --- | --- | --- |
| AD5421 底层访问失败 | `LTD_MAIN_CPU2/src/ad5421.c:93`、`LTD_MAIN_CPU2/src/ad5421.c:122`、`LTD_MAIN_CPU2/src/ad5421.c:156` | SPI 发送、读寄存器、访问锁等底层失败先返回该码 |
| DSM/LTD UART 启动或发送失败 | `LTD_MAIN_CPU2/src/dsm_sensor_communication.c:234`、`LTD_MAIN_CPU2/src/ltd_sensor_communication.c:128` | UART 发送、DMA 接收启动等硬件接口失败 |
| CH9141 AT UART 发送失败 | `LTD_MAIN_CPU2/src/ch9141_at.c:424` | 无线 AT 底层发送失败 |
| 陀螺零点配置异常 | `LTD_MAIN_CPU2/src/measure_tank_height.c:861` | 底部状态检查时发现陀螺零点参考无效 |

### 判断

这是最不适合继续扩大的兜底码。AD5421 已有独立故障码，传感器/无线也有各自责任域；继续使用 `OTHER_PERIPHERAL_CONFIG_ERROR` 会削弱分类治理效果。

### 建议

| 阶段 | 动作 | 影响 |
| --- | --- | --- |
| 立即约束 | 后续新代码不得把具体外设故障直接落入该码，除非确实无法归属 | 无兼容风险 |
| 文档整理 | 标注当前调用为历史兜底，优先回收至 AD5421、传感器通信、无线通信、测量配置责任域 | 无固件影响 |
| 代码整理 | AD5421 底层失败映射到 AD5421 专用码或新增 `AD5421_SPI_COMM_ERROR`；UART 启动/发送失败映射到通信责任域；陀螺零点异常考虑测量配置或传感器校准错误 | 需要逐点回归 |

优先建议先改 AD5421 和 UART 类调用，因为它们责任域最清晰；陀螺零点配置需要结合现场校准流程再定。

| 相对/绝对目标规划异常 | `LTD_MAIN_CPU2/src/motor_ctrl_motion_api.c:1833`、`LTD_MAIN_CPU2/src/motor_ctrl_motion_api.c:1875` | 目标位置计划不可达、越界或换算失败 |
| jog 过程位置一致性异常 | `LTD_MAIN_CPU2/src/motor_ctrl_motion_api.c:1978`、`LTD_MAIN_CPU2/src/motor_ctrl_motion_api.c:1984` | 运动中检查实际位置和目标位置不一致 |
| 停止后恢复校验失败 | `LTD_MAIN_CPU2/src/motor_ctrl_motion_api.c:2237` | 停止 jog 后恢复目标位置校验失败 |

### 判断

该码当前更像“电机位置目标/校验错误”，而不是测量算法本身错误。由于它从测量流程暴露出来，保留在测量类也可以解释，但文档上应明确它依赖电机位置责任域。

### 建议

| 阶段 | 动作 | 影响 |
| --- | --- | --- |
| 文档阶段 | 标注为“测量过程中的电机位置目标或到位校验异常” | 无固件影响 |
| 日志增强 | 记录目标位置、当前位置、位置源、允许范围和测量阶段 | 不改故障码 |
| 可选拆分 | 新增 `MOTOR_POSITION_TARGET_INVALID`、`MOTOR_POSITION_VERIFY_ERROR`，或将同类错误收敛到电机位置模型错误 | 影响运动控制和测量流程联动 |

该码不建议优先改。除非现场已经需要明确区分“目标不可达”和“执行后未到位”，否则先补日志更合适。

## `AD5421_READFAULT_ERROR`

### 当前调用语义

该码只有两个核心场景，但两者语义不同。

| 语义分桶 | 代表调用点 | 说明 |
| --- | --- | --- |
| 故障寄存器读取失败 | `LTD_MAIN_CPU2/src/ad5421.c:340` | `AD5421_ReadRegChecked(READFAULT, &fault_reg)` 失败，实际可能是 SPI、访问锁或底层读异常 |
| 故障寄存器状态异常 | `LTD_MAIN_CPU2/src/ad5421.c:357` | 故障寄存器读取成功，但状态位显示 AD5421 处于故障状态 |

### 判断

这是最适合做小范围拆分的候选码之一。读取失败和芯片报告故障是两类完全不同的处理方向：前者偏通信/访问，后者偏 AD5421 输出或芯片状态。

### 建议

| 阶段 | 动作 | 影响 |
| --- | --- | --- |
| 低风险增强 | 保留 `AD5421_READFAULT_ERROR`，但在 `ao_output_runtime.last_error_code` 或日志中记录子原因 | 不改对外码 |
| 推荐拆分 | 新增 `AD5421_READFAULT_COMM_ERROR` 和 `AD5421_FAULT_STATUS_ERROR`，或至少新增一个通信读取失败码，保留原码表示 fault 状态 | 影响小，但仍需 CPU3 显示同步 |
| 联动整理 | 与 `OTHER_PERIPHERAL_CONFIG_ERROR` 中 AD5421 底层访问失败一起处理 | 可减少 AD5421 责任域外溢 |

如果决定进入代码修改，建议把 AD5421 作为第一批试点：调用点少、责任域清楚、回归范围可控。

### 第 3.4 阶段：新增拆分码

只有在日志增强和低风险收敛后仍无法满足定位要求时，再新增故障码。

| 候选新增码 | 来源 | 适用条件 |
| --- | --- | --- |
| `PARAM_CALL_INVALID` | `PARAM_ERROR`、`PARAM_ADDRESS_OVERFLOW` | 需要明确区分内部调用错误和用户配置错误 |
| `PARAM_CONFIG_MISSING` | `PARAM_ERROR` | 需要把用户可处理的配置缺失单独提示 |
| `MOTOR_TMC_REG_READ_ERROR` | `MOTOR_TMC_COMM_ERROR` | 现场需要区分 TMC 读失败和写失败 |
| `MOTOR_TMC_REG_WRITE_ERROR` | `MOTOR_TMC_COMM_ERROR` | 现场需要区分 TMC 写失败 |
| `MOTOR_TMC_CONFIG_LOST` | `MOTOR_TMC_COMM_ERROR` | CHOPCONF/GSTAT 等读回表现出配置丢失 |
| `AD5421_READFAULT_COMM_ERROR` | `AD5421_READFAULT_ERROR` | 故障寄存器读取失败需要单独定位 |
| `AD5421_FAULT_STATUS_ERROR` | `AD5421_READFAULT_ERROR` | 故障寄存器读取成功但状态位异常需要单独定位 |
| `MOTOR_POSITION_TARGET_INVALID` | `MEASUREMENT_POSITION_ERROR` | 目标不可达、目标越界需要和到位失败区分 |
| `MOTOR_POSITION_VERIFY_ERROR` | `MEASUREMENT_POSITION_ERROR` | 执行后位置偏差或目标恢复失败需要单独定位 |

新增码必须同时更新 CPU2 `ErrorCode`、CPU2 日志名称和原因、CPU3 兼容枚举、CPU3 显示文案、统一表、Markdown 清单和版本资料。

## 不建议直接做的事

| 不建议动作 | 原因 |
| --- | --- |
| 直接删除或复用已有编号 | 编号已进入 CPU2/CPU3 映射和历史资料，删除或复用会破坏兼容 |
| 批量替换所有 `PARAM_ERROR` | 调用语义差异太大，容易把用户配置和内部调用错误混在一起改错 |
| 把所有通信异常都改成一个新通用码 | 传感器、无线、电机驱动的恢复策略不同，统一后会损失责任域信息 |
| 只改 CPU2 不改 CPU3 | CPU3 显示、枚举和协议资料会和 CPU2 不一致 |
| 只改故障码不补日志 | 现场仍无法看出寄存器名、参数名、响应字段等关键上下文 |

## 改代码前检查项

进入源码修改前，至少确认以下事项：

| 检查项 | 要求 |
| --- | --- |
| 兼容范围 | 确认是否允许改变现有故障码对外表现 |
| CPU3 同步 | 新增或改用故障码时同步 CPU3 枚举和显示文本 |
| 日志同步 | CPU2 日志名称、日志原因和错误恢复分类同步更新 |
| 协议资料 | Modbus/保持寄存器、版本资料和故障码统一表同步更新 |
| 回归测试 | 覆盖传感器通信、无线配对、TMC 运动、AD5421 输出、测量流程 |
| 版本说明 | 如果行为码变化，版本改动文档必须写清楚兼容影响 |
