# 当前程序故障代码清单

更新日期：2026-07-10

本文按当前源码整理 CPU2/CPU3 程序使用的故障代码，便于在 Git diff、现场日志和协议资料中直接检索。CPU2 `ErrorCode` 是 73 项共享故障码的权威来源；CPU3 允许定义不占用共享寄存器布局的本机扩展码，权威来源是 CPU3 `ErrorCode`。`LTD故障代码统一表.xlsx` 是唯一表格维护入口，并单独保存 CPU3 本机故障码。

## 整理依据

| 对象 | 路径 | 口径 |
| --- | --- | --- |
| CPU2 故障码定义 | `LTD_MAIN_CPU2/Services/ParamStorage/system_parameter.h` 的 `ErrorCode` | 最终定义来源 |
| CPU2 日志名称和原因 | `LTD_MAIN_CPU2/Services/Utilities/error_log.c` 的 `ErrorLog_GetCodeName()` / `ErrorLog_GetReasonByCode()` | 串口日志和最终报错原因 |
| CPU3 枚举 | `LTD_DISPLAY_CPU3/Application/system_param/system_parameter.h` 的 `ErrorCode` | 同步 73 项共享码；额外保留 `SENSOR_COMM_TIMEOUT` 兼容别名和 CPU3 本机扩展码 |
| CPU3 屏幕显示 | `LTD_DISPLAY_CPU3/Application/display/display.c` 的 `Display_GetErrorReasonByCode()` | 状态页和故障详情显示文案 |
| 统一表格 | `docs/00_构建与版本/故障码/LTD故障代码统一表.xlsx` | “故障代码总表”保存 73 项共享码；“CPU3本机故障码”保存 CPU3 单侧扩展码；同时保存分类规则、链路复查、治理摘要和 CPU3 辅助页 |

## 当前结论

- 当前 CPU2 `ErrorCode` 共 73 项，含 `NO_ERROR` 和 `STATE_SWITCH` 两个非故障状态。
- `LTD故障代码统一表.xlsx` 的“故障代码总表”也是 73 项，和当前 CPU2 `ErrorCode` 无缺失、无多余。
- CPU3 同步 CPU2 的 73 项共享码，并新增本机扩展码 `CPU2_COMM_TIMEOUT = 0x0013000A`；该码由 CPU3 本机产生，不要求 CPU2 增加同名枚举，也不改变共享寄存器布局。
- `CPU2_COMM_TIMEOUT` 的实际触发口径是“连续请求未获得合法响应”：1000 ms 响应超时、CRC/地址/功能码/长度或 `0x10` 回显错误、UART 错误和 TX DMA 启动失败均按 1 次请求失败累计，连续第 10 次置错；任意合法响应只清连续失败计数，只有完整覆盖设备状态和错误码的合法 `0x04` 状态帧才能建立首次状态快照或解除故障锁存。
- 枚举名和屏幕文案“CPU2通信超时”作为兼容名称保留，它是 CPU2 内部链路连续失败的汇总码，不能仅凭该名称断言根因一定是纯响应超时。
- `AD5421_*` 5 项当前归入 `0x00130000 - 0x0013FFFF` 其他错误区间。
- 当前错误码格式为 `0x00TT000N`，其中 `TT` 是类型代码，`N` 是子代码；存在跳号时按源码保留，不补写历史未使用码。
- `LTD故障代码统一表.xlsx` 已新增“分类规则”“链路复查”“治理摘要”三个工作表，用于承接后续分类、拆分和链路复查。
- 按源码调用点统计，当前 73 项中运行使用 54 项、非故障状态 2 项、预留/历史保留 17 项。统计已排除 `ErrorCode` 定义、CPU2 日志映射和 CPU3 显示映射。
- 按治理阶段统计，当前建议先保持 5 项、统一归类 60 项、进入第 3 阶段调用点评审 8 项。

## 分类治理基线

第二步整理不修改故障码编号和固件行为，只在统一表和文档中固化主责任域、故障层级、处理策略、当前使用状态和治理意见。责任域按“最接近真实维护对象”归类：底层硬件/链路错误优先于测量流程，AO/AD5421 虽仍在 `0x13` 区间但作为独立责任域维护。

下表统计口径仍是 73 项共享码。CPU3 本机扩展码单独维护，不并入 CPU2 共享码治理统计。

| 责任域 | 项数 | 整理口径 | 当前建议 |
| --- | ---: | --- | --- |
| 状态/非故障 | 2 | `NO_ERROR`、`STATE_SWITCH`，不进入最终故障出口 | 保持 |
| 电机驱动 | 10 | `MOTOR_*`，含 TMC5130、运行超时、驱动报警、欠压/过温 | 统一归类；`MOTOR_TMC_COMM_ERROR` 进入调用点评审 |
| 编码器 | 10 | `ENCODER_*`，含通信、状态位、数据质量和差值一致性 | 统一归类 |
| 传感器/密度 | 9 | `SENSOR_*`、`DENSITY_*`、`SONIC_FREQ_ABNORMAL`，排除无线/滑环链路 | 统一归类；通用通信/格式错误进入调用点评审 |
| 无线/滑环链路 | 6 | `SLIPRING_*`、`WIRELESS_*`，从 `0x0D` 传感器大类中独立维护 | 统一归类，后续优先复用主机/从机专用超时码 |
| 测量流程 | 15 | `MEASUREMENT_*`，按零点、液位、寻重、水位、密度测量阶段归档 | 统一归类；位置错误进入调用点评审 |
| 参数存储完整性 | 3 | `PARAM_EEPROM_FAIL`、`PARAM_UNINITIALIZED`、`PARAM_CRC_ERROR` | 统一归类，关注 FRAM/参数恢复 |
| 参数调用/配置 | 3 | `PARAM_RANGE_ERROR`、`PARAM_ADDRESS_OVERFLOW`、`PARAM_ERROR` | 地址越界和通用调用错误进入调用点评审 |
| 扭力/称重 | 6 | `WEIGHT_*`，含范围、碰撞、漂移、饱和和通信 | 统一归类 |
| 系统兜底 | 4 | `OTHER_*`，只保留真实系统级兜底 | 减少新调用，外设配置错误进入调用点评审 |
| AO/AD5421 | 5 | `AD5421_*`，文档上从系统兜底中独立维护 | 统一归类；`AD5421_READFAULT_ERROR` 进入调用点评审 |
| CPU3 本机通信 | 1（不计入共享 73 项） | `CPU2_COMM_TIMEOUT`，由 CPU3 内部 UART5/RS485 连续第 10 个请求未获得合法响应触发；失败样本包含超时、非法帧、UART 错误和 TX DMA 启动失败 | 保持 CPU3 本机码，不要求 CPU2 同步定义；名称按兼容汇总码解释 |

## 上报和显示路径

| 场景 | 当前路径 |
| --- | --- |
| CPU2 内部故障状态 | 业务代码写入 `g_measurement.device_status.error_code`，最终报错优先走 `fault_manager` 统一出口 |
| CPU2 到 CPU3 共享寄存器 | CPU2 写 `REG_DEVICE_STATUS_ERROR_CODE`，CPU3 在内部 Modbus 轮询中读取到 `g_measurement.device_status.error_code` |
| CPU3 本机通信故障 | CPU3 连续第 10 个请求未获得合法 CPU2 响应后，本机写入 `STATE_ERROR` 和 `CPU2_COMM_TIMEOUT`；合法非状态响应仅清计数，完整 `0x04` 状态快照才允许恢复 |
| CPU3 屏幕状态页 | `Display_GetErrorReasonByCode(error_code)` 把错误码转成屏幕故障原因 |
| DSM 外部协议 | `INPUTREGISTER_ERRORNUM` 写入 32 位 `g_measurement.device_status.error_code` |
| SI协议 | `10004 Interlock` 当前由 `error_code != NO_ERROR` 或 `profile_blocked_by_process` 合成；`10009 Reel Alarm` 当前由 `error_code != NO_ERROR` 合成 |
| AO/AD5421 运行态 | `REG_AO_OUTPUT_RUNTIME_LAST_ERROR_CODE` 上报 AO 输出最近错误码，系统故障仍以 `device_status.error_code` 为主 |

## 链路复查结论

共享链路复查从 CPU2 源码抽取 73 项 `ErrorCode`，逐项检查 CPU2 日志名称、CPU2 日志原因、CPU3 枚举、CPU3 显示文案和运行调用点。CPU3 本机扩展码另行检查产生点、状态置位和显示文案。`源码使用次数` 只用于定位依赖面，不代表现场故障发生频率。

| 复查结果 | 项数 | 说明 |
| --- | ---: | --- |
| 完整 | 41 | 有运行调用点，且 CPU2 日志名称、CPU2 日志原因、CPU3 枚举和 CPU3 显示均有精确覆盖 |
| 非故障返回 | 2 | `NO_ERROR`、`STATE_SWITCH`，不按故障链路处理 |
| CPU2 日志原因大类兜底 | 13 | 有精确名称和显示，但 CPU2 原因文本走大类兜底，后续可按用户可见日志优化 |
| 当前未见运行触发 | 16 | 保留 enum、日志和显示映射，但当前未看到排除映射后的源码触发点 |
| CPU2 日志原因大类兜底且当前未见运行触发 | 1 | 同时属于原因兜底和未见触发，按历史保留处理 |

当前未见运行触发不等于可以删除。此类编号已进入 CPU2/CPU3 映射和历史资料，原则上保留编号、不删除、不复用旧值。

## 预留和历史保留标注

以下 17 项当前未见明确运行触发点，建议在统一表中标注为“预留/历史保留”。保留这些编号可以维护历史日志、CPU3 显示和上位机解释兼容性。

| 责任域 | 故障码 | 处理原则 |
| --- | --- | --- |
| 电机驱动 | `MOTOR_FAIL_SETTING`、`MOTOR_RESET_FAIL` | 保留编号和映射，不复用旧值 |
| 编码器 | `ENCODER_POWERON_CHANGE` | 作为编码器上电诊断历史/预留项保留 |
| 传感器/密度 | `SENSOR_TEMPERATURE_ERROR`、`SENSOR_VOLTAGE_ERROR`、`DENSITY_UNSTABLE` | 留作传感器数据质量或设备自诊断细分 |
| 无线/滑环链路 | `SLIPRING_BCC_ERROR`、`SLIPRING_PACKET_LOSS` | 纳入无线/滑环链路责任域，暂不删除 |

| 扭力/称重 | `WEIGHT_SENSOR_SATURATION` | 保留为扭力硬件饱和诊断项 |
| 系统兜底 | `OTHER_UNKNOWN_ERROR`、`OTHER_ADDRESS_READ_ERROR`、`OTHER_POWER_FLUCTUATION` | 作为系统兜底或历史解释保留，新代码优先避免使用 |
| AO/AD5421 | `AD5421_FAULT_PIN_ERROR` | 保留为 AO 硬件诊断项，当前不复用 |

## 维护检查项

新增、删除或改写故障码时，按下面顺序检查：

1. 先判断错误码属于 CPU2/CPU3 共享码还是 CPU3 本机扩展码。
2. 共享码检查 CPU2 `ErrorCode` 是否新增或改值，并同步 CPU2 日志名称和原因。
3. CPU3 `ErrorCode` 是否同步共享码，或是否正确记录本机扩展码和兼容别名。
4. CPU3 `Display_GetErrorReasonByCode()` 是否覆盖屏幕显示文案。
5. `LTD故障代码统一表.xlsx` 的共享总表或“CPU3本机故障码”工作表是否同步。
6. 统一表中的责任域、故障层级、处理策略、当前使用状态、治理意见和兼容性影响是否同步。
7. 如果改变共享协议字段、错误码语义或外部协议映射，检查 `DEVICE_PROTOCOL_VERSION`、协议变更记录和版本改动与测试方案。
