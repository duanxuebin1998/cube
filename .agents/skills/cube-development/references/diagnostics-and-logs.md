# 诊断、参数追踪和现场日志分析

## 只读边界

- 用户询问原因、机制、是否存在问题、改动是否引入回归时，先完成证据链和结论；没有明确修复授权时不改文件。
- 诊断不得只依据变量名、参数名、文档描述、构建成功或旧对话结论。
- 说明“当前代码行为”时，区分 HEAD、暂存区和工作区；混合状态下写清结论对应哪一层。

## 行为追踪链

分析参数、命令、状态或异常时，按下列链路追踪：

1. 用户入口：菜单、寄存器、串口命令、上位机请求或启动流程。
2. 校验和转换：地址、类型、signedness、单位、倍率、范围和默认值。
3. 持久化：FRAM/Flash 写入、版本、CRC、回滚和恢复默认。
4. 运行态：实际被业务读取的变量、缓存、快照或状态对象。
5. 消费逻辑：状态机、阈值、计时、循环、命令分发和硬件动作。
6. 输出：寄存器、显示、日志、错误码、ACK/异常响应和测量结果。
7. 恢复：重试、取消、断链、重新初始化、上电加载和故障清除。

判断“立即生效”时必须证明写入口同步到了运行态消费对象；菜单读回、FRAM 保存成功或上电会加载都不能单独证明立即生效。

## 时序和阈值问题

- 找出计时器何时开始、何时重置、何时暂停、超时后走哪个出口。
- 区分“每轮等待”“只在进入流程前等待”“连续超限确认”和“固定周期采样”。
- 检查临界值两侧、首次上电初值、饱和计数、先递增还是先判断、有效响应后的清零和重新进入条件。
- 对状态机列出正常、超时、坏帧、取消、命令切换、重入和恢复路径；不要只读成功路径。

## 现场日志分析

- 先盘点文件、设备/端口、时间范围、固件版本和日志格式，不直接从单条错误打印下结论。
- 对齐错误前后的命令、状态、位置、频率、编码器增量、重试和恢复时序。
- 统计异常次数、最大连续次数、阈值附近分布和不同设备共性；保留原始行号或时间戳证据。
- 区分直接故障、伴随现象、长期趋势和无关噪声。
- 同时检查至少两个竞争解释，例如硬件/机构、参数/操作、运行环境、通信数据和软件逻辑；写清支持证据、反证和置信度。
- 累计量正常但单步异常时，不把它表述成持续丢失；局部回差、粘滑、采样尖峰和阈值过敏应分别评估。

## 改动回归审查

构建或静态契约通过后，仍检查：

- 初始化值与新逻辑语义是否冲突。
- 首次启动、首次超时和首次有效响应。
- 发送成功与响应成功是否被错误等同。
- ACK、回显、坏帧、短帧、CRC/地址错误和 DMA/UART 失败。
- 缓存失效、旧结果、读写并发和切换期间竞态。
- 失败回滚后运行态、持久化和显示是否一致。
- UI 或菜单在操作前后是否都检查状态，避免第 N 次超时仍显示旧参数。
- 测试是否真的覆盖目标行为，而不是脚本自身解析错误、窗口过短或只检查字符串存在。

## 结论格式

诊断结论至少包含：

- 当前实际行为。
- 触发条件和执行链。
- 直接证据位置。
- 确认问题、残余风险和非本次回归的既有问题。
- 已执行验证及其证明边界。
- 如果要修复，给出最小方案和需要新增的失败用例；等待用户授权后再实施。
