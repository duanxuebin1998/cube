# CUBE 任务生命周期、范围和恢复

## 阶段判定

- “分析、检查、梳理、为什么、是否存在、评价、输出理解”属于只读阶段，不修改源码、正式文档、暂存区或版本。
- “规划、方案、先不改、用于沟通”属于方案阶段；只创建用户明确要求的方案资料，不把建议写成已实现事实。
- “修改、优化、修复、执行、落地”进入实现阶段，只处理已经确认的目标和文件边界。
- “升版、暂存、提交、amend、发布”进入发布阶段；重新读取 Git/版本 references，不沿用实现阶段的旧快照。
- “继续”沿用当前已确认阶段和交付物，不自动进入下一分册、下一版本、提交或发布。
- “先输出理解，我来纠正”保持只读，先列事实、推断、矛盾和待确认项；收到纠正后重新形成基线再写入。
- 用户中途停止、缩小范围或替换目标时，立即停止新的旧范围写入，以最新指令为准。

## 事实裁决

按以下顺序判断当前事实：

1. 用户对本任务的最新明确决定。
2. 当前生产调用链、配置、工作区和暂存区实际内容。
3. 已批准且确认仍适用的正式需求、协议和设计资料。
4. 现场抓包、日志、原始设备资料和构建/测试输出。
5. 历史源码、旧版本、参考文档和历史提交。
6. 旧对话、记忆、计划、推测和建议。

正式文档可能正是待纠正对象。发现用户决定、当前源码和文档冲突时，列出冲突及影响，不自行选择旧文档，也不把目标设计写成当前实现。

## 最小范围台账

非简单任务开始时记录：

- 本轮目标、交付物和明确不做的内容。
- 当前阶段允许的动作：只读、方案资料、实现、升版、暂存、提交或推送。
- 目标文件、业务调用链和关联仓库。
- staged、unstaged、untracked、删除和混合状态文件。
- 用户改动、其它任务改动、本轮改动及本机不提交资料。
- 当前版本轴、已有验证、证据边界和下一步。
- 用户已确认决定、仍在使用的假设、开放问题和已经被新决定替代的旧结论。
- 当前事实所依据的源码提交、文档版本、现场固件、原始证据和最近批准交付物。

审查“本次改动”时明确采用 HEAD、index、worktree 或指定提交。目标文件为 `MM`、`AM` 等混合状态时分别读取 cached 和 worktree diff。

## 并行工作和长任务恢复

- 未执行写入时 Git 状态或文件哈希发生变化，视为存在并行任务；重新锁定边界，只继续安全分离的文件。
- 同一工作树只保留一个写入者；独立审查者默认只读，不并发修改同一生成源或正式产物。
- 需要写入的非简单任务先运行 `scripts/manage_task_lease.py --action acquire` 声明最小写入路径。路径与活动租约重叠时不得继续写入；独立改动优先切换到 `.worktrees/`，无法隔离时等待原任务关闭租约。
- 租约只声明写入所有权，不代表文件内容正确、允许提交或获得了发布授权。任务正常收尾使用 `--action close` 把自己的租约标为关闭，不删除其它任务记录。
- 不通过 reset、checkout、覆盖、清理或重新生成来消除其它任务改动。
- 长任务使用 `scripts/snapshot_cube_context.ps1` 保存可恢复状态；跨仓库时显式传入 `-RelatedRepoPath`。示例：

  ```powershell
  & .\.agents\skills\cube-development\scripts\snapshot_cube_context.ps1 `
    -RepoRoot D:\CUBE `
    -OutputPath tmp\<任务号>\cube-context.json `
    -TaskId <任务号> `
    -Objective "<当前目标>" `
    -Stage "<read-only|plan|implement|release>" `
    -AllowedPath @("<允许路径>") `
    -ExcludedPath @("<保留路径>") `
    -CompletedCheck @("<已完成检查>") `
    -OpenRisk @("<开放风险>") `
    -ConfirmedDecision @("<用户已确认决定>") `
    -Assumption @("<仍在使用的假设>") `
    -OpenQuestion @("<开放问题>") `
    -SourceBaseline @("<事实来源和版本>") `
    -LastApprovedDeliverable "<最近批准交付物>" `
    -WritePath @("<最小写入路径>") `
    -WatchPath @("<恢复前必须核对哈希的文件>") `
    -NextStep "<下一步>" `
    -RelatedRepoPath @("<关联仓库绝对路径>")
  ```
- 上下文压缩或任务恢复后，先运行 `scripts/check_context_snapshot.py --snapshot <任务JSON>`，再核对其中的版本、关联仓库、用户决定和开放问题。分支、HEAD、三层状态或 watch 文件变化时重新建立基线，不直接续写。
- 正式产物或生成源哈希变化后，依赖旧哈希的渲染、页级验收或构建结论失效；只重跑受影响链路，不重复已证明未变化的范围。

## 用户用语和目录语义

- “Git库文档区、项目正式文档区、我的Git库中的文档”指 `docs/`。
- “本机预览”指 `docs-site/`；它不是业务事实来源。
- “临时产物”指 `tmp/<任务号>/`；“长期本机证据”指 `outputs/<任务号>/`。
- `docs/00_程序流程导航/` 和 `tools/` 本机维护但不提交。
- “我的库、文档区域、资料库”等仍可能对应多个位置时，先检查当前项目语境；无法唯一确定再询问，不自行移动到 Windows Documents、云端库或其它仓库。

## 计划外问题

- 属于当前目标且不扩大用户授权的缺陷，可以补入范围并说明。
- 只相关但不属于当前交付物的问题，记录证据、影响和建议，不顺手修改。
- 需要改变产品语义、硬件动作、协议兼容、存储迁移、版本或提交范围时，先明确决策点。

## 按任务类型完成

| 任务类型 | 最低完成条件 |
| --- | --- |
| 只读分析 | 当前调用链、事实与推断分离、矛盾、风险和最小下一步 |
| 代码修改 | 最终 diff、编码/注释、相关静态检查、最终源码对应的 clean-first 构建 |
| 参数修改 | 入口、校验、持久化、运行态、消费点、启动加载和迁移 |
| 协议修改 | 通信两端、帧与状态、异常、兼容性、版本和真实联调边界 |
| 文档修改 | 正式来源、路径、链接、结构、必要的全本或视觉检查，不默认生成 PDF |
| 故障分析 | 触发时间线、为何之前未触发、底层原因、影响和证据边界 |
| 提交 | all/scoped 范围、完整四段式正文、版本标题、提交后剩余状态 |
| 发布 | 版本、协议、存储、CHANGELOG、方案、构建、产物和 Git 范围一致 |
