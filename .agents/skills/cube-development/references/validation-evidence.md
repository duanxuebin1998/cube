# CUBE 验证证据和新鲜度

## 证据层级

分别记录以下证据，不互相替代：

1. 文本、编码、链接、结构和静态契约检查。
2. 编译、链接、主机测试和生成产物。
3. 文档渲染、浏览器、OLED或UI视觉检查。
4. 台架、目标板、传感器、FRAM掉电、RS485、运动和故障注入。
5. 现场设备、真实工况和长期运行。
6. 安全分析、独立评审和认证证据。

## 证据记录

每项验证至少记录：

- 任务ID、执行时间、执行者和工作目录。
- 命令或操作步骤、工具版本、退出码和摘要。
- HEAD、index/worktree状态、相关文件或源目录指纹。
- CPU2/CPU3固件、共享协议和参数存储版本。
- 输入数据、设备、端口、配置、前置条件和观测点。
- 产物路径、大小和SHA-256；日志或截图的来源。
- 通过标准、实际结果、未执行项和证明边界。

使用 `scripts/record_validation_evidence.py create` 写入 `tmp/<任务号>/validation-manifest.json`；需要长期保留时写入 `outputs/<任务号>/`。交付前用同一脚本的 `check` 重新计算源与产物哈希。版本方案只引用已完成证据，不提前写“通过”。

## 新鲜度

- 影响目标行为的源码晚于构建或测试时，旧结果失效并重跑相关链路。
- Word/HTML/Markdown源或生成器变化后，旧渲染、页数、视觉检查和站点构建失效。
- 版本头、协议定义、参数结构或构建配置变化后，重新执行对应静态检查和clean-first构建。
- 只修改不影响目标的独立文件时，可以保留旧证据，但要用哈希证明依赖范围未变化。
- 提交前以最终暂存区为范围核对；提交后以真实提交树确认文件、消息和产物记录一致。

## 结果表述

- 静态检查通过只说明规则和代码形状满足检查器。
- 构建通过只说明指定配置可编译链接，不证明目标板、时序和外设行为。
- 主机测试不证明中断、DMA、供电、FRAM或真实总线。
- 台架验证写清设备和覆盖条件，不扩大成全部现场工况。
- 未执行项说明原因、风险、推荐环境和后续动作，不使用“功能正常”“已验证”笼统替代。

## 发布核对

- 版本方案、CHANGELOG和提交正文中的验证条目必须来自同一最终证据记录。
- 构建产物版本名、固定名、版本头和哈希一致；如果产物不提交，仍记录其本机路径和哈希。
- 检查器因历史基线滞后失败时先判定检查器是否适用于当前版本；不得把过期硬编码失败直接认定为固件回归，也不得静默忽略。
- 真实设备证据缺失时作为发布残余风险，不以文档、哈希或构建记录关闭。
