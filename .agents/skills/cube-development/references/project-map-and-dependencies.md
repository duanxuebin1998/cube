# CUBE 整体工程地图和关联仓库

## 使用原则

- 本文件提供工程对象、维护入口和跨仓库边界，不代替当前源码、正式协议或批准设计。
- 每次涉及多个处理器、工具或仓库时先盘点完整链路，不能按 CPU 连续编号、历史目录名或单侧源码推断全部对象。
- 关联仓库路径、分支和 HEAD 会变化；开始任务时实时核对，文档中引用实现事实时记录核对提交。

## 系统对象盘点

- CPU1 表示传感器端处理类别；DSM、LTD、DM4 等具体类型和协议实施状态必须分别核对，不因候选协议或内部 MCU 自动新增整机 CPU 节点。
- CPU2 和 CPU3 的当前实现分别以主仓库对应源码为准。
- CPUW 是非连续命名的称重处理器，不能因只盘点 CPU1～CPU4 而遗漏；当前源码入口为 `D:\CSS_workspace\newhall`。
- CPU4 当前是未来扩展预留，不得在没有用户确认和当前实现证据时写成已设计模块。
- 无线主机/无线从机当前按蓝牙透明传输链路理解，不根据历史 WirelessHost 工程映射为独立 CPU。
- 架构、协议和文档任务遇到上述关系变化时，以用户最新确认和当前正式架构基线为准，并同步更新本文件的入口而非复制整份详细设计。

## 跨仓库调用链

1. 分别记录源码入口和解析后的 Git 根，以及 Git 根的分支、HEAD、staged/unstaged/untracked 状态。
2. 从发送、解析、传递、消费、反馈和异常路径核对通信两端，不凭一侧命名判断协议行为。
3. 区分当前生产调用、测试专用入口、未调用接口、目标设计和历史实现。
4. CUBE 任务默认只对 `D:\CUBE` 授权写入；外部仓库没有明确授权时保持只读。
5. 外部仓库发生并行变化时，重新记录提交和工作区状态；旧核对结论不得无条件沿用。

## 任务启动检查

- 单仓库任务：运行 CUBE 上下文快照并读取命中的业务 reference。
- 跨仓库任务：在快照脚本中显式传入所有 `-RelatedRepoPath`，然后分别确认源码编码、构建入口和 Git 边界。
- 架构或“全部方案”任务：先列完整对象清单和缺失证据，再写结论；不得从最近讨论的几个模块向外推断整体工程。
