# 故障码治理、历史兼容和售后资料

## 权威顺序

故障码事实按以下顺序核对：

1. 用户对编号、保留/取消和版本兼容的最新决定。
2. CPU2 枚举、实际调用点、日志、最终置错、停机和恢复路径。
3. CPU3 兼容枚举、本机扩展码、共享寄存器消费和显示。
4. 当前程序故障码清单、统一工作簿和协议记录。
5. 一代设备、旧 CPU2 版本和旧协议的历史表。

文档与源码冲突时，先记录差异并确认真实运行行为；不要按旧表批量反改源码。

## 状态分类

每个编号明确标为以下之一：

- **使用中**：当前固件能够主动产生。
- **预留**：当前不主动产生，但为已确认的兼容或未来用途保留。
- **仅历史保留**：只用于解释旧固件、旧设备或现场日志。
- **取消**：不进入当前表，但旧编号仍永久冻结。

历史、预留和取消编号都不得复用为其它含义。删除枚举前先证明没有调用，并把旧编号保留在对应固件版本的历史表。

## 一代与二代编号

- “一代类别 + 10、相同子码”是优先映射规则，不是机械强制规则。
- 语义、责任域和现场处理相同才继承子码；二代新增责任域使用新类别。
- 一代已有子码不能改成完全不同的二代含义；扩展子码从历史最大值后安排。
- 最终以主责任模块、恢复动作和售后处理方式为准，不为了编号相似把通信、硬件和测量流程混为一类。

规划重编号时先形成迁移表：旧编号、旧含义、新编号、新责任域、状态、历史对应、拆分/合并、兼容影响和用户决定。用户要求先规划时，不修改枚举、工作簿和协议版本。

## 共享码与 CPU3 本机码

- CPU2 产生并由 CPU3消费的故障码属于共享契约；两端数值和语义必须一致。
- CPU3 自己检测到且不由 CPU2发布的错误单独列为 CPU3 本机码，不并入共享数量。
- 当前清单、统一表和说明必须分别统计：非故障状态、共享故障、CPU3 本机故障、使用中和预留/历史数量。
- 共享码数值或语义变化要评估 `DEVICE_PROTOCOL_VERSION`；单纯 CPU3 本机码变化不自动改变共享协议版本。

## 实现闭环

新增、删除、拆分或重编号时检查完整链路：

1. CPU2/CPU3 定义和值。
2. 所有产生和返回调用点。
3. `ErrorLog_GetCodeName()`、原因和责任域映射。
4. 重试、最终置错、停机和自动恢复分类。
5. CPU2→CPU3 共享传递、本机码边界和未知码兜底。
6. CPU3 状态页、菜单、中文长度和字库。
7. 统一工作簿、当前清单、历史表、协议记录和版本资料。
8. 故障注入、双端显示、日志、恢复和兼容性验证。

只改枚举或工作簿不算完成；批量替换通用错误码前逐调用点确认真实语义，避免改变返回值、重试和恢复行为。

## 工作簿和售后语言

- 面向交付的统一表与内部治理资料分开；不要把内部枚举名、十六进制迁移细节和未批准推测放入售后表。
- 编辑 `.xlsx` 时同时使用电子表格技能，渲染检查合并单元格、边框、列宽、换行和截断。
- 售后表至少包含：显示编号、故障名称、故障说明、可能原因、现场检查/处理、状态和适用固件版本。
- “故障说明”描述设备看到的现象和停止原因；“故障原因”按硬件/机构、设置/操作、运行环境、数据/软件分类。
- 避免使用函数、变量、DMA状态等编程术语；确需技术定位时放入内部治理表。
- 预留码明确写“当前设备不会主动报出”，历史码写清适用代次或 CPU2 固件版本。

## 版本和验证

- 故障码共享数值整体重编号属于不兼容共享协议变化：同步提升 `DEVICE_PROTOCOL_VERSION`，固件通常按新协议能力升 `MINOR`；不因协议不兼容自动升 `MAJOR`。
- 只有参数存储不兼容、升级会清参数或用户明确要求时才升固件 `MAJOR`。
- 验证至少覆盖：唯一性、两端数值一致、名称/原因覆盖、调用点状态、CPU3显示、字库、工作簿数量、历史编号冻结、文档链接和双端构建。
- 真实故障注入未执行时，明确列为发布残余风险，不用静态契约替代现场验证。
