## 构建流程

- 构建、静态检查、产物哈希和现场/台架证据按 `validation-evidence.md` 记录，并绑定最终源码或暂存区指纹；最终源晚于证据时必须重跑受影响链路。
- 遵循仓库构建文档：`D:\CUBE\docs\00_构建与版本\CPU2构建说明.md` 和 `D:\CUBE\docs\00_构建与版本\CPU3构建说明.md`。
- 修改代码后使用文档里的单独子工程构建目录，不使用临时检查目录。
- CPU2 首次配置或 CMake 配置变化时运行：`cmake -S LTD_MAIN_CPU2 -B build/LTD_MAIN_CPU2 -G Ninja "-DCMAKE_TOOLCHAIN_FILE=D:/CUBE/cmake/toolchain-arm-none-eabi.cmake" -DCMAKE_BUILD_TYPE=Debug`。
- CPU2 编译运行：`cmake --build build\LTD_MAIN_CPU2`。
- CPU3 首次配置或 CMake 配置变化时运行：`cmake -S LTD_DISPLAY_CPU3 -B build/LTD_DISPLAY_CPU3 -G Ninja "-DCMAKE_TOOLCHAIN_FILE=D:/CUBE/cmake/toolchain-arm-none-eabi.cmake" -DCMAKE_BUILD_TYPE=Debug`。
- CPU3 编译运行：`cmake --build build\LTD_DISPLAY_CPU3`。
- CPU2 输出目录：`D:\CUBE\build\LTD_MAIN_CPU2`。
- CPU3 输出目录：`D:\CUBE\build\LTD_DISPLAY_CPU3`。
- 不创建 `build\_check_cpu2` 之类临时目录。
- 保留固定名 `.hex` 和带版本号 `.hex`，不要把构建产物移动到源码目录。

## 版本升级规则

- 判断兼容范围前区分已发布现场版本、已提交未发布版本和仅工作区中间格式；未发布中间格式不自动形成永久兼容义务。
- 正常修改需求不在实现阶段主动升固件版本；先评估版本影响并记录需要提交前处理的事项。
- 当用户要求提交、amend、暂存发布、整理发布资料或明确要求升版时，再按最终 diff 统一升级受影响固件版本，并同步版本资料。
- 每次提交会改变固件行为、构建产物、协议行为、参数、显示行为或用户可见逻辑时，提交前必须统一升级受影响固件版本。
- CPU2 版本文件：`D:\CUBE\LTD_MAIN_CPU2\Application\Inc\app_version.h`。
- CPU3 版本文件：`D:\CUBE\LTD_DISPLAY_CPU3\Application\app_version.h`。
- 版本编码格式：`0xMMmmppbb`，显示为 `V<major>.<minor>.<patch>.<build>`。
- 固件版本和 `DEVICE_PROTOCOL_VERSION` 是两套独立判断：`DEVICE_PROTOCOL_VERSION` 覆盖 CPU2/CPU3 共享命令、共享寄存器、共享状态、共享参数语义和共享结构体契约；CPU3 对外 LTD 标准 Modbus 的共享区直接使用同一契约，也随该版本同步。固件版本覆盖本 CPU 固件行为和对外可见行为。
- “不升级 `DEVICE_PROTOCOL_VERSION`”不等于“不升级固件版本”。外部 DSM、SI、Wartsila 等协议适配层，或 LTD 的 CPU3 本机高地址段/非共享行为发生状态翻译、寄存器响应、异常码、命令拦截或兼容占位变化时，只要改变 CPU3 对外行为，提交前仍需升级 CPU3 固件版本。
- 除 LTD 标准 Modbus 共享区外，只影响外部适配层且不改 CPU2/CPU3 共享协议时，保持 `DEVICE_PROTOCOL_VERSION` 不变；提交前仍按影响范围升级对应 CPU 固件版本。LTD 的 CPU3 本机 `0x7000` 高地址段按 CPU3 本机对外字段单独判断。
- 普通小改动升 `BUILD`。
- 修复 bug 或明显行为错误时升 `PATCH`，并重置 `BUILD` 为 0。
- 新功能、新命令、新参数、新菜单、新协议字段或功能级显示新增时升 `MINOR`，并重置 `PATCH/BUILD` 为 0。
- CPU2/CPU3 共享协议不兼容、外部协议不兼容、故障码整体重编号或其它功能级不兼容行为，使用对应协议版本/严格兼容检查拦截，固件通常升 `MINOR`，不因“协议不兼容”自动升 `MAJOR`。
- 只有参数存储不兼容、升级会恢复出厂/清除现场参数、无法可靠迁移旧存储，或用户明确要求大版本发布时，固件才升 `MAJOR`。
- 参数存储版本增加但能够完整迁移、保留现场参数时，按功能影响升 `MINOR`，并记录迁移路径和回滚风险。
- 只改文档、注释、格式或不影响固件输出的本地工具时，不升级固件版本，除非用户明确要求。
- CPU2 和 CPU3 都受影响时，两边版本都要升级；只影响一边时只升对应一边。
- 升级版本后，在最终回复和提交信息里说明旧版本和新版本；未到提交/发布阶段时，只说明版本影响尚未处理。

## 版本脚本和 CHANGELOG

- 只有在提交/发布阶段或用户明确要求升版时，才调用 `bump_version.py`。
- 使用 `py tools\bump_version.py --cpu2|--cpu3|--both build|patch|minor|major` 执行版本升级。
- 只有明确需要指定精确版本时，才使用 `py tools\bump_version.py --cpu2|--cpu3|--both set V<major>.<minor>.<patch>.<build>`。
- 升级版本时传入简洁中文 `--note`，说明升级原因，例如 `--note "新增CPU2/CPU3版本兼容检查"`。
- 版本升级应通过 `bump_version.py` 自动更新 `D:\CUBE\CHANGELOG.md`；如使用 `--no-changelog`，必须说明原因。
- 每次真实版本升级后，`CHANGELOG.md` 要和受影响版本头一起进入同一提交。
- `CHANGELOG.md` 的升级记录必须和 Git 提交信息同等详细，不能只保留脚本自动生成的简短摘要。
- 提交前必须把 `CHANGELOG.md` 中对应版本记录补齐为和提交信息一致的结构：版本、兼容性、本次修改、验证。
- 涉及 CPU2 参数存储、`DEVICE_PARAM_VERSION`、`DeviceParameters` 结构大小、参数默认值或旧存储兼容性时，`CHANGELOG.md` 必须维护“CPU2 程序版本与参数存储版本”对照；每个 CPU2 程序版本都要能看到对应 `DEVICE_PARAM_VERSION`，存储版本升级的版本条目必须重点写明是否恢复出厂参数、哪些旧版本升级会触发、触发原因、现场升级前备份/记录参数和升级后重新下发/复核范围。
- `CHANGELOG.md` 二级标题必须包含日期和本次具体改动内容概括，格式为 `## YYYY-MM-DD - 本次具体改动内容概括`；标题概括要写真实改动对象和动作，不能只写日期，也不能写“版本更新”“改动记录”“问题修复”等空泛词。
- `CHANGELOG.md` 按时间从旧到新排列，最新版本记录追加在文件末尾；用户特别指出顺序时，以“最新放最后”为准。

## 改动与测试方案

- 每次真实版本升级后，必须同步整理一份详细“改动与测试方案”Markdown 文件；普通修改阶段无需提前创建。
- 默认放在 `D:\CUBE\docs\00_构建与版本\版本改动与测试\`。
- 目录不存在时按中文目录名创建。
- 文件名使用中文可读格式，例如 `<日期>_<CPU2版本>_<CPU3版本>_<简述>_改动与测试方案.md`；只影响单 CPU 时只写对应版本。
- 方案必须写清：版本变化、协议版本/兼容性、详细改动点、影响范围、需要重点测试的点、每个测试点的准备条件、具体步骤、预期结果、通过标准、回归范围、未验证风险和已执行验证结果。
- 方案要覆盖本次提交里的全部用户可见行为、协议语义和参数解释变化；即使寄存器地址不变，字段 signedness、单位、范围、默认值或外部解释口径变化也必须写入兼容性、影响范围和测试点。
- 每份涉及 CPU2 参数或协议的方案必须包含“参数存储兼容性”信息：CPU2 `DEVICE_PARAM_VERSION` 旧值 -> 新值、`DeviceParameters` / `struct_size` 是否变化、升级是否会恢复出厂参数、从哪些旧版本升级会清、现场升级前后动作；如果不清参数但复用保留字段或改变参数语义，也要说明旧存储补默认值或归一化方式。
- CPU2 参数存储版本或清参数规则变化时，同步更新 `D:\CUBE\docs\00_构建与版本\CPU2参数存储升级清单.md` 和相关 README 索引。
- 如果本次升版只为文档/构建产物整理且没有运行现场测试，也要在方案中明确“未实测项”和后续联调建议，不能用空泛的“待测试”代替。

## 程序流程资料本机同步

- 升版、发布、提交或 amend 前，按最终 diff 判断是否改变入口、命令分发、状态机、关键判断、循环/闭环、异常出口、通信链路、显示/参数交互或结果上报。
- 命中任一项时，更新 `docs/00_程序流程导航/` 对应 CPU2/CPU3 HTML、业务级 SVG、函数索引和跨页导航；相关生成/校验源在 `tools/` 同步更新。
- 如果确认不影响流程，版本方案和最终回复写明“不更新程序流程图”的具体理由，不能只写“不涉及”。
- 程序流程导航和 `tools/` 只在本机同步、生成和验证，不进入 Git 暂存区；不得用 `git add -f` 绕过仓库边界。

## 可执行级写作标准

“改动与测试方案”必须能让未参与开发的人仅凭文档完成代码复核、台架验证和提交范围核对。不得只写“优化通信”“修复显示”“完善协议”等主题级摘要。

### 1. 以最终差异为唯一范围依据

- 创建或更新文档前，读取最终工作区 diff；提交或 amend 阶段优先读取暂存区 diff，并用 `git diff --cached --name-status` 固化变更文件范围。
- 对照 `git show`、版本号、`CHANGELOG.md`、协议记录和流程文档，确认没有把旧提交、未纳入本次提交的工作区改动或对话设想写成本次已完成内容。
- 按“一个可独立评审、独立验证的行为变化”为一个小改动点拆分；条目数量由最终 diff 决定，不合并漏项，也不为达到固定数量而拆分凑数。
- CPU2、CPU3 通信桥接、界面、DSM、SI、Wartsila、LTD、构建脚本和流程文档等不同链路分别列项；跨 CPU 或跨协议的同一闭环要同时写清入口、传递、消费、反馈和异常出口。

### 2. 每个小改动点的五项必填内容

每个小改动点至少包含以下字段，字段可以写成小标题或紧凑表格，但不得缺项：

1. **源码位置**：相对路径、函数/结构体/宏/脚本入口；必要时列出调用方和消费方，不能只写文件名。
2. **改前问题**：旧逻辑在什么条件下产生什么错误、缺口或风险；说明触发条件和可观察现象。
3. **具体改法**：写清新增或修改的判断条件、变量、状态、返回值、错误码、超时、调用顺序、单位、默认值或数据流；不要只写“增加校验”“完善处理”。
4. **必查边界**：列出正常、异常、临界值、重入/并发、超时、断链、重复包、空值、最大值、旧版本兼容或恢复路径中与该点相关的检查项；不适用的边界明确写“不适用及原因”。
5. **通过标准**：给出可观测、可判定的结果，例如返回码、状态值、寄存器值、界面文本、日志、时序上限、构建结果或“不再出现”的明确现象；不得写“功能正常”。

推荐单项格式：

```markdown
### N. <小改动标题>

- 源码位置：`<path>` 的 `<symbol>`；调用/消费链路为 `<A -> B -> C>`。
- 改前问题：<触发条件、旧行为、现场现象或风险>。
- 具体改法：<精确到条件、数据、状态、错误出口或调用顺序的实现说明>。
- 必查边界：<正常/异常/临界/兼容/恢复检查项>。
- 通过标准：<可观测且可判定的结果>。
```

### 3. 测试内容必须可直接执行

- 保留已有且仍有效的测试矩阵、复杂场景步骤和回归范围；更新文档时不能用新摘要覆盖或删除原有有效用例。
- 每个测试用例写明：用例编号、关联改动点、前置条件、输入/操作步骤、观测位置、预期结果、通过标准、执行状态和证据。
- 复杂闭环按时间顺序写步骤，包括上电、断链、恢复、重试、重复命令、队列积压、CPU2/CPU3 状态变化和外部主机响应；不能只列最终结果。
- 协议测试必须给出关键请求字段和响应字段；适合时提供完整 golden frame、异常码和寄存器值，并区分标准格式与项目兼容格式。
- UI 测试写清进入路径、前置状态、每行显示、刷新/退出行为及异常状态；涉及中文时增加字库、长度和乱码检查。
- 未执行的现场或台架测试单独列为“未验证项”，说明未执行原因、潜在风险、建议环境和后续动作；不得伪装成已通过。

### 4. 构建、变更文件和提交状态必须真实

- 记录最后一次与最终代码一致的 clean-first 构建：固件、命令、执行时间、结果、警告/错误摘要和产物；增量构建不能冒充 clean-first 构建。
- 如果最终代码在 clean-first 构建后又发生影响编译的修改，必须重新构建并刷新时间和结果。
- 按 CPU2 源码、CPU3 源码、共享协议、版本与日志、正式测试文档分类列出 Git 提交文件，并与准备提交的文件清单逐项核对。
- `tools/` 和 `docs/00_程序流程导航/` 单独列为“本机已同步但不提交”；它们需要与最终代码一致，但不得出现在 `git diff --cached --name-status` 中，也不得使用 `git add -f`。
- 文档中的提交状态必须和当前阶段一致：提交前写“本文件随本次提交纳入，提交哈希以 Git 记录为准”；提交或 amend 后如文档需要记录提交，刷新为真实分支、提交标题和哈希。删除已经过期的“尚未提交”“待补文件”或旧构建时间说明。
- 提交前再次对照暂存区 diff；文档提到但未暂存、已暂存但文档未覆盖、版本号/文件名不一致都视为未完成。

### 5. 复核和回归不得省略

- 单列“回归范围”，覆盖未直接修改但可能受影响的相邻命令、状态、协议、菜单、参数、错误恢复和启动流程。
- 单列“风险与未验证项”，区分已由代码检查关闭的风险、已由自动检查覆盖的风险和必须现场验证的残余风险。
- 单列“提交前检查清单”，至少检查版本头、`DEVICE_PROTOCOL_VERSION`、参数存储版本、`CHANGELOG.md`、协议变更记录、流程 HTML/SVG、变更文件、构建结果、`git diff --check` 和仓库版本门禁；不适用项写明理由。
- 文档完成后搜索“待补”“待确认”“尚未提交”“功能正常”“优化”“完善”等模糊或过期措辞，逐项改成事实、动作、检查方法或明确风险。

## 推荐文档结构

版本改动与测试方案默认按以下顺序组织；已有文档结构不同但信息完整时可保留，不为套模板破坏有效内容：

1. 文档目的和适用版本。
2. 版本、共享协议版本和参数存储兼容性。
3. 本次提交范围与分类变更文件。
4. 逐小点详细改动清单。
5. 跨模块/跨 CPU 数据流和异常闭环。
6. 测试环境、工具、固件和前置条件。
7. 可执行测试矩阵。
8. 复杂场景分步验证。
9. 回归范围。
10. 已执行的静态检查、脚本和 clean-first 构建证据。
11. 风险与未验证项。
12. 提交前检查清单和真实提交状态。

## 提交流程中的版本判断

- 不依赖脚本判断语义版本级别。
- Codex 必须先看最终 diff 或暂存区 diff，判断影响 CPU2、CPU3 还是两者，以及应升 `build`、`patch`、`minor` 还是 `major`，再调用 `bump_version.py` 执行。
- 用户要求提交当前改动时，版本判断属于提交流程的一部分：检查 diff、说明升级级别和理由、运行版本升级、暂存版本头和日志、再验证。
- 如果不确定是 `minor` 还是 `major`，先判断旧存储能否迁移、是否会清现场参数；没有存储不兼容证据时不自动升 `major`。只有存储结论或产品发布口径仍不明确且会实质影响交付时，提交前询问用户。
- 如果版本升级可能恢复出厂参数，先按不兼容存储变化处理，明确提示用户和现场升级动作；不要只写“参数结构变化”而漏掉“会清参数”。
- 固件相关提交前，如果存在脚本，运行 `py tools\check_version_bumped.py`。
