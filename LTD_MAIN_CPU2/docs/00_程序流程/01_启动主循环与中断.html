3.1 上电启动到主循环总流程

这张图描述 CPU2 从复位进入 main() 到永久主循环的真实顺序。关键点是时钟配置有明确错误出口，业务初始化前会先停止电机，最终所有后台逻辑都落到应用主循环。

源码依据Core/Src/main.c:73-129：HAL、时钟、外设、MotorCtrl_BootSafeStop()、App_Init()、App_MainLoop() 的启动顺序。
异常出口Core/Src/main.c:137-176 时钟配置失败直接进入 Error_Handler()；多数字外设初始化函数内部也沿用同类错误出口。
已整理问题点启动期错误最终是关中断并死循环，缺少持久化故障记录、通信上报和可恢复策略；现场只能表现为设备停止响应或复位。

3.2 应用初始化与上电默认命令流程

这张图展开 App_Init() 的业务含义：它不仅初始化模块，还决定上电默认命令是否能自动进入主循环。AO 或电机初始化失败不会立即停止初始化，但会保留启动错误码并阻止默认命令继续下发。

源码依据Application/Src/app_main.c:97-137：参数、编码器、HART、称重、Host 通信、继电器、AO 输出服务、电机、故障信息和传感器识别初始化；AO/电机启动错误会在故障信息初始化后恢复保留。
关键分支上电默认命令只有在启动初始化成功，并且编码器位置源可用时才转换为正式测量命令；否则只保留启动错误码或编码器超时状态。
已整理问题点AO 输出改由 AoOutput_Init() 按 AoOutputEnable 控制；未使能时不访问 AD5421，初始化失败时保留错误码。初始化阶段仍强制 zero_point_status = 1，会上电后要求重新回零。

3.3 应用主循环调度优先级流程

主循环不是简单顺序执行，而是每轮只处理一个最高优先级分支：串口原始命令优先于正式命令，正式命令优先于故障恢复，故障恢复优先于空闲错误兜底。

源码依据Application/Src/app_main.c:151-216：每轮后台轮询、命令优先级、故障恢复、全局错误兜底和统一延时。
命令执行包装Application/Src/app_main.c:36-49：执行正式命令前写当前命令，命令完成后更新故障恢复并清空当前命令。
已整理问题点测量命令内部如果长时间阻塞，主循环的后台轮询、延迟保存和恢复判断都会被延后；串口原始命令进入后会取消正在等待的自动恢复。

3.4 中断与通信入口流程

这张图把中断入口按业务来源展开：调试命令串口只置位主循环标志；HART、称重和 Host 通信在中断内直接处理部分协议/帧数据；发送完成回调负责把半双工接口切回接收。

源码依据Core/Src/stm32f4xx_it.c:226-420：TIM4、USART1、USART2、UART4、UART5 的 IDLE/DMA 中断处理；Core/Src/usart.c:70-93：发送完成后恢复接收。
状态回写USART1 写 new_command_ready，UART4 更新称重状态，USART2 调用 HART 协议处理并启动应答，UART5 进入 Host 通信处理。
已整理问题点USART1 中断内有打印，USART2 和 UART5 中断内直接做协议处理，执行时间不可控；UART5 接收中断里重开 DMA 的语句被注释，若无应答路径可能存在接收恢复风险。
