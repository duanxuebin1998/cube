2. 功能域业务总览 SVG

CPU3 主循环是显示端的调度中心。它不是 RTOS 任务，而是单个 while(1) 中按固定优先级轮询不同业务。

3.1 上电初始化到主循环

把 main() 中的 CubeMX 外设初始化和 App_Init 的应用初始化串起来，区分硬件层初始化和 CPU3 应用状态初始化。

硬件初始化Core/Src/main.c:70-116 中 main() 依次初始化 GPIO/DMA/UART/SPI/TIM/CRC/IWDG 后调用 App_Init。
应用初始化Application/app_main.c:367-381 显示 Logo、初始化 RTC、从 FRAM 读取 CPU3 本机参数、重配串口、初始化 DSM 通信。
错误出口Core/Src/main.c:185-193 Error_Handler 关闭中断并进入 while(1)。

3.2 App_MainLoop 调度优先级

主循环先消化串口重配置和显示输入，再处理外部 COM 帧；只有本轮没有外部工作时才访问 CPU2，避免协议响应被 CPU2 轮询阻塞。

调度顺序Application/app_main.c:387-555 中依次调用串口重配、Display_Task、COM1/COM2/COM3、空闲 CPU2 轮询。
空闲轮询Application/app_main.c:550-555 did_work 为 0 才执行 PollingInputData 和 10ms 延时。
协议分发Application/app_main.c:342-360 根据端口参数选择 DSM/Wartsila/SI7000/LTD 协议处理函数。

4. 问题点与优化建议

1. CPU2 轮询是同步阻塞等待响应

CPU2_CombinatePackage_Send 内部等待 wait_response，超时时间注释写 100ms 但判断为 1000 tick；轮询期间外部 COM 和显示刷新都会被主循环阻塞。

建议：把 CPU2 轮询改成非阻塞状态机，或至少将超时常量、注释和实际 tick 对齐，并统计超时次数。

Communication/internal/main_board_modbus/cpu2_communicate.c:300-352

2. 主循环优先级会让 CPU2 数据刷新受外部协议流量影响

只要 COM1/2/3 持续有帧，本轮 did_work 就不为 0，CPU2 轮询会一直后移，显示数据可能滞后。

建议：增加 CPU2 轮询最大间隔保护，或把 CPU2 状态刷新拆成固定节拍任务。

Application/app_main.c:387-555

3. 串口重配依赖三路端口完全空闲

g_cpu3_uart_reinit_pending 在任一端口收发忙或 pending 时直接返回，如果端口持续有流量，重配可能长期不生效。

建议：显示重配等待状态，增加超时或维护窗口机制，避免用户以为参数已应用。

Application/app_main.c:182-221

4. 启动延时固定 1000ms

App_Init 最后固定 HAL_Delay(1000)，没有和外设实际就绪状态绑定。

建议：如果现场启动时间敏感，可以改为检测显示/串口/CPU2 首次响应条件。

Application/app_main.c:379-381
