3.3 写保持寄存器转参数下发

Response16 不是简单写数组：它先校验数量和 byte count，再按地址段判定可写范围。合法写入后，第 6 段当前只作为协议占位回成功，其它地址段会解析为设备参数并尝试同步 CPU2。

4. 问题点与优化建议

1. Response05 在外部协议处理路径中同步下发 CPU2

线圈命令会直接调用 CPU2_CombinatePackage_Send，外部 COM 响应等待 CPU2 同步写完成，可能导致上位机响应时间不可控。

建议：将 CPU2 指令下发改为主循环命令队列，DSM 先回接收确认，再异步下发 CPU2。

DSM_SlaveModbus_modbus2.c:834-914

2. Response16 也可能在外部协议路径同步下发 CPU2 参数

写保持寄存器成功后会进入 UpdateDeviceParamsFromLegacyRegs，解析参数并尝试同步 CPU2；外部 COM 响应时间会受到 CPU2 内部通信状态影响。

建议：把参数同步拆成异步队列或至少为每次 0x10 写入记录 CPU2 下发耗时和失败原因。

DSM_SlaveModbus_modbus2.c:1001-1058; DSM_DataAnalysis_modbus2.c:170

3. 广播地址 0 会进入处理并可能回包

DSM_CommunicationProcess 接受 rcvbuff[0] == 0，但后续 Response 函数统一用 SlaveAddress 组帧，可能违反 Modbus 广播不响应习惯。

建议：明确 DSM 广播口径；如按标准广播，应执行写动作但 tx_len=0。

DSM_communication.c:55-63

4. 部分无效命令是业务口径而非地址不存在

例如 SET_ZEROCIRCLE/SET_ZEROANGLE 映射为 INVALID_CMD，地址存在但返回数据异常，现场联调需要文档化。

建议：在协议说明表中标记“占位成功/无效命令/下发 CPU2”的三类动作。

DSM_SlaveModbus_modbus2.c:750-807

5. 第 6 段写保持寄存器当前只做协议占位

0x300 段通过 IsHoldingRegisterZeroSegment 判定后回正常响应，但注释明确不落参数、不下发 CPU2，容易被上位机误认为参数已生效。

建议：协议表中单独标记 0x300 段为占位成功，并在联调时验证上位机是否依赖这些参数。

DSM_SlaveModbus_modbus2.c:980-1018

6. 03/04 读前全量刷新寄存器

03 读前 SystemParameterSet、04 读前 Input_Write 全量写寄存器数组，读频繁时 CPU3 主循环负担较大。

建议：可按脏标志或固定节拍刷新缓存，读请求只做拷贝。

DSM_communication.c:70-79
